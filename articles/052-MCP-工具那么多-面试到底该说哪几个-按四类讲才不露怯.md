# MCP 工具那么多，面试到底该说哪几个？按四类讲才不露怯

<!-- growth-hook:v1 -->
“说说你知道的 MCP 工具”——这题看着像送分，其实是分水岭。背一两个工具名字谁都会，但面试官在听的是：你能不能把零散的工具归成几类，并说清它们各自补上了 Agent 的哪块外部能力。

## 面试官为什么爱问这题

这是一道基础题，出现频次不高，但它在探你对生态的感知是不是停留在名词层面。很多人准备这题就是背一串工具名，面试官其实明说了不要求死记硬背——真正想听的是你能不能把这些工具归成几类，并说清为什么偏偏是这几类受欢迎。答案指向一个很朴素的判断：热门工具覆盖的正是 Agent 最常见的外部能力需求。能与网页交互、能读写数据、能操作文件和代码、能检索知识，这四件事是绝大多数 Agent 任务都会碰到的。能说出这个"为什么"，比报十个名字更说明你理解生态。前面讲过 MCP 的定位、Server 建设、接入和协议结构，这一篇从具体工具类别切入，把前面讲的能力类型落到真实的工具形态上。

## 一句话先给结论

**受关注的 MCP 工具通常集中在四类：浏览器自动化类（比如 Playwright）、数据与后端类（比如数据库、Supabase 一类服务）、文件与代码类（本地文件系统、代码库）、搜索与知识类（网页搜索、知识库检索）。它们受欢迎的原因不是名字响亮，而是覆盖了 Agent 最常见的外部能力需求——让模型能操作网页、读写数据、处理文件代码、获取知识。面试时按类别讲、说清每类解决什么需求，比背一串名字有价值。**

## 核心原理：四类工具对应四类能力需求

### 为什么是这四类

把热门工具归成四类，不是为了分类而分类，每一类都对应 Agent 的一类高频外部需求。

**浏览器自动化类，比如 Playwright。** Agent 要做很多"像人一样操作网页"的事——打开页面、填表、点击、抓取动态渲染的内容。这类工具让模型能驱动浏览器完成交互，覆盖的是"和 Web 界面打交道"的需求。它和简单的网页抓取不同：抓取拿的是静态内容，浏览器自动化能处理需要交互、需要 JavaScript 渲染的场景。

**数据与后端类，比如数据库、Supabase 一类服务。** Agent 经常要读写业务数据——查订单、更新记录、调后端接口。这类工具把数据层和后端能力暴露给模型，覆盖的是"和结构化的业务数据打交道"的需求。它是 Agent 从"能聊天"走向"能办事"的关键一环。

**文件与代码类，比如本地文件系统、代码库。** 读写文件、检索和修改代码，是编码类 Agent 和文档处理类 Agent 的日常工作。这类工具让模型能操作本地文件系统和代码仓库，覆盖的是"和文件、代码打交道"的需求。

**搜索与知识类，比如网页搜索、知识库检索。** Agent 要回答问题时经常需要外部信息——最新的网页内容、企业内部的文档。这类工具覆盖的是"获取外部知识"的需求，和前面讲过的 RAG 关系密切：检索工具把知识找出来，供 Agent 使用。

| 工具类别 | 典型代表 | 覆盖的需求 |
| --- | --- | --- |
| 浏览器自动化 | Playwright | 操作网页、交互、动态内容 |
| 数据与后端 | 数据库、Supabase 一类服务 | 读写业务数据、调后端能力 |
| 文件与代码 | 本地文件系统、代码库 | 文件读写、代码检索修改 |
| 搜索与知识 | 网页搜索、知识库检索 | 获取外部信息与知识 |

### 从"需求"反推，而不是背名字

这题的答法很重要。如果面试官问"有哪些热门工具"，直接报名字，答得好也只是背得好；更好的答法是先说"热门工具大致分四类，分别对应 Agent 的四类高频需求"，再每类举一两个例子。这样即使某个具体名字你记不全，也不影响答案成立——因为考查点是"对生态有基本了解"，不是"能否背全列表"。

这个答法还有个好处：它经得起追问。面试官顺着问"为什么这类工具火"，你能立刻接到"因为 Agent 办事绕不开这个需求"；如果只会报名字，一追问就露怯。前面讲 MCP 定位时说过它像统一插口，这里的四类工具就是插在不同需求上的四类常见能力，协议统一了接入方式，工具生态则填满了具体的需求场景。

还有一点值得提：这四类工具的边界不是绝对的，一个工具可能横跨两类。比如一个知识库检索工具，既算搜索与知识类，也涉及数据后端。分类是为了把需求讲清楚，不是为了给工具贴死标签。面试时用分类组织答案，但别被分类框住——真要说明某个工具，讲清它解决什么需求就够了。

## 工程实践：选工具时看什么

知道了类别，落到实际选用，有几件事比"哪个最火"更重要。先看一张检查表：

| 检查项 | 要问自己的问题 | 忽略的后果 |
| --- | --- | --- |
| 能力对不对需求 | Agent 到底要干什么？ | 挑了热门工具却用不上 |
| 能力边界清不清 | 描述清楚、粒度合适、错误处理好吗？ | 接进来模型也用不好 |
| 接入与安全边界 | 鉴权成本、所需权限、可访问范围？ | 权限过大或接入成本失控 |

**看能力是否对得上需求。** 先明确 Agent 要干什么，再找对应类别的工具，而不是先挑一个热门工具再看它能干嘛。需求驱动选型，才能选对。

**看暴露的能力边界是否清晰。** 前面讲 Server 建设时说过，能力边界和错误处理最容易被忽略。选现成工具时同样要看：它暴露的工具描述清不清楚、粒度合不合适、错误处理好不好。一个描述含糊的工具，接进来模型也用不好。

**看接入成本和安全边界。** 工具的接入和鉴权成本、它需要什么权限、能访问什么范围，这些在选用时就要评估。特别是能操作文件、执行代码、访问网络的工具，权限边界要格外注意——前面讲接入可控性时说过，MCP 的权限检查要和沙箱配合，这里选工具时就要把这一层考虑进去。

```python
# 伪代码：按需求类别筛选可用工具，再校验权限边界
def pick_tools(need, catalog, policy):
    candidates = catalog.by_category(need.category)   # 按需求类别找候选
    usable = [t for t in candidates if policy.allow(t)]  # 过权限边界
    return usable

# need 是当前任务需求，catalog 是已注册工具目录，policy 是权限策略
# 业务侧实现：按需求找候选、按权限过滤，避免把无权工具交给模型
```

要点：先按需求类别缩小范围，再按权限过滤，最后才把可用工具交给模型。`need`、`catalog`、`policy`、`by_category`、`allow` 都是业务侧实现。这个"先需求、再权限"的顺序，和前面讲接入时"先发现、再过控制闸"是一致的思路。

## 追问逐条作答

### 追问一：这些工具为什么受欢迎？

因为覆盖了 Agent 最常见的外部能力需求。浏览器自动化解决"操作网页"，数据与后端解决"读写业务数据"，文件与代码解决"处理文件和代码"，搜索与知识解决"获取外部信息"。这四类需求几乎是任何实用 Agent 都绕不开的，能满足它们的工具自然受关注。所以"火"的根本原因是需求普遍，不是营销。

### 追问二：浏览器自动化和数据后端类，哪个更常用？

看任务类型，没有绝对答案。做数据采集、网页操作、UI 测试类任务，浏览器自动化是刚需；做业务系统助手、需要处理订单和客户数据的任务，数据后端类更常用。很多实际系统两类都要用。面试时不给绝对答案，而是说"看 Agent 要办什么事"，反而更稳。

### 追问三：工具越多越好吗？

不是。前面讲工具治理时提过，工具一多，模型选错的概率就上去了，定义本身也吃上下文。选用时按需求挑够用的，描述清楚、边界明确，比堆一大堆工具更好。经验值：单次决策暴露给模型的工具控制在十几个以内，多了就分组或按需筛选。这个道理对 MCP 工具同样成立。

### 追问四（自补）：现成的 MCP 工具和自己封一个，怎么选？

看能力和可控性。现成工具接入快、生态成熟，通用需求优先用现成的；但如果涉及企业内部系统、有特殊权限要求、或需要精确控制能力边界和错误处理，自己封一个 Server 更可控。前面讲过手写 MCP Server 的流程，就是为这种场景准备的。判断标准是：现成的能不能满足需求、可控性够不够；不够就自己封。

### 追问五（自补）：搜索与知识类工具和 RAG 是什么关系？

关系密切但不等同。搜索与知识类 MCP 工具把"检索网页或知识库"这一个能力按协议暴露出来，供任何 Agent 使用；RAG 是一套更完整的流程，包含切块、检索、重排、生成等多个环节。一个 MCP 检索工具可以是 RAG 流程里"检索"那一环的载体，但它本身不等于整套 RAG。前面讲过 MCP 和 RAG 的边界，这里是同一个区分落到具体工具上。

## 60 秒面试回答模板

> 热门 MCP 工具大致分四类：浏览器自动化类，比如 Playwright，解决操作网页和动态内容；数据与后端类，比如数据库、Supabase 一类服务，解决读写业务数据；文件与代码类，比如本地文件系统、代码库，解决文件和代码处理；搜索与知识类，比如网页搜索、知识库检索，解决获取外部信息。我觉得重要的不是背名字，而是它们覆盖了 Agent 最常见的外部能力需求，所以才受欢迎。实际选工具时，我会先按需求类别缩小范围，再看能力边界清不清、权限和接入成本合不合适，不是越多越好。现成的够用就直接用，涉及内部系统或特殊权限就自己封 Server。

## 加分项

- 按四类组织，并说清每类对应的能力需求，而不是报名字。
- 点出"火的根本原因是需求普遍"，落到为什么层面。
- 选工具时讲"需求驱动 + 权限边界"，呼应前面讲的可控性。
- 主动说工具不是越多越好，给出数量经验值。

## 常见误区

- **只背一串工具名**：说不出类别和需求，一追问就答不上来。
- **把某类产品说成绝对最常用**：不同任务需求不同，给绝对答案容易答偏。
- **认为工具越多越好**：工具多了模型容易选错，也吃上下文，够用就好。
