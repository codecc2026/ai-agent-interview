# 控制大模型应用成本，你会优先从哪些层面下手？

<!-- growth-hook:v1 -->
“成本太高”是第一反应，“换便宜模型”是第一动作——但很多时候贵根本不贵在模型单价，而是链路在烧钱：全量检索、长历史拼接、重复调用、盲目重试。这题要的是分层拆解，不是单一动作。

## 面试官为什么爱问这题

这题考的是成本优化思维，特别是你有没有"成本是设计出来的，不是调价调出来的"这个意识。很多人一提降本就想到换便宜模型，那是模型层这一个维度；真正成本高企的系统，毛病往往在链路设计上——无差别全量检索、过长历史拼接、多次重复调用、失败后盲目重试，这些浪费换模型也救不了。面试官想听你能不能从模型、上下文、检索、流程四层系统性地看问题，并说清"什么时候该先动哪层"。前面聊过 token 与上下文的工程含义、也聊过检索治理，这一篇把这些收束到成本这个贯穿始终的约束上。

## 一句话先给结论

**通常从模型、上下文、检索、流程四层入手：模型层做高低配分层，大任务用强模型、小任务用轻模型；上下文层压缩 Prompt、减少无效历史、控制返回长度；检索层优化召回和重排、减少无意义进窗内容；流程层减少不必要的 LLM 调用次数，能规则化就不要全靠模型。很多系统成本高，不是因为模型太贵，而是链路设计太浪费——无差别全量检索、过长历史拼接、多次重复调用、工具失败后盲目重试，这些才是优先要治的。**

## 核心原理：四层成本模型

### 模型层：分层用模型

不同任务对模型能力的要求不同。大任务、复杂推理用强模型，简单的分类、摘要、格式化用轻模型。把所有任务都压给最贵的模型，是最常见的浪费。分层的做法是按任务难度路由到合适的模型，代价是引入路由判断，见追问一。

### 上下文层：每一 token 都要有用

上下文是成本的直接来源——输入多少 token 就付多少。这一层要做的是压缩 Prompt、减少无效历史、控制返回长度。前面讲记忆分层时说过窗口是昂贵资源、只放高信号上下文，那是体验设计；从成本视角看，同一套做法直接省钱。长历史全量拼接、prompt 里塞满用不上的背景，都是烧钱。

### 检索层：少往窗口里塞没用的

检索的质量直接影响成本。召回太多无关内容塞进窗口，既花了检索的钱，又让模型处理一堆噪声。优化召回和重排，让进窗的内容更精，既提效果又降成本。前面讲混合检索和重排、讲工具多时的上下文治理，本质都包含这层意思。

### 流程层：少调模型，能规则化就别调

成本的大头常常是调用次数。一个流程里反复调模型、每次都全量处理，次数一乘成本就上去了。这一层的原则是：减少不必要的 LLM 调用，能用规则、缓存、确定性逻辑解决的，就别每次都问模型。前面讲工作流 vs Agent 时说过确定性环节用代码，那也是成本思路。

| 层 | 优化动作 | 解决的问题 |
| --- | --- | --- |
| 模型层 | 高低配模型分层、按任务路由 | 所有任务都用贵模型 |
| 上下文层 | 压缩 Prompt、减无效历史、控返回长度 | token 浪费在噪声上 |
| 检索层 | 优化召回与重排、减少无意义进窗 | 无关内容既费钱又扰效果 |
| 流程层 | 减少调用次数、能规则化就别调模型 | 调用次数堆积放大成本 |

### 真正的问题常在链路，不在单价

题库那句"很多系统成本高，不是因为模型太贵，而是链路设计太浪费"是题眼。四种典型浪费值得单独记，用一张表看得更清楚：

| 浪费类型 | 具体表现 | 为什么贵 |
| --- | --- | --- |
| 无差别全量检索 | 不管相不相干都把检索结果全塞进窗口 | 检索和 token 双份浪费，还扰效果 |
| 过长历史拼接 | 每次调用都把全部历史带上 | 输入 token 随轮次不断累积 |
| 多次重复调用 | 同一个结果反复问模型 | 调用次数直接乘上去 |
| 失败后盲目重试 | 失败就重来，不判断该不该重 | 为注定失败的调用持续付费 |

这四种都不是换模型能解决的，得从链路设计上治。

## 工程实践：成本优化的排查顺序

面对"成本太高"，按什么顺序查？一个务实的思路是从最不敏感的层先动。

**先查流程层。** 看调用次数。一次用户请求触发了多少次模型调用、多少次工具调用、有没有重复调用和盲目重试。调用次数是最直接的乘数——单次成本不变，次数翻倍成本就翻倍。这一层往往藏着最大的浪费，且优化不影响单次效果。

**再查上下文层。** 看每次调用带了什么。历史是不是全量拼接、prompt 里有没有大量用不上的内容、返回长度有没有必要那么长。用前面讲过的摘要、滑动窗口、结构化槽等手段压一压。

**然后查检索层。** 看进窗内容的质量。召回是不是太多太杂、重排有没有做、有没有把无关内容也塞进去。

**最后看模型层。** 前面的都做了再看模型选型和分层路由。换模型是最后一步，因为它的影响面最大、可能牵动效果，而前面的优化大多是纯赚。

```python
# 伪代码：一次请求里统计调用次数与 token，定位成本大头
def trace_cost(request):
    calls = []

    def logged_call(name, fn, **kwargs):
        result = fn(**kwargs)                       # 执行一次模型/工具调用
        calls.append({"name": name, "tokens": count_tokens(kwargs)})  # 业务侧统计
        return result

    handle_request(request, call=logged_call)       # 业务侧：把 logged_call 注入链路
    return summarize(calls)                         # 业务侧：汇总各调用的花费

# count_tokens / handle_request / summarize 为业务侧实现
```

要点：把每次调用包一层记录，跑一次请求就能看到钱花在哪一步。这是优化前的必要动作——没数据就优化，容易凭感觉动错地方。变量都是业务侧实现。

## 追问逐条作答

### 追问一：什么时候应该引入模型路由？

当任务类型明显分化、不同任务对模型能力要求差距大时。比如一批请求里既有简单分类又有复杂推理，全用强模型浪费、全用轻模型效果差，这时按任务难度路由到合适模型才有收益。反之，如果你的任务类型单一、难度接近，引入路由只是增加一层判断，收益有限。经验值：先看清任务分布，确认确实存在"简单任务被贵模型处理"的浪费，再上路由；路由本身的判断也要轻量，别为了省模型钱又加一次贵调用。

### 追问二：如何平衡成本和效果？

不要一刀切，分层处理。核心链路、直接影响效果的地方保住质量，别为省钱牺牲；边缘环节、容错空间大的地方大胆优化。做法是建立评测：优化前后用同一批样例测效果，确认成本降了、效果没掉到可接受线以下，再上线。前面讲评测时会专门讲怎么建评测集，这里是同一个思路在成本场景的应用。经验值：优化一次验一次，别一次改太多导致说不清是哪一步掉了效果。

### 追问三：token 成本和工具成本哪个更值得先优化？

看谁占比大，用数据说话，别拍脑袋。先把一次请求的花费拆开——模型 token 花了多少、工具调用（比如外部 API）花了多少。如果 token 占大头，就走上下文和检索层；如果工具成本占大头，就看工具调用次数、有没有缓存和复用。经验值：多数 Agent 应用里 token 和工具成本都随调用次数放大，所以流程层（减少不必要的调用）常常是两者都受益的切入点，可以先动。

### 追问四（自补）：为什么"换便宜模型"通常不该是第一步？

因为它的影响面最大、最可能伤效果，而链路里的浪费是纯损失——去掉浪费不伤任何效果。换模型要重新验证效果、可能牵动整个 prompt 和评测，成本高；而砍掉重复调用、压缩无用历史这些优化，效果不变甚至更好（噪声少了）。所以顺序上先治链路浪费，再看模型。这不是说不换模型，而是它该排在后面。

### 追问五（自补）：重试怎么设才不浪费钱？

要判断该不该重试。只有那些可恢复的失败，比如网络抖动、临时限流，才值得重试；参数错误、权限不足、内容违规这类确定性失败，重试多少次都是白花钱。重试还要有上限和退避，不能失败就立刻重来。更根本的是让工具返回结构化错误，让系统能判断失败类型再决定重试还是换路。前面讲工具调用兜底时提过这些，落到成本视角就是"别为注定失败的调用付钱"。

## 60 秒面试回答模板

> 我从四层入手。模型层做高低配分层，大任务用强模型、小任务用轻模型。上下文层压缩 Prompt、减少无效历史、控制返回长度。检索层优化召回和重排，减少无意义进窗内容。流程层减少不必要的 LLM 调用，能规则化就别全靠模型。但我认为真正的问题常在链路而不是单价：很多系统贵是因为无差别全量检索、过长历史拼接、多次重复调用、工具失败后盲目重试。排查顺序我会从最不敏感的层先动：先查调用次数有没有浪费，再查上下文，再查检索，最后才看模型——换模型影响面最大、可能伤效果，该排后面。平衡成本和效果要靠评测，优化一次验一次，核心链路保质量、边缘环节大胆省。

## 常见误区

- **一提降本就换模型**：链路里的浪费是纯损失，换模型不解决，且可能伤效果。
- **不统计就优化**：没把花费拆到各步骤，凭感觉动容易动错地方。
- **重试不加判断**：确定性失败重试多少次都是白花钱，要按失败类型决定。
