# RAG 效果不好时，你会怎么排查？

## 面试官为什么爱问这题

RAG 的面试里，讲流水线人人都会，画一张「入库切块 → 向量检索 → 拼上下文 → 生成」的图没有区分度。真正拉开差距的是下一句：「效果不好的时候，你怎么查？」这题考的不是知识点，是**排障的肌肉记忆**——只有亲手搭过、被 badcase 折磨过的人，才会脱口而出「先看检索回来的块里有没有答案」这种二分动作；没做过的人只能回答「换个更强的模型试试」，在面试官耳朵里约等于「没排查过」。

前面聊过的都是怎么搭：完整流水线、文本切块、混合检索与重排序这些环节都拆过。这篇换个方向，讲系统已经跑起来、指标已经开始掉的时候，怎么按层归因、怎么用中间产物定位、怎么避免盲调。

## 一句话先给结论

**RAG 出问题先分层再下钻：检索前查 query 表达（要不要改写、拆问、补上下文），检索中查召回（切块、Embedding、索引参数、top_k、过滤条件、重排），检索后查组装（上下文是否过长、噪声是否淹没关键块、有没有拒答指令）；第一刀永远是把召回结果落盘，看「含答案的块有没有被捞回来」——含答案但答错是生成/组装问题，不含才是召回问题。很多「模型不聪明」，最后都定位到文档解析脏、chunk 太碎、召回噪声大或上下文组装差。**

## 核心原理：先分层，再二分，最后才是调参

### 为什么必须分层

RAG 是链式系统：解析、切块、索引、检索、重排、组装、生成，一环扣一环。如果只盯着端到端的「答案对不对」，任何一环的误差都会表现为同一个症状——答错了。端到端指标没法归因，这就是很多人排查半天毫无进展的根源：拿着一个准确率数字，连该找哪个模块的负责人都不知道。

分层的意义是让每一层有自己的**中间产物**：检索前有原始 query 和改写后的 query，检索中有召回的 chunk 列表和分数，检索后有拼进上下文的最终 prompt。中间产物是可观测、可落盘、可逐条检查的——排查的本质就是顺着中间产物做二分，把「答案错了」逐步收窄成「某一步的输出不符合预期」。

### 三层各自的失效模式

**检索前**：query 本身表达不清。用户的问法和企业文档的写法往往对不上——文档写「增值税专用发票」，用户问「专票」，Embedding 相似度就低。症状是「明明库里有的东西检索不到」，病根却在查询侧。这一层要查的是：query 是否需要改写、是否一个 query 里塞了三个子问题需要拆问、是否缺上下文（「它的报销额度是多少」里的「它」指什么）。

**检索中**：召回环节的问题最多，也是个无底洞。要查切块（太碎导致语义不完整，太大导致命中了但全是噪声）、Embedding 模型与语料的匹配度、向量库索引参数（近似检索的 ef_search、nprobe 之类的搜索宽度参数调小了会漏召回）、top_k 大小、metadata 过滤条件是否误伤（之前讲企业知识库的权限过滤时提过：pre-filter 拼错一个字段名，整类文档直接隐形）、以及要不要上重排。

**检索后**：块都召回对了，答案还是错。常见病因：拼给模型的上下文过长，关键块被噪声淹没；块都进了上下文但排在中间，撞上 Lost in the Middle（长上下文里模型对首尾位置的信息利用明显好于中部，这个机制之前专门拆过）；生成提示没写「无依据就拒答」，模型拿半相关的块硬编。这一层的排查对象是最终 prompt 全文，不是检索日志。

### 企业知识库的三笔额外账

通用场景查三层就够，企业知识库还要多查三样：**文档质量**（解析脏不脏，扫描件 OCR 错了多少；之前讲复杂文档解析时说过，解析错误不可逆，后面任何环节都救不回来）、**版本**（用户问的是新政策，库里存的还是旧版——不是没召回，是召回的全是过时答案）、**权限**（过滤条件把该看的文档挡在外面，症状酷似召回失败，但病根在权限配置）。这三笔账查完，才轮到怀疑模型。

### 归因的主轴：先层，再环节，再参数

一个反面模式值得单独点名：效果一掉就调 top_k、换 Embedding 模型、加一层重排——每一样都改，每一样都不看中间产物，改完跑一遍全量评测，指标波动个两三个点，归因还是失败。正确顺序是反过来的：先确认 badcase 可复现（进黄金集），再看中间产物定位到层，再定位到层里的具体环节，最后才动参数——而且动参数要留对照，改一项测一项。没有黄金集，一切调整都是盲调；没有中间产物，一切归因都是猜。

## 横向对比

三层排查的检查清单，一张表装下：

| 层 | 典型症状 | 检查项 | 常见病因 |
| --- | --- | --- | --- |
| 检索前 | 库里明明有，就是检索不到 | 原始 query 与文档措辞差异；是否多问合一；是否缺指代上下文 | 术语对不上、一个 query 塞三个子问题、代词无先行词 |
| 检索中 | 召回列表里找不到含答案的块 | 召回列表与分数、切块粒度、索引搜索宽度、过滤条件、有无重排 | chunk 太碎语义残缺、近似索引参数过紧、metadata 过滤误伤、纯向量检索捞不回精确词 |
| 检索后 | 块里有答案，模型答错或瞎编 | 最终 prompt 全文、块数与总长度、块的位置分布、生成指令 | 上下文太长噪声淹没关键块、答案块落在中部、无拒答指令导致硬编 |

排查的第一刀，是把召回问题和生成问题切开，两者的信号完全不同：

| 信号 | 召回问题 | 生成问题 |
| --- | --- | --- |
| 召回列表里含答案的块 | 不在 | 在（通常分数也不低） |
| 生成侧的表现 | 拒答或拿别的块硬答 | 块在手边仍答错、答偏、漏要点 |
| 对应药方 | 改写、拆问、换检索策略、修切块、修过滤 | 收紧组装长度、调块顺序、加拒答与引用指令、换生成模型 |
| 盲调的代价 | 优化生成侧全是无效功 | 继续加 top_k 只会引入更多噪声 |

## 工程实践

### 第一刀：用 trace 落盘做二分

排查要有抓手。给每条 query 落一条完整 trace，第一刀的判定逻辑可以直接写成脚本：

```python
# 伪代码：召回问题与生成问题的二分判定
def diagnose(case):
    # case.triple = (query, gold_answer, trace)
    trace = case.trace

    # 第一步：召回列表里有没有「命中块」
    # 命中块定义：与 gold_answer 有实质重叠的 chunk（人工标或 LLM 辅助判）
    hit_chunks = [c for c in trace.recalled_chunks if c.overlaps(case.gold_answer)]

    if not hit_chunks:
        return "recall", trace  # 往检索前/检索中下钻
    if hit_chunks and trace.answer_wrong(case.gold_answer):
        # 命中块在召回列表里，但没进最终上下文 → 重排/组装把它挤掉了
        if not any(c.id in trace.final_context_ids for c in hit_chunks):
            return "rerank_or_assembly", trace
        # 进了上下文还是答错 → 看位置和长度，再查生成
        return "generation_or_position", trace
```

这个函数的关键设计是**中间判定多一刀**：命中块被召回但没进最终上下文，是重排或组装挤掉了它，这既不是纯召回问题也不是纯生成问题——直接二分会漏掉这一类。实际项目里这一类占比不小，重排模型把长尾精确匹配块压到阈外是常见事故。

### 埋点字段清单

上面的 trace 不是事后补的，是设计时就埋好的。最小可用字段集：

```json
{
  "query_id": "q-20261112-0007",
  "raw_query": "专票的报销额度是多少",
  "rewritten_queries": ["增值税专用发票 报销额度"],
  "recalled_chunks": [
    {"chunk_id": "doc12#p3#c2", "score": 0.83, "source": "dense",
     "doc_version": "v3", "in_final_context": true}
  ],
  "final_context_ids": ["doc12#p3#c2"],
  "prompt_tokens": 4100,
  "answer": "……",
  "cited_ids": ["doc12#p3#c2"],
  "latency_ms": {"retrieve": 180, "rerank": 240, "generate": 2100}
}
```

有了这份落盘，三层排查都不用复现环境，直接查日志。`in_final_context` 这个字段尤其值钱——它让「召回命中但被挤掉」这类问题在日志里一眼可见。`doc_version` 则是版本类问题的第一线索：答案错，先看命中的是不是旧版文档。

### 几个具体数字的用法

经验值口径沿用前面讲完整流水线时给的区间：召回池 top_k 取 20～50，重排后进上下文的块收在 3～8 条。排查时的用法是对照：如果进上下文的块数已经到十几条、prompt 冲到上万 token，先怀疑组装过载而不是模型变笨——这时候继续加块，是在恶化位置问题（位置敏感度之前专门讲过：事实型问答对块顺序明显敏感，关键块放首尾通常比埋在中部效果好）。切块粒度对照之前讲文本切块时给的区间（200～500 token，overlap 10%～20%），超出区间太远的块先修切块再谈其他。

### 黄金集：排查的度量衡

badcase 必须先固化成可复现的集合：每条记 query、标准答案、命中块（含来源文档与版本）。规模不用大，几十条有代表性的就能支撑大部分归因判断。每次调整后黄金集全量回放，指标动没动、动在哪些 case 上，一目了然——这比全量评测快得多，也才能回答「这个改动到底修了哪类问题」。用户点踩的 case、追问「不对」的会话，都应该回流进这个集合。

## 追问逐条作答

### 追问一：top_k 是不是越大越好？

不是，而且这是排查中最常见的错误直觉。top_k 越大，召回池里答案块被捞回的概率确实越高，但同时进来的噪声块也越多：重排要处理的候选变多、延迟上升；进上下文的块变多，关键块被淹没和落在中部的风险同步上升（位置效应之前专门讲过）。正确做法是把两个 k 分开：召回池的 top_k 可以放宽（经验值 20～50），靠重排筛；进上下文的条数收紧（经验值 3～8 条）。如果加大召回池后指标不动，说明瓶颈不在召回覆盖率，继续加只是买噪声。

### 追问二：如何识别是召回问题还是生成问题？

看中间产物，不看最终答案。把 badcase 的召回列表落盘，逐条判定含答案的块在不在里面：不在，是召回问题（再往检索前、检索中的检查项下钻）；在但没进最终上下文，是重排或组装问题；进了上下文还答错，才是生成问题。判定「命中块」没有标注时，可以用 LLM 辅助判一遍再人工抽查确认。这套动作的前提是 trace 埋点，所以答案的最后一句通常是：**「这要求系统在设计时就落中间产物，而不是出事了才想看」**——这句本身就是加分回答。

### 追问三：什么是 Lost in the Middle？

指长上下文里模型对信息的利用不均匀：开头和结尾的信息被有效利用，中间的信息容易被忽略。对排查的意义是：它制造了一类「假召回问题」——块明明召回且进了上下文，答案还是错，病根其实是位置。判别方法：把命中块手工挪到上下文首部重跑一次，答对了就基本坐实。药方是组装策略：关键块前置或置尾、控制上下文总长度。机制与对策之前专门展开过，这里只需要能一句话讲清并接上排查场景。

### 追问四：三层都查过了还是定位不到，怎么办？

先别继续下钻，退一步查两样。一是查评测本身：这个 badcase 是不是真 badcase——标准答案错了、问题本身有歧义、或者答案根本不在语料覆盖范围里（语料没有就该拒答，拒答不是错）。二是查变更：Embedding 模型升级后索引有没有全量重建（换模型不重建，新旧向量不在同一空间，检索质量崩塌式下滑且症状诡异）、文档更新有没有同步、最近哪个环节发过版。都没有的话，做对照实验：同一条 query，冻结其他变量，逐项切换单个环节（换改写/关重排/换切块），看中间产物在哪一步分叉。

### 追问五：排查要在系统里提前埋哪些观测点？

全链路 trace 一条不能少：原始 query、改写后 query、召回列表（chunk_id、分数、来源路、文档版本）、重排后列表、最终进上下文的块 id、prompt 全文与 token 数、答案与引用 id、各环节延迟。再加两个线上信号：拒答率（突然飙升先怀疑语料或权限，突然归零先怀疑拒答指令被改）和用户负反馈（点踩、追问纠正）。埋点的原则是「中间产物永远可回放」——排查效率基本由它决定。

### 追问六：线上没有人工标注，怎么低成本定位？

分三步。先看聚合信号分层：拒答率高，优先查检索前和语料覆盖；「答了但错」占比高，优先查检索中和组装。再用 LLM 抽检：按天抽样落盘 trace，让模型按「召回里有没有答案块 / 答案与上下文是否一致」两个问题归类，人工只复核被归为生成问题的部分（这类最需要人眼）。最后让负反馈自动回流：点踩的会话连 trace 一起进 badcase 池，攒够就人工标注成黄金集。标注永远贵，所以让信号先替你筛选。

## 60 秒面试回答模板

> 我会先分层再下钻。第一刀是把召回问题和生成问题切开：把 badcase 的检索结果落盘，看含答案的块有没有被捞回来——没有是召回问题，往检索前和检索中查；有但答错，往组装和生成查。检索前看 query 要不要改写、拆问、补上下文；检索中看切块粒度、索引参数、过滤条件、重排；检索后看上下文长度、块的位置、有没有拒答指令。企业场景还要多查文档质量、版本新旧和权限过滤。最后才动参数，而且改一项测一项，跑黄金集对照。很多看起来「模型不聪明」的问题，最后都定位到解析脏、块太碎、召回噪声大或组装过载。

## 加分项

- **主动提 trace 埋点**：把话题从「怎么排查」引到「系统设计时就该为排查埋什么」，展示的是可观测性意识，比背排查步骤高一个层级。
- **讲「召回命中但被重排挤掉」这个中间态**：多数候选人只知道召回/生成二分，补上这一刀说明真的读过重排日志。
- **讲换 Embedding 不重建索引的事故**：新旧向量不同空间，症状是检索质量整体崩塌——一个具体的坑比十条方法论有说服力。
- **区分两个 top_k**：召回池放宽靠重排筛、进上下文收紧，一句话展示对成本和位置效应的双重理解。

## 常见误区

- **端到端盲调**：不看中间产物，top_k、Embedding、重排一路换过去，指标波动两三个点也无法归因——排查不是试错。
- **把组装问题当召回问题治**：块明明在手边，继续加大 top_k，只会让关键块更靠中部、噪声更多，症状恶化。
- **把权限和版本问题当检索质量问题**：过滤条件误伤、文档没更新，症状都酷似召回失败，企业场景这两笔账要最先查。
- **拿没有可复现性的单次输出做判断**：不进黄金集、不回放，一次生成的对错说明不了任何问题。
