# Prompt Engineering 中，如何系统优化提示词并把准确率做上去？

## 一句话先给结论

**把 Prompt 优化从「反复手改文案」升级成一个工程闭环：先定义什么叫答对（含拒答和澄清），再按「输入分层 + 样例驱动 + 结构化约束」去改提示词本体，每次只动一个变量、在固定的 badcase 评测集上跑回归；收敛不动就老实分流——缺知识上 RAG、缺能力上工具、缺流程拆工作流、要固化行为才微调；而「准确率 95%」这类数字必须绑定具体任务和固定评测集，它从来不是通用承诺值。**

面试官问这题，考的不是你背了多少提示词技巧，而是三件事：**有没有评测闭环意识**（改完凭什么说变好了）、**会不会做单变量归因**（涨分和掉分各是哪个改动带来的）、**知不知道 Prompt 不是万能修复工具**（什么时候该停手去换方案）。答崩的现场通常是背出一串技巧清单，然后被一句「你们怎么知道改完更好了」问住。这题也是第 2 章的收官：第 6 篇讲了 Prompt 怎么组织，第 7 篇讲了改动怎么管住，第 9 篇讲了 Prompt 的能力边界，本篇补上中间缺的那环——在一个能回归、能归因的环境里，准确率是怎么一步步做上去的。

## 核心原理：优化是个闭环，不是玄学

「系统优化」四个字拆开是四个环节，缺一环就退化成碰运气：

**第一环：定义任务边界。**先说清什么叫答对、什么叫答错、哪些情况必须拒答或澄清。听起来像废话，但它是整个闭环的地基——判分标准没定，后面所有「更准了」都是体感。拒答和澄清尤其要提前定义：工单分类里「信息不足，转人工」算对还是算错，必须在写第一版 Prompt 之前就有答案。

**第二环：输入分层。**稳定规则放 System，动态任务放 User，不要把所有约束揉成一段长 prompt。第 6 篇讲过分工逻辑，这里只补一句与优化的关系：分层之后，每次实验改的是哪一层是清晰的，归因才做得了。

**第三环：样例驱动加结构化约束。**few-shot 示例、反例约束、输出格式示例，通常比抽象要求更稳定——模型模仿具体样例的能力强于服从抽象指令。能用 schema、parser、structured output 的地方，不要只写一句「请返回 JSON」，这是第 8 篇的结论，在优化里它对应一条铁律：**格式问题不要用自然语言去修，用约束去修。**

**第四环：评测回归加边界收敛。**线上错例沉淀成固定评测集，每次改动跑回归而不是靠「感觉更准了」；同时 Prompt、模型版本、温度、输出格式要求要一起入版本管理，避免改了一个点却查不清影响——机制第 7 篇展开过，这里只强调它在优化里的角色：**没有版本记录，归因就无从谈起**。当回归分数收敛、连续几轮改动不再有实质提升，就到了该分流的时刻。

还有一条排序原则贯穿全程：**先修大问题，再修措辞。**如果问题本质是缺知识、缺工具、缺流程，不要强行靠 Prompt 硬抬——这既是方法论，也是第 9 篇边界意识在优化上的投影。

最后是准确率的口径问题，题库原文专门强调过：所谓「准确率大于 95%」一定要绑定具体任务——分类、抽取、格式生成、客服问答各是一套口径，脱离场景的数字没有意义。工程目标应该是**某个具体任务在固定评测集上稳定达标**。

## 横向对比：各手段的天花板在哪

优化手段不止一种，先看清每种手段能买到什么、买不到什么：

| 手段 | 解决什么问题 | 起效前提 | 天花板与代价 |
| --- | --- | --- | --- |
| 措辞与规则调整 | 澄清任务要求、堵明显漏洞 | 任务本身在模型能力内 | 低：见效快但容易反复，改 A 坏 B |
| few-shot 正例加反例 | 统一判断口径和输出形态 | 手上有代表性样例 | 中：受示例覆盖度限制，长尾盖不住 |
| 结构化输出约束 | 消除格式波动、保下游解析 | 输出可以 schema 化 | 中：只治格式不治内容对错 |
| 任务拆解、分步引导 | 复合任务一步装太多错得多 | 错误来自步骤耦合 | 中高：步数变多，延迟和成本上升 |
| RAG / 工具 / 工作流 / 微调 | 缺知识、缺能力、缺流程、要固化行为 | 前四类手段已收敛 | 高：效果上限高，但建设与维护成本跳档 |

这张表的用法是从上往下用尽、再考虑最后一行——顺序反了就是「缺知识靠祈使句硬抬」的经典错误。

不同任务的「答对」口径也不一样，报数字之前先想清楚自己站在哪一行：

| 任务类型 | 「答对」怎么定义 | 判分方式 | 优化主抓手 |
| --- | --- | --- | --- |
| 分类 / 打标 | 标签完全一致 | 精确匹配，可全自动 | few-shot 定口径 + 低温度 |
| 信息抽取 | 关键字段内容正确 | 字段级比对，可定位哪个字段退步 | 输出示例 + schema 约束 |
| 格式生成 | schema 校验通过 | 解析成功率 | structured output + 校验重试 |
| 客服问答 | 事实正确且该拒答时拒答 | 关键词初筛 + 人工抽检 | 资料引用约束 + badcase 回归 |

## 工程实践：一个迭代闭环的骨架

以工单自动分类为例，给一套能直接照抄的做法。

### 第一步：给每次改动留实验记录

优化的核心纪律是**一次只改一个变量**，然后把假设、改动、结果记下来，避免「改了三处，涨了 2 分，但不知道是谁的功劳」：

| 轮次 | 假设 | 改动（仅一处） | 回归分 | 结论 |
| --- | --- | --- | --- | --- |
| v0.1 | —— | 基线：单段长 prompt | 71% | 格式错乱 12 例 |
| v0.2 | 格式问题该用约束修 | 加输出 schema（不改文案） | 79% | 格式错乱清零，边界类仍错 |
| v0.3 | 边界类缺判断口径 | System 加两条拒答规则 | 84% | 拒答类修复，新类别混判出现 |
| v0.4 | 混判是缺样例 | User 尾部加 4 条 few-shot（含 1 条反例） | 88% | 连续两轮 ≤1 分，接近收敛 |
| v0.5 | 剩余错误缺背景知识 | 神仙资料实验（见下） | 96% | 上限在知识侧，启动 RAG 评估 |

（表中分数为示例数据，用于展示记录格式。）这张表本身就是面试时最好用的讲料。

### 第二步：分层模板 + 反例 few-shot + schema

v0.4 的模板长这样，三个要素各就各位：

```yaml
# prompts/ticket_cls/v0.4.yaml —— 工单自动分类
system: |
  你是工单分类助手。只能输出以下标签之一：
 退款 / 物流 / 商品质量 / 账号 / 信息不足。
  规则：用户消息里没有可判断依据时，必须输出「信息不足」，
  不得猜测。输出 JSON：{"label": "<标签>", "reason": "<20字内>"}。
few_shot:
  - user: "快递三天没动了，帮我看看"
    assistant: '{"label": "物流", "reason": "物流进度异常"}'
  - user: "你们东西挺好用的，就是想夸夸客服"
    assistant: '{"label": "信息不足", "reason": "无待处理问题，不猜测"}'
output_format: '只输出一个 JSON 对象，不要输出任何其他文字'
params:
  temperature: 0.1        # 经验值：分类任务用低温减少采样波动
  max_tokens: 256
```

注意第二条 few-shot 是**反例性质的边界样例**：夸奖语不带问题，正确行为是输出「信息不足」而不是猜一个标签。挑样例的原则是**覆盖边界类型优先于堆数量**——经验值上 2～8 条就够起步，把「看起来像 A 其实该判 B」的样例放进去，比再加十条平庸正例有用得多。

### 第三步：神仙资料实验，判断该不该分流

当分数收敛、剩余错误都集中在「模型不知道的事」上时，做一个最有信息量的实验：**人工把正确资料贴进 prompt，看分数上限能到多少。**

```python
# 伪代码：上限实验——人工喂数据，测 Prompt 的理论天花板
for case in golden_set:
    enriched = case["input"] + "\n\n【参考信息】\n" + case["gold_context"]
    out = run_prompt(template_v04, enriched)   # 只加资料，模板一字不动
    record(case["id"], score(out, case["expect"]))
```

如果加了正确资料后分数从 88% 跳到 96%，说明缺的是知识而不是指令——该上 RAG；如果加了资料还在 88% 附近，说明瓶颈在推理或流程，RAG 救不了你。一个实验区分两种根因，这是优化闭环里性价比最高的一步。

### 第四步：badcase 分层入库

线上错例按来源分四层入库：主干正常请求的抽样（防止越改越偏）、边界与拒答类（宁多勿少）、对抗与格式攻击类、真实 badcase（一条都不能丢）。每条带 tag 和判分方式，结构沿用第 7 篇的 golden set 格式。另外留一个心眼：**改 Prompt 时盯的集合和最终验收的留出集要分开**，否则你是在对评测集本身过拟合。

## 面试官的追问，你该怎么接

### 追问一：如果 Prompt 怎么改都上不去，你怎么判断应该切到 RAG、Tool、Workflow 还是微调？

先做神仙资料实验确认瓶颈类型，再按这张表分流：

| 症状 | 缺什么 | 首选方案 | 快速验证 |
| --- | --- | --- | --- |
| 答案依赖模型不知道的资料、知识随时间变、引用靠编 | 缺知识 | RAG | 神仙资料实验：贴入正确资料后分数大幅上升 |
| 需要精确计算、查实时状态、调外部系统 | 缺能力 | 工具（Tool / Function Calling） | 人工替模型执行工具后喂回结果，看能否答对 |
| 任务多步，单步都对但整体错误率高 | 缺流程 | Workflow 拆步骤，各自验收 | 把任务手工拆成两步分别跑，看总成功率变化 |
| 格式与领域语言习惯要长期固化、样本量大、要压推理成本 | 缺行为固化 | 微调 | 先确认前三类都不是；微调固化行为，不是补知识 |

两个容易答错的地方：一是**微调不等于续训**，它适合固化「怎么回答」而不是灌「回答什么」，缺知识选微调是把药吃反了；二是分流不是单选，真实系统常常是 RAG 加工具加 Workflow 组合，Prompt 依然是里面的胶水。

### 追问二：badcase 集应该怎么建，才能真的指导迭代？

三个标准。**覆盖**：四层来源都要有，尤其不能只收坏样例——全是 badcase 的集会把 Prompt 越改越保守，正常请求悄悄退化没人发现。**判分**：每条写清期望输出和判分方式（精确匹配 / 关键词 / 字段比对 / 人工），不同人对「答对」理解不同，不写判分方式等于没写。**维护**：规模上经验值 30～100 条覆盖主要分支就够分辨两次改动的高下；每次线上事故把那条样例补进集里，让集子随业务长大。指导迭代的标志是：任何一次改动都能在这张集子上得到「涨了、平了、还是哪个 tag 掉了」的明确回答，而不是「好像好了一点」。

### 追问三：如果线上效果突然下降，怎么判断是 Prompt 问题、模型版本问题，还是外部知识 / 工具链路问题？

原则是**锁变量重跑，不盯日志猜**。第一步查发布记录三件套：template_hash、model_version、采样参数——「没人改 Prompt」经常只是没人改模板文件，参数早被谁动了。第二步只回退一个变量、跑同一份评测集：退模板恢复就是 Prompt 改动问题；退模型快照恢复就是模型版本问题；两个都退才恢复是新旧 Prompt 与新模型的兼容问题。第三步看错误分布分层归因：只有依赖外部资料的用例掉分，先查索引更新和召回质量，资料没送到模型眼前，Prompt 再好也没用。这套机制的第 7 篇展开过，这里补一个容易被漏的情形：**评测集不掉、只有线上掉**，多半是输入分布漂移或上游链路故障——去查流量构成和错误码，别急着动 Prompt。

### 追问四：面试官问「你们准确率做到多少」，怎么答才不踩坑？（自补）

永远带着口径报数：什么任务（工单五分类）、多大规模的评测集（多少条、什么来源）、什么判分方式（自动精确匹配还是人工抽检）、什么条件下（固定模型与参数）。一句话模板：「工单五分类，在我们 80 条含边界与 badcase 的评测集上，字段级自动判分，稳定在 88% 左右，剩余错误主要在缺背景知识一类。」这比一句「95% 以上」可信十倍——后者面试官会立刻追问口径，答不上来前面全白讲。反过来说，**脱离具体任务承诺一个通用准确率，本身就是没做过评测闭环的信号**。

### 追问五：few-shot 示例放几条合适？是不是越多越好？（自补）

经验值上 2～8 条起步，够覆盖主要分支就先跑起来，别一上来铺几十条。三条挑选原则：**边界优先**，一条「看似 A 实则 B」的样例价值高于十条平庸正例；**格式一致**，示例的输出格式必须和你要求模型输出的格式完全一样，示例自己都不遵守 schema，模型不会替你遵守；**反例带解释**，反例要写清错在哪、正确行为是什么，只给错误示范不给判据，模型可能把错误学走。数量多的代价不只是 token：示例过强会引导模型只会照着例子答，没被样例覆盖的新形态泛化反而变差（经验观察），这也是回归集里必须保留「正常请求抽样」层的原因。

### 追问六：把 temperature 调低算不算优化？（自补）

算收敛手段，不算能力提升。降温度减少采样波动、让输出更可复现，对分类、抽取这类有唯一答案的任务通常有益（经验值 0～0.3）；但它不会让模型知道原本不知道的知识，也不会提升推理质量。实践中它的正确位置是：**在比较两版 Prompt 之前先把温度等采样参数锁死**——温度 0.7 下比较两版文案的差异，你测到的很大一部分是采样噪声。反过来，用降温度去掩盖 badcase（「降了温度就不随机出错了」）是把症状当病因，该修的是任务定义或知识供给。

## 60 秒面试回答模板

> 我不会把 Prompt 优化理解成反复手改文案，而是当成一个小工程闭环。第一步定义任务边界：什么算答对、什么算答错、什么时候必须拒答，没有判分标准后面全是体感。第二步改提示词本体：稳定规则放 System、动态任务放 User，用 few-shot 正例加反例统一判断口径，能用 schema 约束的不用自然语言去修格式。

> 第三步是评测回归：线上错例沉淀成固定评测集，每次改动只动一个变量，跑回归看分数和哪个 tag 掉没掉，不靠「好像更准了」。连续几轮不涨分就说明收敛了，这时做一个神仙资料实验——人工把正确资料贴进 prompt 看上限——分数能上去说明缺知识，该上 RAG；上不去说明缺流程或能力，去拆工作流或加工具。

> 最后，准确率必须绑定任务和评测集口径来报，比如什么任务、多少条集子、怎么判分。脱离场景承诺一个 95%，本身就是没做过评测闭环的信号。

## 加分项

- **讲出「神仙资料实验」**。用一个便宜实验区分「缺知识」还是「缺指令」，这是真做过优化的人才会的动作，比任何技巧清单都有说服力。
- **主动报准确率口径**。任务、评测集规模、判分方式一起说，面试官会立刻把你和背数字的候选人分开。
- **强调一次只改一个变量加实验记录**。说明你经历过「改了三处涨两分却无法归因」的痛。
- **知道优化会收敛、主动分流而不是死磕 Prompt**。能说出「微调固化行为、不补知识」这句边界，直接对应第 9 篇的认知层次。

## 常见误区

- **把优化做成措辞玄学**。没有评测集、没有回归，每次改动靠体感，涨跌都说不清原因。
- **缺知识靠祈使句硬抬**。「请你务必准确、不要编造」解决不了模型不知道的事，该上 RAG 就上 RAG。
- **报一个脱离任务的准确率**。「我们做到 95%」被追问口径就崩，反而暴露没做过评测。
- **few-shot 堆数量不讲覆盖**。几十条平庸正例不如几条边界样例，还搭上 token 成本和泛化损耗。
- **拿降温度当优化**。采样参数锁死是为了可比性，不是能力提升的手段。
