# 现在还需要 LangChain 吗？为什么不是直接手写 SDK 就够了？

## 面试官为什么爱问这题

这是高频题，也是在筛态度。盲目崇拜框架的人会罗列一堆组件名，标榜"生态强大"；一味反框架的人会说"都是语法糖，手写就行"。面试官真正想听的是有没有一套选型判断：什么规模下手写更清爽，什么复杂度下抽象开始回本，以及框架到底解决了什么手写解决不了的问题。这题考的不是你会不会用 LangChain，而是你会不会在"引入一层抽象"这件事上做权衡。前面讲过 LCEL 怎么把各类组件统一成一种接口，也讲过图编排解决的是什么；这一篇退到更前面的一层——要不要把这一整套抽象请进项目，判断的依据是什么。

## 一句话先给结论

**LangChain 的价值不在"能不能调模型"，调模型用官方 SDK 几行就够。它真正做的是把模型输入输出、Prompt、Parser、Retriever、Tools、Memory、Callbacks 这些常见能力统一成一套可组合接口，解决的是"应用层编排和生态整合"。最小 Demo 手写 SDK 完全够；一旦进入多模型接入、链式编排、结构化输出、可观测和长期维护，统一抽象会明显降低代码分散度。判断标准是复杂度，不是好不好看。**

## 核心原理：框架到底卖的是什么

### 它替你解决的是编排，不是发请求

把这件事说清楚，答案就成立了一半。调一次模型，官方 SDK 给的接口已经很好用，框架在这件事上没有任何优势。框架真正的价值出现在调用变多、环节变复杂之后：prompt 要拼、输出要解析、要接检索、要调工具、要记历史、要埋回调，这些环节如果各写各的，代码会散落在项目各处，换个模型就要翻遍每个文件。

框架做的是把这些常见能力统一成一套可组合的接口，让它们能像积木一样拼。前面讲 LCEL 时说过，统一接口带来的最大好处是流式、批处理、回调、局部替换这些横切能力只写一次；这里补的是更上一层的判断——当你的项目里这种"多环节组合 + 反复替换"的需求成立时，那套统一抽象才划算。

### 选型的真正分水岭：代码分散度

判断要不要上框架，一个好用的尺子是看"代码分散度"：同一个改动要碰几个地方。

写一个只调一次模型的小工具，从 prompt 到调用到解析就在一个函数里，改什么都一目了然，手写最清楚。但做一个要支持多个模型、带检索、带工具、带日志的应用，情况就不同了：模型调用逻辑散落在五个文件，换一个供应商要改五处；想统一加日志，得在五个地方各埋一遍。这时候统一抽象的收益就出来了：调用收敛到一处，改动也收敛到一处。

| 维度 | 手写 SDK | 用框架 |
| --- | --- | --- |
| 单次调用、最小 Demo | 直接、透明、几行搞定 | 引入抽象反而是负担 |
| 多模型接入 | 每家 SDK 各写一套适配 | 统一接口，切换成本低 |
| 链式编排 | 自己管理环节衔接与数据对齐 | 组合接口现成，环节可替换 |
| 结构化输出 | 自己写解析和兜底 | 解析器作为一环接入 |
| 可观测与回调 | 每个调用点手动埋点 | 回调挂在统一入口 |
| 长期维护 | 代码分散，改动牵一发动全身 | 收敛到统一抽象，改动局部化 |

### 框架不是没有代价

讲平衡，就要认它的成本。引入框架意味着多一层要理解的执行模型，遇到问题时要穿透框架看底层，否则只会调 API、出了问题干瞪眼。框架的接口也会迭代，版本变化时适配要跟。所以在简单场景下用框架，是拿不必要的复杂度换一个暂时用不上的"未来可扩展"。

一个务实的判断口径（经验值）：项目早期链路还没定型时，先用 SDK 把主流程跑通，别急着抽象；等流程稳定、开始出现"换个模型要改好几处""日志要埋好几个地方"这类信号时，再引入框架把已有流程收拢进去。抽象要跟着真实复杂度走，别走在它前面。

把两种选择放到几类典型任务里，取舍会更直观：

| 任务类型 | 更推荐 | 原因 |
| --- | --- | --- |
| 一次性脚本、单次问答 Demo | 手写 SDK | 就一个调用点，抽象无处施展 |
| 单模型、链路固定的小服务 | 手写 SDK | 没有替换需求，透明比可扩展重要 |
| 多模型接入、要能切换 | 框架 | 统一接口把适配收敛到一处 |
| 带检索、工具、结构化输出的应用 | 框架 | 环节多，组合与替换靠统一抽象 |
| 要统一可观测、长期多人维护 | 框架 | 回调和改动都收敛到统一入口 |

这张表不是让你记住"哪行选哪个"，而是给出一个判断习惯：先看你手上任务属于哪一类，再决定要不要把框架请进来。面试官如果在意你有没有盲目崇拜框架，这张表背后的判断逻辑就是答案。

## 工程实践：一个渐进的引入路径

不要一上来就"全框架化"，更稳的是渐进：

**第一步，纯手写跑通主链路。** 用官方 SDK 把 prompt → 模型 → 解析这条主路径写通，此时代码集中在一个模块里，最容易调试。

**第二步，出现重复就抽公共层。** 当第二、第三个调用点出现，且它们在重复同样的模型初始化、同样的错误兜底，把这些抽成一个内部封装。这一步还没引入框架，只是自己收拢重复。

**第三步，需求超出自己封装的成本时再上框架。** 当你发现自己在手写的那些东西，比如统一的多模型适配、链式组合、回调体系，正是框架已经做好的，而且自己维护它们的成本在上升，这时引入框架才回本。

```python
# 伪代码：手写路径 vs 框架路径的对照，说明"改动收敛在哪"
# 手写：每个调用点都要知道用的是哪家模型
# answer_a = openai_client.chat(...).choices[0].message.content
# answer_b = claude_client.messages.create(...).content[0].text

# 框架：调用点只认统一接口，换模型只改初始化这一处
model = init_model(provider="vendor_a")   # init_model 是业务侧封装
chain = prompt | model | parser
answer = chain.invoke({"question": q})
```

要点：换模型时，手写路径要改每一个调用点，框架路径只改 `init_model` 这一处。`provider`、`q`、`prompt`、`parser` 是业务侧自定义，按自己的实现填入。这个对比不是为了炫技，而是回答"为什么统一抽象在复杂项目里划算"——它把改动从散落多处收敛到一处。

## 追问逐条作答

### 追问一：LangChain 和直接调官方 SDK 的本质区别是什么？

本质区别在抽象的层次。SDK 解决的是"怎么发一个请求、怎么拿回结果"，是单次调用层面的；框架解决的是"多个环节怎么组合、怎么替换、怎么统一观测"，是应用层编排层面的。单次调用的 Demo 里 SDK 完全够甚至更清楚；只有当调用变多、环节变复杂，编排层的抽象才有价值。

### 追问二：小项目用框架会有什么问题？

主要是引入不必要的复杂度：多一层执行模型要理解，出了问题要穿透框架查底层；接口迭代要跟着适配；而这些成本在小项目里换不来收益，因为小项目没有多模型、没有复杂编排、没有跨文件的维护痛点。小项目里手写更透明、调试更直接。

### 追问三：什么时候该从手写迁移到框架？

看信号，不看规模数字。出现这些就该考虑：要接多个模型、每家都在写适配；链式编排变多，环节衔接自己管不过来；日志、重试、回调在每个调用点重复写；改一个模型要翻好几个文件。这些都说明代码分散度已经上来了，统一抽象开始回本。迁移时不必一次全改，先把最痛的那段收拢进去。

### 追问四（自补）：用了框架是不是就不用担心底层了？

恰恰相反，越用框架越要懂底层。框架把很多细节藏起来，正常路径很省事，但一旦出问题，比如流式断了、工具没被调用、状态没接上，如果不理解底层的请求结构和执行流程，就只能干瞪眼。面试官看重"会用且懂底层"，就是因为生产环境里迟早要穿透框架排查。前面聊过统一接口调试时要理解执行模型，这里是同一个道理在选型上的体现。

### 追问五（自补）：框架选型时除了功能，还要看什么？

看两点。一是抽象是否贴合你的问题：框架的强项如果是编排和生态整合，而你的痛点正好在这，就值；如果你的痛点只是单次调用，那再强的编排能力也用不上。二是可穿透性：出问题时能不能看到底层、能不能绕开框架直接用 SDK 兜底。一个让你完全看不到底层的框架，在复杂项目里是风险而不是助力。

## 60 秒面试回答模板

> 我的判断是看复杂度，不看流行。LangChain 的价值不在能不能调模型，官方 SDK 几行就够，而在它把模型输入输出、Prompt、Parser、Retriever、Tools、Memory、Callbacks 统一成一套可组合接口，解决的是应用层编排和生态整合。所以最小 Demo 我直接手写 SDK，更透明也更好调。但当项目要接多个模型、做链式编排、结构化输出、统一可观测和长期维护时，统一抽象会把散落在各处的调用收敛到一处，换模型只改一处，加日志只埋一处，这时候框架才回本。代价是多一层要理解，出了问题得能穿透到底层。所以我会渐进引入：先手写跑通，出现重复再收拢，等自己手写适配的成本超过框架时才上。

## 加分项

- 用"代码分散度"作为选型尺子，可判断、不空泛。
- 主动认框架的成本：多一层执行模型、版本适配，不吹不黑。
- 给出渐进引入路径，而不是"全上或全不上"的二元答案。
- 点出"用框架更要懂底层"，呼应生产排查的现实。

## 常见误区

- **罗列组件名标榜生态强**：答不到"它解决编排和生态整合"这个定位，等于没答到点上。
- **说"都是语法糖，手写就行"**：忽略了多模型、长维护场景下统一抽象的真实收益。
- **把框架当成免懂底层的捷径**：越用越要能穿透排查，这是生产环境的基本要求。
