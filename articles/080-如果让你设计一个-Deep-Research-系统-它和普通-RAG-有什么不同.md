# 如果让你设计一个 Deep Research 系统，它和普通 RAG 有什么不同？

<!-- growth-hook:v1 -->
“Deep Research 不就是上下文更长的 RAG 吗？”——这是这题最典型的误答。差别不在量级，在研究过程有没有被拆开、证据有没有被反复求证。把这两件事讲清，才算真的理解。

## 面试官为什么爱问这题

这题考的是你能不能分清"检索问答"和"研究助手"这两类系统。很多人觉得 Deep Research 就是"检索更多、上下文更长的 RAG"，那是把它理解浅了，差别不在量，在质：普通 RAG 是先检索再回答的单轮流程，Deep Research 是拆任务、多轮检索、交叉验证、综合整理的多轮研究流程。面试官想听的是你能不能讲清这个差异，以及由此带来的能力要求变化，比如查询规划、子任务拆分、冲突检测、引用管理、可信度判断、迭代补检。前面讲过 Deep Research 怎么设计（五模块），这一篇专门回答"它和普通 RAG 到底不同在哪"，并答好可靠性、交叉验证、人工审核三条追问。

## 一句话先给结论

**普通 RAG 更接近"先检索，再回答"，Deep Research 更接近"围绕一个复杂主题，先拆研究任务，再多轮检索、交叉验证、综合整理，最后输出结构化报告"。因此它通常需要查询规划、子任务拆分、多源检索、冲突检测、引用管理、可信度判断和迭代补检这些能力，更接近研究助手而不是问答助手，输出也更偏报告、摘要和引用列表，而不是一句直接答案。从工程实现看，它本质是"工作流 / 图编排 + 多轮检索 + 报告生成"的组合，不是把普通 RAG 的上下文塞得更长——重点不只是召回，而是研究过程有没有拆开、证据有没有反复求证、最后能不能形成带引用的结构化结论。**

## 核心原理：从"检索问答"到"研究助手"

### 流程形态不同

**普通 RAG：先检索，再回答。** 用户问一个问题，系统检索相关片段、拼进上下文、让模型生成答案。这是一条单轮流程，重点在"检索准不准、生成忠不忠实"。

**Deep Research：拆任务、多轮研究、出报告。** 围绕一个复杂主题，先拆成子任务，再对每个子任务多源检索、交叉验证，综合整理后输出结构化报告。这是多轮流程，重点在"研究过程全不全、证据可不可靠、结论带不带引用"。

| 维度 | 普通 RAG | Deep Research |
| --- | --- | --- |
| 流程 | 先检索再回答，单轮 | 拆任务、多轮检索、验证、综合，多轮 |
| 定位 | 问答助手 | 研究助手 |
| 输出 | 一句直接答案 | 报告、摘要、引用列表 |
| 核心能力 | 召回、忠实生成 | 规划、拆分、多源检索、冲突检测、引用、可信度、迭代补检 |
| 工程形态 | 检索 + 生成 | 工作流 / 图编排 + 多轮检索 + 报告生成 |

如果把研究流程按阶段拆开，每个阶段需要的能力也不同：

| 研究阶段 | 需要的能力 | 产出 |
| --- | --- | --- |
| 拆解 | 查询规划、子任务拆分 | 可研究的子问题清单 |
| 取证 | 多源检索 | 各子问题的原始材料 |
| 求证 | 冲突检测、可信度加权、迭代补检 | 经过交叉验证的证据 |
| 成文 | 引用管理、结构化组织 | 带引用的报告、摘要 |

普通 RAG 基本只有"取证 + 成文"两步，Deep Research 多了拆解和求证两段，这正是它"研究"二字的由来。理解这四段的划分，答题时就不会把 Deep Research 说成一堆能力的堆砌——那些能力其实分别服务于某个阶段，是有结构的。

### 能力要求为什么变了

因为流程变复杂了，需要的能力也变了。查询规划是把主题拆成可研究的子问题；子任务拆分是明确每个子问题查什么；多源检索针对不同子问题查不同来源；冲突检测在多来源说法不一时要发现矛盾；引用管理让每条结论都能追溯到来源；可信度判断区分权威来源和自媒体；迭代补检在发现证据不足时继续查。这些都是单轮 RAG 不需要、但研究必须有的能力。

### 本质区别：不是上下文更长

题库特别点出：Deep Research 本质是"工作流 / 图编排 + 多轮检索 + 报告生成"的组合，而不是把普通 RAG 的上下文塞更长。这个区分很关键——有人以为只要窗口够大、检索够多，就能做研究，其实不是。研究的核心是"过程"：把研究拆开、让证据被反复求证、形成带引用的结论。上下文长只是手段，过程可拆、可验证才是本质。前面讲工作流与 Agent 的选择时说过，路径清晰、要可控的场景适合显式编排，Deep Research 正是如此。

## 工程实践：可靠性怎么保证

既然是"研究"，可靠性就是生命线。几条关键做法：

**多源交叉验证。** 重要结论不靠单一来源——从多个独立来源查证，说法一致才采信。这是"交叉验证"的字面含义。

**冲突显式处理。** 多来源矛盾时不要悄悄选一个，而是记录冲突、判断哪个更可信、必要时在报告里说明分歧。

**引用可追溯。** 每条关键结论都带引用，能点回到具体来源和位置。没有引用的结论在研究里几乎不可信。

**迭代补检。** 第一轮研究后检查证据缺口，不足就继续查，而不是草草出报告。

```python
# 伪代码：多源交叉验证与冲突检测
def verify(claim, sources):
    evidences = [s.find(claim) for s in sources]      # 多源取证
    evidences = [e for e in evidences if e]            # 去掉没找到的
    if len(evidences) < MIN_SOURCES:                   # 来源不足
        return {"verdict": "need_more", "evidences": evidences}
    positions = [e.position for e in evidences]        # 看各方说法
    if conflicting(positions):                         # 检测到冲突
        return {"verdict": "conflict", "evidences": evidences}
    cred = weighted_credibility(evidences)             # 按来源可信度加权
    return {"verdict": "confirmed", "credibility": cred}

# MIN_SOURCES / conflicting / weighted_credibility 为业务侧实现
```

要点：多源取证、来源不足就补检、冲突显式标记、按可信度加权。`MIN_SOURCES` 是业务侧阈值。变量都是业务侧实现。

## 追问逐条作答

### 追问一：如何保证结果可靠？

靠几道机制叠加。多源交叉验证，重要结论要多个独立来源查证；冲突检测，说法不一要发现并处理，而不是悄悄选一个；引用可追溯，每条结论能回到来源；可信度加权，权威来源权重高；迭代补检，证据不足继续查。再加人工审核点，高风险结论让人把关。经验值：可靠性不靠单一环节，靠这套组合；其中"引用可追溯"是基础，没有它其他机制都落不了地。

### 追问二：什么叫多源交叉验证？

指同一个重要结论，从多个独立来源分别取证，看说法是否一致。一致就提高采信度；不一致就是发现了冲突，要进一步判断哪个更可信或说明分歧。关键在"独立"，如果两个来源其实是同一份信息的转载，不算真正的交叉验证。前面讲 RAG 引用时说过"有引用但不忠实"的坑，交叉验证正是防这类问题，多个独立来源互相印证，比单一来源可靠得多。

### 追问三：这类系统为什么更需要人工审核点？

因为研究结论影响大、且自动化难保证万无一失。研究报告常被用于投资、战略、合规等决策，一个错误结论代价高；而多源信息里冲突、误导、过时内容都可能混入，自动判断未必可靠。所以在关键节点设人工审核，比如高风险结论发布前、检测到冲突难决断时、证据不足但仍要出报告时。前面讲行为边界时说过人工点加在不可逆动作前，研究里"对外发布结论"就是这样的动作。

### 追问四（自补）：冲突检测具体发现什么？

发现多来源对同一事实说法不一致。比如同一数据不同报告数值不同、同一事件不同媒体描述相反、同一政策不同来源解读冲突。系统要比对各来源的立场，识别这些矛盾，而不是简单拼接——把矛盾的说法都塞进上下文，模型可能选错一个，或生成一段自相矛盾的结论。检测到冲突后要标注出来，按可信度判断或交人工决断。

### 追问五（自补）：为什么输出要带时间戳？

因为研究结论有时效性。市场数据、政策、技术动态都会变，一个结论是基于某时点的证据得出的。带时间戳让读者知道结论反映什么时候的情况，也便于日后更新，过段时间重新研究时，能对比哪些结论变了、哪些没变。前面讲幻觉时提过"时间点偏了"是常见错误，时间戳是对它的防范，也是研究报告的基本规范。经验值：不只是报告整体带时间，关键结论的引用最好也标上来源的发布时间——一个三年前的数据和一个上周的数据，可信度完全不同，读者需要能区分。

## 60 秒面试回答模板

> 普通 RAG 是先检索再回答的单轮问答助手，Deep Research 是围绕复杂主题先拆任务、再多轮检索、交叉验证、综合整理、最后出结构化报告的研究助手。因此它需要查询规划、子任务拆分、多源检索、冲突检测、引用管理、可信度判断和迭代补检这些能力，输出是报告、摘要和引用列表，不是一句答案。工程上它本质是工作流或图编排加多轮检索加报告生成，不是把 RAG 上下文塞更长——重点在研究过程有没有拆开、证据有没有反复求证、结论有没有引用。可靠性靠多源交叉验证、冲突显式处理、引用可追溯、可信度加权和迭代补检；因为结论影响大、自动判断未必可靠，还要在关键节点设人工审核点。

## 常见误区

- **当成上下文更长、检索更多的 RAG**：忽略研究过程拆解和证据反复求证这个本质区别。
- **只靠单一来源取证**：不做交叉验证，很容易采信误导性信息或已经过时的内容。
- **悄悄处理冲突**：多来源说法矛盾时要显式标注出来、说明分歧，不能由系统悄悄挑一个采信，那等于把判断风险藏了起来。
