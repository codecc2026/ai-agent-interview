# 设计 Tool：粒度、命名、幂等这几点怎么定？

## 面试官为什么爱问这题

这题在筛一件事：你有没有真的把工具接到生产系统里。课程 demo 里的工具几乎都是查天气、查字典——纯读、无副作用、失败了大不了重来。生产里的工具要连真系统：发消息、下工单、写数据库、触发退款。工具从「查一下」变成「改一笔」，风险等级完全不同，设计时要操心的东西也完全不是一回事。

之前聊过调用出错之后怎么用护栏兜住，那是下游的事。这篇往上游走一步：工具在被模型调用之前，本身该怎么定义，才能让选错、填错、重复执行这些麻烦从源头少发生。一个设计得好的工具，是让后面的护栏有东西可拦；一个设计糟糕的工具，护栏再厚也补不回来。

## 一句话先给结论

**把一个工具做得能上生产，靠四条：单一职责管粒度、明确 schema 管参数、可观测管追踪、可失败管兜底；一旦工具要连业务系统，再加三样——权限校验、幂等控制、审计日志。判断标准不是「能不能调通」，而是「模型一眼看得懂、调得动，调错了也追得到、兜得住」。**

## 核心原理：四条原则拆开讲

### 单一职责：一个工具只做一件清晰的事

反面是「大而全万能工具」：一个 `handle_request` 收一个 `action` 枚举，十几种操作塞在里面，参数是一包通用 dict。看着接口数少，实则把选择题全甩给了模型——它要先从十几个 action 里选对，再猜这个 action 该配哪些参数。选错和填错会一起涨，出错时你连是哪一步出的都定位不到。

粒度怎么定，有个可操作的口径：**按「业务动作」切，不按「API 端点」切，也不按「字段」切**。「查订单」是一个动作，「查订单并顺便看物流」是两个动作，就该拆成两个工具或让模型分两轮调。经验上单场景暴露给模型的工具数控制在 5～10 个以内，超过就按场景分组、先路由再挂载，这个量级和之前聊工具收敛时给的口径一致。

太细也有代价：十几个原子操作摆在那，模型要多跑好几轮，token 和延迟都跟着涨。粒度本质是「模型的选择成本」和「调用轮数」之间的一笔账，没有标准答案，只有对这个场景合不合适。

### 明确 schema：名字和参数都是给模型看的

工具描述是模型选工具的唯一依据。这里有两层：**工具名**和**参数 schema**。

命名上，动词开头、读写一眼可分——`search_order`、`get_inventory` 是读，`create_ticket`、`refund_order` 是写。别用 `handle`、`process`、`manage` 这种无信息量的词，也别让两个工具名字只差一个介词。description 里除了写「能做什么」，补一句「什么时候不该用它」，边界比能力更能防选错。

参数 schema 要具体到类型、必填、枚举和取值约束。模型看到 `status: Literal["paid","shipped","refunded"]` 和看到 `status: str`，填对的概率差很多。工具描述里的一环是 Pydantic 这类声明式模型，把字段钉死在运行时强校验上——前面聊工具幻觉时给过一段 schema 校验的代码，这里不重复，重点落在「写工具描述时就要想着校验」。

### 可观测：每次调用都要能追

工具对模型是个黑盒：模型给出参数，拿到返回值，中间发生了什么它看不见。一旦结果不对，人也看不见——除非你记了 trace。一次调用至少记五样：请求、参数、耗时、结果、错误码，用同一个 trace_id 串起来，能还原「哪个工具、带了什么参数、调了多久、返回了什么」。

为什么非要连结果和耗时也记：选错工具是描述问题，参数错是 schema 问题，超时是下游问题，返回了但内容错是工具实现问题。这几种失败靠抽象地看日志分不出来，得靠一条完整的调用记录做归因。前面聊排查时提过的 trace 埋点思路，在工具这一层同样适用。

### 可失败：不假设一定成功

工具必须自带失败设计：超时时间、异常码、重试策略、降级逻辑。最忌讳的是「假设一定成功」——下游超时了，工具没有超时上限，整个 Agent 链路就卡在那；下游返回异常，工具把异常当正常结果吐回给模型，模型拿着一段错误文本继续推理，越走越偏。

重试尤其要小心：只有幂等的工具才敢自动重试。一次「下工单」如果因为网络抖动重试了两次，可能就下出两张单。可失败这条和幂等是绑在一起的——先做到幂等，重试策略才有意义。

## 横向对比

### 四条原则各管什么

| 原则 | 解决的麻烦 | 不做会怎样 | 落地时看什么 |
| --- | --- | --- | --- |
| 单一职责 | 模型选错工具、调用轮数多 | 万能工具里 action 选错、参数乱填 | 按业务动作切、单场景工具数 |
| 明确 schema | 参数填错、读写边界糊 | 枚举越界、只读场景触发写操作 | 动词命名、类型与枚举、反例描述 |
| 可观测 | 出错无法归因 | 只知道「结果不对」，不知哪一环 | trace_id 串起请求/参数/耗时/结果/错误 |
| 可失败 | 下游超时与异常拖垮链路 | 卡死、把异常当成功回灌模型 | 超时上限、异常码、重试与降级 |

### 只读工具 vs 写工具：设计差别在哪

工具一旦从「查」变成「改」，同一套原则的落法完全不同：

| 维度 | 只读工具（查天气、查库存） | 写工具（发消息、下工单、写库） |
| --- | --- | --- |
| 粒度 | 可稍粗，合并查询能省轮数 | 按业务动作切细，一处失败不牵连别处 |
| schema | 类型对、必填齐基本够 | 追加归属与权限字段，值域卡到业务约束 |
| 权限 | 一般不额外校验 | 每次调用校验「当前用户能不能做」 |
| 幂等 | 天然幂等，重试无所谓 | 必须带幂等键，否则重试会重复执行 |
| 审计 | 记调用即可 | 谁、何时、改了什么，完整留痕备查 |
| 重试 | 放心重试 | 先确认幂等，再定次数与退避 |

经验上，很多线上事故不是模型「变笨」了，而是有人用查工具的思路去设计写工具——没有幂等、没有权限、重试随便开。把这张表的右列当成写工具的上线清单，能挡掉一大半问题。

### 幂等键怎么选

| 做法 | 怎么实现 | 适合 | 注意 |
| --- | --- | --- | --- |
| 业务单号 | 用订单号 / 工单号做键 | 天然有唯一业务标识 | 键由业务侧生成，别让模型编 |
| 请求指纹 | 对参数规范化后取哈希 | 参数相同的重复提交 | 时间戳等漂移字段要先剔除 |
| 去重表 | 执行前查键是否已处理 | 无天然主键的写操作 | 查 + 写要放在同一事务里 |

## 工程实践

### 一个写工具的 schema 长什么样

下面是一段能直接照抄的定义。要点是字段类型钉死、枚举写全、description 里把适用场景和归属约束写清楚——这些信息既是给模型的，也是运行时校验的依据。

```python
# 依赖：pydantic v2
from pydantic import BaseModel, Field, field_validator
from typing import Literal

class CreateTicketArgs(BaseModel):
    user_id: str = Field(..., description="发起人 ID，必须是当前会话用户本人")
    title: str = Field(..., min_length=4, max_length=80, description="工单标题")
    priority: Literal["low", "normal", "high"] = Field("normal", description="优先级")
    idempotency_key: str = Field(..., description="幂等键，由业务侧生成，勿让模型编造")


```

`min_length` / `max_length` 把标题长度卡住，避免模型吐一段话当标题；`Literal` 把优先级收成三个枚举；`idempotency_key` 强制由业务侧生成——这三个字段分别对应「参数合理」「读写边界清楚」「可安全重试」。至于「user_id 必须是当前会话用户」这条归属校验，schema 管不了（它不知道当前是谁），要在执行前拿会话上下文单独比对，也就是下面主流程里的 `authorized`。

### 幂等 + 可观测的主流程

```python
# 伪代码：写工具的执行骨架
def run_tool(name, raw_args, ctx):
    start = time.monotonic()                       # 可观测：计时
    args = validate_call(name, raw_args)           # schema 强校验
    if tool.risk == "write" and not authorized(ctx, args):
        return record_and_return(name, args, "denied", start)   # 权限校验
    key = args.idempotency_key
    if seen(key):                                  # 幂等：查去重表
        return record_and_return(name, args, "duplicate", start)
    with transaction():                            # 查 + 写同事务
        mark_seen(key)
        result = tool.run(args, ctx)               # 真正执行
    return record_and_return(name, args, "ok", start, result)
```

`record_and_return` 负责落那条 trace：请求、参数、耗时、结果、错误码。把可观测做成所有工具共用的出口，比在每个工具里各写一遍日志靠谱——漏记一个工具，排查时就会出现一段盲区。事务那段是关键：查重和执行必须在同一个事务里，否则并发下两个请求可能同时通过查重、各自执行一次。

### 失败反馈要写进 description

工具描述里最好直接告诉模型出错时会收到什么。比如写一句「失败时返回结构化错误码 TIMEOUT / RATE_LIMIT / PERMISSION_DENIED，按错误码决定是否重试」，模型拿到错误就知道该怎么反应，而不是对着一段自由文本继续猜。这些错误码要真实存在于实现里，不能只写在描述中。

## 追问逐条作答

### 追问一：工具粒度到底怎么定，有没有可量化的标准？

没有通用标准，但有三条实用判据。第一，按业务动作切：一个工具对应一个用户能感知的动作，而不是一个 API 端点或一类字段。第二，看调用轮数：如果一个任务因为工具太细要多跑五六轮，token 和延迟都上去了，就该考虑合并相邻动作。第三，看选错率：如果模型在两个相似工具之间反复选错，说明这两个工具的职责边界没写清，要么合并，要么把 description 的差异拉开。经验上单场景 5～10 个工具是个起步区间，具体要按自己的错误率调。

### 追问二：命名真有那么重要吗，不就是个名字？

命名是模型选工具的第一信号，比 description 更早被读到。一个叫 `manage_user` 的工具和一个叫 `disable_user_account` 的工具，后者几乎不需要额外解释。命名要动词开头、读写可分，避开 `handle`、`process` 这类空词，也别让两个名字只差一个介词。前面聊工具幻觉时提过的「读写边界一眼可分」，落到设计阶段就是命名规范这件事。

### 追问三：幂等具体怎么实现，是不是所有工具都要？

不是所有工具都要，只有写工具才必须。读工具天然幂等，重试多少次结果都一样。写工具要有幂等键：优先用业务侧已经存在的唯一标识（订单号、工单号），没有再考虑对参数规范化取哈希，或者维护一张去重表。关键有两点：键由业务侧生成、不让模型编；查重和实际执行放在同一个事务里，堵住并发漏网。

### 追问四：可观测会不会太重，记那么多字段值不值？

值得，而且只记必要的五样：请求、参数、耗时、结果、错误码，用 trace_id 串起来。这点开销换来的是出问题能定位：选错、填错、超时、下游返回错内容，这几种失败靠字段一目了然。真要减负，可以对高频只读工具降采样，但写工具的调用建议全记——它牵涉副作用，事后追责全靠这些记录。

### 追问五：这套设计原则和之前讲的护栏是什么关系？

分工不同，互为补充。护栏是运行时防御：调用发生了，用白名单、schema 校验、副作用确认把错误拦住，重点在「出错也不出大事」。设计原则是事前功夫：把工具切好、描述清、做成可失败可幂等，重点在「让错误少发生，也让护栏有东西可拦」。工具设计糟，护栏再厚也只能拦住一部分；工具设计好，护栏才能专注对付真正棘手的边界情况。

### 追问六：工具上线之后，怎么判断设计得好不好？

看四个数：选错率（调了不该调的工具）、参数校验失败率、重试率、人工接管率。选错率高多半是粒度和命名的问题；参数失败率高是 schema 或 description 没写清；重试率高要看是下游不稳还是超时设置太紧；人工接管率高说明工具的失败反馈没让模型有能力自救。之前讲效果排查时的分层归因思路，用在工具上就是把这四个数分别对应到四类设计问题，别笼统地归成「模型不行」。

## 60 秒面试回答模板

> 我按四条原则设计一个生产可用的工具。单一职责，一个工具只做一个业务动作，别做塞十几个 action 的万能工具；明确 schema，类型、枚举、必填写全，命名动词开头、读写一眼可分，description 补上什么时候不该用；可观测，每次调用用 trace_id 串起请求、参数、耗时、结果和错误码；可失败，带超时、异常码和降级，不假设一定成功。工具一旦要写业务系统，再加三样：权限校验、幂等和审计日志。幂等键由业务侧生成，查重和执行放同一事务。我的判断标准是模型看得懂、调得动，出错追得到、兜得住，而不是只求调通。

## 加分项

- **把粒度和轮数算成一笔账**：讲清「切太细 → 轮数和 token 涨，切太粗 → schema 复杂选错多」，说明你权衡过，不是背原则。
- **幂等键由业务侧生成**：明确不让模型编幂等键、查重与执行同事务，这两点比「我们做了幂等」有说服力得多。
- **可观测做成统一出口**：所有工具走同一个 trace 落点，避免漏记造成排查盲区，这是工程化的做法。
- **用四个数收口**：选错率、参数失败率、重试率、人工接管率，把「设计好不好」变成可观测的指标，而不是感觉。

## 常见误区

- **把「大而全」当省事**：一个万能工具接口数少，却把选择和填参的难题甩给模型，出错还难定位。
- **用查工具的思路设计写工具**：没有幂等、没有权限、重试随便开，这是写操作出事故的主要原因。
- **幂等只加个键就完事**：查重和执行不在同一事务，并发下照样重复执行；键让模型自己编，更是埋雷。
- **工具描述只写「能做什么」**：不写适用边界和反例，模型在相近工具之间就会反复选错。
