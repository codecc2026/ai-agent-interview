# Token 和上下文窗口是什么？它们在工程上意味着什么？

## 面试官为什么爱问这题

第 2 篇我们聊的是上线前要盯哪些指标，而这一题是那一堆指标的底座：延迟、成本、能不能做长文问答，几乎都从同一个数字推出来——这次请求要吃掉多少 token。

题库给它的标签是「基础、高频」，但面试官问它往往不是想听定义。他真正确认的是三件事：你有没有把 token 当字数算过账；你知不知道窗口有上限、超了会发生什么；你能不能把「窗口变大了」和「该不该塞满」这两件事分开讲。

只会背「token 是最小单位、128K 是很长一段内容」的人，答完定义就卡住了。能把窗口讲成一本总账——系统提示、历史对话、检索结果、用户问题、预留输出在上面排队——才算答到点上。

## 一句话先给结论

**Token 是模型计量文本的最小单位，不等于字数；上下文窗口是单次请求里输入与输出共用的 token 上限。工程上它意味着：上下文是一本总额固定的账，越塞越贵、越塞越慢，超了就得裁，所以「塞满」从来不是最优解。**

## Token：模型看到的不是字，是编号

模型训练和推理时看到的不是原始文本。文本先过 tokenizer，被切成一串编号，模型在这串编号上做计算，输出时再解码回文字。

所以「一段话有多少 token」由三件事共同决定：**tokenizer 的切分规则**、**语言类型**、**文本形态**。同一个意思写成中文、英文、代码、JSON、带大量标点的表格，切出来的数量都不一样。

这就是为什么不能把 token 当字数用——它是切分结果，不是字符计数。由此推出两条工程结论：

- **账单按 token 算，不按字数算。** 你按字数做的预算，和实际消耗常常差出一截。
- **估算只能用经验系数。** 要精确卡窗口，就用对应模型的 tokenizer 真跑一遍，不要拿系数硬套。

## 上下文窗口：一次请求的总账

窗口说的是：**这次请求里，系统提示、历史对话、检索结果、用户问题加起来最多能塞多少 token**。题目里常提的 8K、32K、128K，说的都是这个总额。

三个最容易讲混的边界：

- **它不等于最大输出长度。** 输出额度通常由单独的参数限制（例如 `max_tokens`），在很多模型的 API 里，输入和输出合起来占用同一份窗口额度——具体规则以你接入的那家文档为准。
- **它是每次请求的额度，不是累计额度。** 开一轮新请求就是一本新账，历史不会自动延续，除非你把历史重新拼进这次请求里，而拼进去的部分同样要计费。
- **它是硬上限，不是尽力而为。** 超出部分不会被"稍微处理一下"，只会被截断、被压缩，或者请求直接报错。

按题目给的常见经验口径：1 个中文字符约 `0.6` 个 token，1 个英文字符约 `0.3` 个 token，据此 `128K token` 大致对应二十万级别的中文字符量级。这只是估算，tokenizer、语言类型、代码、标点和格式都会让它波动。

## 概念边界表

这四个概念在面试里被混说的概率极高，先把边界钉死：

| 概念 | 它到底是什么 | 最容易被讲错成 |
| --- | --- | --- |
| Token | tokenizer 切出来的最小计量单位，模型在编号序列上计算 | 「字数」或「单词数」，按字符数估成本 |
| 上下文窗口 | 单次请求可用的 token 总额上限 | 「最多能输入多少字」，漏掉输出也占额度 |
| 最大输出长度 | 限制本次最多生成多少 token 的参数（如 `max_tokens`） | 与上下文窗口是同一个东西 |
| 外部知识库 / 检索 | 内容放在模型外面，按需取回再拼进窗口 | 「窗口够大就不需要检索了」 |

## 不同形态的内容，换算口径不一样

同一段信息换成不同载体，token 消耗差别很大。这张表用于在动手前粗估预算——**都是经验口径，不能当精确值**：

| 内容形态 | token 换算的经验口径 | 备注 |
| --- | --- | --- |
| 中文正文 | 1 个中文字符约 0.6 个 token | 题目给出的常见经验口径 |
| 英文正文 | 1 个英文字符约 0.3 个 token | 同上 |
| 代码、JSON、表格 | 通常比同长度的自然语言更费 token | 缩进、括号、标点、字段名都计入 |
| 系统提示与 few-shot 示例 | 按实际文本计算，每次请求都重复付一遍 | 长系统提示是固定成本 |
| 多轮历史 | 每轮都重复计入，随轮次线性增长 | 多轮对话成本的主要来源 |

## 工程实践：把 token 数算出来再发请求

最重要的动作只有一个：**发请求前先数一遍，而不是等它报错再处理**。下面是一个能直接改用的骨架，用的是 OpenAI 开源的 `tiktoken` 库，encoding 要换成你所接入模型对应的那一个：

```python
import tiktoken

ENC = tiktoken.get_encoding("cl100k_base")  # 换成接入模型对应的 encoding

def count_tokens(text: str) -> int:
    return len(ENC.encode(text))

def fit_context(system, history, question, retrieved, *, budget, reserve_output):
    """按优先级装填上下文：系统提示 > 用户问题 > 检索片段 > 历史轮次"""
    used = count_tokens(system) + count_tokens(question) + reserve_output
    left = budget - used
    if left <= 0:
        raise ValueError("预算装不下系统提示 + 问题 + 预留输出")

    kept_docs = []
    for doc in retrieved:                 # retrieved 已按相关度从高到低排好
        t = count_tokens(doc)
        if t > left:
            continue                      # 装不下就跳过，不要截断成半句话
        kept_docs.append(doc)
        left -= t

    kept_turns = []
    for turn in reversed(history):        # 历史从最近一轮往回取
        t = count_tokens(turn["content"])
        if t > left:
            break
        kept_turns.insert(0, turn)
        left -= t

    return {
        "system": system, "history": kept_turns,
        "retrieved": kept_docs, "question": question,
        "used_tokens": budget - left,
    }
```

这段代码里有三个值得单独说的设计：

1. **`reserve_output` 先扣。** 很多超时和 `finish_reason` 异常的根源，是输入把窗口占满、输出没地方放了。经验上先给输出预留一部分额度（常见做法是窗口的 `10%`–`20%`，这是工程经验区间，不是规范），再谈输入怎么装。
2. **检索片段不截断成半句。** 宁可整段丢弃，也别塞进一个被切掉结论的片段——半截文档比没有文档更容易诱发幻觉。
3. **`used_tokens` 要打进日志。** 后面做成本归因、找「为什么这个用户这么贵」时，这个字段是最直接的依据。

## 上下文超了，按什么顺序砍

不是随便删。优先级从高到低大概是：**系统提示 → 当前用户问题 → 输出预留 → 高相关检索片段 → 近期历史 → 早期历史**。理由很直接：系统提示和当前问题决定这次任务是什么，砍掉就等于跑错任务；而最早那几轮对话，往往已经在后来的对话中被复述过。

| 策略 | 做法 | 代价 | 适合场景 |
| --- | --- | --- | --- |
| 丢最老轮次 | 从最早的历史往下砍，保留最近若干轮 | 可能丢掉开头交代的约束 | 任务型多轮对话 |
| 历史摘要压缩 | 让模型把早期对话压成一段摘要再放回 | 多一次调用，细节有损 | 长会话、用户会回头引用前文 |
| 检索结果裁剪 | 只保留 top-k，或按剩余额度取舍 | 召回不足时直接掉效果 | RAG 场景 |
| 去重与合并 | 重复文档、重叠片段先合并再拼 | 需要额外判断相似度 | 多路召回合并后 |
| 预留输出额度 | 从预算里先扣掉输出要用的部分 | 输入可用额度变少 | 所有场景都应该做 |

## 面试官的追问，你该怎么接

### 追问一：1 个汉字、1 个英文单词大概是多少 token，为什么不能死记一个固定值？

先给经验口径：1 个中文字符约 `0.6` 个 token，1 个英文字符约 `0.3` 个 token，所以一个常见英文单词大致落在 1 到 3 个 token 这个区间。

**不能死记的原因要说透，这是加分关键：**

- **切分规则由 tokenizer 决定**，不同模型、不同版本的 tokenizer 切法不同，同一个词换一个模型可能就不是同一个数。
- **切分粒度不是词。** 常见词可能整体是一个 token，生僻词、专有名词、数字会被拆成多个片段，所以「一个单词等于一个 token」这句话本身就是错的。
- **文本形态影响很大。** 代码、JSON、表格里的缩进、括号、标点、字段名都要计 token，同样长度的代码通常比自然语言更费。
- **标点与空白也计入。** 这一点最常被忽略，也是"按字数估算"失真的主因。

回答的落点是：**估算用系数，卡边界用 tokenizer 真跑。**

### 追问二：如果上下文被截断了，你会优先怎么处理？

分四步走，顺序不能反：

1. **先确认信息到底丢了没。** 看响应的结束原因（很多 API 会返回 `finish_reason` 之类的字段）和返回的用量统计，判断是被截断，还是压根没进去。
2. **再排优先级。** 系统提示、当前问题、高相关检索片段保留，早期历史先砍，按上一节那张表的顺序来。
3. **能压缩就别硬删。** 早期历史压成摘要，比直接丢掉更不容易破坏指代关系；检索片段则反过来——宁可整段丢，也不要半截。
4. **最后补上可观测与兜底。** 截断次数要上报；如果砍完仍然装不下核心信息，就降级：走检索、拆成多次请求，或者明确告诉用户「这份内容超长，请指定范围」，而不是悄悄给一个不完整的答案。

### 追问三：窗口做到 128K 甚至更长，是不是就不需要 RAG 了？

不是，这是两个维度的事。可以分三层说：

- **成本与延迟**：把全部资料常驻进窗口，意味着每一条请求都要为这些 token 付一遍钱、等一遍时间。检索只把相关的几段放进去，成本结构完全不同。
- **上限永远存在**：资料库会增长，长上下文只是把天花板抬高，并没有取消天花板。今天装得下，明年不一定。
- **注意力稀释**：相关内容被大量无关文本包围时，模型更容易抓错重点。检索做的是"先筛一遍"，这和"能不能装下"是两件事。

结论：**长上下文降低了对检索的依赖程度，但没有替代检索。**

### 追问四：`max_tokens` 和上下文窗口是同一个东西吗？

不是。窗口是**这次请求总的额度**，`max_tokens` 是**限制这次最多生成多少 token 的参数**。两者的关系是：输出额度通常要设在窗口之内，在很多模型的 API 里，输入 token 与输出 token 合起来不能超过窗口——具体规则以所接入模型的文档为准。

对应的两个坑：

- 把 `max_tokens` 设得过大，可能导致输出还没写完就把窗口耗尽，响应看起来是"话说到一半断了"。
- 反过来设得过小，长答案会被硬截断，用户看到半句话，而 HTTP 状态码依然是 200，不判业务语义失败的话监控上根本看不出来（这一点和第 2 篇讲的语义判失败是同一个道理）。

### 追问五：多轮对话一直累积，成本和延迟怎么控？

历史是每轮都要重复计入的，所以多轮对话的成本大致随轮次增长。常见的四种控制手段：

- **轮次窗口**：只保留最近若干轮，超出部分直接不进请求。
- **滚动摘要**：超过阈值后把早期对话压成摘要，用摘要替代原文。
- **结构化留存**：把已确认的关键信息抽成字段（如用户目标、已填参数）放在系统提示里，比保留整段对话省得多。
- **缓存复用**：对稳定的前缀内容，看接入的服务是否支持前缀缓存一类能力，避免重复计算。

判断标准是：**保留的是"模型下一步需要的信息"，不是"用户说过的话"。**

## 60 秒面试回答模板

> Token 是模型计量文本的最小单位，由 tokenizer 切分产生，不等于字数，也不等于单词数。模型看到的不是原始文本，而是一串编号。

> 上下文窗口是单次请求里输入和输出共用的 token 上限，常说的 8K、32K、128K 都是这个总额。系统提示、历史对话、检索结果、用户问题都要在里面排队，输出也要占额度。

> 工程意义有三条：它决定了能不能做长文问答和长多轮；token 越多成本越高、延迟也更容易上升；超出窗口的内容会被截断或根本进不了模型，所以不是塞得越多越好。

> 真到工程上，我会在发请求前先用 tokenizer 数一遍，给输出预留额度，然后按优先级裁剪——系统提示和当前问题必留，早期历史先砍，检索片段宁可整段丢也不截成半句，并把用量打进日志做成本归因。

## 加分项

- **能说出「输出也占窗口」**，并且知道要先给输出预留额度——很多人只算输入。
- **能区分「长上下文」和「检索」**：前者抬高天花板，后者做筛选，不是互相替代的关系。
- **能给出可执行的裁剪顺序**，而不是一句"超了就截断"。
- **能把 token 用量打进日志**，把它当成成本归因的一等公民。

## 常见误区

1. **把 token 当字数。** 按字符数估成本，预算和实际账单对不上。
2. **把窗口当"能输入多少字"。** 忘了输出也占额度，长答案被截断还查不出原因。
3. **认为窗口大就该塞满。** 塞满带来的是更高的成本、更长的延迟，以及被无关内容稀释的注意力。
4. **认为长上下文能取代检索。** 上限只是被抬高，没有被取消，成本结构反而更差。
