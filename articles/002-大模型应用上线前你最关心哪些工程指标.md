# 大模型应用上线前你最关心哪些工程指标？

## 面试官为什么爱问这题

第 1 篇我们聊的是方案层面的取舍：RAG 还是微调。这一篇往下走一层，问的是**你怎么证明这个方案在线上是活的**。

题库给这道题标的考察点只有一句话：是否具备生产环境意识。这句话翻译过来就是——你会不会只盯着"模型答得准不准"，而忽略延迟、成本、故障和可追溯性。

做过 Demo 的人和做过线上的人，回答这道题的差别非常明显。前者的答案是"准确率、响应速度、成本"三个词；后者的答案里有口径、有分位数、有阈值、有降级，还有"这个指标怎么骗人"。

## 一句话先给结论

**上线前要能回答五个问题：答得对不对、快不快、贵不贵、稳不稳、出了事查不查得到。** 对应效果、性能、成本、稳定性、治理性五个维度，缺一个都不算能上线。

这五个维度不是并列的清单，而是一条链：效果决定有没有人用，性能决定用户愿不愿意等，成本决定这门生意成不成立，稳定性决定口碑，治理性决定你多快能止血。

## 五个维度，每个都有口径问题

### 效果：别只报一个准确率

题库给的四个指标各有分工，混着说就等于没说：

- **准确率**：答案对不对。
- **忠实度**：答案是不是只依据检索到的内容，没有自己编。RAG 场景里这个指标比准确率更敏感。
- **任务完成率**：端到端任务有没有完成，而不是单轮答对。多轮工具调用的 Agent 必须看这个。
- **引用正确率**：引用的那段文档，是不是真的支持这句话。

**准确率高不代表可用。** 举个常见情形：答案对了，但引用挂到了另一篇文档上。业务方验收时会直接判不合格，因为用户点进去发现原文不支持，信任就没了。所以在 RAG 项目里，我通常把"忠实度 + 引用正确率"和准确率放在同一层级看，而不是当成附属指标。

还有一个容易被漏掉的：**拒答率**。很多团队不统计它，但拒答率突然上涨，往往意味着检索层出了问题——召回不到东西，模型只能说不确定。它是最早的报警信号之一，比准确率下跌来得更早。

### 性能：首 token 延迟比总延迟更重要

- **首 token 延迟（TTFT）**：从发请求到吐出第一个字的时间。这是用户真正感知到的"响应速度"。
- **端到端延迟**：一次完整回答的总耗时。
- **P95 / P99**：分位数。

为什么强调 TTFT？因为生成是流式的。用户看到第一个字之后，后面慢慢出字是可以接受的；但如果两三秒一个字都不出，他会怀疑页面卡死了。经验值上，交互式场景把 TTFT 压到 1 秒上下体感较好，超过 2 秒就开始明显掉体验——这是工程经验区间，不是行业标准。

**平均值会骗人。** 100 个请求里 95 个 800ms、5 个 8s，平均值看着很漂亮，但每天有 5% 的用户在骂人。所以性能指标一律看 P95/P99。

这里有个特别容易踩的坑：**只统计成功请求的延迟**。超时那批恰恰是最慢的，把它们从分母里剔掉，P95 会假性变好，你会误以为优化生效了。正确做法是超时样本按超时阈值计入统计。

### 成本：三层结构，摊到单任务

- **token 消耗**：输入和输出要分开算，输出单价通常更高。
- **检索成本**：向量库查询、embedding 调用。
- **工具调用成本**：外部 API 往往按次计费，Agent 多跑几轮就翻倍。

关键口径是：**成本要摊到"单次成功任务"，不是"单次调用"**。因为重试、降级、多轮工具调用都会把分母做大。你按调用算出来 3 分钱一次，按任务算可能是 1 毛 5，差的这 5 倍就是重试和兜底吃掉的。

同时要盯一个指标：**缓存命中率**。同一批高频问题反复打模型，是最没必要的开销。

### 稳定性：四个率，缺一不可

- **超时率**：超过设定阈值的请求占比。
- **错误率**：要分层看——参数错（4xx）、上游错（5xx）、限流（429）。混在一起看，你分不清是自己的问题还是供应商的问题。
- **重试率**：重试率高说明上游不稳，而且重试会同时放大成本和延迟。
- **降级命中率**：降级被触发的比例。这个指标直接反映主链路的健康度，很多人不采，等于蒙着眼睛开车。

**错误率只按 HTTP 状态码统计，是新手最常犯的错。** 大模型应用里大量失败是"200 但内容不可用"——空回答、被截断、JSON 解析不出来、工具参数不合法。这些在网关层面全是成功。所以必须补一层**业务语义判失败**：解析失败、schema 校验不过、答案长度异常，都要计入失败。

### 治理性：五件套

- **日志**：请求与响应，注意脱敏。
- **Trace**：一次请求跨检索、模型、工具的完整链路，靠 trace_id 串起来。
- **Prompt 版本**
- **索引版本**
- **权限审计**

核心是这一句：**Prompt 版本和索引版本必须能和每一条日志对上**。否则用户投诉"昨天还好好的"，你连当时用的是哪版提示词、哪版索引都查不到，badcase 根本无法复现。这是最容易被忽略、又最影响排障效率的一项。

## 五个维度速查

把上面五段压成一张表，面试前扫一眼就能回想起口径：

| 维度 | 核心指标 | 口径要点 | 最容易骗人的地方 |
| --- | --- | --- | --- |
| 效果 | 准确率、忠实度、任务完成率、引用正确率 | 忠实度与引用正确率要和准确率同级看 | 答对但引用错，业务方直接判不合格 |
| 性能 | 首 token 延迟、端到端延迟、P95/P99 | 分位数，且超时样本必须计入 | 只统计成功请求，P95 假性变好 |
| 成本 | token（入/出分开）、检索成本、工具调用成本 | 摊到单次成功任务 | 按单次调用算，漏掉重试与降级 |
| 稳定性 | 超时率、错误率、重试率、降级命中率 | 错误分层（4xx/5xx/429）＋ 语义判失败 | 只看 HTTP 状态码，200 当成功 |
| 治理性 | 日志、Trace、Prompt 版本、索引版本、权限审计 | 版本必须能和日志对上 | 只存日志不存版本，badcase 无法复现 |

## 和传统 Web 服务比，差在哪

这张表能解释为什么不能照搬原来的监控体系：

| 维度 | 传统 Web 服务 | 大模型应用 | 差异根源 |
| --- | --- | --- | --- |
| 延迟 | 看平均 RT 就够用 | 必须拆 TTFT + 分位数 | 生成是流式的，用户先看到第一个字 |
| 正确性 | 5xx、业务异常 | 语义正确性、忠实度、引用 | 返回 200 也可能是错答案 |
| 成本 | 机器带宽，近似固定 | 随 token 线性变动 | 边际成本不为零 |
| 故障定义 | 服务挂了才算 | 降级、幻觉、拒答也算 | 失败是连续的，不是二元的 |
| 变更管理 | 代码版本 | 代码 + Prompt + 索引 + 模型 | 四类版本都得能独立回滚 |

## RAG / Agent 还要多看四个

题库特别点了这四个，因为它们衡量的是**链路**而不是**模型**：

- **检索召回质量**：recall@k、命中率。检索不到，模型再强也是无米下锅。
- **工具调用成功率**：要区分"调用失败"和"选错工具"。前者是工程问题，后者是理解问题，修法完全不同。
- **人工兜底比例**：转人工率。它是最诚实的体验指标。
- **badcase 回灌效率**：从发现一个问题，到它进入评测集/训练集，花了多久。这个"时长"指标决定了你的系统会不会越用越笨。

## 工程实践：最小可用的埋点

不用一上来就上全套 APM。一次请求记一条结构化日志，字段齐了，后面什么看板都能拼出来：

```python
import time, json, logging

def traced_stream(call_model, *, prompt_version, index_version, model):
    rec = {
        "prompt_version": prompt_version,
        "index_version": index_version,
        "model": model,
        "ttft_ms": None,
        "total_ms": None,
        "error": None,
    }
    t0 = time.perf_counter()
    try:
        for chunk in call_model():
            if rec["ttft_ms"] is None:
                rec["ttft_ms"] = round((time.perf_counter() - t0) * 1000)
            yield chunk
    except Exception as e:
        rec["error"] = type(e).__name__
        raise
    finally:
        rec["total_ms"] = round((time.perf_counter() - t0) * 1000)
        logging.info(json.dumps(rec, ensure_ascii=False))
```

有了这条日志，TTFT 分位数、超时率、错误分类都是 SQL 能算出来的事。再把阈值配成一份可改的配置，而不是写死在代码里：

```json
{
  "ttft_ms_p95": 1200,
  "e2e_ms_p95": 8000,
  "error_rate": 0.02,
  "timeout_rate": 0.01,
  "fallback_rate": 0.15,
  "cost_per_task_cny": 0.05
}
```

这组数字是示例值，不是标准答案——**阈值要按你们自己的业务容忍度定，定完必须配上告警**。指标采了一堆、没有一条设阈值，等于没采。

## 面试官的追问，你该怎么接

### 追问一：你怎么设计降级策略？

分三层降，从最贵的开始塌：

- **模型层**：大模型 → 小模型 → 缓存结果 → 固定话术。
- **检索层**：向量库不可用 → 退到关键词/BM25 → 再退到固定知识包。
- **工具层**：工具超时 → 跳过该工具并明确告知"这项信息暂时查不到"，而不是硬编一个答案。

设计上有三个必须做到的点：**降级可观测**（降级命中率要上报，否则你不知道自己在降级状态下跑了多久）、**兜底不空转**（宁可给一句诚实的"暂时查不到"，也别给幻觉）、**恢复要判定**（探活通过 + 滑动窗口指标回到阈值内才恢复，不能探活成功一次就全量切回，那会造成雪崩式抖动）。

### 追问二：成本超预算，先优化哪一层？

顺序是：**先砍无效输入，再调模型路由，再压输出，最后才动检索和工具。**

1. 砍无效输入：上下文裁剪、历史轮次截断、重复文档去重、加缓存。这一步不影响效果，收益往往最大。
2. 调模型路由：把简单任务（分类、抽取、改写）切到小模型，复杂任务留在大模型。这一层要做任务分级。
3. 压输出：限制 max_tokens、强制结构化输出、减少不必要的解释性文字。
4. 最后才动检索和工具：因为这两个直接影响召回质量和能力边界，动了就是拿效果换成本。

这个顺序背后的原则是：**先动不影响效果的，再动影响可控的，最后动伤筋骨的。**

### 追问三：怎么做 Prompt / 模型 / 索引回滚？

三者都要版本化，而且要能**独立回滚**：

- **Prompt**：放配置中心，别写代码里。发布走灰度，带版本号和变更记录。
- **模型**：在路由层切流量，保留上一个版本的调用通道，出问题按比例切回。
- **索引**：用别名（alias）指向具体版本，重建新索引后先切 10% 流量验证，回滚只改别名，秒级生效。

核心要求是：**回滚要秒级，不能靠重新发版**。发版回滚十分钟，线上已经烧掉十分钟的差评了。

### 追问四：效果指标怎么定验收线？

双轨：**离线评测集 + 线上抽样**。

离线集覆盖高频场景和高风险场景（合规、金额、医疗建议这类），每次改动都跑，看相对上一版有没有退化；线上按固定比例抽样人工标注，校准离线集和真实分布的偏差。

验收线从**业务可接受度**倒推，不是从模型能力定。比如客服场景，"答错但引导转人工"是可接受的，"答错还理直气壮"是不可接受的。这意味着验收线不只是准确率数字，还要包含"错误类型分布"。

### 追问五：指标突然抖了，怎么归因？

按解释力从强到弱查，三步不能反：

1. **流量结构变了吗**：新入口、新人群、新问法。占比变化经常伪装成效果下降。
2. **依赖变了吗**：索引刚重建过？模型版本切了？Prompt 发过版？上游限流了？
3. **最后才怀疑模型随机性**。它的解释力最弱，但因为最省事，最容易被当替罪羊。

顺序反了，你会花两天调 Prompt，最后发现是索引没更新完。

## 60 秒面试回答模板

> 我会从五个维度看：效果、性能、成本、稳定性、治理性。

> 效果不只看准确率，还要看忠实度、任务完成率和引用正确率——RAG 场景里答对但引用错，业务方是不认的。性能重点看首 token 延迟和 P95/P99，不看平均值，而且超时样本必须计入统计，否则分位数会假性变好。成本要摊到单次成功任务上，因为重试和降级会把真实成本放大好几倍。稳定性看超时率、错误率、重试率和降级命中率，错误要分层看，还要按业务语义判失败，因为大模型很多失败是 200 但内容不可用。治理性上，日志、Trace、Prompt 版本、索引版本、权限审计这五样必须齐，尤其是版本要能和日志对上，否则 badcase 没法复现。

> 如果是 RAG 或 Agent 项目，我会额外盯检索召回质量、工具调用成功率、人工兜底比例和 badcase 回灌效率——这四个衡量的不是模型，是链路。

## 加分项

- 能说出「错答案也算故障」，说明你理解大模型应用的失败是连续的，不是二元的。
- 能主动把成本摊到单任务，而不是单次调用。
- 能说出「版本四件套」（代码、Prompt、索引、模型）都能独立回滚。
- 能提到降级命中率这个指标——采这个指标的人，通常真的被降级坑过。

## 常见误区

1. **只报平均值**，不分位数。用户体感由最慢那 5% 决定。
2. **只统计成功请求**，超时样本被悄悄剔除。
3. **把 HTTP 200 当成功**，不判语义失败。
4. **指标采了一堆，没一条设阈值和告警**。数据进了看板，没人看，等于没采。
