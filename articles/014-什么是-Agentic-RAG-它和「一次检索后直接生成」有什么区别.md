# 什么是 Agentic RAG？它和「一次检索后直接生成」有什么区别？

## 一句话先给结论

**传统 RAG 是固定流水线：检索一次、拼上下文、生成答案；Agentic RAG 是闭环：模型根据当前进展动态决定要不要检索、检索什么、要不要改写 query、要不要补检，证据不足时主动回头重查。两者最大的区别不在「有没有检索」，而在检索是不是被当成一个动态决策过程来管理。**

## 面试官为什么爱问这题

因为这题是「背过流水线」和「理解检索边界」的分水岭。RAG 的标准链路人人会背，但背链路的人有个盲区：他们默认「一次检索拿到的证据够用」。而实际系统里，相当一部分 badcase 恰恰卡在第一跳——问题需要拆问、证据分散在多份文档、甚至要先判断该查知识库还是查业务系统。这时继续调 embedding、换切块策略，边际收益趋近于零，因为瓶颈根本不在检索质量，在检索次数。

这题考察的是：你能不能识别出「固定流水线的隐含假设失效」的场景，同时不被 Agentic 这个词吸走注意力——它的代价是链路更长、成本更高、失控风险更高，题库原话讲得很直白，不装护栏的 Agentic RAG 会从「更聪明的检索」变成「更贵的随机游走」。能同时讲清收益条件和代价清单的人，才是真在业务里权衡过的人。

另外提醒一句概念边界：Agent ≠ Workflow。把「先查库、不够再查网页」用代码写死，那是固定编排；由模型在运行时自主决定下一步做什么，才是 Agentic。这条线贯穿全文。

## 核心原理：从「一次交卷」到「动态决策」

### 固定流水线的隐含假设

传统 RAG 的链路是稳定的：query 进来 → 检索一次 → top_k 结果拼进上下文 → 生成。它的优点题库给了三条：流程稳定、成本可控、实现简单——每次请求的调用量是确定的，延迟可以预估，出问题归因也简单。所以单轮问答和大多数标准知识库场景，它就是正解，不需要升级。

但它有一条隐含假设：**一次检索就能拿到足够的证据**。这条假设在两类问题上会失效：一是问题本身要拆——「A 公司收购 B 公司后，B 的专利归属和股价各自怎么变」需要拆成两个子问题分别检索；二是证据要交叉验证——单来源可能过时、可能片面，需要多源互证。固定流水线对这两类问题不是答得差，是结构上答不了：它没有「发现证据不够」这个环节。

### Agentic RAG：检索变成被管理的决策过程

Agentic RAG 把检索从「链路中的一步」变成「可以被反复调用、被动态选择的工具」。题库列出的决策点有四个：要不要检索、检索什么、是否改写 query、是否继续补检；再加上发现证据不足时主动回头重查。落到机制上，就是一个循环：

- **规划**：模型先判断当前问题缺什么证据，决定这一轮查什么、怎么改写 query；
- **执行**：调用检索工具，可能路由到知识库、网页或业务系统；
- **自检**：拿到证据后评估够不够、矛不矛盾，决定是进入生成、继续补检，还是换方向重查；
- **退出**：满足条件才生成答案。

收益对应的是题库点出的三类 badcase：一次检索经常拿不到足够证据、问题需要拆问或多轮求证或多源交叉验证、生成前需要先路由判断查哪个源。而代价同样是结构性的：链路每多一跳，延迟和 token 成本都叠上去；决策权交给模型，就存在决策错、绕圈、反复检索同一个 query 的可能——这就是「失控风险更高」的具体含义。

### 边界：不是「更高级」，是「更贵」

题库的工程判断很冷静：**通常不会一开始就上 Agentic RAG**，而是先看 badcase 是否真的集中在上面那三类问题上。这个顺序值得展开：如果 badcase 主要是「检索到的内容不对题」，那是召回质量问题，改 query 改写、调切块、加 rerank 都可能解决，固定流水线就够；只有 badcase 集中在「证据不够、需要拆问、需要路由」上，升级才有意义。先归因，再选架构——顺序反了就是把 Agentic 当银弹。

## 横向对比：两种 RAG 的取舍

| 维度 | 传统 RAG（固定流水线） | Agentic RAG（动态闭环） |
| --- | --- | --- |
| 检索次数 | 固定一次 | 零到多次，由模型按进展决定 |
| 决策方 | 代码写死的链路 | 模型在运行时自主决策 |
| 典型成本 | 每请求调用量确定，可预估 | 随跳数线性叠涨，方差大 |
| 失控风险 | 低：路径唯一 | 高：可能绕圈、重复检索、拒不退出 |
| 适合场景 | 单轮问答、标准知识库 | 多跳证据、拆问求证、多源路由 |
| 归因难度 | 低：错在检索或生成二选一 | 高：错可能在任何一跳的决策上 |

第二张表把「该不该升级」的判断依据列出来，这也是追问二的正面答案：

| badcase 信号 | 固定流水线的表现 | 对应的 Agentic 能力 |
| --- | --- | --- |
| 一次检索拿不到足够证据 | 上下文里只有半截事实，模型硬答或幻觉 | 自检发现证据不足，改写 query 补检 |
| 问题需要拆问 / 多轮求证 / 交叉验证 | 子问题没机会分别检索，答案混在一起 | 先拆问再逐个检索，最后汇总 |
| 不知道该查知识库 / 网页 / 业务系统 | 只能查一个源，答非所问 | 生成前先路由，按问题类型选源 |

## 工程实践：护栏四件套

题库点名的四个护栏——步数上限、预算限制、失败退出条件、可观测性——缺一个都会出事。先看各自管什么：

| 护栏 | 管住什么失控 | 机制 | 不装的事故 |
| --- | --- | --- | --- |
| 步数上限 | 无限循环、绕圈 | 硬性 max_steps（经验值 3～5 步） | 两个子问题互相触发检索，永远不收敛 |
| 预算限制 | 成本失控 | token / 调用次数上限，超了强制走降级 | 一个疑难 query 吃掉整个请求预算 |
| 失败退出条件 | 拒不承认证据不足 | 连续 N 次补检无新证据即停（经验值 N=2） | 反复查同一 query，烧钱不出结果 |
| 可观测性 | 无法归因 | 每一跳的决策与结果落日志 | badcase 只能重放，答不出「哪一跳错了」 |

写成代码骨架大概是这样（伪代码）：

```python
# 伪代码：带护栏的 Agentic RAG 主循环
def agentic_rag(question, budget, max_steps=5, max_empty=2):
    state = {"evidence": [], "tried_queries": set()}
    for step in range(max_steps):              # 护栏 1：步数上限
        if budget.exhausted():                 # 护栏 2：预算限制
            return fallback_answer(state)      # 降级：用已有证据给保守答案
        plan = model.decide(question, state)   # 模型决策：补检 / 改写 / 直接生成
        if plan.action == "generate":
            return model.generate(question, state.evidence)
        if plan.query in state.tried_queries:
            continue                           # 查过的 query 不再查，防绕圈
        hits = retrieve(plan.source, plan.query)   # 路由到知识库 / 网页 / 业务系统
        new = dedupe(hits, state.evidence)
        if not new:
            state.empty_rounds += 1
            if state.empty_rounds >= max_empty:    # 护栏 3：失败退出
                return fallback_answer(state)
        state.evidence += new
        state.tried_queries.add(plan.query)
        log(step, plan, hits, state)           # 护栏 4：可观测性
    return fallback_answer(state)              # 步数耗尽也走降级，不硬答
```

四个细节值得抠：`tried_queries` 防的是最隐蔽的失控——模型换个说法重查同一个问题，日志里每次都是「新 query」，实际毫无进展；空轮计数 `max_empty` 是失败退出的判定依据，「连续补检没有新证据」比「模型自己说够了」可靠得多；所有退出路径最后都指向 `fallback_answer`，用已有证据给保守答案或明说「证据不足」，绝不硬答；`log` 必须记决策而不只记结果——复盘时要知道模型当时为什么选择补检，这是 Agentic 特有的归因需求。

## 追问逐条作答

### 追问一：什么情况下应该坚持固定 RAG，而不是升级成 Agentic RAG？

三条判据都满足就别动：一是 badcase 主要集中在检索质量（查到的不对题），改写、切块、rerank 还有空间；二是问题形态以单轮问答为主，一次检索的证据通常够用；三是对延迟和成本敏感——固定流水线每次调用量确定，这个确定性本身就是产品特性（比如面向 C 端的秒级问答）。升级的动机必须来自 badcase 归因，不能来自「Agentic 更先进」。

### 追问二：Agentic RAG 的收益通常体现在哪些 badcase 上？

就是题库那三类，可以各配一个画像：一次检索拿不到足够证据的，表现为「答案只覆盖问题的一半」；需要拆问和多源交叉验证的，表现为「单来源答案过时或片面，换个问法又给相反结论」；需要路由的，表现为「问题明明在业务系统里，模型拿知识库的相近内容硬套」。共同点是：这些 badcase 在固定流水线里无论怎么调检索参数都治不好，因为病根在「只查一次、只查一个源」这个结构上。

### 追问三：如何防止多轮补检把延迟和成本拉得太高？

分三层。硬层：步数上限、token / 调用预算、失败退出条件——这三个是保险丝，触发了就降级出保守答案，宁可答得保守也不无限等。软层：查过的 query 去重、每轮补检必须带「上一轮缺什么」的新意图（防止换皮重查）、补检证据做去重合并控制上下文长度。观测层：延迟和跳数做成监控指标，P95 跳数持续上涨说明模型在变相绕圈。经验值：多数多跳问题 3 步内应该收敛，超过 5 步还没收敛的请求，大概率不是步数不够，是问题该被路由到人工了。

### 追问四：把「先查库、不够再查网页」用代码写死，算 Agentic RAG 吗？

不算，这是 Workflow——固定编排的检索循环。区别在决策方：写死在代码里的分支，无论跑多少次都走同样的路径，行为可完全预测；Agentic 的特征是模型在运行时看着当前证据决定下一步，路径因问题而异。两者不冲突反而互补：工程上常见的做法是骨架用 Workflow 定死（循环、护栏、退出都在代码里），循环内部「这一跳查什么、够不够」交给模型决策。纯 Workflow 聪明度不够，纯 Agentic 失控风险高——「Workflow 管流程、模型管决策」是稳妥的中间态。

### 追问五：模型怎么判断「证据不足、需要补检」？判错了怎么办？

机制上通常是在每轮检索后让模型对当前证据做自评：覆盖了问题的哪些子面、缺什么、缺的证据大概率在哪个源——把缺失项转成下一轮的 query。判错有两个方向：误判「够了」提前生成，靠生成端的引用校验兜底（引用支撑不了论断就打回）；误判「不够」反复补检，靠追问三里的空轮退出兜底。要点是：自评结论要落进日志，因为「模型为什么觉得证据不够」是这类系统最值得复盘的决策数据。

### 追问六：Agentic RAG 会引入哪些固定流水线没有的新风险？

两个。一是注入面变大：检索回来的网页内容直接进入上下文，而模型还会据此决定下一步动作——第 10 篇讲过的 Prompt Injection 在这里从「污染答案」升级成「操纵行为」，恶意网页可以诱导它去查不该查的源。对策是外部内容做隔离标注、动作白名单限死它能动用的工具。二是决策不可复现：同一个问题两次运行可能走不同路径、给不同答案，回归测试要按「证据集合 + 最终答案」而不是「完整轨迹」来断言，否则测试天天红。这两个坑固定流水线都没有，升级时必须一起补。

## 60 秒面试回答模板

> 两者的区别不在有没有检索，而在检索是不是被当成动态决策来管理。传统 RAG 是固定流水线：查一次、拼上下文、生成，流程稳定、成本可控，适合单轮问答和标准知识库。Agentic RAG 是闭环：模型根据进展决定要不要检索、检索什么、改写 query 还是补检，证据不足主动回头重查，适合多跳证据、需要拆问和路由的场景——代价是链路更长、成本更高、失控风险更高。

> 所以我不会一开始就上，先看 badcase 是否集中在「一次检索拿不到足够证据、需要拆问交叉验证、需要先路由选源」这三类上。真要落地，四道护栏必须同时装：步数上限、预算限制、失败退出条件、可观测性——不装的话，它就不是更聪明的检索，是更贵的随机游走。

## 加分项

- **先归因再选架构的顺序感**。开口第一句不是「Agentic 更强」，而是「badcase 集中在哪」，直接把自己和银弹型候选人区分开。
- **「更贵的随机游走」这个代价表述**。能说出失控的具体形态（绕圈、换皮重查、拒不退出），说明真想过决策循环的失败模式。
- **Agent 与 Workflow 的边界**。主动点出「代码写死的检索循环不是 Agentic」，再给出「骨架 Workflow 化、决策交给模型」的混合架构，这是概念准确性的直接证明。
- **可观测性落在决策层**。强调日志要记「模型为什么决定补检」而不只是检索结果——Agentic 特有的归因需求，多数人答不到这层。

## 常见误区

- **把 Agentic 当升级必选项**。固定 RAG 在单轮问答上流程稳定、成本可控，本身就是正解；为「先进」而升级，是用确定的成本换不确定的收益。
- **只讲收益不讲护栏**。四个护栏是题库明写的前提条件，缺一个，「聪明检索」和「随机游走」之间就没有边界。
- **拿 Agent 框架名当答案**。这题考的是检索决策化的边界和代价，报菜名式列框架说不出「模型在哪个环节决策、失控在哪」。
- **混淆改写 query 与补检**。改写是对同一次检索的输入修正，补检是基于已有证据的追加检索，触发条件和目的都不同。
