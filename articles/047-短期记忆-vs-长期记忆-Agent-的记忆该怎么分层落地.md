# 短期记忆 vs 长期记忆：Agent 的记忆该怎么分层落地？

## 面试官为什么爱问这题

这是必刷题，出现频次高，因为它是对话系统和 Agent 状态设计的基本功。很多人把"记忆"当成一个东西，往 prompt 里一股脑塞历史，结果上下文越来越长、成本越来越高、效果还越来越差——因为真正相关的信息被一堆无关历史淹没了。面试官想听的是你能不能分清三个容易混的概念：上下文窗口、短期记忆、长期记忆，并说清各自放什么、怎么取、为什么不这么分层就会出问题。这题还爱顺着追问截断策略、Redis 的作用、记忆和 RAG 的区别，都是在考你有没有真的设计过一套状态系统。前面讲图的持久化时提过 checkpointer 存线程内状态、Store 存跨会话信息，这一篇把视角拉到整个记忆体系，看三层怎么分工落地。

## 一句话先给结论

**上下文窗口是模型单次推理能看到的内容上限，短期记忆是会话级状态，长期记忆是跨会话保留的用户或任务信息，三者不能混为一谈。窗口是昂贵资源，不能无限塞历史；短期记忆保留当前任务相关历史、摘要和线程状态；长期记忆存偏好、画像、历史结论和可复用事实，按需检索，不应该每次全量放进 prompt。成熟系统是：窗口里只放高信号上下文，短期记忆保证当前线程不断档，长期记忆通过数据库或向量库按需召回。**

## 核心原理：三层各司其职

### 上下文窗口：昂贵且有限的稀缺资源

窗口是模型单次能看到的全部内容，它的关键属性是"贵且有限"：按 token 计费，装得下多少有硬上限。所以往窗口里塞什么，是设计的核心问题。一个常见的错误是把所有历史都堆进去，结果是成本上去了、相关信号却被稀释，模型在长上下文里容易顾此失彼。窗口里应该只放对当前这一步真正有用的高信号上下文。

### 短期记忆：保证当前线程不断档

短期记忆是会话级的状态，管的是"这次对话/这个任务进行到哪"。它保留当前任务相关的历史、摘要和线程状态。在 LangGraph 这类框架里，checkpointer 按 `thread_id` 存的状态就属于这一层——前面聊持久化时说过，它服务于断点恢复和多轮承接，作用域是线程内。短期记忆的目标是让当前线程不因为窗口截断而丢失上下文线索。

### 长期记忆：跨会话、按需召回

长期记忆是跨会话保留的信息，存的是偏好、画像、历史结论和可复用事实。它和短期记忆的根本区别是生命周期：短期记忆随会话走，长期记忆跨越会话长期留存。前面讲 checkpointer 时提过，跨会话的长期信息走的是另一条线（Store 这类），这里补的是它怎么用。

关键原则：长期记忆按需检索，不应该每次全量放进 prompt。一个用户积累的长期记忆可能有几百上千条，全塞进去既不现实也没必要。正确做法是存到数据库或向量库，当前任务需要时按相关性召回一小部分进窗口。

| 层 | 存什么 | 生命周期 | 怎么进模型 |
| --- | --- | --- | --- |
| 上下文窗口 | 当前这一步的高信号上下文 | 单次推理 | 直接作为输入 |
| 短期记忆 | 当前任务历史、摘要、线程状态 | 会话内 | 随线程组装进窗口 |
| 长期记忆 | 偏好、画像、历史结论、可复用事实 | 跨会话 | 按需检索后召回 |

三层在存储选型上也有不同取向，这点和后面的追问（Redis 该做什么）相关：

| 层 | 典型存储取向 | 原因 |
| --- | --- | --- |
| 短期记忆 | 内存数据库 / 会话存储 | 高频读写，要求低延迟，随会话释放 |
| 长期记忆 | 向量库 / 关系数据库 | 要按语义或条件检索，量大且需持久保存 |
| 上下文组装结果 | 不落存储，运行时拼装 | 每次推理按当前需要现组装 |

三者串起来的工作流是：当前任务来了，从短期记忆取出这次会话的上下文线索，从长期记忆按相关性召回几条相关事实，和当前输入一起组装进窗口；推理完的状态更新回短期记忆，过程中产生的可复用结论写回长期记忆。窗口始终是那块最贵的"工作台"，只放当下要用的东西。

## 工程实践：一套分层落地方案

把这三层落到实现上，大致是这样：

```python
# 伪代码：组装一次推理的上下文
def build_context(user_input, thread_id, user_id):
    recent = short_term.load(thread_id)          # 短期：当前线程近期历史/摘要
    facts = long_term.search(user_id, user_input)  # 长期：按当前输入检索相关事实
    context = assemble(recent, facts, user_input)  # 组装：只保留高信号内容
    return context                                 # 送进窗口

def after_turn(thread_id, user_id, result):
    short_term.append(thread_id, result)         # 更新短期：本轮状态
    if is_reusable_fact(result):                  # 判断：是否值得长期保存
        long_term.save(user_id, result)          # 写回长期
```

要点：`short_term`、`long_term`、`assemble`、`is_reusable_fact` 都是业务侧实现。核心机制是"读的时候分层取、写的时候判断要不要长期存"。`assemble` 这一步很关键——它决定什么能进窗口，是控制成本和信噪比的地方。经验值：长期召回的条数从个位数起步试，太多会稀释当前输入的相关性。

写回长期记忆的判断也要设计：不是所有对话都值得长期保存。偏好、明确的事实、可复用结论才存；临时闲聊、一次性的查询不该沉淀。判断逻辑做不好，长期记忆会变成垃圾堆，越往后检索质量越差。

## 追问逐条作答

### 追问一：记忆和 RAG 的区别是什么？

两者技术上有重叠（都涉及检索），但目的不同。RAG 解决的是"模型怎么拿到外部知识"，检索的是文档库这类外部知识源，目的是让回答有据可依；记忆解决的是"系统怎么记住和用好对话与用户的状态"，长期记忆检索的是用户偏好、历史结论这些沉淀下来的信息。一个偏"外部知识"，一个偏"用户与会话状态"。实现上可能都用到向量库，但定位和设计目标不同，不要混为一谈。

### 追问二：为什么说记忆不是训练模型？

因为记忆是在推理时、在模型外部管理的状态，不改变模型参数。把用户偏好记进数据库、需要时召回放进 prompt，模型本身没变；而训练或微调是改模型权重。记忆是应用层的工程设计，成本低、能即时更新、能精确删除某条；训练是模型层的事，贵且不可随时改。所以"记住用户喜欢什么"这件事，用记忆系统做，不用训练模型做。之前聊过微调和续训的边界，这里是同一个区分在记忆场景的体现。

### 追问三：Redis 在记忆里适合做什么？

Redis 是内存数据库，读写快，适合做短期记忆或会话状态的存储——比如按 `thread_id` 存当前会话的状态、近期历史，需要高频读写、低延迟访问。它也可以用来做短期记忆的缓存层。但长期记忆那种需要语义检索、按相关性召回、量大且要持久保存的场景，更适合向量库或数据库，不是 Redis 的强项。选型看访问模式：高频读写的会话状态用 Redis，语义检索的长期沉淀用向量库/数据库。具体用哪种按你的数据量和检索需求定。

### 追问四：如果上下文太长被截断了，你会选滑动窗口、摘要压缩还是检索式补充？怎么判断？

三种手段各有适用面，通常组合用。滑动窗口最简单——保留最近 N 轮，丢掉更早的；适合对话轮次多但信息密度低、早期内容确实不重要的场景，缺点是可能被丢弃的部分里有关键信息。摘要压缩是把较早的历史压成一段摘要，保留主线、牺牲细节；适合长对话要保留整体脉络的场景，缺点是摘要会丢细节、且摘要本身要额外调用模型。检索式补充是把历史存起来、按需召回相关的；适合信息量大、只有小部分与当前相关的场景，效果通常最好，但要建索引、工程复杂。

怎么判断：先看被截断的内容里有没有当前任务还需要的信息。如果基本没有，滑动窗口够用；如果要保留脉络，加摘要；如果关键信息散落在长历史里、只有部分相关，用检索式补充。经验值：生产里常见的是组合——近期用窗口保细节，早期做摘要保脉络，长期沉淀走检索。具体阈值按任务调。

### 追问五（自补）：长期记忆怎么避免存进垃圾？

靠写入判断和定期治理。写入时只沉淀真正可复用的信息，比如明确偏好、稳定事实、历史结论，不存一次性闲聊和临时查询；可以给记忆标类型、带时间戳，方便后续判断。治理上，长期不用的可以降低权重或清理，冲突的信息要有更新机制（新偏好覆盖旧偏好）。判断逻辑和治理做不好，长期记忆会随使用不断劣化，检索质量越来越差。

### 追问六（自补）：多轮对话里，短期记忆的摘要压缩什么时候该做？

看窗口占用和任务阶段。经验值：当近期历史已经占到窗口的一大半、再堆下去会挤压当前输入时，就该把更早的部分压成摘要。压缩要保留任务主线、关键结论和未完成的待办，丢掉寒暄和重复的中间过程。压缩本身要额外调用一次模型，不能每轮都做，否则成本和延迟都上去了——常见做法是设一个轮数或 token 阈值，超过才触发一次。具体阈值按任务的对话长度调。

## 60 秒面试回答模板

> 我会把记忆分三层：上下文窗口、短期记忆、长期记忆。窗口是模型单次能看的内容，昂贵且有限，只放高信号上下文，不能无限塞历史。短期记忆是会话级状态，存当前任务的历史、摘要和线程状态，保证当前线程不断档，在框架里对应按 thread_id 存的 checkpointer。长期记忆跨会话，存偏好、画像、历史结论，放数据库或向量库按需召回，不该每次全量塞进 prompt。工作流是读的时候分层取、组装进窗口，写的时候判断什么值得长期存。记忆和 RAG 不一样，RAG 偏外部知识，记忆偏用户和会话状态；记忆也不是训练模型，它是推理时外部管理的状态。上下文被截断时，窗口保近期细节、早期做摘要、长期沉淀走检索，组合着用。

## 常见误区

- **把历史全塞进 prompt**：窗口是昂贵资源，无限塞历史会推高成本、稀释信号。
- **混淆记忆和 RAG**：一个偏用户与会话状态，一个偏外部知识，实现可能都用向量库但定位不同。
- **把记忆当成训练模型**：记忆是推理时的外部状态，不改模型参数，能即时增删。
- **长期记忆每次全量注入**：应该按需检索召回一小部分，全量塞既浪费又稀释相关性。
