# 如何开发浏览器自动化 Agent？

<!-- growth-hook:v1 -->
浏览器自动化 Agent，难点从来不在“怎么点那个按钮”。网页会变、元素异步加载、状态随时漂移、误操作还可能真花钱——这题真正考的是怎么把“看、理解、操作、校验”做成一个稳闭环。

## 面试官为什么爱问这题

这题偏难，考的是浏览器工具、任务规划和可靠性设计。很多人觉得浏览器自动化就是"让模型点按钮"，面试官想听的是你能不能把它看成一个闭环系统——看页面、理解页面、操作页面、校验结果，缺一不可。更关键的是那句判断：最大的难点不在"会不会点按钮"，而在网页不稳定、异步加载、状态漂移和误操作成本高。这句话把考点从"会不会用工具"提升到了"怎么保证可靠"。前面聊过工具调用、执行闭环、行为边界，这一篇把它们落到浏览器自动化这个具体场景。

## 一句话先给结论

**浏览器自动化 Agent 的核心是把"看页面、理解页面、操作页面、校验结果"做成一个稳定闭环。合理设计包括五层：页面感知层拿 DOM、截图和可交互元素信息；决策层根据目标决定点击、输入、滚动、等待还是回退；执行层调用浏览器自动化工具完成动作；校验层确认动作是否生效、页面是否进入预期状态；治理层做超时、重试、幂等、防误操作和日志回放。最大难点不在会不会点按钮，而在网页不稳定、异步加载、状态漂移和误操作成本高，所以一定要把验证和回滚意识做进去。**

## 核心原理：五层设计

### 页面感知层：看到页面

拿到 DOM、截图、可交互元素信息。DOM 提供结构和文本，截图提供视觉信息，有些东西在 DOM 里看不出来（比如布局、颜色、图标状态），要截图才能判断。可交互元素信息告诉决策层哪些能点、哪些能填。感知的质量决定后面决策的质量，看不清页面就点不准按钮。

### 决策层：决定下一步

根据目标决定点击、输入、滚动、等待还是回退。注意"等待"和"回退"也是决策——很多时候页面还没加载完，正确动作是等一下，而不是急着点；走错了要能回退。决策层把"目标 + 当前页面状态"映射到下一步动作，这是模型的活。前面讲意图识别和任务规划时说过决策分层，这里是它在浏览器场景的具体化。

### 执行层：完成动作

调用浏览器自动化工具完成动作——Playwright 这类工具真正去点、去输入、去滚动。前面讲 MCP 工具生态时提过浏览器自动化类工具，这里是它们在闭环里的执行位置。执行层要保证动作真的发出去、发出后有反馈。

### 校验层：确认生效

确认动作是否生效、页面是否进入预期状态。这是最容易被省略却最关键的一层——点了按钮不代表成功，可能没点上、可能加载中、可能跳错页。校验层每次动作后检查页面状态，确认进入预期才继续，否则重试或调整。没有校验，Agent 会在错误页面上越走越远。

### 治理层：兜住风险

超时、重试、幂等、防误操作和日志回放。网页不稳定，操作要有超时；失败了要能重试；重试要幂等，别重复提交；高风险操作（付款、删除）要防误触；全程日志要能回放，出事能查。前面讲 Agent 行为边界和沙箱时说过这些，落到浏览器场景就是这一层。

| 层 | 做什么 | 缺了会怎样 |
| --- | --- | --- |
| 页面感知 | DOM、截图、可交互元素 | 看不清页面，决策失准 |
| 决策 | 点/输/滚/等/退 | 不知道下一步做什么 |
| 执行 | 调浏览器工具完成动作 | 意图落不了地 |
| 校验 | 确认动作生效、状态符合预期 | 在错误页面越走越远 |
| 治理 | 超时、重试、幂等、防误、回放 | 网页不稳就崩、误操作难追 |

浏览器场景的四个典型难点，和对应的对策可以列成一张表：

| 难点 | 表现 | 主要对策 |
| --- | --- | --- |
| 网页不稳定 | 结构变化、弹窗干扰、元素失效 | 多重定位，文本/语义/截图结合 |
| 异步加载 | 点了内容还没出来 | 显式等待条件，不用固定延时 |
| 状态漂移 | 跳错页、新标签、登录弹窗 | 每步校验，偏离就回退或重规划 |
| 误操作成本高 | 点错提交、付款、删除 | 高风险二次确认、幂等、日志回放 |

### 核心闭环：感知—决策—执行—校验

五层里前四层构成一个循环：感知当前页面 → 决策下一步 → 执行动作 → 校验结果 → 再感知……循环推进直到任务完成。治理层贯穿全程。理解这是"闭环"而不是"流水线"很关键——每一步之后都要回到感知，根据新的页面状态重新决策，而不是按预设序列一路点下去。网页是动态的，死板的序列会在状态变化时失效。

## 工程实践：应对网页的不稳定

题库点出的四个难点，各有对策：

**网页不稳定。** 页面结构会变、元素会改、广告弹窗会干扰。对策是多重定位——别只靠一种选择器定位元素，DOM 结构变了就找不到；结合文本、语义、截图位置多种方式，一个失效还有备选。

**异步加载。** 点了按钮内容还没出来，急着操作会失败。对策是显式等待——等目标元素出现、等状态变化，而不是固定睡几秒。等待本身也是决策层的一个动作。

**状态漂移。** 页面跳到意外状态、打开新标签页、弹出登录框。对策是每步校验状态，发现偏离就回退或重新规划，而不是硬着头皮继续。

**误操作成本高。** 点错"提交订单"要付出真实代价。对策是高影响动作二次确认、日志回放可追溯，关键操作前必须校验页面状态。

```python
# 伪代码：感知—决策—执行—校验闭环
def run(goal):
    state = perception.observe(page)           # 感知：DOM + 截图 + 元素
    while not done(goal, state):
        action = decision.next(goal, state)    # 决策：点/输/滚/等/退
        if action.risky and not confirmed(action):  # 治理：高风险二次确认
            continue
        result = executor.perform(action)      # 执行：调浏览器工具
        state = perception.observe(page)       # 再感知
        if not validator.check(action, state): # 校验：动作是否生效
            governance.retry_or_rollback()     # 治理：重试或回退
    return result

# perception / decision / executor / validator / governance 为业务侧实现
```

要点：每步执行后重新感知、校验，不生效就重试或回退。这是闭环结构的具体化。变量都是业务侧实现。

## 追问逐条作答

### 追问一：浏览器自动化 Agent 和普通 RAG / 问答 Agent 最大的区别是什么？

区别在于动作有真实副作用、环境不稳定。问答 Agent 答错了可以重来；浏览器自动化点了"提交"就真的提交了，误操作成本高。而且网页是动态的——异步加载、结构变化、状态漂移，不像知识库那样相对静止。所以浏览器自动化必须把校验、幂等、回滚、防误操作做进闭环，不能只追求"能点到按钮"。

### 追问二：为什么校验层不能省？

因为"点了"不等于"成功了"。按钮可能没点上、页面可能没跳转、可能跳到了错误页面。没有校验，Agent 以为成功继续往下走，实际在错误状态上操作，越走越偏。校验层每步之后确认页面进入预期状态，是防止偏离的关键。前面讲完成判断时说过"不能靠感觉"，浏览器场景里"动作反馈"就是那个不能靠感觉的东西——必须看页面实际状态。

### 追问三：异步加载怎么处理？

用显式等待，不用固定延时。固定睡几秒不可靠，网络快时浪费时间，网络慢时还没加载完就操作。正确做法是等目标元素出现、等某个状态变化、等加载指示消失，条件满足才继续。等待本身要作为决策层的一个动作，由模型判断"现在该等而不是该点"。前面讲 Deep Research 迭代时说过"证据不足继续补检"，这里的"没加载完继续等"是同一类耐心机制。

### 追问四（自补）：为什么要日志回放？

因为浏览器操作链条长、出错难复盘。用户报"那次为什么下了单"，你得能还原当时页面长什么样、Agent 做了什么动作、每一步校验结果如何。日志回放提供这个能力，记录每步的页面快照、动作、校验结果，出事能回溯。它也是防误操作的依据，发现某类误操作反复出现，能定位到具体环节改进。

### 追问五（自补）：幂等在浏览器自动化里为什么重要？

因为重试可能重复执行副作用。点了"提交"没收到确认，Agent 重试一次——如果第一次其实成功了，就提交了两次。幂等设计让重试安全：要么操作本身可重复不产生额外影响，要么重试前先检查状态（订单是不是已经提交过了）。前面讲 Agent 行为边界和成本排查时都提过幂等，浏览器场景里它是防止"重试造成重复损失"的关键。经验值：对提交、付款、删除这类动作，重试前一定要先读页面状态确认上一次的结果，别凭"没收到反馈"就断定失败。

## 60 秒面试回答模板

> 我会把浏览器自动化做成感知—决策—执行—校验的闭环，外面套治理层。页面感知层拿 DOM、截图和可交互元素；决策层根据目标决定点击、输入、滚动、等待还是回退；执行层调浏览器工具完成动作；校验层每步确认动作生效、页面进入预期状态；治理层做超时、重试、幂等、防误操作和日志回放。关键是它是闭环不是流水线——每步之后重新感知、重新决策，因为网页是动态的。最大难点不在点按钮，而在网页不稳定、异步加载、状态漂移和误操作成本高：用多重定位应对结构变化、显式等待应对异步、每步校验应对漂移、二次确认和幂等应对误操作。校验层绝不能省，点了不等于成功。

## 加分项

- 用"稳定闭环"定性，五层加闭环结构清楚。
- 点出难点不在点按钮而在环境不稳和误操作成本，拔高一层。
- 四个难点各有具体对策，可落地。
- 强调校验、幂等、回放这些可靠性机制。

## 常见误区

- **当成"让模型点按钮"**：忽略感知、校验、治理，闭环不完整。
- **省略校验层**：点了不等于成功，不校验会在错误页面越走越远。
- **用固定延时等异步**：不可靠，应显式等待条件满足。
