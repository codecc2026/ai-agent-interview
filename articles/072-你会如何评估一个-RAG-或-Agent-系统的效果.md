# 你会如何评估一个 RAG 或 Agent 系统的效果？

<!-- growth-hook:v1 -->
“效果怎么样？”——如果回答只有一个总分，面试官大概率会追问“那到底哪一层不行”。评测的关键不是算分，是能定位：检索错了还是生成错了，轨迹偏了还是结果错了。

## 面试官为什么爱问这题

这是必刷题，考的是评测闭环意识。很多人答评测就是"算个准确率、看个总分"，面试官想听的恰恰相反——评测的目的不是给你一个分数，而是告诉你哪里出了问题、该改哪一层。一个只报总分的评测，出了问题你只知道"分数变低了"，不知道是召回差、上下文组装差、生成幻觉还是工具失败，而这些问题的修法完全不同。这题还要求你分清离线和在线、RAG 和 Agent 各自该怎么评、自动和人工怎么配合。前面聊过 RAG 的分层排查、运维指标、幻觉治理，这一篇把这些收束成一套完整的评测体系，也是第 9 章的收官。

## 一句话先给结论

**评估先拆成离线评测和在线评测，再把问题拆到具体层级，而不是只盯一个总分。RAG 按检索层和生成层看；Agent 分轨迹级评测和结果级评测。在线看用户满意度、转人工率、任务中断率、耗时、badcase 类型分布，Agent 还要看工具调用成功率、重试率、循环次数和人工兜底比例。自动评测把规则评测、LLM-as-a-judge 和人工抽检结合。评测的关键在于不能只说"分数变低了"，而要能定位是哪一层出问题。推荐闭环：先分层建指标，再沉淀 badcase，最后让 badcase 反过来驱动 Prompt、检索、工具和流程迭代。**

## 核心原理：离线与在线，分层与分类

### 先分离线和在线

**离线评测**：上线前用固定数据集测，决定能不能发版、改动有没有退步。可控、可复现，适合做回归。

**在线评测**：上线后看真实用户的行为和指标，发现离线测不出来的问题。真实、但不可控，适合发现趋势和异常。

两者互补：离线守上线关口，在线守运行质量。前面讲运维指标时说过"评测决定是否放行、指标决定要不要回滚"，那正是两者分工的体现。

### RAG：检索层和生成层

**检索层**：相关内容有没有被召回、引用片段对不对、badcase 是卡在切块、召回、重排还是过滤。这一层看的是"正确的证据有没有进到上下文"。

**生成层**：答案是不是忠实于证据、引用是否正确、无依据时能不能拒答、最终回答对业务有没有帮助。这一层看的是"有了证据有没有用好"。

分层是关键——答案错了，先分清是检索层没给对证据，还是生成层没用好证据。前面讲 RAG 上线坑时说过用标注数据分层测，分清切块还是召回，这里是同一个思路的评测化。

### Agent：轨迹级和结果级

**轨迹级评测**：有没有选对工具、参数对不对、有没有无效循环、是不是过早结束。看的是"过程对不对"。

**结果级评测**：最终任务有没有完成、输出质量和用户体验是否达标。看的是"结果好不好"。

为什么轨迹也要评？因为 Agent 可能结果蒙对了但过程很糟——调了十次工具、绕了一大圈、差点陷入循环。这种系统上线后不稳定、成本高，只看结果发现不了。轨迹级评测能揪出这类隐患。

| 系统 | 评测维度 | 看什么 |
| --- | --- | --- |
| RAG | 检索层 | 召回、引用片段、切块/召回/重排/过滤 |
| RAG | 生成层 | 忠实度、引用正确、拒答、业务帮助 |
| Agent | 轨迹级 | 工具选择、参数、无效循环、过早结束 |
| Agent | 结果级 | 任务完成、输出质量、用户体验 |

### 在线评测看什么

在线看用户满意度、转人工率、任务中断率、耗时、badcase 类型分布。对 Agent 还要看工具调用成功率、重试率、循环次数、人工兜底比例。这些是前面讲运维指标时那些指标的评测视角——不只是看系统跑得怎么样，而是把它们当作效果信号：转人工率升高说明自动化效果变差、循环次数增多说明轨迹出问题、重试率上升说明工具链不稳。

### 自动评测：三种结合，不押一种

规则评测、`LLM-as-a-judge`、人工抽检结合：

**规则评测**适合客观、明确的判断——格式对不对、字段全不全、有没有命中必答项。快、稳、可复现。

**LLM-as-a-judge**适合主观、规模化的判断——用另一个模型评答案质量、忠实度。能放大规模，做回归测试。

**人工抽检**负责兜住高风险误判和评价漂移——规则覆盖不了、LLM 判断也可能跑偏，关键场景要人来把关。

三者结合：规则和 LLM 适合放大规模，人工兜住高风险。只押一种都会有问题——纯规则覆盖不了主观质量，纯 LLM 评测会漂移，纯人工规模化不了。

| 评测方式 | 擅长 | 短板 | 适合场景 |
| --- | --- | --- | --- |
| 规则评测 | 客观判断、快速稳定 | 覆盖不了主观质量 | 格式、字段、硬性指标 |
| LLM-as-a-judge | 规模化主观判断、回归 | 会漂移、可能被误导 | 忠实度、相关性等软指标 |
| 人工抽检 | 兜住高风险误判 | 规模化不了、成本高 | 高风险场景、评价校准 |

## 工程实践：评测闭环怎么转

题库给的闭环是：先分层建指标，再沉淀 badcase，最后让 badcase 反过来驱动迭代。

```python
# 伪代码：badcase 驱动的评测闭环
def evaluation_loop(candidates):
    for candidate in candidates:              # 每次改动是一个候选版本
        report = run_offline_eval(candidate)  # 分层评测：检索/生成或轨迹/结果
        if report.regressed():                # 和基线比有没有退步
            reject(candidate)
            continue
        promote(candidate)                    # 上线
    online_badcases = collect_badcases()      # 从线上收集 badcase
    for bc in online_badcases:
        layer = locate_layer(bc)              # 业务侧：定位是哪一层的问题
        add_to_eval_set(bc, layer)            # 沉淀进对应层的评测集
    # 下一轮迭代用更新后的评测集，形成闭环

# run_offline_eval / locate_layer / add_to_eval_set 为业务侧实现
```

要点：`locate_layer` 把 badcase 归到具体层，`add_to_eval_set` 把它沉淀成评测集的一部分。这样评测集会随线上真实问题不断丰富，下一次迭代就能测到这些问题。变量都是业务侧实现。

## 追问逐条作答

### 追问一：RAGAS 这类框架适合做什么？

适合快速建立 RAG 的自动化评测基线，它提供一套现成的指标，比如忠实度、答案相关性、上下文相关性这些，能让你在早期快速拿到评测数据、做回归对比。但要清楚它的边界：框架给的是通用指标，不一定覆盖你的业务场景；它也不能替代分层定位，答案相关性低究竟是检索问题还是生成问题，还得自己拆开看。经验值：用框架起步，再根据业务补自己的分层指标和 badcase 集，别把框架指标当成全部。

### 追问二：如何建设 badcase 数据集？

从两个来源沉淀。一是线上真实问题，用户反馈的、满意度低的、转人工的、任务中断的，这些是最高价值的 badcase，因为它们是真实分布。二是离线主动构造，针对已知薄弱点（表格解析、复杂多跳、权限边界）专门造测试样例。每条 badcase 要标注它属于哪一层，是检索、生成、轨迹还是结果，这样才能驱动对应层的迭代。经验值：badcase 集要持续更新，定期从线上补充新样本、淘汰已经解决的问题。

### 追问三：自动评测和人工评测怎么配合？

自动评测负责规模和回归，每次改动都跑一遍，快速发现明显退步；人工评测负责兜底和校准，定期抽检自动评测的结果，看它有没有漂移、有没有把错判成对。两者的结合点是：人工发现自动评测判错的地方，回头修正规则或调整 judge 的提示词，让自动评测更准。经验值：高风险场景提高人工抽检比例，低风险场景靠自动评测放大规模，比例按风险调。

### 追问四（自补）：为什么评测一定要分层，只看总分不行？

因为总分定位不了问题。总分从 85 掉到 80，你不知道是检索召回变差、还是生成开始编、还是工具失败变多——这些问题的修法完全不同。分层评测能告诉你"检索层的召回率掉了"，直接指向该改切块还是召回。前面讲 RAG 上线坑和性能定位时都强调"先拆开再看"，评测是同一个道理：可定位的评测才有用，笼统的总分只能看趋势。

### 追问五（自补）：轨迹级评测为什么对 Agent 特别重要？

因为 Agent 可能"结果对但过程糟"。一个任务最终完成了，但过程里调了十次工具、绕了远路、甚至触发过无效循环——这种系统成本高、不稳定、容易在某个边界条件下崩。只看结果级评测发现不了这些隐患。轨迹级评测看工具选择对不对、有没有无效循环、是不是过早结束，能揪出"侥幸成功"的系统。前面讲 Agent 行为边界时说过熔断和步数上限，轨迹评测是发现"为什么需要这些限制"的手段。经验值：轨迹评测不追求每一步都最优，重点抓无效循环、错误工具、过早结束这几类明显问题，否则标准太严会把合理的探索也判成错误。

## 60 秒面试回答模板

> 先分离线和在线，再把问题拆到具体层，不盯总分。离线守上线关口，在线看真实运行。RAG 分检索层和生成层：检索看召回、引用片段、卡在切块还是召回重排；生成看忠实度、引用、拒答。Agent 分轨迹级和结果级：轨迹看工具选择、参数、无效循环、过早结束；结果看任务完成和体验。在线看满意度、转人工率、中断率、耗时、badcase 分布。自动评测不押一种，规则、LLM-as-a-judge、人工抽检结合，规则放大规模、人工兜高风险。关键是评测要能定位哪层出问题，闭环是分层建指标、沉淀 badcase，让 badcase 驱动 Prompt、检索、工具和流程迭代。

## 加分项

- 先分离线在线、再分层分类，框架清楚。
- RAG 两层、Agent 两类，维度准确。
- 自动评测三种结合，说清各自定位和边界。
- 点出评测要能定位问题层，给出 badcase 驱动迭代的闭环。

## 常见误区

- **只盯总分**：分数掉了不知道哪层问题，无法驱动改进。
- **只看结果不看轨迹**：Agent 结果对但过程糟，隐患发现不了。
- **自动评测押一种**：规则覆盖不了主观、LLM 会漂移、人工规模化不了，要结合。
