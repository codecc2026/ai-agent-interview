# 面试官让你介绍一个做过的 RAG / Agent 项目，你应该怎么讲？

<!-- growth-hook:v1 -->
“介绍一个你做过的项目”——面试官一天听几十遍技术栈，早就不耐烦了。真正抓人的是顺序：先说解决了什么业务问题，再说你的方案和你负责的部分，最后用指标收尾。

## 面试官为什么爱问这题

这是必刷题，考的是项目表达能力。很多人一被要求介绍项目就从技术栈开口，"我们用了 LangChain、向量库、某某模型"，讲了三分钟面试官还不知道这个项目解决什么问题、你具体做了什么。这题想听的是一套结构化的表达：先讲业务目标，再讲方案，重点讲你负责的部分，然后讲难点和你怎么解的，最后给可量化结果。面试官真正想验证的不是"你用没用过某个框架"，而是你有没有真的做过、做得多深、能不能反思。前面讲过那么多系统设计题，这一篇反过来看，怎么把你做过的事讲得有说服力。

## 一句话先给结论

**更稳的表达顺序是"业务目标 → 方案设计 → 你负责的部分 → 难点 → 指标结果"。不要一上来报技术栈，而要先讲项目解决了什么业务问题，比如"降低客服查文档成本"或"让运营能自然语言查数"；再讲架构；接着重点说你自己具体做了什么，比如索引策略、权限设计、工具接入、评测体系、成本优化；最后给可量化结果，比如命中率、耗时、转人工率、人工节省时长。可以用轻量 STAR 结构把表达撑稳。**

## 核心原理：五步表达顺序

### 第一步：业务目标

先讲这个项目解决了什么业务问题，比如降低客服查文档成本、让运营能自然语言查数、把研究报告生成时间从半天压到十分钟。业务目标要让面试官立刻明白"这事为什么值得做"。避免上来就说"我们做了一个智能问答系统"，那是产品名，不是目标。

### 第二步：方案设计

再讲架构——用了 RAG、Tools、LangGraph 还是平台工作流，整体链路怎么走。这一步要简洁，把关键选择说清即可，不要展开每个细节。面试官需要一张"地图"，不是一张"施工图和施工日志"。

### 第三步：你负责的部分

这是最关键的一步。面试官最常追的动词是"你具体负责哪一层，别把团队成果全讲成自己做的"。要说清哪些是你主导设计的、哪些是你参与的、哪些是团队其他人的——边界诚实反而更可信。具体讲你做了什么：索引策略怎么定、权限怎么设计、工具怎么接入、评测体系怎么建、成本怎么优化。越具体越可信。

### 第四步：难点和你的解法

讲遇到过的真实困难——某个 badcase 怎么发现、怎么定位、最后怎么修；为什么这么选型而不是别的方案；上线后效果怎么评估、问题怎么排查。这部分最能体现深度，因为背不出来的细节需要有真经验才讲得清。前面讲过的那些系统设计的坑，正是这里可以调用的素材。

### 第五步：指标结果

给可量化结果——命中率、耗时、转人工率、人工节省时长、成本下降比例。没有上线就给离线评测数据，但要说清是离线还是线上。数字让前面的努力有了落点，也是面试官判断"这事做得怎么样"的依据。

| 步骤 | 讲什么 | 面试官在听什么 |
| --- | --- | --- |
| 业务目标 | 解决什么问题 | 这事值不值得做 |
| 方案设计 | 架构和关键选择 | 你有没有全局理解 |
| 你负责的部分 | 具体做了什么、边界在哪 | 你是真做过还是旁观 |
| 难点与解法 | badcase、选型、排障 | 有没有深度 |
| 指标结果 | 可量化数据 | 做成了没有 |

题库还点出面试官最常往下追的四个方向，准备项目时要把这些答案备好：

| 追问方向 | 面试官想验证什么 | 准备要点 |
| --- | --- | --- |
| 你具体负责哪一层 | 是不是真做过，边界诚实 | 说清主导 / 参与 / 他人的部分 |
| 遇到过哪些 badcase | 有没有真实排障经验 | 备好发现—定位—修复—验证的链条 |
| 为什么这么选型 | 有没有工程判断 | 说清权衡的两头和取舍理由 |
| 上线后怎么评估和排查 | 有没有闭环意识 | 指标、评测、排障路径都要能讲 |

### 轻量 STAR 结构

如果希望表达更稳，可以用适合应用岗的轻量 STAR：

**情境（Situation）**：业务问题和约束是什么——为什么要做，有什么限制。

**任务（Task）**：你负责哪一段，目标指标是什么——明确你的责任边界。

**行动（Action）**：你具体做了哪些设计、排障、优化——这是主体，讲细节。

**结果（Result）**：最终指标、上线效果、复盘收获——量化收尾。

STAR 的价值是给表达一个骨架，避免讲到一半散掉。但别机械套用——重点是"你把事情讲清楚、讲出深度"，结构只是辅助。

## 工程实践：一段项目介绍怎么组织

把五步串成一段可讲的稿子，关键是每步都落到具体内容：

```text
业务目标：客服团队查文档平均要 5 分钟，我们做一个知识库问答帮他们秒级定位。
方案设计：用 RAG 链路，文档解析切块入向量库，查询时混合检索加重排，生成带引用。
我负责的部分：我主导索引策略和权限过滤设计——按部门隔离文档，检索前过滤；
              还建了评测集和 badcase 回灌流程。（明确边界，参与的工具接入交给队友讲）
难点与解法：上线发现"有引用但不忠实"的 badcase，我通过引用可追溯 + 忠实度抽检定位，
            调整了上下文组装方式，把这类问题压下去了。
指标结果：命中率从 70% 到 88%，平均响应时间 1.2 秒，客服查文档时间节省约 60%。
```

要点：每步都有具体内容，尤其"我负责的部分"和"难点"要具体到可追问。"从 70% 到 88%"这种前后对比比单说"效果很好"有说服力。这只是示意结构，真实项目填你的内容。

## 追问逐条作答

### 追问一：这个项目最难的点是什么？

答一个真实的、有深度的难点，而不是泛泛说"调模型效果好难"。好答案通常指向系统性问题——"解析质量不稳导致检索效果差，我用了真实文档做基准测试，逐个排查切块和表格解析的问题";或者"权限和检索的顺序，一开始查完再过滤，发现有泄露风险，改成检索前过滤"。难点要具体到"难在哪、你怎么发现、怎么解决"，这样面试官能追问下去，也能看出你真的做过。

### 追问二：你做过哪些 trade-off？

trade-off 体现工程判断力。常见的几条：效果和成本，强模型效果好但贵，你把简单任务路由到轻模型；准确率和覆盖率，检索阈值调高提高准确率但降低覆盖率，你按业务取舍；速度和质量，重排提升效果但增加延迟，你对长任务才启用；自建和平台，平台快但定制受限，核心链路自建、边缘用平台。答 trade-off 时说清"权衡的两头是什么、你选了哪头、为什么"，比单说"我们做了优化"成熟得多。

### 追问三：如果重做一次，你会怎么改？

这题考反思能力。好的回答不是"没遗憾，做得挺好"，也不是泛泛说"会做得更好"，而是具体的改进："评测集应该一开始就从真实日志取，我们早期用理想样例，上线后才发现分布不对"；"权限应该设计在架构之初，我们中途加的，改动很大"；"知识更新应该从一开始就版本化，早期原地改索引踩了坑"。真实的具体遗憾，比完美的假答案更可信。

### 追问四（自补）：面试官追问 badcase 时怎么答？

按"发现、定位、修复、验证"四步讲。发现：这个 badcase 是怎么暴露的，是用户反馈、抽检还是评测集；定位：你怎么找到根因的，是切块问题、召回问题还是生成问题；修复：你做了什么改动；验证：改完怎么确认解决了、有没有引入新问题。这条链条讲下来，面试官能看出你有完整的问题解决能力，而不是只会说"我们优化了 prompt"。

### 追问五（自补）：结尾总结时需要注意什么？

别把团队成果揽到自己身上，也别把自己的贡献说得模糊。面试结尾常有"你再总结一下"的环节，这时要回到"业务目标—你的贡献—结果"的主线，简短有力。贡献说不清是大忌，面试官会怀疑你是不是真的做了。经验值：准备项目介绍时，专门练一遍"我负责的部分"这段，做到三句话能讲清、经得起追问。还有一点：整个介绍要留出被追问的口子——你主动讲到的难点，面试官大概率会深挖；别讲自己接不住的内容，能展开的才讲，讲到三五层细节都不慌，才是真正的准备充分。

## 60 秒面试回答模板

> 我介绍项目会按五步走：先讲业务目标，比如降低客服查文档成本，而不是先报技术栈；再讲方案设计，用了 RAG 加混合检索加带引用生成；然后重点讲我负责的部分，我主导了索引策略和检索前的权限过滤，明确哪些是团队其他人做的；接着讲难点，上线发现有引用但不忠实的 badcase，我通过引用可追溯和忠实度抽检定位到上下文组装的问题并修掉；最后给结果，命中率从 70% 到 88%，响应 1.2 秒，查文档时间省了六成。如果讲得更稳，我会用轻量 STAR 把情境、任务、行动、结果撑起来。面试官追问时我会具体讲 badcase 的发现到修复链条、做过的 trade-off，以及如果重做会怎么改。

## 加分项

- 表达顺序结构化，先业务后技术，先贡献后结果。
- 明确"你负责的部分"的边界，不揽团队成果。
- 难点讲"发现—定位—修复—验证"的完整链条。
- 结果可量化，有前后对比。

## 常见误区

- **上来就报技术栈**：面试官还不知道项目解决什么问题。
- **把团队成果说成自己的**：一追问就露馅，诚实划边界反而更可信。
- **只说效果很好不给数字**：没有量化结果，说服力大打折扣。
