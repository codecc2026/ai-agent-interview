# 结构化输出有哪些常见做法？各自的优缺点是什么？

## 一句话先给结论

**结构化输出不是一个开关，而是四级台阶：Prompt 只能「尽量要求」，Parser 是事后收拾，前约束（在生成前定好 schema）才是真保证，而校验重试无论走到哪一级都得留着；工程默认顺序是——能用原生结构化输出就先用，需要强校验就上 Pydantic 一类 schema，最后一定补业务校验、缺省值处理和失败重试。**

面试官把这题丢过来，考的从来不是「你会不会拼一个 JSON」，而是你有没有从**「能输出 JSON」到「能稳定接进系统」**的工程意识。答崩的人通常停在第一层：写一段提示词说「请只输出 JSON」，然后演示一次成功的结果——可生产环境里真正要命的，恰恰是那一次不成功的。

四层可以这样记：**Prompt 是请求，Parser 是翻译，前约束是规则，校验重试是保险。**第 5 篇讲选型时提过「行为不稳就上结构化输出约束」，本篇把它铺开：约束到底有几种、每一种的约束力从哪来、哪一种才配叫生产可用。

## 从「能输出 JSON」到「能接进系统」，差在哪

### 第一层：Prompt 约束只有「要求」，没有「保证」

纯 Prompt 约束就是直接在提示词里写「只输出 JSON，不要任何解释」。它最大的优点是零成本：不需要改代码，不需要平台支持，当天就能跑通一个 demo。

它的失效方式也很朴素——**模型多说一句话、少写一个逗号，你的解析就崩了**。更麻烦的是这种失效是概率性的，测试跑十次全过，第十一次上线就炸。所以它能用来验证想法，但不能用来承接流量。这里要纠正一个常见误解：**提示词里写了「只输出 JSON」，不等于输出一定有语法保证**，约束力和写法无关，只和平台有没有在生成侧动手有关。

### 第二层：Parser 是事后收拾，链路稳定但救不了质量

`StrOutputParser`、`JsonOutputParser`、`PydanticOutputParser` 这一类属于后处理解析：模型已经输出了字符串，我负责把这段字符串转成程序能用的数据结构。它天然适合 `prompt | model | parser` 这条经典链路——每一步职责清楚，中间想插日志、缓存、重试都很方便。

但它的定位必须说清：**Parser 处理的是「已经发生的事实」，它不会让模型变得更守规矩**。模型输出了一段带前言的话，Parser 可以帮你把代码块里的 JSON 抠出来；模型把 `amount` 写成了「一百二十元」，Parser 帮不了你。所以这一类解决的是「接得住」，不是「输出对」。

### 第三层：把约束放到生成之前

真正的差别在于约束发生在哪一时刻。像 `with_structured_output(TypedDict / Pydantic / JSON Schema)` 这样的写法，本质是**在模型开口之前就把 schema 定好**，让模型照着结构生成，框架顺带完成解析。同一个目标，从「事后把乱的理顺」变成「事前让它不许乱」，约束力和可预测性完全不在一个量级。

再往下，还有一类依赖推理侧支持的做法：在每一步解码时按 schema 或文法裁剪候选 token，不合规则的分支根本走不到最终结果里。这是目前约束力最强的一档，但门槛也最高——需要对应的模型服务或推理框架提供能力，且复杂的 schema 通常会带来额外的编译与首 token 开销（定性判断，不同实现差异很大）。

### 边界：schema 合规不等于内容正确

最后一层边界最容易被忽略：**结构合法是一回事，字段对不对是另一回事**。`{"amount": 0.0, "seller": "未知"}` 完全符合 schema，业务上却一文不值。这就是为什么题库把业务校验、缺省值、失败重试列为必须补的第三步——前约束管形状，业务校验管内容，两者不能互相替代。

## 六类做法横向对比

下表按「约束力从哪来」排序。生产可用性一列的判断是**常见工程经验**，不同团队、不同模型平台会有出入，用来横向比对量级，不要当成承诺值。

| 做法 | 约束力来源 | 典型适用 | 优点 | 缺点 / 失效点 | 生产可用性 |
| --- | --- | --- | --- | --- | --- |
| 纯 Prompt 约束 | 只靠自然语言请求 | 验证想法、一次性脚本、内部小工具 | 零改造成本，起步最快，不依赖平台能力 | 多一句话、少个逗号就崩；失效是概率性的，难以复现 | 最低，不建议承接线上流量 |
| 后处理解析 Parser | 输出之后再解析成数据结构 | `prompt \| model \| parser` 链路、需要中间插日志/缓存的场景 | 链路清晰易调试，对模型无要求，可兼容任意模型 | 只解决「怎么接住」，不提升输出质量；改不了模型的坏习惯 | 中，作为过渡或兜底手段 |
| JSON 模式 | 服务端保证「返回合法 JSON」 | 只需要语法合法、schema 相对简单的场景 | 基本消灭语法错误，调用方式简单 | 常常只是「长得像 JSON」，字段名、类型、枚举值仍可能跑偏 | 中，需叠加后续校验 |
| Schema 约束的结构化输出 | 生成前给定 schema，按结构生成 | 字段抽取、表单填充、分类打标等大多数生产场景 | 约束力最强的一档通用做法，字段与类型基本可控，可自动解析 | 依赖平台是否支持；复杂嵌套 schema 会增加提示体积 | 高，优先作为默认选择 |
| 受限解码 / 文法约束解码 | 解码时逐步裁剪不合规 token | 输出格式极严、错一个字符就不可用的场景 | 语法层面几乎不可能出错，确定性高 | 依赖推理侧支持，并非所有平台提供；复杂规则有额外开销 | 较高，但受限于平台可用性 |
| Function / Tool Calling | 同上，目标是「调用意图 + 参数」 | 工具调用、外部接口编排、Agent | 天然带「选哪个工具 + 传什么参数」的语义，便于编排 | 目标偏向生成调用意图，不适合承载自由文本内容 | 高，Agent 场景首选 |

表里最容易被含糊带过的就是中间那三行的关系：**JSON 模式保证语法，schema 约束保证结构，受限解码保证生成过程**。三者名字都常被口头喊成「结构化输出」，但它们不是一回事，能不能答清这条边界，基本就能看出有没有真的接过生产链路。

## 三种 schema 描述方式怎么选

定好了要「先给 schema」，接着是拿什么描述 schema。三种载体没有优劣，只有分工：

| 载体 | 适合场景 | 强项 | 弱项 |
| --- | --- | --- | --- |
| `TypedDict` | 字段固定、结构清晰，不追求很强运行时校验的内部场景 | 写法最轻，几乎就是类型注解，IDE 提示好 | 运行时基本不做校验，脏数据容易一路流到下游 |
| `Pydantic` | 字段类型、取值范围、必填项要求严格的业务场景 | 类型、范围、默认值、嵌套校验一套解决，报错信息可读 | 需要学习一套模型定义写法；版本间细节有差异 |
| `JSON Schema` | 跨语言、跨系统共享结构协议的场景 | 与语言无关，适合作为团队或系统间的契约 | 手写偏繁琐，通常还是由代码里的类型生成 |

一句话总结取舍：**内部轻量处理选 `TypedDict`，业务要有保障选 `Pydantic`，要对外交付或跨语言共享就落 `JSON Schema`。**实际项目里三者常常同时存在：代码里用 `Pydantic` 定义并校验，对外导出 `JSON Schema` 作为协议。

## 工程实践：给一份能照抄的兜底链路

### 一份 schema 样例

下面是一份标准 JSON Schema（字段名和约束按业务替换），注意三点：`additionalProperties` 关掉是防模型自作主张加字段；枚举用 `enum` 而不是在描述里写「只能是 A 或 B」；每条 `description` 都写成给模型看的抽取说明。

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["seller", "amount", "items"],
  "properties": {
    "seller":   { "type": "string", "minLength": 1, "description": "销售方名称，原样抽取" },
    "amount":   { "type": "number", "minimum": 0, "description": "价税合计，单位元，只填数字" },
    "items":    { "type": "array", "items": { "type": "string" }, "description": "货物名称列表" },
    "category": { "type": "string", "enum": ["餐饮", "交通", "办公"], "description": "费用类别" }
  }
}
```

### 校验 + 重试的 Python 骨架

schema 交出去之后，下面这段才是重点：**语法校验、业务校验、定向重试三件事一件都不能少**。

```python
from typing import Optional
from pydantic import BaseModel, Field, ValidationError


class Invoice(BaseModel):
    seller: str = Field(min_length=1, description="销售方名称")
    amount: float = Field(ge=0, description="价税合计，单位元")
    items: list[str] = Field(default_factory=list, description="货物名称列表")
    invoice_no: Optional[str] = Field(default=None, description="发票号码，可能缺失")


SCHEMA = Invoice.model_json_schema()   # 交给平台的 schema 约束参数（各家 SDK 参数名不同）


def extract(client, messages, max_retry=2):
    """client.invoke(messages, schema=SCHEMA) 为伪代码，按所用 SDK 替换。"""
    ctx, last_err = list(messages), None
    for _ in range(max_retry + 1):
        raw = client.invoke(ctx, schema=SCHEMA)
        try:
            data = Invoice.model_validate_json(raw)      # 语法 + 结构 + 取值范围一次过
        except ValidationError as e:
            last_err = str(e.errors()[:2])
            ctx = ctx + [{"role": "user", "content": f"上一次输出不合规：{last_err}，请只输出 JSON。"}]
            continue
        if not (data.amount > 0 and data.seller.strip()):   # 业务校验：结构对了不代表值对
            last_err = "amount 或 seller 业务上不成立"
            ctx = ctx + [{"role": "user", "content": f"字段合法但业务不成立（{last_err}），请重新抽取。"}]
            continue
        return data.model_dump()
    raise RuntimeError(f"结构化输出重试 {max_retry} 次仍失败：{last_err}")
```

这段代码里有三个容易被跳过的细节：

1. **重试要把上一次的报错原文塞回上下文**，而不是笼统说「请重试」。模型看不到自己错在哪，重试就是换个姿势重犯。
2. **重试要有次数上限**，超了就抛错转人工或走降级默认值，不能让它无限转圈烧 token。经验值上 `max_retry` 取 1 到 2 次足够，再多基本是在赌运气。
3. **所有字段都要有缺省值语义**。抽不到就不填，和抽出来是空字符串，对下游是完全不同的两件事，别用同一个 `""` 糊过去。

### 常见问题对照表

| 你看到的现象 | 说明什么 | 下一步动作 |
| --- | --- | --- |
| 十次里偶发一两次解析报错 | 停在了 Prompt 约束层 | 换 Schema 约束的结构化输出，别再改提示词措辞 |
| 输出永远合法 JSON，但字段名忽长忽短 | 只开了 JSON 模式，没有 schema 约束 | 补上明确的 schema，并关闭额外字段 |
| 字段类型合规，值明显不合理 | 结构对了，内容没管 | 加业务规则校验（范围、互斥、枚举一致性） |
| 加了 schema 之后延迟上涨 | token 开销与约束计算的成本 | 精简 schema 层级，去掉不必要的嵌套与长描述 |
| 重试三次还是同一种错法 | 不是随机抖动，是任务本身没定义清 | 回去补 few-shot 示例，必要时重拆任务 |

## 面试官的追问，你该怎么接

### 追问一：JSON 模式和结构化输出是一回事吗？

不是。**JSON 模式保证的是「语法合法」，结构化输出保证的是「符合你给定的 schema」**。前者只负责让你不用再写正则去抠代码块，字段名写错、类型写反、枚举值跑偏它一概不管；后者因为 schema 已经进了生成过程，这些才被管住。所以能用带 schema 约束的那一档时，不要停在只保证「返回合法 JSON」的那一档——后者很多时候只是长得像 JSON。

### 追问二：Parser 和 Structured Output 到底差在哪？

差在**约束发生的时刻**。Parser 属于「模型已经输出了，我再把结果转成程序可用的数据」，是后处理；Structured Output 属于「在模型输出前就先把 schema 定好」，是前约束。前者像质检员，后者像模具。质检能保证挑出来的是好的，但不能提高良品率；模具直接决定了产出的形状。这也是为什么 `prompt | model | parser` 这条经典链路好调试、却不适合承担强约束任务。

### 追问三：有了结构化输出，还需要自己写校验和重试吗？

需要，而且这是必答题。** schema 保证的是形状，业务规则保证的是内容 **。金额必须大于零、开始日期不能晚于结束日期、一级类目和二级类目必须匹配——这些规则大多塞不进 schema，或者塞进去会让 schema 变得极难维护。所以标准做法是三层叠加：schema 管结构，业务校验管语义，重试兜住偶发抖动。任何一层都不要省。

### 追问四：Function Calling 算不算结构化输出？什么时候用它？

算，它本质上就是结构化输出的一种，只不过目标不同：**它输出的不是「答案」，而是「调用意图和参数」**——要调哪个工具、传什么参数。所以工具调用、外部接口编排、Agent 这些场景该用它；反过来，如果你只是想让模型把一段合同抽成若干字段，用普通 schema 输出更直接，不必绕一层工具语义。把它当成「带意图的结构化输出」来理解，边界就不会混。

### 追问五：TypedDict、Pydantic、JSON Schema 怎么选？

按「要不要运行时校验」和「要不要跨语言」两个维度切：字段固定、内部流转、不追求运行时校验的用 `TypedDict`，最轻；类型范围必填都要卡死的业务场景用 `Pydantic`，它能把取值范围和嵌套结构一次校验完；要跨语言跨系统共享协议时用 `JSON Schema`，它跟语言无关，适合作为契约。常见组合是内部用 `Pydantic` 定义并校验，对外导出 `JSON Schema`。

### 追问六：模型不支持结构化输出能力，怎么办？

降级顺序是：先退到 **JSON 模式 + 后处理 Parser**（至少把语法问题交给平台）；再退到 **Prompt 约束 + Parser**（写法要给示例、少给自由度）；无论退到哪一层，**都要补一份自己的校验和重试**，因为后面的层级没有平台给你兜底。另外可以把评分 / 抽取类任务拆成更小的输出单元，字段越少越不容易出错。这里的原则是：降级是降级保证强度，不是降级工程要求。

## 60 秒面试回答模板

> 我会先把结构化输出分成两大类：后处理解析和前约束结构化输出，核心区别在于约束发生在模型输出之前还是之后。

> 最弱的是纯提示词约束，多一句话少个逗号就崩；Parser 是把已经输出的字符串转成数据结构，适合经典链路但救不了输出质量；真正有保证的是生成前就把 schema 定好的结构化输出，平台支持的严格模式下应该用带 schema 的那一档，而不是只保证「返回合法 JSON」的 JSON 模式。Function Calling 本质上也是结构化输出，只不过目标是调用意图和参数，适合工具编排和 Agent。

> 工程上的顺序是：能用原生结构化输出就先用，需要强校验就上 Pydantic 这样的 schema 载体，最后一定要补业务校验、缺省值和失败重试，因为 schema 管形状、业务校验管内容，谁也替不了谁。

## 加分项

- **能说出「限制的只有形状，不是正确性」**：这是面试官判断你有没有真接过系统的分水岭，顺手带出业务校验那一层就稳了。
- **把约束时刻当主线**：用「事前 / 事后」这条线串起 Prompt、Parser、前约束、受限解码四类做法，比逐个背定义清楚得多。
- **能量化重试策略**：`max_retry` 取 1 到 2 次（经验值），失败要把原始报错回传给模型、超限转人工兜底，这三点说出来就是落地过的样子。
- **点出 Function Calling 的定位差异**：它输出的是调用意图而非答案，选它还是选普通 schema 输出，取决于你下一步要不要真的去执行某个动作。

## 常见误区

- **以为提示词写了「只输出 JSON」就有语法保证**。写法不产生约束力，约束力只来自平台在生成侧做了什么。
- **把 JSON 模式当成结构化输出的全部**。它只保证语法合法，字段名、类型、枚举照样可能错。
- **有了结构化输出就砍掉自己的校验**。schema 过了不等于业务成立，尤其是数值范围、字段互斥、跨字段一致性这三类。
- **把「接得住」当成「输出对」**。Parser 只解决前一半，靠反复改 Parser 是治不好输出质量的。
