# Agent 应该如何接入 MCP 工具？

## 面试官为什么爱问这题

这题考的是你有没有把 MCP 真正接进 Agent 的架构里想过，而不是只会配一个客户端。很多人觉得"能调通"就完事了，面试官偏偏在追问里把话题引到权限和安全沙箱——因为真实系统里，接通只是起点，接通之后一个 Agent 拿着一堆外部工具能干什么、被谁拦住、出事能不能查，才是决定它敢不敢上生产的东西。这题想听两层：一层是接入的主链路怎么走，一层是接通后怎么保持可控。前面讲过 MCP 的定位、并发治理和流式传输，也聊过给 Agent 行为划边界；这一篇把视角收到"接入"这个动作上，看主链路怎么搭、可控性怎么保。

## 一句话先给结论

**Agent 接入 MCP 的核心，是把 MCP 暴露出来的能力纳入自己的工具注册和调度体系。主链路是四步：先发现 Server 暴露的工具或资源；再把这些能力转成 Agent 能消费的工具描述和 schema；执行时让模型决定何时调用、由宿主真正发起 MCP 请求；把结果回传给 Agent 进入下一轮决策。真正的关键不在"接通"，而在"接通后仍然可控"——权限、超时、失败重试、观测和审计。**

## 核心原理：接入的四步主链路

### 第一步：发现能力

Agent 先要知道对面的 MCP Server 提供了什么。发现机制让客户端拉取 Server 暴露的工具、资源列表及其描述。这一步是动态的前提——能力不是写死在 Agent 代码里的，而是运行时从 Server 获取的，所以 Server 加了新工具、改了描述，Agent 这头不用重新发版就能感知到。

### 第二步：转成 Agent 能消费的 schema

发现到的能力要转换成 Agent 侧统一的工具描述格式。MCP 暴露的能力有自己的描述和参数 schema，Agent 有自己的工具注册结构，这一步做转换，让模型能理解"有哪些工具、各自干什么、参数怎么传"。转换质量直接决定模型用得准不准——描述含糊、参数不清，模型就会选错或传错参。

### 第三步：模型决策，宿主执行

这是职责分界的关键一步。模型负责决定"什么时候调用哪个工具、传什么参数"，但它自己不发起 MCP 请求——真正发起请求的是宿主（客户端/运行时）。模型吐出调用意图，宿主接住这个意图、解析出工具名和参数、向 Server 发起请求。把"决策"和"执行"分开，宿主才能在中间插入权限检查、超时控制、日志审计这些环节。

### 第四步：结果回灌，进入下一轮

MCP 调用的结果回传给 Agent，作为新的上下文进入下一轮决策。模型看到工具返回，再决定继续调工具、还是给出最终答案。这一步把 MCP 调用嵌进了 Agent 的循环里——它不是孤立的一次请求，而是决策—执行—回传链条中的一环。前面讲过一条 `tool_calls` 消息在运行时怎么流转，这里回灌的就是同类消息。

| 步骤 | 谁负责 | 关键动作 |
| --- | --- | --- |
| 发现能力 | 宿主 / 客户端 | 拉取 Server 暴露的工具和资源 |
| 转换 schema | 宿主 | 转成 Agent 能消费的工具描述 |
| 决策与执行 | 模型决策、宿主执行 | 模型定何时调，宿主发起请求 |
| 结果回灌 | 宿主 | 结果作为上下文进入下一轮 |

### 关键不在接通，在可控

四步走完只是"能用了"。真正区分生产级和 Demo 的，是接通之后的可控性。具体有五项：权限，这个 Agent 有没有权限调这个工具、以谁的身份调；超时，工具卡住不能无限等；失败重试，失败了该重试还是换路、重试几次；观测，每次调用都留痕，能看清楚谁在什么时候调了什么；审计，事后能追责、能回放。这些环节大多挂在"模型决策、宿主执行"这一步的宿主侧，因为宿主夹在中间，才有地方做这些控制。如果模型直接调 Server，这些控制就无处安放。

这五项控制分别落在哪一层，也值得说清：

| 可控项 | 主要落在哪一层 | 作用 |
| --- | --- | --- |
| 权限 | 宿主 + 环境沙箱 | 应用层判断能不能调，系统层限制能碰到什么 |
| 超时 / 重试 | 宿主 | 防止卡死，按幂等性决定是否安全重试 |
| 观测 / 审计 | 宿主 | 调用留痕，支持排障和事后追责 |
| 参数校验 | 宿主 | 挡住畸形或越界参数，不让请求打到 Server |

可以看到宿主动着了绝大部分控制，这就是"决策与执行分离"这个设计的回报——执行权在宿主手里，控制才有落脚点。

## 工程实践：在宿主侧建一道控制闸

把可控性落到宿主这一层，接入代码的关键不是"怎么连上"，而是"连上之后在哪里拦一道"。

```python
# 伪代码：宿主接住模型意图，先过控制闸，再发起 MCP 请求
def execute_tool_call(intent, agent_context):
    name, args = parse_intent(intent)                  # 解析模型给出的工具名和参数
    if not policy.allow(agent_context.user, name, args):  # 权限：谁能调哪个工具
        return structured_error("无权限调用 " + name)
    try:
        result = with_timeout(                          # 超时：防止工具卡死
            lambda: mcp_client.call(name, args),
            seconds=tool_timeout,
        )
        audit.log(agent_context.user, name, args, result) # 观测与审计：留痕
        return result
    except TimeoutError:
        return structured_error("工具调用超时")
```

要点：模型只给出 `intent`（调用意图），所有控制都在宿主侧完成。`policy`、`with_timeout`、`mcp_client`、`audit`、`structured_error`、`tool_timeout` 是业务侧实现。权限检查决定"能不能调"，超时决定"等多久"，审计记录"谁调了什么、结果如何"。经验值：超时值按工具类型分别设，查询类可以短些，重计算类放宽；重试次数从 2 到 3 次起步，按工具的幂等性决定是否安全重试。

## 追问逐条作答

### 追问一：MCP 在你的架构里是只做权限检查，还是会和环境级安全沙箱一起工作？

两者不在一个层面，通常要一起工作。MCP 这边的权限检查是应用层的白名单/身份校验，决定"这个 Agent、这个用户能不能调这个工具"；环境级安全沙箱是系统层的隔离，限制工具执行时能碰到什么——能访问哪些文件、哪些网络、哪些系统调用。权限检查管"该不该让你调"，沙箱管"就算让你调，你最多能碰到什么"。只靠前者，一旦权限判断有漏洞或工具本身有 bug，Agent 就能碰到不该碰的资源；所以高风险场景要两层都上。

### 追问二：如果已经有 MCP，为什么还需要容器、只读挂载或系统级隔离？

因为 MCP 是协议层，不提供进程和资源隔离。MCP 规范了"能力怎么暴露和调用"，但它不限制工具执行时对宿主环境能做什么。一个工具如果有 bug 或被诱导做越权操作，没有系统级隔离时它可能读到宿主机上的任意文件、访问不该访问的网络。容器限定它能看到的资源边界，只读挂载防止它改关键文件，系统级隔离兜住协议层拦不住的那部分。这是纵深防御：MCP 管应用层准入，容器和挂载管系统层边界，互相补位而不是互相替代。前面讲给 Agent 行为划边界时说过，行为约束和运行时隔离要配合，这里是同一个道理落到 MCP 场景。

### 追问三：发现机制是动态的好在哪？

好在 Server 侧的能力变化能自动被 Agent 感知。不用把工具列表写死在 Agent 代码里，Server 加了工具、改了描述，Agent 下次发现就能拿到。这让工具和 Agent 解耦——工具团队改 Server，不用通知每个 Agent 重新发版。代价是动态带来的不确定性：工具描述变了可能影响模型选择，所以描述变更也要做回归测试。

### 追问四（自补）：模型给出的工具参数不合法怎么办？

在宿主侧校验，别直接透传给 Server。解析出参数后先按 schema 校验：类型对不对、必填有没有、取值合不合法；不合法就返回结构化的错误给模型，让它在下一轮修正，而不是让一个畸形请求打到 Server。这一步既是健壮性，也是安全，防止模型被诱导传入越界参数。

### 追问五（自补）：多个 MCP Server 的工具混在一起，怎么避免选错？

靠描述质量和分组。每个工具的描述要写清"是干什么的、什么时候别用"，避免相似工具描述雷同；能力多的场景可以按业务域分组，先让模型判断用哪个域，再在域内选工具。经验值：暴露给单次决策的工具数量控制在十几个以内，超过就考虑分组或动态筛选。工具一多就选错的道理前面聊过，这里同样是那个问题。

## 加分项

- 讲清"模型决策、宿主执行"的分工，并指出可控环节挂在宿主侧这个要害。
- 正面答好权限检查与环境沙箱的关系，用"应用层准入 + 系统层边界"概括纵深防御。
- 指出 MCP 是协议层、不提供资源隔离，所以容器/挂载不是冗余。
- 落到宿主侧的控制闸代码：权限、超时、审计、参数校验都有位置。

## 常见误区

- **把"接通"当终点**：能调通只是起点，权限、超时、重试、观测、审计才决定敢不敢上生产。
- **以为 MCP 的权限检查能替代沙箱**：MCP 是协议层，不做资源隔离，系统级隔离是另一层防线。
- **让模型直接调 Server**：决策和执行要分开，宿主夹在中间才能插入控制，否则可控性无处安放。
