# 什么是 AI Agent？它和传统 AI 应用的区别是什么？

## 面试官为什么爱问这题

这是 Agent 岗出现率最高的一类题，也是答得最糟的一类。题库给的考察点只有一句：是否理解 Agent 的本质，不会把任何聊天机器人都叫 Agent。

难答的原因不在知识点，而在词被用滥了。只要接过大模型的 Demo，PPT 上多半写着 Agent。面试官真正想筛掉两种人：一种把「调用了几次工具」当成 Agent，理解得太浅；一种把「长期记忆、复杂规划、多智能体」当成准入门槛，理解得太玄。

他要的答案只有一层：**控制权在哪**。下一步由开发者写死的代码决定的，是传统应用；下一步由模型在运行时根据中间结果决定的，才是 Agent。答到这一层，后面的追问基本就落在你的节奏里了。

## 一句话先给结论

**Agent = 模型 + 工具集 + 运行循环 + 当前状态；它和传统 AI 应用的根本区别不在于有没有用大模型，而在于「下一步由谁决定」——传统应用由代码写死的路径决定，Agent 由模型在运行时看着工具返回的结果决定。**

顺着这条结论还有两个推论，面试时补上去很加分：**没有动态决策和状态推进，接再多工具也只是带插件的单轮问答**；反过来，只有三个工具、一个十几行的循环脚本，也完全可以是 Agent。判断标准从来不是功能多少，而是那个决策闭环存不存在。

## 核心原理：四件套怎么咬合在一起

### 每一件各自负责什么

- **模型**：负责理解目标和决定下一步。关键在「决定下一步」这半句——它的输出从"答案"变成了"动作"。这一步最容易被忽略：模型不直接产出用户要的东西，它先产出"接下来该干什么"。
- **工具集**：负责提供外部能力。查库、调接口、跑代码、读写文件，工具是 Agent 唯一能触碰真实世界的手脚。没有工具，模型的决策只在文本里打转，改变不了任何外部状态。
- **运行循环**：让系统不是只回答一次，而是"想一步、做一步、看结果、再决定下一步"。这是四件里最核心也最常被省略的一件——很多挂着 Agent 名字的产品，只给了一次调用工具的机会，循环压根不存在。
- **当前状态**：负责保存消息、工具结果和中间结论。没有它，循环在下一轮就不知道自己刚做了什么、拿到了什么，所谓决策就成了无米之炊。

四件缺一不可，但权重不同：**运行循环是骨架，当前状态是血液，模型和工具是可替换的器官**。换一个更强的模型、加一个工具都不改变架构；把循环拿掉，它就退化成单轮调用了。

### 为什么这么设计：把不确定性从开发期挪到运行期

传统链路要求你在写码时穷举分支，但用户永远会问出你没想到的问法。Agent 的做法是把选择权推迟到运行期：先用工具返回的事实（观察）压缩不确定性，再决定下一个动作。

代价同样直白：**你用可控性换了覆盖面**。路径一旦不可枚举，延迟、成本、成功率就都变成了分布而不是确定值。理解这笔交易，才能在追问里答好"Agent 的可靠性怎么保证"——答案从来不是"换个更好的模型"，而是给循环加护栏。

### 边界：什么才算、什么不必算

题库原文专门点破了一个流行误解：很多人把**长期记忆、复杂规划、多智能体协作**当成必备条件，**不是**。对入门场景来说，能做到"理解目标、决定是否调工具、拿到结果再继续判断"，就已经是 Agent 了。这三项是增强而非定义项，把它们写进必要条件里，等于把绝大多数真实业务场景排除在外。

另一半边界同样重要：固定表单生成、固定知识问答、固定流程审批，这类系统用普通链路或 Workflow 就够了。什么时候才真正需要 Agent？题库给的判据是两条——**路径不固定**，并且**需要根据中间结果继续选择工具或调整路线**。两条同时成立才值得上；只有一条成立，先用编排。

## 横向对比：单轮应用、Workflow、Agent

三者的差异不是能力强弱，而是"决策发生在哪个时刻"：

| 维度 | 传统 AI 应用（单轮） | Workflow（编排） | AI Agent |
| --- | --- | --- | --- |
| 下一步由谁决定 | 代码，只有一条路 | 代码，多分支但提前枚举 | 模型，运行时看着结果决定 |
| 决策时刻 | 开发期 | 开发期 | 运行期（每一次循环） |
| 状态 | 基本不留存 | 流程变量，按节点传递 | 消息 + 工具结果 + 中间结论 |
| 循环 | 无 | 有，但次数与顺序通常固定 | 有，次数与路径不固定 |
| 边界情况的表现 | 答非所问 | 落到兜底节点或直接报错 | 可能绕路自我纠正，也可能绕死 |
| 延迟 / 成本 | 高度可预测 | 可预测 | 是分布，需要预算上限 |
| 典型适用 | 固定问答、模板生成 | 审批流、固定 ETL、批处理 | 排障、调研、开放式助手 |

一句话记法：**从左到右，你在用可预测性换覆盖面**。选型不是追新，而是看你的路径能不能提前画出来。

## 易混概念的边界

面试里答崩，多半不是不会，而是把下面这些混着说了：

| 概念 | 它到底是什么 | 容易混淆的说法 |
| --- | --- | --- |
| Agent vs Workflow | Agent 的下一步由模型决定；Workflow 的下一步由编排图决定 | "节点够多的 Workflow 就是 Agent"（不是，决策者没变） |
| Function Calling vs MCP | 前者是模型侧能力：模型输出结构化的调用意图；后者是工具接入侧的协议约定，解决能力怎么被发现和接入 | "接了 MCP 才有 Function Calling"（两者在不同层） |
| ReAct | 一类"推理—行动—观察"交替推进的模式，是一类写法，不是一个框架或产品的名字 | "我们系统基于 ReAct 框架"（ReAct 不是框架名） |
| 多轮对话 vs Agent | 多轮只是历史消息累积；Agent 必须有工具、循环与状态推进 | "能接着聊就是 Agent" |
| 长期记忆 / 多智能体 | Agent 的可选增强项 | "没有长期记忆就不算 Agent" |

这张表里最关键的一行是倒数第二行：**能记住上句话只说明有状态记录，不等于有决策闭环**。

## 工程实践

### 循环的最小骨架

下面这份是 OpenAI 兼容接口风格的骨架，变量全部有定义，重点看四处注释——它们就是"循环 + 状态"真正落地的地方：

```python
# Agent 循环最小骨架（OpenAI 兼容接口，变量均已定义）
import json, os, time
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
MODEL_NAME = "gpt-4o-mini"
MAX_STEPS = 8              # 经验值：入门场景通常 5–15 步
STEP_TIMEOUT_S = 30        # 单步墙钟超时（经验值，非标准）
RESULT_CHAR_LIMIT = 2000   # 工具结果裁剪上限（经验值，常用区间 1k–4k 字符）

def search_order_fn(keyword: str) -> dict:
    """真实实现里这里查订单库"""
    return {"orders": [{"id": "A1001", "status": "已发货"}]}

TOOL_SPECS = [{
    "type": "function",
    "function": {
        "name": "search_order",
        "description": "按手机号或订单号查询订单状态",
        "parameters": {
            "type": "object",
            "properties": {"keyword": {"type": "string", "description": "手机号或订单号"}},
            "required": ["keyword"],
        },
    },
}]
TOOL_IMPL = {"search_order": search_order_fn}

def run_agent(user_goal: str) -> str:
    messages = [
        {"role": "system", "content": "你是可调用工具的助手。信息不足先调工具，"
                                      "拿到结果再决定是否继续；能回答时直接输出自然语言。"},
        {"role": "user", "content": user_goal},
    ]
    deadline = time.time() + STEP_TIMEOUT_S * MAX_STEPS
    for step in range(1, MAX_STEPS + 1):
        if time.time() > deadline:
            return "已超出总时限，任务中止并转人工。"
        resp = client.chat.completions.create(
            model=MODEL_NAME, messages=messages,
            tools=TOOL_SPECS, tool_choice="auto",
        )
        msg = resp.choices[0].message
        messages.append(msg)                 # ① 模型的"决定"入状态
        if not msg.tool_calls:
            return msg.content               # ② 不再调工具 = 循环出口
        for call in msg.tool_calls:
            name, raw_args = call.function.name, call.function.arguments
            try:
                result = TOOL_IMPL[name](**json.loads(raw_args))
            except Exception as exc:         # ③ 失败也回喂，绝不中断循环
                result = {"error": f"{type(exc).__name__}: {exc}"}
            messages.append({                # ④ 观察结果入状态，驱动下一轮决策
                "role": "tool",
                "tool_call_id": call.id,
                "content": json.dumps(result, ensure_ascii=False)[:RESULT_CHAR_LIMIT],
            })
    return "达到最大步数仍未完成，已中止并转人工。"
```

### 六个护栏：没有它们，循环就是事故源

| 风险 | 具体做法 | 取值参考（均为经验值） |
| --- | --- | --- |
| 空转死循环 | 步数上限 + 总时长上限 + token 预算三道闸，任一触发即转人工 | 步数 5–15；总时长 30s–120s |
| 工具失败即崩 | 异常结构化写回 `role="tool"` 的消息，让模型改参数重试或换路 | 同一工具连续失败 2 次建议换策略 |
| 状态无限膨胀 | 工具结果先裁剪再入库；长对话做滚动摘要 | 单条结果 1k–4k 字符 |
| 写操作重复执行 | 重试必须带幂等键；删除、转账、下单类操作走人工确认 | 幂等键建议由调用方生成 |
| 问题无法复现 | 每一步记录 trace：步序、工具名、参数、耗时、成败，用 trace_id 串起来 | 每步一个 span |
| 只盯终态指标 | 看任务完成率与平均每任务步数，而不是单轮准确率 | 步数突然上涨通常意味着在绕路 |

其中最值得强调两处：**工具失败一定要写回消息**。直接 `raise` 会把已经拿到的上下文全部丢掉，而"根据中间结果调整路线"恰恰要求模型看得见失败原因——参数写错、权限不足、查无记录，这三种失败对应的下一步完全不同。第二处是**幂等键**：Agent 会重试，重试遇上写操作就是重复下单，这是最贵的一类 bug。

## 面试官追问，逐条怎么答

### 追问 1：接了 Function Calling 就算 Agent 吗？

不算，这正是本题最常见的答偏点。这么答：**"接了 Function Calling 只说明模型能表达调用意图，关键是后面有没有把结果拿回来、放进状态、再让模型决定下一步。没有这个循环，它只是一次带工具的单轮调用。"** 顺手把骨架里的四个编号点出来，比说十句定义都有效。

### 追问 2：Workflow 编排出来的东西能叫 Agent 吗？

**"节点再多也不行，因为决策者是编排图而不是模型。"** 但别把话说死：可以补一句折中做法——在 Workflow 的固定节点里，让某一个节点内部由模型自主决定调什么工具、调几次，那是"局部 Agent 化的 Workflow"，工程上很常见，也很务实。

### 追问 3：没有长期记忆、没有多智能体，还算 Agent 吗？

**"算。这两项是可增强项，不是定义项。"** 接着给题库口径：入门场景做到理解目标、决定是否调工具、拿到结果再继续判断，就已经是 Agent。这么答能同时避开"太浅"和"太玄"两个坑。

### 追问 4：什么时候不该用 Agent？

给判据而不是感觉：**路径能提前枚举 → 用 Workflow；写操作不可回滚且容错极低 → 先别自主；延迟和成本有硬上限而路径又不可控 → 谨慎。** 可以用题库里的三个例子收尾：固定表单生成、固定知识问答、固定流程审批，都属于编排就够的场景。

### 追问 5：Agent 的可靠性怎么保证？

先把问题翻译成四件套的语言：**你担心的是不可控性，我用四道闸接住**——步数与预算上限做熔断、工具失败结构化回喂、每一步打 trace、写操作幂等加人工确认。再补一句口径：Agent 的指标看任务完成率而不是单轮准确率，因为它是围绕目标推进的，单轮答对没有意义。

### 追问 6：Function Calling 和 MCP 是一回事吗？

**"不是，它们不在同一层。"** Function Calling 是模型侧能力，解决"模型怎么表达我要调用"；MCP 是工具接入侧的协议约定，解决"外部能力怎么被发现、描述和接入"。可以只有前者没有后者，也可以两者一起用，互不替代。

### 追问 7：成本和延迟怎么估？

给口径而不是数字：**单任务成本 = 步数 × 每步 token + 工具调用费，步数是分布，所以估成本只能估期望和尾部。** 经验做法是先用 max_steps 压住尾部，再看平均每任务步数收敛到哪，反推是否需要降级模型或裁剪状态。

## 60 秒面试回答模板

> 我理解 Agent 是四件套：**模型 + 工具集 + 运行循环 + 当前状态**。模型负责理解目标并决定下一步，工具提供外部能力，循环负责"做一步、看结果、再决策"，状态存住消息与工具结果。

> 它和传统 AI 应用的区别不在用没用大模型，而在**下一步由谁决定**：传统应用是输入请求、返回结果的单轮系统，路径写死；Agent 围绕目标持续决策，路径不固定。

> 不是所有 AI 应用都该叫 Agent：固定表单、固定问答、固定审批用 Workflow 就够；只有路径不固定、需要根据中间结果换工具时才真正需要。长期记忆和多智能体是增强项，不是必备项。

> 护栏我会配四样：步数上限、工具失败结构化回喂给模型、写操作带幂等键、每步打 trace；指标看任务完成率，不看单轮准确率。

## 加分项

- 能把差异收敛成一句话：**"区别在谁决定下一步"**，而不是背四件套定义。
- 主动区分 Agent 与 Workflow，且能说出"某个节点内部自主"这种折中做法。
- 指出长期记忆、复杂规划、多智能体是增强而非门槛，说明你看过真实落地的系统。
- 提到"工具失败要写回消息让模型改参数重试"——这是真写过循环的人才有的肌肉记忆。
- 主动给护栏（步数上限、幂等键、trace），把"不可控"讲成了"可控地不可控"。

## 常见误区

1. **把"调了工具"当 Agent**。缺了循环和状态推进，那只是一次带 tool 的单轮调用。
2. **把条件抬得过高**。要求长期记忆、复杂规划、多智能体齐备才承认是 Agent，等于把入门场景全否掉。
3. **把 Agent 当 Workflow 的升级版**。二者不是版本关系，而是决策者不同，选型看路径能否提前枚举。
4. **只谈能力不谈成本**。循环次数不可枚举，延迟和成本都是分布，不设上限的项目迟早出事故。
