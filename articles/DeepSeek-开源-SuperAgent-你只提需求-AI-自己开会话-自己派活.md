# DeepSeek 开源 SuperAgent：你只提需求，AI 自己开会话、自己派活

## 一个有点反常识的场景

团队群里有人随口说了一句「登录好像偶尔 500」。没有 @ 任何 AI，也没有人建 Issue。

过了一阵子，仓库里多了一个 PR：复现步骤、根因、修复方案都写好了。如果它复现不出来，或者修法需要人来拍板，那就什么都不发。

这不是演示视频里的设想。DeepSeek 内部基于这套架构的实例已经在日常研发中持续跑着，参与问题复现、代码审查响应，甚至参与这套系统自己的迭代。

10 月 31 日晚，DeepSeek Harness 团队把设计思路公开了，配套原型以 MIT 协议开源。没有发布会，也没有跑分榜，只有一篇讲设计的文章和一个能跑起来的仓库。

## 一句话结论

**SuperAgent 不是一个更聪明的模型，而是一层系统：它把「管会话」这件事从人手里拿走，交给 AI 自己调度。**

它要的效果是——你始终觉得自己只在跟一个助手说话，但底下开了几个会话、谁在干什么、上下文怎么同步，你都不用管。

整套设计的原则只有一句，写在开源仓库 docs 的第一行：

> 尽可能少占用人的注意力，尽可能多给出价值。

## 一、它要解决的不是模型强弱，是你顾不过来

过去一年，单任务 Agent 已经证明了一件事：模型能自己调用工具，把一件复杂的事做完，中间不太需要人盯着。

问题转移到别处了。

一个人通常只能同时跟进 **3 到 5 个活跃会话**。超过这个数，你就得手动切换、自己记住「哪句话是在哪个窗口里说的」。而现有 Agent 都是以「单个会话」为单位工作的，于是出现四个绕不过去的约束：

- **同步阻塞**：一个任务跑着，新指令进不来
- **上下文搬运**：群里定了方案 A，PR 评论里改成方案 B，两条信息两个窗口，得你自己搬
- **上下文污染**：几个任务挤在一个会话里，细节互相干扰
- **离线即停**：进程挂在本地终端，电脑一合盖，任务就断了

所以结论很不对称：**单任务的上限看模型能力，多任务的上限看人的注意力。**

SuperAgent 的出发点就是把这一层接管掉。

## 二、它想变成什么样：四个特征

| 特征 | 具体表现 | 靠什么实现 |
| --- | --- | --- |
| 连续 | 在群聊、PR 评论里交互，跨渠道理解同一件事 | 多信道接入 + Thread 统一建模 |
| 高效 | 上一条没跑完，也能接新指令 | 异步工具调用 + Worker 并发 |
| 主动 | 环境里有事就推进，没事就闭嘴 | 事件驱动 + 两级过滤 |
| 持久 | 一直在线，出异常能自己恢复 | 存算分离 + 外部巡检 |

四个词听起来像宣传语，但每一个都对应一组具体的工程决定。下面拆开看。

## 三、架构：五个模块，基本都是操作系统借来的

官方自己说得很直白：这套设计没有提出新理论，是把调度、缓存、存算分离、看门狗这些计算机系统里的老思路，搬进了 Agent。

| 模块 | 解决什么 | 借自哪里 |
| --- | --- | --- |
| 双层架构 | 上下文连续 vs 并发吞吐 | 进程 / 调度器分工 |
| 事件驱动 | 没人派活时怎么知道该干啥 | 中断与事件循环 |
| 订阅直通 | 中心节点被消息压垮 | 发布订阅、旁路 |
| 上下文当缓存 | 长任务撑爆窗口 | 局部性与 Cache |
| 存算分离 + 巡检 | 掉线即停、静默跑偏 | 无状态计算 + Watchdog |

### 1. 双层架构：Router 只分派，Worker 只干活

这是整套设计的骨架。

**Router** 是常驻的全局协调节点，接所有渠道的消息，理解任务之间的关系，决定派给谁。它**不执行任务**——只有 14 个编排工具，文档里说它甚至可以不给 Bash。实践中配一个轻量模型就够。

**Worker** 是真正干活的人。每个工单一个独立会话、一个独立工作目录，上下文互相隔离，挂载完整工具，配最强的模型。它不直接对人说话，结果由 Router 统一回复。

这里有个细节值得单独说：**Worker 的工具是白名单裁出来的**——保留文件、shell、搜索、子 Agent 这些执行类工具，但不给「向人提问」「改配置」「启动别的会话」「编辑外部文档」。

换句话说，职责分离不是靠提示词写「你是调度器，不要执行」，而是**靠工具清单物理隔绝**。想越权也没有工具可用。做过 Agent 的人都知道，这比任何提示词约束都可靠。

### 2. 事件驱动：环境本身会派活

驱动 Agent 的输入从「人敲提示词」变成「环境里发生的事」——群消息、Issue 评论、CI 失败、日程提醒。这类事件叫 Trigger。

难点在噪音。真实群聊里绝大多数消息跟 Agent 无关，全丢给模型判断，成本和时间都扛不住。所以分两级：

- **快路径**：程序规则按来源、群组、白名单先筛一遍，确定性条件，零模型成本
- **慢路径**：剩下的候选才交给模型，按提示词里的策略判断「要不要接」

配套的还有一个机制叫**投机执行**，借自 CPU 的推测执行：结果会不会被采用还不确定时，先在后台试着做。群里有人报 Bug，它先去复现、定位、找修法，确认修得动才把 PR 递上来；修不动就保持安静，一个字都不说。

这一条是主动型 Agent 的生死线。没有它，「主动」会立刻退化成「刷屏」。

### 3. 订阅直通：让 Worker 自己收消息

Worker 接手一个 PR 之后，会**直接订阅这条 Thread**。之后的评论由程序直接投给它，不再经过 Router。Router 只处理「还没人认领」的新事件。

订阅是多对多的：两个 Worker 订阅同一个 PR，就能看到彼此在改什么，自己发现冲突。

这个设计省下的不是延迟，是钱和中心节点压力。官方实验里，把直通去掉，完成时间基本没变，但 Router 的决策数多了约 30%，读缓存 Token 从 2,323 万涨到 3,177 万。

本质是：**把 Router 从「消息总线」降级成「调度器」。** 总线一旦承载所有流量，就会同时变成瓶颈和成本中心。

### 4. 上下文当缓存管

长任务最容易死的地方是上下文窗口。做法是把窗口当 Cache 用：

- 一定会用到的信息**内联**进去
- 长内容截断后**留一个续读入口**，需要时再展开
- 每个对象都带上「下一跳」的 ID，形成一条引用链，可以从一条消息顺着 Thread、会话一路找回去

预算给得很具体：单次评估最多带 4,000 字符的事件、最多 8 个相关工单；对话窗口取前 5 条加两侧各 5 条，通常每条 400 字符，紧邻的两条放宽到 1,200 字符，其余只给 50 字符摘要。

原文有句话挺狠：**浪费上下文窗口，就是浪费模型的智能。**

### 5. 存算分离 + 外部巡检：让它真的能「一直在线」

把三样东西拆开放：

| 部分 | 放在哪 | 解决什么 |
| --- | --- | --- |
| Agent 的推理循环 | 云端 | 前台不被长任务卡住 |
| 会话状态 | 独立存储（一个 SQLite 文件） | 进程重启、设备离线都能恢复 |
| 代码仓库与工具链 | 你自己的机器 | 代码不出本地，权限边界清楚 |

再加一个**外部巡检**：不在主流程里，另起一个会话定时检查。它不只看接口有没有报错，还要判断各个 Worker 是不是真的在推进、有没有陷入无效循环。

这点很关键——长任务里，「卡住了」和「在思考」从外部看一模一样，接口级健康检查根本抓不到。

## 四、跑一遍：一条消息的完整旅程

把上面五块串起来，其实一条链路就够：

```python
# 伪代码：一次事件的完整生命周期
t = source.poll()          # 每分钟轮询一次
store.record(t)            # 入库
thread.attach(t)           # 挂到 Thread
if not fast_path(t): return    # 规则先筛
if not slow_path(t): return    # 模型再判断
d = eval.decide(t)         # accept/stop/ignore
if d == ACCEPT:
    k = tickets.create(t)  # 建工单（含授权）
    workers.reserve(k)     # 占一个槽位
    worker.run(k)          # 独立会话 + 目录
    # 后续评论由订阅直通投给 worker
    reply.outbox(k.conversation)   # 回原对话交付
```

几个容易被忽略的设计：

- **工单带授权范围**：不只是「做什么」，还有「做到什么程度」「谁能提要求」
- **没人认领的消息不会丢**：工单结束后剩下的跟进会回落到评估环节重新判断；评估超时会重排，连续两次超时、第三次才标记为不可用
- **拒绝也要说清楚**：每个决定都带原因码，面板上按码渲染人话

长跑系统里，「这条消息后来去哪了」必须有确定答案，否则丢任务只是时间问题。

## 五、效果和代价

实验设置：群聊加 CI 消息流，单次约 300 条消息、其中约 20 条是真实工作请求，编码部分用「只耗时」的工具替代（只测调度、不测编码质量），每种方案跑 5 次。

| 指标 | SuperAgent | 单会话 + 子 Agent 工具 |
| --- | --- | --- |
| 完成时间 p50 | 12.4 分钟 | 未披露 |
| 完成时间 p95 | 15.7 分钟 | 29.5 分钟 |
| 读缓存 Token | 偏高（多会话的固有成本） | 较低 |

比「快一倍」更值得看的是括号里那行：单会话方案 5 次里**一次都没主动调用子 Agent**。不是不能，是没想到。

这说明在单会话范式下，并行化依赖模型临场判断，而临场判断不可靠。SuperAgent 的改进不是模型变聪明了，是**把分配动作写进了系统结构**。

另外两组拆解也很有意思：去掉订阅直通，时间不变但 Token 涨 37%；把事件频率从每分钟 1 条拉到 40 条，单次请求从 2.5 秒变慢到 3.9 秒，但单次决策的成本从 6.4 秒降到 1.6 秒。

**延迟和吞吐是两套优化目标。** 用单一指标评价 Agent 调度，几乎必然得出错误结论。

## 六、它和别的东西有什么不一样

| 形态 | 谁开会话 | 谁分派 | 断线后 |
| --- | --- | --- | --- |
| 聊天助手 | 人 | 无 | 没有任务 |
| 单会话 Agent | 人 | 人 @ 它 | 任务停 |
| 多 Agent 框架 | 人跑一次 | 框架内调度 | 通常不持久 |
| 工作流引擎 | 事件触发 | 确定性编排 | 持久化好 |
| SuperAgent | 系统 | Router 判断 | 可恢复 |

它的位置介于工作流引擎和模型自主之间：**决策由模型做，但决策的边界由规则框住**（快路径先筛、慢路径再判、主动工作必须先写规则、默认只观察不执行）。

## 七、现在能用到什么程度

官方态度很明确：**这是研究原型，不是产品，不建议直接上生产。** 代码大量由 coding agent 写成，可能有 bug；开源版和内部版、和文章描述的实现也不完全一致。

几个已知的限制值得提前知道：

- 只支持单个 GitHub 仓库加可选飞书，不支持 GitHub Enterprise Server
- 权限很大：运行时是完整系统权限，官方建议用专门的系统账号隔离
- 存储不清理：事件、决定、已结束工单都无界增长，长跑必然要面对
- Router 是单点，文档没有多 Router 方案
- 多 Worker 冲突只做到「互相看得见」，没有仲裁机制，最后仍要人裁

想自己跑通，路径是「先看、再说、最后才做」：

1. 起一个专门的 GitHub 账号给 Agent 用，别用自己的
2. 装好 Node 22 以上、pnpm、git、Python、tmux、GitHub CLI
3. 装 CLI、clone 原型、构建、把本地目录挂成插件
4. 模型分层配：Router 用便宜的，Worker 用强的
5. 面板里配事件源、准入策略、执行目录
6. **白名单先只放自己，用观察模式跑一周**，看它「本来会做什么」
7. 自动合并最后再开

## 结语

如果只记一件事，记这个：**SuperAgent 把「Agent 该不该开始干活」从一个提示词问题，变成了一个有过滤、有预算、有审计、有回落的系统流程。**

它的价值不在于提出了新概念，而在于证明了「人的注意力」可以被当成一个可设计的系统约束——而不是只能靠个人精力硬扛。

至于它会不会成为下一代 Agent 的标准形态，取决于两件它自己还没解决的事：Router 怎么水平扩展，多 Worker 冲突怎么自动仲裁。解决了是架构，解决不了，它是一份极好的工程笔记。
