# 你会怎么做大模型应用的可观测性？

<!-- growth-hook:v1 -->
系统上线后用户说“答得不对”，你却查不到它当时检索了什么、调了哪个工具、看到了什么状态——这才是大多数项目最难堪的时刻。这题考的就是你会不会把可观测性当成基础设施而不是补丁。

## 面试官为什么爱问这题

这题考的是你有没有把大模型应用当成正经分布式系统来运维。很多人做完一个 Agent 就交付了，日志打几行 print、出错看控制台，一旦上了生产、链路变长，出了问题根本查不清。面试官想听的是一套完整的可观测性体系——日志、指标、Trace 三件事，以及怎么用一个 ID 把全链路串起来。对 Agent 系统尤其如此，因为问题大多发生在中间步骤，而不是最终输出那一刻。前面聊过性能瓶颈怎么定位、也聊过幻觉治理靠监控，这一篇把这些收束到"可观测性体系怎么建"这个基础能力上。

## 一句话先给结论

**至少做到三件事：有日志、有指标、有 Trace。也就是能看见请求怎么流过系统、每一步花了多久、失败在哪里、用了多少 token、最后输出了什么。具体上要打通 trace_id / request_id，把入口请求、Prompt 版本、模型版本、索引版本、检索结果、工具调用、异常信息、耗时和 token 用量串起来。如果用 LangChain / LangGraph，还要重点看节点流转、状态更新、人工中断点、重试次数和最终退出原因。真正有用的可观测性不是"最后报错了"，而是能告诉你它在哪个节点卡住、为什么重试、为什么结束、当时看到了什么状态。**

## 核心原理：日志、指标、Trace 三件事

### 日志：发生了什么

日志回答"发生了什么"——每一次关键动作的记录：入口请求是什么、调用了哪个工具、返回了什么、抛了什么异常。日志要带上下文，不是孤零零一行错误，而是能看出这次错误发生在哪个请求、哪个环节。没有结构化日志，排查只能靠翻文本、靠猜。

### 指标：整体表现怎么样

指标回答"整体表现怎么样"——可聚合的量化数据：请求量、成功率、延迟分布、token 用量、错误率、各分支的调用量。指标的作用是看趋势和异常：某个时间点错误率突然升高、某类请求延迟变大，这些靠单条日志看不出来，靠指标才能发现。

### Trace：一次请求怎么流过的

Trace 回答"一次请求怎么流过系统"——把一次请求的所有环节串成一条链，每个环节是一个 span，带耗时和上下文。前面讲性能瓶颈定位时说过给每步打 trace 和 span、按 wall time 排序找头部，那是 Trace 在性能场景的用法；这里讲的是它作为可观测性基础设施的完整形态。

| 能力 | 回答什么 | 典型内容 |
| --- | --- | --- |
| 日志 | 发生了什么 | 入口请求、工具调用、返回结果、异常 |
| 指标 | 整体表现怎么样 | 请求量、成功率、延迟、token、错误率 |
| Trace | 一次请求怎么流过 | 各环节 span、耗时、上下文串联 |

三者互补，缺一不可。只有日志，看不清全局趋势；只有指标，定位不到具体问题；只有 Trace，没有聚合视图发现不了系统性异常。

### 关键：用一个 ID 串起来

三件事要真正有用，前提是把它们串起来。打通 trace_id / request_id——一次请求分配一个 ID，所有日志、指标、Trace span 都带上它。要串联的信息包括：入口请求、Prompt 版本、模型版本、索引版本、检索结果、工具调用、异常信息、耗时、token 用量。

为什么要串版本？因为大模型应用的效果变化常常来自版本变更——换了 Prompt、换了模型、重建了索引，某个时间点效果突然变了，你得能对应上当时用的是哪个版本。没有版本字段，出了问题只能靠回忆"那会儿是不是改过什么"。

| 要串联的信息 | 为什么重要 |
| --- | --- |
| trace_id / request_id | 把全链路串起来，双向定位 |
| Prompt / 模型 / 索引版本 | 效果变化常来自版本变更 |
| 检索结果 / 工具调用 | 看清中间步骤看到了什么 |
| 异常信息 / 耗时 / token | 定位失败点和成本 |

### Agent 系统为什么更需要它

因为 Agent 的问题大多在中间步骤，而不是最终输出。最终输出可能看着正常——答出来了，但过程可能走了十条弯路、重试了三次、在一个节点绕了半天。只看结果你以为一切正常，看 Trace 才发现链路早就乱了。题库那句很到位：真正有用的可观测性，是能告诉你它在哪个节点卡住、为什么重试、为什么结束、当时看到了什么状态。

如果用 LangChain / LangGraph，还要重点看：节点流转（走了哪些节点、什么顺序）、状态更新（状态怎么变的）、人工中断点（在哪挂起等审批）、重试次数（哪个节点反复重来）、最终退出原因（为什么结束——是正常完成、达到上限、还是异常退出）。这些是图编排特有的观测点，普通应用的观测维度覆盖不到。

## 工程实践：从一次请求看观测点怎么埋

落到实现，关键是给一次请求建立贯穿始终的上下文：

```python
# 伪代码：给一次请求建 trace，把关键字段串进每个环节
def handle(request):
    trace_id = new_trace_id()                 # 业务侧：生成并透传全链路 ID
    ctx = {"trace_id": trace_id,
           "prompt_ver": PROMPT_VERSION,      # 版本字段：便于效果回溯
           "model_ver": MODEL_VERSION}

    log(ctx, "request_in", request)           # 日志：入口
    with span(ctx, "retrieve"):               # Trace：检索段
        docs = retrieve(request)
        log(ctx, "retrieval_result", docs)    # 检索结果进日志
    with span(ctx, "model"):                  # Trace：模型段
        out = model.invoke(request, docs)
        metric("tokens", len(out), ctx)       # 指标：token 用量

    log(ctx, "request_out", out)              # 日志：出口
    return out

# new_trace_id / span / log / metric 为业务侧或观测库实现
```

要点：`ctx` 里的 trace_id 贯穿所有日志、span、指标；版本字段记录当时用的 Prompt 和模型；检索结果、token 都带上下文记录。变量是业务侧实现。真实项目用专门的观测框架会更完整，这里只示意"一个 ID 串全链路、关键字段都带上"的思路。

## 追问逐条作答

### 追问一：日志、指标、Trace 为什么缺一不可？

因为它们回答不同问题。日志回答"发生了什么"，能看单个细节但看不清全局；指标回答"整体怎么样"，能看趋势和异常但定位不到具体请求；Trace 回答"一次请求怎么流过"，能看单条链路但没有聚合视图。三者组合才能既发现系统性问题、又定位到具体请求、还能看清过程细节。只做一样，排查都会有盲区。

### 追问二：为什么必须串联版本信息？

因为大模型应用的效果变化常来自版本变更。换了 Prompt、换了模型、重建了索引，效果可能在某个时间点突然变化。如果观测数据里带了版本字段，就能对应上"效果变差是从换 Prompt 那次开始的";没带，就只能靠回忆和逐个试。前面讲提示词版本管理和回归时说过版本的重要性，落到可观测性上，版本字段是效果回溯的关键线索。

### 追问三：Agent 和普通应用的可观测性有什么不同？

普通应用看输入输出和异常就够了；Agent 更要看中间过程，包括节点流转、状态更新、重试、中断、退出原因。因为 Agent 的输出可能看着正常但过程已经乱了，只看结果发现不了。前面讲性能瓶颈定位时说过"问题常在闭环设计"，那些闭环问题，比如反复进同一节点、缺完成信号，都得靠过程级观测才能看见。这些观测点要在图编排时就埋好，等出问题再补往往来不及——那时候你连当时发生了什么都复原不出来。

### 追问四（自补）：可观测性和"多打日志"是一回事吗？

不是。多打日志只增加了日志量，甚至会制造噪声；可观测性强调的是结构化、可串联、能回答具体问题。关键不是日志多，而是每条记录都带上下文（trace_id、版本）、关键节点都有埋点、日志指标 Trace 能互相对照。一堆没有上下文的散乱日志，出了事照样查不清。经验值：埋点要覆盖关键节点，但别什么都打，否则噪声淹没信号、还增加存储成本。

### 追问五（自补）：怎么判断可观测性做得够不够？

用一个实际问题检验：用户报"上次那个回答不对"，你能否在几分钟内定位到——那次请求走了哪些节点、用了什么 Prompt 和模型版本、检索到了什么、模型看到了什么状态、为什么那样结束。如果能在几分钟内回答，观测就够了；如果只能翻日志猜、甚至根本查不到，就是不够。经验值：别等出事才发现观测缺口，平时定期拿真实问题做"排障演练"，检验观测数据到不到位。

### 追问六（自补）：观测数据本身要不要治理？

要。观测数据也会失控——日志量随请求量膨胀、Trace 采样太多存储爆掉、敏感信息被记进日志造成泄露。经验值：给日志设留存期限、给 Trace 设采样率（比如全量记录异常请求、正常请求按比例采样）、对 prompt 和用户输入做脱敏再落盘。观测的目的是排障，不是把系统拖垮或制造新的安全风险。这一点在内网和合规场景尤其重要，因为观测数据往往也受数据不出域的约束。

## 60 秒面试回答模板

> 我会做三件事：日志、指标、Trace，分别回答发生了什么、整体怎么样、一次请求怎么流过，三者互补缺一不可。关键是用 trace_id / request_id 串起全链路，带上入口请求、Prompt / 模型 / 索引版本、检索结果、工具调用、异常、耗时、token 用量，版本字段尤其重要，因为效果变化常来自版本变更。Agent 更要观测中间步骤：节点流转、状态更新、人工中断、重试次数、退出原因。有用的观测不是告诉你最后报错了，而是卡在哪个节点、为什么重试、为什么结束、当时看到什么状态。我会拿真实问题做排障演练，看几分钟内能不能定位来判断够不够。

## 加分项

- 用日志、指标、Trace 三件事搭框架，说明各自回答什么、为何互补。
- 强调 trace_id 串联和版本字段，落到效果回溯这个真实价值。
- 点出 Agent 观测的重点在中间过程，不是最终输出。
- 给出"排障演练"判断观测是否到位，方法可操作。

## 常见误区

- **把可观测性当多打日志**：散乱无上下文的日志制造噪声，不等于可观测。
- **只观测最终输出**：Agent 问题多在中间步骤，只看结果发现不了。
- **忽略版本信息**：没有版本字段，效果变化无法回溯到具体变更。
