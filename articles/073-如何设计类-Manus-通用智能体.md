# 如何设计类 Manus 通用智能体？

<!-- growth-hook:v1 -->
类 Manus 的通用智能体一火，很多人把“通用”当成卖点来讲。但这题的高分答法恰恰相反：先回到 Agent 的最小骨架，再说通用性是怎么扩展出来的——没骨架，谈通用就是空中楼阁。

## 面试官为什么爱问这题

这题偏难，考的是通用任务型 Agent 的系统拆分能力。很多人一听"类 Manus 通用智能体"就往大了说，通用、自主、什么都能干，面试官想听的恰恰相反：先别谈通用，回到 Agent 的最小骨架，想清楚这类系统是在什么基础上扩展的。题库给了很好的切入点：类 Manus 本质是把"模型 + 工具集 + 运行循环 + 当前状态"这四层扩展到更长任务链和更复杂任务空间。前面聊过 Agent 的最小核、工具调用、状态管理、行为边界，这一篇把这些收束成"设计一个通用任务执行框架"的系统视角，也是第 10 章业务场景设计题的开篇。

## 一句话先给结论

**这类系统不宜先强调"通用"，而应先回到 Agent 的最小骨架：模型 + 工具集 + 运行循环 + 当前状态。所谓类 Manus，本质上是把这四层能力扩展到更长任务链和更复杂任务空间。设计上要有五个模块：任务理解与规划、工具调度、状态与记忆、执行与反思、安全与治理。它和普通 Agent 的区别不在"工具更多"，而在于需要长期推进任务、处理中间产物、管理复杂状态，并在长链路里维持稳定性——它更接近一个通用任务执行框架，而不是单轮问答机器人的放大版。**

## 核心原理：从最小骨架扩展

### 最小骨架：四层

任何 Agent 都逃不出这四层：模型（决策大脑）、工具集（能做什么）、运行循环（怎么一步步推进）、当前状态（进行到哪）。类 Manus 不是凭空造一个新物种，而是把这四层做深、做长——任务链更长、工具更复杂、状态更庞大、循环更持久。先说清这个，才不会陷入"通用"的空谈。

### 五个核心模块

**任务理解与规划模块。** 把目标拆成可执行步骤。用户给的是一个模糊的目标——"帮我调研这个市场并出报告"，系统要能拆成检索、整理、分析、生成等步骤。这是长任务的起点，拆得合不合理决定后面能不能推进。

**工具调度模块。** 统一接搜索、浏览器、代码执行、文件系统等工具。工具多不是重点，重点是统一调度——让模型能用一致的方式发现、选择、调用各种能力。前面讲 MCP 接入、工具治理时说过这些，这里是它们在通用 Agent 里的位置。

**状态与记忆模块。** 维护任务上下文、待办和阶段成果。长任务会产出大量中间结果，这些不能全堆在窗口里，得有状态管理——什么放当前上下文、什么存起来按需取、待办怎么跟踪。前面讲记忆分层时展开过，这里是它在长任务场景的应用。

**执行与反思模块。** 根据中间结果继续执行、修正或重试。这是"运行循环"的深层形态——不是一路走到黑，而是每步之后看结果、判断对不对、要不要调整。前面讲执行闭环和完成信号时说过这些，长任务里反思尤其重要，因为一步错可能后面全错。

**安全与治理模块。** 权限控制、日志、失败恢复和人工接管。前面讲行为边界、沙箱隔离、可观测时都展开过，这里作为通用 Agent 不可或缺的模块列进来——任务越长、能力越强，治理越重要。

| 模块 | 解决什么 | 扩展了骨架的哪一层 |
| --- | --- | --- |
| 任务理解与规划 | 把目标拆成步骤 | 运行循环 |
| 工具调度 | 统一接入和调用工具 | 工具集 |
| 状态与记忆 | 维护上下文、待办、阶段成果 | 当前状态 |
| 执行与反思 | 继续、修正、重试 | 运行循环 |
| 安全与治理 | 权限、日志、恢复、接管 | 贯穿四层 |

把类 Manus 和普通 Agent 在几个维度上对比，区别会更直观：

| 维度 | 普通 Agent | 类 Manus 通用智能体 |
| --- | --- | --- |
| 任务长度 | 单轮或短链路 | 长任务链，持续推进 |
| 中间产物 | 少，上下文能装下 | 多，需落盘和索引 |
| 状态管理 | 简单上下文 | 复杂状态、待办、阶段成果 |
| 反思机制 | 可有可无 | 每步检查、修正、重试 |
| 稳定性要求 | 做完即可 | 长链路全程要稳 |
| 本质 | 问答/单任务的放大 | 通用任务执行框架 |

### 和普通 Agent 的区别

题库点得很准：区别不在"工具更多"，而在于四点——需要长期推进任务、处理中间产物、管理复杂状态、在长链路里维持稳定性。所以它是"通用任务执行框架"，不是"单轮问答机器人的放大版"。

这个区分很重要。如果只是工具更多，那堆工具就行；但长期推进意味着要解决"任务怎么不跑偏、状态怎么不丢、失败怎么恢复、链路怎么稳定"——这些是框架级问题，不是堆能力能解决的。面试官想听的就是你能看到这一层。

## 工程实践：长任务怎么维持稳定

设计这类系统，最大的挑战是"长"。几个关键动作：

**任务拆解要有边界。** 拆得太粗，一步太长不好控制；拆得太细，步骤爆炸、调度成本高。经验值：每个子步骤应该是可验证结果的——做完一步能判断成没成，这样便于反思和重试。

**中间产物要落盘。** 长任务会产生大量中间结果，不能全靠上下文记着。把阶段成果存起来、带索引，需要时取回。前面讲记忆分层时说过长期信息按需召回，这里同理。

**每步之后要检查。** 执行与反思模块的核心——每步做完检查对不对、有没有偏离目标、要不要调整计划。没有这个检查，长任务会在错误路上越走越远。

**要有明确的完成信号和上限。** 前面讲 Agent 终止条件时说过，长任务更要明确"什么叫完成"，否则会反复检查停不下来；同时设步数和时间上限，防止无限推进。

```python
# 伪代码：类 Manus 的长任务运行循环骨架
def run_task(goal):
    plan = planner.decompose(goal)              # 任务理解与规划
    state = TaskState(plan)                     # 当前状态
    while not state.done and state.within_budget():  # 完成信号 + 预算上限
        step = state.next_step()
        result = tools.execute(step)            # 工具调度
        verdict = reflector.check(result, goal) # 执行与反思
        if verdict.needs_retry:
            state.retry(step)
        elif verdict.needs_replan:
            state.replan(reflector.suggestion())
        else:
            state.commit(step, result)          # 存阶段成果
        audit.log(goal, step, result, verdict)  # 安全与治理
    return state.final_result()

# planner / tools / reflector / TaskState / audit 为业务侧实现
```

要点：规划—执行—反思—提交的循环，带完成判断和预算上限，每步留审计。`TaskState` 管状态，`reflector` 做反思。变量都是业务侧实现。

## 追问逐条作答

### 追问一：类 Manus 和普通 Agent 最大的区别是什么？

不是工具数量，而是任务的长度和复杂度。类 Manus 要长期推进任务、处理大量中间产物、管理复杂状态，还要在长链路里维持稳定。普通 Agent 通常是单轮或短链路，做完就结束。所以它是"通用任务执行框架"——重点在框架如何支撑长任务，而不是堆更多工具。

### 追问二：为什么任务规划模块很重要？

因为长任务不能想到哪做到哪。用户给的是模糊目标，规划模块把它拆成可执行步骤，系统才知道先做什么、后做什么。拆得好，任务推进有序、每步可验证；拆得差，系统会在步骤间反复横跳、偏离目标。前面讲任务拆解时说过每步要可验证结果，那样反思和重试才有抓手。

### 追问三：执行与反思模块为什么不能省？

因为长任务里一步错会导致后面全错。执行模块推进任务，反思模块每步之后检查结果——对不对、有没有偏离、要不要调整。没有反思，系统就是一路走到黑，错了一步后面全在错误基础上继续。前面讲执行闭环时说过中间结果要被用来调整，反思模块正是这个机制的落地。

### 追问四（自补）：长任务的中间产物怎么管？

落盘 + 索引 + 按需取回。长任务会产生大量中间结果，全堆在上下文里既贵又乱。把阶段成果存到外部、带索引，需要哪部分再取回。前面讲记忆分层时说过长期信息按需召回，长任务的中间产物同理。经验值：只把当前步骤需要的上下文留在窗口里，其余存起来，用一个轻量索引记录"什么成果存在哪"。

### 追问五（自补）：这类系统最容易在哪里失控？

三个地方。一是长链路跑偏，没有反思和完成信号，任务越走越离谱；二是状态丢失，中间结果没管好，后面步骤拿不到前面的成果；三是资源失控，步数、时间、成本没有上限，一直试下去。前面讲 Agent 行为边界时说过熔断和预算，这里更要严格执行，因为任务链越长、失控的代价越大。

## 加分项

- 用"最小骨架扩展"定性，不空谈通用，落地感强。
- 五个模块对应到骨架四层，逻辑自洽。
- 点出区别在任务长度和复杂度，不在工具数量。
- 给出长任务稳定性的具体做法，可操作。

## 常见误区

- **先谈通用、堆工具**：忽略长任务的状态、反思和稳定问题。
- **把中间产物全堆上下文**：又贵又乱，应落盘按需取回。
- **缺完成信号和上限**：长任务容易跑偏或无限试下去。
