# 如何设计一个 Deep Research 系统？

<!-- growth-hook:v1 -->
Deep Research 最容易被理解成“多查几轮再总结”。可真正的差别不在查几次，而在它把研究过程拆开了：规划、检索、交叉验证、引用管理，每一步都要能被追溯。答不到这一层，就只是个长一点的 RAG。

## 面试官为什么爱问这题

这题偏难，考的是复杂研究型系统的模块拆分能力。很多人把 Deep Research 想成"增强版搜索 + 总结"，那是把它降级成了单轮问答；面试官想听的是你能不能说出它与普通 RAG 的本质差异——从"单轮问答"升级成"多轮研究流程"，以及围绕这个差异该怎么拆模块。还要能指出一个工程取向：这类系统倾向于用 Workflow 或 LangGraph 这类显式编排，而不是完全交给黑盒对话 Agent。前面聊过工作流与 Agent 的选择、RAG 分层、引用的事，这一篇把这些收束成"设计一个 Deep Research 系统"的完整答案。

## 一句话先给结论

**Deep Research 的核心不是"查一次资料再总结"，而是"围绕复杂问题持续研究并形成结构化结论"。完整设计通常包括五个模块：查询规划器拆子问题、检索执行器多源检索、信息融合层去重与冲突检测与证据对齐与可信度加权、迭代控制器在证据不足时继续补检、报告生成器输出摘要正文引用和时间戳。它和普通 RAG 最大的差异是从单轮问答升级成多轮研究流程，设计重点不只是召回率，还包括规划质量、引用质量、可信度和过程可回放性；落地更倾向 Workflow 或 LangGraph 这类显式编排，而不是交给黑盒对话 Agent。**

## 核心原理：五个模块

### 查询规划器：把复杂问题拆成子问题

用户给的是一个复杂问题——"这个行业过去三年的格局变化"，系统要先把它拆成可研究的子问题：市场规模、主要玩家、技术路线、政策环境……拆得好不好决定研究的覆盖面和深度。这是从"单轮问答"走向"多轮研究"的第一步。

### 检索执行器：多源检索

面向搜索、数据库、知识库做多源检索。不同子问题适合不同来源——有的要查网页、有的要查数据库、有的要查内部知识库。执行器统一调度这些来源，为每个子问题找到证据。前面讲 MCP 接入和工具调度时说过统一接入，这里是它们在研究场景的应用。

### 信息融合层：从材料到证据

做去重、冲突检测、证据对齐和可信度加权。多源检索拿回来的材料有大量重复、相互矛盾、可信度参差——同一个数据不同来源说法不一，权威媒体和自媒体的权重也不同。融合层要去掉重复、发现冲突、把证据对齐到同一个事实维度、按可信度加权。这是 Deep Research 里最容易被忽略却很关键的一层。

### 迭代控制器：证据不够就继续

发现证据不足时继续补检，而不是一次性结束。研究是迭代的——第一轮检索后可能发现某个子问题证据不足、或发现了新的关键线索，控制器要判断要不要再查、查什么。这是"持续研究"的核心机制，也是它和普通 RAG 最大的过程差异。

### 报告生成器：结构化输出

输出摘要、正文、引用和时间戳。最终不是给一段话，而是一份结构化报告——有摘要、有正文、有可追溯的引用、有时间信息。前面讲 RAG 引用和忠实度时说过引用的重要性，这里把它作为报告的基础组成部分。

| 模块 | 解决什么 | 对应研究工作流的哪段 |
| --- | --- | --- |
| 查询规划器 | 拆子问题 | 任务拆解 |
| 检索执行器 | 多源检索 | 检索编排 |
| 信息融合层 | 去重、冲突、对齐、加权 | 证据处理 |
| 迭代控制器 | 证据不足继续补检 | 多轮迭代 |
| 报告生成器 | 摘要、正文、引用、时间戳 | 结构化输出 |

把 Deep Research 和普通 RAG 放一起对比，差异会更清楚：

| 维度 | 普通 RAG | Deep Research |
| --- | --- | --- |
| 交互轮次 | 单轮问答 | 多轮研究流程 |
| 问题处理 | 直接检索 | 先拆子问题再检索 |
| 检索方式 | 通常一次 | 多源、多轮、按需补检 |
| 证据处理 | 拼接上下文 | 去重、冲突检测、可信度加权 |
| 输出形态 | 一段答案 | 摘要+正文+引用+时间戳的结构化报告 |
| 设计重点 | 召回率 | 规划、引用、可信度、过程可回放 |

### 研究型工作流：三段式理解

更工程化的表达是把整个系统看成一个研究型工作流：

**前面是任务拆解和检索编排。** 规划器拆问题、执行器安排检索。

**中间是多轮证据收集、去重、冲突处理。** 检索—融合—判断够不够—不够再检索，循环推进。

**后面是结构化报告生成和引用整理。** 把研究结论组织成带引用的报告。

这个三段视角把五个模块串成了一条流程，回答了"它们怎么配合"。

## 工程实践：为什么倾向显式编排

题库点出一个重要取向：Deep Research 更倾向用 Workflow 或 LangGraph 这类显式编排，而不是完全交给一个黑盒对话 Agent。原因有几层：

**过程要可控。** 研究是多步长流程，显式编排能把每一步画出来、可监控、可干预；黑盒 Agent 的路径不可预测，跑到一半偏了不好发现。

**要能回放。** 题库强调"过程可回放性"——事后要能看清当时查了什么、怎么融合的、为什么判断证据够了。显式编排天然留痕，黑盒对话难还原。

**迭代逻辑要明确。** "证据不足就继续补检"是个循环，显式编排能清楚定义循环条件和退出条件，避免无限检索或过早结束。

```python
# 伪代码：研究型工作流的迭代骨架
def deep_research(question):
    sub_questions = planner.decompose(question)          # 查询规划
    evidence = []
    for round in range(max_rounds):                       # 迭代控制，带轮数上限
        found = retriever.multi_source_search(sub_questions)  # 多源检索
        fused = fusion.dedupe_and_align(found, evidence)      # 去重、冲突、对齐
        evidence = fusion.weight_by_credibility(fused)        # 可信度加权
        gaps = controller.find_gaps(question, evidence)       # 找证据缺口
        if not gaps:                                           # 证据充分，退出
            break
        sub_questions = planner.refine(sub_questions, gaps)    # 针对缺口补检
    return reporter.generate(question, evidence)              # 结构化报告 + 引用

# planner / retriever / fusion / controller / reporter 为业务侧实现
```

要点：检索—融合—找缺口—补检的循环，带轮数上限；融合层做去重对齐和加权。变量都是业务侧实现。这段代码把"多轮研究流程"具体化了。

## 追问逐条作答

### 追问一：Deep Research 和普通 RAG 最大的区别是什么？

从"单轮问答"升级成"多轮研究流程"。普通 RAG 是查一次、拼上下文、生成答案；Deep Research 是拆问题、多轮检索、融合证据、发现缺口继续补检，最后出结构化报告。所以设计重点也变了——不只是召回率，还有规划质量、引用质量、可信度和过程可回放性。前面讲 RAG 上线坑时说过它是索引+检索生成链路，Deep Research 是在那条链路上加了规划和迭代循环。

### 追问二：为什么信息融合层这么重要？

因为多源检索拿回来的材料是未经加工的，大量重复、相互矛盾、可信度参差。不做融合，报告就会出现同一数据说法不一、引用了低可信来源、关键结论证据不足等问题。融合层做去重、冲突检测、证据对齐、可信度加权，把杂乱材料变成可依赖的证据。这一层常被忽略，但它决定了最终报告的可靠度。

### 追问三：迭代控制器如何判断什么时候停？

看证据是否充分。控制器检查当前证据能不能覆盖问题的各个子问题、关键结论有没有足够支撑；有缺口就继续补检，没缺口就结束。同时要有硬上限——最大轮数、时间预算，防止无限检索。经验值：停止条件要明确且可观测，别让系统"感觉差不多了"就停，也别让它无限查下去。

### 追问四（自补）：为什么要输出时间戳？

因为研究结论有时效性。市场格局、技术动态、政策环境都会变，报告里的结论是基于某个时间点的证据得出的。带时间戳让读者知道这份报告反映的是什么时候的情况，也便于后续更新——过段时间重新研究时，能对比哪些结论变了。前面讲幻觉时说过"时间点偏了"是常见错误，时间戳是对这个的防范。

### 追问五（自补）：为什么倾向显式编排而不是黑盒 Agent？

因为研究流程需要可控、可回放、可干预。显式编排把流程画出来，每步能监控，偏了能发现、能改；过程留痕，事后能回放"当时查了什么、怎么判断的"；迭代循环的条件和上限能明确定义。黑盒对话 Agent 路径不可预测，长研究任务里容易偏、难还原、难设退出条件。前面讲工作流 vs Agent 时说过"路径可预测用工作流",Deep Research 的流程主干是清晰的，所以适合显式编排。不过这不等于每个环节都要写死——在"怎么拆解子问题""发现缺口查什么"这类需要灵活判断的节点，仍可以让模型参与决策，只是把它的决策放进明确的节点里，而不是放任整个流程自由发挥。

## 60 秒面试回答模板

> Deep Research 不是查一次再总结，是围绕复杂问题持续研究形成结构化结论。五个模块：查询规划器拆子问题；检索执行器做多源检索；信息融合层去重、冲突检测、证据对齐、可信度加权；迭代控制器在证据不足时继续补检；报告生成器输出摘要、正文、引用和时间戳。理解成工作流就是前面拆解和检索编排、中间多轮证据收集处理、后面结构化报告。它和普通 RAG 的区别是单轮问答变多轮研究流程，重点不只是召回率，还有规划质量、引用质量、可信度和过程可回放。落地我更倾向 Workflow 或 LangGraph 显式编排，因为流程可控、可回放、迭代条件和上限能明确定义，不适合完全交给黑盒 Agent。

## 加分项

- 用"持续研究形成结构化结论"定性，不和单轮检索混淆。
- 五模块 + 三段式工作流，系统拆清楚。
- 点出信息融合层这个常被忽略的关键层。
- 给出显式编排 vs 黑盒 Agent 的取向判断，落到可控可回放。

## 常见误区

- **当成增强版搜索总结**：忽略多轮迭代、证据融合和结构化输出。
- **忽略信息融合**：多源材料不去重不对齐，报告说法矛盾、可信度失控。
- **全交给黑盒 Agent**：长研究流程需要可控、可回放、退出条件明确。
