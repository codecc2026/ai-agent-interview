# 搭一个能落地的 Agent：哪些组件真必要，哪些是过度设计？

## 面试官为什么爱问这题

这题看着在问组件清单，其实在筛有没有把 Agent 真正送上线过。会背「大模型 + 工具 + 记忆 + 规划」的人很多，可一追问「记忆模块修掉了哪个具体失败」「上了规划为什么反而更慢」，多数人答不上来。面试官要听的是取舍：哪些缺了跑不起来，哪些 demo 里好看、进生产就添乱。

之前讲过 Tool、Function Calling、Agent 三层怎么分，也聊过 ReAct 循环、工具幻觉怎么兜、单个工具怎么设计，那些是零件视角。这里换到整机视角：一个需求过来，装什么、先不装什么、凭什么定，出事能不能定位到哪一层。

## 一句话先给结论

**能落地的 Agent，骨架只有四件：模型、工具集、运行循环、当前状态；记忆、规划、反思、多智能体都是看到失败信号才加的扩展件。决定它能不能上生产的，不是能力堆得多全，而是目标职责、工具边界、状态设计、停止条件、治理能力这五件事有没有收口。判断某个组件该不该加，只问一句「拿掉它，哪个已知 badcase 会恶化」就够了。**

## 核心原理：四件套是骨架，其余是扩展

### 四个组件，各管一件别人替不了的事

模型负责理解目标、判断当前局面、决定下一步，它是唯一的决策者，不是执行者。工具集把决策变成对外部世界的读写，搜索、数据库、文件系统、业务 API 都算，也顺带定义了能力边界：模型只能在这些口子上产生副作用。运行循环让「想一步、做一步、看结果、再决定」能够重复，没有它，系统一次调用就答完，谈不上根据工具返回调整下一步。当前状态把消息、工具返回、中间结果、线程上下文攒起来，是循环记住「上一步看到了什么」的唯一载体。

这四件是最小集，少任何一件闭环就断：去掉模型没人决策，去掉工具只能空想，去掉循环退化成单轮问答，去掉状态每步都从零开始。它们还能互相推导：既然要运行期决策就得有循环，有循环就得有状态把观察带进下一轮。

### 为什么这么设计：把能力和控制拆成两件事

四件套解决「能不能跑起来」，五个控制项解决「跑起来可不可控」。这两件事最容易被混着做：需求一到，先接向量库当记忆、写个 planner、加一轮自我反思、再拆三个 agent 分工，四件套还没跑稳，就先引进了四个新失败源。经验上每多一个自主决策环节，就多一次模型调用、多一段要回灌的状态、多一处排查盲区，端到端延迟大致按调用轮数往上叠，收益却要看任务类型，不是加了就线性变好。

先跑稳骨架再按信号加扩展，出问题时很直接：控制项齐了，能一键关掉某个扩展件做二分，很快知道是主干还是新加那层在捣乱。一上来全堆满，trace 里十几步混着规划、反思、agent 间传话，答错了分不清是哪一层。

### 边界：什么算必要，什么算过度设计

给判据，别给「看情况」。必要组件的标准是拿掉它，系统对某个已知 badcase 直接失败或明显变差；过度设计是加上它却指不出对应的失败信号，或它要解决的问题当前根本没发生，或它引入的新失败（延迟、不确定行为、调试盲区）比修掉的还多。中间还有一档「现在不需要、但留好接口」，等信号真出现再加，比赌一把全装上稳妥。

判断依据是 badcase，不是组件听起来高不高级。有个很实在的自检：动手加之前，把「哪个已知失败会因为少了它变差、加了拿什么指标验证」写成一句话，写不出来，基本就是过度设计。

### 概念边界别混着说

Agent 不等于 Workflow。Workflow 的分支在开发期写死，Agent 的下一步在运行期由模型根据观察决定，前面聊 ReAct 时讲过这个夹角。所以「编排一串固定步骤」不算 Agent，哪怕每步都调了工具；接了 Function Calling 也不等于有了 Agent，前者是一次结构化调用意图，后者是带循环和状态的运行模式。

两个容易顺嘴说错的：把检索接进来只是给工具集添了个能力，不等于系统有了「记忆」，跨会话状态的写入、淘汰、一致性是另一套问题；RAG 也不等于长上下文，一个是在库里找片段喂进去，一个是把内容直接摊在窗口里。

## 横向对比：三种架构取向，差在控制不在能力

| 维度 | 最小骨架（够用就好） | 全组件堆满 | 按信号增量加 |
| --- | --- | --- | --- |
| 起步组件 | 四件套 | 四件套 + 记忆 + 规划 + 反思 + 多智能体 | 四件套，扩展件只留接口 |
| 首版延迟 | 基准 | 明显更高，一次额外规划或自评通常多引入一轮以上模型调用（经验值） | 接近基准 |
| 出问题定位 | Trace 短，容易复现 | 链路长，分不清是哪一层 | 可逐个关掉扩展件做二分 |
| 适用场景 | 目标单一、工具少、链路短 | 研究原型、Demo | 生产迭代 |
| 主要风险 | 复杂任务能力不够 | 过度设计、行为不可控 | 需要 badcase 积累和纪律 |

三种取向差在控制粒度，不在能力高低。最小骨架任务一复杂就露怯；全组件堆满在 Demo 里最出彩，上了量延迟和不可复现一起找上门；按信号增量加更适合生产，代价是得有人维护那批 badcase。

### 扩展能力逐项判据

| 扩展件 | 它修的具体失败 | 该加的信号 | 没有信号就加，会变成什么样 |
| --- | --- | --- | --- |
| 长期记忆 | 用户偏好、跨会话事实记不住 | 反复出现「同一信息要用户重说」的 badcase | 接上向量库就宣称有记忆，其实只做了检索 |
| 显式规划 | 多步任务漏步、子目标顺序错 | 循环里反复漏掉某个必要子目标 | 单工具查询也先生成一份计划，白多一次调用 |
| 反思自评 | 结果明显错但系统不自查 | 存在可判定的质量信号却没人用 | 让模型给自己打分，分数不稳还费 token |
| 多智能体 | 角色、权限、上下文需要隔离 | 单上下文串味、权限收不住 | 三个 agent 互相转述，trace 里全是传话 |

每个扩展件都对应一种具体的失败形态，反过来用也成立：先拿线上失败例去对，对不上任何一行的，就别急着装。

## 工程实践：把五个控制项写进代码

### 一个最小可运行骨架长什么样

下面是伪代码，函数名是工程封装的占位，不代表任何特定框架接口。它只保留四件套，把五个控制项全落进去：工具白名单对应工具边界，结构化 state 对应状态设计，四类出口对应停止条件，每步 trace 对应治理能力。

```python
# 伪代码：最小 Agent 主循环
MAX_STEPS = 12          # 经验值：单目标任务 8～15 步，超了强制收口
TIMEOUT_MS = 20000      # 经验值：按最慢工具的 P95 留余量

def run(goal, tools, trace):   # tools：调用方注册的工具实现，键集合就是白名单
    state = {"messages": [{"role": "user", "content": goal}],
             "tool_results": [], "scratch": {}}   # 当前状态显式建，不塞全局
    seen = set()
    for step in range(MAX_STEPS):
        action = model.decide(state, tools=tools)  # 模型只出意图，不执行
        trace.log(step, "decide", action)          # 治理：每步可回放
        if action.done:
            return action.answer                    # 停止条件：正常完成
        if action.name not in tools:
            return escalate("tool_not_allowed", state, trace)
        key = (action.name, freeze(action.args))
        if key in seen:
            return escalate("repeated_action", state, trace)  # 停止条件：重复动作
        seen.add(key)
        obs = call_with_timeout(tools[action.name], action.args, TIMEOUT_MS)
        state["tool_results"].append(obs)          # 观察回灌，供下一轮决策
        state["messages"].append({"role": "tool", "content": obs})
    return escalate("step_budget_exceeded", state, trace)     # 停止条件：兜底收口
```

`seen` 那道重复检测值得单说。两个工具互相调用时步数往往没到上限，系统已经在空转，只靠 `MAX_STEPS` 兜不住，得看「同工具同参数是否出现第二次」。`escalate` 每次把 `state` 和 `trace` 一起交出去，转人工不是把异常吞掉，接手的人得看得到之前发生了什么。

### 状态和停止条件的配置长什么样

把散在代码里的约束收成一份显式配置，review 和改参数时不用翻主循环。字段名是自定义配置，非某个库的固定 schema。

```json
{
  "goal": "查询订单并答复退款进度",
  "state_slots": ["messages", "tool_results", "scratch", "thread_id"],
  "stop": {
    "max_steps": 12,
    "timeout_ms": 20000,
    "on_repeated_action": "escalate",
    "on_low_confidence": "ask_human",
    "on_budget_exceeded": "handoff"
  },
  "tools_allowlist": ["query_order", "search"],
  "trace_fields": ["step", "action", "tool", "latency_ms", "error_code"]
}
```

注意 `max_steps`、`timeout_ms` 与主循环里的 `MAX_STEPS`、`TIMEOUT_MS` 必须一致，一处改了另一处忘改，线上就会出现「配置说 12 步、代码跑到 15 步」这种查半天的问题。经验值给的是区间，具体按自己最慢的工具和任务长度定，别照抄。

### 五个控制项，最容易漏哪一个

| 控制项 | 漏了会出的具体事故 | 最小落地做法 |
| --- | --- | --- |
| 目标和职责 | 一个 Agent 又查订单又改地址又发券，工具选错率跟着涨 | 一个实例只背一个目标，超出的拆给别的实例 |
| 工具边界 | 模型越权调到写接口，或工具太多在相近名字间选错 | 白名单 + 只读优先，单场景控制在 5～10 个（经验值，与之前讲工具收敛时的口径一致） |
| 状态设计 | 中间结果全塞进 messages，多跑几轮上下文膨胀、最早的工具返回被挤掉 | state 分槽，每步只把决策真正需要的回灌给模型 |
| 停止条件 | 两个工具来回调用空转到超时；或模型说「完成」其实没做完 | 完成 / 超时 / 重复 / 转人工四道，缺一不可 |
| 治理能力 | 线上答错但复现不了，不知道哪一步的工具返回出了错 | 每步记 step、action、tool、latency_ms、error_code，可回放可审计；超时、重试、人工接管都补齐，重试前先确认工具幂等 |

两个常见的坑都在这里。一个是空转好几步还不收敛，多半不是模型笨，是没设重复检测，trace 里同一步的 action 反复出现；另一个是把工具返回和中间结论一股脑塞进 messages，后面几轮模型看不到最早那条关键观察，就开始编。换个更强的模型往往照样复现，因为根子在状态、边界、治理。

## 追问逐条作答

### 追问一：在构建一个复杂 Agent 时，你认为最主要的挑战是什么？

不是选哪个模型或框架，是不确定性从哪冒出来、怎么收口。四件套里模型每步都在决策，决策一多，失败面就从「单次答错」变成「链路跑偏」：选错工具、参数填错、观察没回灌、循环收不住，任何一种都会让后面几步建立在错的基础上。主要挑战是让系统在模型能力有限的前提下依然可控，落点还是那五个控制项。

一个好用的判据：能说清「上次线上事故出在哪一步、trace 里是哪一行」的团队，架构基本收口了；只能说「模型有时候不太行」的，多半是骨架跑起来了、控制项没补。

### 追问二：为什么很多 Agent 不是能力不够，而是状态、边界和治理没设计好？

因为能力问题好识别，也容易被「换个更大的模型」暂时盖过去，而这三类在 Demo 里几乎不暴露，一到生产才成批出现。状态没设计，中间结果靠 messages 硬塞，多轮之后丢上下文，模型开始编；边界没设计，工具白名单没做，模型能摸到本不该碰的写接口；治理没设计，没有 trace，答错了复现不了，只能靠猜。

共同点是它们都不体现在单轮回答质量上，拿一批标准问答去测分数可能还挺好，线上却不断出事。补法没有捷径，就是五个控制项逐条落地：结构化状态分槽、工具白名单、四道停止条件、每步可回放的 trace。

### 追问三：记忆、规划、反思、多智能体，到底什么时候才算该加？

用 badcase 反推，不用组件清单。长期记忆对应「同一信息反复要用户重说」，显式规划对应「循环里总漏某个必要子目标」，反思对应「有可判定的质量信号却没人用」，多智能体对应「上下文串味、权限收不住」。对得上哪一行的失败才考虑装哪件，一行都对不上就是装饰。

加之前先写清两件事：哪个已知失败会因为少了它变差，加了拿什么指标验证。这里能复用之前讲效果排查时的分层归因思路，扩展件也要能 A/B：同一批 case 打开和关掉各跑一遍，指标没动就撤。这样「要不要上记忆」就从偏好之争变成一次能复现的实验。

### 追问四：状态应该怎么存，全塞进上下文窗口行不行？

短期对话历史放 messages 没问题，工具返回、中间结论、线程元数据不该全往里塞。三个原因：token 随轮数一路涨，最早的关键观察会被截断，结构化和非结构化混在一起后没法做淘汰和权限。做法是把 state 分槽，messages 只留对话主线，tool_results 留原始返回，scratch 放中间结论，每步只把决策真正需要的部分回灌给模型。

要分清：上下文窗口是给模型的视图，不是系统的存储。混成一个东西，迟早会在「要不要保留第 2 步那条工具返回」上纠结。检索进来的内容属于观察，是这一轮喂给模型的材料，不等于状态里的长期记忆，跨会话要留的事实得单独设计写入和淘汰。

### 追问五：停止条件怎么设，才既不死循环又不该停时乱停？

至少四道，还要把「正常完成」和「兜底收口」分开：步数上限（经验值 8～15 步，超了转人工）、单步和整体超时、重复动作检测、低置信度转人工。最常漏的是第三道，两个工具互相调用时步数还没到上限，系统已在原地打转，光靠预算拦不住。

另一个容易做反的是把所有非正常出口都当异常吞掉。转人工是设计好的一等出口，触发时要把当轮 state 和 trace 一起递出去，人才能接着办；低置信度时向用户澄清一句，往往比硬凑一个答案再被投诉更划算，这也是停止条件的一部分。

### 追问六：怎么证明这个 Agent 能落地，而不只是 Demo 跑通？

拿三样东西说话：一批含失败例的固定 case、每步可回放的 trace、扩展件的开关和 A/B 结果。具体些，能回答「这批失败例里分别有多少是工具选错、观察没回灌、循环收不住、停止条件误判」，能一键关掉某个扩展件看指标变化，能在答错时把当轮 state 完整复现。

Demo 只需要 happy path 走通，落地要能把失败归档、定位、回归，下次不重犯。所以治理能力不该当成上线后再补的锦上添花，它是能迭代的前提：没有 trace 和固定 case，任何优化都只能凭感觉。

## 60 秒面试回答模板

> 我理解能落地的 Agent，骨架就四件：模型做决策、工具集定能力边界、运行循环让想一步做一步看结果能重复、当前状态把消息和工具返回攒起来。记忆、规划、反思、多智能体不是标配，是看到具体 badcase 才加的扩展件，判断标准是拿掉它哪个已知失败会恶化。真正决定能不能上生产的是五件事：目标单一、工具白名单、状态分槽、停止条件给足完成超时重复和转人工四道、每步留 trace 能回放。很多线上问题不是模型不行，是状态被塞爆、边界没画、出错复现不了。我会先把四件套跑稳，再按失败信号一件件加扩展，每个都能开关、能 A/B。

## 加分项

- **用 badcase 当组件取舍判据**：把「要不要上记忆」从偏好之争换成信号到了没，一句话就能让讨论落地。
- **分清视图和存储**：上下文窗口是给模型看的一帧，结构化 state 才是账本；顺带说清检索结果是观察、不等于长期记忆。
- **把转人工设计成一等出口**：触发时连 state 和 trace 一起交出去，而不是当异常吞掉，接手的人才接得上。
- **扩展件一律带开关和 A/B**：能一键关掉做二分定位，把治理当迭代前提，而不是上线后补的装饰。

## 常见误区

- **把接了 Function Calling、上了编排框架当成有了 Agent**：没有运行期的决策和状态，那还是单轮调用或 Workflow。
- **骨架没跑稳就堆满扩展件**：四件套还在丢观察，先上记忆、规划、反思、多智能体，等于一次引进四个新失败源，出问题定位不了。
- **靠长上下文硬扛状态**：工具返回和中间结论全塞 messages，多轮后关键观察被挤出窗口，模型开始编，还以为是能力问题。
