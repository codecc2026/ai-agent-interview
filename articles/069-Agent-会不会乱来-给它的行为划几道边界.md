# Agent 会不会乱来？给它的行为划几道边界

<!-- growth-hook:v1 -->
“怎么防止 Agent 乱来？”只答“做好对齐”太单薄了。模型对齐只是第一层，真正兜底的是应用层的权限、流程、审计和熔断——越有执行能力的 Agent，越需要这几道闸门。

## 面试官为什么爱问这题

这题高频且偏难，考的是你有没有分清"模型对齐"和"应用治理"这两套机制。很多人觉得模型做过 SFT、RLHF 就够了，Agent 不会乱来；面试官想听的是：模型层的安全只是基础边界，真到业务系统里，还得靠应用层一道道防线把风险收住——工具不给裸权限、危险动作要审批、无限循环要熔断。更关键的是那句总结：模型对齐解决"基础行为别太离谱"，应用治理解决"在你的业务系统里别出事"。前面聊过 MCP 的权限沙箱、也聊过幻觉防线，这一篇把视角拉到"Agent 行为边界"的完整体系。

## 一句话先给结论

**不能只寄希望于模型本身够聪明或已对齐。模型层的 SFT、RLHF / RLAIF 只提供基础安全边界，真正落地到应用还必须补应用层治理，通常分四层：模型与提示层用 System Message 明确角色、边界、安全规则和拒答策略；工具与权限层不给裸权限，所有 Tool 做 schema 约束、鉴权、参数校验和最小权限暴露；执行与流程层设最大步数、超时、人工审批、转人工、失败兜底；观测与审计层保留调用日志、trace、输入输出、关键决策点和人工复盘链路。再加预算控制和熔断机制，把"模型可能一直试下去"的风险收住。**

## 核心原理：四层治理 + 预算熔断

### 第一层：模型与提示层

用 System Message 明确角色、边界、安全规则和拒答策略。告诉模型它是谁、能做什么、不能做什么、遇到什么情况要拒答。这是最软的一层——靠提示词约束，有用但不牢靠，不能单独依赖。前面讲提示词设计时说过边界要写清，这里是它在安全场景的应用。

### 第二层：工具与权限层

不给模型裸权限。所有 Tool 都要做 schema 约束、鉴权、参数校验和最小权限暴露。模型只能调用被允许的工具、只能传符合 schema 的参数、只能访问最小够用的权限。前面讲 MCP 接入时说过权限检查要和环境沙箱配合，这里是同一原则的落地——不给 Agent 一把通吃系统的钥匙。

### 第三层：执行与流程层

设置最大步数、超时、人工审批、转人工、失败兜底。目的是避免无限循环和危险动作直接落地：模型可能反复试同一个失败的操作，最大步数和超时能让它停下；删数据、发消息、付款这类动作不能直接执行，要人工审批或转人工。前面讲工作流设计时说过人工点加在不可逆动作前，这里是它在 Agent 安全上的应用。

### 第四层：观测与审计层

保留调用日志、trace、输入输出、关键决策点和人工复盘链路。前面讲可观测性时展开过这些，落到安全上，它的价值是"出事能查、能复盘"——知道 Agent 做了什么、为什么那么做、当时看到什么状态。

| 层 | 核心手段 | 防什么 |
| --- | --- | --- |
| 模型与提示 | System Message 明确角色、边界、拒答 | 基础行为跑偏 |
| 工具与权限 | schema、鉴权、参数校验、最小权限 | 越权、乱调工具 |
| 执行与流程 | 步数上限、超时、审批、兜底 | 无限循环、危险动作 |
| 观测与审计 | 日志、trace、决策点、复盘 | 出事查不清 |

这四层从软到硬，性质不同：

| 约束类型 | 对应层 | 特点 |
| --- | --- | --- |
| 软约束 | 模型与提示 | 靠模型自觉遵守，可能被绕过 |
| 硬约束 | 工具与权限、执行与流程 | 强制执行，模型想乱来也被挡住 |
| 事后兜底 | 观测与审计 | 不阻止出事，但能查清和复盘 |

只做软约束等于只靠模型自觉；把防线押在任何单层上都不稳，软硬叠加才有体系。

### 生产视角：预算控制和熔断

题库特别补了一层生产视角：

**预算控制。** 最大工具调用次数、时间预算、token 预算、费用预算。给 Agent 的活动设上限——它能试，但不能无限试下去。这不只是省钱，更是把失控风险收住。

**熔断机制。** 连续失败停止、异常率告警、重复无进展退出。当检测到 Agent 在原地打转，比如反复失败、重复同一个无进展的动作，就强制停止。这是防止"模型一直试下去"的最后一道闸。

这些机制的价值不只是省钱，更在于把"模型可能一直试下去"的风险收住。一个没有预算和熔断的 Agent，可能因为一个死循环把额度烧光、或在错误路上越走越远。

### 两套机制，不是二选一

题库的总结拔高了一层：模型对齐解决"基础行为别太离谱"，应用治理解决"在你的业务系统里别出事"。真正稳的 Agent 是"模型能力 + 权限边界 + 流程控制 + 人机协同"一起做，不是只靠某一层。前面讲模型对齐和注入防御时说过各自的边界，这里把它们放回一个整体——模型层和各应用治理层是互补关系，不是谁替代谁。

## 工程实践：哪些动作必须人工审批

把"执行与流程层"落到具体判断，关键是分清哪些动作能让 Agent 直接做、哪些必须人来点头。

判断标准是**不可逆性和代价**。可逆的、代价小的动作，比如查数据、生成草稿、读文档，可以让 Agent 直接做，做错了能改。不可逆的、代价大的动作，比如删除数据、对外发送消息、付款转账、修改权限，必须人工审批。经验值：问自己"这个动作做了能撤销吗"，不能撤销的就要审批。

```python
# 伪代码：动作分级，高危动作触发人工审批
HIGH_RISK = {"delete_data", "send_message", "transfer", "change_permission"}

def execute(action, params):
    if action in HIGH_RISK:                        # 高危动作
        approved = human_review(action, params)    # 业务侧：人工审批
        if not approved:
            return rejected("未获人工批准")
    with budget_guard(action):                     # 业务侧：预算与熔断检查
        return tool_registry[action](**params)

# human_review / budget_guard / tool_registry 为业务侧实现
```

要点：高危动作先过人工审批，所有动作都在预算和熔断的约束下执行。`HIGH_RISK` 清单按业务实际定。这段代码把"流程控制"和"预算熔断"两层的思路落到了实现。

## 追问逐条作答

### 追问一：模型已经对齐了，为什么应用层还要做这么多安全治理？

因为两层解决的问题不同。模型层的 SFT、RLHF 解决的是"基础行为别太离谱"——让它不输出有害内容、不明显跑偏；但它不知道你的业务系统里哪些工具能调、哪些动作不可逆、什么情况要转人工。这些是业务特定的约束，模型对齐覆盖不到。所以应用层必须自己设权限边界、流程控制和熔断。把安全全押在模型对齐上，等于把一个通用模型当成了懂你业务的守卫。

### 追问二：哪些动作你会要求人工审批，而不是让 Agent 直接执行？

看不可逆性和代价。删除数据、对外发送消息、付款转账、修改权限这类不可逆或高代价的动作，必须人工审批；查数据、生成草稿、读文档这类可逆、低代价的动作，可以直接执行。经验值：一条链路里真正需要人工卡点的通常就一两个，多了说明把可逆动作也当成了风险点，会把人淹没在审批里、反而降低警惕。

### 追问三：预算和熔断为什么不只是省钱？

因为它们收住的是"无限试下去"的风险。一个 Agent 如果卡在某个失败动作上反复重试，没有步数上限和时间预算，它会一直耗下去——烧额度是显性的损失，更麻烦的是它在错误路上越走越远、可能产生更多副作用。熔断检测"连续失败""重复无进展"并强制停止，是在失控前刹车。所以预算熔断是安全机制，不只是成本机制。

### 追问四（自补）：System Message 的安全约束可靠吗？

有用但不牢靠，不能单独依赖。提示词约束属于软约束，模型可能忽略、可能被注入攻击绕过、也可能在长对话里"忘掉"。所以它只能作为第一层基础，后面必须有工具权限、流程控制这些硬约束兜底。把安全全写在 System Message 里，等于只装了个看起来像门的东西，一推就开。

### 追问五（自补）：最小权限怎么落到工具上？

按"这个 Agent 完成当前任务最少需要什么"来给。一个只查订单的 Agent，不该拿到删除订单的权限；一个只读的知识库问答，不该有写库权限。落到工具上就是：按角色暴露工具子集、工具参数做 schema 约束、访问范围按用户和任务隔离。前面讲 MCP 接入时说过权限检查加沙箱配合，这里是把"最小"二字落实到每个工具的暴露范围。

## 60 秒面试回答模板

> 我不会只指望模型够聪明。模型层的 SFT、RLHF 只给基础安全边界，应用层必须补四层治理：提示层用 System Message 明确角色、边界和拒答；工具权限层不给裸权限，做 schema、鉴权、参数校验和最小权限暴露；执行流程层设最大步数、超时、人工审批、转人工和失败兜底；观测审计层保留日志、trace、决策点和复盘链路。生产上再加预算控制，包括调用次数、时间、token、费用上限；以及熔断，包括连续失败停止、异常率告警、重复无进展退出。高危不可逆动作必须人工审批，判断标准是做错了能不能撤销。模型对齐解决基础行为别离谱，应用治理解决在你的系统里别出事，两者互补。

## 加分项

- 分清模型对齐和应用治理两套机制，用"基础行为 vs 业务系统"概括。
- 四层治理 + 预算熔断，体系完整。
- 给出"不可逆性"作为人工审批的判断标准，可操作。
- 点出预算熔断的安全价值，不只是省钱。

## 常见误区

- **只靠模型对齐**：模型对齐只管基础行为，不懂你的业务边界，哪些动作不可逆、哪些工具不能调它并不知道，所以应用层治理绝不能省。
- **把安全全写在 System Message**：软约束会被绕过，需要硬约束兜底。
- **忽略预算熔断**：没有上限，Agent 可能无限试下去、在错误路上越走越远。
