# 如何设计 Python 代码解释器？

<!-- growth-hook:v1 -->
代码解释器这题，只答“生成代码、执行、拿结果”是入门分。真正被追问的是：怎么在给模型执行能力的同时，不把宿主环境暴露出去。沙箱、白名单、产物回传，一个都不能少。

## 面试官为什么爱问这题

这题偏难，考的是执行型智能体和安全沙箱设计。很多人觉得"跑 Python 有什么难的"，面试官想听的恰恰是它真正的难点：不是"会不会运行 Python"，而是"如何既让它有执行能力，又不把宿主环境暴露出去"。代码解释器让模型生成并执行代码，这是能力，也是巨大的安全风险，一段恶意代码能删库、读凭据、访问网络。前面聊过多用户沙箱隔离、Code Agent 设计，这一篇聚焦 Python 代码解释器这个具体系统，看它五层怎么搭、安全边界怎么划。

## 一句话先给结论

**Python 代码解释器本质上是"模型生成代码 + 安全执行 + 回传结果"的闭环系统。核心设计五层：代码生成层把用户需求转成 Python 代码；沙箱执行层做隔离环境、白名单模块、超时限制、资源限制；结果回传层收集 stdout、stderr、文件产物、图表和返回值；状态管理层支持多轮执行时保留变量或工作目录；安全治理层禁止危险系统调用、网络访问和越权读写。真正难点不在"会不会运行 Python"，而在"如何既让它有执行能力，又不把宿主环境暴露出去"。**

## 核心原理：五层设计

### 代码生成层

模型把用户需求转成 Python 代码。这一层负责理解意图、写出可执行的代码。代码质量影响执行成功率——生成的代码有语法错、逻辑错，后面执行层再稳也没用。前面讲 Code Agent 时说过代码生成，这里它是解释器闭环的起点。

### 沙箱执行层

隔离环境、白名单模块、超时限制、资源限制。这是整个系统的核心——代码要在受控环境里跑：隔离环境让它碰不到宿主；白名单模块让它只能用允许的标准库；超时和资源限制防止死循环、内存爆炸拖垮系统。前面讲多用户沙箱时说过容器隔离、只读根目录、非 root 运行，这里是它们在代码执行场景的具体应用。

### 结果回传层

收集 stdout、stderr、文件产物、图表和返回值。代码跑完要把结果带回来——打印输出、错误信息、生成的文件、画的图、函数返回值。结果收集不全，模型就不知道执行成功没、看不到图表数据，没法继续推理。这一层决定闭环能不能"回得上"。

### 状态管理层

支持多轮执行时保留变量或工作目录。代码解释器往往不是执行一次就结束——用户问"再算一下"，希望接着上次的环境继续，变量还在、生成的文件还在。状态管理层要维护这个执行上下文，让多轮执行连贯。

### 安全治理层

禁止危险系统调用、网络访问和越权读写。这是贯穿全程的约束——哪些系统调用不能碰、`os.system` 这类要拦；网络默认不通，防止数据外传或拉取恶意内容；文件读写限定在授权范围。前面讲行为边界时说过最小权限和纵深防御，这里是它们在代码执行场景的落地。

| 层 | 做什么 | 缺了会怎样 |
| --- | --- | --- |
| 代码生成 | 需求转 Python 代码 | 代码本身跑不通 |
| 沙箱执行 | 隔离、白名单、超时、资源限制 | 宿主被暴露、资源被拖垮 |
| 结果回传 | stdout/stderr/文件/图表/返回值 | 闭环回不上，模型看不到结果 |
| 状态管理 | 多轮保留变量和工作目录 | 每轮都从头来，不连贯 |
| 安全治理 | 禁危险调用、网络、越权读写 | 越权删库、读敏感文件 |

五层按作用可以分成两组：

| 分组 | 包含层 | 作用 |
| --- | --- | --- |
| 能干活 | 代码生成、沙箱执行、结果回传、状态管理 | 让代码跑起来、结果带回来、多轮连起来 |
| 别闯祸 | 安全治理 | 贯穿全程，防越权、防外泄 |

把安全单独成层而不是揉进沙箱，是因为它贯穿全程：生成时要考虑代码危不危险，回传时要防止产物带出敏感信息。

### 真正的难点：能力与安全

题库点得很准：难点不在"会不会运行 Python"，而在"如何既让它有执行能力，又不把宿主环境暴露出去"。这是一对矛盾——沙箱限制太松，安全风险大；限制太紧，很多正常任务做不了（比如无法读数据文件、无法用某些库）。设计的艺术在于找到平衡：默认最小权限，按任务需要逐项开放，且每项开放都有审计。

## 工程实践：防越权的纵深防线

落到追问关心的"怎么防止越权删库、读主机敏感文件"，靠多层：

**权限层。** 危险系统调用直接禁——`os.system`、`subprocess` 调用 shell 这类要拦住或白名单化。网络默认关闭，需要时按目标地址白名单开放。

**隔离层。** 容器隔离、非 root 运行、只读根目录、只挂必要的工作目录。宿主机敏感文件根本不挂进容器——看不到就读不到。

**资源层。** 超时、内存上限、CPU 上限、磁盘配额。防止死循环、内存炸弹、磁盘写满。

**审计层。** 记录每段执行的代码、产生的调用、读写的文件。出事能追溯，异常模式能发现。

```python
# 伪代码：受限执行环境的骨架
def run_code(code, state):
    if not scanner.is_safe(code):                 # 静态检查：危险调用
        return error("代码含被禁止的操作")
    with sandbox(                                  # 业务侧：隔离执行环境
        timeout=SEC_LIMIT,                         # 超时
        memory=MEM_LIMIT,                          # 内存上限
        network=False,                             # 默认断网
        allowed_modules=WHITELIST,                 # 模块白名单
        mounted_dirs=[state.workspace],            # 只挂工作目录
    ) as env:
        out, err = env.exec(code, state.vars)      # 执行，带上轮变量
        state.vars = env.snapshot_vars()           # 保存变量供下轮
    audit.log(code, out, err)                      # 审计留痕
    return collect(out, err, env.artifacts())      # 收集 stdout/stderr/产物

# scanner / sandbox / audit / collect 为业务侧实现
```

要点：静态检查 + 沙箱隔离 + 资源限制 + 审计，执行后保存变量支持多轮。`WHITELIST` 和各限制是业务侧配置。

## 追问逐条作答

### 追问一：如果 Agent 需要执行系统命令或访问文件，你怎么防止它越权删除数据库、读取主机敏感文件？

多层防线叠加。权限层：危险系统调用直接禁或白名单化，网络默认关；隔离层：容器隔离、非 root、只读根目录，宿主机敏感目录根本不挂进容器，看不到就读不到；资源层：超时和资源上限；审计层：记录每次执行的代码和文件访问，异常能发现能追溯。关键思路是"不给机会"，与其靠检测拦截，不如让危险资源从一开始就不在执行环境里。前面讲多用户沙箱时说过"凭据不进容器"，这里是同一原则。

### 追问二：除了白名单，宿主隔离上还会做哪些限制？

容器隔离、非 root 运行、只读根目录、临时工作目录、只挂必要的目录、CPU / 内存 / 磁盘配额、网络隔离。白名单是应用层的"允许什么"，宿主隔离是系统层的"能碰到什么"——两层互补。前面讲多用户场景的沙箱隔离时展开过 seccomp、AppArmor、只读根目录这些，代码解释器场景同样适用：即使白名单被绕过，宿主隔离还能兜住。

### 追问三：为什么要支持多轮执行时保留状态？

因为真实任务是连续的一一用户可能先让代码读数据、再让分析、再让画图，每一步都依赖前面的变量和文件。每轮都从头开始，用户就得每次重复提供数据，体验很差、也做不了复杂任务。状态管理层保留变量和工作目录，让多轮执行像在同一个会话里连续工作。前面讲会话记忆时说过"不断档"，这里是代码执行环境的"不断档"。

### 追问四（自补）：结果回传层为什么要收集图表和文件产物？

因为代码解释器的很多价值在"产出物"上，用户让画个图、生成个文件，光返回一句"执行成功"没用，得把图表和文件实际带回来给用户看。如果只收 stdout，用户看不到生成的图，模型也拿不到图表数据做后续分析。结果回传层要支持富产物，文本输出、错误、生成的文件、图表对象都要能收集并呈现。

### 追问五（自补）：静态检查和沙箱执行是什么关系？

互补，不是二选一。静态检查在执行前拦明显的危险代码，调用了被禁的函数、访问了敏感路径，直接拒绝，省得进沙箱；但它会被动态构造、混淆绕过，不能全靠它。沙箱是执行时的硬边界，不管代码怎么写，运行环境本身就限制住了。静态检查是前置的快筛，沙箱是兜底的硬约束，两者一起才稳。前面讲纵深防御时说过这个道理，这里正是它的体现。经验值：别把静态检查做成"看起来很严"的规则堆砌——规则太多会误拦正常代码、影响可用性；聚焦真正高危的模式，其余交给沙箱兜底，是更务实的分工。

## 60 秒面试回答模板

> Python 代码解释器是模型生成代码、安全执行、回传结果的闭环，分五层：代码生成层把需求转成 Python；沙箱执行层做隔离、白名单、超时和资源限制；结果回传层收集 stdout、stderr、文件产物、图表和返回值；状态管理层支持多轮保留变量和工作目录；安全治理层禁危险调用、网络访问和越权读写。真正难点不是会不会跑 Python，而是既给执行能力又不暴露宿主。防越权靠纵深：危险调用白名单化、网络默认关、容器隔离非 root、只读根目录、敏感目录不挂载、资源配额、全程审计，关键是让危险资源从一开始就不在执行环境里。静态检查做前置快筛，沙箱做兜底硬边界，两者互补。

## 加分项

- 用"能力与安全矛盾"定性，点出真正难点。
- 五层覆盖完整，尤其结果回传和状态管理这两层常被忽略。
- 防越权给出纵深防线，落到"不给机会"的思路。
- 讲清静态检查和沙箱的互补关系。

## 常见误区

- **只关注能不能跑 Python**：忽略宿主暴露这个核心风险。
- **只靠白名单**：应用层白名单会被绕过，还要系统层隔离兜底。
- **只收 stdout**：图表、文件产物这些回传不了，闭环价值大打折扣。
