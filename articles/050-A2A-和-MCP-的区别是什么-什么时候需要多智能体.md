# A2A 和 MCP 的区别是什么？什么时候需要多智能体？

<!-- growth-hook:v1 -->
“多智能体”是这两年面试里最容易说错的词：很多人一上来就画一群 Agent 互相调用，却说不清它们凭什么协作、什么时候根本不该拆。这题真正考的，是你能不能把两条协议线分开，又懂什么时候拆分是负收益。

## 面试官为什么爱问这题

这是大厂一面的真题，考的是两件事：协议边界的清晰度，和系统拆分的判断力。A2A 和 MCP 名字都带协议，容易被当成一类东西；多智能体又是热门词，很多人一说架构就想拆成一群 Agent。面试官想听的是你能不能把两者划开：一个管"模型怎么接外部能力"，一个管"Agent 之间怎么协作"；以及你能不能克制住"过度拆分"的冲动，说清什么时候多智能体才真的划算。这题的五条追问层层递进，从 Supervisor/Handoff 到 Skill 边界，都是在探测你有没有真的搭过多智能体系统、踩过协同的坑。前面讲过 MCP 的定位、接入和传输，这一篇把视角从"工具接入"拉到"智能体协作"，看这两个协议各管一段，以及什么时候才需要把系统拆开。

## 一句话先给结论

**MCP 更关注"模型和外部能力怎么接"，是工具与资源接入标准；A2A 更关注"Agent 和 Agent 之间怎么协作"，偏多智能体通信和分工协作。系统如果只是接搜索、数据库、文件系统，MCP 的价值更明显；只有当系统演化出多个角色明确、职责分离的 Agent（规划、检索、执行、审阅各自独立），A2A 或多智能体编排才有意义。多智能体不是越早越好——单 Agent 能清晰处理时，拆分只会增加通信、调试和治理成本；只有职责边界清晰、单 Agent prompt 已过载、确实需要角色分治时，拆分才划算。**

## 核心原理：两个协议，两个方向

### MCP 和 A2A 各管一段

把两者放在一张表里，边界就清楚了：

| 维度 | MCP | A2A |
| --- | --- | --- |
| 关注点 | 模型和外部能力怎么接 | Agent 和 Agent 之间怎么协作 |
| 定位 | 工具与资源接入标准 | 多智能体通信与分工协作标准 |
| 连接的双方 | Agent / 模型 ↔ 工具、资源、提示 | Agent ↔ Agent |
| 典型价值 | 统一接入搜索、数据库、文件系统 | 多个角色分工、通信、协调 |

一句话记法：MCP 解决"Agent 往下接工具"的问题，A2A 解决"Agent 横向接同伴"的问题。方向不同，一个向下、一个横向，服务的场景也不同。前面讲过 MCP 像 AI 世界的统一插口，那是就"接外部能力"而言；到了 Agent 之间协作这一层，就是 A2A 要管的事。

### 什么时候才需要多智能体

这是这题真正的重点。多智能体不是架构先进性的象征，而是一种有成本的拆分，只在特定条件下才划算。

先算成本。拆成多个 Agent 之后，多了三样开销。一是通信，Agent 之间要传递信息、协调进度；二是调试，一个问题可能出在任何一个 Agent 或它们的交接处；三是治理，权限、状态、失败处理都要跨 Agent 设计。单 Agent 能搞定的任务，凭空多出这些成本，得不偿失。

再看收益成立的三个条件：

1. **职责边界清晰。** 能明确分出规划、检索、执行、审阅这类角色，各自的活互不重叠。边界模糊的拆分只会让 Agent 互相推诿或重复劳动。
2. **单 Agent 的 prompt 已经过载。** 一个 Agent 要同时兼顾太多角色、prompt 写得又长又杂、注意力顾不过来，这时拆分能减轻单个 Agent 的负担。
3. **流程确实需要角色分治。** 比如需要不同视角互相校验（生成和审阅分离能减少自嗨），或不同角色有不同的权限边界。

三个条件都成立，拆分才划算；只为了满足"我们有多个 Agent"的架构冲动而拆，通常是负收益。

### 多智能体最常见的失败，出在交接处

多智能体系统出问题，很少是某个 Agent 单独崩了，更多是交接处出错。信息传丢了，上游的关键上下文没传给下游；职责重叠，两个 Agent 都以为对方会做，结果都没做；循环扯皮，Agent 之间来回交接，任务迟迟不收敛。所以在设计多智能体时，接口契约（传什么、谁负责、何时结束）比单个 Agent 的内部实现更值得投入。这一点在后面的追问里会展开。

## 工程实践：先判断要不要拆，再谈怎么拆

面对一个要搭的系统，判断顺序应该是：

**第一步，看单 Agent 能不能扛。** 先把角色、工具、流程列出来，评估一个 Agent 配好 prompt 和工具能不能清晰处理。能，就别拆。很多时候"需要多智能体"是一种错觉，其实是 prompt 没写好、工具设计得不好。

**第二步，看拆分条件是否成立。** 对照前面三个条件：职责能不能划清、单 Agent 是不是过载、是否真需要分治。三个都不满足，继续用单 Agent。

**第三步，确定了再选协作模式。** 拆分之后，是选一个 Supervisor 统一调度，还是让 Agent 之间 Handoff 自主接力，见追问一。

经验值：从单 Agent 起步，确实出现瓶颈再逐步拆出某个角色，比一开始就用多智能体框架更容易收敛。多智能体的复杂度最好是被"逼"出来的，不是主动堆出来的。

把判断过程写成一张表，对着现状套就行：

| 系统现状 | 建议 | 理由 |
| --- | --- | --- |
| 一个角色、几个工具就能跑 | 单 Agent | 没有拆分收益，只有拆分成本 |
| 要接很多外部能力，但角色单一 | 单 Agent + MCP | 扩展的是工具，不是角色 |
| 多个角色但职责有重叠 | 先划清职责，别急着拆 | 边界不清的拆分会互相推诿 |
| 角色清晰、单 Agent prompt 过载 | 拆多智能体 | 满足拆分条件，收益才开始显现 |

一个结构化的交接对象长这样（示意，字段按业务定义）：

```python
# 伪代码：多智能体交接时用结构化对象承载，避免自然语言丢信息
handoff = {
    "task_id": task_id,
    "conclusion": conclusion,        # 上游得出的结论
    "evidence": evidence_ids,        # 依据的引用
    "pending": pending_items,         # 未完成事项
    "owner": next_agent,              # 下一个接手的角色
}
validate_handoff(handoff)             # 业务侧：必填字段缺失就打回
next_agent.receive(handoff)
```

要点：交接传的是结构化字段，不是一大段自由文本；`validate_handoff` 在交接处拦截信息不全的任务。`task_id`、`conclusion`、`evidence_ids`、`pending_items`、`next_agent` 是业务侧数据。

## 追问逐条作答

### 追问一：Supervisor 和 Handoff 怎么选？

两者是多智能体的两种协调模式。Supervisor 是设一个中心调度者，由它决定下一步派给哪个 Agent，其他 Agent 被动接受任务，结构清晰、好控制、好调试，适合职责固定、流程要可控的场景。Handoff 是 Agent 之间自主交接，当前 Agent 判断该交给谁就把控制权转过去，更灵活、更贴近真实协作，但路径更不可预测、调试更难。怎么选：任务流程明确、要强管控用 Supervisor；需要灵活路由、角色自主性更重要用 Handoff。经验值：起步阶段优先 Supervisor，等协作模式稳定再考虑 Handoff。

### 追问二：多智能体最常见的失败点是什么？

交接处。具体三类：信息在传递中丢失，上游知道的关键上下文下游拿不到；职责边界模糊，两个 Agent 重复做同一件事或都以为对方会做；循环扯皮，Agent 之间来回转交，任务迟迟不结束。这些都不是单个 Agent 的能力问题，而是协作契约没设计好。所以多智能体设计里，定义清楚"每个角色接什么、交出什么、什么时候算完成"，比打磨单个 Agent 的 prompt 更关键。

### 追问三：什么情况下 Skill 比独立 Agent 更合适？

当一段能力是"可被多个角色复用的动作"，而不是"一个独立职责角色"时，做成 Skill 更合适。Skill 是被调用的能力模块，没有自己的决策循环和状态；独立 Agent 是有角色、能自主决策、有自己上下文的实体。比如"查询订单"是一个动作，做成 Skill 让规划 Agent 和执行 Agent 都能用就行，没必要为它单拆一个 Agent。判断标准：它需要独立的角色视角和自主决策吗？不需要，就做成 Skill；需要，才考虑独立 Agent。前面讨论过 Skill 和工具、独立 Agent 的边界，核心就是看它有没有"独立决策"的必要。

### 追问四：A2A 和 LangGraph 这类应用内编排框架、普通 Agent 框架的边界到底是什么？

它们在不同层面。LangGraph 这类编排框架是在单个应用内部把 Agent 的流程搭成图——状态、节点、边都是应用内的实现，属于"怎么把一个系统做出来"。A2A 是 Agent 之间的通信协议，解决的是不同主体（可能是不同团队、不同系统开发的 Agent）之间怎么发现彼此、怎么通信协作，属于"独立的 Agent 之间怎么对话"。普通 Agent 框架是构建单个 Agent 的工具。简单说：编排框架管内部实现，A2A 管跨主体的协作标准。一个系统内部可以用编排框架搭好多 Agent，而它们对外若要和别人的 Agent 协作，才需要 A2A 这类协议。

### 追问五：Agent Skills 和 Tool、独立 Agent 的边界怎么理解？什么时候更适合做成 Skill 而不是再拆一个 Agent？

三者按"自主程度"排列：Tool 是无自主能力、被调用就执行的动作；Skill 是可复用、带一点编排的能力模块，通常还是被调用；独立 Agent 有角色、有状态、能自主决策。什么时候做成 Skill：当这段能力需要复用、内部有点复杂（不是一次函数调用能搞定），但不需要独立的角色判断时。比如"生成一份合规报告"涉及查模板、填数据、校验，值得封装成 Skill，但它不需要自己决定"接下来整个任务怎么办"，所以不必拆成 Agent。只有当它需要独立的视角、要参与任务分工决策时，才升级成独立 Agent。判断口诀：不会自己做决定的，做成 Skill；要自己做决定的，才考虑 Agent。

### 追问六（自补）：多智能体之间怎么避免信息在交接时丢失？

关键是定义清楚交接契约。每个角色交出什么、以什么结构传递、下游必须消费哪些字段，都要明确，而不是把一大段自然语言历史直接丢给下一个 Agent。做法上，用结构化的交接对象代替自由文本——上游把结论、依据、未完成事项填进约定的字段，下游按字段读取。同时在交接处做一次校验，必填字段缺失就打回，别让信息不全的任务往下流。这样信息丢失能在交接点被拦住，而不是到最后才发现。

### 追问七（自补）：多智能体系统怎么判断一个任务该结束了？

要有明确的终止判断，否则容易陷入 Agent 之间反复交接。常见做法有三种：设一个负责汇总和判断的 Supervisor，由它判定任务是否完成；给每个子任务设完成标准，达到就归档；设全局的轮数或步数上限，超过就强制收口并输出当前结果。经验值：终止条件要在设计多智能体时就定义好，而不是等它跑起来发现停不下来再补——这是多智能体相比单 Agent 多出来的必答题。

## 60 秒面试回答模板

> MCP 和 A2A 是两个方向：MCP 管模型和外部能力怎么接，是工具与资源接入标准；A2A 管 Agent 之间怎么协作，偏多智能体通信与分工。只是接搜索、数据库、文件系统，MCP 就够；出现多个职责分明的角色，比如规划、检索、执行、审阅各自独立，才需要多智能体。但多智能体不是越早越好，它增加通信、调试、治理成本，只有职责清晰、单 Agent prompt 过载、确实需要分治时才值得拆，我会从单 Agent 起步，遇瓶颈再拆。协作上，流程固定用 Supervisor，灵活自主用 Handoff。多智能体最容易错在交接处，契约比单个 Agent 实现更重要。能复用又不需要自主决策的能力，做成 Skill 比拆 Agent 合适。

## 加分项

- 用"MCP 向下接工具、A2A 横向接同伴"概括方向差异，好记又准确。
- 把"要不要拆多智能体"讲成成本收益判断，给三个成立条件，而非一味推崇。
- 指出多智能体失败多在交接处，落到接口契约的设计重点。
- 用"会不会自己做决定"作为 Skill 与独立 Agent 的判断口诀。

## 常见误区

- **把 A2A 和 MCP 当成同类协议**：一个管 Agent 接能力，一个管 Agent 间协作，方向不同。
- **认为多智能体越多越好**：单 Agent 能搞定就别拆，多智能体会实打实增加通信、调试和治理成本。
- **把编排框架和 A2A 混为一谈**：编排框架管单个应用内部实现，A2A 管独立 Agent 之间的协作标准。
