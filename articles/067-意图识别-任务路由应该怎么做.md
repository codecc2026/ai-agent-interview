# 意图识别 / 任务路由应该怎么做？

<!-- growth-hook:v1 -->
意图识别这题，最容易一开口就冲着模型分类去。但它和模型路由是两件事：这里判断的是请求该走 FAQ、RAG、工具、Agent，还是干脆转人工。分不清这层，后面答得再细也偏题。

## 面试官为什么爱问这题

这题高频且偏难，第一个考点就是你能不能把它和"模型路由"分开。很多人一听路由就想到强模型还是轻模型，但那是用哪个模型的问题；意图识别 / 任务路由问的是这次请求到底该走哪条业务链路——FAQ、RAG、Tool、Agent、Workflow，还是直接转人工。这是系统入口的设计，决定了后面所有链路。面试官想听你能不能把它做成分层、多级、可治理、可评测的体系，而不是一个"单层万能路由器"。前面讲过模型路由怎么做，这一篇讲它上游的意图识别和任务路由，两者正好配套。

## 一句话先给结论

**这题和模型路由不是一回事：模型路由决定用大模型还是小模型，意图识别 / 任务路由决定请求该走 FAQ、RAG、Tool、Agent、Workflow 还是转人工。稳妥的设计分三层：目标分类先定义清楚有哪些路由终点；路由机制在高确定性场景用规则和关键词兜底、模糊场景用分类模型或 LLM 做语义判断；置信度治理在低置信度时不强判，允许澄清、降级或转人工。工程上更偏好多级路由：先业务意图路由，再子域路由，最后才模型路由。**

## 核心原理：三层设计

### 第一层：目标分类，先定义终点

路由之前先想清楚有哪些终点：闲聊、FAQ、知识问答、查状态、执行动作、复杂任务、人工兜底。这一步常被跳过，但它最重要——终点定义不清，路由器就不知道往哪分。每个终点还要说清边界：什么算 FAQ、什么算知识问答、什么情况必须转人工。边界模糊，后面分类再准也会分错。

### 第二层：路由机制，规则先行语义兜底

高确定性场景先用规则和关键词兜底，明确的指令、固定格式的问题、命中关键词的，用规则判断又快又准，也不需要额外调用模型。模糊场景再用分类模型或 LLM 做语义判断，用户说得含糊、需要理解上下文才能判断的，交给语义分类。规则成本低、确定性高，但覆盖有限；语义分类覆盖广，但有成本和延迟。两者搭配，不是二选一。

### 第三层：置信度治理，不强判

低置信度时不要强行判定一个路由，允许澄清、降级或转人工。这是很多系统缺的一环——路由器总会给出一个分类结果，哪怕它自己也不确定，然后系统带着这个误判往下跑，越跑越偏。置信度治理就是说：判断自己没把握时，宁可回头问一句、或者降级到更通用的链路、或者转人工，也别硬着头皮走一条可能错的链路。

| 层 | 做什么 | 关键点 |
| --- | --- | --- |
| 目标分类 | 定义路由终点及边界 | 终点和边界要先说清 |
| 路由机制 | 规则兜底 + 语义分类 | 规则优先，语义补模糊场景 |
| 置信度治理 | 低置信度不强判 | 允许澄清、降级、转人工 |

### 多级路由：不要做单层万能路由器

题库强调工程上通常不做"单层万能路由器"，而是多级：

**先做业务意图路由。** 判断这是 FAQ、RAG、Tool 还是 Agent。这是最粗的一刀，决定请求进哪条大链路。

**再做子域路由。** 比如客服场景里，再分订单、退款、工单、投诉。大链路确定后，在链路内细分子域。

**最后做模型路由。** 在具体链路里决定用强模型还是轻模型。这就是前面讲过的模型路由，它处在多级路由的最末端。

这样做的好处是容易治理、容易评测。每一级只解决一个问题，边界清楚；出问题时能定位到是哪一级分错；评测时也能分级看指标，而不是一个混合的正确率让人不知道问题在哪。

## 工程实践：多级路由的评估指标

路由做得好不好，要有一组指标，而不是凭感觉。题库点出五个：

| 指标 | 看什么 | 说明什么 |
| --- | --- | --- |
| 路由准确率 | 分到正确终点的比例 | 路由本身准不准 |
| 低置信度占比 | 多少请求判不准 | 规则/模型覆盖够不够 |
| 误路由成本 | 分错的代价有多大 | 不是所有错误代价相同 |
| 澄清命中率 | 澄清后是否走对 | 置信度治理有没有用 |
| 各分支完成率 | 每条链路的最终任务完成率 | 端到端效果如何 |

这里有个关键洞察：**误路由成本不是均等的**。把闲聊误判成 FAQ，代价很小；把"执行转账"误判成"查状态"，代价就很大。所以评估不能只看总体准确率，要看每类误判的代价。经验值：对高代价的误判方向单独设更严的门槛——宁可把简单问题误判成复杂链路（多花点资源），也别把高风险任务误判成低风险链路。

```python
# 伪代码：多级路由 + 低置信度治理
def route(request):
    intent, conf = business_intent(request)         # 第一级：业务意图 + 置信度
    if conf < 0.6:                                 # 低置信度不强判
        return ask_clarification(request)          # 澄清，或转人工

    subdomain = subdomain_route(request, intent)   # 第二级：子域
    model = model_route(subdomain)                 # 第三级：模型路由
    return dispatch(intent, subdomain, model)

# business_intent / subdomain_route / model_route / dispatch 为业务侧实现
```

要点：每一级分开，置信度低时在入口就拦住。`0.6` 是示意阈值，按业务调；澄清比带着误判往下跑更安全。变量都是业务侧实现。

## 追问逐条作答

### 追问一：什么时候先用规则路由就够了，什么时候必须上语义分类？

判断依据是场景的确定性。意图明确、表达固定、能用关键词或规则覆盖的，用规则就够，比如固定指令、特定前缀、已知的高频问题。意图模糊、表达多样、需要理解上下文的，才需要语义分类。经验值：先用规则覆盖能明确判断的那部分，规则判不了的模糊请求再交给语义分类，别一上来就全用模型，那会增加成本和延迟，规则能做的事没必要让模型做。

### 追问二：如果一个问题同时像 FAQ 又像 Tool 调用，你怎么处理？

看置信度和代价。如果两个都比较接近、判不准，触发澄清——问一句"你是想了解信息，还是要我帮你操作？"让意图明确。如果必须判，按误路由代价来：把 Tool 调用误判成 FAQ（该做没做）通常比把 FAQ 误判成 Tool（多做了一步查询）代价更高，那就倾向于往高代价方向保守处理。也可以设计成先给答案再提供动作入口，兼顾两种意图。

### 追问三：如何避免错误路由把后续链路全部带偏？

三道防线。一是置信度治理，没把握就澄清、降级、转人工，别带着低置信度结果往下跑。二是设置检查点，在进入高代价链路（比如执行动作）前再确认一次意图，别只靠入口那一次判断。三是可回滚，链路执行到一半发现路由错了，能退回重路由，而不是一路错到底。再加评测侧的监控：发现某类请求持续被误路由，回头调规则或模型。

### 追问四（自补）：意图识别和模型路由到底怎么区分？

一句话：意图识别决定"走哪条业务链路"，模型路由决定"这条链路里用哪个模型"。意图识别在前，模型路由在后，是上下游关系。前面讲模型路由时说过它按复杂度、风险分流到强弱模型，那是已经确定要走某条链路之后的事；而意图识别是更早一步，决定这条链路本身是什么。两者别混：一个选路，一个选车。

### 追问五（自补）：路由终点定义不清会怎样？

会导致下游全乱。路由器只能在你给的终点集合里分类，如果终点边界模糊，比如 FAQ 和知识问答没分清、什么情况转人工没定义，分类结果必然不稳定，同一类问题可能这次走这、下次走那。评测也没法做，因为你连"分对了"的标准都没有。所以目标分类这层看着像准备工作，实际是整个路由系统的地基，要先花时间定义清楚每个终点的职责和边界。

### 追问六（自补）：多级路由的每一级都要单独评测吗？

最好分级评。因为分级评测能告诉你问题出在哪一级：是业务意图分错了、子域分错了、还是模型路由选错了。如果只看最终的端到端完成率，你只知道"效果不好"，不知道该改哪一级。经验值：给每一级都标注一小批测试集，单独看准确率；同时保留端到端指标看整体。两级指标结合，既定位得准、又不偏离最终目标。

> 先划清界限：模型路由是用大模型还是小模型，意图识别 / 任务路由是决定请求走 FAQ、RAG、Tool、Agent 还是转人工，两者一前一后。设计分三层：目标分类先定义清楚路由终点和边界；路由机制上高确定性场景用规则和关键词兜底、模糊场景用语义分类；置信度治理在低置信度时不强判，允许澄清、降级、转人工。工程上做多级路由：先业务意图、再子域、最后模型路由，每级只解决一个问题，好治理也好评测。评估看路由准确率、低置信度占比、误路由成本、澄清命中率和各分支完成率，尤其注意误路由成本不均等——高风险方向要设更严门槛，宁可多花点资源也别把高危任务带偏。

## 常见误区

- **和模型路由混淆**：意图识别选链路，模型路由选模型，是上下游不是一回事。
- **做单层万能路由器**：一个路由器包打天下既难治理也难评测，多级路由才容易定位问题和分级评估。
- **低置信度还强判**：带着误判往下跑，越跑越偏。
