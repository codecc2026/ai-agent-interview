# 什么是“工具幻觉”？工程上怎么缓解？

## 面试官为什么爱问这题

这题看着在问一个名词，其实在筛有没有把 Tool Calling 真正上过生产。只会写 demo 的人，讲得出工具怎么注册、怎么把结果拼回上下文；被线上事故教过的人，会先问一句「这次调用到底是谁执行的、错了谁兜底」。工具幻觉几乎不发生在演示环境：工具一多、描述一含糊、读写边界一混，模型就开始调不存在的名字、塞不合理的参数，或者在只该查一下的场景里试着去下单。

真正要答的是 Tool Use 的稳定性和风险控制两件事。前者问你怎么让调用稳定落在合法集合里，后者问你出了界能不能把损失摁住。这两件事都不在「接上一个工具」的教程里，只能从踩过的坑里长出来。

## 一句话先给结论

**工具幻觉不是「模型不会用工具」，而是「对工具边界理解错了」；治理它不靠换更强的模型，而是把模型返回的每次调用当成不可信输入，用注册表白名单、schema 强校验、最小工具集、副作用确认和限次失败反馈这五道护栏兜住——让模型调得准、调得住，调错了也出不了大事。**

## 核心原理：先把「调错」拆清楚

### 三类表现，别混成一团

工具幻觉至少有三种长相，触发条件和拦截层都不一样：

- **调不存在的工具**：模型编出一个注册表里没有的 `name`，或者把几个工具名拼在一起、大小写前缀写错。这类最好治，白名单一挡就没了。
- **传不合理的参数**：工具名对了，但参数缺必填、类型不对、枚举值越界，甚至塞进一段自然语言当 JSON。这类得靠运行时 schema 校验。
- **越权的写操作**：用户只问「帮我看看上个月的订单」，模型却发起退款、发消息、写库这类带副作用的动作。前两类是「调错」，这一类是「调对了但不该调」，风险最高。

把三类分开不是文字游戏：第一类是命名空间问题，第二类是数据契约问题，第三类是权限问题，各自要挂在不同的拦截层上。合成一句「模型又不准了」去调 Prompt，通常哪一类都治不好。

### 根因不是能力，是边界没画清

之前讲过 Tool、Function Calling、Agent 是三层：能力单元、发起一次结构化调用的机制、带状态多轮决策的运行模式。工具幻觉就发生在这三层的接缝上——模型在某一轮里要决定调谁、填什么，而它手里只有一份工具描述。工具数量多、名字相近、description 写得含糊、参数 schema 不清晰，边界就糊了。

一个容易被忽略的判断是：模型有时并不是「不会用」，而是「对工具边界理解错了」。`search_order` 和 `refund_order` 在语义上挨得很近，用户又顺口带一句「不行就退了吧」，模型很容易把查询意图读成执行意图。这类错的源头是描述和取舍没给够，不是推理能力不够。换个说法，它选错的是「该用哪个工具、能用到什么程度」，而不是「怎么把工具调通」。

### 为什么工具一多就明显变糟

候选集变大之后，出错概率上升几乎是必然的，机制上有三条：相近名称在模型看来几乎等价，选谁都像合理；描述越长越容易只被扫到前半句，关键的适用条件反而被忽略；参数空间跟着膨胀，同一个 `id` 在不同工具里含义不同，填串了也不易察觉。经验上，单场景把工具数压到 5～10 个以内，选错率会明显下一个台阶；再往上堆，往往不是模型变笨，是给它的选择题本身变得没法做了。

这里也能反推出一个诊断手法：同一个任务，把工具集收窄到只剩两三个必需项，如果幻觉立刻消失，那基本可以断定是边界和收敛的问题，而不是模型能力的问题。这个二分在排查时很省时间，比一上来就调 Prompt 有效。

### 立论支点：模型给的是意图，不是执行

前面聊过 Function Calling 只是让模型产出一次结构化的调用意图，并不等于它执行了函数；真正去查库、发消息、扣款的，永远是我们自己的服务端代码。既然执行权在我们手里，护栏就该放在「意图」和「执行」之间这一段，而不是指望模型自觉。

把它想成一条流水线：模型产出 `{name, arguments}` → 白名单判断 name 是否存在 → schema 校验 arguments → 副作用分级决定要不要人确认 → 才真正调函数。任何一环不放行，都轮不到函数执行。工具幻觉之所以能变成事故，几乎都是因为有人把这段跳过了，拿到 `tool_calls` 就直接反射调用或 `eval` 执行。

### 边界：哪些不算工具幻觉

概念别泛化，否则答着答着就散了。工具本身返回了脏数据、模型把正确的工具结果读错了、或者循环自己跑偏停不下来，这些是另外的失败模式。还有一种更隐蔽的：参数结构完全合法，但语义不对——查订单时把 `user_id` 填成了别人的 ID，时间区间写反了。它过了 schema 校验，却仍然是错的。这类要归到业务约束层，后面单独讲。

## 横向对比

### 三类幻觉 × 触发条件 × 拦截层

| 类型 | 典型表现 | 主要触发条件 | 该拦在哪 |
| --- | --- | --- | --- |
| 不存在的工具名 | 编造 `name`、拼接工具名、大小写或前缀写错 | 工具数量多、命名相近、没做白名单 | 注册表查表，执行前直接拒绝 |
| 不合理的参数 | 缺必填、类型不符、枚举越界、把自然语言塞进 JSON 字段 | schema 不清晰、description 没写值域 | 运行时强校验，失败回传 |
| 越权的写操作 | 只读场景发起发消息 / 写库 / 下单 / 发工单 | 读写工具混在一套里、没做副作用分级 | 权限层加审批或二次确认 |

### 五道护栏 × 各管什么

| 护栏 | 主要治哪类 | 拦在执行前还是后 | 漏了会怎样 |
| --- | --- | --- | --- |
| 工具注册表白名单 | 不存在的工具名 | 执行前 | 反射调用报错，或误命中同名危险函数 |
| schema 强校验 | 不合理的参数 | 执行前 | 脏参数进业务层，报错难定位甚至写坏数据 |
| 工具集收敛 | 主要降工具名错与越权 | 挂载时 | 几十个相近工具里乱猜，错误率随数量上升 |
| 描述清晰 | 参数错、越权 | 生成前 | 读写边界分不清，模型反复选错 |
| 失败反馈加限次 | 前两类没一次调对 | 执行失败后 | 死循环重试、token 空转，或干脆静默失败 |

### 按副作用给工具分级

一刀切地「所有工具都要确认」会很快把用户训练成闭眼点同意，反而更危险。更稳的做法是按副作用分三档：

| 风险档 | 例子 | 默认处置 |
| --- | --- | --- |
| 只读 | 查订单、查库存、检索文档 | schema 校验通过后直接放行 |
| 内部写 | 改草稿、写本地状态、更新看板 | 校验加记录，可回滚 |
| 外部副作用 | 发消息、发工单、退款、下单 | 审批或二次确认，且保证幂等 |

「只读」这一档要特别标出来：工具名和 description 里就该写明「只查询、不修改」，让模型在生成阶段就能把它和写工具分开。分档本身也是一种收敛——把高风险工具从日常候选集里摘出去，等于顺手砍掉了一部分越权的可能。

## 工程实践

护栏不是并列堆上去就行，顺序有讲究。白名单必须排在最前，因为一个不存在的 `name` 根本不该走到参数解析，更不该触发反射；schema 校验紧随其后，把脏参数挡在业务层之外；副作用确认放在真正执行前的最后一刻，早点弹窗只会打断流程；失败反馈是唯一的「事后」环节，且要回环到模型、带着次数上限。顺序乱了，比如先 `json.loads` 再查白名单，一个不存在的名字可能被一路带到反射层才报错，也可能先撞上参数解析异常，两种结果都回不给模型一条干净的错误。

### 用 schema 把参数钉死

参数校验这层，落到代码上我一般直接用 Pydantic：声明式定义字段，运行时强校验，报错还带字段级信息。要点是模型返回的 `arguments` 是一段 JSON 字符串，先解析，再交给一个显式模型做校验，任何字段不合规就抛 `ValidationError`。

```python
# 依赖：pydantic v2；接口字段按 OpenAI 兼容的 tool_calls 格式
from pydantic import BaseModel, Field, ValidationError, field_validator

class SearchOrderArgs(BaseModel):
    user_id: str = Field(..., description="下单用户 ID，必须属于当前会话用户")
    status: str = Field(..., description="订单状态")
    limit: int = Field(10, ge=1, le=50, description="返回条数")

    @field_validator("status")
    @classmethod
    def check_status(cls, v: str) -> str:
        allowed = {"paid", "shipped", "refunded", "pending"}
        if v not in allowed:
            raise ValueError(f"status 须为 {sorted(allowed)} 之一，收到 {v!r}")
        return v

def validate_call(name, arguments_json):
    # 白名单：注册表里没有的 name 直接拒绝；None 表示该工具无参数
    registry = {"search_order": SearchOrderArgs, "get_inventory": None}
    if name not in registry:
        raise ValueError(f"未注册的工具：{name}")
    model = registry[name]
    if model is None:
        return {}
    import json
    raw = json.loads(arguments_json)          # 可能抛 JSONDecodeError
    return model.model_validate(raw)          # 可能抛 ValidationError
```

`ge` / `le` 把值域钉住，`field_validator` 把枚举写死，`description` 既是给人看的，也是给模型看的——字段含义写清了，模型填错的概率会明显下降。注意 `validate_call` 返回的是校验过的模型实例，不是原始 dict，后面执行时拿到的就已经是干净数据。

### 主流程：意图到执行之间的五道闸

```python
# 伪代码：把护栏串进「意图 → 执行」这一段
# load_tool 返回带 risk 字段的工具对象；ask_model_to_fix 返回修正后的
# arguments JSON 字符串；confirm_with_human / brief_error /
# fallback_to_human / refuse / as_tool_message 均为业务侧实现
MAX_RETRY = 2          # 经验值：连续重试上限 2～3 次，再多基本是空转

def dispatch(tool_call, ctx):
    name = tool_call.function.name
    args = tool_call.function.arguments
    for attempt in range(MAX_RETRY + 1):
        try:
            parsed = validate_call(name, args)        # 白名单 + schema
            tool = load_tool(name)
            if tool.risk == "external_side_effect":   # 副作用分级
                if not confirm_with_human(name, parsed):
                    return refuse("用户未确认，调用已取消")
            result = tool.run(parsed, ctx)            # 到这里才真正执行
            return as_tool_message(tool_call.id, result)
        except (ValueError, ValidationError) as e:
            if attempt == MAX_RETRY:
                return fallback_to_human(name, str(e))
            args = ask_model_to_fix(name, args, brief_error(e))
    return None
```

### 失败反馈该回传什么

`brief_error(e)` 是这套闭环里最容易被写坏的一环。把整个异常栈灌回上下文，既迅速撑大 token，又带着一堆无关信息诱导下一次乱填；只回「参数非法」，模型又无从改起。合适的是字段级、可直接照着改的一句话。比如 `limit` 越界时，回传给模型的应该是：

```text
调用 search_order 被拒：limit 须为 1～50 的整数，你给的是 500。
请只修正该字段后重新给出完整 arguments。
```

配套还有三条：`MAX_RETRY` 给硬上限，连续同类失败直接降级到人工或退回固定流程，别让循环空转；每轮把「上次为什么被拒」留在上下文里，避免同一个错反复犯；所有被拒调用留痕，供事后复盘。工具数量、重试上限这类阈值都是工程经验值，不是通用常数，要按自己工具集和模型表现调，别照搬。

## 追问逐条作答

### 追问一：工具幻觉和常说的「模型幻觉」是一回事吗？

不是，两者错的位置不同。「模型幻觉」是内容层编造了不存在的事实，靠检索、引文、事实校验去治；工具幻觉是动作层调错了工具或参数，靠调用护栏去治。把它们混起来，最典型的错法是拿 RAG 去治越权下单——检索再准，也拦不住一次不该发生的写操作。答的时候先分开「内容错」和「动作错」，再说各自手段，边界就清楚了。

### 追问二：schema 校验全过了，参数还是不合理怎么办？

这正好是前面留的那个坑：结构合法不等于语义合法。`user_id` 类型对、必填齐，但填成了别人的 ID；`start` 晚于 `end`；`limit` 落在 1～50 内，却一次拉了不该看的数据。schema 管的是形状和值域，管不了归属、权限和状态机。补法是三件事：字段级加业务约束（区间先后、归属一致），执行前查当前会话的权限上下文，写操作再过一遍状态机（订单已退款就不能再退）。一句话，把「不信任模型返回」从参数层一路延伸到业务层。

### 追问三：怎么区分模型是「故意越权」还是「没理解」？

工程上不需要从意图上区分，一律当不可信输入处理，结论都一样：先校验、再分级、后执行。但为了归因，值得在埋点里分开记：工具名不存在，多半是描述和收敛没做好；参数反复错，多半是 schema 或 description 写得糊；只读场景发起写调用，多半是读写工具混挂、权限没分层。三类信号指向三种改法，混在一起统计就只知道「又错了」，不知道该改哪儿。

### 追问四：把错误回传给模型让它自己改，会不会越改越离谱？

会，尤其在错误描述含糊、或者循环没有退出条件的时候。前面聊过 ReAct 循环里观察会驱动下一轮决策，观察本身是噪声，模型就会带着噪声继续跑。兜底是四条一起上：错误要结构化且只给必要字段、重试有硬上限、连续同类失败直接降级、每轮把上次被拒原因写进上下文。别指望模型第二次一定改对，要设计成「改不对也不出事」。

### 追问五：工具越接越多，怎么控制幻觉？

先收敛再分组。按场景只挂载当前任务用得到的工具，读数场景不要把写工具一起塞进去；工具多到必须分组时，先做一层路由选出工具子集，再把子集交给模型。命名上让读写边界一眼可分（`search_` 对 `create_` / `refund_`），description 里写明适用范围和反例，尤其补一句「什么时候不该用它」。这些都是降低猜错概率的事前手段，比事后加校验便宜。

### 追问六：怎么证明这套护栏真的有效？

把稳定性当可测指标，而不是靠感觉。每次调用都留一条记录：`name`、`arguments`、校验是否通过、被哪一层拦下、最终是否执行、重试了几次。再攒一批「故意构造的坏调用」当回归集——之前聊过用自有黄金集做评估的思路，这里一样适用——统计两个率：坏调用被拦下的比例，和好调用被误拦的比例。只盯拦截率，会把护栏调得越来越紧、正常调用全被挡；两个率一起看，才知道该松还是该紧。上线后按这份记录复盘事故，也能很快定位是哪道闸漏了。

## 60 秒面试回答模板

> 工具幻觉我理解成三类：调了不存在的工具、传了不合理的参数、在只读场景发起写操作。根因多半不是模型不会用，而是工具多、描述糊、schema 不清，边界理解错了。治理上把它当不可信输入，在意图和执行之间加五道闸：注册表白名单挡名字，schema 强校验挡参数，按场景收敛工具集降低猜错概率，副作用动作走审批或二次确认，失败只回传结构化错误并限制重试次数。还有一点容易被忽略——schema 过了不代表语义对，归属、权限、状态机得在业务层再兜一遍。目标是调得准、调得住，出错了也不至于闯祸，而不是指望换个更强的模型。

## 加分项

- **把意图和执行分离讲清楚**：模型只产出 `{name, arguments}`，执行权在服务端，护栏天然该放在中间层。这一句能把 Tool Calling 稳定性讲成架构判断，而不是一堆零散技巧。
- **按副作用分级，而不是一刀切确认**：只读放行、内部写记录可回滚、外部副作用才二次确认加幂等。既控住风险，又避免确认疲劳把用户训练成无脑点同意。
- **把失败反馈设计成可降级的闭环**：结构化错误、硬上限、连续失败转人工，顺手回应「循环跑偏停不下来」这类追问，说明你想过循环本身会失控。
- **给护栏配可测指标**：坏调用回归集加拦截率、误拦率双看，把稳定性从主观感受变成能回归、能复盘的数值。

## 常见误区

- **换更强模型就能解决**。幻觉来自边界没画清，不是推理能力不足；工具集不收敛、描述不清晰，换模型照样猜错，甚至更自信地猜错。
- **拿治内容幻觉的办法治动作幻觉**。加检索、加引文、加事实校验都对内容有效，拦不住一次越权的写调用。
- **schema 过了就当万事大吉**。值域和类型只是第一层，归属、权限、状态机没兜住，参数「合法」照样能写坏数据。
- **所有工具都弹二次确认**。确认一多，用户闭眼点同意，护栏等于没有；该按风险档区别对待。
