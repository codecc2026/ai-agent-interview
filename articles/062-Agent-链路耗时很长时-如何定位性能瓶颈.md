# Agent 链路耗时很长时，如何定位性能瓶颈？

<!-- growth-hook:v1 -->
“Agent 太慢了”——这是最像结论、其实最没信息量的一句话。慢在哪一层？模型、检索、工具、编排、结果生成，五段耗时完全不同。这题看的就是你有没有把耗时拆开测的习惯。

## 面试官为什么爱问这题

这题高频且偏难，考的是你有没有把长链路延迟拆解定位的能力。一条 Agent 链路跑几分钟，很多人脱口而出"模型太慢"，这是外行答案，因为几分钟里模型调用可能只占一小部分，大头在别处。面试官想听的是你能不能把耗时按层拆开、用 trace 和 span 定位到具体环节，再对症下药。更深的考点在题库最后一句：很多慢不是单次调用慢，而是状态流转和执行闭环没设计好，表现为反复判断、没有明确完成信号导致的来回检查。前面聊过成本排查"钱花在哪"，这一篇讲"时间花在哪"，两件事方法相通但落点不同。

## 一句话先给结论

**Agent 链路跑到几分钟，不能只说"模型太慢"，要先把耗时拆开：模型层看单次推理时长、首 token 延迟、输出 token 长度；检索层看召回、重排、外部搜索、知识库请求；工具层看 API 延迟、浏览器动作、代码执行、等待外部系统；编排层看路由判断、Supervisor 判断、重复重试、串行等待；结果层看后处理、校验、存储、日志落盘。稳的做法是给每步打 trace 和 span，先看 wall time 花在哪，再决定换模型、改链路、减步骤还是改串行为并行。**

## 核心原理：五层耗时分解

### 先看 wall time 花在哪

定位的第一步不是猜，是测。给每一步打上 trace 和 span——trace 是一次完整请求的全链路，span 是其中每个环节的耗时片段。有了这个，你能看到总耗时里每一段占多少，而不是凭感觉 blame 模型。

wall time（墙钟时间）是关键指标，它衡量用户实际等了多久。它不等于各段 CPU 时间之和，因为里面有大量等待，比如等工具返回、等外部系统、等串行的上一步结束。这些等待恰恰是长链路的大头，也是不看 trace 发现不了的。

### 五层各自的耗时来源

| 层 | 耗时来源 | 典型大头 |
| --- | --- | --- |
| 模型层 | 单次推理时长、首 token 延迟、输出 token 长度 | 输出越长越慢，首 token 延迟影响体感 |
| 检索层 | 召回、重排、外部搜索、知识库请求 | 外部搜索、重排链路叠加 |
| 工具层 | API 延迟、浏览器动作、代码执行、等待外部系统 | 慢 API 和浏览器动作 |
| 编排层 | 路由判断、Supervisor 判断、重复重试、串行等待 | 重复判断和不必要的串行 |
| 结果层 | 后处理、校验、存储、日志落盘 | 通常占比较小，但不可忽略 |

五层拆开后，瓶颈在哪一目了然，对应的优化手段也不同：

| 瓶颈层 | 主要优化手段 | 副作用 |
| --- | --- | --- |
| 模型层 | 换更快的模型、缩短输出长度 | 可能影响效果 |
| 检索层 | 减少检索环节、优化召回重排 | 需重新评估检索质量 |
| 工具层 | 优化慢工具、加缓存、改并行 | 依赖外部系统配合 |
| 编排层 | 减少判断次数、串行改并行 | 需理清步骤依赖 |
| 结果层 | 精简后处理、异步落盘 | 通常收益有限 |

这张表回答了"定位之后怎么办"：不同层的瓶颈对应不同手段、不同代价。比如模型层换模型可能伤效果，得配评测；编排层改并行收益大但要先理清依赖。知道瓶颈在哪还不够，还得知道这一层的手段和代价，才是完整的排查能力。

### 题眼：慢常在闭环设计，不在单次调用

题库点出一个关键判断：很多五分钟任务，不是卡在单次模型调用，而是卡在多步链路过长、工具等待、监督节点重复判断，或者中间没有明确成功信号导致反复检查。这说明性能问题很多时候不是"模型太慢"，而是**状态流转和执行闭环没有设计好**。

这句话把性能问题从"调用层"提升到了"设计层"。一个没有明确完成信号的 Agent，会反复检查"做完了没"，每检查一次就多一次模型调用；一个状态流转混乱的链路，会在节点之间来回绕。这些都不是换更快的模型能解决的，得回头改流程设计。

### 如果用了 LangGraph，重点看三处

题库专门提了图编排的排查视角：看节点级耗时，哪个节点最慢；是不是反复进入同一节点，可能有循环没收敛；有没有因为缺少明确完成信号而来回判断。这三处都指向"闭环设计"这个根。前面讲过图的三件套和时间回溯，这里用节点级观测来定位性能问题，是同一套能力的另一个用法。

## 工程实践：一次性能排查的顺序

按这个顺序查，能少走弯路：

**第一步，拿到全链路 trace。** 没有 trace 就没法定位。先确保每一步都有 span——模型调用、检索、每个工具、每个编排节点，都记录起止时间和耗时。

**第二步，按 wall time 排序。** 看哪几段耗时最长，优先看头部。二八分布常见——少数几段占了大部分时间。

**第三步，区分"执行慢"和"等待慢"。** 一段耗时很长，是它自己在算，还是在等别的？等工具返回、等串行前序，这类等待的优化思路完全不同，前者要优化工具，后者要改并行。

**第四步，看编排层有没有重复。** 数一数某个节点进了几次、某个判断是否重复做。反复进入同一节点、缺少完成信号导致的循环检查，是隐藏的大头。

```python
# 伪代码：给链路各段打 span，汇总后按耗时排序
spans = []

def traced(name, fn):
    def wrapper(*args, **kwargs):
        start = now()                          # 业务侧：取当前时间
        result = fn(*args, **kwargs)
        spans.append((name, now() - start))     # 记录这一段耗时
        return result
    return wrapper

run_pipeline(
    model=traced("model", call_model),          # 模型段
    retrieve=traced("retrieve", do_retrieve),   # 检索段
    tool=traced("tool", call_tool),             # 工具段
)

report = sorted(spans, key=lambda x: -x[1])     # 按耗时降序，看头部
```

要点：把每个环节包一层 `traced`，跑一次就能拿到各段耗时并排序。`now`、`call_model`、`do_retrieve`、`call_tool`、`run_pipeline` 是业务侧实现。真实项目用专门的追踪框架会更完整，这里只示意"打点—汇总—排序"的思路。

## 追问逐条作答

### 追问一：为什么不能笼统说"模型太慢"？

因为一条几分钟的链路里，模型调用往往只占一部分，大头可能在工具等待、串行编排、重复判断上。笼统归因于模型，会导致优化方向错误——换了更快的模型，总耗时可能没明显变化。正确做法是先打 trace 看 wall time 分布，确认瓶颈在哪一层再动手。

### 追问二：首 token 延迟和输出 token 长度为什么要分开看？

因为它们影响的是不同东西。首 token 延迟主要影响用户体感，即多久看到第一个字；输出 token 长度主要影响总耗时和成本，生成得越多越久。一个链路可能首 token 很快但输出很长，体感好但总耗时长；也可能反过来。分开看才知道该优化哪里：体感问题动首 token，总时长问题动输出长度。

### 追问三：编排层的"串行等待"怎么优化？

看哪些步骤之间没有依赖。如果两个调用互不依赖，比如同时查订单和查库存，就把串行改成并行，总耗时从两者之和降到接近最大者。前面讲并发治理时说过动态检索工具的选择，这里说的是编排层的并行化。经验值：先画出步骤间的依赖关系，只在真正独立的地方并行，别把有依赖的步骤强行并发导致结果错乱。

### 追问四（自补）：怎么判断是"执行慢"还是"等待慢"？

看这段 span 里有没有在等外部。工具调用、外部 API、数据库请求这类 span，大部分时间花在等对方返回，是等待慢；模型推理、本地计算这类 span，时间花在自己算，是执行慢。等待慢要靠优化被调用方、加缓存、改并行；执行慢要靠换更快的模型或算法。区分清楚，优化方向才对。

### 追问五（自补）：为什么"没有明确完成信号"会导致慢？

因为 Agent 判断不出"已经完成了"，就会反复检查、多跑几轮。一个任务如果没定义清楚什么叫成功，模型只能一次次回头看"够不够、对不对"，每次都多一次模型调用。给它明确的完成条件，说明达到什么状态就算完成，它才能及时停。前面讲 Agent 终止条件、讲工作流停止条件时都提过这一点，落到性能上就是：缺完成信号既影响正确性，也拖慢速度。

### 追问六（自补）：为什么 trace 要覆盖每个环节，而不是只看总耗时？

因为总耗时只能告诉你"慢"，告诉不了你"慢在哪"。一个五分钟的请求，如果只知道总共五分钟，你无法判断是模型占了四分钟、还是三十次工具调用各自十秒累积的。只有每个环节都有 span，才能看到耗时分布，找到头部。经验值：打点本身也有成本，但在排查阶段这点开销远小于盲目优化的浪费；定位完成后可以只保留关键 span，常态化观测。

- 强调先看 wall time 和 trace，不凭感觉归因。

## 常见误区

- **笼统归因模型慢**：不改方向只换模型，总耗时可能没变化。
- **不看 trace 就优化**：没有耗时分布，容易优化错地方。
- **忽略编排层的重复判断**：反复进节点、缺完成信号是隐藏的大头。
