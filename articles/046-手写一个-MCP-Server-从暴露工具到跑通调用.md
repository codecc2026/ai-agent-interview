# 手写一个 MCP Server：从暴露工具到跑通调用

## 面试官为什么爱问这题

这题考的是你有没有真正动手建过服务端，而不只是会用别人写好的。很多人对 MCP 的接触停在"配一个现成的 Server 来调",真让自己写一个，就卡在能力怎么划边界、schema 怎么定、错误怎么返回这些细节上。面试官问"从暴露工具到跑通调用",想听的是一条完整的建设路径——从第一步的能力设计到最后一步的联调，每一步该做什么、哪里最容易踩坑。前面讲过 MCP 的定位，也看过一个 Server 暴露三类能力的结构；这一篇往前落到"动手建"的工程流程，重点放在两个最容易被忽略的地方：能力边界和错误处理。

## 一句话先给结论

**手写 MCP Server 的典型流程是五步：明确要暴露的能力边界（工具、资源还是提示模板）；定义输入输出 schema 和错误处理方式；选传输方式（STDIO 或 HTTP）；实现服务端逻辑并补齐鉴权、日志、超时和异常处理；最后在客户端完成注册、发现、调用和联调测试。工程上最容易被忽略的不是"会不会套壳",而是能力边界和错误处理——MCP Server 不是把现有 API 套一层壳，而是要把能力设计成真正适合模型消费的接口。**

## 核心原理：五步走，每步的关键

### 第一步：明确能力边界

动手之前先回答：要暴露的到底是工具、资源还是提示模板。这三者面向模型的消费方式不同，先看清楚该怎么选：

| 能力类型 | 模型的消费方式 | 适合什么 |
| --- | --- | --- |
| 工具（Tools） | 被执行，拿到返回结果 | 查询、计算、调用外部动作 |
| 资源（Resources） | 被读取，作为上下文 | 文档、记录、配置等只读内容 |
| 提示模板（Prompts） | 被引用，作为提示结构 | 可复用的固定提问框架 |

把一个"查数据并生成结论"的能力，拆成"查数据的工具"还是"可读的资源"，设计取向不一样。

边界还要划清粒度。一个 Server 暴露的能力不宜过杂，每个能力职责单一、描述清楚，模型才好判断什么时候用。前面讲工具设计时说过粒度和命名的重要性，这里同样适用：能力是给模型消费的，不是给人调用的 API，设计时要站在模型怎么理解和选择的角度。

### 第二步：定义 schema 和错误处理

这一步决定接口好不好用。输入输出 schema 要清晰——每个参数什么类型、哪些必填、返回什么结构，都要定义明确。模型靠这些描述理解怎么用你的能力，schema 含糊，模型传参就会错。

错误处理同样关键，而且最容易被忽略。能力执行失败时要返回结构化的错误信息，让模型能读懂"失败了、为什么、该怎么办",而不是抛一个它看不懂的异常栈。一个好的错误返回，能让模型决定是换参数重试、还是换一条路；一个糟糕的错误返回，会让模型卡住或瞎猜。

### 第三步：选传输方式

STDIO 或 HTTP，取决于部署形态。STDIO 适合本地、进程内集成，客户端启动一个服务端子进程通信；HTTP 适合跨进程、跨网络，服务端独立部署给多个客户端访问。选型看你是在本机集成还是做共享服务。

### 第四步：实现服务端并补齐工程要素

实现核心逻辑之外，还要补齐鉴权、日志、超时和异常处理。这几项在 Demo 里能省，在生产里一项都不能少：鉴权决定谁能调、日志用于排障、超时防止慢调用拖死、异常处理兜住各种意外。题库把这几项并列提出，说明它们本来就是服务端建设的一部分，不是可选装饰。

### 第五步：客户端注册、发现、调用、联调

服务端写完不算完，要在客户端把它跑通：注册 Server、发现它暴露的能力、实际调用、联调测试。设计得再好，客户端这边接不上、发现不到、调用不对，等于白做。联调阶段最容易暴露前四步的疏漏——schema 没对齐、错误返回格式不对、传输配置有误，往往都是在这一步才现形。

| 步骤 | 关键动作 | 最易忽略的点 |
| --- | --- | --- |
| 定能力边界 | 分清工具/资源/提示模板，划好粒度 | 把能力当普通 API 堆砌，不考虑模型怎么消费 |
| 定 schema 与错误处理 | 明确参数与返回，设计结构化错误 | 错误处理缺失，模型读不懂失败原因 |
| 选传输 | STDIO 或 HTTP 按部署形态选 | 本地与跨网络场景混用 |
| 实现服务端 | 核心逻辑 + 鉴权日志超时异常 | 只写核心逻辑，工程要素全缺 |
| 客户端联调 | 注册、发现、调用、测试 | 跳过联调，前几步的错到最后才发现 |

## 工程实践：把"套壳"改成"适合模型消费"

题库里那句"不是简单把现有 API 套一层壳"是这题的题眼。展开讲，一个适合模型消费的能力和一个人用的 API 有什么不同。

人用 API 时，调用方会读文档、理解上下文、自己处理各种边界；模型用能力时，只能靠你给的 schema 和描述来理解。所以：

**描述要写给人看更要写给模型看。** 能力的描述、参数的说明要具体明确，最好带上"什么时候用、什么时候别用"。含糊的描述会让模型在该用时不用、不该用时乱用。

**错误要结构化。** 失败时返回清晰的错误信息，而不是抛异常栈。经验值：错误信息里给出"失败原因 + 可采取的下一步",比只给一个错误码对模型更友好。

**粒度要贴着模型的决策需要。** 一个能力对应一个清晰的动作，参数尽量少。别把需要人来判断的复杂逻辑塞进一个能力里，模型传参容易错。

一段示意代码（以暴露一个查询工具为例，具体 API 以实现为准）：

```python
# 伪代码：一个带 schema 和错误处理的工具能力
@server.tool(
    name="get_order",
    description="根据订单号查询订单状态。仅在用户明确给出订单号时调用。",
)
def get_order(order_id: str) -> dict:
    if not order_id:                                  # 参数校验
        return {"ok": False, "error": "缺少订单号", "hint": "请向用户询问订单号"}
    try:
        status = query_order(order_id)                # query_order 为业务侧实现
        return {"ok": True, "status": status}
    except OrderNotFound:                             # 结构化错误，模型可读
        return {"ok": False, "error": "订单不存在", "hint": "请核对订单号后重试"}

# 返回统一的 {ok, ...} 结构，错误里带原因和建议，便于模型判断下一步
```

要点：描述里写清"什么时候调用";参数先校验；异常被转成结构化错误，带 `error` 和 `hint` 让模型知道怎么应对。这些都不是套壳能自动得到的，是设计出来的。

## 追问逐条作答

### 追问一：MCP Server 的能力是不是越多越好？

不是，粒度和边界更重要。能力太多、职责重叠，模型选择时会混淆，反而更容易选错；能力划分清楚、每个职责单一，模型才好判断何时用哪个。经验值：先暴露真正需要的核心能力，跑起来看模型用得准不准，再按需要增补，别一开始就堆一堆。具体设计仍以能力边界清晰为准。

### 追问二：写 Server 时最容易踩的坑是什么？

两个。一是能力边界没划好，把现有 API 直接套壳，结果描述含糊、粒度不对，模型用不好；二是错误处理缺失，失败时抛异常栈或什么都不返回，模型读不懂、卡住或瞎猜。这两点都在题库强调的范围里——能力设计和错误处理，比"会不会写代码"更决定 Server 好不好用。

### 追问三：STDIO 和 HTTP 在联调时有什么不一样？

STDIO 是客户端启动服务端子进程、通过标准输入输出通信，联调时两者生命周期绑在一起，本机就能测，适合本地开发。HTTP 是服务端独立部署、客户端通过网络访问，联调时要先起服务、配地址和鉴权，能测跨网络的真实调用。具体怎么配按你用的 SDK 来，选型原则是本机集成用 STDIO、共享服务用 HTTP。

### 追问四（自补）：为什么要做客户端联调，服务端自测通过还不够吗？

服务端自测只能证明"我的逻辑对",证明不了"客户端能接上"。很多问题出在两端之间：schema 对不齐、错误返回格式客户端解析不了、传输配置两边不一致、发现机制没注册上。这些只有真跑一遍客户端的注册—发现—调用才能发现。所以联调不是走过场，是验证接口契约真的对上了。

### 追问五（自补）：能力描述应该怎么写才适合模型消费？

写具体、写边界、写反例。不只说"查询订单",还说"仅在用户明确给出订单号时调用";不只说参数是什么，还说必填还是可选、什么格式。适当给出"什么时候别用",能减少模型误触发。描述是模型理解你能力的唯一依据，花点心思写清楚，比事后加一堆兜底更划算。

## 60 秒面试回答模板

> 手写 MCP Server 我按五步走。第一步明确能力边界，分清是工具、资源还是提示模板，划好粒度；第二步定义输入输出 schema 和错误处理，错误要结构化、模型能读懂；第三步选传输，本地集成用 STDIO，跨网络共享服务用 HTTP；第四步实现服务端逻辑，补齐鉴权、日志、超时和异常处理；第五步在客户端做注册、发现、调用和联调，验证接口真的对得上。最容易踩的坑是能力边界和错误处理：Server 不是把现有 API 套一层壳，而是要把能力设计成适合模型消费的接口——描述写清边界、错误带原因和建议、粒度贴着模型决策的需要。服务端自测通过不等于客户端能用，联调不能省。

## 加分项

- 强调"不是套壳，是设计给模型消费的接口",点出题眼。
- 错误处理展开到"结构化错误 + 原因 + 下一步建议",落到具体做法。
- 主动提联调的必要性：验证两端接口契约，不是走过场。
- 五步流程讲完整，每步说出关键动作和最易忽略点。

## 常见误区

- **把 Server 当成 API 套壳**：不做能力设计和错误处理，模型用不好，这是最常见也最致命的偏法。
- **错误处理靠抛异常**：模型读不懂异常栈，失败要返回结构化、可读的错误。
- **跳过客户端联调**：服务端自测通过就以为完事，结果 schema、发现、传输的问题到最后才暴露。
