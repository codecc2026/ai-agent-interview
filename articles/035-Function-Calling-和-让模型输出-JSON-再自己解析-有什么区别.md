# Function Calling 和“让模型输出 JSON 再自己解析”有什么区别？

## 面试官为什么爱问这题

这题看着在问两种输出格式怎么选，其实在筛你有没有「协议」和「约定」的分层意识。不少人用了半年结构化输出，还觉得两条路子是同一回事，都是让模型吐一段能被 `json.loads` 吃进去的文本；一问到「模型多说一句『好的』怎么办」「平台不给原生工具调用，你怎么把 JSON 方案做到能上线」「换个模型供应商要改哪些地方」，就答不到点子上了。面试官想听的是你清不清楚：结构到底是谁在保、失了格式谁兜底、什么时候这层保证值不值得付出的迁移成本。这几个问题答得出来，说明你是真的接过线上链路，不是照着示例跑过一遍 demo。

## 一句话先给结论

**两条路子都能拿到结构化结果，区别在于约束放在哪一层：让模型输出 JSON 是 Prompt 层的一句约定，模型照不照做全靠自觉，程序端只能事后校验和兜底；Function Calling 是接口层的契约，工具定义、参数 schema、消息角色都是协议的一部分，结构由接口保证，失败能定位到具体环节。抽字段、做轻量结构化返回，用 JSON 加 parser 起步就够；一旦要接真实工具调用、外部系统编排、带副作用的执行，就该上原生 Function Calling 或等价的 Tool Use 协议。**

## 核心原理：约束放在哪里，决定了可靠性

### 两条路子各自怎么产出结构化结果

让模型输出 JSON，做法是在系统提示或用户提示里写清要求：只输出 JSON，字段有哪几个，类型分别是什么，最好再贴一两个示例。模型读到这段要求，生成一整段文本，程序拿到后 `json.loads` 反序列化，再按自己维护的规则检查字段。整条链路里，程序只在末端出现一次，前面生成什么完全由模型的概率采样决定。

原生 Function Calling 不是这么干的。请求发出前，宿主把工具定义随请求一起下发，每个工具有 `name`、`description`、以及用 JSON Schema 写的 `parameters`；模型判断要调哪个工具，返回一个带固定字段的 `tool_calls`，里面写明工具名和参数。宿主读出这份结构，校验、鉴权、执行，再把结果封成专门的消息角色回灌。之前拆过一条工具调用消息从发出到回灌的五步链路，这里不重复那套运行时，只看两条路子在「谁来保证结构」这件事上的分工。

### 可靠性的根因：约束前移还是事后校验

两种方案稳定性差一截，常被解释成「模型不乖」，其实不是。根子在约束施加的位置。JSON 方案的约束是事后的：模型先把整段文本按概率生成完，程序再检查合不合格，格式错了只能发现、重试、兜底，生成过程本身没有任何东西拦着它多说一句话。原生方案把约束前移了一层：工具定义和参数 schema 随请求下发，模型本身经过针对工具调用的训练，在带约束解码的实现里，输出还会被限制在符合 schema 的候选 token 中，天然落进接口规定的字段；接口层再把结果封成固定结构交给宿主。约束从事后挪到生成这一段，是两者稳定性差距的来源，不是模型更听话。

这一点决定了失败形态完全不同。JSON 方案里，一次输出不合格式，你拿到的是一段孤立文本，除了重试几乎没有别的抓手；原生方案里，一次调用不合约定，你能知道是工具名不在列表、参数缺了必填字段，还是回灌的结果和调用对不上，错误本身是结构化的，能被校验、审计、重试和观测分别接住。

### 契约里到底有什么

题库里那句「模型和宿主之间有一层明确契约」，值得拆开看这层契约具体装了什么。JSON 方案的契约只有一句自然语言要求，机器没法直接校验：字段、类型、可空性全写在提示词里，程序端还得自己另维护一份校验规则，两份东西很容易对不上。原生 Function Calling 的契约是双向的：请求侧带 `tools` 和参数 schema，响应侧带 `tool_calls` 的固定字段，回灌侧有专门的消息角色和调用标识。每一环都有结构化的锚点，挂什么工程能力都方便。

锚点多了，后面的事就好做。要给一次调用做审计，能记下哪个工具、哪些参数、哪次调用、成功还是失败；要做重试，能按参数错、无权限、超时分开处理；要做观测，能统计工具命中率和参数校验通过率。这些在纯文本方案里不是做不了，是每一样都得自己从一段自由文本里把信息抠出来再补结构。契约越清楚，越不用重复造这层轮子。

### 从纯 prompt 到原生工具调用，其实是一条能力阶梯

把「让模型表达结构化意图」当成二选一，容易漏掉中间的档位。按接口保证的强弱，实际是一排阶梯，越往上结构越可靠、工程配套越全，绑特定平台也越紧：

| 档位 | 关键做法 | 接口保证到什么程度 | 典型用途 |
| --- | --- | --- | --- |
| 纯 prompt 约定 | 提示词写「只输出 JSON」+ few-shot | 无保证，全靠模型自觉，程序事后校验 | 原型、跨模型通用抽取 |
| JSON mode | 请求带 `response_format: {"type":"json_object"}` | 保证输出是合法 JSON 对象，字段和类型不保证 | 只要一段能解析的 JSON |
| 结构化输出 | `json_schema` + `strict: true` | 保证输出贴合给定 schema | 字段固定的抽取、分类、打标 |
| Function Calling | `tools` + `tool_choice` + `tool_calls` | 结构化之上加工具语义、多轮回灌、宿主执行契约 | 真实工具调用、外部编排、副作用执行 |

这张阶梯也顺手回答了「什么时候够用」：抽字段不需要工具语义，走到结构化输出那档通常就够稳了，不必硬上 Function Calling；只有调用意图要被宿主拿去执行、结果还要回灌，才需要最上面那档的契约。中间两档是接口能力，不是所有平台都提供，选之前先看手上的模型支持到哪一档。还有个细节别想当然：带 `strict` 的结构化输出约束的是最终响应内容，工具调用那档约束的是调用结构，两者力度不一样，`arguments` 里的内容通常仍要宿主按 schema 过一遍，不能因为都叫 schema 就当成同一种保证。

### 概念边界：别把三件事混成一团

结构化输出和工具调用不是一回事。前者只管「结果长成什么形状」，可以纯粹拿来做字段抽取，不产生任何工具调用；后者在结构化之上多了「调用哪个工具、参数交给谁执行」的语义。两者交叠在结构化，分野在有没有工具语义和宿主执行契约。

Function Calling 和 MCP 也不是一层东西。MCP 管的是工具怎么被发现和连接，解决跨进程、跨服务把工具接进来的问题；Function Calling 管的是模型用什么格式把调用意图表达出来。一个是连接协议，一个是输出协议，之前划过 MCP 和 Agent 的边界，这里同样别混。还有个更细的混淆：让模型输出 JSON 和 JSON mode 是两码事，一个纯靠提示词，一个是接口参数，中间还夹着带 schema 约束的结构化输出，三档可靠性差着层级。

## 横向对比：把两种方案摆到一起逐项看

### 全维度对比

昨天给过一张四行的基础区别表，这里按面试官爱深挖的维度展开一层，尤其把格式自由度、模型能力依赖、调试和迁移成本补齐：

| 维度 | 让模型输出 JSON 再解析 | 原生 Function Calling |
| --- | --- | --- |
| 约束位置 | 事后校验，生成过程不受限 | 生成阶段受 schema 或协议约束，接口封装结构 |
| 结构保证方 | 模型自觉 + 程序兜底，没有机器可校验的 schema | 接口保证响应字段齐备（工具名、arguments 都在），arguments 内容仍要校验 |
| 格式自由度 | 高，任意嵌套结构都能要求，不受工具语义限制 | 受工具定义约束，结构要落在 name / arguments 里 |
| 失败形态 | 多说一句话、少字段、类型错、非法 JSON，混在一段文本里 | 错误结构化，能定位到工具名、必填参数、调用标识 |
| 多轮对接 | 要自己设计回灌格式和调用对应关系 | 有专门消息角色与调用标识配套，天然对得上 |
| 模型能力依赖 | 低，只要模型会照格式说话，跨模型通用 | 高，依赖模型对原生工具调用的对齐支持，小模型常弱 |
| 调试难度 | 靠打印原文猜模型多写了什么 | 结构化字段可直接落日志、重放、比对 |
| 校验/审计/重试/观测 | 都要自己在 parser 外面补一层 | 可挂在协议字段上，锚点现成 |
| 迁移成本 | 低，换模型改改提示词即可 | 偏高，工具定义与响应格式由厂商定义，换供应商要调 |
| 起步成本 | 极低，起步快 | 要先定义工具、接消息角色、搭宿主执行循环 |

表里有两处最常被追问。一是格式自由度：JSON 方案能让模型吐任意形状的结果，做复杂嵌套抽取时反而灵活；原生方案的结构被工具定义框住，想多带一层字段都得改 schema。二是模型能力依赖：原生工具调用要靠模型做过相应对齐，一些开源模型或小尺寸模型支持得弱，这时候硬上原生，效果未必比精心调过的 JSON 提示词好。

### 按任务选型

把维度落到具体任务上，判断就清楚了：

| 任务形态 | 推荐 | 判断依据 |
| --- | --- | --- |
| 从一段文本抽城市、日期、金额等固定字段 | 结构化输出，退而求其次用 JSON + parser | 不需要工具语义，结构固定，schema 能兜住 |
| 分类、打标、情感判断，结果只是个标签 | JSON + parser | 输出极轻，解析成本可以忽略 |
| 把结果写进业务表单，字段多且要校验 | 结构化输出 | 需要机器可校验的 schema，别靠提示词描述字段 |
| 查天气、查订单、调下游 HTTP 接口 | 原生 Function Calling | 有真实执行，需要工具名、参数校验、结果回灌 |
| 多步编排、一次多个调用、带写操作 | 原生 Function Calling | 依赖调用标识、消息角色、幂等与失败分类 |
| 平台不支持原生工具调用，或模型对齐弱 | JSON + parser 做稳 | 先把兜底链补齐，别硬套不成形的原生能力 |

这张表可以直接背下判断口径：看有没有副作用和真实执行。只产出数据、不触发动作，轻量方案够用；要触发动作、结果还要回到模型继续推理，就上原生契约。中间那条「平台不支持」是现实里很常见的约束，下面工程实践整段都在讲怎么把它做稳。

### JSON 方案最常见的输出毛病与兜底

纯 prompt 方案的麻烦基本集中在这几类，见过线上日志就都眼熟：

| 模型输出毛病 | 触发时的样子 | parser 侧兜底动作 |
| --- | --- | --- |
| 前后多说一句话 | 「好的，结果如下：」+ 一段 JSON | 截取首个 `{` 到末个 `}`，或提示词里禁解释 |
| Markdown 围栏 | 被 ```json ... ``` 包起来 | 正则剥掉围栏再解析 |
| 少字段 | 漏了 `city`，或该必填的没给 | schema 校验捕获，回灌重试或向用户澄清 |
| 类型写错 | `"temp": "22"` 本该是数字 | 安全强转，转不了算校验失败，不让脏值流下去 |
| 非法 JSON | 尾逗号、单引号、中文引号、注释 | `json.loads` 兜底失败就重试，绝不用 `eval` |
| 多包一层 | 该给对象，给了 `{"result": {...}}` | 约定取值路径，或回灌让模型按结构改 |
| 对象数组混淆 | 该给对象却给了数组 | schema 校验直接拒绝，别在下游到处判类型 |

最后两行最容易被忽略：解析成功不等于数据可用。`json.loads` 过了只说明它是合法 JSON，字段对不对、类型对不对是另一道关，两道都要过。还有一条安全底线，模型输出永远别用 `eval` 去「解析」，那等于把一段不受控文本当代码执行，遇到提示词注入直接出事。

## 工程实践：把弱的那种做到能上线

### 一条稳健的 JSON 兜底链

平台没有原生能力时，JSON 方案不是不能上生产，是要把兜底补齐。下面这段是常见做法的骨架，变量都有定义，`retry` 由调用方注入，负责把错误要求拼进提示词再让模型重生成：

```python
import json, re
from pydantic import BaseModel, ValidationError

class WeatherArgs(BaseModel):
    city: str
    date: str | None = None

FENCE = re.compile(r"```(?:json)?\s*(.*?)```", re.S)

def extract_structured(raw, retry, max_retries=2):
    # retry(plan_text) -> 模型按修正要求重生成的原始文本；重试 2～3 次为经验值
    for attempt in range(max_retries + 1):
        fenced = FENCE.search(raw)
        payload = fenced.group(1) if fenced else raw
        payload = payload[payload.find("{"): payload.rfind("}") + 1]
        try:
            data = json.loads(payload)
        except json.JSONDecodeError:
            raw = retry("上次不是合法 JSON，只输出 JSON 对象，不要解释和代码围栏")
            continue
        try:
            return WeatherArgs.model_validate(data)   # Pydantic v2 按 schema 校验
        except ValidationError as e:
            raw = retry("字段不合法：%s，按 schema 补齐后只输出 JSON" % e.errors()[0]["msg"])
    return None   # 超限降级：转人工或返回固定兜底结构
```

几个点值得说清。剥围栏和掐首尾大括号是两道，只做一道都会在另一类输入上翻车。`json.loads` 抛的是 `json.decoder.JSONDecodeError`，报错常是 `Expecting value: line 1 column 1 (char 0)`，基本就是模型在 JSON 前面多说了一句；`model_validate` 抛的 `ValidationError` 会指明哪个字段缺了或类型不对，正好拿去拼重试提示。重试次数控制在 2～3 次是经验值，再多就是烧 token 换不确定收益，超了直接降级比反复重试更可控。配这类链路时把采样温度压到 0～0.2（经验值），也会少掉很多自由发挥。

### 原生侧的三档请求字段

对照看原生这边，结构化输出和工具调用在请求体上差什么。先是不带工具语义、只保证贴合 schema 的写法：

```json
{
  "model": "gpt-4o",
  "messages": [{"role": "user", "content": "从订单备注里抽出城市和日期"}],
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "order_fields",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}, "date": {"type": "string"}},
        "required": ["city", "date"],
        "additionalProperties": false
      }
    }
  }
}
```

这里 `strict: true`、`required` 列全字段、`additionalProperties: false` 是配套要求，不是随便塞个 schema 就能保证贴合；支持的 schema 关键字也有范围，复杂嵌套得按接口规则写。同族的 JSON mode 是 `response_format: {"type":"json_object"}`，只保证吐出来是个合法 JSON 对象，字段和类型照样不保；常见实现还要求系统提示里同时出现 JSON 字样，否则可能直接报错。这三档别记混。

换成真要调工具，请求体里的 `response_format` 让位给 `tools` 和 `tool_choice`：

```json
{
  "tools": [{
    "type": "function",
    "function": {
      "name": "create_order",
      "description": "按城市和日期创建订单",
      "parameters": {
        "type": "object",
        "properties": {
          "city": {"type": "string"},
          "priority": {"type": "string", "enum": ["normal", "urgent"]}
        },
        "required": ["city", "priority"],
        "additionalProperties": false
      }
    }
  }],
  "tool_choice": "required"
}
```

`enum` 把优先级这个参数锁死在两个取值里，`tool_choice: "required"` 强制这轮必须产出工具调用，用来做「只抽取不闲聊」的场景很顺手。这些字段把格式约束写进了请求，是纯 prompt 约定给不了的。见过有人把 `response_format` 和 `tools` 一起塞，指望着既自由又受约束，结果两边打架，选一档用就够了。

### 上线前要盯的几个观测信号

不管走哪条路，都得有几个数值能看出链路在不在退化。解析成功率、schema 一次通过率、重试触发占比、降级占比这四个最实用：一次通过率往下掉，多半是提示词里的示例和真实输入分布偏了；重试占比突然抬高，常见是新模型版本对格式没那么听话；降级占比不为零，说明有一部分请求始终兜不住，得回头看是不是该换档位。这些是观测口径，不是拍脑袋的目标值，阈值按自己业务定。之前聊过给调用链路埋 trace 字段，把这四个量挂上去，换模型、改提示词前后一对比，回归一眼就能看出来。

## 追问逐条作答

### 追问一：什么时候 JSON + parser 已经够用？

三条同时满足就够用：输出只是数据、不触发任何外部动作；结构比较轻，字段少或能靠一个 schema 兜住；平台原生能力有限，或者要跨好几个模型保持一致。典型是从文本里抽几个字段、给内容打标签、把一次分类结果写成固定结构。这类任务里，模型多说一句话的代价只是多一次重试，不会有扣款、写库、发消息这种副作用，程序端兜得住。反过来，只要结果要被拿去执行、要回灌给模型继续推理、或字段错了会污染下游，就别停在 JSON + parser，往上走一档。判断口径就一句：看有没有真实执行和副作用。

### 追问二：为什么 Function Calling 更适合接生产系统？

四个理由，都跟「契约」有关。一是结构由接口保证，工具名、参数、必填字段随请求下发，少了事后猜文本的一环；二是错误结构化，参数错、无权限、超时、结果和调用对不上，能分开定位和处理，而不是在一大段文本里找；三是工程配套现成，专门的消息角色和调用标识让多轮回灌、审计、重试、观测都有锚点，校验挂得上、日志落得下；四是工具定义集中在请求里，改一个 schema 不用满世界改提示词模板。代价是绑定具体接口、换供应商要调工具定义，但接生产系统时，省掉的解析和兜底工作远大于这点迁移成本。

### 追问三：如果平台没有原生 Function Calling，怎么尽量把 JSON 方案做稳？

按前面那条兜底链补齐，五件事缺一不可。第一，提示词里给足 few-shot、写死「只输出 JSON、不要解释」，把采样温度压低。第二，parser 分层：先剥 Markdown 围栏、掐首尾大括号，再 `json.loads`，再用 Pydantic 这类 schema 校验，两道关都过才算数据可用。第三，失败结构化回灌，把「不是合法 JSON」或「缺了哪个字段」拼进重试提示，让模型有机会自己修，重试限 2～3 次。第四，超限要有降级出口，转人工或返固定兜底结构，别拿空值让模型自由发挥。第五，把解析成功率、重试率挂到观测上，改提示词前后做回归。补完这五件，纯 JSON 方案接轻量抽取是能上线的；但要老实承认，涉及副作用和多工具编排时，这套模拟出来的契约仍不如原生协议牢靠。

### 追问四：JSON mode、结构化输出和 Function Calling 是同一回事吗？

不是，是同一条阶梯上的三档。JSON mode 只保证输出是合法 JSON 对象，字段和类型不保证，还得在提示词里同时提 JSON；结构化输出在它之上加了 `strict` 的 schema 约束，保证结果贴合给定字段，适合字段固定的抽取和打标；Function Calling 再往上加了工具语义，产出的是「调哪个工具、传什么参数」，配套消息角色和宿主执行契约。三者交叠在「结构化」，区别在保证到哪一层、有没有工具语义。面试里能顺手把这三层排出来，比笼统答一句「都是输出 JSON」清楚得多。选哪一档，看的是任务需不需要执行，不是看哪个听起来高级。

### 追问五：用了原生 Function Calling，arguments 就一定合法吗？

不一定，这是最容易答偏的一处。原生方案保证的是「结构存在且字段规整」，比如 `tool_calls` 这个字段一定在、工具名一定是个字符串、`arguments` 一定给到了；但 `arguments` 本身在常见实现里是一段 JSON 字符串，反序列化出来仍可能缺必填字段、类型不对、或填上模型自由发挥的额外字段。协议保证的是信封，不是信封里的内容完全合规。所以宿主侧那道参数校验不能省：拿工具 schema 对着解析出来的字典过一遍，缺必填、类型不符就回灌一条带错误说明的结果让模型修，别直接拿去 `fn(**args)` 硬调。之前拆五步链路时把「执行在宿主」讲过，这里补的是另一面：连原生协议也只保证到结构这一层，校验仍得自己兜。

### 追问六：换模型供应商时，两种方案各要改什么？

差别正好落在迁移成本这一栏。JSON + parser 的耦合点只有提示词和程序端那份校验规则，换模型主要调 few-shot 和措辞，因为不同模型对格式要求的服从度不一样，schema 校验那层通常不用动，跨供应商几乎无痛。原生 Function Calling 的耦合点更多：工具定义的写法、响应字段的结构、消息角色的命名、流式分片怎么拼，都由厂商定义，换一家往往要重写适配层，甚至 `arguments` 是字符串还是对象这种细节都不一样。所以工具一多，很多团队会在宿主和模型之间垫一层薄适配，把各家差异收在适配器里，业务侧只认一套内部调用结构。这是工程判断，不是接口自带的能力。顺带一提，支持原生工具调用的强弱也随模型变，小模型对齐弱的时候，精心调过的 JSON 提示词未必更差，别迷信「原生一定更好」。

### 追问七：怎么判断一条 JSON 解析链路够不够稳？

别只看「能不能解析出来」，要看四个量在一段时间里的走势：一次就通过 schema 校验的比例、触发重试的比例、最终降级的比例、以及降级请求里能归因到哪类毛病的分布。一次通过率高且稳，说明提示词和真实输入对得上；重试率慢慢抬高，多半是模型版本或输入分布变了；降级率不为零，就要看那部分是不是集中在某类结构上，能收敛就改提示词或 schema，收敛不了就说明这个任务该换档位了。再补一刀，把失败样本按前面那张毛病表分个类，看是「多说一句话」这类好兜的，还是「字段语义错」这类 parser 根本兜不住的，后者靠重试解决不了。这套判断对原生链路一样适用，只是原生那边错误本来就是结构化的，归因成本更低。

## 60 秒面试回答模板

> 两者都让模型吐结构化结果，区别在约束放在哪一层。输出 JSON 是 Prompt 层的约定，靠模型自觉，格式错了程序端只能事后校验和兜底；Function Calling 是接口层的契约，工具定义、参数 schema、消息角色都是协议的一部分，结构由接口保证，错误能定位到工具名和字段。所以抽字段、打标签这类不触发动作的任务，JSON 加 parser 起步就够；一旦要接真实工具、外部编排、带副作用的执行，就上原生 Tool Use，校验、审计、重试、观测都能挂在协议字段上。两个点别漏：原生也只保证响应结构，arguments 解析出来仍要按 schema 校验；换供应商时 JSON 只改提示词，原生得动适配层。

## 加分项

- **把二选一拆成能力阶梯**：纯 prompt 约定、JSON mode、结构化输出、Function Calling 四档，每档说清保证到哪一层，比只答两种方案更显层次。
- **点到约束前移**：稳定性差距的根因是约束从事后校验挪到生成阶段，不是「模型更听话」，这句话能看出你理解的是机制不是现象。
- **主动划清概念边界**：结构化输出不等于工具调用，Function Calling 不等于 MCP，一个是输出协议一个是连接协议，别混着答。
- **承认原生的边界**：原生协议保证的是信封，`arguments` 反序列化后仍要校验；也能指出小模型对齐弱时原生未必占优，这种不吹的判断面试官更信。

## 常见误区

- **把两者当成同一回事，只差一个 API**：一个是提示词约定，一个是接口契约，失败由谁兜底、能不能接副作用完全不同。
- **以为解析成功就等于数据可用**：`json.loads` 过了只说明是合法 JSON，缺字段、类型错还得靠 schema 校验拦，两道关都要过。
- **用了原生就省掉参数校验**：`arguments` 是字符串，解析出来照样可能不合规，校验放宿主这层不能省。
- **拿 `eval` 去解析模型输出**：等于把不受控文本当代码执行，遇到提示词注入直接出事，老老实实用 `json.loads` 加 schema 校验。
