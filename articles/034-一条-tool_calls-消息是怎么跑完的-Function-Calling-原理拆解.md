# 一条 tool_calls 消息是怎么跑完的？Function Calling 原理拆解

## 面试官为什么爱问这题

这题考的不是你会不会调 API，而是你有没有把"模型"和"程序"的职责分清楚。很多人用了半年 Function Calling，还以为工具是模型自己去执行的，一问"鉴权在哪做、超时谁负责、参数错了谁兜底"就答不上来。面试官要听的是你把一条消息从发出到回来的整个过程能不能讲清楚：工具定义怎么进去、意图怎么出来、谁真正执行、结果怎么回灌。这五步里但凡有一处理解错了，线上出了问题你就定位不到该改模型还是改代码。

## 一句话先给结论

**Function Calling 的核心分工只有一句：模型负责决策，程序负责执行。模型返回的 `tool_calls` 只是"调哪个工具、传什么参数"的结构化意图，不是它真的调了 API；真正的鉴权、参数校验、超时、幂等、重试和安全控制，全部在宿主程序这一层。**

## 核心原理：一条消息走完的五步

把一次带工具调用的请求按时间顺序摊开，就是下面这条链路。每一步都要说清"谁在做"。

### 第一步，宿主把工具定义发给模型

请求发出前，宿主程序先把每个工具的 `name`、`description`、参数 schema 一起塞进请求。注意这一步是**宿主做的**，模型看到的只是一段描述："有个叫 get_weather 的工具，接受 city 参数，返回天气"。模型并没有这个函数的代码，也不知道函数在哪台机器上。

工具描述在这里扮演的是"说明书"角色。模型靠 description 判断这个工具能不能满足当前需求，靠参数 schema 知道该填什么字段。之前聊过工具设计要名字清楚、schema 明确，那些原则的作用点就在这一步——描述写得含糊，模型要么乱调、要么该调不调。

### 第二步，模型返回 tool_calls 而不是最终答复

模型读完请求，做一个判断：这次要不要调工具？如果不调，它直接返回自然语言；如果要调，它返回一个结构化的 `tool_calls` 字段，里面写明调用哪个工具、参数是什么。

这里有个关键认知：**模型输出的始终是 token，所谓"结构化意图"也是它按约定格式生成出来的文本，只是被解析成了结构。** 它没有执行任何东西，只是填了一张"调用单"。填完这张单，它这轮的活就干完了，此时它给不出最终答复，因为还没有工具结果。

### 第三步，宿主读取 tool_calls 并真正执行

宿主程序拿到模型返回的消息，从里面读出 `tool_calls`（在常见的 SDK 里就是 `AIMessage.tool_calls`），这才是真正干活的开始：解析参数、校验合法性、查权限、找到对应的函数或 HTTP 接口、实际发起调用。

这一整步都是程序的行为，模型完全不参与。它不知道调用成功了没有、耗时多久、返回了什么。把这步记牢，就不会再说"模型调用了天气 API"——准确说法是"模型表达了调用天气工具的意图，宿主程序执行了它"。

### 第四步，结果封成 ToolMessage 回灌

工具执行完，宿主把结果封成一条 `ToolMessage`（或等价的消息角色）追加到对话里，再交给模型。这条消息要带上对应的调用标识（比如 `tool_call_id`），让模型知道这条结果是对哪次调用的回应——一次可能发多个工具调用，结果和调用要对得上。

### 第五步，模型基于结果生成最终答复

模型读到回灌进来的工具结果，这时才具备回答的依据，生成自然语言回复给用户。如果一次调用链有多轮，第二轮的答复里可能又产生新的 `tool_calls`，回到第三步继续循环，直到模型给出不带工具调用的消息为止。

这就是完整的五步。核心边界在第三步：所有"能不能调、参数对不对、失败怎么办"的问题，都属于宿主程序的职责，不属于模型。

### 为什么执行必须在宿主侧，而不是交给模型

这条边界不是设计偏好，是被三个硬约束逼出来的。第一是安全：模型是个推理服务，它没有你家数据库的账号、也没有第三方 API 的密钥，把执行权交给它等于把凭据暴露给一个会被 prompt 注入影响的对象。第二是状态：调用要读写业务库、要记账、要事务，这些都是有副作用的动作，必须跑在你可控、可回滚、有审计的服务里，模型那边一个无状态的推理端点承担不了。第三是确定性：鉴权规则、幂等策略、重试次数需要精确执行，而模型是概率性的，同样的输入不保证每次给出一样的行为，把这类规则交给它等于把一致性交给运气。

反过来看，模型擅长的恰恰是另一头：在模糊的自然语言里判断意图、从对话里抽出参数、在结果出来后组织成人话。它不适合的是精确、有副作用、要兜底的活。Function Calling 这条链路的本质，就是把一个概率性的决策模块和一个确定性的执行模块拼起来，中间用 `tool_calls` 这份结构化契约对接。想通这一层，很多设计选择就顺理成章了：为什么校验放宿主、为什么失败要回灌、为什么权限不能交给模型判断。

## 横向对比：三个角度看清这条链路

### 生命周期里每一步谁负责

| 步骤 | 谁执行 | 发生什么 | 出错时归谁 |
| --- | --- | --- | --- |
| 发工具定义 | 宿主 | 把 name / description / schema 塞进请求 | 描述写不清，模型乱调，改工具定义 |
| 产出 tool_calls | 模型 | 生成结构化调用意图 | 选错工具、参数填错，改描述或提示 |
| 执行工具 | 宿主 | 校验、鉴权、调用、超时、重试 | 权限、超时、幂等，全是代码问题 |
| 结果回灌 | 宿主 | 封成 ToolMessage 追加进对话 | 结果和调用对不上，改调用标识 |
| 生成答复 | 模型 | 基于工具结果说话 | 曲解结果、编数字，做输出校验 |

这张表里最该记的是第三列和第四列的对应：出问题时先看"这一步是谁的活"。模型选错工具，别去改后端的超时配置；工具超时了，也别去改 prompt。这条分工线是排查的起点。

### 原生 tool_calls 与"输出 JSON 自己解析"的基础区别

| 维度 | 原生 Function Calling | 让模型输出 JSON 再解析 |
| --- | --- | --- |
| 意图表达 | 模型按结构化字段产出，协议层约束 | 靠 prompt 要求模型吐 JSON 文本 |
| 解析可靠性 | 结构由接口保证，字段完整 | 可能带多余文字、少括号、字段缺失 |
| 多轮对接 | 有 ToolMessage 等消息角色配套 | 要自己设计回灌格式 |
| 失败处理 | 非法参数在宿主侧统一校验 | 解析失败也要自己兜 |

后有专篇专门拆这两种方案的取舍，这里只要记住一条：原生 Tool Calling 把"表达意图"这件事做成了协议的一部分，省掉了自己解析文本的一堆麻烦，所以生产环境更推荐它。至于两者更深的区别，放到后面单独讲。

### 工具执行失败的几种类型

| 失败类型 | 谁发现 | 处理方式 |
| --- | --- | --- |
| 参数不合法（缺字段、类型错） | 宿主校验时 | 不发起调用，把错误回灌让模型重试或澄清 |
| 无权限 / 工具不在白名单 | 宿主鉴权时 | 直接拒绝，返回固定错误结构，不暴露内部信息 |
| 超时 / 下游不可用 | 宿主调用时 | 按幂等性决定是否重试，超限返降级结果 |
| 结果模型读不懂 | 输出层 | 归一成约定结构再回灌，不塞原始返回 |

## 工程实践：把五步落成真实消息

### 一条完整的消息序列

下面用近似 OpenAI 风格的写法展示一次调用从头到尾的消息形态，变量值都是示例。

```json
// 1) 请求里带上工具定义
{
  "messages": [{"role": "user", "content": "北京今天天气怎么样"}],
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_weather",
      "description": "查询指定城市的当日天气",
      "parameters": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"]
      }
    }
  }]
}

// 2) 模型返回的是调用意图，不是答复
{
  "role": "assistant",
  "tool_calls": [{
    "id": "call_abc123",
    "function": {"name": "get_weather", "arguments": "{\"city\": \"北京\"}"}
  }]
}

// 3) 宿主执行后，把结果封成 ToolMessage 回灌
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"temp\": 22, \"condition\": \"晴\"}"
}
```

注意 `arguments` 是个**字符串**（内容是 JSON），不是直接的 JSON 对象，宿主拿到后要先反序列化。这就是为什么第三步必须做参数校验：字符串解析出来可能是缺字段的、类型不对的，甚至是模型自由发挥出来的字段。`tool_call_id` 把回灌结果和那次调用绑定，多工具并发时才不会串。

### 流式返回下的 tool_calls

上面的消息序列是"一次性返回"的理想形态，实际聊天产品多用流式：模型的输出是一个 token 一个 token 推过来的，工具调用也一样是逐步成形的。这带来一个处理细节——流式过程中，`tool_calls` 是分片到达的，参数字符串可能这半句只来了 `{"city": "北`，下半句才补齐 `京"}`。宿主必须按分片序号把同一轮调用的内容拼起来，等流结束、结构完整了，再做反序列化和校验，不能在流中间就急着执行。

常见的坑有两个。一是把流式过程中每一次增量都当成一次完整调用，结果同一个工具被执行了好几遍，参数还是残缺的；二是并发多个工具时，不同调用的分片交错到达，没按调用序号归类就拼，把 A 工具的参数拼到 B 工具上。稳妥的做法是按调用序号各自维护一个累积缓冲区，流结束后逐条校验再执行。这也是为什么很多团队在流式场景下干脆先把整条消息收齐、再统一处理工具调用，牺牲一点首字延迟换正确性。

### 宿主执行循环的伪代码

```python
def run_once(messages, tool_specs, handlers, model):
    # tool_specs: 工具定义列表；handlers: {name: 可执行函数}，键集合即白名单
    ai = model.chat(messages=messages, tools=tool_specs)   # 第一、二步
    if not ai.tool_calls:
        return ai.content                                  # 没调工具，直接是答复

    for call in ai.tool_calls:                             # 第三步：宿主执行
        fn = handlers.get(call.function.name)
        if fn is None:                                     # 不在白名单，拒绝
            result = {"ok": False, "error": "tool_not_allowed"}
        else:
            args = parse_and_validate(call.function.arguments, fn.schema)
            if not args.ok:                                # 参数校验失败，不发起调用
                result = {"ok": False, "error": args.error}
            else:
                result = fn(**args.data)                   # 真正执行，含超时/重试/幂等
        messages.append({"role": "tool", "tool_call_id": call.id,
                         "content": to_json(result)})      # 第四步：回灌

    return run_once(messages, tool_specs, handlers, model)  # 第五步：带着结果再来一轮
```

这段伪代码把职责边界写得很直白：`model.chat` 只出现在"产出意图"和"生成答复"两处，中间的执行、校验、拒绝、回灌全是宿主代码。递归调用体现了多轮循环——只要模型还返回 `tool_calls`，就继续；返回自然语言才结束。生产版本还要加最大轮数和超时预算，防止不收敛，之前聊循环和停止条件时讲过，这里不重复。

## 追问逐条作答

### 追问一：Function Calling 和文本解析调用有什么区别？

最常见的差别在可靠性。原生 Function Calling 由接口约束模型按结构化字段输出，工具列表、参数 schema 都是协议的一部分，宿主拿到的是规整的调用意图；而"让模型输出 JSON 再自己解析"完全靠 prompt 约定，模型可能带上解释文字、漏字段、写错引号，解析失败要自己兜。另外原生方案有 ToolMessage 这套消息角色配套，多轮回灌天然对得上；纯文本方案得自己设计回灌格式。生产里更推荐原生，就是因为它把这些脏活收进了协议。两者还有格式自由度、模型能力依赖、调试难度上的分歧，后面有专篇单独拆，这里先把"协议保证 vs 文本约定"这条主线记住。

### 追问二：为什么生产环境更推荐原生 Tool Calling？

三个理由。一是结构可靠，减少因为模型多写一句话就把 JSON 解析崩掉的事故；二是生态配套，消息角色、多轮对接、流式返回都有现成约定，不用自己造；三是可维护性，工具定义集中在请求里，改一个工具的 schema 不用满世界改 prompt 模板。反过来说，原生方案也不是没有代价——它绑定具体模型接口，格式由厂商定义，换供应商时工具定义可能要跟着调。但综合下来，省掉的解析和兜底工作远大于这点迁移成本，所以生产更推荐它。

### 追问三：工具执行失败怎么处理？

分清是谁的失败，再决定回灌什么。参数错、无权限这类宿主校验阶段就能发现的，不要发起调用，直接把明确的错误结构回灌给模型，让它要么纠正参数、要么向用户澄清；超时和下游不可用按幂等性决定要不要重试，查询类通常幂等可重试，写操作要带幂等键防止重复扣款；重试仍失败就返回降级结果，并在结果里带状态标记，让输出层知道该说"暂时查不到"，而不是让模型拿空结果自由发挥。核心原则：失败要显式送回给模型，不能吞掉一个空值假装成功。之前讲工具设计强调"可失败、失败信息写进描述"，落到实处就是这套回灌机制。

### 追问四：arguments 解析出来缺字段或类型不对，怎么办？

别直接 `fn(**args)` 硬调，那会把一个 `TypeError` 抛到链路上。宿主要有一层校验：拿工具的 schema 对照解析出来的字典，缺必填、类型不符都算校验失败，回灌一条带错误说明的 ToolMessage，让模型有机会自己修。这里有个边界要拿捏——是让模型自动重试填补，还是向用户澄清，取决于错误是不是"信息本来就缺"。比如城市名没给，模型再怎么重试也变不出来，就该反问用户；城市给成了数字类型，模型能自己改成字符串，可以自动重试。

### 追问五：一次返回多个 tool_calls，要并行执行吗？

看有没有依赖。互不依赖的调用可以并发发，总延迟取最慢的那个；有依赖的只能串行，因为后一个的参数要靠前一个的结果。并发时要注意每个结果都带上自己的 `tool_call_id`，回灌时才能对上。还有个坑：并发放出去的调用如果部分成功部分失败，要分别回灌各自的成败，不能一个失败就把整批结果丢掉重来——那会让已经成功的写操作重复执行。

### 追问六：工具定义每次请求都要带上吗，token 成本怎么考虑？

通常每次都得带，因为模型是无状态的，请求里不带它就没有工具信息。工具多、schema 长的时候，这部分确实吃 token。工程上的优化有两条路：一是按需下发，按当前意图只把相关工具的 definition 放进请求，而不是一把全塞；二是精简 description，把冗长说明挪到系统提示或文档里，工具描述只留模型判断"调不调、怎么填"必需的信息。注意别为了省 token 把描述删到模型看不懂，那是捡芝麻丢西瓜。

### 追问七：ToolMessage 里要不要告诉模型"调用失败了"？

要，而且要说清楚。模型只能看到回灌进来的 ToolMessage，它不知道底层发生了什么。如果你回灌一个空字符串或泛泛的"失败"，模型可能自己脑补一段内容。正确做法是把失败的结构化原因写进 content，比如 `{"ok": false, "error": "timeout"}`，让模型明确知道这次没成功，从而选择重试、换工具或告知用户。这也是为什么前面强调结果要封成固定结构——成功失败都用同一套 schema，模型才好判断。

## 60 秒面试回答模板

> Function Calling 的核心是模型负责决策、程序负责执行，模型返回的 tool_calls 只是"调哪个工具、传什么参数"的结构化意图，不是它真的调了 API。完整链路五步：宿主先把工具的 name、description、参数 schema 发给模型；模型判断要不要调，要调就返回 tool_calls 而不是最终答复；宿主读取 tool_calls 真正执行函数或接口；把结果封成 ToolMessage 回灌；模型基于结果生成答复。

> 关键边界在第三步：鉴权、参数校验、超时、幂等、重试和安全控制全在宿主这一层，模型不参与。所以 Function Calling 只解决"模型怎么表达调用意图"，不解决工具是否安全、是否允许、失败怎么兜底，那些都是程序的活。生产更推荐原生 Tool Calling，因为结构由协议保证、配套消息角色齐全，比让模型输出 JSON 自己解析可靠得多。

## 加分项

- **点出 tool_calls 本质是 token**：说清"结构化意图也是模型生成出来的文本，只是被解析成结构"，比把它当成 API 返回值更深一层。
- **把边界落到具体项**：能逐条列出鉴权、校验、超时、幂等、重试、安全各在哪一层，说明你真接在线上过。
- **区分 intent 和 execution**：主动强调"模型不执行函数"，顺手划清它和 MCP 的关系（MCP 是另一套工具发现与连接协议），概念边界清楚。
- **给失败分类而非一句"重试"**：把参数错、无权限、超时、结果读不懂分开处理，是有工程经验的标志。

## 常见误区

- **以为模型自己调了 API**：这是最致命的误解。模型只产出调用意图，执行永远在宿主。答错这一点，后面全盘皆输。
- **把 Function Calling 当成函数执行机制**：它解决的是"模型怎么表达调用意图"，不解决工具安全、权限和失败兜底，那些是程序的职责。
- **arguments 拿过来直接执行**：不校验就 `fn(**args)`，缺字段类型错会直接抛异常，还会让模型有机会注入非预期参数。
- **失败就吞掉返回空**：用户看到的是模型拿空结果编出来的一段话，比明确报错更危险。失败必须结构化回灌。
