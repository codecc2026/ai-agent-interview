# 有了超长上下文模型，还需要 RAG 吗？

## 一句话先给结论

**长上下文不是 RAG 的替代品，更接近它的补充能力：窗口变大只改了「单次能装多少」这一个变量，而成本、权限、版本追溯、引用审计这四层约束一层都没变；所以多数企业场景仍然需要检索，只是检索的产物从「一堆碎片」变成了「值得精读的整节」。**

面试官为什么爱问这题？因为它是一道伪装成技术趋势题的选型题。答「RAG 过时了，全塞就行」的人，把容量当成了能力；答「RAG 永远需要」的人，又不敢承认边界在移动。真正想听的是三层拆分：**容量层**（装不装得下）、**经济层**（装不装得起）、**治理层**（该不该让他看见）。第 4 篇聊过 token 与窗口的工程含义，本篇接着往下走一步：窗口抬到百万级之后，选型的判断依据到底变了没有。

## 核心原理：变的只有一个变量

### 第一层：容量确实变大了，但知识总量更大

上下文窗口是单次请求的上限，系统提示、历史对话、检索结果、用户问题加起来不能超过它。按题库给出的经验口径，1 个中文字符大约 0.6 个 token，所以 128K token 大致相当于二十万级中文字符；百万级窗口也就是百万字量级。

问题在于，一个中型企业的制度文档、产品手册、工单历史、合同档案加起来，通常是千万字量级甚至更多（视企业规模，这里只作量级示意）。**窗口再大也是一个"单次上限"，而企业知识是"累计存量"，两者根本不是同一个量纲。**你不可能为了回答一句"报销标准是多少"，把整个知识库塞进一次请求——不是模型装不下，是这件事本身没有意义。

### 第二层：成本与延迟不是「贵一点」，是量级差

这一层最容易被轻描淡写。三个机制值得说清楚：

- **输入 token 直接决定计费和 prefill 计算量。**长度翻倍，注意力部分的计算量大致按平方增长（标准全注意力），KV 缓存占用按长度线性增长。所以"塞两倍"不是"贵两倍"这么温和。
- **长请求更快撞上配额。**模型服务通常按每分钟 token 数（TPM）限流，一个几十万 token 的请求会把额度吃掉一大块，高并发时表现为排队和 429，而不是"稍微慢一点"。这是容量规划问题，不是优化问题。
- **边际收益递减。**真正有用的证据往往只有几段，剩下的是噪声。而上下文一长，模型对首尾信息的利用通常好于中间部分，噪声越多，关键证据越容易被稀释。**"全塞"经常同时买到更贵和更不准。**

反过来看检索的账：一次 embedding 加一次近似向量检索，经验值在几十到数百毫秒（视索引规模与部署方式），而且**这个开销与知识库总量基本无关**——这正是它能扛住规模的原因。

### 第三层：窗口是个平面，治理是有结构的

这是最容易被忽略、也最能区分「做过 Demo」和「上过生产」的一层。

**权限。**窗口没有「按人裁剪」的能力。你不能把 A 租户、B 部门的文档一起塞进去，然后指望模型"别看那部分"。检索可以在 metadata 层做过滤，在候选进入上下文之前就把不该看的裁掉——这是结构性隔离，不是提示词约束。

**版本。**塞进去的是哪一版，事后无从追溯。RAG 的每个 chunk 带 doc_id、version、生效日期，文档更新时可以定位哪些向量需要增量重建，出问题可以回滚索引。

**引用。**业务方要的不是"答案听起来对"，而是"这句话出自哪份文件第几节"。检索链路能给出 chunk 级定位并回链原文；全塞进上下文时，模型给的"引用"是它自己复述的，你无法校验。

**所以更准确的说法是：长上下文解决的是"读得完"，RAG 解决的是"找得准、管得住、查得回"。**这是两个不同层次的问题，不存在谁替代谁。

## 横向对比：两条路的取舍

| 维度 | 全量塞进长上下文 | 检索后塞入 |
| --- | --- | --- |
| 可处理规模 | 受窗口硬上限约束 | 与库总量近似无关，只与召回条数有关 |
| 单次输入成本 | 随语料线性上升 | 只随召回条数上升 |
| 首 token 延迟 | prefill 长，明显变慢 | 多一次检索开销，但 prefill 短 |
| 噪声控制 | 全靠模型自己"忽略" | 检索、rerank、阈值可主动裁掉低分片段 |
| 权限与租户隔离 | 无天然隔离，只能靠提示词约束 | metadata 过滤，候选进上下文前就裁掉 |
| 版本与时效 | 塞哪版就是哪版，不可追溯 | doc_id / version 随 chunk 入库，可增量更新 |
| 引用可校验 | 模型复述，无法定位原文 | chunk 级定位，可回链原文 |
| 实现复杂度 | 低（拼字符串） | 高（解析、切块、索引、rerank、增量更新） |
| 调试难度 | 难：错了分不清是没看到还是没用好 | 可分「检索」「生成」两段分别定位 |

这张表的读法不是"RAG 全面胜出"。前两行和最后一行，长上下文是明显赢的——尤其实现复杂度和调试成本，全塞在原型阶段几乎无成本。真正的判断要落到场景上：

| 场景 | 更适合 | 理由 |
| --- | --- | --- |
| 单份两三百页合同 / 财报精读 | 长上下文 | 语料一次性、无权限差异、要通读跨章节推理 |
| 多份文档对比、会议纪要整合 | 长上下文 | 需要全局视野，检索容易漏掉"没被问到但相关"的段落 |
| 万人规模制度问答、多部门权限 | RAG 为主 | 权限必须结构性隔离，且语料远超窗口 |
| 客服 FAQ、高频重复提问 | RAG 为主 | 单次成本乘以查询量，量级差会被放大 |
| 代码库问答 | RAG + 长上下文 | 检索定位文件与符号，再把整文件读进去 |
| 必须给出处、要审计留痕 | RAG 为主 | 引用要能回链到原文片段 |
| 数百份文档的跨文档归纳 | RAG 缩圈 + 长上下文精读 | 先筛到十几份，再整份读 |

判断口诀可以简化成四个条件：**语料在窗口内、权限单一、调用低频、不需要出处**。四条同时满足，才轮到"可以不用 RAG"；只要踩中两条以上（海量、多租户、高频、要审计），检索就是基础设施，不是可选项。

## 工程实践：成本账怎么算，链路怎么接

### 先算一笔量级账

面试里说"长上下文贵很多"是没信息量的，给倍数才有。假设某知识库 50 万 token（约八十多万中文字），按全量塞入与检索后塞入各算一次：

| 口径 | 单次输入 token | 相对倍数 |
| --- | --- | --- |
| 全量塞入 | 约 50 万 | 50× |
| 检索 20 条 × 500 token | 约 1 万 | 1× |

（表中为示例量级测算，不是厂商报价，用来说明数量级差异。）再乘查询频次：每天 1 万次请求，就是 50 亿 token 对 1 亿 token 的差别。**这个量级差不是"优化一下"能抹平的，只能靠架构选择。**

需要补一句公平的话：如果同一份长文档要被反复问，前缀缓存（prompt caching）能把稳定前缀的成本显著摊薄，这时候长上下文的账会好看很多。但缓存摊薄的是「重复读同一份」的成本，摊不掉「每次都读一份不同的全库」。

### 路由：先判断该走哪条路

不是所有请求都值得建检索链路。一个务实的入口判断：

```python
# 伪代码：按「语料规模 + 租户形态 + 调用频次」分流
def choose_path(corpus_tokens, tenant_count, daily_calls, need_citation):
    usable = 300_000                     # 可用窗口，已扣掉 system 与输出预留
    if need_citation:
        return "rag"                     # 要回链原文，只能走检索
    if corpus_tokens <= usable * 0.6 and tenant_count == 1 and daily_calls < 200:
        return "stuff_all"               # 低频一次性分析：全塞，省掉整条检索链路
    return "rag_then_read"               # 其余一律先缩圈，再精读
```

三个参数的用意：`corpus_tokens` 决定装不装得下，`tenant_count` 决定要不要做隔离，`daily_calls` 决定成本差是否会被放大。`need_citation` 是一票否决项——只要业务要求出处，就别省这一步。

### 接法：检索小片，回填整节

窗口变大真正改变的不是「要不要检索」，而是**检索的粒度**。以前窗口紧张，只能塞 300–500 字的碎片，答案常被切断；现在可以做「小块命中、大块阅读」：

```python
# 伪代码：small-to-big，命中细粒度 chunk，回填它所在的整节
# budget 取自上一节的 evidence 份额，不要写死
def expand(hits, budget, max_sections=6):
    sections, used = [], 0
    for h in sorted(hits, key=lambda x: -x["score"]):
        sec = load_section(h["doc_id"], h["section_id"])   # 取父级整节
        if sec["id"] in {s["id"] for s in sections}:
            continue                                       # 同一节只保留一份
        if used + sec["tokens"] > budget:
            continue                                       # 放不下就跳过，不硬截断
        sections.append(sec); used += sec["tokens"]
        if len(sections) >= max_sections:
            break
    return sections
```

这段的价值在于：**向量检索仍然在细粒度上做（保证命中精度），但送给模型的是语义完整的整节（保证可读性）。**这是长上下文与 RAG 结合最实用的形态，也是很多团队真正在用的做法。

### 预算与排布：塞不下时先砍什么

窗口再大也会满。预算分配和裁剪顺序要提前定好，否则线上就是一个 `context_length_exceeded` 然后整条请求失败。

```yaml
# 上下文预算分配（经验值，按任务微调）
context_budget:
  system_and_tools: 0.08
  history: 0.12          # 多轮场景才吃满，单轮可让给证据
  evidence: 0.65
  output_reserve: 0.15   # 给输出留位，别让生成被截断
```

超限时的裁剪顺序固定为：**先砍历史对话 → 再砍 rerank 分数最低的证据 → 最后才做摘要压缩**。顺序反了就是灾难：先压缩最关键的证据，等于把精度最高的信息糊掉，去保一段几轮前已经无关的闲聊。

排布上还有个小技巧：证据按分数降序，但把最强的两条分别放在**最前和最后**——首尾位置的利用率通常更高，中间放次优证据。同时在每条证据前加编号（`[1] [2]`），要求模型按编号引用，这样答案里的每句话都能回查到具体片段，也顺带压住了编造。

## 追问逐条作答

### 追问一：窗口都到百万级了，什么情况下你会真的不用 RAG？

四条同时满足我才敢不用：**语料在窗口内且相对稳定**（一份合同、一套财报、一份 PRD）、**单租户或无细粒度权限差异**（或权限已在入口处收口）、**低频一次性分析**（不是每天几万次问答）、**不需要回链出处**。少一条就要打折，少两条就老实上检索。这个答法的价值不在结论，在于你敢给出边界——只会说"都需要"的人，往往没真正做过成本决策。

### 追问二：那长上下文是不是只让 RAG 剩下「省钱」一个理由？

不止，而且省钱排最后。前三个是能力差异，不是成本差异：**权限**——窗口没有按人裁剪的能力，检索可以在候选进上下文前就把不该看的裁掉；**版本**——chunk 带 doc_id 与版本号，能增量更新、能回滚，全塞进去的文档事后查不清是哪一版；**引用**——检索给的是 chunk 级定位，可回链原文，全塞时模型给的引用是复述，无法校验。把这三条讲出来，比讲成本更有说服力。

### 追问三：成本到底差多少，你怎么算给面试官听？

三步：先估语料 token 量（中文字符数 × 0.6 左右），再估召回量（top_k × chunk 长度），两者相除得到单次倍数；最后乘日请求量得到总量级差。给一个具体例子：50 万 token 的库对 1 万 token 的召回，单次就是 50 倍，日万次请求就是接近两个数量级的差别。补一句公允的：如果同一份长文档被高频重复提问，前缀缓存能显著摊薄成本，但这摊不掉"每次读不同全库"的开销。

### 追问四：长上下文和 RAG 该怎么组合，才算接对了？

三种接法，各有适用面。**小块命中、大块阅读**（small-to-big）：细粒度检索保精度，回填父级整节保完整，最常用。**分段 map-reduce**：超长文档按章切，逐段抽取要点再汇总，避免一次性注意力稀释。**按需二次检索**：先给一个初步答案，发现证据不足再补检，适合多步推理。要避免的是"先检索一堆碎片，再全部塞进大窗口"——两头不讨好：既付了检索的复杂度，又付了长上下文的成本和噪声。

### 追问五：业务方坚持「全塞更简单」，你怎么说服他？

不谈架构，谈三件事。**成本量级**：把上面那笔账算给他看，乘以真实请求量。**权限风险**：问他一句"这份文档 F 部门的人不该看，你打算怎么保证模型不引用"，窗口方案答不上来。**效果实验**：挑二三十个真实问题，同一批问题分别用"全塞"和"检索后精读"跑，人工判分——很多时候全塞并不更准，因为噪声稀释了关键证据。一次 A/B 的说服力远大于架构争论。

### 追问六：证据塞进窗口之后，怎么排布才不容易被淹没？

四个动作：**控条数**——经验值 5～20 条，rerank 分数出现明显断层时，断层以下直接砍掉；**去重**——同一节的多个 chunk 只留一份，重复内容占位置还放大偏置；**首尾优先**——最强证据放最前和最后，中间放次优；**编号引用**——每条证据带 `[n]`，要求答案标注来源，既方便校验也抑制编造。这四条合起来，等价于把"长上下文"变成"高质量上下文"。

## 60 秒面试回答模板

> 我的判断是：多数场景仍然需要 RAG，因为「能塞进去」和「应该塞进去」不是一回事。长上下文改的只是一个变量——单次能装多少；但成本、权限、版本、引用这四层约束一层都没变。窗口是单次上限，企业知识是累计存量，两者不是一个量纲。

> 具体看：成本上，全量塞入和检索后塞入常差一到两个数量级，长请求还更容易撞 TPM 限流；治理上，窗口是个平面，没法按人裁剪，而检索能在 metadata 层做租户和角色过滤，还能带版本号、给 chunk 级引用。

> 所以我不会二选一，而是组合：检索负责缩圈和隔离，长上下文负责精读——小块命中、回填整节，让送进去的是语义完整的段落而不是碎片。判断能不能不用 RAG，我看四条：语料在窗口内、权限单一、调用低频、不需要出处，四条同时满足才可以。

## 加分项

- **把问题拆成容量／经济／治理三层**。一句话就把"技术趋势题"还原成"选型题"，比任何站队都有分量。
- **敢给「可以不用 RAG」的边界**。能说出四条前提的人，通常是真的做过成本决策，而不是只会背 RAG 流水线。
- **指出窗口变大改变的是检索粒度**（small-to-big）。这是长上下文给 RAG 带来的真实增量，多数候选人想不到这一层。
- **用倍数和口径谈成本**。"50 倍""日请求量乘上去差多少"比"贵很多"有信息量，而且顺手展示了你会算容量规划。

## 常见误区

- **把容量当能力**。"窗口有一百万 token 了，检索没用了"——忽略了噪声稀释、权限隔离和引用追溯都不在容量这一层。
- **把 RAG 只当省钱手段**。一旦只谈成本，面试官追问"那业务愿意多花钱是不是就该全塞"，就答不上来了；真正的护城河是治理能力。
- **先检索再全塞**。既没省下成本，又背上了检索链路的复杂度，是最常见的四不像。
- **只算单次成本不算频次**。单次差 50 倍看着能忍，乘以日请求量就是预算事故。
