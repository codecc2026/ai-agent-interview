# Tool、Function Calling、Agent 三者是什么关系？

## 面试官为什么爱问这题

这是工具与 Agent 这一章的开门题，考的不是背定义，是**概念拆分是否干净**。面试里最容易露怯的回答是把这三个词当同义词轮换着用——「我们用了 Agent 调工具」「Function Calling 就是让模型调 Agent」——说的人自己都没分层，后面再问怎么设计工具、什么时候不该上 Agent，答案必然乱。

这题还有个隐藏考点：能不能把「技术能力」和「运行模式」分开。Tool 和 Function Calling 是能力层面的东西，Agent 是系统怎么组织这些能力的模式。分不开的人会得出「接了 Function Calling 就是做了 Agent」这种结论，然后为一个只需要查一次天气的需求搭一整套循环。面试官想听的是你有没有那条边界感：什么时候一次结构化调用就够了，什么时候才需要让模型自己决定调几次。

## 一句话先给结论

**Tool 是能力单元，解决「能做什么」；Function Calling 是调用机制，解决「怎么发起一次结构化调用」；Agent 是把模型、工具、状态和决策流程组织起来的运行模式，解决「围绕目标多轮地决定要不要调用、调谁、调几次」。三者是三层，不是三个近义词——Tool 不等于 Agent，单次 Tool Calling 也不等于 Agent；只有任务需要多步规划、反复决策和状态推进时，Agent 才值得引入。**

## 核心原理：把三层拆开

### 第一层：Tool 是能力单元

Tool 就是「模型能调用的一个能力」。它可以是查数据库、发请求、读文件、下单——对模型来说，一个工具就是一段有名字、有输入参数、有返回值的可执行能力。这一层关心的是**能做什么**，跟谁发起调用无关。

一个容易混的点：Tool 和它的「实现」不是一回事。实现可以是 Python 函数、HTTP 接口、一段 SQL，但提供给模型的是**描述**——名字、用途、参数 schema。模型看描述决定要不要用，真正执行的是你的代码。所以工具有两面：面向模型的可理解性，和面向系统的可靠性（权限、超时、幂等）。

### 第二层：Function Calling 是调用机制

Function Calling 解决的是「怎么把模型的意图变成一次机器可执行的结构化调用」。它的工作过程是：你把工具列表连同用户问题一起发给模型，模型不直接回答，而是返回一段结构化的调用意图——调哪个工具、参数填什么；你的代码执行这个工具，把结果作为消息回灌给模型，模型再基于结果继续生成。

关键在**结构化**三个字。没有 Function Calling 时，让模型输出「请调用查天气工具，城市是北京」这种自然语言，你要写正则去抠，抠错一个字就跑偏。Function Calling 把这件事变成由模型按你给的 JSON schema 产出参数，字段、类型都在契约里，代码拿到就能执行。它是模型和你的程序之间的一次握手，一次往返。

常见错觉是把 Function Calling 当成「模型执行了函数」。模型从头到尾没执行任何东西，只产出「调什么、参数是什么」的结构化结果，执行永远在你的代码里。想通这点，安全归属就顺了：能否调用、参数校验、权限是谁的，责任都在执行侧，不在模型侧。

### 第三层：Agent 是运行模式

Agent 是把模型、工具、状态和决策流程组织起来的运行模式。它关心的是**围绕目标多轮地决定**：这一轮要不要调工具、调哪个、参数怎么填、拿到结果后是继续调下一个还是收尾回答。一次 Function Calling 是这循环里的一拍；Agent 是「观察—决策—调用—再观察」这个能跑很多拍的循环本身。

判断一个系统是不是 Agent，就看三件事在不在这：

- **多轮决策**：下一步动作不是写死的流程，而是模型根据当前状态现决定的。
- **状态推进**：有中间状态在积累——已经查到了什么、还差什么、试过哪些路径。
- **目标收尾**：有明确的停止条件，模型判断「够了」才结束循环，而不是调用完一个固定序列就停。

三样齐了才叫 Agent。缺了任何一样，多半是「带工具的流程」或者「一次工具调用」，不该硬往 Agent 上靠。

### 三层之间的关系

一句话串起来：**Tool 是可被调用的能力，Function Calling 是发起调用的那次结构化交互，Agent 是反复用这两者推进目标的循环。**

所以「Tool 不等于 Agent」很好理解——工具本身没有决策循环。「单次 Tool Calling 不等于 Agent」也成立——只调一次、返回结果、结束，没有多轮决策和状态推进。这个边界是这题的核心，讲清这两句就够了。

前面聊 Agentic RAG 时说过「Agent 是动态决策、Workflow 是固定编排」，那条线在这里同样适用：重点在「下一步由模型现场决定」，不在「用了几个工具」；固定编排里接十个工具，它还是 Workflow。

## 横向对比

三层各管什么，这张表是回答这题的主体：

| 维度 | Tool（能力单元） | Function Calling（调用机制） | Agent（运行模式） |
| --- | --- | --- | --- |
| 回答的问题 | 能做什么 | 怎么发起一次结构化调用 | 围绕目标多轮决定调什么、调几次 |
| 存在形态 | 描述 + 实现 | 一轮请求/响应的消息结构 | 带状态和停止条件的循环 |
| 谁在决策 | 无决策，被动可调用 | 模型在单次里选工具填参数 | 模型在每轮里决定下一步动作 |
| 状态 | 无 | 一次往返，无跨轮状态 | 有中间状态在积累 |
| 典型产物 | 一个查询接口、一个下单函数 | 一条 `tool_calls` 消息 + 一条工具结果消息 | 多轮消息序列 + 最终答案 |
| 单独能用吗 | 能，被程序直接调 | 能，做一次查询就结束 | 不能，必须挂在模型和工具之上 |

再看工程选型，什么需求该停在哪一层：

| 需求形态 | 停在哪层 | 理由 |
| --- | --- | --- |
| 确定流程：接了参数就查一次库返回 | Tool 或直接写代码 | 路径写死，不需要模型决策，连 Function Calling 都省了 |
| 一次选择：用户问天气，模型判断是否查、查哪个城市 | Function Calling | 只需要一次结构化调用，结果直接生成回答 |
| 多步不确定：排查问题要查日志、查配置、再决定查什么 | Agent | 路径依赖上一步结果，需要状态推进和多轮决策 |
| 固定审批流：每一步谁做、做什么都规定好 | Workflow | 确定性流程，给模型自由度只会引入不稳定 |

最后一组容易混的边界，单独列出来：

| 概念对 | 边界在哪 |
| --- | --- |
| Function Calling vs MCP | 前者是模型产出结构化调用意图的能力；后者是工具 discovery 与连接的开放协议，规定工具怎么被描述和挂载。一个是能力，一个是协议层的约定 |
| Tool vs Function Calling | 一个是可被调的能力本身，一个是发起调用的那次交互；工具可以在没有 Function Calling 时被程序直接调用 |
| Agent vs Workflow | 前者下一步由模型现场决定；后者步骤由人预先编排。两者都可以用工具 |

## 工程实践

### 一次 Function Calling 的消息长什么样

拿最常见的形态看（字段按主流 API 的通用写法，具体名称以你用的服务商为准）。先是第 1 轮，模型返回调用意图、不直接回答：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "query_order",
        "arguments": "{\"order_id\": \"SO-20261119-001\"}"
      }
    }
  ],
  "finish_reason": "tool_calls"
}
```

第 2 轮由你的代码执行工具后把结果回灌，`tool_call_id` 与上面那条对应：

```json
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"status\": \"shipped\", \"eta\": \"2026-11-21\"}"
}
```

这段有两个实操要点。其一，`arguments` 是字符串形式的结构化参数，执行前要解析并按 schema 校验，不能直接丢给下游；其二，`tool_call_id` 是串起调用和结果的钥匙，多工具并发时靠它区分谁是谁的返回，漏了模型下一轮就拿到对不上号的上下文。这两个坑单次调用里就会踩到，跟做不做 Agent 无关。

### 从单次调用到 Agent 循环

Agent 就是把上面那一轮包进循环里，加上状态和停止条件。伪代码：

```python
# 伪代码：带状态与停止条件的 Agent 主循环
def run_agent(goal, model, tools, max_steps=8):
    messages = [user_message(goal)]      # 状态：完整消息历史
    for step in range(max_steps):
        reply = model.call(messages, tools=tools)
        if reply.finish_reason == "stop":      # 停止条件一：模型判断任务完成
            return reply.content
        for call in reply.tool_calls:          # 执行本轮所有调用意图
            result = execute_tool(
                call.name,
                validate_args(call.arguments)  # 参数按 schema 校验后再执行
            )
            messages.append(tool_result(call.id, result))  # 结果回灌，推进状态
        messages.append(reply)
    return fallback(messages)                  # 停止条件二：步数上限兜底
```

两个停止条件缺一不可。模型自判完成是正常出口，但模型在循环里打转（同一个工具调三次、每轮都说「再查一次」）时得有个硬上限把流程截断——`max_steps` 就是防跑飞的护栏，经验值按任务复杂度取 5～15，简单查询类压到 3～5。没有这个上限，一次幻觉能把工具调用刷到几百次，账单和下游系统一起遭殃。

### 工具设计的粒度

这是从「会不会分层」进阶到「做得好不好」的分水岭。工具太细，模型要在十几个原子操作里选，选错概率和调用轮数一起涨；工具太粗，一个工具塞五六个功能，schema 复杂到模型填不对，出错时连哪一步出问题都定位不到。

一个能落地的判断标准：**按「模型需要做的业务决策」切，不按「系统的函数划分」切**。拿订单场景说，`query_order`、`refund_order` 是两个合理的工具，因为「查」和「退」是模型要做的不同决策；而把「查订单」拆成 `get_order_by_id`、`get_order_status`、`get_order_items` 三个工具，通常没有必要——模型要做的就是「查这个订单」，三次调用只增加出错点。反过来，把一个「查完还要判断能不能退、然后退」的大动作塞进一个工具，模型就失去了中途决策的机会，出了问题也不好解释。

描述字段同样要认真写：工具名和用途描述是模型选工具的唯一依据，写得含糊等同于让它猜。参数 schema 里该必填的标必填、该给枚举的给枚举、该写清格式的（时间、编号）写清——这些约束影响模型填参的正确率。

## 追问逐条作答

### 追问一：单工具助手算不算 Agent？

看那一个工具是不是被「决策」出来的，不看数量。如果用户问什么都要查同一个知识库、查完直接生成，工具是固定调用的，没有「要不要调、调几次」的判断，那它是带工具能力的 RAG 应用，不是 Agent——之前讲过权限过滤要放在检索前，那套流程里工具是流水线的一环。反过来，哪怕只有一个工具，但模型要判断「要不要查、查什么关键词、结果不够要不要换个说法再查」，有决策、有状态、有收尾判断，就具备 Agent 形态。答案就是：**工具数量不是判据，决策循环才是**。

### 追问二：ReAct 和 Function Calling 什么关系？

不在同一层，别放一起比大小。Function Calling 是一次结构化调用的机制，管的是「怎么把意图变成参数」；ReAct 是一种运行机制，管的是「推理和行动怎么交替推进」——它表现为 Thought、Action、Observation 的循环，模型先判断、再行动、再根据观察更新判断。两者能组合：用 Function Calling 来产出 ReAct 循环里的 Action 那一步，工具返回结果当 Observation，下一轮继续。也能不用：ReAct 的 Thought 和 Action 早期就是靠 Prompt 约束模型按格式输出文本实现的，不一定非要 Function Calling。所以准确说法是：**Function Calling 可以作为 ReAct 循环里行动环节的一种实现手段，不是 ReAct 本身**。至于 ReAct 的完整机制和它解决什么问题，明天专门展开。

### 追问三：Tool 设计的最小粒度应该是什么？

按业务决策切，不按代码函数切——这条判断标准上面讲过，这里补三个可操作的校验问题。第一，模型有没有可能只想要这个工具的一部分能力？如果有，说明切得太粗，该拆。第二，这个工具会不会几乎总是和另一个工具连着一起调？如果会，考虑合并成一个，减少模型的选择和调用轮数。第三，这个工具出错了，错误信息能不能让模型知道下一步该怎么调整？如果工具内部吞了错误、只返回「失败」，模型在循环里无从修正，工具边界要重新划，把可恢复的错误暴露成结构化返回。三问过完，粒度基本就稳了。经验上一个 Agent 挂 3～10 个工具比较容易驾驭，再多就该想想是不是把场景拆成多个 Agent 或用检索来发现工具了。

### 追问四：Function Calling 是不是等于让模型执行了函数？

不是，这是最需要当场纠正的误解。模型只产出结构化的调用意图——调哪个工具、参数是什么，它没有任何执行能力。真正的执行在你的代码里：解析参数、校验、调接口、把结果回灌。理解这一点，几个工程问题自然有答案：工具权限用谁的身份，是你的服务身份，不是模型的；参数要不要校验，必须校验，模型填错或恶意填都可能；工具报错谁兜底，你的执行侧兜底，然后决定是返回结构化错误让模型重试，还是直接截断流程。把「模型决策、程序执行」这条线画清楚，工具调用的审计、限流、权限问题就有了明确归属。

### 追问五：接了 MCP 是不是就等于有了 Agent？

两码事，这条边界面试里很值钱。MCP 解决工具怎么被描述、发现和连接——让不同提供方用统一协议把能力挂上来，省掉每个工具写一套适配，管的是「有哪些工具、怎么调通」，属于工具供给这一侧。Agent 管的是「要不要调、调哪个、调几次、什么时候停」，属于决策循环这一侧。一个接了 MCP 的应用可以完全没有 Agent：工具挂在那，程序按固定流程调用，一样跑；反过来，手工注册工具的 Agent 也成立。所以 MCP 是工具生态的协议层，不是运行模式。

### 追问六：怎么判断一个需求该不该上 Agent？

先问三个问题，有一个答「否」就别上。第一，路径是不是事先能枚举？能枚举就用 Workflow 写死，确定性流程给模型自由度只会引入不稳定。第二，下一步动作是不是依赖上一步的结果？不依赖的话一次调用或固定序列就够，不需要循环。第三，出错后要不要模型自己调整重试？如果错误由人兜底或走固定重试策略，也不用 Agent。三个都过了，再看成本账：Agent 的链路更长、每轮都带完整上下文，token 成本和延迟都随轮数涨（经验值：一轮多轮循环的耗时与成本通常是单次调用的若干倍，具体看工具延迟和上下文长度），调试也比固定流程麻烦。所以默认从最简单的形态起步——能直接写代码就写代码，需要一次选择就 Function Calling，确实要现场决策再升级到 Agent。

## 60 秒面试回答模板

> 我会把三个词拆成三层。Tool 是能力单元，解决能做什么；Function Calling 是调用机制，把模型意图变成一次结构化调用；Agent 是把模型、工具、状态和决策流程组织起来的运行模式，决定要不要调、调谁、调几次。所以 Tool 不等于 Agent，单次 Tool Calling 也不等于 Agent——判据是有没有多轮决策、状态推进和停止条件。工程上我不默认上 Agent：路径固定就写代码或 Workflow，一次选择用 Function Calling 够，只有结果依赖上一步、需要模型自己调整时才做循环。至于 MCP，那是工具怎么被描述和连接的协议，跟 Agent 不是一层。

## 加分项

- **开口先分层再举例**：把「能力单元 / 调用机制 / 运行模式」三个词先摆出来，后面所有论证都挂在这三层上，结构感一眼可见。
- **当场纠正「模型执行了函数」**：明确「模型产出意图、程序负责执行」，顺势带出权限、校验、审计都归执行侧，工程理解直接拉满。
- **给出 Agent 的三条判据**：多轮决策、状态推进、停止条件，把「是不是 Agent」从感觉题变成检查题。
- **默认从简单形态起步**：能写代码不调用、能单次调用不做循环，把成本意识放在概念题里讲，面试官很吃这套。

## 常见误区

- **把接了 Function Calling 当成做了 Agent**：一次结构化调用没有决策循环，是能力不是模式；这题的核心边界就在这，答错等于概念没分层。
- **把 MCP 和 Agent 混为一谈**：MCP 是工具发现与连接的协议，解决工具从哪来、怎么接；Agent 是决策循环，解决调什么、调几次。两个层面。
- **用工具数量判断是不是 Agent**：单工具也可能有完整决策循环，多工具的固定编排也可能只是 Workflow；数量不是判据，决策才是。
