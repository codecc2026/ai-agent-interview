# 如何设计 Agent 的完成判断与终止条件，避免过早结束？

<!-- growth-hook:v1 -->
“Agent 怎么知道任务做完了？”——靠提示词里写一句“完成后结束”是行不通的，多数过早结束都源于此。这题要你给出显式的完成条件，从任务、工具、状态到保护机制一层层立住。

## 面试官为什么爱问这题

这题高频且偏难，考的是终止条件设计和状态机思维。Agent"什么时候算做完"看着简单，实际是长链路里最容易出问题的地方——太早结束，把半成品返回给用户；该停不停，陷入无限循环。很多人只靠一个 Supervisor 节点判断完成率、或者看日志感觉差不多了，这两种都不靠谱。面试官想听的是你能不能设计显式的完成条件：分任务、工具、状态、保护四层，并且说清 Supervisor 该扮演什么角色。前面讲 Agent 执行闭环、Deep Research 迭代、工作流停止时都提过终止，这一篇把它作为专门主题讲透。

## 一句话先给结论

**Agent 的"结束"不能只靠感觉，也不能只看日志或一个宽泛的完成率分数，更稳的做法是设计显式的完成条件。终止逻辑拆四层：任务层看是否达成用户目标、是否拿到必须的产物或字段；工具层看关键工具调用是否成功、返回是否满足约束；状态层看 state 是否进入 done / failed / need_human 这样的终态；保护层设最大步数、超时、重复无进展次数、异常退出条件。Supervisor 更适合当辅助审查和异常兜底，不是唯一结束依据。只有关键任务结果、工具返回和状态机条件都满足，才允许进入最终答复节点，否则宁可继续、澄清或转人工。**

## 核心原理：四层终止逻辑

### 任务层：目标达成了吗

判断是否达成用户目标、是否拿到了必须的产物或字段。这是最根本的一层——任务本身的完成标准。比如用户要一份报告，那报告生成了没、关键章节齐了没；用户要查一个结论，那结论拿到了没。任务层的完成标准要在设计时就定义清楚，不能模糊。

### 工具层：关键调用成功了吗

看关键工具调用是否成功、返回结果是否满足预期约束。很多任务的完成依赖某个关键工具——查到了订单、写成功了数据库、调通了外部 API。工具没成功，任务就没真正完成，即使模型觉得自己答了。这一层把"完成"绑定到真实的执行结果上，而不是模型的自我感觉。

### 状态层：进入终态了吗

看当前 state 是否进入 done / failed / need_human 这样的终态。这是状态机思维——把 Agent 的执行建模成状态流转，只有进入明确的终态才算结束。done 是成功完成、failed 是失败、need_human 是需要人工接管。状态显式化后，结束判断就变成"当前状态是不是终态"，可观测、可控制。

### 保护层：兜住异常

设最大步数、超时、重复无进展次数、异常退出条件。这一层不是为了判断"完成了"，而是为了判断"不能再继续了"——任务可能永远达不到完成条件，这时候要靠保护层强制收口，防止无限循环和资源耗尽。前面讲 Agent 行为边界时说过熔断和预算，这里是它们在终止逻辑里的位置。

| 层 | 判断什么 | 作用 |
| --- | --- | --- |
| 任务层 | 目标达成、产物/字段齐全 | 根本的完成标准 |
| 工具层 | 关键工具成功、结果满足约束 | 绑定到真实执行结果 |
| 状态层 | state 进入 done/failed/need_human | 状态机终态判断 |
| 保护层 | 步数、超时、无进展、异常 | 强制收口，防失控 |

四层里前三层判断"是否完成"，保护层判断"是否必须停"。把它们混在一起会出问题——比如任务没完成但超时了，如果当成完成就误导用户；如果不当成完成又一直耗着。正确的做法是让保护层触发时进入异常终止，并在返回时如实说明任务进展到哪、因为什么停下。

| 结束方式 | 触发条件 | 对外怎么说 |
| --- | --- | --- |
| 正常完成 | 任务、工具、状态层都满足 | 给出完整结果 |
| 需要澄清 / 转人工 | 状态进入 need_human | 说明缺什么、请用户补充 |
| 异常终止 | 保护层触发（超时、步数、无进展） | 说明已做到哪、为何停止 |
| 失败 | 状态进入 failed | 说明失败原因，不冒充完成 |

### Supervisor 的定位：辅助审查和异常兜底

如果链路里有 Supervisor 或监督节点，题库强调它更适合当"辅助审查"和"异常兜底"，而不是唯一的结束依据。为什么？因为 Supervisor 本身也是一次模型判断——它可能判错、可能被误导、可能"感觉差不多了"就说完成。把结束全押在它身上，就回到了"靠感觉"的老路。

真正稳的方案是：只有当关键任务结果、工具返回和状态机条件都满足时，才允许进入最终答复节点。Supervisor 在这些硬条件之上再做一层审查，看有没有遗漏、有没有异常，发现问题时要求继续或转人工。它是加固，不是替代。

## 工程实践：一个显式终止条件的骨架

落到实现，把四层条件写清楚：

```python
# 伪代码：四层终止判断，全部满足才进入最终答复
def should_finish(state, task_spec, tool_results):
    if not task_layer_ok(state, task_spec):        # 任务层：目标和产物
        return "continue"
    if not tool_layer_ok(tool_results):            # 工具层：关键调用结果
        return "retry_or_continue"
    if state.phase not in TERMINAL_STATES:         # 状态层：done/failed/need_human
        return "continue"
    if protection.triggered(state):                # 保护层：步数/超时/无进展
        return "force_stop"
    return "final_answer"                          # 都在终态且满足条件

# task_layer_ok / tool_layer_ok / protection 为业务侧实现
```

要点：四层按顺序检查，只有前面都满足才走到 `final_answer`；保护层触发则强制停止。`TERMINAL_STATES` 是显式定义的终态集合。变量都是业务侧实现。这比"让 Supervisor 说一句完成了"可靠得多——每层的条件都可检查、可观测。

## 追问逐条作答

### 追问一：只靠监督节点统计完成率和查日志，为什么慢还容易误判？

因为那是事后统计，不是实时判断。监督节点靠完成率分数和日志去推断"是不是做完了"，一是滞后，要等统计出来才知道；二是间接，完成率高不等于这次任务真完成，可能只是大部分步骤跑了。模型"感觉完成"也可能漏了关键产物。这种判断既不及时也不精确，容易把半成品当成完成。

### 追问二：有没有更通用的判断方式，比如直接看关键工具调用结果和状态字段？

有，直接看关键工具调用结果和状态字段。这是比"监督节点打分"更硬的依据：关键工具成功了没、结果满足约束没、状态机进终态没——这些都是明确的、可检查的事实，不依赖模型的感觉。前面讲状态机思维时说过，把结束建模成状态流转，判断就变成"当前状态是不是终态"，清晰可控。通用的做法就是让这些硬条件成为终止的主依据，Supervisor 只做辅助审查。

### 追问三：如何避免任务没做完就提前返回？

把"进入最终答复节点"的门槛设成硬条件组合，任务层、工具层、状态层都满足才放行，缺一不可。只要有一层没满足，就继续、澄清或转人工，而不是让用户看到一个未完成的结果。经验值：尤其要盯工具层，很多"提前返回"是模型在关键工具还没成功时就自以为完成了；把关键工具的返回结果作为放行的必要条件，能挡住大部分这类问题。

### 追问四（自补）：保护层触发算不算"完成"？

不算，它是"强制收口"，和正常完成要区分开。任务达到完成条件是成功结束；保护层触发（超步数、超时、重复无进展）是异常终止——系统不能再继续了，但任务未必完成。返回给用户时要如实说明：是完成了，还是因为达到上限而停止、当前进展到哪。把强制停止当成完成，等于用"停下来"冒充"做完了"，是误导。

### 追问五（自补）：need_human 这种终态怎么触发？

当任务需要人的判断或授权时触发，比如遇到不可逆动作要审批、关键信息缺失要用户澄清、模型连续判断不了要人工接管。它在状态机里是一个明确的终态：Agent 停止自主推进，把控制权交给人。设计时要定义清楚什么情况进入 need_human、进入后怎么恢复，也就是人处理后是继续任务还是终止，要有明确流程。前面讲人工审核点和行为边界时说过这些，这里把它们建模成状态机的一部分。

### 追问六（自补）：怎么避免"重复无进展"却一直跑？

要能识别"无进展"。做法是给每个关键状态留指纹，包括当前产物、待办、关键字段，每轮结束比一比：如果和上一轮几乎没变化，就是在原地打转。连续几轮无进展就触发保护层，强制收口或转人工，而不是继续耗下去。经验值：无进展的判断别只看"有没有输出"，要看输出有没有实质推进，模型可能每轮都生成一段话，但内容翻来覆去，那也是无进展。前面讲成本排查时提过盲目重试浪费钱，这里是从终止条件侧给出同样的防线。

## 60 秒面试回答模板

> 我不靠感觉或完成率分数判断结束，而是设计显式的完成条件，分四层。任务层看有没有达成用户目标、产物和字段齐不齐；工具层看关键工具调用成功没、返回满不满足约束；状态层看 state 有没有进入 done、failed、need_human 这样的终态；保护层设最大步数、超时、重复无进展和异常退出，防止无限循环。如果有 Supervisor，我把它当辅助审查和异常兜底，不是唯一结束依据——因为它本身也是模型判断，会误判。只有任务结果、工具返回、状态机条件都满足才允许进入最终答复，否则继续、澄清或转人工。保护层触发是强制收口，不算完成，要如实告诉用户当前进展。

## 加分项

- 用四层终止逻辑搭框架，层次清楚、可检查。
- 点出 Supervisor 是辅助审查不是唯一依据，避免"靠感觉"。
- 引入状态机终态思维，把结束判断显式化。
- 区分正常完成和保护层强制收口，不把停止当完成。

## 常见误区

- **靠完成率和日志判断结束**：事后统计、间接推断，滞后且易误判。
- **把 Supervisor 当唯一依据**：它也是模型判断，会"感觉完成"而漏项。
- **把强制停止当完成**：超时停权是收口，不是做完了，要如实说明。
