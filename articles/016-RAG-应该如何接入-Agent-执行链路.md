# RAG 应该如何接入 Agent 执行链路？

## 面试官为什么爱问这题

很多候选人的简历上写着「RAG + Agent」，但一问细节就露馅：RAG 是怎么接到 Agent 里的？回答往往是「用户问题进来，先检索一遍，把结果塞进 prompt 再让模型回答」。这等于把 RAG 当成了一条固定的前置流水线，Agent 只是个「会说话的壳」。面试官问这题，真正想考察的是：你有没有想过**检索发生在执行链路的哪个环节、由谁决定、失败怎么办**。答得出「接法有取舍」的候选人，和只会画一条直线流水线的候选人，工程段位差着一截。这道题也天然连接前几篇的内容——第 14 篇讲过 Agentic RAG 的判断与护栏，本篇往回收一步，专讲「接入」本身的工程选型。

## 一句话先给结论

**RAG 接入 Agent，不能只理解成「先查一遍资料再回答」，更稳的做法是把检索能力封装成 Agent 可按需调用的一环，通常按需检索为主、前置检索为辅、后置校验作增强。**

## 核心原理：三种接法，各有各的位置

题库给出了三种接法，先把每一种的机制、动机和边界讲透。

**前置检索：问题一进来就统一查。** 用户消息进入链路的第一步就是检索，证据随问题一起交给 Agent，后续规划、生成都在这份证据之上进行。它的好处是路径固定、行为可预测：不需要模型做「要不要检索」的决策，延迟也稳定。边界同样明显——它默认「每个问题都需要查知识库」，但真实 Agent 任务里，相当一部分步骤是规划、路由、参数确认、调外部工具，跟知识库毫无关系；前置检索等于在这些步骤上白付了一次检索延迟和 token 成本。而且多步任务里，第一步就拿用户原话去查，往往查得太早：真正该查的实体可能要到第三步规划完才明确。

**按需检索：把 Retriever 封成工具。** 检索和搜索被封装成一个普通工具（tool），Agent 在需要事实依据的那一步主动调用，query 也由 Agent 根据当前子任务改写。这是三种接法里最「Agent 原生」的一种：检索从「流水线的固定工序」变成「规划空间里的一个动作」，Agent 可以决定何时查、查什么、查几条。代价是把决策权交给模型，就引入了决策出错的可能——该查不查（漏检）、不该查乱查（过度调用）、query 改写跑偏。这些都要靠工具设计和护栏兜住，第 14 篇讲过的护栏思路在这里直接复用。

**后置校验：先生成，再核对。** 先让 Agent 产出答案，再用检索做证据核对或引用补全。它适合做增强层——比如对高风险结论做一次「有没有证据支撑」的复核。但题库明确指出了它作为主链路的问题：一是增加延迟，生成完了还要再查一轮；二是**一旦前面已经跑偏，后面校验修正的成本更高**——发现答案没证据时，是重生成还是打回重来？主链路越靠后发现问题，返工半径越大。

**为什么推荐「按需为主、前置为辅」？** 因为不是每一步都需要查知识库。把 RAG 做成可调用能力，能减少无效检索，也更适配多步任务。「前置为辅」的意思是：对那些高频、模式固定的简单问答（比如客服里 60% 的问题都是标准 FAQ，经验值），可以保留一条前置快速通道，命中就直接答，不进多步规划；复杂或多跳问题再走按需检索的完整链路。

## 横向对比：三种接法怎么选

| 维度 | 前置检索 | 按需检索（工具化） | 后置校验 |
| --- | --- | --- | --- |
| 检索由谁决定 | 链路固定，无决策 | Agent 规划，按需触发 | 生成后统一触发 |
| 延迟特征 | 每问必查，延迟稳定 | 只在需要时查，平均延迟通常更低但方差大 | 在生成之上叠加一查，总延迟最高 |
| query 质量 | 用户原话，未聚焦子任务 | Agent 按子任务改写，通常更聚焦 | 用生成的结论反查证据 |
| 多步任务适配 | 差，第一步查完证据可能就过期 | 好，每步可查可换 query | 一般，只能事后补救 |
| 典型失效模式 | 无关问题也查、查得太早 | 漏检、过度调用、改写跑偏 | 前面跑偏后修正成本高 |
| 适合位置 | 简单高频问答的快速通道 | 主链路 | 增强层 / 高风险复核 |

落到具体场景，选型判断可以这样落：

| 场景特征 | 推荐接法 | 理由 |
| --- | --- | --- |
| 单轮 FAQ，问题模式固定 | 前置检索 | 决策开销不值得，路径短即正确 |
| 多跳问题（先查 A 再由 A 查 B） | 按需检索 | 每跳的 query 都依赖上一步结果，没法预先查 |
| 步骤混杂（规划 + 工具执行 + 问答） | 按需为主 | 大量步骤与知识库无关，前置就是浪费 |
| 答案高风险（合规、医疗、法务） | 按需 + 后置校验 | 生成后对关键结论补一次证据核对 |
| 简单与复杂问题混合的入口 | 前置快速通道 + 按需兜底 | 简单题走捷径，难题走完整链路 |

## 工程实践：把检索封装成一个「好用」的工具

按需检索说起来是「封成工具」，工程上真正决定成败的是工具的**接口设计**。一个可用的检索工具大致长这样（伪代码，函数名与字段名为通用写法）：

```python
# 伪代码：检索工具的封装
def retrieve_knowledge(
    query: str,              # Agent 改写后的查询，非用户原话
    top_k: int = 5,          # 返回条数，上限 10，防止撑爆上下文
    filter: dict | None = None,  # 元数据过滤，如 {"source": "product_docs"}
) -> dict:
    # 返回结构：每条含正文摘要、来源、得分、chunk_id
    chunks = vector_store.search(query, top_k=top_k, metadata_filter=filter)
    if not chunks:
        # 关键：空结果要显式返回，不能返回空字符串
        return {"status": "no_result", "chunks": [],
                "hint": "未命中知识库，建议改写 query 或确认是否需要检索"}
    return {"status": "ok",
            "chunks": [{"text": c.text[:500],        # 单条截断，经验值 300～500 字
                        "source": c.doc_title,
                        "score": round(c.score, 3),
                        "chunk_id": c.id} for c in chunks]}
```

三个最容易踩的坑，都藏在细节里：

**坑一：空结果导致幻觉。** 工具返回空字符串时，模型最常见的反应不是「没查到」，而是拿自己参数里的知识编一段，还带上「根据知识库」的口吻。所以空结果必须返回结构化的 `no_result` 状态，并在工具描述里写明「返回 no_result 时，如实告知用户未查到，不要编造」。

**坑二：返回内容不设预算。** top_k 给 20、每条不截断，一次调用就能吃掉几千 token，多轮下来上下文直接爆掉。要同时限三层：条数上限、单条截断长度、以及**优先返回摘要而非原文**——需要原文时可以再提供一个按 `chunk_id` 取全文的工具，形成 small-to-big 的两级结构（第 15 篇对比表里讲过的父子块回填：小块检索、大块进上下文）。

**坑三：过度调用。** 把检索开放给 Agent 后，经验值上最常见的失控是循环检索：query 不理想 → 结果不满意 → 换个说法再查 → 再不满意……一晚上几毛钱的 API 账单就这么烧掉。要在循环外加预算控制（伪代码）：

```python
# 伪代码：Agent 主循环里的检索预算与去重
max_retrieve_calls = 5            # 单次任务检索调用上限，经验值 3～6
retrieve_count = 0
seen_queries: set[str] = set()    # 语义去重：改写后与历史 query 相似度过高则拦截

for step in agent_loop():
    if step.tool == "retrieve_knowledge":
        if retrieve_count >= max_retrieve_calls:
            step.override("检索预算已用尽，请基于已有证据作答或向用户澄清")
        if is_similar_to_any(step.args["query"], seen_queries, threshold=0.9):
            step.override("该问题已检索过，请调整 query 或改用其他工具")
        seen_queries.add(step.args["query"])
        retrieve_count += 1
```

判断接入后的检索是否「失控」，线上看这几类信号：

| 信号 | 健康表现 | 失控表现 | 对策 |
| --- | --- | --- | --- |
| 单任务平均检索次数 | 1～2 次（经验值） | 4 次以上 | 收紧预算、改写工具描述 |
| 重复 / 高相似 query 占比 | 低 | 大量近重复改写 | 加语义去重阈值 |
| 检索结果被后续步骤引用率 | 高 | 查了不用、查完弃 | 检查工具返回质量与截断策略 |
| no_result 占比 | 低且稳定 | 持续升高 | 知识库覆盖不足，回查索引侧 |

## 追问逐条作答

### 追问一：你了解生成过程中多次检索、自适应检索或 Agentic RAG 吗？它和「先检索一次再生成」有什么区别？

区别的本质在「检索次数与决策权」。先检索一次再生成，检索是静态前置工序，查到什么就用什么，查偏了后面全歪。Agentic RAG 把检索变成循环里的动作：生成过程中发现证据不足，可以再查、换 query 查、甚至拆成多个子问题分别查，检索时机和次数由模型按需决定。第 14 篇详细讲过它的判断标准（简单查询不值得上）与护栏设计，这里补一句接入视角的总结：升级成 Agentic RAG 后，护栏（预算、去重、空结果处理）从「可选」变成「必选」，因为多轮检索的失控面远大于单轮。

### 追问二：什么情况下应该从「一次检索」升级成「多轮检索 + 中途补检」？

看三个信号。第一，**问题结构**：多跳问题（答案依赖链式事实，先查 A 的结果才能确定查 B）天然没法一次检索命中，必须中途补检。第二，**badcase 分布**：如果线上「证据不足导致的编造」和「答非所问」占比持续偏高，且排查确认是索引与召回侧已经优化到位、问题出在一次检索覆盖不了信息需求，就该升级。第三，**中间产物可检验**：升级的前提是每步生成的事实断言能被下一步检索验证，否则多轮只是把一次错误放大成多次。反过来，单轮 FAQ 类流量占比高的系统，强行上多轮检索纯属增加延迟与成本。

### 追问三：前置和按需是二选一吗？实际系统怎么混着用？

不是二选一，实际系统常见分层混用：入口先过一道轻量路由（可以是小模型或规则），判断问题类型——高频简单问答走前置快速通道，检索一次直接生成；判定为复杂或多跳的问题才进入完整 Agent 链路，走按需检索。经验值上，这类混合结构在 FAQ 占比高的场景（客服、内部知识助手）能明显降低平均延迟与调用成本，因为大头流量根本不进多步规划。路由器本身的准确率要监控，路由错方向的代价是简单题被复杂化、难题被简化。

### 追问四：检索工具的返回结构怎么设计，模型才「用得好」？

三件事。一是**显式状态**：ok / no_result 必须可区分，杜绝空字符串。二是**带来源与得分**：每条结果给 source 和 score，模型在生成时才有素材做引用标注，也能对低分结果保持怀疑；引用的合规要求（第 13 篇讲过的引用合法性）从这里就开始铺。三是**控制体量**：条数上限 + 单条截断 + 摘要优先，配一个按 chunk_id 取全文的二级工具。另外字段名用模型熟悉的词（source、score、text），比自造缩写名词的遵循率高。

### 追问五：Agent 改写 query 比直接用用户原话好在哪、坏在哪？

好在聚焦：用户原话常含口语、上下文代词（「那它支持吗」）、多意图混排，改写能把当前子任务需要的事实抽成独立、完整的查询，通常显著提升召回相关性。坏在两个风险：一是**改写过猛丢实体**——模型为了「通顺」把型号、版本号这类精确实体意译掉，检索直接 miss；二是**改写漂移**——多轮任务里改写累积偏移，离用户本意越来越远。工程对策：工具描述里写明「保留专有名词与版本号原样」；对含明确实体的 query 跳过改写直查；必要时同轮并发「原话 + 改写」两个 query 再合并去重。

### 追问六：接入之后，怎么证明这套设计真的省了成本、稳了质量？

别拿感觉说话，上三类指标对比接入前后：**成本侧**，单任务平均检索次数、检索 token 占比、API 调用费用；**质量侧**，证据引用率（答案中有来源支撑的断言比例）、no_result 后的幻觉率、badcase 里「证据不足型编造」的占比变化；**延迟侧**，P50 / P95 端到端延迟——注意按需检索的方差比前置大，P95 可能不降反升，要如实呈现。评测要用同一批固定测试集跑对照，别拿不同时间段的线上流量直接比。

## 60 秒面试回答模板

> RAG 接 Agent 不是「先查一遍再回答」这么简单。我会分三种接法讲：前置检索，问题一进来统一查，路径稳定但无关步骤也在付检索成本；按需检索，把 Retriever 封成工具，Agent 在需要证据的那一步主动调用，query 按子任务改写；后置校验，生成后用检索核对证据，适合做增强但不宜当主链路，因为发现跑偏越晚、修正成本越高。实际项目我推荐按需为主、前置为辅：高频简单问答留一条前置快速通道，复杂多跳问题走工具化检索的完整链路。工具设计上有三个硬要求：空结果显式返回防幻觉、返回内容设 token 预算、外层加调用次数与 query 去重防过度检索。

## 加分项

- 能主动区分「RAG 是能力，Agent 是调度者」：检索、重排、取全文都可以是独立的工具，粒度由任务决定，而不是一整个 RAG 流水线糊成一个黑盒工具。
- 提到 small-to-big 两级工具结构：小 chunk 检索保精度，按 chunk_id 回填大 chunk 保上下文完整，兼顾召回相关性与 token 预算。
- 有线上指标意识：单任务检索次数、no_result 占比、证据引用率、P95 延迟方差，能说出「按需检索 P95 可能升高」这种反直觉细节。
- 能把接法选择和第 14 篇的护栏、第 13 篇的引用合规串起来，说明接入设计不是孤立的。

## 常见误区

- **把「接入」答成「拼接」**：只说「先检索再生成」，暴露没理解 Agent 的规划循环，这是本题最典型的答偏方向。
- **把后置校验当万能保险**：忽略「前面跑偏、后面修正成本更高」的结构性问题，校验发现没证据之后的动作（重生成？打回？）没有想清楚。
- **认为按需检索天然省成本**：忽略了过度调用与 query 改写失败带来的重复检索，不加预算控制的工具化检索可能比前置更贵。
