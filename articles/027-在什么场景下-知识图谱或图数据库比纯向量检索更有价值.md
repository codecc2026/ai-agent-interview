# 在什么场景下，知识图谱或图数据库比纯向量检索更有价值？

## 面试官为什么爱问这题

这是检索选型里典型的「考边界」题：语义召回和关系推理的边界画在哪，决定了架构怎么选。候选人的常见翻车姿势有两种——一种把「知识图谱更高级」当结论背出来，一听就没扛过线上事故；另一种倒是知道图，但讲不出向量检索在这些场景里**具体怎么错**，回答停在「图能做多跳」这一句，再追问一层就空了。

面试官想听的是两个判定：什么形态的问题天生不该交给向量检索；图进来之后是做主通路还是做增强。前面聊过 GraphRAG 这条路线怎么落地——抽取建图、多路召回融合，那篇的重心在「路线怎么搭」。这篇换个角度，不看路线看场景：什么问题的答案根本不在「最像的段落」里，以及图在架构里该站在什么位置。

## 一句话先给结论

**当问题的核心是「谁和谁有什么关系」——实体关系、路径推理、多跳关联、结构化约束——而不是「哪段文本最像」时，知识图谱或图数据库更有价值；工程上把它定位成增强而不是替代：向量检索管语义召回，图管结构化约束、实体消歧和关系推理，只有问题本身高度结构化、关系链特别关键时，图才升为主通路。**

## 核心原理：语义相似，恰恰是这类场景的陷阱

### 「语义接近但关系错误」是怎么发生的

向量检索给的是语义距离：query 和文本段各自变成向量，按远近排序。它不校验关系真假，也不校验答案完整性——这两点在关系类问题上正好都是致命的。

拿设备故障排查举例。问「故障码 E-0502 该找谁处理」，语义上最像的段落当然是故障手册里描述 E-0502 的那几段，检索得非常准。但「该找谁」取决于另一条链：E-0502 由哪个传感器触发、传感器装在哪个工位、工位属于哪条产线、这条产线的维保合同签给了哪家供应商。这条链可能拆在手册、台账、合同三种文档里，任何单独一段与问题的相似度都不高，纯向量召回大概率给出一份「讲得很对但答非所问」的手册段落。

这类错答案的恶劣之处在于**它错得有理有据**：引用的文档是真的，段落内容也是真的，错的是关系推理。之前讲过引用合法性校验，那是防「引用不存在」；这种 case 引用合法、内容真实，校验放行，错误只能靠业务方踩到才知道。它是纯向量 RAG 里最难发现的一类坏例。

### 五类场景的共性

设备故障排查、商品属性关联、组织关系、法规条文引用、依赖链分析——这五类场景经常被当作「图谱案例集」罗列，但值得记的是它们的共性：**语料里真正值钱的是实体和关系，文档只是关系的载体，而用户问的是关系本身**。

由此推出向量检索的两个先天缺陷。一是答案不在任何单段文本里：影响面、责任链、汇报线都是跨文档拼出来的链路，召回单位是 chunk，chunk 之间的关联在切片那一刻就丢了。二是相似度表达不了布尔逻辑和路径约束：「既是 X 的客户、又不依赖 Y 的供应商」这种问题，「语义最像」和「满足条件」是两回事，最像的段落可能恰好不满足约束。

反过来，这些场景的语料往往有权威结构化来源：设备台账在资产系统里，组织架构在 HR 系统里，依赖关系在构建工具的清单文件里。这一点直接决定了架构选型，下面展开。

### 主通路还是增强：一个判定，两种形态

图谱进架构有两个位置。**增强形态**：向量检索仍是主路，图谱负责结构化约束、实体消歧和关系推理，两边结果融合——这是企业项目的常态，因为语料长尾里大量问题还是单点语义召回。**主通路形态**：问题进来先实体链接、再查图，答案直接就是图上的链路或实体集合——只有当问题本身高度结构化、关系链特别关键时才这么干。

判定的关键变量不在「图强不强」，在**数据形态和失败代价**：关系数据有没有权威的结构化来源、关系答错的业务代价有多大。这个判定展开成工程清单放在后面，先看横向对比。

## 横向对比

先按场景看纯向量的失败方式和图谱的接法，这张表是回答「什么场景」的主体：

| 场景 | 问题核心 | 纯向量检索的典型失败 | 图谱接住的方式 |
| --- | --- | --- | --- |
| 设备故障排查 | 故障→部件→产线→责任方，一条链 | 召回手册段落，答得出「是什么」，答不出「找谁」 | 沿触发、挂载、维保边做受限遍历 |
| 商品属性关联 | 「同时满足几个属性条件的商品」 | 相似度表达不了布尔组合，召回不全 | 属性落成边，约束翻译成图查询过滤条件 |
| 组织关系 | 汇报线、审批链、兼任关系 | 介绍性段落语义相近，「现任」和「曾任」容易混 | 关系带生效区间属性，按时间过滤 |
| 法规条文引用 | 条文 A 引用条文 B，改版后引用是否仍成立 | 召回旧版条文，且引用是真的 | 版本入图做节点，引用边带生效日期 |
| 依赖链分析 | 某组件出问题，下游哪些服务受影响 | 影响面拆在大量文档里，无单段可召回 | 反向遍历依赖边，影响面直接拉出 |

再看主通路和增强两种形态的架构差异，这张表回答「图放在哪」：

| 判定维度 | 图做主通路 | 图做增强 |
| --- | --- | --- |
| 数据来源 | 已结构化：系统台账、组织架构导出、构建清单 | 关系埋在非结构化文本里，要靠抽取 |
| 问题形态 | 接口化查询，答案就是链路或实体集合 | 关系类只占问题的一部分，多数还是语义召回 |
| 失败兜底 | 图上查不到就是查不到，靠数据覆盖度兜底 | 向量路和关键词路继续兜底，单路失明不拖垮系统 |
| 建图成本 | ETL 管道，一次性加例行同步 | 抽取、消歧、增量对齐，持续投入 |
| 典型例子 | 设备台账问答、审批链查询、影响面分析 | 企业知识库问答里补上关系类问题 |

## 工程实践

### 判定清单：立项前先过四问

- **答案能不能写成一组实体或一条链路？** 能，就是关系问题；不能，先修切块和混合检索，别急着上图。
- **关系数据有没有权威的结构化来源？** 有——组织系统、资产系统、构建工具的依赖清单——直接入图，走 ETL，不用抽取，这是成本最低的一条路。没有、关系只在文本里，才需要抽取建图，成本口径参照之前聊过的全量抽取账。
- **关系答错的业务代价多大？** 停产追责、合规风险这类高代价场景，值得把关系链做成主通路；答错了顶多用户重新问一句的场景，增强甚至不上图都够。
- **关系类坏例占比多少？** 延续 badcase 归因的思路：把线上负反馈按「单点事实 / 关系链路」归类，关系类占比上不去，图谱立项就没有地基。

### 结构化数据直接入图

组织关系是这个思路最顺的例子：汇报线在 HR 系统里本来就是表结构，ETL 灌进图数据库，边就是「汇报给」，属性带生效区间，改版有版本。设备台账、依赖清单（如 package.json 这类构建工具的清单文件）同理。**这类场景不需要 LLM 抽取**——抽取是给非结构化文本准备的，数据已经结构化还上抽取，等于放着权威源不用、引入一层新的错误率。

### 关系约束翻译成图查询

约束落在图上就是查询语言里的谓词。以 Neo4j 的 Cypher 为例，语法真实可跑：

```cypher
// 设备故障责任链：故障码 → 触发设备 → 所在产线 → 维保供应商
MATCH (f:Fault {code: $code})<-[:TRIGGERS]-(e:Equipment)
      -[:INSTALLED_ON]->(l:Line)-[:MAINTAINED_BY]->(v:Vendor)
WHERE v.status <> 'suspended'
RETURN f.description, e.name, l.name, v.name, v.phone
LIMIT 10
```

一条 `MATCH` 把整条链写出来，「维保供应商已停用则排除」这种约束就是一个 `WHERE` 谓词——这在向量检索里没有对应物，相似度打分插不进任何布尔条件。这也是关系类问题上图之后可解释性变好的原因：返回的是一条带命名的路径，能直接拿给业务方核对。

### 实体链接：进图的第一道坎

自然语言问句不会恰好用图上的规范名。问「三车间的注塑机坏了找谁」，图上的节点叫「注塑成型单元 IM-03」，进图第一步得把「三车间注塑机」链到这个节点——靠别名表加向量模糊匹配兜底，实体链接失败就返回空、退回向量路。值得留意的一个交叉点：**图做主通路的系统，进图第一步仍然要靠向量检索做模糊匹配**，两套技术在这个位置是咬合的，不是竞争关系。

把上面几步串成中间层，伪代码：

```python
# 伪代码：自然语言约束 → 图查询的中间层
def build_graph_query(utterance):
    seeds = entity_link(utterance)      # 别名表精确匹配，未命中用向量模糊匹配兜底
    if not seeds:
        return None                    # 链接失败，退回向量检索路
    cons = extract_constraints(utterance)   # 「不是…」「排除已停用」这类布尔条件
    return plan_pattern(seeds, cons,          # 生成点边模式，遍历深度默认 2，
                        max_hops=3)           # 护栏 3（经验值，再深噪声上升）
```

## 追问逐条作答

### 追问一：「语义接近但关系错误」的坏例，怎么从线上日志里挑出来？

靠答案的可验证性反推。关系类问题的答案大多可枚举验证——「找谁」是一个人或一个团队，「影响面」是一组服务，「引用哪版」是确定条文——先按「答案形态是实体集合或链路」把日志分流，这一类用黄金关系集核对即可批量挑出。其次盯一个信号：**引用校验通过但用户标记答错**的 case，多半就是这个类型，因为它的引用和内容都是真的。挑出来之后按「图上应该走通、实际没走通」归因，就是上图的立项证据。

### 追问二：图做主通路和做增强，架构上具体差在哪？

主通路形态里，图查询是答案的生产者：实体链接成功就直接遍历出链路，返回给用户，失败模式是「查不到」——兜底靠数据覆盖度和实体链接质量。增强形态里，图谱路只是召回的一路，与向量、关键词并列，融合重排后进上下文，图失明时另外两路接得住，系统整体可用性不依赖图。工程上从增强升主通路，真正要补的不是图本身，是**数据覆盖的验收标准**：拿已知关系做验证集，量「应该走通的链路实际走通多少」，这个数字过线了才敢让图独挑（经验值：核心链路可达率要稳在九成上下再谈主通路，视业务容错浮动）。

### 追问三：法规条文引用为什么也算关系场景？版本怎么处理？

因为「引用」本身就是一条边。条文 A 引用条文 B，业务问题的真实形态往往是「B 在最新版里还存不存在、这条引用现在还成立不成立」——这不是找相似段落，是查带版本的关系。处理方式是把条文版本入图做节点，引用落成边、带生效日期，改版时新增版本节点而不是改写旧节点，这样「某时间点适用的引用链」可以按属性过滤重放。这和之前讲过的引用合法性校验是上下楼的关系：那边防「引用的文档不存在」，这边防「引用的版本已失效」。

### 追问四：数据已经结构化，还要不要 LLM 抽取？

不要，这是最容易白花钱的地方。组织架构、设备台账、依赖清单本来就是权威结构化数据，ETL 直接入图，关系是系统保证的，没有抽取错误率。LLM 抽取只在关系埋在非结构化文本里时才需要——比如故障记录的自由文本描述、维保合同的条款。同一个系统里两条建图路径可以并存：台账走 ETL，自由文本走抽取，两拨节点在图上对齐。把权威结构化数据也过一遍抽取，等于放着系统背书不用，额外引入一层错误率。

### 追问五：不上图数据库，关系库的递归查询能扛多少？

小规模浅跳数扛得动。MySQL 8.0 和 PostgreSQL 都支持 `WITH RECURSIVE` 递归 CTE，两三跳、几千节点内的查询通常够用，先把结论说诚实。差距在三个地方：跳深和规模上来后，每跳一次表连接，性能随深度变陡；路径上的过滤与剪枝要手工写进递归条件，表达力远不如图查询语言里点边模式直写的谓词；边上属性（生效区间、合同编号）在关系模型里没有自然位置，塞进关联表列越塞越乱。图数据库靠索引无关邻接（index-free adjacency）换深度遍历的稳定性——每跳都是指针寻址。判定边界（经验值，随表结构与索引质量浮动）：依赖链两三跳、数据量在百万行内、查询模式固定，递归 CTE 先顶着；查询模式多变、跳深要放开、边上属性多，再上图。

### 追问六：怎么向业务方证明值得上图？

别拿「图能做推理」当论据，拿对比实验。做法是攒一组**可枚举验证的关系题集**——每题的答案是一组实体或一条链路，能机器判分——让纯向量路线和图谱路线各答一遍，报两个正确率。题集从两处来：线上挑出的关系类坏例，加上业务方给的典型问题。这个实验同时回答了立项和验收两件事：立项时它证明差距存在，上线后同一题集就是回归测试。如果差距拉开不明显，这个实验同样有价值——它替项目省了一次错误的架构升级。

## 60 秒面试回答模板

> 我的判断标准就一句：问题问的是「哪段文字最像」，还是「谁和谁有什么关系」。设备故障排查、组织关系、法规引用、依赖链这类场景，答案是一条链路或一组实体，关系答错业务代价还大——向量检索只按语义相似度召回，最像的段落可能关系是错的，而且引用真实、内容真实，是最难发现的坏例。这时候图接手结构化约束、实体消歧和关系推理。但我不把它当替代：向量继续管语义召回，图管关系这条线；只有问题高度结构化、关系链特别关键——比如数据直接来自组织系统、设备台账——图才升主通路。选型时我先看关系类坏例占比，再看关系数据有没有权威结构化来源，两个都成立才上图。

## 加分项

- **把「语义接近但关系错误」讲成一个独立的坏例类型**：指出它的引用合法、内容真实、校验放行，说明真踩过纯向量系统的排查，比背「图能做多跳」高一个段位。
- **区分两条建图路径**：权威结构化数据走 ETL、免抽取，非结构化文本才走抽取——能讲清「什么时候根本不需要 LLM」，说明成本意识在架构层而不在组件层。
- **主动给出不上图的边界**：递归 CTE 在浅跳数小规模下够用，能报出 `WITH RECURSIVE` 这种真实写法，把「上图」从信仰问题变成规模问题。
- **用可枚举验证的题集做立项和验收**：一个实验同时回答「要不要上」和「上得值不值」，方法论延续黄金集的思路。

## 常见误区

- **把「图谱更有价值」答成「图谱更先进」**：价值来自问题形态和数据形态的匹配，不是技术新旧；在单点语义召回为主的知识库里硬上图，抽取和维护成本全是负资产。
- **忽略数据形态就拍主通路**：关系还埋在文本里就让图独挑，实体链接一失败系统整体失明；主通路的门槛是数据覆盖度，不是架构图好看。
- **答非所问地背 GraphRAG 流程**：这题问的是场景判定和架构定位，直接铺抽取建图流程，等于把「什么时候用」答成了「怎么建」。
