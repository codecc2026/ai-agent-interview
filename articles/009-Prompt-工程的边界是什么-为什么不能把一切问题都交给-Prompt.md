# Prompt 工程的边界是什么？为什么不能把一切问题都交给 Prompt？

## 一句话先给结论

**Prompt 是一种「任务表达与约束手段」，它改的是模型这一次看到什么、被要求什么，改不了模型知道什么、能做什么、能记住什么；知识缺失、强执行需求、复杂状态与流程、行为固化这四类问题，Prompt 只能有限缓解，越往后越应该分别交给 RAG、Tools / Function Calling、Workflow / Graph、微调——工程上的分工是 Prompt 表达规则，RAG 补知识，Tools 给执行能力，Graph / Workflow 管流程控制。**

面试官把这题递过来，考的不是「你会不会写提示词」，而是你有没有**越界意识**：知道一条指令写到什么程度就该停手换手段。答崩的常见形态是把 Prompt 当成万能膏药——效果不好就改提示词，改到最后变成一条几千字长、没人敢动的巨型系统提示，任何一处改动都可能引起别处回归。第 5 篇给过「缺什么就选什么」的选型漏斗，第 7 篇讲过怎么做 Prompt 的版本与回归，第 8 篇铺开过结构化输出；本篇换个角度往下钻：**怎么判断一段 Prompt 已经越界了**，越界之后往哪迁，迁的时候要留下什么。

## Prompt 改的到底是什么

### 它只作用在输入侧

一次推理请求里，模型的权重是冻结的。Prompt 的全部作用，发生在「这次请求输入了什么」这一层：它决定模型看到的指令、示例、资料与输出要求，从而改变注意力的分配和表达的方式。

类比一下：**Prompt 相当于给同一位专家换一份简报和要求清单**，你换不了他读过什么书，也换不了他手上有没有工具。所以它能显著提升「同一批知识条件下怎么表达、怎么组织、怎么取舍」，却造不出它没见过的事实。

这条第一性原理值得背下来，因为它能一次性解释后面所有边界：**凡是「改输入」解决不了的问题，Prompt 都解决不了。**

### 四类能力不在它的射程内

题库把边界点得很清楚，展开成四类更好记：

1. **知识缺失**：模型没见过你的保单条款、上周刚改的退货政策、内部接口文档。这类内容既不在权重里，也不会因为你写进提示词就变得可靠——除非它真的被塞进上下文，而塞多了又有新的问题（下一节讲）。
2. **强执行需求**：要真的去查库、调接口、发消息、改订单状态。模型输出的是文本，**文本没有副作用**。写在提示词里的「请你调用订单接口」，模型最多回你一段长得像调用结果的文字。
3. **复杂状态与流程**：多步骤、带分支、要回溯、失败要重试。把这些全写进一条指令，等于让模型在每次生成时临场重新推演一遍流程，稳定性与可观测性都很差。
4. **行为固化**：跨会话统一的语气、格式、分类边界。这一条要说得准确——**它部分在射程内**：加规则、加 few-shot 示例、上结构化输出约束都能缓解；但要让它「稳定成为默认行为」，成本会持续上升，最终要落到权重侧（微调）。把它说成「Prompt 完全管不了行为」是错的，说成「Prompt 就能彻底固化行为」更错。

### 三个硬约束，划出边界的物理位置

- **权重冻结**：推理期不更新参数。想改「模型本身」只能微调，不能靠写得更好的一段话。
- **上下文有限**：窗口有上限，塞满就被截断；输入越长，成本与延迟通常越高（定性判断，各平台差异很大），而且长上下文中段的信息召回会下降——也就是常说的 Lost in the Middle，这一条后面有专篇展开。
- **无副作用**：模型不会真的触发外部动作，执行的责任必须由宿主程序承担。

## 越界的四个症状，和对应的迁移方向

下面这张表是本篇最该记住的东西。它的读法是：先看左列的**现象**，再判断中间列的**真实缺口**，最后落到右列的**迁移方向**。

| 你观察到的现象 | 真实缺的是什么 | 继续改 Prompt 会发生什么 | 应该转向 |
| --- | --- | --- | --- |
| 答得流畅但内容是错的、旧的、泛泛而谈 | 知识 | 越写越长的背景资料，塞进上下文仍可能漏掉关键那一段 | RAG（检索 + 重排） |
| 资料一多就成本高、噪声大、丢关键信息 | 知识组织方式 | 全量塞入导致窗口吃紧、中段信息丢失 | RAG，而不是加长窗口 |
| 模型在文本里说「已为您查询到……」却没有真实数据 | 执行能力 | 变成演示好看、线上出事的幻觉式执行 | Tools / Function Calling |
| 一次调用做不完，需要多步、分支、失败重试 | 流程与状态 | 系统提示膨胀成不可维护的长指令，改一处坏三处 | Workflow / Graph（如 LangGraph） |
| 同一任务每次说法、格式、分类边界都不同 | 行为稳定性 | 不断堆规则与示例，边际收益持续下降 | 先 few-shot + 结构化约束，顶不住再考虑微调 |

表里第 1 行和第 2 行常被当成同一件事，其实不同：**前者是「知识不在模型里」，后者是「知识塞得不对」**。前者靠检索补内容，后者靠切块、召回与重排补组织方式——两个都指向 RAG，但要动的地方不一样。

## 五种手段的职责边界

再往上一层看，Prompt 和其他手段不是五选一，而是**分层叠加**。下面这张表按「各自改变什么」来切：

| 手段 | 它改变的对象 | 典型输入 | 失效信号 | 与 Prompt 的关系 |
| --- | --- | --- | --- | --- |
| Prompt | 这一次请求里的指令、示例、约束 | 文本指令、few-shot | 指令越写越长仍然不稳 | 基线，任何方案里都存在 |
| RAG | 这一次请求里附带的外部资料 | 检索回来的片段 + 引用 | 召回错、切块不合理导致答非所问 | 提供输入，不替代约束 |
| Tools / Function Calling | 输出的语义：从「答案」变成「调用意图 + 参数」 | 工具名、description、参数 schema | 工具描述模糊导致选错工具、编造参数 | 使用规则仍写在 Prompt 里 |
| Workflow / Graph | 任务被拆成几步、每步之间怎么走 | 节点、边、状态定义 | 分支画不出来，或下一步取决于中间结果 | 每个节点内部依然有 Prompt |
| 微调 | 模型权重本身 | 训练数据与训练配置 | 数据不足，或知识仍需频繁更新 | 微调之后照样需要 Prompt 表达当次任务 |

一句话收口：**没有任何一种手段会消灭 Prompt，它们只会把 Prompt 从「万能胶」里解放出来，让它专心干表达与约束这一件事。**反问一句就能验出真假——上了 RAG 之后要不要写提示词？要，而且要求更细（第 3 节展开）。

## 工程实践：把「越界」变成可观测的信号

边界讲了半天，落地要靠三件事：**算得出来、看得见告警、改得动结构**。

### 先算预算，再塞上下文

下面这段是上下文预算的守卫逻辑，核心是**先算后塞**，而不是塞爆了让平台截断：

```python
# 伪代码：encode() 按所用 SDK 的 tokenizer 替换
MAX_CTX = 32_000     # 上下文窗口上限，按你实际使用的模型填写
RESERVE = 4_000      # 预留给输出与系统提示，经验值，按业务调整

def build_context(system_prompt, user_query, chunks, encode):
    """chunks: 检索候选，每项含 .text 与 .score（相似度分数）"""
    budget = MAX_CTX - RESERVE - len(encode(system_prompt)) - len(encode(user_query))
    picked, used = [], 0
    for c in sorted(chunks, key=lambda x: x.score, reverse=True):
        n = len(encode(c.text))
        if used + n > budget:
            break                      # 预算用完就停，绝不硬塞
        picked.append(c)
        used += n
    if len(picked) < len(chunks):      # 有片段被砍掉 = 已经在越界
        print(f"[warn] 上下文预算不足：取 {len(picked)}/{len(chunks)} 段，建议回到检索侧做精排")
    return picked
```

三个容易被忽略的细节：

1. **截断位置不可控**。靠平台截断时，被切掉的往往是末尾，而末尾常常恰好放着最新的约束条件。所以预算必须自己算。
2. **「取不满」就是越界信号**。出现这个告警，正确的动作不是去申请更长的窗口，而是回到检索侧做筛选与重排。
3. **成本是每次重复付的**。把资料全量塞进提示词，意味着每次请求都在为同一批资料重复付费；转成 RAG 后只有命中片段进入上下文，成本与延迟的结构都变了。

### 把长指令拆成配置，而不是继续堆字符串

```yaml
# prompt.yaml —— 与代码一起版本化（第 7 篇讲过版本与回归怎么管）
role: 你是企业报销助手
rules:
  - 只依据「检索到的政策片段」回答，未覆盖的一律说明不知道
  - 金额一律以元为单位，只输出数字
  - 政策未明确的场景，要求用户补充发票类型后再答
output:
  format: json
  schema_ref: ./schemas/expense.json    # 结构化输出约束，做法见第 8 篇
few_shot_refs:
  - ./shots/ok_001.md
  - ./shots/reject_002.md               # 拒答示例，和正例同等重要
```

三条硬规矩：**规则写进结构化配置**，不要在字符串里拼几十条「必须 / 不得」；**示例外置成文件**，单条系统提示里堆 few-shot 是让上下文最快爆掉的做法；**输出格式交给 schema**，不要用自然语言描述 JSON 长什么样——写法不产生约束力，这一点第 8 篇已经讲透。

### 执行需求：识别「文本里假装调用」

```python
FORBIDDEN = ["已为您查询", "系统已提交", "已为您预订"]   # 经验值：按业务词表补充

def looks_like_fake_action(text, tool_calls):
    """没有任何真实工具调用，却出现完成态措辞 —— 典型的「假装执行」"""
    return not tool_calls and any(k in text for k in FORBIDDEN)
```

一旦命中，说明执行需求被错误地交给了 Prompt。正确做法是把能力包成工具：把工具名、description、参数 schema 交给模型，由宿主程序真正执行，再把结果回灌进上下文。Function Calling 的价值在于**模型和宿主之间有一层明确契约**，而文本里的「已为您查询」没有任何契约保证——这也是第 8 篇说它是「带意图的结构化输出」的原因。

### 流程需求：从长指令搬进图里

```python
# 伪代码：把「查库存 → 算优惠 → 调支付，失败重试」从提示词里搬出来
g = StateGraph(State)
g.add_node("check_stock", check_stock)
g.add_node("calc_discount", calc_discount)
g.add_node("pay", pay)
g.add_edge(START, "check_stock")
g.add_conditional_edges("check_stock", route_by_stock)  # 分支由代码判定，不由模型临场发挥
g.add_edge("calc_discount", "pay")
app = g.compile(checkpointer=MemorySaver())             # 状态由框架托管，不再塞进提示词
```

差别是确定性与可观测性：写在提示词里，分支靠模型「理解」，跑错了你只能看到最终文本，说不清卡在第几步；写成图，每一步是独立节点，状态由 checkpointer 托管，失败能定位到具体节点重试或转人工。代价是前期多写代码、灵活性下降——所以判断标准还是第 5 篇那句：**能不能事先把流程画成图**，能画出来且长期稳定，就该写成图。

### 症状到动作的速查表

| 现象 | 判定 | 下一步动作 |
| --- | --- | --- |
| 加一条规则只修好一个 badcase，却带坏两个 | 边际收益转负 | 停止加规则，拆任务或换手段 |
| 回归集波动，但说不清是哪条改动引起的 | 复杂度超出可控范围 | 拆解成配置 + 逐项灰度（见第 7 篇） |
| 输出里出现完成态措辞却没有工具调用 | 执行类越界 | 抽成工具，走 Function Calling |
| 上下文预算告警频繁 | 知识类越界 | 回到检索侧做切块、召回与重排 |
| 换模型后同一段提示词效果明显变化 | Prompt 与模型强耦合 | 回归对象是「Prompt + 模型」组合，不是单段提示词 |

最后一行最常被漏掉：**换底层模型之后，旧提示词不一定还能保持原效果**。所以回归的粒度要放到组合上，这一点第 7 篇也强调过。

## 面试官的追问，你该怎么接

### 追问一：怎么判断该转 RAG 还是微调？

先看「错在哪」。内容是错的、旧的、没见过的——知识问题，转 RAG；知识是对的但每次说法、格式、分类边界不一致——行为问题，先加 few-shot、再上结构化输出约束，顶不住才轮到微调。一句话概括：**RAG 补的是模型不知道的，微调补的是模型做不稳的。**千万别用微调去塞知识（知识一变就得重训），也别用提示词去死追稳定性。

### 追问二：Prompt 写到多长算越界？有没有量化标准？

没有通用字数线，但有三个可观测信号：**一是新增规则的边际收益下降**，加一条规则只修好一个 badcase 却带坏两个；**二是改动的影响无法预测**，回归集波动但说不清原因；**三是上下文预算开始吃紧**，需要砍掉别的内容才塞得下指令。三者出现任意一个，就该拆结构而不是继续加字。经验值上，一个需要几十条「必须 / 不得」才能描述清楚的任务，通常已经不属于 Prompt 该承担的范畴。

### 追问三：上了 RAG 之后，Prompt 还需要吗？会不会被取代？

需要，而且更重要。RAG 决定「喂什么资料」，Prompt 决定「怎么用这些资料」——要不要引用出处、什么时候必须拒答、输出什么格式、用什么语气，全在 Prompt 里。最常见的错误就是把检索片段一塞了事，结果模型照样脱离资料自由发挥。所以两者不是替代关系：**RAG 提供输入，Prompt 提供约束，缺一个都不成立。**

### 追问四：能不能用 Prompt 让模型「记住」用户偏好？

要分三层讲清楚。**会话内**可以，靠上下文里的历史消息；**跨会话**不行，因为 Prompt 只在当次请求生效，下一次请求不带就没有了——正确做法是把偏好落到外部存储，每次按用户 ID 取回再拼进 Prompt（这是记忆机制在工作，不是模型记住了）；**要让它变成默认行为**，那就是微调的范畴。把这三层分开说，能立刻和「模型记住了」这种外行表述拉开距离。

### 追问五：流程写进 Prompt，和写成 Workflow，成本差在哪？

差在**确定性与可观测性**。写进提示词，分支由模型临场判断，出问题只能看最终文本，不知道卡在第几步；写成 Workflow / Graph，每一步是独立节点，状态由框架托管，失败能定位到节点、能针对该节点重试或转人工。代价是前期开发量更大、灵活度更低。所以取舍标准是：流程长期稳定就写成图，需要临场决策才交给 Agent——这道判断题第 5 篇已经给过顺序。

### 追问六：这条边界和成本、延迟有什么关系？

有直接关系。上下文越长，单次调用的输入成本与首字延迟通常越高（定性判断，各平台差异较大），而把资料全量塞进提示词，意味着每次请求都在为同一批资料重复付费。转成 RAG 之后，只有命中片段进入上下文，成本与延迟的结构都变了。所以「Prompt 越界」不只是可维护性问题，也是成本问题——能顺手算这笔账，面试官会认为你接过生产链路。

## 60 秒面试回答模板

> Prompt 本质是任务表达和约束手段，它改的是这一次请求里模型看到什么，改不了模型知道什么、能做什么、能记住什么。所以它解决不了四类问题：知识缺失、强执行需求、复杂状态与流程、行为固化。

> 对应的迁移方向是：资料多、知识旧转 RAG；要真调接口转 Tools 和 Function Calling，别让模型在文本里假装调用；多步分支流程转 Workflow 或 Graph；行为不稳定先加示例和结构化约束，顶不住再考虑微调。工程上的分工是 Prompt 表达规则、RAG 补知识、Tools 给执行能力、Graph 管流程。

> 我会强调两点：一是这些手段是叠加而不是替代，上了 RAG 之后提示词反而更重要；二是越界有可观测信号，比如加规则的边际收益转负、上下文预算频繁告警、输出里出现完成态措辞却没有真实工具调用。看到这些就该换手段，而不是继续加字。

## 加分项

- **能说出「只改输入、不改权重」这条第一性原理**。它一句话就能推出后面所有边界，比罗列现象高一个层次。
- **能给出可观测的越界信号**。边际收益转负、回归波动不可解释、上下文预算吃紧——说得出这三个，面试官基本会认定你调过线上系统。
- **强调「叠加而非替代」**。很多人会顺嘴说「有了 RAG 就不需要 Prompt」，这正好踩在考察点上。
- **把边界和成本挂钩**。上下文长度直接关系单次调用的输入成本与延迟，能算这笔账是加分项而不是超纲。

## 常见误区

- **把「不知道」当成「提示词没写好」**。模型没见过的内容，写得再清楚也是编，这是知识问题不是表达问题。
- **相信文本里的「已为您查询」**。没有真实工具调用就没有执行发生，演示环境和生产环境的差距往往就在这句话上。
- **用错手段**：拿微调塞会变的知识，拿提示词死磕稳定性。前者该重训时才动，后者该用示例与 schema 约束先顶。
- **以为提示词越长越强**。长度带来的是维护成本、上下文压力和噪声，而不是约束力的线性提升。
