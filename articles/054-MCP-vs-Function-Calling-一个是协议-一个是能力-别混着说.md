# MCP vs Function Calling：一个是协议，一个是能力，别混着说

<!-- growth-hook:v1 -->
MCP 和 Function Calling 经常被放进同一句话里说，甚至被当成竞品。但它们根本不在一层：一个负责把能力按统一协议暴露出来，一个负责让模型决定调哪个。把这层关系说反，整段回答就垮了。

## 面试官为什么爱问这题

这题高频，因为它精准命中一个最常见的概念混淆。MCP 和 Function Calling 常被并列提起，很多人以为它们是两种"调工具的方式"、可以互相替换，面试官问出来就是要看你能不能把它们放回各自的位置。真正的关系是上下层：Function Calling 是模型侧的结构化调用机制，解决模型怎么表达"调哪个函数、传什么参数"；MCP 是应用侧的统一能力接入协议，解决外部工具、资源、提示模板怎么按统一标准暴露给客户端。前面讲过 Function Calling 和输出 JSON 的区别，也聊过 MCP 与 Tool / RAG / Agent 的边界；这一篇把这一对拎出来，专讲它们的上下层关系，以及为什么"别混着说"。

## 一句话先给结论

**Function Calling 更接近模型侧的"结构化调用机制"，MCP 更接近应用侧的"统一能力接入协议"。前者解决模型如何表达"要调用哪个函数、传什么参数"；后者解决不同外部工具、资源、提示模板如何用统一标准暴露给客户端。两者不是替代关系，而是上下层关系：Function Calling 更靠近模型决策，MCP 更靠近生态接入和协议标准化。落地时 Agent 完全可以在 MCP 暴露的能力之上，继续用 Function Calling 做调用决策。**

## 核心原理：一个在下，一个在上

### Function Calling：模型侧的表达机制

Function Calling 解决的是"模型怎么表达调用意图"。模型本身只会生成文本，Function Calling 让它能输出结构化的结果，比如"我要调用哪个函数、参数是什么"。这是模型能力的一部分，发生在模型输出这一侧。前面讲过它和"让模型输出 JSON 自己解析"的区别：Function Calling 是接口层的契约，工具定义、参数 schema、消息角色都是协议的一部分。这里要强调的是它的位置，即模型侧、调用决策这一层。

### MCP：应用侧的接入协议

MCP 解决的是"外部能力怎么被统一暴露和接入"。它定义 Host、Client、Server 之间的标准，让不同来源的工具、资源、提示模板能被统一发现、暴露、调用。这是应用生态侧的协议标准，发生在能力接入这一侧。前面讲过 MCP 像 AI 世界的统一插口，它统一的是接入方式，不是模型本身。

### 上下层关系，不是二选一

把两者放一起，关系就清楚了：

| 维度 | Function Calling | MCP |
| --- | --- | --- |
| 本质 | 模型侧的结构化调用机制 | 应用侧的统一能力接入协议 |
| 解决什么 | 模型怎么表达调哪个函数、传什么参数 | 外部能力怎么按统一标准暴露给客户端 |
| 所处层次 | 靠近模型决策 | 靠近生态接入与协议标准化 |
| 类比 | 模型"说"出要调什么 | 把能力"摆"成统一接口供发现调用 |

关键结论：它们不在同一层，谈不上互相替代。一个在模型输出侧，一个在能力接入侧。真正落地时，两者常常同时出现——MCP 负责把外部能力按统一标准暴露出来，Function Calling 负责让模型能表达"我要调其中一个"。前面讲接入链路时说过"模型决策、宿主执行"，Function Calling 更靠近"决策"这一端，MCP 更靠近"能力从哪来、怎么接"这一端。

### 一个常见的错误推论

既然两者都涉及"调工具"，就容易推出"用了 MCP 就不需要 Function Calling"或反过来。这两个推论都错。MCP 把能力暴露出来，但模型要能表达"调哪个、传什么参"，这仍需 Function Calling 这类机制；Function Calling 让模型能表达调用意图，但意图要打到哪个具体的外部系统，需要 MCP 这类协议来统一接入。它们配合工作，不是此消彼长。

这个混淆之所以普遍，是因为两者在链路里紧贴着出现：能力通过 MCP 暴露后，紧接着就被转成 function 定义交给模型；模型吐出调用意图后，紧接着就通过 MCP 发出去。两个环节挨得近，从外面看像一件事，容易让人以为是同一个东西的两种叫法。但只要问一句"这一步作用在模型侧还是应用侧"，就能把它们分开。

再补一个判断表，帮你决定一个具体需求该归到哪一层：

| 你关心的问题 | 属于哪一层 | 该看哪个概念 |
| --- | --- | --- |
| 模型怎么输出"调哪个函数、传什么参数" | 模型侧 | Function Calling |
| 工具 schema 怎么交给模型、调用结果怎么回灌 | 模型侧 | Function Calling |
| 外部能力怎么被描述、发现、暴露给客户端 | 应用侧 | MCP |
| 多个应用怎么复用同一批外部能力 | 应用侧 | MCP |
| 能力来源不同、要统一接入方式 | 应用侧 | MCP |

这张表也解释了为什么面试爱问：它逼你说清每一件事发生在哪一层。能把表中每一行归对，就说明你没有把两个概念揉成一团。

## 工程实践：一次调用里两者怎么配合

走一遍完整链路，就能看清两者的分工：

1. **能力接入（MCP 的活）**：Host 通过 MCP 连接到 Server，发现它暴露的工具列表和参数 schema。
2. **转成模型可消费的工具定义**：把这些能力转成模型能理解的 function 定义，随请求交给模型。
3. **模型决策（Function Calling 的活）**：模型输出结构化的调用意图——调哪个 function、传什么参数。
4. **宿主执行**：宿主解析意图，通过 MCP 向对应 Server 发起真正的请求。
5. **结果回灌**：结果返回给模型，进入下一轮决策。

```python
# 伪代码：一次调用里 MCP 与 Function Calling 的分工
tools = mcp_client.list_tools()                 # MCP：发现并接入能力
function_defs = to_function_schemas(tools)      # 转成模型可消费的 function 定义
intent = model.invoke(messages, tools=function_defs)  # Function Calling：模型输出调用意图
if intent.tool_call:                            # 模型决定要调
    result = mcp_client.call_tool(              # MCP：宿主发起真正的请求
        intent.tool_call.name, intent.tool_call.args
    )
# mcp_client / to_function_schemas 为业务侧实现
```

要点：`list_tools` 和 `call_tool` 是 MCP 这条线（能力接入与执行），`model.invoke(..., tools=...)` 是 Function Calling 这条线（模型决策）。两者在同一条链路里各管一段，不是替代关系。变量都是业务侧实现，具体 API 按你用的库来。

## 追问逐条作答

### 追问一：用了 MCP 是不是就不需要 Function Calling 了？

不是。MCP 把外部能力按统一标准暴露出来，但模型要能表达"我要调哪个、传什么参数"，这仍需要 Function Calling 这类结构化调用机制。一个负责"能力怎么接进来"，一个负责"模型怎么表达要调"，是上下游配合。去掉任何一个，链路都断。

### 追问二：反过来，有 Function Calling 还需要 MCP 吗？

看规模。如果只有一个模型、几个固定的函数，直接在应用里定义这些 function、解析模型意图、自己执行就够了，不一定要 MCP。但当外部能力多、来源杂、要被多个应用复用时，MCP 的统一暴露和发现就体现出价值——不用为每个应用各写一套适配。所以 MCP 解决的是"生态接入的标准化"，不是单次调用本身。

### 追问三：为什么说它们是上下层，而不是两种并列的工具调用方式？

因为它们的抽象对象不同。Function Calling 抽象的是"模型的输出"，让模型吐出结构化的调用意图；MCP 抽象的是"能力的接入"，让外部能力有统一的描述和发现方式。一个作用于模型侧，一个作用于应用生态侧。并列意味着它们解决同一问题的不同方案，但实际上它们解决的是不同问题，所以是上下层，不是并列。

### 追问四（自补）：Function Calling 和 Tool Calling 是一回事吗？

日常语境里常混用，严格说工具调用（Tool Calling）是更宽的说法，Function Calling 是其中一种常见机制。这题抓的是大边界——模型侧机制 vs 应用侧协议，不必在这个细分层面上纠缠。面试时把大边界讲清楚，比纠结术语细节更重要。

### 追问五（自补）：判断一个东西属于哪一层，有什么简单方法？

看它作用在哪一侧、解决什么问题。如果它关心"模型怎么输出调用意图、参数 schema 怎么给模型"，是模型侧机制那一层；如果它关心"能力怎么被描述、发现、暴露给不同客户端"，是应用侧协议那一层。用这个尺子套，绝大多数混淆都能划开。遇到一个新名词，先问它作用在哪一侧，就不会乱。

把分层理解清楚，实际排障时也用得上。假设模型死活不调用某个工具，如果是 Function Calling 这一层的问题，表现通常是模型压根没输出调用意图，可能是工具定义没给到、描述写得让模型看不懂什么时候用；如果是 MCP 这一层的问题，模型明明输出了调用意图，但请求发到 Server 失败，可能是能力没被发现、传输没连通。按"模型有没有吐出意图"这个分界点一切，问题属于哪一层立刻清楚，省得在两层之间来回瞎找。这就是把概念放回正确位置的工程价值：不只是答对一道面试题，更是排障时知道该往哪一层看、该查哪一类配置，避免把时间浪费在错误的方向上。

> Function Calling 和 MCP 不是一回事，也不是替代关系，而是上下层。Function Calling 是模型侧的结构化调用机制，解决模型怎么表达要调哪个函数、传什么参数，靠近模型决策；MCP 是应用侧的统一能力接入协议，解决外部工具、资源、提示模板怎么按统一标准暴露给客户端，靠近生态接入和协议标准化。落地时两者常常同时出现：MCP 把能力暴露出来，模型用 Function Calling 表达调用意图，宿主再经 MCP 发起真正的请求。所以别混着说，一个在下管模型表达，一个在上管能力接入。判断所属层次看它作用在哪一侧：关心模型怎么输出是前者，关心能力怎么暴露是后者。

## 加分项

- 用"上下层"而非"并列方案"定性，直击题目要害。
- 走一遍完整调用链路，指出哪几步是 MCP、哪几步是 Function Calling。
- 纠正两个方向的错误推论（用了 MCP 就不需要 FC、反过来）。
- 给出"看作用在哪一侧"的判断尺子，方法可迁移。

## 常见误区

- **把两者当成可互相替代的两种调工具方式**：它们解决不同问题，是上下游配合。
- **认为用了 MCP 就不需要 Function Calling**：模型表达调用意图仍需 FC 类机制。
- **在术语细节上纠缠**：Tool Calling 与 Function Calling 的细分层面上不必纠结，大边界讲清更重要。
