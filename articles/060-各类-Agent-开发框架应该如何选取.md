# 各类 Agent 开发框架应该如何选取？

<!-- growth-hook:v1 -->
Agent 开发框架更新得比谁都快，背名字没有意义。这题真正的问题是：给你一个任务、一个团队、一个交付要求，你能不能说出该用哪个框架、为什么不用另一个。

## 面试官为什么爱问这题

这题高频，考的是工程判断，而不是你用过多少框架。很多人答这类题就是比"哪个最火"，或者把每个框架的功能列一遍，面试官想听的是一套选型逻辑：按任务复杂度、团队能力、交付要求来判断，什么场景用什么更划算。更成熟的回答还会给出成功指标和迁移路径——这说明你不是在静态挑工具，而是想过"选完之后怎么验、将来怎么换"。前面聊过平台 vs 框架的层间选择，这一篇聚焦"各类框架之间怎么选"，把四类方案的适用场景讲清，并正面回答两条追问。

## 一句话先给结论

**框架选型不要看热度，要看任务复杂度、团队能力和交付要求。快速原型、要生态丰富和常见组件齐全，LangChain 合适；任务有显式状态、循环、条件路由、人机协同或多智能体，LangGraph 更合适；低代码、快速验证业务流程，Coze / Dify 更适合；系统边界简单、需求非常明确，直接手写 SDK 也可能是成本最低的方案。成熟的回答不是说"哪个最好"，而是说清"什么场景用什么更划算"，并能给出替代方案和迁移路径。**

## 核心原理：四类方案按场景对号入座

### 四个选项各自的甜蜜点

| 方案 | 甜蜜点 | 适用场景 |
| --- | --- | --- |
| LangChain | 快速原型、生态丰富、常见组件齐全 | 组件级编排、要快速拼出能跑的东西 |
| LangGraph | 显式状态、循环、条件路由、人机协同、多智能体 | 复杂控制流、要让编排显式可管 |
| Coze / Dify | 低代码、快速验证业务流程 | 业务侧主导、要快速看到效果 |
| 手写 SDK | 成本最低（边界简单时） | 系统边界简单、需求非常明确 |

四者不是强弱排序，是不同场景下的划算与否。选型时先给任务画像，看复杂度多高、团队能不能驾驭、交付要有多快，再对号入座。同一套工具在这个场景很划算，换个场景可能就成了负担，所以脱离具体条件谈"哪个框架好"没有意义。

### 三个判断维度

**任务复杂度。** 简单的组件串联用 LangChain 或直接 SDK；复杂控制流（状态、循环、条件路由、人机协同、多智能体）用 LangGraph。复杂度决定你需要多少编排能力。

**团队能力。** 框架用得起来，前提是团队能驾驭。低代码平台对编码能力要求低，适合业务侧主导或工程资源紧张；代码框架需要扎实工程能力。一个团队驾驭不了的方案，再强也是负担。

**交付要求。** 要快速验证、给业务看效果，低代码平台优势大；要长期维护、严格工程化，代码框架更稳。交付节奏决定你愿意为速度付出多少工程债。

### 选型不是静态决定

题库特别强调"能说出替代方案和迁移路径，通常比单纯夸某个框架更有说服力"。意思是选型不是一锤子买卖：今天用平台快速验证，明天业务验证通过可能迁到代码框架；今天用 LangChain 拼原型，后天复杂度上来可能引入 LangGraph。成熟的回答要能讲清这条路怎么走，见后面的追问二。

前面聊平台 vs 框架时说过"先平台验证、再迁框架"的路径，这里把它放进更一般的框架选型视角——任何选择都留有退出通道，才不会被锁死。

## 工程实践：怎么让选型可验证

选完框架，怎么知道选对了？一个务实的做法是设几个可观察的指标，跑一段时间再回头看。

**开发效率。** 同类需求，从提出到上线要多久。如果框架让简单需求也变得繁琐，说明选型偏重了。

**可控性与排障。** 出问题时能不能快速定位。框架把细节藏得太深、出问题只能干瞪眼，是复杂项目里的隐患。

**维护成本。** 改一处要动多少地方、版本升级是否顺畅、团队上手快不快。这些决定长期成本。

**匹配度。** 框架的能力是不是用得上，有没有大量功能闲置、同时核心需求还得绕路实现。匹配度低说明选错了方向。

| 指标 | 怎么观察 | 说明什么 |
| --- | --- | --- |
| 开发效率 | 同类需求从提出到上线的耗时 | 框架是否适配任务节奏 |
| 可控性与排障 | 问题定位的平均耗时 | 抽象是否藏得太深 |
| 维护成本 | 改动波及范围、上手速度 | 长期是否划算 |
| 能力匹配度 | 常用能力占比、核心需求是否绕路 | 选型方向对不对 |

```python
# 伪代码：用一个最小探针任务验证框架是否趁手
def probe_framework(framework, task_spec):
    app = framework.build(task_spec)            # 用框架搭一个最小实现
    metrics = {
        "lines": count_lines(app),              # 代码量：简单任务代码多说明框架偏重
        "stable": run_twice_consistent(app),    # 稳定性：同样输入结果是否一致
        "debuggable": has_trace(app),           # 可排障：能不能看到执行轨迹
    }
    return metrics

# task_spec 是业务侧定义的最小任务；count_lines / run_twice_consistent / has_trace 为业务侧实现
```

要点：用一个真实的最小任务去试框架，而不是看文档想象。代码量、稳定性、可排障性这些指标跑出来，选型就有了依据。变量都是业务侧实现。

## 追问逐条作答

### 追问一：你最终会用哪些指标判断这次框架选型是不是成功的？

看四类指标。开发效率：同类需求从提出到上线的耗时是不是缩短；可控性与排障：出问题能不能快速定位、抽象有没有藏得太深；维护成本：改一处要动多少地方、团队上手快不快；能力匹配度：框架能力用上了多少、核心需求要不要绕路。这些指标跑一段时间就有答案。经验值：选完框架先用一个真实的最小任务做探针，别等全线铺开才发现不趁手。

### 追问二：如果前期先用平台，后期迁到自研框架，迁移边界应该怎么划？

先迁核心链路，把最需要定制和可控的部分迁走，非核心的继续留在平台，逐步进行。迁移边界的划法：看哪部分需求平台已经撑不住，深度定制、复杂状态治理、合规审计、内部系统耦合这些，是最该先迁的。迁移时最大的坑不是技术重写，而是平台上隐性配置的显性化，那些可视化点点画画出来的逻辑，得先梳理成文档再重写。前面聊平台和框架选型时说过"先把平台流程逐项导出成文档"，这里是同一个道理。经验值：迁移期间新旧两套并行一段时间，用同一批请求对比结果，确认迁过去的部分行为一致再切流量，比一次性整体切换稳妥得多。

### 追问三：LangChain 和 LangGraph 到底怎么分？

看编排复杂度。LangChain 适合把 Prompt、Model I/O、Parser、Retriever、Tools 这些组件按代码方式组合，应对组件级编排、快速原型；LangGraph 适合状态显式、循环、条件路由、人机协同、多智能体这类复杂控制流。简单串联用 LangChain，带环的复杂编排用 LangGraph。一个系统里两者常共存，图里的节点内部就是一条 LangChain 链。

### 追问四（自补）：什么时候手写 SDK 反而最划算？

系统边界简单、需求非常明确时。就调一个模型、几个固定函数，没有多模型适配、没有复杂编排、没有跨文件的维护痛点，这时引入框架只是白增一层抽象。直接手写 SDK 更透明、更好调、成本最低。经验值：先手写跑通，等出现"换个模型要改好几处""日志到处埋"这类信号，再考虑引入框架。

### 追问五（自补）：团队能力怎么影响选型？

影响很大。框架能不能用起来，取决于有没有人驾驭得了。低代码平台对编码要求低，业务侧主导或工程资源紧张时合适；代码框架需要扎实工程能力，团队不具备就是负担。选型不能只看技术优劣，还要看"谁来维护、能不能长期维护"。经验值：小团队或业务侧主导优先平台，工程能力强的团队可以更早引入代码框架。

### 追问六（自补）：选型时怎么避免被框架的宣传带偏？

回到自己的真实需求。框架宣传通常强调"支持什么",但选型要看的是"你的场景需要什么、这个框架用起来顺不顺"。一个务实的办法是列三到五个当前最典型的任务，用候选框架各做一个最小实现，比较开发耗时、代码量和排障体验。跑出来的结果比任何对比文章都可信。经验值：别在选型阶段追求"选一个能覆盖所有未来需求的框架",未来需求会变，选一个契合当下、又留有退出通道的方案，比一步到位更现实。

## 60 秒面试回答模板

> 框架选型不看热度，看任务复杂度、团队能力和交付要求。快速原型、要生态和常见组件齐全，用 LangChain；有显式状态、循环、条件路由、人机协同、多智能体，用 LangGraph；低代码快速验证业务流程，用 Coze、Dify；系统边界简单、需求明确，直接手写 SDK 成本最低。成熟的回答不是说哪个最好，而是说什么场景用什么更划算，还要能给出迁移路径：前期用平台验证，后期把最需要定制可控的核心链路先迁到自研框架，逐步进行。判断选型成功我会看开发效率、可控性和排障、维护成本、能力匹配度这几类指标，选完先用一个真实最小任务做探针，别等全线铺开才发现不趁手。

## 加分项

- 用任务复杂度、团队能力、交付要求三个维度定性，不比热度。
- 给出四类方案的甜蜜点，对号入座而非强弱排序。
- 正面答好成功指标和迁移边界两条追问，落到可操作。
- 强调"先探针再铺开"，显示务实的验证思路。

## 常见误区

- **按热度选型**：不看任务和团队是否匹配，火的框架未必适合。
- **静态看待选型**：不考虑迁移路径，容易被框架锁死。
- **忽略团队能力**：驾驭不了的方案再强也是负担。
