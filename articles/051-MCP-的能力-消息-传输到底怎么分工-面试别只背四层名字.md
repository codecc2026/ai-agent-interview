# MCP 的能力、消息、传输到底怎么分工？面试别只背四层名字

<!-- growth-hook:v1 -->
被问到“MCP 协议由什么组成”，八成候选人会背出 Tools、Resources、Prompts 三个词就停了。可面试官要听的从来不是名词——而是这三类能力分别归谁控制、消息怎么走、传输又扮演什么角色。这题答清楚了，MCP 才算真的入门。

## 面试官为什么爱问这题

这题考的是你有没有把 MCP 当成一个协议去理解它的结构，而不是只把它当成一个"现成插件市场"。很多人用过几个 MCP Server，就以为自己懂 MCP，但让你说清它主体由哪几部分构成、各部分管什么，往往答得零散。面试官问"能力、消息、传输分别管什么"，想听到的是一个有层次的框架——角色、能力、通信、传输四层各司其职。这题还有个容易被忽略的要点：三类能力不是一回事，它们的控制归属不同，谁能决定用不用它，差别很大。前面聊过 MCP 的定位、Server 建设、接入和传输，这一篇把这些零散的点收进一个协议结构的框架里，看它们各自在协议的哪一层。

## 一句话先给结论

**MCP 的主体内容按四层讲最清楚：参与角色（Host、Client、Server）；能力类型（Tools、Resources、Prompts）；通信机制（能力发现、请求、响应、错误、通知）；传输方式（stdio、Streamable HTTP 等承载协议的通道）。还有个关键细节：Tools 偏 model-controlled，由模型自动决定要不要调；Resources 偏 application-driven，由宿主决定怎么纳入上下文；Prompts 偏 user-controlled，适合复用提示或工作流模板。按这个结构答出来，面试官能看出你理解的是协议本身，而不是只把它当插件市场。**

## 核心原理：四层结构逐层看

### 第一层：参与角色

协议先定义谁在参与。三个角色：

- **Host**：发起连接的一方，通常是 AI 应用本身，比如一个助手、一个 IDE。它管理着整个交互。
- **Client**：Host 内部的客户端，负责和某个 Server 建立连接、按协议通信。一个 Host 可以同时连多个 Client。
- **Server**：提供能力的一方，把工具、资源、提示模板按协议暴露出来。

把角色分清很重要，因为后面很多设计都落在这三者的边界上：谁发起、谁执行、谁提供能力。一个 Host 可以同时挂多个 Client、各自连不同的 Server，这种一对多关系也建立在角色划分之上。前面讲接入链路时说过"模型决策、宿主执行"，这里的 Host 和 Client 就是那个宿主侧，Server 是能力提供方，三者配合才构成一次完整的 MCP 会话。

### 第二层：能力类型

Server 能暴露三类能力，它们的定位和控制归属都不同：

| 能力 | 是什么 | 控制归属 | 典型用途 |
| --- | --- | --- | --- |
| Tools | 可被执行的动作 | model-controlled，模型决定何时调 | 查询、计算、调用外部动作 |
| Resources | 可读取的上下文 | application-driven，宿主决定纳入 | 文档、记录、配置 |
| Prompts | 可复用的提示模板 | user-controlled，用户或流程选用 | 固定提问框架、工作流模板 |

控制归属这一列是这题的精髓。三类能力虽然都是 Server 暴露的，但"谁决定用它"完全不同：Tools 是模型在推理时自己决定要不要调用；Resources 是宿主应用按需要把它读进来当上下文；Prompts 是用户或流程显式选用的模板。理解这一点，才知道为什么协议要把它们分成三类，而不是笼统叫"能力"。

### 第三层：通信机制

角色和能力定了，还要定义它们怎么对话。通信机制包括几种消息类型：

- **能力发现**：Client 问 Server"你提供什么"，Server 返回工具、资源、提示列表。
- **请求与响应**：Client 发起调用请求，Server 处理后返回结果。
- **错误**：调用失败时按约定格式返回错误信息，让对端能读懂。
- **通知**：不需要响应的单向消息，用于推送状态变化等。

这套消息机制是协议的"语法"——光有角色和能力还不够，得定义它们之间用什么消息、按什么流程交互，能力才能真正被用起来。前面讲接入四步时说的"发现能力"，用的就是这里的发现消息。

### 第四层：传输方式

最后，消息得跑在某种通道上。传输方式定义协议消息怎么承载：stdio 走标准输入输出，适合本地、进程内集成；Streamable HTTP 这类基于 HTTP 的传输，适合跨进程、跨网络。传输层是"管道"，上面三层是"管道里跑的内容"。前面专门讲过流式 HTTP 传输的优势，这里把它放回协议结构里——它是承载层，服务于上面的通信机制。

| 层 | 管什么 | 一句话 |
| --- | --- | --- |
| 参与角色 | 谁在交互 | Host、Client、Server 各司其职 |
| 能力类型 | 能提供什么 | 工具、资源、提示三类 |
| 通信机制 | 怎么对话 | 发现、请求、响应、错误、通知 |
| 传输方式 | 跑在哪 | stdio、Streamable HTTP 等通道 |

四层从"谁"到"什么"到"怎么对话"到"跑在哪"，层层递进，构成一个完整的协议框架。

## 工程实践：用四层框架定位一个具体问题

这套框架不只是背的，它能帮你定位问题出在哪一层。举个例子：一个 Client 调 Server 的工具总是失败。

按四层顺序排查。先看传输层：连接建起来了吗？stdio 的子进程起没起、HTTP 的地址通不通？传输不通，上面都白搭。再看通信层：发现消息拿到工具列表了吗？请求格式对不对？错误返回的是什么？很多"调不通"其实是发现阶段就没拿到能力，或请求消息格式不对。再看能力层：这个能力是 Tool 还是 Resource？如果它是个 Resource，却被当成 Tool 去调，当然失败，这是控制归属搞错、用错了消费方式。最后看角色层：是不是 Client/Server 的职责搞混了，谁该发起、谁该执行没分清。

这个排查顺序的价值在于自下而上：底层没通，去查上层消息是白费力气；传输通了再看消息，消息对了再看能力用没用对。经验值：多数"调不通"卡在传输层或发现阶段，先确认连接和能力列表能拿到，能省掉大量在业务逻辑里的无效排查。四层框架把问题空间切成互不包含的几块，定位时逐层排除，比凭经验乱试要稳。

```python
# 伪代码：一次典型的"发现—调用"消息流，对应通信层
tools = client.list_tools()                 # 发现：拉取 Server 暴露的工具
resp = client.call_tool(                    # 请求：发起一次工具调用
    name=tools[0].name,
    arguments={"query": "订单状态"},
)
if resp.is_error:                           # 错误：按约定格式处理失败
    handle_error(resp.error)
else:
    handle_result(resp.content)            # 响应：拿到结果
```

要点：`list_tools` 对应发现、`call_tool` 对应请求与响应、`is_error` 对应错误处理，这些是通信层的几种消息。`client`、`handle_error`、`handle_result` 是业务侧实现。具体 API 名以你用的 MCP 客户端库为准，这里只示意消息类型。

## 追问逐条作答

### 追问一：为什么说 Tools 是 model-controlled，Resources 是 application-driven？

因为它们被消费的方式不同，决定权就不同。Tools 是可执行的动作，模型在推理时根据实际需要自己决定"要不要调这个工具、传什么参数"，所以是模型控制。Resources 是可读的上下文，通常由宿主应用根据当前情况决定"要不要把这份资源读进来放进上下文"，不是模型每次自己点名要的，所以是应用驱动。分清这个，才知道同一份信息做成 Tool 还是 Resource，用法完全不同。

### 追问二：Prompts 为什么是 user-controlled？

因为提示模板通常是人显式选用的。它更像一个可复用的工作流入口——用户选了某个模板，模板里带好固定的提问结构和占位符，再填入具体参数使用。它不是模型自动触发的（不像 Tool），也不是应用悄悄注入的（不像 Resource），而是用户或流程明确选择的，所以归为 user-controlled。

### 追问三：通信机制里为什么要专门有"错误"和"通知"？

因为一次能力调用不总是成功、也不总是请求—响应这么简单。错误消息让失败按约定格式返回，对端能读懂"失败原因是什么、该怎么办"，而不是干瞪眼。通知是单向的、不需要响应的消息，用于推送状态变化这类信息——比如能力列表更新了，Server 可以主动通知 Client，而不必等 Client 来问。有这两类消息，协议才能处理异常和异步场景，而不只是最简单的请求—响应。

### 追问四（自补）：stdio 和 Streamable HTTP 在四层框架里属于哪一层？

属于最底层的传输层，是承载协议消息的通道，不改变上面三层的语义。同一套角色、能力、消息，既能跑在 stdio 上也能跑在 HTTP 上，区别只在"消息怎么传"，不在"消息是什么"。把传输明确成独立的一层，好处是协议和具体通道解耦——换传输方式，上层不用改。选型时按部署形态定：本地集成用 stdio，跨网络共享服务用 HTTP 类传输。

### 追问五（自补）：为什么说理解了四层，就不只是把 MCP 当插件市场？

因为插件市场只是表层的"有很多现成能力可用"。理解四层，你能回答更深的问题：一个能力的控制归属是什么（能力层）；它怎么被发现、怎么调用、失败怎么返回（通信层）；它跑在什么通道上、能不能跨网络（传输层）；谁在发起、谁在执行（角色层）。这些是协议的结构，决定了你能不能自己设计、排查、扩展一个 MCP 系统，而不只是配置别人做好的插件。

## 60 秒面试回答模板

> MCP 协议主体按四层讲。第一层参与角色：Host、Client、Server。第二层能力类型：Tools、Resources、Prompts，控制归属不同，Tools 偏模型控制，模型自己决定何时调；Resources 偏应用驱动，宿主决定怎么纳入上下文；Prompts 偏用户控制，用户显式选用。第三层通信机制：能力发现、请求、响应、错误、通知。第四层传输方式：stdio、Streamable HTTP 这些通道。四层从谁、有什么、怎么对话到跑在哪。这套框架也能排查问题：先传输通不通，再通信消息对不对，再看能力用没用对，最后看角色职责清不清。理解到这一层，才算懂协议本身，不只是把它当插件市场。

## 常见误区

- **只把 MCP 当插件市场**：说不出协议的四层结构，说明只停留在使用层面。
- **混淆三类能力的控制归属**：把 Resource 当 Tool 调、把 Prompt 当自动触发，都是没分清谁决定用。
- **把传输当成协议全部**：stdio 和 HTTP 只是承载通道，是四层里最底下的一层。
