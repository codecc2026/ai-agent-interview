# MCP 到底解决了什么？它和 Tool / RAG / Agent 的边界在哪？

## 面试官为什么爱问这题

这是大厂一面真实出现过的题，考的是概念边界。MCP 这两年太热，到处都在挂这个名词，结果很多人把它和 Agent、Function Calling 混成一团，答起来听着热闹其实分不清谁是谁。面试官问"它和 Tool / RAG / Agent 的边界"，就是想看你能不能给每个概念划清职责，把 MCP 放回它该在的位置——协议和生态层。前面讲 Function Calling 时特意区分过它和 MCP，前面也聊过工具、检索、Agent 各自的活；这一篇把这些放到一张图里，专门讲"统一插口"这件事到底统一了什么、和旁边几个概念怎么划界。

## 一句话先给结论

**MCP 是 Model Context Protocol（模型上下文协议），一套开放标准，规范 AI 应用如何以统一方式连接外部工具、资源和提示模板。它本质上是"模型能力接入的统一协议层"，解决的是"不同 AI 应用怎样用统一方式接外部能力"，而不是"模型能不能调工具"。可以把它看成 AI 世界的统一插口：统一的不是模型本身，而是 Host、Client、Server 之间发现、暴露和调用能力的方式。它既不是 Agent，也不是 Tool，更偏协议和生态层。**

## 核心原理：统一插口统一的是什么

### MCP 统一的是接入方式，不是模型

先把定义立住：MCP 是一套开放标准，规范 AI 应用怎么连接外部工具、资源和提示模板。它定义的是 Host、Client、Server 三者之间怎么发现能力、怎么暴露能力、怎么调用能力的一套约定。

用一个比喻更好记：它像 AI 世界的统一插口。电器只要符合插口标准，就能插到任何支持这个标准的插座上；同样，一个能力只要按 MCP 暴露出来，任何支持 MCP 的 Host 都能发现并接入它。统一的不是模型，也不是某个具体能力，而是"能力怎么被描述、怎么被发现、怎么被调用"这套方式。

MCP Server 不只会暴露 Tools，还能暴露 Resources 和 Prompts。这点是它和"工具调用"最直观的区别——它管的范围比"调一个函数"宽，还包括可读的资源、可复用的提示模板。

### 四者边界：各管一段

这道题的核心是把四个概念各归各位。记住一句话：它们不在同一个层面上，不是竞争关系。

| 概念 | 解决什么 | 所在层次 |
| --- | --- | --- |
| Tool / Function Calling | 模型如何表达"调哪个工具、传什么参数" | 模型能力 / 调用层 |
| RAG | 模型如何拿到外部知识 | 知识获取层 |
| Agent | 谁来规划、决策、调用这些能力 | 编排决策层 |
| MCP | 这些外部能力如何被标准化暴露和接入 | 协议 / 生态层 |

Function Calling 解决的是模型表达调用意图——它让模型输出"我要调哪个函数、参数是什么"这样的结构化结果，是模型侧的能力。MCP 解决的是这些能力怎么被统一地暴露出来、被不同应用接入，是协议和生态侧的标准。一个是"模型怎么表达要调"，一个是"能力怎么被标准化接进来"，完全不是一回事。之前专门区分过 Function Calling 和 MCP，这里再把它放回边界表里，就是为了不混淆。

RAG 解决的是知识获取，把外部知识检索出来喂给模型；MCP 也可以暴露 Resources 这类资源，但它的重点是"接入方式的标准"，不是"怎么检索、怎么重排"那套检索逻辑。Agent 是那个做决策的主角，负责规划、决定调什么、何时停；MCP 只是给主角提供标准化接口的"插口"，它不做决策。

### 价值：一次暴露，多处复用

MCP 偏协议和生态层，它的价值就来自这层定位：一次暴露、多处复用、统一 schema、降低接入成本。这几个价值是连在一起的：因为有了统一 schema，能力才有确定的描述格式，客户端才能自动发现它；因为能被自动发现，所以一次暴露就能被多处复用；因为多处复用摊薄了每家各写适配的成本，接入成本才降下来。把这条因果串起来讲，比单独罗列四个词更能让面试官听出你是理解这个定位，而不是背了一组口号。反过来说，如果你的场景只有一个应用接一个能力，复用和标准化都无从谈起，这时引入协议层的收益就很有限——这也是判断要不要用它时的现实依据。

一个能力按 MCP 标准暴露一次，任何支持 MCP 的 Host 都能接，不用为每个应用各写一套适配。统一 schema 让能力有确定的描述格式，客户端能自动发现和理解它。接入成本降低，是标准化带来的直接好处，这也是为什么企业会关心它，后面追问里展开。

从 Server 的角度看，暴露一个能力大致长这样（示意结构，字段按具体实现为准）：

```python
# 伪代码：一个 MCP Server 同时暴露三类能力
server = MCPServer(name="order-service")

@server.tool(description="根据订单号查询状态")       # Tools：可调用的动作
def get_order(order_id: str) -> str:
    return query_order(order_id)                      # query_order 为业务侧实现

@server.resource(uri="order://policy")               # Resources：可读取的上下文
def return_policy() -> str:
    return load_policy_doc()                          # load_policy_doc 为业务侧实现

@server.prompt(name="complaint_reply")               # Prompts：可复用的提示模板
def complaint_reply(order_id: str) -> str:
    return compose_prompt(order_id)                   # compose_prompt 为业务侧实现

server.run(transport="stdio")                        # 或 http，取决于部署形态
```

这段代码想说明的是：三类能力用同一种注册方式暴露给任何 Host，Host 侧不需要知道它们内部怎么实现。注意 Tools、Resources、Prompts 的划分：前者是"能被执行的动作"，中间是"能被读取的上下文"，后者是"能复用的提示模板"。变量和函数都是业务侧自定义，这里只示意暴露方式。

## 工程实践：判断一个东西是不是 MCP

面试里想说清边界，一个好用的方法是给出"反例判断"：什么情况下一件事不是 MCP 该管的。

| 场景 | 该不该用 MCP | 说明 |
| --- | --- | --- |
| 让模型输出要调用的函数和参数 | 不是 MCP 的活 | 这是 Function Calling，模型侧能力 |
| 把公司文档检索出来喂给模型 | 不是 MCP 的活 | 这是 RAG，检索逻辑在应用层 |
| 决定先查订单还是先退款 | 不是 MCP 的活 | 这是 Agent 的决策编排 |
| 把一个内部系统能力按统一标准暴露给多个 Host | 是 MCP 的活 | 统一暴露、发现、接入 |
| 让工具同时带出可读取的资源和提示模板 | 是 MCP 的活 | Server 可暴露 Tools/Resources/Prompts |

这张表的判断逻辑是：只要涉及"能力怎么被标准化描述、发现、暴露、接入"，就是 MCP 的活；涉及"模型怎么表达调用""怎么检索知识""谁来做决策"，分别是另外三个概念的活。面试官如果追问一个具体场景归哪类，用这把尺子去套就行。

## 追问逐条作答

### 追问一：MCP Server 通常暴露哪些能力？

三类。一是 Tools，可被模型调用的函数或动作；二是 Resources，可读取的上下文资源，比如文件内容、数据记录；三是 Prompts，可复用的提示模板。很多人的印象停在"MCP 就是暴露工具"，其实资源和提示模板同样是 Server 能暴露的东西，这也是它比单纯的"工具调用"覆盖面更宽的地方。

### 追问二：STDIO 和 HTTP 传输怎么选？

两者是 MCP 的传输方式，适合不同部署形态。STDIO 走标准输入输出，适合本地、单机、进程内集成的场景：客户端和服务端在同一台机器上，启动一个子进程通信，简单直接。HTTP 适合跨进程、跨网络的场景，服务端是独立部署的服务，多个客户端通过网络访问。经验值：本地开发工具、单机助手多用 STDIO；要把能力做成共享服务给多个应用用，选基于 HTTP 的传输。具体选型看你是在本机集成还是跨网络接入。

### 追问三：为什么企业会关心 MCP？

因为它降低了"能力接入"的重复成本。企业里往往有一堆内部系统，比如订单、库存、工单、知识库，每个都想让 AI 应用用上。没有统一标准时，每个 AI 应用都要为每个系统写一套适配，N 个应用接 M 个系统就是 N×M 的工作量。MCP 让系统按统一标准暴露一次，各应用按统一方式接入，复杂度从 N×M 降到 N+M 的量级。统一 schema 还带来可发现、可治理的好处。这是生态层的价值，不是单次调用能体现的。

### 追问四（自补）：MCP 和 Function Calling 到底怎么一句话区分？

Function Calling 是模型能力，解决"模型怎么表达我要调哪个工具、传什么参数"；MCP 是协议标准，解决"这些工具能力怎么被统一暴露、发现、接入"。一个发生在模型输出侧，一个发生在能力接入侧。之前专门区分过这两者，这里再强调：它们不在同一层，谈不上互相替代。

### 追问五（自补）：用了 MCP 是不是就不需要 RAG 了？

不是，两者不在一个层面。RAG 是一套检索和生成的流程，解决"怎么把外部知识找出来喂给模型"，里面涉及切块、检索、重排这些具体环节。MCP 可以暴露 Resources 这类资源，但它定义的是"资源怎么被标准化暴露和接入"，不负责检索那套逻辑。一个系统里两者常并存：RAG 流程负责把知识查准，MCP 负责把这个能力以统一接口提供给不同 Host。

## 60 秒面试回答模板

> MCP 是 Model Context Protocol，模型上下文协议，一套开放标准，规范 AI 应用怎么统一连接外部工具、资源和提示模板。它做的是模型能力接入的统一协议层，像 AI 世界的统一插口，统一的是 Host、Client、Server 之间发现、暴露、调用能力的方式，不是模型本身。边界是：Function Calling 管模型怎么表达调哪个工具、传什么参数；RAG 管模型怎么拿到外部知识；Agent 管谁做决策；MCP 管能力怎么被标准化暴露和接入。Server 除 Tools 还能暴露 Resources 和 Prompts。它偏协议和生态层，不是 Agent 也不是 Tool，价值在一次暴露、多处复用、降低接入成本。

## 加分项

- 用"统一插口"这个比喻，并点明统一的不是模型而是接入方式。
- 把四个概念放进同一张边界表，各归其位，不说成竞争关系。
- 主动点出 Server 还能暴露 Resources 和 Prompts，不止 Tools。
- 用 N×M 降到 N+M 解释企业价值，落到生态层的复用。

## 常见误区

- **把 MCP 等同于 Agent 或 Tool**：它偏协议和生态层，管的是能力怎么被标准化接入，不做决策也不是模型调用能力本身。
- **以为 MCP Server 只暴露工具**：还能暴露 Resources 和 Prompts，覆盖面比"调函数"宽。
- **混淆 Function Calling 和 MCP**：前者是模型侧的表达能力，后者是接入侧的协议标准，不在同一层。
