# 如果让你设计一个客服智能体，你会优先考虑哪些能力？

<!-- growth-hook:v1 -->
客服智能体不是“FAQ 接个大模型”就完事。查订单、走退款、开工单、安抚情绪，背后都是真流程、真权限、真责任。这题看的是你能不能分清哪些该自动化、哪些必须留人工兜底。

## 面试官为什么爱问这题

这题高频且偏难，考的是业务型 Agent 的设计能力。很多人把客服机器人想成"问答 + 知识库"，面试官想听的恰恰是客服场景的复杂性——它同时涉及 FAQ、订单查询、退款流程、工单流转和情绪安抚，既要能回答，也要能查状态、调接口、补资料，还要在不确定时及时转人工并完整交接上下文。更关键的是最后那句：上线后要持续复盘高频未解决问题、误判意图、知识缺口和转人工原因，系统才会越做越稳。前面聊过意图识别路由、工作流设计，这一篇把它们落到客服这个具体业务场景。

## 一句话先给结论

**优先考虑五类能力：意图识别、知识检索、流程执行、人机协同和复盘闭环。客服场景不是简单问答，它往往同时涉及 FAQ、订单查询、退款流程、工单流转和情绪安抚，所以系统既要能回答，也要能查状态、调接口、补资料，还要在不确定时及时转人工，并把上下文完整交接过去。上线后还要持续复盘高频未解决问题、误判意图、知识缺口和转人工原因，这样系统才会越做越稳，而不是只在演示时好看。**

## 核心原理：五类优先能力

### 意图识别：先搞清用户要干什么

客服入口的请求五花八门——问产品、查订单、要退款、投诉、闲聊。意图识别要把它们分到不同处理链路。前面专门讲过意图识别和任务路由，这里的关键是客服场景的意图特别多、特别杂，而且用户表达常常含糊、带情绪，识别难度比一般场景高。识别错了后面全错，所以这是第一优先。

### 知识检索：回答有据可依

FAQ、产品文档、政策条款这些要靠知识检索，让回答基于真实资料而不是模型瞎编。前面讲 RAG 时说过引用和拒答，客服场景里答错政策、答错价格会直接引发投诉，知识检索的准确性和引用可追溯尤其重要。检索不到时要能承认不知道，而不是硬编一个答案。

### 流程执行：不只是回答，还要办事

订单查询、退款、工单流转这些不是"回答"能解决的，要查状态、调接口、走流程。这是客服 Agent 和普通问答机器人的分水岭——它能真正办事。前面讲工具调用和工作流时说过执行层，这里对应客服的具体业务流程。流程执行要接后端系统、要处理状态、要保证幂等，比回答问题复杂得多。

### 人机协同：不确定就转人工，且要完整交接

客服场景里"知道什么时候不该自己答"很重要。用户情绪激动、问题超出能力、涉及高风险操作、多次解决不了——这些情况要及时转人工。而且转人工不能把上下文丢掉，要把之前的对话、查到的信息、已经尝试过的方案完整交接过去，让人工客服能接着处理，而不是让用户从头再说一遍。

### 复盘闭环：上线后持续变稳

持续复盘高频未解决问题、误判意图、知识缺口和转人工原因。这是让系统越做越稳的机制——高频未解决问题提示该补知识或补能力；误判意图提示该调路由规则；知识缺口提示该补文档；转人工原因提示哪些场景自动化还不行。前面讲评测闭环时说过"badcase 反过来驱动迭代"，客服场景正是这套闭环最该落地的地方。

| 能力 | 解决什么 | 缺了会怎样 |
| --- | --- | --- |
| 意图识别 | 分清用户要什么 | 路由错，后面全错 |
| 知识检索 | 回答有据可依 | 答错政策、瞎编答案 |
| 流程执行 | 查状态、调接口、办业务 | 只会答不会办 |
| 人机协同 | 不确定转人工并交接 | 硬撑着答，激化问题 |
| 复盘闭环 | 上线后持续改进 | 只在演示时好看 |

人机协同是这五类里最考验设计的，因为它要解决"什么时候不该自己答"。把转人工的触发条件列清楚，比笼统说"不确定就转"更可操作：

| 触发条件 | 典型情况 | 为什么要转 |
| --- | --- | --- |
| 能力边界外 | 超出知识库和流程覆盖 | 系统确实办不了 |
| 高风险动作 | 大额退款、账户安全 | 代价高，需人工把关 |
| 情绪信号 | 用户明显不满、要求转人工 | 硬撑会激化情绪 |
| 多次失败 | 反复解决不了 | 自动化此路不通 |
| 置信度低 | 意图不清、检索无可靠答案 | 硬答不如交给人 |

### 客服场景的特殊性

题库点出客服"不是简单问答"，它同时涉及 FAQ、订单查询、退款流程、工单流转和情绪安抚。这几类能力的性质完全不同——FAQ 是知识问题、查订单是查询问题、退款是流程问题、情绪安抚是对话技巧。一个系统要同时处理好这几类，不能只靠一个问答模型。这也是为什么设计时要按能力拆，而不是做一个"万能问答机器人"。

## 工程实践：转人工条件怎么设计

五类能力里"人机协同"最考验设计，落到具体条件：

**能力边界外。** 问题超出系统能处理的范围——不是知识库能覆盖的、不是设计好的流程能办的，转人工。

**高风险动作。** 大额退款、争议处理、涉及账户安全的操作，让人工把关，别让 Agent 自动执行。

**情绪信号。** 用户明显不满、反复表达负面情绪、说了"转人工"，不要硬撑着自动应答，直接转。

**多次失败。** 同一问题反复解决不了、用户表示"没解决"，说明自动化这条路走不通，转人工。

**置信度低。** 意图识别不确定、检索不到可靠答案、决策没把握，转人工比硬答更安全。

```python
# 伪代码：转人工判断与上下文交接
def should_handoff(state):
    if state.out_of_scope or state.high_risk:      # 能力边界外 / 高风险
        return True
    if state.negative_emotion or state.repeat_fail: # 情绪 / 多次失败
        return True
    if state.intent_confidence < THRESHOLD:        # 置信度低
        return True
    return False

def handoff(state):
    package = {
        "dialog": state.dialog,                     # 完整对话
        "found_info": state.retrieved,              # 已查到的信息
        "tried": state.tried_actions,               # 已尝试的方案
        "reason": state.handoff_reason,             # 为什么转人工
    }
    return human_agent.receive(package)

# THRESHOLD / human_agent 为业务侧实现
```

要点：转人工判断覆盖多种条件，交接包把对话、已查信息、尝试过的方案、转接原因都带上——让人工能接着处理，不用用户重说。变量都是业务侧实现。

## 追问逐条作答

### 追问一：转人工条件怎么设计？

覆盖五类情况：能力边界外的问题、高风险动作、明显的负面情绪、同一问题多次失败、判断置信度低。只要命中一条就转，别让系统硬撑——客服场景里"答不好还硬答"比"承认处理不了"更伤用户。转的时候要带完整上下文：对话历史、查到的信息、尝试过的方案、转接原因。经验值：转人工率本身是评测指标，太高说明自动化能力不足，太低可能该转的没转、在硬撑。

### 追问二：客服场景为什么更需要长期记忆或用户画像？

因为客服是持续关系，不是一次性问答。知道用户是谁、历史买过什么、之前提过什么工单、偏好什么沟通方式，能大幅减少重复询问、让回答更贴合。比如用户说"上次那个问题"，系统要能调出上次的处理记录。前面讲记忆分层时说过长期记忆存偏好、画像、历史结论，客服正是这些最有用的场景。但要注意权限——用户画像只能用于服务该用户，不能串给他人。

### 追问三：如何做满意度和闭环评估？

满意度可以显式收集，对话结束请用户评分；也可以看隐式信号，比如是否重复追问、是否转人工、是否投诉。闭环评估是把这些和具体环节关联：满意度低的是哪类问题、误判意图集中在哪、知识缺口在哪些文档、转人工原因分布如何。前面讲评测闭环时说过"badcase 反向驱动迭代"，客服里就是拿这些数据去补知识、调路由、改流程。经验值：定期复盘高频未解决问题，它们是系统能力缺口最直接的指示。

### 追问四（自补）：客服 Agent 为什么要特别处理情绪？

因为客服对话不只是信息传递，还是情绪互动。用户带着不满来时，一个"正确但冰冷"的答案可能让情绪更糟。系统要能识别负面情绪、先安抚再解决问题，情绪强烈时及时转人工让真人接手。前面讲意图识别时说过客服表达常带情绪，这里是它的另一面——情绪不只是识别难点，也是处理对象。

### 追问五（自补）：流程执行为什么要强调幂等？

因为退款、改单这类操作有真实副作用，重试可能造成重复执行。网络抖动导致"没收到成功反馈"，系统重试一次——如果第一次其实成功了，就退款两次。客服场景涉及钱和订单，这类错误代价高。前面讲浏览器自动化和行为边界时都提过幂等，这里同样适用：关键操作前先查状态，确认没做过再执行，或设计成天然可重复。

## 60 秒面试回答模板

> 客服场景不是简单问答，同时涉及 FAQ、查订单、退款、工单和情绪安抚，我会优先五类能力。意图识别先把五花八门的请求分到不同链路；知识检索让回答基于真实资料、检索不到就拒答；流程执行负责查状态、调接口、真办事，这是和普通问答机器人的分水岭；人机协同在能力外、高风险、情绪激动、多次失败或置信度低时及时转人工，并把对话、已查信息、尝试过的方案完整交接；复盘闭环持续看高频未解决问题、误判意图、知识缺口和转人工原因，驱动系统迭代。转人工率本身也是指标，太高说明自动化不足，太低可能在硬撑。这样系统才会越做越稳，不是只在演示时好看。

## 常见误区

- **当成问答机器人**：忽略查状态、调接口、走流程的执行能力。
- **该转人工时硬撑**：答不好还硬答比承认处理不了更伤用户。
- **转人工不交接上下文**：让用户从头再说一遍，体验极差。
