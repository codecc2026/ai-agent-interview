# 什么是 Lost in the Middle？它对 RAG 设计有什么启示？

## 面试官为什么爱问这题

这道题听着像常识——谁不知道中间容易被忽略。但它其实是道分水岭题：只会调 top_k 的人答出来是「少放点就行了」，真正做过 RAG 调优的人会把它拆成三问——位置偏置从哪来、怎么验证是位置问题而不是召回问题、工程上怎么把证据摆到模型真读得进去的地方。面试官问它，测的是你对注意力机制有没有直觉、有没有做过归因（把「答错」拆成召回、排序、组装三类原因）、会不会用一个现象反推设计。前几篇分别讲了流水线（第 15 篇）、权限与引用（第 13 篇）、接入 Agent（第 16 篇），本篇补最容易被跳过的一环：**证据进来之后，摆在哪里**。

## 一句话先给结论

**长上下文不等于高质量上下文：模型对上下文的利用是位置敏感的，开头和结尾的信息更容易被用上，中间的关键证据常常「看见了却没用好」，所以 RAG 的正确做法不是塞更多，而是先筛、再排、把最强证据放到模型最容易取用的位置。**

## 核心原理：为什么「放进去了」不等于「用上了」

### 现象本身：一条 U 形曲线

把同一份关键证据放在上下文的不同位置、其余内容保持不变，反复测同一个问题，准确率通常呈现「两头高、中间低」的走势——这就是 Lost in the Middle 描述的现象。注意它讲的是**利用效率**，不是**可见性**：中间那段内容确实被编码进了上下文，只是生成时分配给它的权重不够，于是答案「沾了一点边、但结论错」。

这类 badcase 特别难归因：答案和证据高度相关，既不像幻觉，也不像召回失败。很多人第一反应是「检索没查准」，去换 embedding、换模型、加数据，折腾一圈准确率不动——因为问题根本不在检索侧。

### 为什么会这样：三层机制

**第一层，注意力是零和的。** 生成每个 token 时，模型要把注意力分配到全部上下文上，权重经过归一化。上下文从 2K 涨到 20K，可分配的位置翻了十倍，单条证据能分到的份额被摊薄。这不是「模型记不住」，而是「分母变大了」。

**第二层，位置先验很可能来自训练分布。** 模型见过的文本里，开头往往是任务定义、系统指令、文档标题，结尾往往是「现在请回答」这类提问，中间大量是背景叙述。久而久之它学到一个先验：**开头和结尾更可能承载「要做什么」和「要答什么」，中间更可能是「背景」**。把黄金证据放在中间，等于让它被自动归进「背景」这一类。

**第三层，中间位置缺少角色信号。** 开头的证据紧邻指令，模型知道它是「依据」；结尾的证据紧邻问题，模型知道它是「刚看过的材料」；中间的片段两边都不挨着，语义上最像「路上经过的风景」。这也是为什么**结论前置**有效——把结论挪到开头，等于把它从背景区搬进了指令区。

### 边界：什么时候这条规律最凶、什么时候可以忽略

- **上下文长度**：几 K 以内，位置差异在小样本上通常测不出来；十几 K 以上、证据条数多时才明显。经验值上，单次组装的证据超过 8～10 条、上下文超过 8K 后，位置效应开始稳定可测。
- **任务类型**：单点抽取式问答（「退款时效是几天」）最敏感，只要一条证据，位置决定生死；聚合式任务（「对比这三份合同的责任条款」）没那么敏感，因为它本来必须扫全文，但会退化成「只对比了前两份」。
- **重排强度**：rerank 已经把真正有用的三条顶到前面，位置问题被顺带解决了一半；反之进了上下文却不排序、一塞十几条，等于主动制造中间噪声。
- **模型侧**：经过长上下文专项训练的模型会削弱这个效应，但通常不消除（定性判断，没有可靠的通用数字）。工程上不能假设「换个模型就好了」。

## 横向对比：四种「检索到了还是答错」

把「答错」按链路拆开，比笼统说「效果不好」有用得多。下面是排查顺序：

| 失效环节 | 典型症状 | 怎么验证 | 对策 |
| --- | --- | --- | --- |
| 召回未命中 | 答案完全无关，或答「知识库里没有」 | 用标准答案里的原句去检索，看能否进 top_k | 改切块、补 query 改写、换 embedding |
| 命中但被截断 | 正确片段在 top 20 里，但不在 top 5 | 把 top_k 临时开到 50，看正确片段的排名 | 上 rerank，别靠加大 top_k |
| 进上下文但位置不利 | 正确片段在，答案沾边但结论错 | 只挪动这条片段的位置（头 / 中 / 尾），看准确率变化 | 位置感知组装、结论前置 |
| 进上下文但被淹没 | 多条相似片段互相干扰，答案混入邻近细节 | 只保留这一条、删掉其他，看是否正确 | 减少进上下文的条数、去重、按主题聚簇后择优 |

第三、第四行最容易混：位置不利是「单条证据也答不对」，被淹没是「多给几条反而更差」。验证方法不同——前者做**位置替换实验**（内容集合不变，只换顺序），后者做**消融实验**（逐条删，看哪条在拖后腿）。两个实验都很便宜，一天能跑完，比盲调参数有效得多。

## 横向对比：上下文组装的四种策略

| 策略 | token 成本 | 位置风险 | 延迟 | 适用 |
| --- | --- | --- | --- | --- |
| 全塞（进上下文十几条、不排序） | 最高 | 最高，中间大量噪声 | 高 | 几乎不推荐，只在离线对照实验里用 |
| 相关度降序截断（重排后只留 3～5 条） | 低 | 中，最强证据在开头、尾部空着 | 中 | 单点抽取型问答的默认解 |
| 两头夹心（强证据前置 + 结论尾部核对） | 低 | 最低 | 中 | 依赖一两条硬证据的高价值问答 |
| 分阶段检索（先定位主题，再就子问题二次检索） | 中 | 低 | 高（多一次往返） | 多跳、聚合类问题 |

「两头夹心」值得解释一句：它不是把证据复制两份（浪费 token，还可能引出矛盾表述），而是**前面放原始证据、尾部放一条由证据推出的结论或核对清单**。开头给「依据」，结尾给「要交付什么」，两个高权重区都被占住，中间的次要证据即使被忽略也不影响正确性。

再按任务类型看一层：

| 任务类型 | 位置敏感度 | 主要风险 | 应对 |
| --- | --- | --- | --- |
| 单点抽取（时效、金额、型号） | 高 | 证据在中间被忽略 | 重排后留 3～5 条 + 强证据前置 |
| 多跳推理（B 依赖 A 的结果） | 中高 | 第二跳证据被挤到中间 | 分阶段检索，每跳单独组装 |
| 聚合对比（多文档比对） | 中 | 只覆盖了前几份 | 按文档分组，先摘要再汇总 |
| 长文摘要 | 低 | 漏掉中段章节 | 分段摘要 + 二级汇总，别一次塞完 |

## 工程实践：位置感知的上下文组装

落地时「摆位置」必须写进代码，不能靠 prompt 里一句「请重点参考以下资料」。下面是一个可直接照抄结构的组装函数（伪代码，字段名为通用写法）：

```python
# 伪代码：位置感知的上下文组装
TOKEN_BUDGET = 6000        # 证据预算（token），经验值：占整窗 30%～50%
HEAD_SLOTS = 3             # 前置强证据条数，经验值 2～3
TAIL_SLOTS = 1             # 尾部结论 / 核对条数

def assemble(query, candidates, budget=TOKEN_BUDGET):
    # 1) 去重：同一文档的相邻 chunk 只留信息量最大的一条
    uniq = dedup_by_doc(candidates, keep="max_score")
    # 2) 排序：用 rerank 分数，不要用向量相似度
    ranked = sorted(uniq, key=lambda c: c.score, reverse=True)
    # 3) 装填：单条上限 500 字，装不下就跳过，不截半句
    head, tail, used = [], [], 0
    for c in ranked:
        cost = count_tokens(c.text[:500])
        if used + cost > budget:
            continue
        if len(head) < HEAD_SLOTS:
            head.append(c); used += cost
        elif len(tail) < TAIL_SLOTS:
            tail.append(c); used += cost
        # 其余候选直接丢弃：不进中间区
    # 4) 组装：头（证据）+ 尾（核对清单），中间不留「可能相关」的填充
    return build_prompt(
        query=query,
        evidence=[f"[{i+1}] {c.text}" for i, c in enumerate(head)],
        checklist=tail[0].text if tail else None,
    )
```

四个必须注意的点：

**一、别把「可能相关」放进中间区。** 上面代码的 `else` 分支是直接丢弃而不是塞进中部，这是刻意的。中间区是最贵的死区，放进去的每一条都在稀释前排证据的权重，收益为负。

**二、score 要用 rerank 的分，不要用向量相似度。** 向量相似度衡量「语义接近」，rerank 衡量「能不能回答问题」，两者在排序上经常打架（第 15 篇对比过召回与重排的分工）。用错分数，前置的三条可能只是「字面很像」的三条。

**三、编号是低成本的强约束。** 给每条证据编号 `[1] [2] [3]`，要求答案逐句标注来源编号，通常能提升中间证据的利用率——模型必须回到那一条去取内容，而不是扫一遍凭印象写。这条技巧一般比在提示词里多加一句「请仔细阅读」更有效。

**四、预算要留余量。** 只按「证据预算」算会翻车：对话历史、工具返回、输出长度都在同一个窗口里。经验值上，证据占用控制在整窗的 30%～50%，否则历史一变长，最先被挤掉的恰恰是你精心安排的前置顺序。

一个具体的线上信号：如果 badcase 里「答案包含正确片段的关键词、却把两个相似片段的属性串了」占比偏高，基本可以判定是中间区噪声叠加位置不利，先把进上下文的条数收到 5 以内、清空中间区，再观察。

## 追问逐条作答

### 追问一：怎么证明是「位置问题」，而不是「检索不准」？

做**位置替换实验**：固定同一组证据（比如 5 条，其中 1 条是标准答案依据），只改变这条的位置——放第 1 条、第 3 条、第 5 条，其余内容不变，跑同一批固定问题（经验值 30～50 条就能看出趋势）。如果第 1 条和第 5 条的准确率明显高于第 3 条，就是位置效应；三种位置都答错，问题在召回或证据本身不含答案。这个实验的关键控制变量是**内容集合不变、只变顺序**，否则测出来的是内容差异。

### 追问二：那是不是把进上下文的条数从 20 降到 5 就行了？

方向对，但砍条数只解决「减少中间区」，不解决「最强证据没排到最前」。经验值上：重排后留 3～5 条、排序来自 rerank，能解决大部分单点抽取型问题——第 15 篇给的区间是重排后留 3～8 条，在位置效应明显的场景往下沿取。多跳或聚合任务砍到 5 会直接丢证据，这类任务的解法是**分段组装**（每跳、每份文档各组装一次），而不是一个更小的全局条数。副作用要盯住召回率：命中率随候选条数单调上升，砍太狠会把本来能答对的问题变成「查不到」。

### 追问三：rerank 能不能彻底解决这个问题？

不能，两者职责不同。rerank 决定**谁能进上下文**，位置策略决定**进来之后摆在哪**。rerank 做得好，前置几条确实是最强证据，位置问题被顺带缓解；但只要证据超过 2～3 条，或者必须保留一段长文档原文，中间区就一定存在。而且 rerank 自己有天花板：它按 query 与片段的匹配度打分，对「需要多条证据拼起来才能回答」的问题，单条分数都不高，排序结果接近随机——这种场景位置策略救不回来，得换检索范式。

### 追问四：多轮对话里历史越来越长，也适用这个规律吗？

适用，而且更严重。历史消息天然按「越靠后越相关」排列，中间那几轮的关键约束（用户早先说的「预算不超过 2 万」）恰好落在最容易被忽略的位置。常见做法是三层：近期若干轮保留原文；更早的轮次压成结构化摘要（保留实体、约束、已确认结论，丢掉寒暄与试错过程）；贯穿全程的硬约束（预算、权限、输出格式）单独提到系统区，不依赖历史。判断标准很直接：用户中途回头说「我刚才说过不能超过两万」而系统没接住，说明历史处理有洞。

### 追问五：现在动辄 128K、1M 上下文，这题还成立吗？

依然成立，只是形态变了。窗口变大解决的是「装不装得下」，位置偏置解决的是「装了用不用得上」，两者不是同一个问题。窗口越大中间区越宽，顺手塞进去的噪声也越多——第 12 篇讲过超长上下文在容量、经济、治理三个层面的现实约束，这里补一条质量层面的：**能装 100 万 token，不代表每条都影响决策**。所以长上下文的正确用法是「少而准」，而不是「多而全」，这跟 RAG 的筛选逻辑本来就是同一件事。

### 追问六：需要综合多份材料的任务（比如对比三份合同），没法只前置一条证据，怎么办？

这类任务的核心不是摆位置，而是**改结构**：先分组、再摘要、最后汇总。具体是每份文档各自做一次抽取（只回答「这份文档里责任条款是什么」），把结果压成同构的结构化条目（字段一致才便于横向对比），再让模型在「三份摘要 + 一个对比任务」这个短上下文里做比对。这样文档内部不存在位置竞争，最终比对时上下文也很短。代价是多几次模型调用、延迟上升；收益是对比结论可核对——每条都能追到「第几份文档的第几条」，比让模型在几千字里自己找可靠得多。

## 60 秒面试回答模板

> Lost in the Middle 说的是模型对上下文的利用是位置敏感的：开头和结尾的信息更容易被用上，中间那段关键证据常常「看见了但没用好」。机制可以拆三层——注意力是零和的，上下文越长单条证据分到的权重越少；训练分布让模型形成「开头是任务、结尾是问题、中间是背景」的先验；中间位置还缺少角色信号。所以 RAG 不能靠塞更多 chunk 解决，做法是先 rerank 过滤、再位置感知地组装：强证据前置、结论或核对清单放尾部、中间区不留「可能相关」的填充。验证我一般做位置替换实验，固定内容只换顺序，看准确率是否随位置波动。长上下文模型会削弱但不消除这个效应，别指望换模型解决。

## 加分项

- 能区分「位置不利」和「被噪声淹没」两种失效，并给出不同验证实验（换顺序 vs 逐条消融），这是很多人答不出的分界线。
- 主动提到「编号 + 逐句标注来源」这种低成本约束，说明你知道用输出格式反向约束模型去读中间证据。
- 把现象接回容量与成本：长窗口不等于高质量上下文，第 12 篇的经济账和这里的位置账要一起算。
- 指出聚合类任务必须改结构（分组摘要再汇总），而不是在单次组装里硬塞，体现「换范式而非调参数」的判断力。

## 常见误区

- **把它当「模型记性差」**：说成「模型记不住长文本」，掩盖了真正的原因（权重摊薄与位置先验），也导不出任何工程动作。
- **用加大召回条数来「提高召回」**：在位置敏感的链路里，多加的条目大多落在中间区，反而拉低准确率，典型现象是「资料给得越多答得越差」。
- **只改 prompt 不改组装**：在提示词里写「请重点参考中间的资料」作用有限，真正的杠杆在代码里的排序与摆放。
