# 什么是向量数据库？它和传统数据库有什么区别？为什么不能只用 MySQL？

## 面试官为什么爱问这题

这题看着基础，实际是个分水岭：它考察的是候选人有没有摸过检索这一层的地基。一类候选人答「向量数据库就是存向量的」，下一问「MySQL 也能存向量，为什么要多一个库」就卡住——说明 RAG 是调接口调出来的，没想过召回背后发生了什么。另一类能从索引结构讲起：为什么 B+ 树管不了高维距离、暴力检索的计算量随数据量怎么涨、过滤和召回怎么搅在一起。面试官想筛的是后一类，因为检索设施的选择直接决定召回上限和成本结构，前面聊过的流水线、切块、混合检索，全都跑在这层地基上。

之前讲完整流水线和混合检索时，向量库一直是当黑盒用的：切块往里塞，top_k 从里取。这篇把黑盒拆开，顺带正面回答那个经典追问——为什么不能只用 MySQL。

## 一句话先给结论

**向量数据库是专门面向「相似度检索」的存储系统：向量、原始内容、元数据存在一起，用近似最近邻（ANN）索引把「找最像的 K 条」从全库扫描压到近实时，再配元数据过滤、混合检索、增量写入这些检索专用能力。它和 MySQL 是分工关系不是替代关系：结构化条件、事务、精确过滤走传统数据库，语义召回走向量库，两边靠元数据里的 doc_id 桥接。只用 MySQL 的问题不在「存不下」，而在检索这一步会退化成暴力扫描，规模一上来延迟和工程复杂度都失控。**

## 核心原理：从「查得准」到「查得像」差在哪

### 传统数据库的索引为什么帮不上忙

MySQL 的主力索引是 B+ 树，它高效的前提是「一维有序」：等值和范围查询都能靠有序性剪掉大半搜索空间。而相似度检索的问题是——给定一个 d 维向量，找距离最小的 K 条。高维空间里的距离没有全序关系，无法预先排好序再剪枝，B+ 树这套优势直接作废。LIKE 和全文索引匹配的是字符串字面或分词，回答「含不含这个词」，回答不了「语义像不像」——「报销流程」和「费用审批怎么走」没有一个字相同，但用户预期它们命中同一段文档。

### 向量数据库的三件套

一件事要做到「专门面向」，就得把存储、索引、接口整条链都为它重新设计。存储上，向量、原文、元数据存在同一条记录里，召回即拿到可用的上下文，不用回表拼接。索引上，用 ANN 结构（HNSW 一类的图索引、IVF 一类的倒排量化是两个主流家族，取舍明天单独展开）替代 B+ 树，接受少量漏召回，换取延迟不随数据量线性恶化。检索接口上，top_k 近邻、元数据过滤、混合检索（稠密加稀疏）做成原生能力，不用上层自己拼。

### 「能存」不等于「能用」

把 embedding 存进 MySQL 当 BLOB，完全可行：全取出来在内存里算一遍余弦距离、排个序，几千条数据毫秒级出结果。问题出在增长曲线上——暴力检索的计算量等于条数乘维度，随条数线性上涨，没有任何剪枝。经验值：十万条以内内存暴力通常扛得住；到百万级，单次检索从毫秒级涨到秒级（视维度与硬件浮动），线上问答这种高频场景就没法用了。ANN 索引的价值就是把这条曲线压平：牺牲一点召回率，换数量级级的延迟下降。

### 边界：向量数据库不是检索层的全部

向量库只解决「存与召回」这一段。切块质量、查询改写、重排序、生成，全在它外面；Embedding 模型也不归它管。之前讲流水线时定的口径——召回池 20～50 条、重排后 3～8 条进上下文——是检索策略层的决定，向量库只负责把这 20～50 条又快又不太漏地吐出来。选库选得再好，也只是把地基打平，上层策略一样省不掉。

## 横向对比

先看两类数据库在根本维度上的差异：

| 维度 | 传统数据库（MySQL） | 向量数据库 |
| --- | --- | --- |
| 数据模型 | 行、列、约束、事务 | 向量 + 原文 + 元数据 |
| 查询范式 | SQL：精确匹配、范围、JOIN | top_k 近邻 + 过滤 + 混合检索 |
| 索引结构 | B+ 树等一维有序索引 | ANN 图索引 / 倒排量化（HNSW、IVF 一类） |
| 擅长 | 精确过滤、事务一致性、结构化查询 | 语义相似召回、大规模近邻搜索 |
| 短板 | 相似度检索退化为暴力扫描 | 复杂 JOIN、事务、精确报表 |
| 典型操作 | 更新一条订单的状态 | 召回 50 条最像的 chunk |

再看「向量到底存在哪」的四条现实路线，这张表比「要不要向量库」这个二选一有用得多：

| 路线 | 代表形态 | 适用阶段 | 代价 |
| --- | --- | --- | --- |
| 纯关系库暴力 | MySQL 存 BLOB，内存算距离 | 原型验证、万级以内 | 规模一涨延迟失控 |
| 关系库向量扩展 | pgvector 一类插件 | 中等规模、不想多养一套设施 | 索引与生态深度不如专用库 |
| 专用向量数据库 | Milvus、Qdrant 等开源方案 | 生产级、大规模、要过滤与混合检索 | 多一套分布式设施的运维成本 |
| 内存检索库 | FAISS 一类算法库 | 实验与算法调优、单机高频 | 持久化、服务化、过滤都要自己补 |

第三张表回答「什么时候只用 MySQL 真的够」，这也是面试里展示判断力的地方：

| 场景 | 只用 MySQL 行不行 |
| --- | --- |
| 万级以内 chunk、查询频率低 | 行，内存暴力足够，还省一套运维 |
| 强结构化过滤为主、语义检索是点缀 | 行，这本来就是关系库的主场 |
| 百万级 chunk、检索延迟有硬要求 | 不行，需要 ANN 设施扛延迟 |
| 要混合检索、多路召回、增量更新 | 硬凑很痛苦，工程复杂度反而更高 |

## 工程实践

### 两库分工的桥接设计

企业里最常见的形态就是开头结论说的：结构化条件走传统数据库，语义召回走向量库，靠元数据把两边结合起来。落到表结构上是「真相源 + 检索副本」的关系：MySQL 里放文档表、chunk 表、权限表、状态表，是唯一真相；向量库里存 chunk 的检索副本——向量、原文、以及一份元数据（doc_id、chunk_id、来源、版本、权限标签，沿用之前讲过的元数据契约思路）。

检索路径的分工写成代码最清楚：

```python
# 伪代码：两库分工的检索路径
def search(query, user, top_k=50):
    vec = embed(query)                          # 查询向量化
    hits = vdb.search(                          # 向量库只管语义召回
        vector=vec, top_k=top_k,
        filter={"version": "live"},             # 元数据过滤兜住版本口径
    )
    chunk_ids = [h.chunk_id for h in hits]
    rows = mysql.query(                         # MySQL 只管精确校验
        "SELECT chunk_id, status, owner FROM chunk "
        "WHERE chunk_id IN %s", chunk_ids)
    allowed = {r.chunk_id for r in rows
               if r.status == "active" and can_read(user, r.owner)}
    return [h for h in hits if h.chunk_id in allowed]   # 交给重排
```

权限这道墙有两种砌法：检索前用权限标签做过滤，或检索后回 MySQL 校验——之前讲企业 RAG 时展开过两者的取舍（pre-filter 保召回稳定、post-filter 保权限实时性），这里不重复。要补的一句是：top_k 取 20～50 的口径下，回库校验只是一次主键 IN 查询，成本通常低到可以忽略，别为了省这一步把权限墙砌薄了。

### 双写一致性：最容易被忽略的坑

两库并存必然引入双写，双写必有失败窗口。MySQL 写成功、向量库写失败，检索侧就出现「库里有、但永远召回不到」的幽灵数据；删除更阴险——MySQL 软删了、向量库没同步，权限校验挡住算走运，挡不住就是已下线内容被召回进上下文。工程上三个动作兜底：向量库写入失败进重试队列而不是静默丢弃；以 MySQL 为真相源做定时对账，之前讲过的文档级 hash 增量同步可以直接复用，差异集重灌即可；删除一律软删加状态标记，让过滤条件把死数据挡在召回之外，物理清理留给低峰期的批任务。

### 换模型就是换索引：重建与灰度

换 Embedding 模型等于全量重建索引——维度或语义空间变了，新旧向量在同一个索引里做距离计算没有意义。正确节奏是版本隔离：新模型全量重嵌、写入带新版本字段的独立索引；新旧索引并存期间按版本灰度切流；黄金集上召回命中率与线上 badcase 率平稳后，旧索引再保一两个版本下线。这套版本管理与之前讲过的提示词回归是同一个思路，只是对象换成了索引级。

## 追问逐条作答

### 追问一：有了向量数据库，查询改写和重排还要不要做？

要，它们根本不在同一层。向量库决定的是「召回快不快、漏不漏」；改写解决「query 与文档措辞对不上」，重排解决「召回池里谁真正该排前面」——这两个问题向量库一个都不管。之前讲排查时归因的第一刀就是把召回和生成分开看，同理，检索质量差也得先分层：召回命中但排序不对是重排的事，query 本身没表达清楚是改写的事。把检索质量全押在选库上，是这题最常见的答偏方向。

### 追问二：向量数据库和 FAISS 这类检索库有什么区别？

一个是「服务」，一个是「库」。FAISS 是单机内存里的索引算法库，管建索引和查向量这两步；持久化、元数据过滤、增量写入、分布式、高可用，全都不在它的职责里——进程一重启索引就得重建，过滤要在结果上自己二次筛。向量数据库把这些工程能力补齐：数据落盘、增量 upsert、带元数据的过滤检索、混合检索接口、副本与扩展。所以实验阶段拿 FAISS 起步非常顺，上生产要不要换，看三样东西：过滤需求、数据规模、可用性要求。

### 追问三：结构化条件到底应该在哪一边过滤？

两条路：检索前过滤（pre-filter，条件先作用于候选集再近邻搜索）和检索后过滤（post-filter，先召回扩大 top_k 再在结果上筛）。判断变量是条件的选择性：过滤后仍剩大头时，pre-filter 走向量库的过滤索引更高效；条件极挑（一筛只剩百分之几）时，ANN 索引在小候选集上会退化，post-filter 或干脆对筛后集合暴力反而更稳（经验值，需按自己数据测）。一个具体的坑是「带过滤的召回截断」——过滤加 top_k 组合下实际返回条数经常拿不满，选型评测必须带上真实元数据分布去测，裸数据排名会骗人。

### 追问四：数据规模多小的时候，可以不上向量库？

给可操作的边界。万级以内、查询频率不高、过滤逻辑简单——MySQL 或内存暴力完全够，内部工具的真实形态大把如此，这不丢人。判断变量三个：条数决定暴力延迟，QPS 决定能不能靠缓存扛，过滤复杂度决定要不要过滤索引。经验值：十万级是分水岭附近，过了十万条或者 QPS 上两位数，就该认真评估 ANN 设施。面试里主动给出「什么时候不用」的边界，比「一律上向量库」有说服力得多。

### 追问五：选向量数据库要看什么？

四个维度，不点名厂商优劣。一看索引：支不支持主流 ANN 结构、能不能按场景换索引类型；二看过滤：元数据过滤走不走索引、高选择性条件下表现如何；三看混合检索：稀疏稠密能不能在一个接口里查、要不要自己在外面拼一层；四看工程面：增量写入吞吐、副本与备份、和现有技术栈的集成成本。评测方法比维度更重要：拿自己的元数据分布和过滤条件去跑，延迟和满额率一起看——裸向量基准的排名和真实负载的排名经常是两回事（经验值）。

### 追问六：双库架构下，怎么保证向量库的数据不烂掉？

靠对账机制，不靠祈祷。三个层次：写入层，双写失败必须可观测、可重试，不允许静默丢失；对账层，定时以 MySQL 为真相源做差异检测（文档 hash 对比是最省的做法），差异集自动重灌；语义层，索引重建和模型切换都走版本字段灰度，禁止新旧向量混索——混了不报错，只是召回质量悄悄塌掉，这种问题排查起来最费时间。之前讲 RAG 排查时说过「先分层再归因」，数据腐烂属于「不用分层就能定位但要靠机制预防」的那类，事后救火不如事前埋闸。

## 60 秒面试回答模板

> 向量数据库是专门做相似度检索的存储系统：向量、原文、元数据一起存，靠 ANN 索引把「找最像的 K 条」压到近实时。它和 MySQL 是分工不是替代——B+ 树和全文索引回答「等于什么、含什么词」，回答不了「语义像不像」；向量塞进 MySQL 只能暴力扫描，十万级以内凑合，百万级延迟就到秒级了。企业常规形态是两库并存：MySQL 做真相源，管结构化条件、事务和状态；向量库做检索副本，管语义召回；靠元数据里的 doc_id 桥接，权限要么检索前用标签过滤，要么检索后回库校验。一句话：不是 MySQL 不行，是「查得像」这件事它没有对应的索引结构，规模一大就得交给专门的设施。

## 加分项

- **先答「为什么不行」再答「是什么」**：从 B+ 树的一维有序性讲到高维距离无全序，展示的是对索引结构的理解，不是背产品名单。
- **主动给「什么时候不用」的边界**：万级暴力够用、pgvector 一类中间态，说明选型是按规模和负载算出来的，不是跟风。
- **讲双写一致性与软删**：「真相源 + 检索副本」的架构关系、对账与 hash 重灌，能讲清这套的人不多，是真实生产踩过坑的痕迹。
- **点出带过滤的召回截断**：pre/post-filter 取舍加上「top_k 拿不满」这个具体故障形态，直接把话题引到检索深水区。

## 常见误区

- **把向量数据库当「能存向量的 MySQL」**：核心差异在索引结构和查询范式，不在存储本身；只答「能存向量、查询快」等于没答到点上。
- **二选一思维**：拿向量库替换 MySQL，事务、报表、精确查询全丢；正确形态是分工加桥接，各管各的强项。
- **「上了向量库 RAG 就稳了」**：它只管召回这一段，切块、改写、重排的质量问题一个都解决不了，检索质量要分层归因、分层优化。
