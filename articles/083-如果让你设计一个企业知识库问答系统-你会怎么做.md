# 如果让你设计一个企业知识库问答系统，你会怎么做？

<!-- growth-hook:v1 -->
企业知识库问答要让甲方满意，第一次答对其实没那么难——难的是长期可维护：知识会过期、索引要回滚、多租户要隔离、答不上来要能转人工。这题考的是“上线思维”。

## 面试官为什么爱问这题

这是必刷题，考的是从需求到架构的完整表达能力。企业知识库问答听起来是 RAG 的直接应用，但面试官想听的不是"接个向量库、调个模型"——而是你能不能把系统拆成数据接入、检索链路、生成链路、治理能力四层，每层说清关键设计，并且意识到企业场景真正影响长期可用性的往往不是"第一次答对"，而是知识更新、权限、回滚、多租户这些治理能力。前面聊过 RAG 上线坑、平台选型、权限与引用，这一篇把这些收束成一套从零设计企业知识库问答系统的完整表达，也是第 10 章的收官。

## 一句话先给结论

**通常按"数据接入、检索链路、生成链路、治理能力"四层设计。先把文档接入、解析、切块、向量化和索引更新机制搭好；再设计查询链路，包括 query 改写、混合检索、rerank、权限过滤和上下文组装；生成层强调基于证据回答、无依据时拒答、尽量带引用；治理层补上权限、版本、监控、评测和 badcase 回灌。企业场景还会预留转人工、知识修订、索引回滚和多租户隔离能力，因为这些往往比"第一次答对"更影响长期可用性。**

## 核心原理：四层架构

### 一、数据接入层：把知识变成可检索的索引

文档接入、解析、切块、向量化、索引更新。这是链路的最上游，源数据处理不好，后面检索生成全被拖垮。前面讲 RAG 上线坑时说过解析和切块是地基，表格读错、版式丢失、切块把语义切开，这些都会传导到最终答案。这一层还要设计索引更新机制，也就是新增文档、修改文档后索引怎么同步，是增量更新还是全量重建。

### 二、检索链路：查得准

query 改写、混合检索、rerank、权限过滤、上下文组装。用户的问题往往表达含糊、口语化，query 改写把它转成更适合检索的形式；混合检索结合关键词和语义；rerank 把最相关的排到前面；权限过滤保证只检索用户有权看的内容；上下文组装把选中的内容组织好送进模型。前面讲混合检索、重排、权限过滤放在检索前时都展开过，这里是它们在一条链路里的完整组合。

### 三、生成链路：答得准

基于证据回答、无依据时拒答、尽量带引用。这三条是生成层的核心原则——让模型的回答落在检索到的证据上，找不到依据时敢说"不知道"而不是编，回答尽量带引用让用户能核对。前面讲幻觉四道防线、讲"有引用但不忠实"时说过这些，这里作为生成层的设计要求。

### 四、治理能力：长期可用

权限、版本、监控、评测、badcase 回灌。这一层决定系统能不能长期稳定——权限保证合规、版本支持回滚、监控发现问题、评测衡量效果、badcase 回灌驱动迭代。前面讲评测闭环、可观测性、RAG 版本治理时说过这些，这里是它们作为"治理层"的整体呈现。

| 层 | 关键设计 | 决定什么 |
| --- | --- | --- |
| 数据接入 | 解析、切块、向量化、索引更新 | 知识能不能被正确检索 |
| 检索链路 | query 改写、混合检索、rerank、权限过滤、组装 | 能不能查到对的内容 |
| 生成链路 | 基于证据、无依据拒答、带引用 | 回答忠不忠实、可不可信 |
| 治理能力 | 权限、版本、监控、评测、回灌 | 能不能长期稳定可用 |

四层是骨架，但每层的投入优先级要随阶段调整：

| 阶段 | 重点层 | 原因 |
| --- | --- | --- |
| 早期验证 | 数据接入 + 检索链路 | 先让系统能查对、答对 |
| 上线部署 | 生成链路 + 治理能力 | 可信、合规、能监控 |
| 长期运营 | 治理能力为主 | 知识更新、评测回灌、多租户决定长期可用 |

### 企业场景的特殊要求

题库特别点出：企业场景还会预留转人工、知识修订、索引回滚和多租户隔离能力，因为这些往往比"第一次答对"更影响长期可用性。这句话点破了企业系统和 Demo 的区别——Demo 追求 demo 那一刻答对，企业系统要面对知识天天变、权限分部门、出错要回滚、多部门共用的现实。这些治理能力看着不像"智能"，但恰恰是能不能上线、能不能长期用下去的关键。

## 工程实践：知识更新的完整设计

追问里问"如何支持知识更新"，这是企业场景的核心工程问题，落到实现：

**变更捕获。** 文档新增、修改、删除要能感知——靠定时扫描或事件通知。

**增量处理。** 只处理变化的部分，别每次全量重建——全量慢且贵。切块变化的文档重新切块、向量化，更新索引。

**版本与回滚。** 每次索引变更留版本，出问题能回滚到上一个可用版本。前面讲知识治理时说过版本回滚要内建，这里是具体实现。

**双索引切换。** 高要求场景可以用新旧两套索引——新索引建好、验证通过后切换，出问题切回旧的，避免更新过程中服务中断。

```python
# 伪代码：知识更新的增量处理 + 版本管理
def update_knowledge(changed_docs):
    version = versions.create()                     # 创建新版本
    for doc in changed_docs:                        # 只处理变化的文档
        chunks = parser.chunk(doc)                  # 重新切块
        vectors = embedder.encode(chunks)           # 重新向量化
        version.index.upsert(doc.id, vectors)       # 增量更新索引
    if validator.check(version.index):              # 验证新索引可用
        versions.switch_to(version)                 # 切换，旧版本保留可回滚
    else:
        versions.rollback()                         # 验证不过，回滚
```

要点：增量处理、版本创建、验证后切换、失败回滚。`parser` / `embedder` / `validator` / `versions` 是业务侧实现。这段伪代码把"知识更新"从"重新跑一遍"变成了可控的版本化流程。

## 追问逐条作答

### 追问一：如何支持知识更新？

增量更新 + 版本管理 + 验证切换。感知文档变化后只处理变化的部分，别全量重建；切块、向量化、更新索引；每次变更留版本，验证通过才切换，出问题能回滚。高要求场景用双索引——新旧并行，新索引验证通过再切流。经验值：最忌讳的是直接原地改索引，改到一半出错、服务中断还没法回滚；版本化是知识更新的基本纪律。

### 追问二：如何避免用户问到权限外文档？

关键是权限过滤放在检索之前，而不是查完再过滤。查完再过滤已经让无权内容进入了系统内部，存在泄露风险；检索前过滤，让无权内容根本不参与召回。做法：按用户身份确定可见文档范围，在检索时把这个范围作为过滤条件。前面反复说过"权限过滤要放在检索之前"，企业知识库是最该严格执行这条的场景。再加一道数据库层的权限兜底——即使过滤被绕过，底层也读不到无权数据。

### 追问三：如果系统答非所问，优先排查哪里？

沿链路从上游往下游查。先看检索，用户问题有没有被正确理解、query 改写对不对、该命中的文档有没有召回、排没排到前面；检索对了再看生成，上下文组装有没有把关键内容放进去、模型有没有忠实于证据。为什么不先看模型？因为答非所问更常见的原因是检索没找对内容，而不是模型表达差。前面讲 RAG 排查时说过"从数据层开始逐层排除"，这里是同一个顺序。

### 追问四（自补）：为什么要支持转人工？

因为企业场景里"答不出来"比"答错"更安全。问题超出知识库范围、权限不足无法回答、用户明确要求人工、模型置信度低，这些情况硬答会误导用户或泄露信息，转人工才是负责任的做法。转人工时要带上下文，说清用户问了什么、系统查到了什么、尝试过什么，让人工能接手。前面讲客服 Agent 的人机协同时展开过，企业知识库同理。

### 追问五（自补）：多租户隔离怎么体现在知识库里？

不同部门、不同客户的知识要在索引和检索两层都隔离。索引层：不同租户的文档分开存，或在同一索引里用租户标识严格区分；检索层：查询强制带上租户过滤条件，确保只检索本租户内容。两道防线的道理和权限过滤一样，检索前就限定范围，而不是查完再筛。前面讲多用户沙箱时说过"看不到就读不到"，知识库里是"检索不到就不会进入答案"。经验值：租户标识要在文档接入时就打上、贯穿切块和索引全程，事后想补隔离会非常麻烦——数据混在一起就很难拆开了。

## 60 秒面试回答模板

> 我会按四层设计。数据接入层把文档解析、切块、向量化、建索引，并设计增量更新机制；检索链路做 query 改写、混合检索、rerank、权限过滤和上下文组装，关键是权限过滤要放在检索之前；生成层强调基于证据回答、无依据拒答、尽量带引用；治理层补上权限、版本、监控、评测和 badcase 回灌。企业场景还要预留转人工、知识修订、索引回滚和多租户隔离，因为这些比第一次答对更影响长期可用性。知识更新用增量加版本管理，验证通过再切换、出问题能回滚。答非所问时从检索层往上游查，先看该命中的有没有召回，再看生成有没有忠实于证据。

## 加分项

- 四层架构完整，每层关键设计清楚。
- 点出企业场景治理能力比"第一次答对"更影响长期可用。
- 知识更新给出增量、版本、验证切换的可控流程。
- 权限过滤放检索前，反复强调这条企业硬要求。

## 常见误区

- **只搭检索加生成**：忽略数据接入和治理层，系统无法长期稳定。
- **查完再过滤权限**：无权内容已进入系统，应检索前就限定范围。
- **原地改索引更新**：出错无法回滚，应版本化、验证后切换。
