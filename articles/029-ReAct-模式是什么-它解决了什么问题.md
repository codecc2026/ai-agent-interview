# ReAct 模式是什么？它解决了什么问题？

## 面试官为什么爱问这题

这题看着基础，其实是考你有没有真的看过 Agent 跑起来的样子。背得出「Thought、Action、Observation」三个词不难，难的是讲清楚**它到底补了什么的短板**——为什么光让模型想不够，为什么把工具调用写死成流程也不够。面试官顺着问一句「你项目里的 Thought 在哪」，很多人就卡住了，因为真实代码里那东西常常根本没明文打印。

还有一个隐藏考点：能不能把 ReAct 当成一种机制，而不是某个固定 Prompt 模板。把它理解成「必须在提示词里写 Thought: / Action: 三个字」的人，看到现代 Tool Calling Agent 里没有这三个字就以为不是 ReAct 了。这题的答案要能在两个层次上都站得住：机制层面是什么，代码层面长什么样。

## 一句话先给结论

**ReAct 把「推理」和「行动」交替串起来：模型先做当前判断（Thought），决定调用什么工具（Action），拿到工具返回后更新判断（Observation），循环直到任务完成。它解决的是纯生成看不到外部世界、固定流程又不能临场调整之间的夹角——适合路径不确定、要多步决策、强依赖外部信息的任务。准确地说，ReAct 是一种工作机制，不只是某个固定 Prompt 模板：现在的代码里 Thought 常常不再明文展示，换成了结构化的工具调用消息。**

## 核心原理：把「想」和「做」串成一个圈

### 纯推理的天花板在哪

只让模型在脑子里想，再一次性吐出答案，这条路有个硬边界：模型看不到外部世界。它不知道数据库里现在的值、接口返回了什么、上一步操作成没成功。知识可能过时，算数可能出错，涉及实时状态的问题基本答不准。Chain of Thought 让模型「多想几步」，提升的是推理质量，但想得再久也变不出它没看到的信息——它缺少的不是思考步骤，是**观察**。

### 固定流程的天花板在哪

另一个极端是把工具调用写成固定流程：先查 A、再查 B、最后汇总。这条路能拿到外部信息，但路径是人提前写死的，遇到计划外的情况就傻。查 A 发现结果为空，流程还是会照常查 B；B 返回了意外字段，没有分支能处理。它缺少的是**临场调整**——根据上一步的真实结果，决定下一步该干什么。

### ReAct 正好补这个夹角

ReAct 的做法是让模型在一个循环里交替做两件事：推理和行动。一轮的姿态是——Thought：根据当前掌握的信息判断下一步该做什么；Action：调用一个工具；Observation：拿到工具返回，作为新的信息进入下一轮。然后重复，直到模型判断任务完成。

它同时拿到了两边的好处：因为能行动，模型看得到真实世界，不再凭记忆猜；因为每一步之后都重新推理，路径不写死，可以根据观察随时改主意——查 A 发现为空，下一轮就决定换个关键词再查；B 返回了意外字段，模型能临时决定去查 C 确认。前面说过 Agent 的重点是「下一步由模型现场决定」，ReAct 就是把这个「现场决定」落成可执行循环的经典形式。

### 为什么说是机制，不是模板

这块是这题的分水岭。ReAct 最早是用 Prompt 约束模型按固定格式输出——提示词里写明让它按 `Thought:`、`Action:`、`Observation:` 逐行写，程序从文本里解析出动作去执行。所以很多人以为「ReAct = 这套 Prompt 格式」。

但现在的代码里，这套明文格式常常不见了。主流做法是用结构化的工具调用：模型产出的不是一段带 `Thought:` 字样的文本，而是 `AIMessage.tool_calls` 这样的结构化字段，里面写明调哪个工具、参数是什么；工具执行结果作为新的消息回灌，模型据此生成下一轮。Thought 这一步仍然发生了——模型内部确实在判断下一步——只是不再要求它把思考明文写出来给你看。

所以准确的理解是：**ReAct 描述的是「推理—行动—观察」这个交替推进的机制，固定 Prompt 格式只是它的一种早期实现**。判断一个 Agent 是不是 ReAct 式，看的是有没有「行动之后拿观察、再据此决定下一步」这个环，不是看提示词里有没有那三个标签。这也解释了为什么明文 Thought 会退场：让它写出来要额外烧 token，还容易把内部推理暴露给终端用户，把它藏在结构化消息里更省、更干净。

### 代价：灵活不是免费的

ReAct 的每一项好处都有账要付。链路更长——一轮循环要额外请求模型、执行工具、再回灌，多步任务下来往返次数成倍涨；成本更高——每一轮都把完整上下文重新发给模型，token 消耗随轮数累积；调试更难——出错时要回溯整条 Thought/Action/Observation 轨迹，定位是哪一步的判断偏了，比查一个固定流程麻烦。这些代价决定了它不是默认选项，后面「什么时候该上」会给出判断线。

## 横向对比

先看 ReAct 和两种「邻居」的区别，这张表是理解它定位的关键：

| 维度 | 纯生成 / CoT | ReAct | 固定工具流程（Workflow） |
| --- | --- | --- | --- |
| 能否看外部世界 | 不能，只凭已有知识 | 能，行动后拿观察 | 能，按预设步骤调用工具 |
| 路径谁决定 | 无路径，一次性生成 | 模型每轮根据观察现决定 | 人提前写死 |
| 面对意外结果 | 无从感知 | 下一轮重新推理、改主意 | 无分支则照原计划走 |
| token / 延迟成本 | 最低 | 最高（多轮往返 + 全量上下文） | 中（固定次数调用） |
| 适合的任务 | 知识性问答、纯推理题 | 路径不确定、依赖实时信息 | 步骤明确、可枚举的流程 |

再看不同类型的任务该停在哪一层，这张表回答「什么时候值得上 ReAct」：

| 任务特征 | 建议 | 理由 |
| --- | --- | --- |
| 答案在模型已有知识里 | 纯生成 / CoT | 不需要外部信息，加循环只是加成本 |
| 需要实时数据，但取数步数确定 | 固定流程或一次工具调用 | 路径可枚举，没有临场决策的必要 |
| 路径依赖上一步结果、无法预先枚举 | ReAct | 每步都要看观察再定下一步，正是循环的用武之地 |
| 出错后需要换策略重试 | ReAct | 观察能告诉模型这次错在哪，支持改主意 |
| 对延迟和成本极敏感、任务又简单 | 别上 ReAct | 多轮往返的开销换不来对应收益 |

最后一组容易混的概念，单独列出来：

| 概念 | 它是什么 | 和 ReAct 的关系 |
| --- | --- | --- |
| CoT | 让模型在回答前多写几步推理 | 只管「想」，不管「做」；可作为 ReAct 里 Thought 环节的推理基础 |
| Function Calling | 把模型意图变成一次结构化调用 | 可作为 ReAct 里 Action 环节的实现手段，不等于 ReAct 本身 |
| Prompt 模板 | 约束输出格式的提示词写法 | 是实现 ReAct 的一种方式，不是 ReAct 的定义 |

## 工程实践

### 一个最小循环长什么样

把机制落到代码，最核心的结构就是一个「调用—执行—回灌」的循环（伪代码，字段名按常见框架的通称）：

```python
# 伪代码：ReAct 式主循环（结构化工具调用版）
def run_react(question, model, tools, max_steps=8):
    messages = [user_message(question)]        # 观察历史在此累积
    for step in range(max_steps):
        ai_msg = model.call(messages, tools=tools)
        messages.append(ai_msg)                # 结构化调用意图进入历史

        if not ai_msg.tool_calls:              # 没有调用意图 = 模型判断任务完成
            return ai_msg.content

        for call in ai_msg.tool_calls:         # Action：执行每个工具
            obs = tools[call.name].run(validate(call.args))
            messages.append(tool_message(call.id, obs))  # Observation 回灌
    return fallback(messages)                  # 步数用尽，兜底退出
```

对照三段式看这段代码：`model.call` 之前积累的消息是 Thought 的依据，`ai_msg.tool_calls` 是 Action，`tool_message(...obs)` 回灌的是 Observation。注意 Thought 没有单独一行代码——它发生在这个循环每一步的推理里，在结构化工具调用的版本中不需要明文产出。这正是「机制不是模板」在代码层面的体现。

两个护栏不能省。`max_steps` 是硬上限，防止模型在循环里打转（经验值：按任务复杂度取 5～15，简单任务压到 3～5）；`fallback` 是步数用尽后的兜底，返回已有信息或明确说「没查到」，而不是把半截轨迹丢给用户。再加一条：工具执行要能返回结构化错误，模型看到「参数错了、正确格式是 X」才有机会在下一轮自我修正，只返回一个「失败」它会卡在原地。

### 明文 Thought 该不该留

这是落地时绕不开的选择。让模型明文输出 Thought 有两个用处：调试时能看到它的判断链条，定位哪一步想偏了；某些复杂任务里，把推理写出来确实能提升下一步的质量。代价前面说过——额外 token、更长响应、内部推理暴露给用户。

一个折中做法：调用侧用结构化消息跑（省成本、不暴露），另外维护一份内部 trace，只在 DEBUG 或复盘时让模型输出推理摘要。判断标准看你的用户是谁——面向终端用户的应用通常关掉明文，面向开发者的调试工具留着更值。这不是非黑即白，按场景取舍。

### 什么时候该上，什么时候别上

把账摊开算一遍再决定。ReAct 的额外成本来自两处：每多一轮就多一次模型请求，且这次请求带着到目前为止的全部消息；工具本身的执行延迟也叠加在链路上。所以任务越简单、步数越少，循环的收益越盖不过成本。一个能落地的判断线：**先看能不能用一次工具调用或固定流程解决，能就别上；只有「下一步动作依赖上一步结果、且无法预先枚举」时，ReAct 才真正划算**。前面讲工具设计粒度时说过类似的话——路径能不能事先枚举，是贯穿这几题的共同判据。

## 追问逐条作答

### 追问一：Chain of Thought（CoT）是什么？它为什么能提升复杂推理题的效果？

CoT 是让模型在给出最终答案之前，先把推理过程一步步写出来，而不是直接跳到结论。它提升复杂推理题效果的直觉解释是：把一步到位的「跳」拆成多步「走」，每一步只处理一个小推理，出错概率比一次性完成整条推理链低；写出来的中间步骤又成了后续推理的上下文，后面的步骤能踩着前面的结论往前走。用在这类题上——多步计算、逻辑推断、需要分解的问题——效果明显；但知识性问答、简单事实查询用不上，写出来只是多耗 token。要诚实补一句：CoT 提升的是推理质量，不解决「模型看不到外部世界」的问题，这正是 ReAct 要在它之上加行动环节的原因。

### 追问二：CoT 和 ReAct 的区别是什么？什么时候只用 CoT 就够，什么时候要升级到 ReAct？

区别一句话：**CoT 只让模型多想几步，ReAct 让模型想一步、做一步、看结果再想**。CoT 全程在模型内部打转，不接触外部世界；ReAct 有行动和观察，能拿真实结果修正判断。判断线看任务要不要外部信息、路径能不能预先定：答案在已有知识里、或问题是纯推理题（数学、逻辑），只用 CoT 就够，加工具调用是浪费；需要实时数据但取数步数固定，一次工具调用配一点 CoT 推理即可；只有路径依赖上一步结果、又没法提前枚举——比如排查问题要边查边决定查什么——才需要升级到 ReAct。所以是按需升级，不是 ReAct 全面替代 CoT。

### 追问三：ReAct 是不是必须在 Prompt 里写 Thought / Action 这些标签？

不是，这是最常见的误会。那套标签是 ReAct 早期的实现形式——用提示词约束模型按固定格式输出文本，程序再解析。但 ReAct 的本质是「推理—行动—观察」交替推进这个机制，格式只是承载它的一种方式。现代 Tool Calling Agent 用 `AIMessage.tool_calls` 这类结构化字段产出行动意图，工具结果作为消息回灌，Thought 在模型内部发生但不明文输出——没有那些标签，跑的仍然是 ReAct 式的循环。判断是不是 ReAct，看有没有「行动后拿观察、再据此决定下一步」这个环，别看提示词长什么样。

### 追问四：ReAct 和 Function Calling 到底谁包着谁？

不在一层，别套娃。ReAct 是运行机制，管的是整条循环怎么推进——什么时候想、什么时候行动、拿到结果怎么接着想。Function Calling 是一次行动的技术实现，管的是「怎么把这一步的行动意图变成结构化参数」。ReAct 的 Action 环节可以用 Function Calling 实现，也可以早期用文本格式实现；Function Calling 单独用一次就结束，不构成 ReAct——因为没有观察后的再推理。所以是 ReAct 可以使用 Function Calling 作为行动手段，不是两者互相包含。

### 追问五：循环跑偏了怎么办？

跑偏的常见形态有三种，各有对应处理。一是原地打转——同一个工具反复调、参数几乎一样，多半是模型没从观察里读出新信息，做法是检测重复调用并在回灌消息里明确提示「这次和上次相同，换个思路」，连续重复就截断。二是步数耗尽——任务太难或目标描述含糊，`max_steps` 到顶还没完成，这时 `fallback` 要返回已查到的部分结果并说明没做完，别让用户对着半截轨迹猜。三是工具连续报错——观察里全是失败信息，模型越试越乱，设一个连续失败阈值，超了就停下来把错误原文交给人处理。三种都靠护栏兜，不能指望模型自己永远走对。

### 追问六：ReAct 的 Thought 都明文写出来是不是更好？

不一定，看成本和受众。明文的好处是可解释、方便调试，复杂任务里写出来有时能提升下一步推理质量；坏处是费 token、拉长响应、把内部推理暴露给终端用户。工程上的常见选择是：面向终端用户的调用用结构化消息跑，Thought 藏起来；同时留一份内部 trace，在 DEBUG 或复盘时让模型输出推理摘要。若是面向开发者的调试产品，默认留明文反而更有价值。所以这题的答法是「按场景取舍」，而不是一刀切地说写或不写。

## 60 秒面试回答模板

> ReAct 是把推理和行动交替串起来的机制：先判断当前该做什么，再调用工具行动，拿到返回作为观察更新判断，循环到任务完成。它补的是纯推理看不到外部世界、固定流程又不会临场调整的夹角——路径不确定、依赖实时信息的任务最适合。要注意它是机制不是模板：早期靠 Prompt 写 Thought、Action 标签，现在主流用结构化工具调用消息，Thought 在内部发生但不明文展示。CoT 只管多想几步，ReAct 多了行动和观察。代价是链路长、成本高、调试难，所以先看一次调用或固定流程能不能解决，只有下一步依赖上一步结果又无法预先枚举时才上。

## 加分项

- **把「机制不是模板」讲透**：从明文标签讲到结构化 `tool_calls`，说明看过真实代码，不是背论文概念。
- **用夹角定位价值**：一手点纯推理看不到世界，一手点固定流程不会调整，ReAct 正好补中间，定位一句话说清。
- **说出代价和判断线**：链路长、成本高、调试难，加上「路径能否预先枚举」这条判据，说明有成本意识而非追新。
- **跑偏处理讲具体**：原地打转、步数耗尽、工具连错三种形态各有护栏，是可落地的工程经验。

## 常见误区

- **把 ReAct 和固定 Prompt 格式画等号**：以为没有 Thought 标签就不是 ReAct；判断标准是有没有「行动—观察—再推理」的环，不是提示词长相。
- **把 CoT 和 ReAct 混着用**：CoT 只多想几步、不接触外部世界，纯推理题用它就够；见题就上 ReAct 是拿成本换不需要的能力。
- **只背三段式不说代价**：答不出链路长、成本高、调试难，也没有判断线，会被当成「读过概念没落地」。
