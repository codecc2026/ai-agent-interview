# 复杂文档 RAG 或多模态 RAG 应该怎么做？

## 面试官为什么爱问这题

RAG 的教程 demo 里，语料永远是干净的分章节 Markdown；企业里的语料是扫描的设备手册、盖红章的合同、Excel 转出来的 PDF、图文混排的操作规程。很多候选人把 RAG 等同于「向量库加检索算法」，这题一问就露馅：他没意识到检索之前还有一整层文档解析的工程，更没想过答案可能藏在一张贴图里而不是文字里。

第 15 篇讲流水线时把「加载解析」当一环带过，第 18 篇讲切块时说过表格要整体保护；本篇把镜头对准解析层本身——版面分析、表格提取、图文对应这一整层怎么做——再加上多模态路线的选型判断。这也是这道题的两个采分点：**解析意识**和**路线判断**。

## 一句话先给结论

**复杂文档 RAG 的关键是把解析层当独立工程：版面分析、OCR、表格提取、标题层级恢复先于切块，页码、坐标、层级链这些结构信息进 chunk 和 metadata；查询时文本、表格、图注多路召回再统一重排。多模态 RAG 只在答案真的藏在图片内容里时才值得上，图片能被文字说清时，图注路线性价比更高。**

## 核心原理：解析层决定上限

### 机器读到的，和你看到的不是一回事

PDF 是排版格式，不是语义格式。它内部存的大致是「哪些字符画在页面哪个位置」，并不存「这几个格子是一个表格」「这行加粗的字是三级标题」。用抽取式工具直接抽字符流，肉眼看是整整齐齐一张报价表，机器拿到的是一串数字和零散汉字——行列关系全丢，合并单元格彻底变成乱序。

扫描件更糟：它连字符都没有，只有一张页图，一切内容都要先过 OCR。所以「把 PDF、扫描件、表格、图片、网页全当普通纯文本处理」不是偷懒，是主动把语义结构扔掉——这也是这类场景最大的坑。

### 解析层要恢复的四样东西

把解析层单独看待，是因为它有明确的交付物：从一页版面里恢复出四样东西。

- **版面角色**：每个区域是标题、正文、表格、图片、图注还是页眉页脚。页眉页脚通常是噪声，识别出来是为了删掉它，不让「第 3 页 共 47 页」混进检索块。
- **表格结构**：行列关系、表头位置、合并单元格。表格提取的输出应该是结构化数据，而不是把单元格内容按读序拼成一串。
- **标题层级链**：从一级标题到当前块的完整路径。第 15 篇说过，块脱离标题链就变成「自 2024 年起适用于一般纳税人」——没主语的句子。
- **图文对应**：图注挂到哪张图、正文里那句「如下图所示」引用的是哪张图。这个对应关系 PDF 里不存在，要靠版面位置推断，丢了它，图注就成了孤儿文本。

### 为什么解析错误不可逆

解析错了，后面没有环节能救。向量检索不会发现「表格行列错位」，它只会把错的内容「算准」——第 15 篇讲过一个反直觉现象：行列错位的表格块因为数字密集，反而更容易被检索命中。重排、改写、换更大的模型，都是在错误文本上做优化。所以判断是：**解析质量决定这套系统的上限，模型选型只决定逼近上限的速度**。企业知识库里设备手册、制度文件占比越高，这句话越成立。

### 边界：解析层不解决什么

解析对了不等于 RAG 就对了——切块要按结构块切（第 18 篇管这层），召回要能把表格块和文本块都捞回来（第 19 篇的混合检索），引用要能回链到页码（第 13 篇的 metadata 契约）。另外两条概念边界要拎清：**多模态 RAG 不等于「把图片 OCR 成文字」**——OCR 只能拿走图里的文字，拿不走折线图的走势；**多模态 RAG 也不等于长上下文一把梭**——把整本扫描册塞进上下文，成本和 Lost in the Middle（第 17 篇）都在等着。

## 横向对比

先看四类最难啃的文档，各自的坑和解法：

| 文档类型 | 机器视角的坑 | 解析策略 |
| --- | --- | --- |
| 设备手册 | 层级深、图文紧耦合、参数表跨页 | 版面分析识别图注和表格，跨页表格做拼接，层级链全程保留 |
| 制度 / 合同 PDF | 条款编号是唯一结构信号，红章遮挡文字 | 按条款边界切，OCR 后清洗噪声，印章区域按遮挡处理 |
| 扫描件 | 无字符层，全靠 OCR，倾斜和分辨率都影响识别 | 先做方向矫正和去噪，OCR 后过清洗环节再切块 |
| 网页 / 导出 HTML | 导航栏、广告、正文混在一起 | 抽正文区域，剥掉模板噪声，保留标题层级 |

再看三条技术路线的取舍——这是「多模态什么时候值得上」的核心判断表：

| 路线 | 索引什么 | 能答什么 | 代价与适用 |
| --- | --- | --- | --- |
| 纯文本 RAG | 解析出的正文和表格文本 | 答案在文字里的问题 | 成本最低；图片信息全部丢失 |
| 图注增强 RAG | 文本 + 模型生成的图片说明 | 图片内容已被文字说清的问题（流程图步骤、照片里的设备型号） | 多一道图注生成与抽检；图注错会污染检索 |
| 原生多模态 RAG | 文本向量 + 图像向量（图文对齐的双塔模型，如 CLIP 这一类） | 答案在图像细节里的问题（「这张图里的曲线趋势」） | 图像嵌入成本高、可解释性差；只在确有需求时上 |

第三张表留给工程实践里的多路召回设计。

## 工程实践：解析产物、表格线性化、多路召回

### 解析产物先定契约

解析层的输出不是「一堆文本」，是结构块列表，每块带完整定位信息。契约不定，后面引用回链全都做不了：

```python
# 伪代码：解析层输出的结构块契约
block = {
    "type": "table",              # title / paragraph / table / figure_caption
    "text": "<线性化后的表格内容>",
    "page": 12,                   # 页码：引用回链给用户看
    "bbox": [88, 240, 512, 690],  # 页面坐标：回链时高亮原文位置
    "heading_path": ["运维手册", "3 故障处理", "3.2 报警代码"],
    "figure_id": "FIG-3-7",       # 图注块挂到对应图片
    "doc_id": "MAN-2026-031",     # 源系统稳定 ID，沿用第 13 篇的契约
    "version": "v3"
}
```

页码和坐标这两项最容易被省掉，但「答案在第 12 页」和「点击引用直接跳到那一段高亮」，是用户对这类系统能不能信任的分水岭。

### 表格线性化：检索和呈现是两件事

表格块进向量库前要线性化成文本。通用做法是转 Markdown 表格；超长表格按行分组、每组复制表头——这个策略第 18 篇讲切块时说过，这里补上「为什么要复制表头」：分组后的第二组如果不带表头，就变成「L2 报警｜停机｜2 小时」这种没头没尾的行，检索命中了也读不懂。

```python
# 伪代码：表格线性化与分组
def table_to_chunks(table, max_rows=15):
    header = "| " + " | ".join(table.header) + " |"
    for i in range(0, len(table.rows), max_rows):
        rows = table.rows[i : i + max_rows]
        lines = [header] + ["| " + " | ".join(r) + " |" for r in rows]
        yield {"type": "table", "text": "\n".join(lines),
               "page": table.page, "bbox": table.bbox}
```

`max_rows` 取多少没有权威值，经验上 15～30 行一组，让单块落在第 18 篇说的 200～500 token 区间内，收口依据同样是评测集上的召回表现。

### 多路召回：三路各建各的索引

解析层把文档拆成了文本块、表格块、图注块，查询时就按类型分路召回，再融合成一张榜单：

| 召回路 | 索引内容 | 典型问题 | 典型失灵 |
| --- | --- | --- | --- |
| 文本路 | 标题、正文段落 | 「报警代码 E-21 怎么处理」 | 表格被切碎时漏检 |
| 表格路 | 线性化表格块 | 「L2 报警对应的停机时长」 | 表头没复制导致块不可读 |
| 图注路 | 图片说明文本 | 「接线示意图里有没有接地端子」 | 图注生成错了，检错图 |

```python
# 伪代码：三路召回 + RRF 融合（融合逻辑同第 19 篇，k=60）
def multi_route_retrieve(query, top_k=32):
    cands = []
    for route in (text_index, table_index, caption_index):
        cands.append(route.search(query, k=top_k))
    fused = rrf_fuse(cands, k=60)          # 认排名不认分数
    return rerank(query, fused)[:8]         # 统一重排后收窄，沿用第 19 篇口径
```

两个细节：三路各自打分同样量纲不可比，所以融合必须走 RRF 这类只认排名的方法；重排在融合后的总榜上做一次，不要每路各自精排再拼。召回宽度沿用第 19 篇的经验值——各路 top_k 20～50，重排后进上下文总共 3～8 条。

## 追问逐条作答

### 追问一：为什么很多设备手册、制度 PDF 特别难做 RAG？

三个结构性原因叠加。一是**图文紧耦合**：手册的正文大量使用「如下图」，答案不在文字里在图里，抽字符直接丢掉这层信息。二是**表格跨页**：一张参数表横跨两页，抽取工具按页解析，前半张有表头后半张没有，拼起来行列对不上。三是**层级深且不规则**：三级四级标题、条款编号、图表编号混在一页里，标题层级链一断，块就没了主语。制度 PDF 还多一条：改版频繁，旧版没清干净就「新旧的答案同时在库里」，这是第 13 篇讲过的版本问题，在制度类语料上爆发得最频繁。

### 追问二：OCR 准确率和最终问答效果是什么关系？

不是线性关系，是**放大关系**。OCR 的错误发生在关键词上的代价，远大于发生在普通字词上：设备型号里的一个字符错了、报警代码识别错一位，这个块就永远检索不到——因为查询词和入库文本对不上。反过来，标点、页眉页脚这类位置的错字几乎不影响。所以工程上不追求整体准确率的绝对值，而是盯着**关键实体区域**的识别质量：表格里的编码列、型号列要不要单独校验（比如对照正则模式或实体表）。经验上，先改用更合适的解析工具、对扫描件做方向矫正和去噪，比纠结 OCR 引擎换哪家收益大。

### 追问三：多模态 RAG 什么时候值得上，什么时候纯文本就够？

判断标准只有一条：**答案是否只存在于图像内容里**。图片能被文字完整说清——流程图的步骤、示意图的组成部件——图注增强就够了，成本只多一道生成。答案依赖图像本身的视觉特征——「这两张图里哪个曲线的斜率更陡」「照片里这台设备的锈蚀程度」——才需要原生多模态：图像走视觉编码器进向量库，查询也编码成同空间向量去检索。多数企业知识库场景（手册、制度、合同）属于前者，一上来就建图像索引是过度设计。中间态也存在：图注回答「图里有什么」，需要时把原图调出来交给多模态模型看，索引还是纯文本的。

### 追问四：图注是模型生成的，生成错了怎么办？

图注错是图注路线最大的风险，因为它会以「看起来正常的文本」身份进索引，错得悄无声息。三道防线：**生成时给约束**，图注只描述图内可见内容，禁止推断和补充背景，降低幻觉率；**入库前抽检**，经验上按 5%～10% 比例人工抽看，高频文档的图注全检；**图注块标注来源标记**，metadata 里记 `caption_generated: true`，出 badcase 时能快速定位是图注层的问题而不是检索层。追问下去还有一层：图注答不了视觉细节问题时，把 `figure_id` 对应的原图调出来交给多模态模型现场看——图注是给检索用的，不是给阅读用的。

### 追问五：表格检索回来之后，怎么交给模型？

线性化格式直接决定模型读不读得对。三种做法按场景选：短表转 Markdown 表格原文进上下文，模型读 Markdown 表格的能力通常够用；超宽表（列太多）转成「每行一条记录」的键值对文本，`列名: 值` 逐行展开，避免表格被排版截断；聚合类问题（「一共有几种报警级别」）如果高频出现，解析阶段就把表格同时落一份结构化数据，交给代码去算而不是让模型数表格行——数数是语言模型的弱项，能走工具就别赌。

### 追问六：解析层怎么验收？总不能每份文档人工看一遍。

分文档类型定抽检策略，不做全检。文本类按块抽 1%～5% 人工比对原文；表格类抽验要看「行列还原是否正确」而不只是「文字是否识别对」——文字对、行列错，照样答错；图注按追问四的 5%～10%。另外把**解析层的 badcase 单独建账**：效果排查时先判断是「解析错了」还是「检索错了」，两类问题的修法完全不同——前者回解析层修规则或换工具，后者才是第 19 篇那套组件的事。解析质量没有万能指标，抽检加 badcase 归因是务实做法。

## 60 秒面试回答模板

> 复杂文档 RAG 我会先把解析层单独拎出来做：PDF 和扫描件不直接抽字符，先过版面分析，把每个区域的角色识别出来——标题、正文、表格、图片、图注，表格单独做结构提取，标题层级链全程保留。切块沿结构块切，表格整体不切，页码、坐标、层级链进 metadata，保证引用能回链到原文位置。查询时按内容类型分路召回：文本、表格、图注各建索引，RRF 融合后统一重排。多模态我不默认上——先判断答案是否真的藏在图像细节里，能被文字说清的图走图注增强，只有视觉特征本身是答案时才建图像向量索引。我的判断是解析质量决定上限，模型选型只决定逼近上限的速度。

## 加分项

- **说得出「图文对应关系要靠版面位置推断」**：图注和图的对应、正文「如下图」的指代，PDF 里都不存在显式记录——意识到这一点的人是真趟过手册类语料的。
- **给表格线性化的具体方案**：Markdown 化、超宽表键值对展开、聚合问题走代码计算——三档策略对应三类问题，比一句「转成文本」高出两个层次。
- **图注路线的风险管理**：约束生成、比例抽检、来源标记三道防线，说明你知道生成式图注是会错的。
- **解析 badcase 和检索 badcase 分账归因**：这是排查效率的分水岭，也自然衔接第 21 篇的效果排查主题。

## 常见误区

- **把多模态 RAG 理解成「图片过一遍 OCR」**：OCR 只取图内文字，折线图的趋势、示意图的结构关系它全拿不到，这是路线选型里最常见的答偏。
- **以为换个更强的 OCR 引擎能解决一切**：方向矫正、去噪、表格结构恢复这些前处理做不好，识别引擎再强也接不住；反过来关键实体区域的校验，比整体准确率更值得投入。
- **解析和切块混为一谈**：解析层恢复结构（第 15 篇的流水线视角），切块层决定结构怎么用（第 18 篇）。解析把表格还原对了，切块阶段照样可能把它拦腰剁断——两层都要各管各的验收。
