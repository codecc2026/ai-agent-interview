# RAG 上线后才会遇到的坑：从检索到权限

<!-- growth-hook:v1 -->
RAG 的 Demo 往往一小时就能跑通，但上线后能折磨你几个月。这题之所以高频，是因为它考的不是“会不会做检索”，而是“知不知道上线之后会坏在哪”——数据、权限、评测，每类坑都藏在细节里。

## 面试官为什么爱问这题

这题高频且偏难，考的是生产系统思维。很多人做 RAG 停在"能检索、能回答"的 Demo 阶段，一上线就发现到处是坑——离线上线效果差距大、知识更新跟不上、权限管不住、出问题不知道哪层坏了。面试官想听的是你能不能把 RAG 当成一条完整工程链路，而不是一个"检索增强"的黑箱，并且说清这条链路上有哪些坑、出问题怎么定位。前面聊过 RAG 的切块、引用、权限、评测、可观测，这一篇把它们组织成一张完整的"上线后坑位图"。

## 一句话先给结论

**RAG 真正上线后，难点不在"能不能检索"，而在"从索引到回答的完整链路能不能长期稳定运行"。RAG 不是单点能力，而是"索引阶段 + 检索与生成阶段"的工程链路。挑战分六类：数据侧的解析切块、检索侧的召回重排、生成侧的上下文与引用、治理侧的权限版本、评测侧的 badcase 与指标闭环、工程侧的延迟成本与运维。更稳的答法不是说"部署会有很多工程问题"，而是明确讲出：RAG 是从数据接入、索引构建、检索召回到生成回答的完整链路，任何一层出问题，最终答案都会出问题。**

## 核心原理：六类坑位图

### 一、数据侧：源数据决定上限

文档解析质量、切块策略、表格和 PDF 处理、知识更新时效。如果源数据脏、切块不合理，后面检索和生成都会被拖垮。这是链路的最上游——前面讲 RAG 切块坑时说过，很多效果问题根子在数据处理阶段。表格读乱、版式丢失、切块把完整语义切开，这些坑在 Demo 阶段不明显，量一大就全暴露。

### 二、检索侧：离线能答，上线就露馅

Embedding 选型、召回质量、混合检索、重排效果、metadata 过滤。很多系统离线看起来能答，线上一放大就暴露"召回不准、噪声太多、漏关键片段"的问题。离线样例少、问题简单，检索问题被掩盖；真实用户问题多样、知识库量大，召回的短板就显形了。前面讲混合检索和重排时展开过这些手段，这里是把它们作为上线后的坑位来看。

### 三、生成侧：检索了也会编

上下文组装、引用溯源、忠实度控制、拒答策略。RAG 不是"检索了就不会幻觉"——如果上下文拼接差、Prompt 弱、引用不清，模型照样会编。前面讲幻觉四道防线、讲"有引用但不忠实"时说过这些，落到 RAG 链路上，生成侧就是把检索到的东西组织好、让模型忠实于证据、该拒答时拒答。

### 四、治理侧：最怕答了权限外内容

权限隔离、版本管理、引用可追溯、知识回滚。企业里最怕的不是答错，而是答了权限外的内容，或者答出来了却说不清依据来自哪里。前面反复讲过企业 RAG 必须重视权限、版本、引用，权限过滤要放在检索之前——这里把它们统到治理侧，作为上线后最硬的约束。

### 五、评测侧：不知道问题出在哪一层

badcase 建设、离线评测和在线指标闭环。没有评测，你很难知道问题到底出在切块、召回、重排还是生成——只知道"效果不好"，不知道该改哪。前面讲幻觉治理和运维指标时都提过评测与指标的配合，这里强调它在 RAG 链路里的定位：评测是分层定位问题的手段。

### 六、工程侧：链路长了，运维问题就来了

延迟、成本、缓存、可观测性、索引重建和线上运维。比如知识库一更新，是全量重建还是增量更新？查询慢是卡在检索、重排还是模型？这些都得拆开看。前面讲性能定位、成本优化、可观测性时讲的方法，落到 RAG 上就是工程侧这个问题的答案。

| 类别 | 主要挑战 | 上线后典型症状 |
| --- | --- | --- |
| 数据侧 | 解析、切块、表格 PDF、更新时效 | 源数据脏，检索生成都被拖垮 |
| 检索侧 | Embedding、召回、混合检索、重排、过滤 | 离线能答，线上召回不准噪声多 |
| 生成侧 | 上下文组装、引用、忠实度、拒答 | 检索了照样编，引用不清 |
| 治理侧 | 权限、版本、引用追溯、回滚 | 答了权限外内容，说不清依据 |
| 评测侧 | badcase、离线评测、在线指标 | 不知道问题出在哪一层 |
| 工程侧 | 延迟、成本、缓存、可观测、索引重建 | 查询慢、更新难、定位不到 |

六类坑的排查优先级不一样，出事时先处理哪类、平时先投入哪类，可以照这张表判断：

| 类别 | 出事优先级 | 平时投入优先级 | 原因 |
| --- | --- | --- | --- |
| 治理侧 | 最高 | 高 | 权限事故不可挽回，且合规硬要求 |
| 数据侧 | 高 | 高 | 最上游，错了后面全废 |
| 检索侧 | 高 | 高 | 直接影响答案相关性 |
| 生成侧 | 中 | 中 | 有证据仍可能不忠实 |
| 评测侧 | 中 | 高 | 决定能否定位问题，平时就要建 |
| 工程侧 | 中 | 中 | 影响稳定和成本，长期要投入 |

### 链路视角：任何一层出错，最终答案都出错

这六类不是并列的清单，而是链路上的六个环节。数据→检索→生成是主干，治理和评测是贯穿全程的约束与反馈，工程是承载一切的底座。理解"链路"是关键——用户看到的是最终答案，但答案不好可能是上游任何一层的问题。只看最终答案，你永远定位不到根因。

## 工程实践：分层定位的排查顺序

上线后效果不好，怎么查？按链路从上游到下游逐层排除：

**先查数据。** 看解析和切块对不对——拿几个 badcase，看检索到的片段是不是完整的语义、有没有被切坏、表格是不是读乱了。数据错了后面全白搭，先排掉这个。

**再查检索。** 看召回和重排——该命中的片段有没有被召回、排没排到前面、有没有大量噪声挤占上下文。用标注数据算召回率，别凭感觉。

**然后查生成。** 看上下文组装和 Prompt——检索到的内容有没有正确拼进上下文、模型有没有忠实于证据、该拒答的拒了没。

**治理侧全程要查。** 权限过滤有没有放在检索前、引用能不能追溯到源头、版本对不对。这类问题不是"效果不好"，是"出事了"，优先级最高。

```python
# 伪代码：一条 badcase 逐层定位，看问题出在哪
def diagnose(question, gold_chunk):
    chunks = retrieve(question)                # 检索层
    if gold_chunk not in chunks:
        return "召回问题：该命中的片段没召回"

    ranked = rerank(question, chunks)          # 重排层
    if gold_chunk not in ranked[:5]:
        return "重排问题：命中了但没排到前面"

    context = assemble(ranked[:5])             # 生成层
    answer = model.answer(question, context)
    if not faithful(answer, context):          # 业务侧：忠实度判断
        return "生成问题：有证据但没忠实于证据"
    return "链路正常，检查评测标准"

# retrieve / rerank / assemble / faithful 为业务侧或库实现
```

要点：逐层设检查点，把问题定位到具体环节。`gold_chunk` 是标注的正确答案片段，`faithful` 是业务侧的忠实度判断。这段代码是"分层排查"的具体化——不猜，逐层验。

## 追问逐条作答

### 追问一：RAG 线上效果不好，优先从哪一层排查？

从数据层开始，沿链路逐层排除。先看解析和切块有没有问题，拿 badcase 看检索片段是不是完整、有没有切坏；数据没问题再看召回重排，看该命中的有没有召回、排没排前面；再看生成侧的上下文组装和忠实度。为什么不先看模型？因为数据错、召回错是更常见的原因，且改了收益更大。前面讲 RAG 排障时说过"很多问题根子在数据处理阶段"，这里是同一个顺序。

### 追问二：知识库频繁更新时，怎么处理索引重建和版本回滚？

看更新量和时效要求。小批量、高频更新适合增量更新，只处理变化的部分，快且省；大规模、结构性变化可能需要全量重建。关键是要有版本管理：每次索引变更留版本记录，出问题能回滚到上一个可用版本。前面讲知识治理时说过版本回滚要内建，这里落到"频繁更新"的场景：没有版本，更新出错就没法撤。经验值：增量更新为主、定期全量校准，同时保证每个版本可回滚。

### 追问三：为什么说治理侧的问题比效果问题更严重？

因为效果问题是"答得不好"，治理问题是"出了事故"。答错一个知识问答，用户可能重新问；但答了权限外的内容，比如把 A 部门的文档答给 B 部门的人，是安全事件，不可挽回。或者答出来了却说不清依据，在合规场景里无法交代。所以治理侧的优先级最高，权限过滤必须放在检索之前，引用必须可追溯。

### 追问四（自补）：离线评测好、线上效果差，通常是什么原因？

多是数据分布和规模的问题。离线样例少、问题简单、文档干净，检索轻松命中；线上问题多样、知识库量大、文档杂乱，召回的短板被放大。也可能是评测集没覆盖真实问题分布——离线测的都是理想问题，用户实际问法千奇百怪。经验值：评测集要从真实日志里取、定期更新，别用固定的理想样例测完就上线。

### 追问五（自补）：怎么知道问题出在切块还是召回？

用标注数据分层测。准备一批"问题—正确片段"的标注，先测切块：把文档切成块后，正确片段是否完整存在于某个块里（没被切坏）；再测召回：给定问题，正确块有没有被召回。如果正确片段在块里但没被召回，是召回问题；如果正确内容被切块切碎了，是切块问题。分层测才能分清，笼统看效果分不出来。

## 60 秒面试回答模板

> 我不把 RAG 当单点能力，它是索引阶段加检索生成阶段的完整工程链路，上线后任何一层出问题最终答案都会出错。坑分六类：数据侧的解析、切块、表格 PDF、更新时效；检索侧的 Embedding、召回、混合检索、重排、过滤；生成侧的上下文组装、引用、忠实度、拒答；治理侧的权限、版本、引用追溯、回滚；评测侧的 badcase 和指标闭环；工程侧的延迟、成本、缓存、可观测、索引重建。排查从数据层开始沿链路逐层排除，先排解析切块、再看召回重排、然后看生成，治理侧全程要查——权限问题比效果问题更严重。我还会用标注数据分层测，分清问题到底在切块还是召回。

## 常见误区

- **只说"部署有很多工程问题"**：要说清是链路的哪一层、什么坑。
- **只看最终答案**：答案不好可能是上游任何一层的问题，要分层定位。
- **忽视治理侧**：答了权限外内容比答错更严重，优先级最高。
