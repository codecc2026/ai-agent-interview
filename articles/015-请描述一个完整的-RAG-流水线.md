# 请描述一个完整的 RAG 流水线。

## 一句话先给结论

**完整的 RAG 是两条链：离线索引链——文档加载、清洗、切块、向量化、写入向量库并补齐元数据；在线检索链——接收问题、必要时改写 query、检索召回、重排过滤、组装上下文、交给模型生成答案，最后做引用、脱敏和格式化输出。但面试官真正想听的是后半句：线上效果差，大多数卡在文档解析、切块语义、检索相关性这三处，而不是最后那轮生成。**

## 面试官为什么爱问这题

这题是 RAG 章节的「地图题」，也是一句行话的分水岭：只会说「检索增强生成」的人，链路说不全；背熟八环的人，追问他「哪一环最容易断」就露底。它的考察点题库写得很直白——是否真正理解 RAG，而不是只会喊缩写。

而且这题自带三个深挖口：chunk 怎么切、metadata 存什么、为什么加 rerank——正好对应索引侧两环加检索侧一环，面试官可以顺着任何一个口往下挖三层，看你是在业务里趟过坑，还是只在教程里跑过 demo。

在本专栏里它也值得单独占一篇：第 12 篇算的是「有了超长上下文为什么还要 RAG」的选型账，第 13 篇讲的是权限、版本、引用三道墙，第 14 篇讲的是把检索变成动态决策的 Agentic RAG。本篇回到地基，把静态流水线的每一环讲透——它是后面所有话题的坐标系。

## 核心原理：两条时间线，一个连接点

### 索引阶段：离线，决定系统的上限

索引链是离线跑的，五环各有一句要说的话：

**文档加载与解析**。难点从来不在「读文件」，在格式：PDF 里的表格、扫描件的图片、Word 里的多级标题，机器读出来的和肉眼看到的经常不是一回事。这一环错了，后面全白费——向量算得再准，也只是把错误的内容「算准了」。

**清洗**。去页眉页脚、水印、乱码、跨页断行，统一编码。脏内容一旦入库就是持久污染：每次检索都可能命中它，而且事后清理要定位到向量级别。清洗是整条流水线里 ROI 最高的环节之一——它不性感，但省下的是后面所有环节的排查时间。

**切块（chunking）**。把长文档切成检索的基本单位。核心矛盾：块太大，检索粒度粗、一个块里混多个主题，向量「稀释」；块太小，单块语义不自足，命中了也读不懂。这道题的完整答案放在追问一里展开。

**向量化**。用 embedding 模型把每个块映成向量。有一条容易被忽略的纪律：同一系统里 embedding 模型不能中途换——换了就要全量重新嵌入，否则新旧向量在同一个空间里不可比，检索结果会「莫名变差」。

**写入向量库并补充元数据**。metadata 是块级随行数据，检索时用来过滤、溯源、展示。字段怎么定，追问二展开。

### 检索阶段：在线，决定系统的下限

检索链是在线跑的，一次请求走完七步：

**接收问题，必要时做 query 改写**。单轮独立提问通常不需要改写；多轮对话里必须做——用户问「那它的税率呢」，不改写成完整问题，拿「它」去检索就是灾难。这就是题库里「必要时」三个字的分量。

**检索召回**。拿 query 的向量在库里做相似度检索，取回 top_k 个候选块。这一步是「粗排」：追求快，牺牲精度，所以 k 要给得宽裕，宁可多捞再筛。

**重排过滤**。用更重的排序手段对候选精排，同时做过滤——包括权限的 pre-filter（第 13 篇讲过：过滤要放进检索请求本身，否则「取 10 条剩 1 条」）、相似度阈值、去重。为什么要单独立一环，追问三展开。

**上下文组装**。把重排后的块按 token 预算拼进 prompt，超预算就裁剪——保头部证据，别把最相关的裁掉。

**交给模型生成答案**。模型基于拼好的上下文作答。注意这一步的输入质量已经由前面六步决定了。

**引用、脱敏、格式化输出**。引用是答案回链原文：每条证据编号、模型标注来源、程序校验编号真实存在（模型可能标一个不存在的编号）；脱敏是出站前的最后一道闸；格式化是按业务要求出 Markdown、表格或结构化 JSON。

### 为什么拆成两条链

把贵的、慢的活（解析、切块、嵌入）放到离线，把快的活（检索、生成）留给在线——离线决定上限，在线决定下限。两条链的连接点只有两个：**向量 + metadata**。块正文不参与检索期的任何决策，所以 metadata 契约漏了什么字段，线上就永远没得用。

边界也说清楚：本篇讲的是固定流水线，它隐含假设「一次检索拿到的证据够用」。这个假设什么时候失效、失效了怎么办，是第 14 篇 Agentic RAG 的领地，这里不重复展开。

## 横向对比：三张表看取舍

**表一：索引五环节，做错各是什么症状**

| 环节 | 在干什么 | 做错的典型症状 |
| --- | --- | --- |
| 加载解析 | 把 PDF / Word / 网页还原成结构化文本 | 表格行列错位、标题层级丢失，检索命中了内容也是错的 |
| 清洗 | 去页眉页脚、乱码、断行 | 页脚电话号码被检索出来当「客服制度」的答案 |
| 切块 | 切出语义完整的检索单位 | 关键句被拦腰切断，证据命中却答非所问 |
| 向量化 | 块映成向量 | 换 embedding 模型未全量重嵌，检索质量莫名下滑 |
| 写库 + 元数据 | 落库并挂上溯源与过滤字段 | 线上想按权限过滤，发现库里根本没这个字段 |

**表二：切块策略对比**

| 策略 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 固定长度 | 每 N 个 token 切一刀，加 overlap | 实现最简单，块大小均匀 | 无视语义，关键句常被切断 |
| 按标题边界 | 沿文档标题层级切 | 块有主题，主语天然完整 | 依赖解析质量，长章节需二次切 |
| 语义切块 | 按语义相似度变化点切 | 块内主题最纯 | 实现最重，效果不稳定 |
| 父子块回填 | 小块检索、大块（父块）进上下文 | 检索准且上下文够读 | 索引结构复杂，库要存两套 |

**表三：召回（粗排）vs 重排（精排）**

| 维度 | 召回 | 重排 |
| --- | --- | --- |
| 目标 | 快速捞足候选 | 精确排出先后 |
| 手段 | 向量相似度一次计算 | 对 query 与候选逐对精细打分 |
| 候选量级 | 宽（经验值 top_k 20～50） | 窄（经验值留 3～8） |
| 延迟与成本 | 低 | 高，所以只对召回结果做 |
| 典型失误 | k 给太窄，好证据没进候选 | 以为重排能救一切——解析错了救不回来 |

## 工程实践：参数、报错和一段能照抄的切块代码

先给一组经验值参数（均为工程经验区间，非权威结论，随语料和模型调整）：chunk 大小 200～500 token；相邻块重叠（overlap）10%～20%，防止关键句落在切口上；召回 top_k 20～50；重排后进上下文保留 3～8 条。这组数字的正确用法不是照抄，而是**作为分层实验的起点**：每次只动一个参数，用固定评测集对比，否则你永远说不清是哪个改动起了作用。

再给三个真实世界最常见的坏味道：一是**表格被从中间切断**——行列错位后，向量反而更容易命中这个「数字密集」的块，答案却必然错；处理方向是表格整体不切、单独成块。二是**标题层级丢失**——解析时没保留标题链，块变成「自 2024 年起适用于一般纳税人」，没人知道「适用」的主语是谁；处理方向是切块时把上级标题回填进块内。三是**多轮对话没做改写**——「那它呢」直接进了向量库，检索出一堆不相干的高频词文档；处理方向是在召回前加一步指代补全。

切块这一环给一段伪代码（按标题边界切、二次切长章节、带标题回填）：

```python
# 伪代码：按标题边界切块 + 标题回填 + 长章节二次切
def chunk_by_heading(doc, max_tokens=400, overlap_ratio=0.15):
    chunks = []
    for section in doc.sections:            # 解析阶段保留的标题层级
        context = " > ".join(section.heading_path)   # 如 "财务制度 > 报销"
        text = section.body
        if n_tokens(text) <= max_tokens:
            chunks.append(Chunk(text=f"{context}\n{text}", meta=section.meta))
        else:                               # 长章节滑动窗口二次切
            for piece in slide(text, max_tokens,
                               overlap=int(max_tokens * overlap_ratio)):
                chunks.append(Chunk(text=f"{context}\n{piece}", meta=section.meta))
    return chunks
```

三个细节值得注意：块内第一行回填标题路径，解决「无主语」问题；二次切用滑动窗口并保留 overlap，代价是块数变多、库变大；`meta` 随块走，这就是索引和检索两条链的契约交接点。

## 追问逐条作答

### 追问一：chunk 应该怎么切？

答「一条原则加三个动作」。原则：**切语义单位，不切物理长度**——块是检索的基本单位，它必须在脱离原文的情况下仍然自足。三个动作：第一，优先沿文档结构切——标题、段落、列表天然就是作者划好的语义边界，固定字数硬切是最后手段；第二，块内补上下文——把上级标题回填进块，或者用第 12 篇提过的父子块方案（小块检索、大块进上下文）；第三，特殊内容单独处理——表格、代码块整体不切。字数区间用经验值 200～500 token 起，但收口依据永远是评测集上的召回表现，不是拍脑袋。

### 追问二：metadata 应该存哪些字段？

第 13 篇从权限与版本角度给过契约，这里给检索视角的最小集合，按用途分三类：**过滤类**——租户、可见组、ACL 标签，检索时 pre-filter 靠它们；**溯源类**——`doc_id`（源系统稳定 ID，不要用文件名）、`content_hash`、章节定位，引用回链和增量重建靠它们；**展示类**——标题、来源链接、更新时间，前端渲染引用条靠它们。一条铁律收尾：metadata 只能在入库时补，检索期不能凭空变出来——契约设计要在第一份数据入库前定稿，这是整条流水线返工成本最高的一处。

### 追问三：为什么要加 rerank？

因为召回和重排的目标不同。召回要在几十毫秒内从百万级块里捞出候选，只能用「query 和块各自算向量再比距离」这种省算力的方式——它必须先把文本压成一个向量，细节信息有损失，所以「语义相关」和「能回答这个问题」经常不一致：候选里全是相似话题的块，但真正含答案的可能排在第十。重排对 query 和每个候选**逐对**精细打分，能分辨「相关」和「命中」，把真证据顶到最前面，也让下游少喂无效上下文。为什么不让召回直接用重排？贵且慢，候选是百万级时算不动。所以分工是：召回给宽（经验值 20～50），重排收窄（经验值 3～8）。

### 追问四：query 改写什么时候需要？不做会怎样？

判据看问题是否「自足」。单轮独立提问通常自带完整信息，可以跳过改写、省一跳延迟；多轮对话必须做——「那它的税率呢」里的「它」要靠历史轮次补全；用户口语和检索语言有落差时也值得做——「报销单贴错了怎么办」改成「发票粘贴错误 更正流程」这种更接近语料的表述。工程上这一步可以是规则（拼接上一轮主题）也可以是模型改写，判断标准是：改写带来的召回增益是否大于它新增的延迟和失败面。

### 追问五：线上效果差，怎么按流水线定位问题？

答「分层评测，逐层归因」，不要一上来就换模型。先测**检索层**：拿标注好的「问题—应命中文档」对，看应命中的块在不在召回候选里——不在，问题在索引侧（解析、切块、embedding），重排和生成都救不了；在候选里但没进最终上下文，问题在重排或过滤。再测**生成层**：证据给对了答案仍错，才是生成侧的问题。题库那句「效果差大多卡在解析、切块、检索相关性，而不是最后那轮生成」，落到操作上就是这套分层定位法：**先查证据对不对，再查答案对不对**。

### 追问六：引用和脱敏放在流水线哪一步做？

都在生成之后、出站之前，但机制不同。**引用**在组装阶段就要铺垫——每条证据带编号进上下文，要求模型标注来源；生成后程序校验：模型给的编号必须真实存在于本次上下文，标了不存在的编号就打回或去掉引用。**脱敏**是出站前的最后一道闸，对答案文本过一遍敏感信息处理——手机号、身份证、内部代号，按业务合规清单来。两者顺序有讲究：脱敏在引用校验之后做，避免把引用编号一起洗掉。

## 60 秒面试回答模板

> 完整的 RAG 分两条链。离线索引链：文档加载解析、清洗、切块、向量化、写进向量库并补齐元数据；在线检索链：接收问题、必要时改写 query、检索召回、重排过滤、组装上下文、交给模型生成，最后做引用、脱敏和格式化输出。这道题我会特别补一句：工程上真正难的不是把模型接起来，而是三件事——文档是否被正确解析、切块是否保留语义、检索结果是否真的对当前问题有帮助。线上效果差，大多数卡在这三层，而不是最后那轮生成。所以排查时我会先查证据对不对，再查答案对不对。

## 加分项

- **说出「离线决定上限、在线决定下限」**：一句话暴露你是从系统视角看流水线，而不是从 API 视角。
- **把 rerank 讲成经济学问题**：召回快而糙、重排准而贵，top_k 从宽收到窄——能讲清「为什么不全用重排」的人，是真算过延迟和成本账的。
- **提分层评测**：检索召回率和生成忠实度分开测，badcase 先归因到层再谈优化——大多数候选人只会说「调一调 prompt」。
- **点破清洗的 ROI**：愿意承认最不起眼的清洗环节性价比最高，说明你真处理过脏语料，而不是只跑过干净 demo。

## 常见误区

- **把流水线答成「接 API」**：从「调用 embedding 接口」讲起，跳过解析、清洗、元数据——面试官立刻知道你只搭过 demo，没维护过生产语料。
- **把切块当超参数调**：只会改 chunk 大小数字、不谈语义边界和标题回填，等于承认不理解切块的目的。
- **把 rerank 当银弹**：解析错、切块错，重排只能「在错误候选里排出错误顺序」——它优化排序，不修复数据。
- **和 Agentic 混着说**：本篇讲的是固定流水线，一次检索一个答案；让模型运行时自己决定要不要再查，那是第 14 篇的 Agentic RAG，概念别混。
