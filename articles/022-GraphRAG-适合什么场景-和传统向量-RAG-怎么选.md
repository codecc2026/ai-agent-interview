# GraphRAG 适合什么场景？和传统向量 RAG 怎么选？

## 面试官为什么爱问这题

这题是检索选型里少有的「考权衡而非考知识」的题。GraphRAG 这两年热度高，候选人分两类：一类把它当新名词背——「GraphRAG 更强，能做复杂推理」，一听就没落地过；另一类能说清「什么问题上向量检索先天失效、图谱路线的收益要在什么条件下才盖得过复杂度」。面试官真正想听的是第二类，因为它考察的是成本意识：图谱路线的构建、维护、调试成本都显著高于向量检索，拍板上图的工程师如果讲不出代价，项目大概率做到一半被成本拖死。

前面把检索侧的主流环节拆得差不多了：完整流水线、切块、混合检索与重排序、排查归因都讲过。这篇把向量检索的能力边界画出来，再看图谱路线在边界外补的是什么、代价是什么、怎么选。

## 一句话先给结论

**向量检索回答「哪段文字最像」，GraphRAG 回答「谁和谁怎么关联、要经过几跳」；实体关系密、多跳推理、全局归纳、结构约束强的问题才值得上图——工程上不默认二选一，先向量 RAG 打底，badcase 集中在多跳、实体消歧、结构约束时引入图谱，最终形态常见的是「向量召回 + 图谱召回 + 融合重排」三路并存。只有当问题核心在关系结构上时，图谱路线的收益才大于复杂度。**

## 核心原理：先画清向量检索的失效边界

### 向量检索的三个先天盲区

向量 RAG 的召回本质是语义相似度匹配：query 和 chunk 各自编码成一个向量，按距离取最近的若干条。它天然擅长「问题与答案措辞不同但语义相近」的场景，也天然回答不了三类问题。

第一类是**多跳关系**。「A 公司的二级供应商里有没有给 C 车型供过件的」——答案拆散在十几份文档里，供应商目录写一层关系，物料清单写另一层，任何单独一段与 query 的相似度都不高，或者干脆没有一段包含完整答案。向量检索的召回单位是 chunk，chunk 与 chunk 之间的关联在索引那一刻就丢了。

第二类是**全局归纳**。「这批合规文档整体在关注什么风险」——这类问题没有任何一段文本与它「相似」，因为答案不在任何单段里，而在语料的整体分布上。纯向量路线连召回什么都不知道。

第三类是**硬结构约束**。「既是 X 的客户、又是 Y 的供应商、同时不依赖 Z 的公司」——这是布尔逻辑加路径约束，相似度打分表达不了「与」「或」「路径长度」，语义最像的段落可能恰好不满足约束。

### GraphRAG 补的是什么

GraphRAG 的通用做法分两步。构建期，用 LLM 对语料做实体和关系抽取：识别出文档里的人、组织、部件、条款，把「A 供货给 B」这类陈述变成图上的边，同指实体（「小王」「王工」「王某」）做消歧合并，形成一张属性图。检索期换一种召回方式：从 query 里识别出的实体出发，沿边做受限深度的遍历，把命中的路径或子图线性化成文本进上下文；全局归纳类问题则依赖图上的社区摘要——用图聚类把联系紧密的实体聚成社区，为每个社区生成摘要，问「整体在讲什么」时按社区摘要作答。

对照前面三个盲区就能看清分工：多跳问题变成图上的显式路径遍历，跳数是受控参数而不是靠文本接龙碰运气；归纳问题由社区摘要接住；结构约束翻译成图查询的过滤条件。代价也藏在「构建期」三个字里——这部分后面单独算账。

### 为什么不默认上 GraphRAG

图谱路线的每一项能力都要用工程复杂度换。抽取要 LLM 把全语料过一遍，比一次性向量化贵得多（经验值：全量抽取的 token 成本通常是建向量索引的数倍以上，视语料密度浮动）；schema 要预先设计实体类型和关系类型，设计错了返工是图级别的；消歧没有银弹，合并阈值松紧都是坑；新文档进来要做增量抽取加实体对齐，对齐错一次就可能把两个不相干的事实链焊死。调试链路也不成熟——向量检索 badcase 可以肉眼比对召回列表，图谱 badcase 要看子图、看路径、看抽取质量，排查成本明显更高。

所以稳妥路径是渐进的：向量 RAG 先解决八成的单点语义召回；运行一段时间，看 badcase 的结构分布；当多跳、实体消歧、结构约束类问题明显集中时，才立项引入图谱增强；落地形态通常也不是替换，而是融合——图谱路负责关系类问题，向量路继续兜底语义类问题，关键词路兜精确匹配（之前讲混合检索时说过 BM25 与向量互补的思路，图谱路是同一逻辑的第三条腿）。

## 横向对比

先按问题形态选路线，这张表是选型的主判断：

| 问题形态 | 例子 | 向量 RAG | GraphRAG | 建议路线 |
| --- | --- | --- | --- | --- |
| 单点事实 | 「报销时限是几天」 | 强项，语义相似直接命中 | 图谱能答但杀鸡用牛刀 | 向量 |
| 多跳关系 | 「A 的二级供应商谁供过 C」、设备故障链路溯源 | 召回单位是 chunk，跨文档链路拼不起来 | 路径遍历显式可达 | 图谱或融合 |
| 全局归纳 | 「这批法规文档整体关注什么冲突」 | 无相似段落可召回 | 社区摘要按主题簇汇总 | 图谱 |
| 硬结构约束 | 「满足 X 且不依赖 Y 的客户」 | 相似度表达不了布尔与路径逻辑 | 翻译成图查询过滤条件 | 图谱 |
| 精确词与编号 | 「报错码 E-4021 是什么」 | 向量易漏精确串 | 图谱不覆盖此需求 | 关键词（BM25） |

再看两条路线的全维度账，这张表决定「收益是否大于复杂度」：

| 维度 | 向量 RAG | GraphRAG |
| --- | --- | --- |
| 召回单位 | chunk（文本段） | 实体、边、路径、社区摘要 |
| 匹配机制 | 语义相似度 | 关系遍历 + 结构过滤 |
| 构建成本 | 一次性切块向量化，低 | LLM 全语料抽取 + 消歧 + schema 设计，高（经验值：数倍以上） |
| 增量更新 | 重建受影响 chunk 的向量，局部 | 抽取后要做实体对齐与冲突消解，全局性风险 |
| 可解释性 | 「为什么召回这段」难讲 | 路径可展示，「A→B→C」直接给用户看 |
| 调试成熟度 | 召回列表肉眼可比 | 要看子图、路径与抽取质量，链路长 |
| 典型适用 | 开放式问答、语义模糊查询 | 关系密集语料、多跳与归纳问题 |

## 工程实践

### 立项判断：用 badcase 结构说话，不用热度说话

要不要上图，别在选型会上拍，让 badcase 数据拍。做法延续之前讲过的排查思路：把黄金集和线上负反馈的 case 按「单点事实 / 多跳关系 / 全局归纳 / 结构约束 / 精确匹配」归类，统计分布。经验值：多跳加结构约束类占比能到三成上下、且这些 case 业务上确实高频，才值得立图谱项；占比不到一成，先去修切块和混合检索，大概率是把检索质量问题误判成了「需要图谱」。这一步的产出是一张归因统计表，它同时是立项文档和日后验收标准——图谱上线后，就盯着这两类 case 的修复率。

### 图谱路检索与路径线性化

图谱路的检索核心是「进图、限定深度、防爆炸」三件事。伪代码：

```python
# 伪代码：图谱多跳检索 + 路径线性化
def graph_recall(query, graph, max_hops=3, max_paths=50):
    seeds = link_entities(query)          # query 实体链接到图上节点（对齐实体别名表）
    if not seeds:
        return []                          # 实体没链接上，交给向量路兜底

    paths = graph.bfs(seeds, max_hops,     # 受限深度遍历，防止子图爆炸
                      edge_filter=query.constraints,
                      max_paths=max_paths)

    texts = []
    for p in paths:                        # 路径线性化成文本，供生成用
        rel = " -> ".join(f"{n.name} -[{e.relation}]->" for n, e in p.steps)
        texts.append(f"{rel} {p.tail.name}（依据：{p.doc_refs}）")
    return texts                           # 路径上带 doc_refs，引用校验沿用之前讲过的做法
```

三个参数都是护栏：`max_hops` 通常压在 2～3（经验值，再深噪声指数上升）；`max_paths` 限死进上下文的路径条数；`edge_filter` 就是把结构约束翻译成边过滤。实体链接失败直接返回空、让向量路接管——这是融合架构的兜底逻辑，单路失效不能拖垮整个系统。

### 三路融合

最终形态里三路召回怎么合，沿用之前讲过的 RRF 融合思路，只把图谱路当第三路加进来：

```python
# 伪代码：向量 + 关键词 + 图谱 三路召回，RRF 融合
def fused_recall(query, k=50):
    cands = []
    cands += vector_search(query, top_k=k)     # 语义相似（召回池经验值 20～50）
    cands += keyword_search(query, top_k=k)    # BM25 精确词
    cands += graph_recall(query)               # 关系路径，天然带依据

    return rrf_fuse(cands)                     # 排名倒数融合，规避三路分数量纲不一
```

图谱路返回的路径文本天然带「依据文档」，重排之后进上下文的可解释性比纯向量块好——这是给用户展示推理链的现成材料。

## 追问逐条作答

### 追问一：GraphRAG 和知识图谱数据库是什么关系？

两层东西，经常被混成一回事。图数据库是存储与查询基础设施，管的是怎么把点和边存起来、怎么高效跑遍历查询，开源方案不止一种（Neo4j 是常见的一类）；知识图谱是数据资产，可以只建不查。GraphRAG 则是检索范式的路线：图谱在这里的角色是「召回与组织语料的中介」，检索生成才是目的。所以三者可以自由组合——有图数据库没有 RAG 的项目到处都是（BI、关系分析）；GraphRAG 也不必用图数据库，语料规模小的时候图直接放内存文件里遍历都行。答这题的关键是把「存储层、图谱资产、检索范式」三层拆开讲，拆完关系自然清楚。

### 追问二：什么情况下多路召回比纯图谱主路更现实？

三种典型情况。其一，图谱覆盖率不足：LLM 实体抽取有漏（经验值：召回率随语料与提示词质量浮动，做不到全量），没进图的关系图上遍历不到，纯图谱主路会整段失明，向量路是天然兜底。其二，用户措辞与图上实体名对不上：图上的实体是抽取时定下的规范名，用户的问法五花八门，进图第一步的实体链接就要靠向量模糊匹配来找种子节点——纯图谱主路绕不开向量。其三，多跳链路太脆：路径上任何一环的边没抽出来，整条链就断，多路融合能拿「语义相近但没进图」的块做替补。所以现实工程里图谱路做增强、不做独木桥，是更稳的结构。

### 追问三：图谱更新和维护成本会不会太高？

会，这是图谱路线最常见劝退点，正面承认再讲对冲。成本贵在三处：增量抽取（新文档要过 LLM）、实体对齐（新实体要和存量节点判同指，合错比漏合更伤——把两个公司焊成一个节点，跨链污染立刻出现）、结构重算（社区摘要要跟着图变更刷新）。对冲手段：沿用之前讲过的文档级 hash 增量同步，变更文档才触发抽取；只对关系密集的核心语料子集建图，长尾文档留在向量索引里；抽取口径做版本管理，换抽取模型或改 schema 要跑黄金集回归，不然新旧实体的类型口径漂移，图慢慢烂掉。预算充足度决定图谱覆盖范围，这句话在选型会上比任何技术论据都有用。

### 追问四：图谱怎么建？实体关系抽取的质量怎么控？

先定 schema：实体类型和关系类型都要枚举封闭，开放式的「自由抽取」会得到一张节点爆炸、边名五花八门的废图。抽取用带 schema 约束的提示词过全语料，重要语料跑两遍（抽取加复核）或者抽样人工核对精确率与召回率。消歧是质量主战场，两个方向都要防：漏合（同一实体多个节点，链路断）与过合（不同实体并成一个节点，链路污染），合并阈值要按语料调，人名、公司简称这类高危类型最好留人工复核队列。建完别急着上线，先拿已知关系做验证集测路径可达率——「图上应该能走通的链路，实际走通多少」，这个数字比抽取精确率更贴近最终效果。

### 追问五：多跳问题能不能靠多轮向量检索解决，不上图？

部分能，先给这个诚实的答案。之前聊 Agentic RAG 时讲过迭代检索：第一轮召回的块里挖出实体，把实体拼进 query 再检索第二轮，两三跳的关系浅问题确实能滚出来。但它有两个结构性弱点。一是误差累乘：每一跳都依赖上一跳召回正确，两跳各自八成可靠，联合就只剩六成多，跳数越深衰减越狠（这是概率乘法，不是经验值）。二是措辞接力断链：每跳的衔接依赖「上一段文档的写法」恰好能被下一轮检索匹配，语料措辞不规整时链路说断就断。图谱路的优势正在这里：跳是显式遍历，边存在就能走，不靠文本接龙。所以判断标准是跳深与语料规范性：一跳两跳、文档写得规整，多轮检索性价比高；三跳起步、实体命名混乱，图更稳。这个对比答出来，「为什么还要图」就不用再解释了。

### 追问六：社区摘要到底解决什么问题？

解决全局归纳这一类向量检索的死角。「这批文档整体关注什么风险」这类问题，答案不存在于任何单段文本，纯向量路线无物可召回。社区摘要在图上做文章：图聚类把联系紧密的实体聚成社区（一簇供应商、一簇法规条款），每个社区生成一段覆盖性摘要，归纳类问题按社区摘要作答，粒度比逐 chunk 摘要粗但完整得多。它和普通 chunk 摘要的分工也就清楚了：chunk 摘要服务单点查询的加速与压缩，社区摘要服务跨文档的主题归纳。顺带一句，社区摘要要跟着图更新重算，这也是追问三里维护成本的一部分。

## 60 秒面试回答模板

> 我的判断标准是问题核心在不在关系结构上。向量检索回答「哪段文字最像」，多跳关系、全局归纳、结构约束这三类问题它先天吃力——答案拆散在多份文档里，或者根本不在任何单段里。GraphRAG 用 LLM 抽实体和关系建图，检索变成显式的路径遍历加社区摘要，正好接住这三类。但图谱的构建和维护成本高——抽取、消歧、增量对齐都是持续工程，所以我不默认上图：先向量 RAG 打底，看 badcase 分布，多跳和结构约束类集中了才引图谱，而且通常不替换，做向量、关键词、图谱三路召回加融合重排。一句话：问题核心在语义相似，向量够；在关系结构，图才划算。

## 加分项

- **先给判断句再展开**：「只有问题核心在关系结构上，图谱收益才大于复杂度」放在最前面，展示的是决策框架而不是技术罗列。
- **用 badcase 结构做立项依据**：把「要不要上图」从技术争论变成归因统计，延续黄金集方法论，工程味最重也最稀缺。
- **讲消歧的双向坑**：漏合断链、过合污染，能同时讲清两个方向说明真碰过图数据。
- **讲多轮检索与图谱的分界**：跳深与措辞规范性两个变量，加上误差累乘的算法解释，直接把「为什么 Agentic 多跳还不够」说透。

## 常见误区

- **把 GraphRAG 当向量 RAG 的升级版**：默认新项目就上图，八成问题向量就能解，多出来的抽取与维护成本全是负资产。
- **以为图建好检索就准**：检索上限由抽取质量决定，schema 混乱、消歧失控的图比没有图更糟——错误的路径遍历会给出「看起来有依据」的错答案。
- **二选一思维**：拿图谱替换向量，覆盖率不足时整体指标反而下滑；正确形态是融合，让各路兜各自的底。
- **把关系可视化项目当 GraphRAG**：建图谱做展示、查询、分析的系统不需要生成环节；GraphRAG 的落点是「图作为召回中介服务生成」，别在面试里混着讲。
