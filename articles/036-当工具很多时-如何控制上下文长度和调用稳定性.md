# 当工具很多时，如何控制上下文长度和调用稳定性？

## 面试官为什么爱问这题

这题在筛一个很现实的东西：你有没有做过"工具多到装不下"的系统。教程里的 Agent 挂三个工具，查天气、查汇率、查字典，全塞进提示词毫无压力。真实业务不是这样——一个电商后台，订单、库存、物流、退款、优惠券、客服、风控，随随便便几十个域，每个域下又有好几个动作，工具总数上百并不稀奇。这时候把它平铺着一股脑交给模型，会同时踩两个坑：提示词被工具定义撑得老长，真正的对话内容和中间结果反而没地方放；模型在一堆名字相近的工具里来回猜，选错和调乱一起涨。面试官想听的是你能不能把"工具集"当成一个要治理的资源来设计，而不是把工具一个个写好就完事。

## 一句话先给结论

**工具多不是问题，让模型在一个没有层次的工具海里盲选才是。治理分两层：控上下文长度靠分层暴露、动态检索和工具聚合，让模型每一轮只看到该看的少数工具；控选择稳定性靠描述治理和把"选工具"独立成路由阶段，让它从该选的候选里选、选错也有边界。核心思路是把平铺的工具集变成有层次的供给，而不是指望模型在几百个函数里自己挑。**

## 核心原理：先把"工具多了到底哪里坏"算清楚

工具一多，坏的地方其实是两笔独立的账，很多团队只算了其中一笔。

### 第一笔是上下文账

每个工具要进上下文的不是一个名字，而是名字、description、参数 schema 这一整包定义。一个定义占多少 token 没有定数，常见实现里从几十到几百不等（经验值），单个看着不多，乘上工具数就很吓人。假设五十个工具、平均每个两百 token（经验值），光工具定义就上万 token 常驻。更要命的是模型无状态：这些定义不是发一次就完，多轮对话里每一轮请求都得重新带上，等于从头到尾都在为工具定义付租金。

这笔账挤压的是别的东西——对话历史、检索回来的资料、Agent 的中间轨迹，全都要从同一个上下文窗口里切。工具定义塞得越满，留给真正干活的信息越少。所以控上下文长度不是单纯的省钱，是给推理腾地方。

### 第二笔是选择账

候选集变大之后选错概率上升，机制之前讲工具幻觉时拆过三条：相近名称在模型看来几乎等价、长描述只有前半句被扫到、参数空间膨胀容易填串。这里不重复，补一个更关键的判断：**省 token 的手段和降选错的手段并不总是一回事。** 比如把 description 截断能省 token，却可能把区分两个工具的那句"什么时候不用"删掉，选错率反而上去；再比如把所有工具合并成一个万能接口，工具数看着少了、上下文省了，模型却要在十几个 action 里做选择题，错得更隐蔽。所以调工具集的时候，两笔账要分开看、一起管，别为了压一笔把另一笔搞崩。

### 治理的四个抓手，加上一层独立路由

题库给的稳法可以归成四类，再加一个更靠前的阶段，恰好对应上面两笔账：

- **分层暴露**：按业务域把工具拆成搜索类、数据类、执行类、写操作类，不同场景、不同角色挂载不同子集，不给同一个 Agent 一次看全。
- **动态选择（Tool Retrieval）**：把工具描述当成可检索的文档，按当前意图先检索出 Top-N 个最相关的工具，只把这几个的定义放进上下文，而不是全量列出。
- **工具聚合**：把过细的底层 API 封装成更高层的业务动作，减少模型在几十个相近函数里猜名字的机会。
- **描述治理**：工具名、description、参数说明里写清"什么时候用、什么时候不用、有没有副作用"，把边界写进模型选工具时唯一看得到的东西里。
- **独立选择阶段**：再往前一步，把"选工具"本身做成一个独立环节——先做意图分类或子域路由，判定任务属于哪个域，再进入那个域的工具集。

前三个主要压上下文账（也让选择变简单），第四个主要压选择账，第五个是把分层暴露变成动态的、同时压两笔账。它们不是互斥选项，真实系统里常常叠着用：先路由到域，域内再做 Tool Retrieval，剩下的工具描述本身写得清楚。

## 横向对比：三张表看清取舍

### 五个抓手各管什么

| 抓手 | 主要压哪笔账 | 怎么做 | 落地成本 | 单独用的局限 |
| --- | --- | --- | --- | --- |
| 分层暴露 | 上下文 + 选择 | 按业务域拆集，按场景挂载子集 | 低，主要是配置 | 分错域就够不着工具，需要路由配合 |
| 动态检索 | 上下文为主 | 按意图检索 Top-N 工具注入 | 中，要建工具索引 | 检索召回不全会漏掉该用的工具 |
| 工具聚合 | 选择为主 | 原子 API 封成业务动作 | 中高，要写聚合层 | 聚合粒度不好定，太粗失去灵活性 |
| 描述治理 | 选择为主 | 名字/描述写清边界和副作用 | 低，但费心思维护 | 工具数太多时，光靠描述不够 |
| 独立路由阶段 | 两笔都压 | 先意图分类/子域路由再进工具集 | 中，多一个决策点 | 路由判错，后面全错 |

这张表最该记住的是最后一列：没有一个抓手是万能的。所以工程上的常态是组合——路由解决"进哪个域"，检索解决"域内看哪几个"，描述治理保证"看到的能分清"。

### Tool Retrieval 和普通知识检索有什么区别

这是追问里最容易答糊的一条，两者都叫"检索"，但不是一回事：

| 维度 | Tool Retrieval | 普通知识检索（RAG） |
| --- | --- | --- |
| 检索对象 | 工具定义（名字、能力、参数） | 文档片段、知识条目 |
| 检索目的 | 挑出下一步可执行的动作 | 找出能支撑回答的信息 |
| 结果怎么用 | Top-N 工具定义注入 `tools` 字段，供模型发起调用 | 片段拼进提示词，当生成依据 |
| 对内容的要求 | 描述要写清能力边界、适用与不适用、副作用 | 语义相关、能回答问题即可 |
| 错了会怎样 | 选错工具等于发起错动作，可能带副作用 | 找错资料多半是答偏或答不全 |
| 评测看什么 | 该用的工具有没有进候选、选中的对不对 | 召回率、NDCG 这类检索指标 |

一句话区分：知识检索找的是"说什么"的依据，工具检索找的是"做什么"的能力。因为工具检索的结果会直接变成可执行的调用候选，它对描述质量和召回的要求比知识检索更苛刻——知识漏一条可能只是回答少个细节，工具漏一个可能就是该退款时找不到退款工具。

### 原子 API 级工具 vs 业务动作级工具

| 维度 | 原子 API 级（细） | 业务动作级（粗） |
| --- | --- | --- |
| 单个工具职责 | 一步操作，如扣库存、发通知 | 一个完整动作，如下单含校验扣减通知 |
| 模型要做的事 | 自己编排顺序、补参数、串联结果 | 选中动作、给齐业务参数 |
| 工具数量 | 多，名字容易撞 | 少，每个边界清楚 |
| 调用轮数 | 多轮，token 和延迟都涨 | 少轮 |
| 出错点 | 散在多步，定位靠 trace | 集中在动作内部，外部看得见成败 |
| 灵活性 | 高，能自由组合出非常规流程 | 低，聚合层没覆盖的流程做不了 |

这张表不是要谁取代谁：常规路径用业务动作级求稳，长尾的非常规操作保留少量原子 API 兜灵活。全部聚合成大动作，遇到没预设的流程就抓瞎；全部拆成原子，模型天天在细节里迷路。

## 工程实践：把动态选择落成代码

### 按意图检索工具，只注入 Top-N

下面这段是动态选择的骨架。`embed`、`search`、`build_tool_schema` 都是业务侧实现，这里只串流程；`always_on` 放高频或兜底工具，不参与检索、常驻候选。

```python
# 伪代码：按当前意图检索一小撮工具，再把它们的定义注入 tools 字段
def select_tools(query, tool_index, top_n=6, always_on=("get_current_time",)):
    # tool_index: 每条含 name / description / embedding / schema
    hits = search(tool_index, embed(query), top_k=top_n)   # 语义检索候选工具
    names = [h.name for h in hits]
    for n in always_on:            # 兜底工具常驻，不占检索名额
        if n not in names:
            names.append(n)
    return [build_tool_schema(n) for n in names]           # 组装成 tools 参数
```

`top_n` 取 6 是经验值，实际按"够覆盖当前任务又不撑爆上下文"来调。两个细节决定这段能不能用：一是检索用的文本不能只拿 `query`，最好把最近几轮对话意图也并进去，否则用户说"那个改一下"时检索不到东西；二是 `always_on` 不能塞太多，它不占检索名额但照样占上下文，塞成了变相全量就白做了。检索出来的工具定义要和静态工具集保持同一份 schema 来源，别出现"检索库里说三个参数、实际执行要四个"的错位。

### 按业务域分层暴露，高风险工具默认不挂

分层暴露通常配一份域到工具的映射，再按场景和风险档过滤：

```python
# 伪代码：按业务域给不同场景挂不同工具子集
DOMAIN_TOOLS = {
    "query":   ["search_order", "get_inventory", "get_logistics"],
    "execute": ["create_ticket", "send_message"],
    "write":   ["refund_order", "cancel_order"],
}

def tools_for(scene, risk_level):
    # is_write_tool / build_tool_schema 均为业务侧实现
    names = DOMAIN_TOOLS.get(scene, [])
    if risk_level == "readonly":
        names = [n for n in names if not is_write_tool(n)]   # 只读场景摘掉写工具
    return [build_tool_schema(n) for n in names]
```

这段代码把两件事一起做了：按 `scene` 只挂当前域的工具，减上下文也减选择；只读场景再把写工具摘掉，等于把"越权写操作"在暴露阶段就掐掉一部分，而不是等到执行前才靠权限层拦。之前讲副作用分级时把工具分成只读、内部写、外部副作用三档，落到暴露层就是这里 `risk_level` 的过滤——高风险工具默认不出现在日常候选里，要用时按需挂载并走确认。

### 一个能暴露问题的信号面板

工具集治理得怎么样，别凭感觉，盯几个能算的数：每轮请求里工具定义占的 token 比例、平均完成一个任务要几轮调用、工具选错率、以及该用某工具却没挂在候选里的"漏挂"次数。token 比例居高不下说明该做动态检索或聚合了；轮数偏多可能是工具拆得太细；选错率高先查描述和命名；漏挂次数高说明路由或检索的召回有问题。这几个数和之前聊工具设计时给的那套指标是同一类东西，只是观察对象从"单个工具好不好"换成了"整个工具集供给得合不合适"。

## 追问逐条作答

### 追问一：工具太多时，应该优先做路由还是优先改工具粒度？

先看选错集中在哪，再决定动哪。如果错在"选错域"，比如查订单的任务跑去调了退款工具，说明工具集太杂、缺层次，优先做路由，先判意图再进子域工具集，收益最大也最快。如果错在"域内选错"，同一堆订单工具里反复选错、一个任务要跑五六轮，说明是粒度问题，该把过细的原子操作聚合成业务动作，或把相似工具的边界描述拉开。还有个顺序上的讲究：路由改的是入口、成本相对低、能先止血；粒度要动工具实现和聚合层、成本高但治本。实际常是路由先上、粒度随后跟，别一上来就重写几十个工具。

### 追问二：Tool Retrieval 和普通知识检索有什么区别？

核心区别是检索对象和目标不同。知识检索找的是文档片段，目的是拿信息支撑回答，找错了多半是答偏；工具检索找的是工具定义，目的是挑出下一步能执行的动作，找错了等于发起一个错动作，可能带副作用。所以工具检索对描述质量更敏感——工具描述里必须写清能力边界、什么时候不该用、有没有副作用，这些在普通知识文档里不是必需的。结果用法也不同：知识片段拼进提示词当上下文，工具定义要注入 `tools` 字段变成合法调用候选。评测上，知识检索看召回和排序质量，工具检索更该看"该用的工具有没有进候选、最后选中得对不对"。把它当成一个特殊检索来做可以，但不能直接套 RAG 那套指标和描述写法。

### 追问三：为什么业务动作级工具通常比原子 API 更适合模型调用？

因为模型擅长的是"理解意图并做选择"，不是"按步骤编排 API"。原子 API 把编排负担甩给模型：下单要它自己记住先查库存再扣减再发通知，顺序错一步、参数串一个就出问题，还要多跑好几轮，token 和延迟都涨。业务动作级工具把这套固定流程封在里面，模型只要选中"下单"、给齐业务参数，剩下的确定性步骤由代码完成——这正好落在模型擅长的那头。另外工具数也少了，名字边界清楚，选错概率跟着降。代价是灵活性：聚合层没预设的非常规流程走不了。所以稳妥的做法是主路径用业务动作级，长尾保留少量原子 API 兜底，而不是非此即彼。

### 追问四：动态检索把工具漏掉了怎么办？

这是动态选择最常见的副作用，必须有兜底。第一，检索文本别只用当前一句话，把最近几轮对话意图并进去，减少"那个改一下"这类指代导致的漏检。第二，设一组 `always_on` 的高频和兜底工具常驻，不参与检索——像获取当前时间这种谁都可能用的，漏了很尴尬。第三，给模型留一条"没找到合适工具"的表达通路，让它能说"现有工具做不了"，而不是硬从一个不相关的候选里挑一个。第四，把漏挂次数记进观测，定期看哪些工具该被召回却没进候选，回头调检索阈值或描述。检索召回不可能是百分之百，关键是漏了之后有退路、还能被发现。

### 追问五：工具定义每次不一样，会不会破坏缓存和增加延迟？

会，这是动态选择要付的代价，得工程设计上消化。提示词缓存通常要求前缀稳定，而动态注入的工具定义位于提示词里，每次变了就可能让缓存失效、延迟和成本反而上去。一个办法是把稳定的系统提示和角色设定放前面、动态工具定义放后面，让前缀尽量命中缓存；另一个办法是别每次都重检索——同一轮对话里意图没变就复用上次选出的工具子集，等意图明显切换再重选。检索本身是向量比对，代价通常远小于一次模型调用，真正要盯的是缓存命中率和端到端延迟，别只盯着"检索快不快"。

### 追问六：怎么判断工具集已经多到该治理了？

看几个会自己冒出来的信号。一是上下文里工具定义的 token 占比持续偏高，挤压了资料和轨迹；二是任务平均完成轮数变长，模型在多步原子操作里打转；三是工具选错率上升，尤其在名字相近的工具之间；四是出现"该用的工具没被挂上"的漏挂。这些信号各自指向不同抓手——占比高做检索或聚合、轮数多改粒度、选错高查描述和路由、漏挂高调召回。任何一个信号冒头，先做最小改动试，别一上来全量重构。工具治理是随业务增长持续做的事，不是一次性的开关。

### 追问七：读工具和写工具在暴露策略上要分开吗？

要，而且这层分开比事后拦更省事。只读工具可以宽松暴露，让它常驻候选、随便检索，反正查错了最多答错；写工具默认不进日常候选，按当前任务确实需要时才挂载，并且挂上后走权限校验和二次确认。这样做的好处是把高风险动作从模型的选择空间里整体摘出去——它看不见，就谈不上误选。之前讲副作用分级时强调的是执行前按风险档处置，落到暴露层就是再往前挪一步：在"给模型看什么"这一步就先筛一遍。分层暴露里把写操作单列一类，正是这个用意。

## 60 秒面试回答模板

> 工具多的麻烦不在会不会调，而在上下文被工具定义撑爆、模型在相似工具里乱选，这是两笔账，要分开治。控长度有三招：按业务域分层暴露、按意图做 Tool Retrieval 只注入 Top-N 个工具、把过细的原子 API 聚合成业务动作。控稳定靠描述治理和把选工具独立成路由阶段，先判意图分类或子域路由，再进具体工具。Tool Retrieval 和普通知识检索不一样，它找的是可执行的动作，描述要写清边界和副作用，漏了工具得有兜底。判断该不该动手，看工具定义占的 token、调用轮数、选错率和漏挂次数。核心就是别让模型在没有层次的工具海里盲选。

## 加分项

- **把两笔账分开**：明确上下文长度和选择正确性是两个独立问题、手段不总重合，比笼统说"工具要少一点"深一层。
- **指出 Tool Retrieval 的特殊性**：检索对象是可执行动作、错了带副作用、描述要求更高，说明你不是把 RAG 那套直接搬过来。
- **暴露阶段就掐掉风险**：写工具默认不挂、只读场景过滤掉写操作，把副作用治理从执行前挪到供给层。
- **治理效果可量化**：token 占比、轮数、选错率、漏挂数四个信号分别指向不同抓手，体现规模化的系统感。

## 常见误区

- **把所有工具一股脑塞进提示词**：以为工具越全越好，结果上下文被撑爆、模型在相似工具里选错，两笔账一起欠。
- **靠截断描述省 token**：把区分工具的"什么时候不用"删掉，token 是省了，选错率反而上去。
- **把工具聚合当万能解**：全聚合成几个大动作，遇到聚合层没覆盖的非常规流程就抓瞎；主路径求稳、长尾留原子兜底才是平衡。
- **动态检索只检索不兜底**：漏掉该用的工具却没有 `always_on` 和"没有合适工具"的表达通路，模型只能硬挑一个错的。
