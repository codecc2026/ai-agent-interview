# 内网环境下怎么设计 Agent / RAG 系统？

<!-- growth-hook:v1 -->
内网、离线、信创环境里的 Agent / RAG，最忌讳把公网方案直接搬进来再换个模型地址。数据不出域、模型可控、依赖可替换、链路可观测——这四条立不住，架构再漂亮也过不了评审。

## 面试官为什么爱问这题

这题较难，考的是企业私有化部署的系统观。很多人把内网方案想成"把公网方案搬进来、断网就能跑"，那是把生产架构降格成了离线 Demo。面试官想听的是你能不能先立住几条硬约束：数据不出域、模型可控、依赖可替换、链路可观测，然后按层把系统搭出来，并且讲清安全边界、运维治理和降级。这也是为什么题目强调"解耦"：内网环境里模型和依赖随时可能变，架构必须留好替换的口子。前面聊过 RAG 的权限、版本、引用，也聊过 MCP 的安全沙箱，这一篇把这些约束放到内网整体架构里看。

## 一句话先给结论

**内网环境下做 Agent / RAG，核心不是把公网方案照搬一遍，而是先把"数据不出域、模型可控、依赖可替换、链路可观测"立住。按企业级部署通常拆三层：应用层负责工作流、Agent 编排、权限和业务接口；推理层用 Xinference 这类平台统一管理 LLM、Embedding、Rerank，对外暴露 OpenAI-compatible API；数据层把向量库、关系库、对象存储、索引、日志审计都放在可控域内。内网方案不是离线版 Demo，而是更强调安全边界、运维治理和模型可替换性的生产架构。**

## 核心原理：三层架构与五个关键点

### 三层怎么分

| 层 | 负责什么 | 典型形态 |
| --- | --- | --- |
| 应用层 | 工作流、Agent 编排、权限、业务接口 | Dify、Coze 类平台的私有化版本，或自研后端服务 |
| 推理层 | 统一管理模型，对外提供标准接口 | Xinference 这类托管平台，暴露 OpenAI-compatible API |
| 数据层 | 存储、索引、日志审计 | 内网向量库、关系库、对象存储、知识库索引、日志审计系统 |

分层的价值在解耦：应用层只认标准接口，不关心背后是哪个模型、跑在哪个推理引擎上；模型要换、推理引擎要换，改推理层就行，应用层不动。这对内网尤其重要——内网模型选型常受合规、硬件、授权影响，变动比公网频繁。

### 五个关键点

**模型接入统一。** 上层尽量都走兼容 API（比如 OpenAI-compatible API），这样在线模型、本地模型、不同推理引擎能统一接入、方便替换。接口统一是"依赖可替换"的技术基础。

**网络和权限隔离。** Agent 能访问哪些内网系统，必须按最小权限开放，不让模型拿到一把通吃内网的钥匙。前面讲 MCP 接入时说过权限检查要和环境沙箱配合，内网场景把这条推到极致——权限边界就是安全边界。

**知识治理。** 文档解析、索引重建、版本回滚、租户隔离、引用追踪都要内建。前面讲企业 RAG 必须重视权限、版本、引用时展开过这些，内网知识库如果没有这套治理，很快就会失控——文档改了索引没更新、出错没法回滚、谁看什么分不清。

**可观测与审计。** 请求链路、工具调用、检索结果、模型版本、token 用量、异常告警，都要能在内网闭环查看。"闭环"是关键词——数据不出域，观测数据也不能往外发，整套监控审计得在内网里自成一体。

**降级能力。** 内网模型会抖动，要有缓存、规则链路、人工兜底或备用模型。没有降级，模型一抖整个系统就脆。前面讲工作流设计时说过确定性环节用代码、关键节点留人工，那些思路在内网降级里同样成立。

| 关键点 | 立住什么 | 没有的后果 |
| --- | --- | --- |
| 模型接入统一 | 依赖可替换 | 换模型要改整个上层 |
| 网络权限隔离 | 安全边界 | 模型拿到通吃内网的权限 |
| 知识治理 | 知识库可控 | 索引混乱、无法回滚、越权 |
| 可观测审计 | 内网闭环排查 | 出问题看不到、追不了责 |
| 降级能力 | 系统韧性 | 模型一抖全系统停摆 |

## 工程实践：一次内网落地的设计顺序

落到动作上，内网项目通常按这个顺序立东西：

先立接口标准。确定上层统一走什么接口（比如兼容 API），这一步决定后面模型能不能替换。接口没定好，后面全被绑死。

再划权限边界。列出 Agent 能访问的内网系统清单，按最小权限逐个开放，能不给的不给。这一步决定安全底线。

然后建知识治理。文档怎么解析、索引怎么重建、版本怎么回滚、租户怎么隔离、引用怎么追踪——这些流程要在上线前定好，不能等知识库乱了再补。

最后补观测和降级。链路、工具、检索、模型版本、token、告警的观测要在内网闭环；缓存、规则链路、人工兜底、备用模型的降级要能切。

```python
# 伪代码：统一模型接口 + 降级链，体现"依赖可替换"和"韧性"
class ModelGateway:
    def __init__(self, primary, backup, cache):
        self.primary = primary      # 主模型（经兼容 API 接入）
        self.backup = backup        # 备用模型
        self.cache = cache          # 缓存

    def answer(self, request):
        if hit := self.cache.get(request):       # 先查缓存
            return hit
        try:
            return self.primary.invoke(request)  # 走主模型
        except ModelUnavailable:                  # 主模型抖动
            return self.backup.invoke(request)   # 降级到备用模型

# primary / backup 都走统一兼容 API，替换模型只改注入的对象
# cache / ModelUnavailable 为业务侧实现
```

要点：主备模型都走统一接口，模型替换只改注入对象，不改调用代码；缓存和备用模型构成降级链。变量是业务侧实现。这个网关就是"模型接入统一 + 降级能力"的具体落点。

## 追问逐条作答

### 追问一：为什么选"应用层 + 推理层"解耦，而不是混在一台机器上？

因为内网模型选型和依赖变化频繁，解耦才能让替换成本可控。应用层只认标准接口，不关心背后是哪个模型、哪个推理引擎；要换模型或引擎，改推理层就行。混在一台机器上看着简单，实际上把应用和模型绑死了——换模型要动应用，扩容要整体扩，出问题也不好隔离。经验值：解耦会多一层接口和部署成本，但只要模型有替换的可能，这层成本通常值得。

### 追问二：LLM、Embedding、Rerank 为什么最好分开部署和管理？

因为它们的资源特性和变动节奏不同。LLM 对算力要求高、部署重；Embedding 和 Rerank 相对轻、但调用频繁，可能需要独立扩缩容。把它们分开，能按各自负载调配资源、独立升级替换，不会因为一个组件瓶颈拖累整体。统一放在一起看着省事，实际容易出现资源争抢和升级互相牵制。还有一层考虑：RAG 链路里这三类模型常常要独立替换或调参，分开管理才支撑得了这种灵活性。

### 追问三：不能访问公网搜索，动态信息怎么补？

几条路组合用。一是接内网已有的数据源，比如内部新闻、公告、业务系统里的数据，把能拿到的动态信息先接进来。二是如果有授权的外部数据馈送，走合规通道同步进内网再检索。三是明确系统边界，说清哪些是系统能答的、哪些因为拿不到实时信息答不了，让 Agent 如实说明而不是编造。经验值：内网系统最忌讳假装什么都知道，拿不到动态信息时明确告知，比硬答一个过时结论更可信。前面讲 RAG 输出边界时也提过类似原则。

### 追问四（自补）：内网知识库治理为什么容易被忽略？

因为它在 Demo 阶段不显眼。几篇文档、固定索引，解析器够用、版本也不用管。但真实企业知识库文档量大、更新频繁、多部门共用，没有治理很快失控：文档改了索引没跟上、出错无法回滚、不同部门权限混淆。前面讲企业 RAG 时说过权限、版本、引用必须重视，内网场景因为数据不出域、运维闭环更难，这套治理反而更要提前建。

### 追问五（自补）：内网的可观测为什么强调"闭环"？

因为数据不能出域。公网方案常把日志、指标、追踪发到外部观测平台，内网做不到，所有观测数据必须在内网里采集、存储、查看。这要求在内网自建可观测能力：链路追踪、工具调用记录、检索结果、模型版本、token 用量、异常告警都得在内网闭环。闭环不只是合规要求，也决定了出问题时能不能在内网里自己查清，没有它，排障就得靠猜。

### 追问六（自补）：内网系统的模型替换通常怎么做到平滑？

靠接口统一和灰度切换。上层只认兼容 API，替换模型时先在新模型上跑一批评测样例，确认效果达标；再小流量灰度，观察完成率、延迟和成本，稳定后逐步切全量。同时保留旧模型一段时间作为回退——新模型出问题能立刻切回去。经验值：内网模型替换往往受硬件和授权约束、窗口期有限，更要提前备好回退路径，别一次切死。

## 60 秒面试回答模板

> 内网方案不是照搬公网，也不是离线版 Demo，先立住四条：数据不出域、模型可控、依赖可替换、链路可观测。架构拆三层：应用层做工作流、Agent 编排、权限和业务接口；推理层用 Xinference 这类平台统一管理 LLM、Embedding、Rerank，暴露兼容 API；数据层把向量库、关系库、对象存储、索引、日志审计放在可控域内。关键点五个：模型接入统一、权限最小隔离、知识治理内建、可观测审计内网闭环、要有降级能力。分层解耦为模型好替换；三类模型分开管是因资源和变动节奏不同；拿不到公网信息就接内网数据源、走合规通道，并明确告诉用户哪些答不了。

## 加分项

- 用"数据不出域、模型可控、依赖可替换、链路可观测"四条硬约束开头。
- 三层架构 + 五个关键点，层次清楚。
- 讲清解耦的价值在模型可替换，三类模型分开的理由在资源和变动节奏。
- 动态信息缺失时强调如实说明，不编造，落到边界意识。

## 常见误区

- **把内网方案当离线版 Demo**：忽略安全边界、运维治理和降级，上不了生产。
- **应用和模型绑死**：模型一换就要改上层，没有留替换口子。
- **权限一把通吃**：Agent 拿到过大的内网访问权限，安全边界失守。
