# 什么时候该用 Prompt、RAG、微调、Workflow、Agent？

## 一句话先给结论

**选型不是挑最先进的技术，而是按顺序判"缺什么"：模型会不会 → 缺不缺外部知识 → 行为稳不稳 → 流程能不能写死 → 要不要当场决策，答案依次落在 Prompt、RAG、微调、Workflow、Agent 上。**

面试官把这题丢过来，考的从来不是名词解释，而是你有没有一条**稳定的收敛顺序**。答崩的人通常栽在两个地方：一种是张口就是 Agent，讲得天花乱坠但算不出成本账；另一种是把五个概念摆成一排挨个解释，解释得很清楚，却没有回答"我这个项目该用哪个"。

一句话记住它们各自管的那一摊事：**Prompt 管任务表达，RAG 管知识来源，微调管行为稳定，Workflow 管固定流程，Agent 管动态决策。**第 1 篇讲过 RAG 与微调在原理上的区别，本篇换个角度：拿到一个需求，按什么顺序问自己哪些问题，才能一步步收敛到某个方案，以及选错之后会看到什么信号。

## 先判"缺什么"，再谈"用什么"

这一步是整个选型的地基。需求到手的第一件事不是想技术方案，而是做一个三选一的归因：**这个问题到底缺知识、缺行为，还是缺流程能力？**三层可以由浅入深逐个排除。

### 缺知识：往外部找

典型表现是模型答得很流畅、格式也对，但内容是错的、旧的或者泛泛而谈——它压根没见过你的保单条款、上周刚改的退货政策、内部接口文档。

这类问题的标志是**知识在模型之外，而且会变**。既然会变，就不该焊进模型里，应该用检索把最新内容在推理时递到眼前。同时它还顺带解决另一件事：答案能附上引用出处，业务方验收时能自己判断对不对。

### 缺行为：往权重里找

第二种表现恰好相反：知识是够的，但每次说法都不一样。同一份材料，今天输出 JSON、明天输出一段说明文字；客服语气时冷时热；一个十二类的分类器，边界样本每次归类不同。

这是"不稳定"而不是"不知道"。先别急着改模型，常规顺序是先加 few-shot 示例、再上结构化输出约束（多数厂商的对话接口都提供按 JSON Schema 约束输出的参数）；只有当这些手段顶不住时，才轮到微调。

### 缺流程能力：往上编排层找

第三种是最容易被误判的：单个环节都对，但整件事一次调用做不完。要先查库存、再算优惠、再去调支付、失败还要重试——这时候缺的不是知识也不是行为，而是**把多个环节组织起来的能力**。

这一层要问的只有一件事：**能不能事先把这个流程画成一张图？**能画出来且长期稳定，就是 Workflow；画不出来，或者下一步取决于中间拿到的结果，才轮到 Agent。

三个层次的边界要卡死：Prompt 改的是输入里的指令和示例，RAG 改的是每次动态喂进去的资料，微调改的是模型的权重参数，Workflow 和 Agent 改的是任务被拆成几步、每步之间怎么走。前三个在内容层，后两个在流程层，它们不是同一维度的五选一，是可以叠加的。

## 把判断顺序固化成一条漏斗

口头讲顺序容易飘，写成规则的好处是团队里每个人得到的选择一致，复盘时也能说清当时为什么这么选。下面是一个示意实现（字段含义见注释，可直接改成你自己的规则引擎）：

```python
def pick_solution(req):
    """req 字段：
    probed_with_best_model            是否已用最强基座 + 20~30 条真实样本探过底（条数为经验值）
    missing_private_or_fresh_knowledge 是否缺私有/时效性知识
    behavior_unstable                 输出是否忽好忽坏（格式、语气、分类漂移）
    multi_step                        是否一次调用做不完
    branches_can_be_enumerated        分支能否穷举
    next_step_depends_on_intermediate 下一步是否取决于中间结果
    """
    if not req.probed_with_best_model:
        return {"action": "先探底", "plan": ["prompt"]}

    if req.missing_private_or_fresh_knowledge:
        plan = ["prompt", "rag"]
    elif req.behavior_unstable:
        plan = ["prompt", "structured_output"]
    else:
        plan = ["prompt"]

    if req.multi_step:
        if req.branches_can_be_enumerated:
            plan.append("workflow")
        elif req.next_step_depends_on_intermediate:
            plan.append("agent")           # 必须配套步数与预算上限
        else:
            plan.append("workflow")        # 穷举不完但无依赖，多半是需求没收窄

    # 知识要新 + 行为要稳 同时成立，才值得再叠一层微调
    if req.missing_private_or_fresh_knowledge and req.behavior_unstable:
        plan.append("finetune")

    return {"action": "按此顺序推进", "plan": plan}
```

这段逻辑里藏着两个容易被忽略的判断：**一是"多重分支但没有依赖"不等于该做 Agent**，那通常说明需求还没收窄，先回去和业务方确认流程；**二是"知识 + 行为"两个缺口同时存在才叠加微调**，单一缺口没必要加这一层，因为它最贵也最难回退。

## 五种方案横向对比

下面这张表按"什么时候该用它 / 要花什么 / 多久能看到变化 / 出了什么事"来排。表里的成本与周期是常见项目的**工程经验值**，不同团队差异很大，只用来横向比对量级，不要当成承诺值。

| 方案 | 适用场景 | 主要成本 | 迭代速度 | 可控性 | 典型失败信号 |
| --- | --- | --- | --- | --- | --- |
| Prompt | 模型本来就具备这个能力，只是任务没说清；低频或一次性任务 | 几乎只有多出来的那部分 token | 分钟到小时级 | 最高，改文字即生效 | 换个模型或换个问法效果就抖；越写越长，靠打补丁堆规则 |
| RAG | 缺私有、最新或外部知识，答案还要能溯源 | 检索链路 + 每次调用的上下文 token | 天级 | 高，换文档即换答案 | 召回不到就答非所问；召回噪声导致引错来源；文档更新了答案还是旧的 |
| 微调 | 固定格式、固定语气、固定分类习惯，且 Prompt 反复约束不住 | 一次性算力 + 高质量标注数据 | 周级及以上 | 中，训坏需要回滚 | 格式稳了但知识变旧还答得很自信；新增一个类别就得重训；样本少时过拟合 |
| Workflow | 流程固定、节点明确、要求可审计可回放 | 编排开发与每个节点的调试 | 天到周级 | 最高，每一步都可见 | 分支随业务长尾爆炸；遇到没覆盖的输入直接失败；每加一个例外就要改图 |
| Agent | 路径无法事先穷举，下一步取决于中间结果 | 单次任务多次模型调用，成本与延迟随步数增长 | 周级，含评测建设 | 低，同输入可能走出不同路径 | 原地打转不收敛；成本与延迟失控；同题重跑结果不一致；出事故难复现 |

有两点值得单独拎出来：其一，**迭代速度和可控性是强相关的**——改动越快生效的方案，回退成本也越低，所以它们应当优先被尝试；其二，**Agent 那一行的"可控性低"不是缺点而是代价说明**，接受它之前先确认业务真的需要那份自由度。

## 失败信号：什么时候说明选错了

真实项目里几乎没有一次选对的，大家都是在"看到某个症状 → 调整"的循环里收敛。下面这张表把常见症状翻成了诊断结论：

| 你看到的症状 | 它说明什么 | 下一步动作 |
| --- | --- | --- |
| Prompt 里塞满了专有名词解释，越写越长 | 手写知识塞不下了 | 转 RAG，让知识外部化并可更新 |
| 换个问法、换个人问，质量就飘 | 任务表达没固化 | 先补 few-shot 示例与输出约束，不行再上微调 |
| 答案说得通，但引用来源对不上 | 知识进了上下文，可信性没守住 | 留在 RAG，补重排序和引用校验，不要急着微调 |
| 偶发输出不合规，下游解析报错 | 行为不稳 | 结构化输出约束优先，再考虑 LoRA 这类轻量微调 |
| 任务要分几步，但这些步骤能穷举 | 缺的不是知识，是编排 | 上 Workflow，暂时不需要 Agent |
| 中间结果决定下一步，且分支穷举不完 | 需要动态决策 | 上 Agent，同时配预算和步数上限 |
| Agent 跑多次路径各不相同，多数是错的 | 任务其实没那么开放 | 回退 Workflow，固化高频路径后再放 Agent |
| 调用链路越跑越长，延迟和账单都不可控 | 自由度超出了业务承受的上限 | Agent 降级为 Workflow，只在个别节点保留单点决策 |

这张表的用法是：**每一行都对应一个可观测、可验证的现象**，而不是"感觉效果不好"。面试时能把诊断说成这种颗粒度，基本就告别"名词解释型回答"了。

## 工程实践：演进路径与四条护栏

落到项目上，最常见的三条演进路径是这样的：

- **问答类**：Prompt → RAG → Workflow。先把问题说清楚，再把知识挂上去，最后用流程把多轮追问、引用校验、人工兜底串起来。
- **抽取与生成类**：Prompt → 结构化输出约束 → Workflow。字段抽取、表单填写这类任务，绝大多数卡在输出不稳定，压不到需要微调的程度。
- **开放式助手类**：Workflow → 局部 Agent。先用 Workflow 把主干跑稳，再在"确实写不死"的那一个节点里放一个带护栏的模型决策，而不是一开始就整条链路都交给它。

无论走哪条路径，有四条护栏建议从第一天就装上：

1. **先有评测集再谈升级**。经验值上，覆盖主要分支与典型错误类型的 30～100 条用例，就足以分辨两次改动谁的效果好；每条要写清期望输出和判分方式，否则"感觉变好了"不算数。
2. **一次只改一处**。先关掉检索重跑一遍，还错就不是 RAG 的问题；换成最强基座重跑，还错就不是 Prompt 的问题。这叫消融，比盯着日志猜快得多。
3. **给 Agent 设硬上限**：最大步数、单次运行的 token 上限、单步超时、同一个工具的重复调用次数，以及写操作必须幂等。下面是一个自用的配置示意（数值是经验值的保守起点，不是任何产品的默认值）：

```json
{
  "task": "refund_assistant",
  "plan": ["prompt", "rag", "workflow"],
  "fallback": "manual_review",
  "guardrails": {
    "max_steps": 8,
    "max_tokens_per_run": 60000,
    "step_timeout_ms": 20000,
    "retry_per_step": 1
  },
  "gates": {
    "prompt_to_rag": "评测集上缺知识类错误占比仍高于两成",
    "workflow_to_agent": "长尾用例多到分支加不动了"
  }
}
```

4. **把回退路径也做成产品行为**。Agent 失败时降级到 Workflow，Workflow 失败时转到人工，并且让用户看得到这句提示。这既是稳定性设计，也是和业务方谈妥的预期管理。

最后提醒一句这里最容易犯的顺序错误：**不要用一个更重的方案去掩盖一个没查清的问题。**Prompt 没调好就上微调，等于把错误固化进权重；检索没召回就上 Agent，等于让模型在一堆噪声里做更多次决策。

## 面试官的追问，你该怎么接

### 追问一：为什么很多项目不一开始就做微调？

从"换挡条件"讲，比从"成本高"讲更有说服力。第 1 篇谈过成本侧的取舍，这里补工程口径：微调必须有明确的触发线。经验做法是，**同一套 Prompt 加上十几个 few-shot 示例和结构化输出约束之后，仍有稳定复现的格式、语气或分类错误**，并且手里有数百到数千条（经验值区间）标注一致的干净数据，才值得动权重。

达不到这两条就先别动。因为微调一旦把某种行为焊进模型，后续想调整就得重训；而 Prompt 改一行字的成本几乎为零。真到非做不可的时候，也优先 LoRA 这类只训一小撮参数的轻量方案，训砸了丢掉适配器就能回到原点，不伤基座。

### 追问二：为什么不是所有复杂任务都适合 Agent？

关键在于把"复杂"和"开放"分开。**复杂是步骤多，开放是路径不确定**，Agent 只解决后者。步骤再多，只要能穷举、能画成图，Workflow 通常更划算也更稳。

还有三类任务即使开放，也要慎重：一是单次延迟和成本有硬约束的场景（Agent 一次任务可能触发多次模型调用，经验值在个位数到二三十次之间）；二是错一次代价很高的写操作（转账、发券、删数据）；三是结果必须可复现、可审计的场景。这三类要么不上 Agent，要么把写操作收回到 Workflow 里执行，Agent 只负责"决定怎么做"，不负责"直接做"。

### 追问三：Workflow 和 Agent 的分界线是什么？

一句话：**下一步由谁决定，就叫谁。**边是人画的，就是 Workflow；边是模型现场画的，就是 Agent。

再给一个人人能执行的操作判据：把过去一段时间的真实请求复盘一遍，如果绝大多数（经验值在八成上下）的路径都能画进同一张图且长期稳定，那就用 Workflow，剩下的长尾单独兜底或交给 Agent 处理。更常见也更推荐的形态其实是混合的：**Workflow 做主干，其中某一个节点内部嵌一个小 Agent**。这样既保住了整体可观测，又给开放的部分留了口子，出问题时能精确定位到那个节点。

### 追问四：Prompt、RAG、微调在同一个系统里怎么叠加？

可以叠加，而且中大型项目往往三个都在。分工上建议：**Prompt 定任务和输出格式，RAG 供料，微调兜底行为**，三者各管一层，不要互相越界。

有一条实践原则值得记住——**同一条规则只写在一个地方**。如果你既在 Prompt 里写了"必须用敬语"，又在训练数据里训了一遍敬语表达，将来改规则就得改两处，还可能出现两边不一致的情况。很多团队会忽略这点，结果半年后没人敢动那条规则。

### 追问五：怎么判断该从 Agent 回退到 Workflow？

看三个信号就够了：**高频路径稳定下来**（跑一段时间发现绝大多数请求就走那三五条路）、**成本或延迟失控**、**同题结果不一致开始引起用户投诉**。

这时的正确做法不是推翻 Agent，而是"固化高频、留口给长尾"：把那几条高频路径写成 Workflow 主干，剩下的长尾继续交给 Agent，并给整个链路设兜底节点。很多团队做完这一步会发现，成本降下来的同时效果反而更稳了——因为本来大部分请求压根不需要那份自由度。

### 追问六：上线后效果变差，怎么判断是选型错了还是实现错了？

按四步走：**先做错误分类**（每条坏样例标注是缺知识、行为不稳还是流程跑偏）；**再做消融**（关掉检索重跑、换成最强基座重跑，逐个排除）；**然后看全链路 trace**，确认坏在哪一步的输入输出；**最后才动 Prompt**。

这一步最容易犯的错是同时改三处，改完效果变好了也不知道是哪处在起作用。坚持一次只改一处、每次改动都用同一份评测集复测，是这个问题最实在的答案。

## 60 秒面试回答模板

> 我会先判断这个需求到底缺什么，而不是先挑技术。模型本来就会的，用 Prompt 把任务说清楚；缺私有或者最新知识的，上 RAG；固定格式、固定语气这类行为反复压不住的，才考虑微调。

> 再看这个任务要不要分步。流程能穷举、要求稳定可审计的，用 Workflow；只有下一步取决于中间结果、路径事先写不死的时候，才上 Agent。

> 所以落地顺序基本是 Prompt、RAG、Workflow 覆盖大部分需求，Agent 只在真正开放的任务上叠加，而且要带步数和预算上限。选错了也有信号：Prompt 越写越长说明该上 RAG，Workflow 分支加不动说明该考虑 Agent，反过来 Agent 同题重跑结果不一致，就说明该退回 Workflow。

## 加分项

如果能再说出这几点，基本就是加分回答了：

- **把五个词拆成两个层次**：Prompt、RAG、微调管内容层，Workflow、Agent 管流程层。能点出"它们不是同一维度的五选一，而是可以叠加"，面试官立刻知道你做过真项目。
- **每一次升级都配闸门和回退**：不是"我们上了 Agent"，而是"达到什么指标才允许上、上了之后什么情况退回来"。
- **明确说得出微调的换挡条件**，而不是笼统讲"微调成本高"。
- **强调"不用更重的方案掩盖没查清的问题"**：这句说出来，通常会被追问"那你一般怎么排查"，正好接上消融那一套。

## 常见误区

- **当成五选一**。实际上前三个解决"内容对不对"，后两个解决"流程怎么走"，一个成熟系统里常常同时出现三四种。
- **复杂就等于 Agent**。步骤多但可穷举的任务，Workflow 在成本、延迟、可观测性上全面占优。
- **用微调去灌知识**。把会变的内容焊进权重，等于给自己造了一个"改一次要重训一遍"的负债，这是第 1 篇也强调过的红线。
