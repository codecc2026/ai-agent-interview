# 近似检索和精确检索怎么权衡？

## 面试官为什么爱问这题

前面聊向量库和 MySQL 分工的时候留过一句：向量检索「需要 ANN」。这题就是在验收那句话。它考察的不是背结论——「大规模用近似、小规模用精确」谁都会说——而是取舍能力：牺牲掉的精确性到底牺牲在哪、多出来的性能从哪来、上线前拿什么证明这一刀砍得值。答不好的候选人通常两种表现：一种一口咬定 ANN 没毛病，追问「召回率多少、怎么测的」当场哑火；另一种能把 HNSW、IVF 的参数名背一遍，却说不清哪个参数跟召回挂钩、调大之后代价是什么。面试官要的是中间那层：把「近似」从一个形容词，变成一个可测量、可调参、可回滚的工程决策。

## 一句话先给结论

**精确检索是基准，近似检索是一笔交易：拿一部分召回率，换规模、延迟和成本；这笔交易线上敢不敢做，取决于 recall@k 有没有被测出来、盯得住，并用放宽召回加 rerank 兜底。**

## 核心原理：近似到底「近」掉了什么

### 精确检索为什么扛不住规模

精确检索就是暴力 KNN：每个查询和全库 N 条向量逐条算距离，复杂度 O(N×d)。以 768 维、fp32 存储为例，一条向量约 3KB，百万条库扫一遍就是 GB 级内存读取，延迟随 N 线性增长，并发一上来内存带宽先打满。经验值：十万级以内，暴力通常几毫秒到几十毫秒，多数业务能接受；到百万级往上，单查询延迟明显抬升，QPS 稍高就顶不住。所以「精确检索效果可控」这句话，只在数据量不失控的前提下成立。

### 两大家族怎么把计算省下来

图索引，以 HNSW 为代表：把向量组织成多层近邻图，查询从顶层入口贪心下行，底层沿邻边扩展候选队列，全程只访问一小部分节点。ef_search 控制候选队列长度（pgvector、Milvus 用这个名，faiss 里叫 efSearch，hnswlib 里通过 set_ef 设置）——队列越长访问越多，结果越接近暴力，召回越高、延迟也越高；M 是建图时每个节点的连接数，属于建库期参数，建好之后基本不再动。

倒排桶，以 IVF 为代表：先用聚类把全库切成 nlist 个桶，查询只扫离它最近的 nprobe 个桶。省计算的逻辑很直白：一万桶只扫一百桶。代价同样直白：目标向量所在的桶没被扫到，它就漏了。faiss 里把 nprobe 拉到 nlist，等于全扫，退化为精确检索。

量化（PQ、标量量化）是第三件事：把向量压缩存储，省内存，但算出来的距离本身带误差。它跟「访问哪些向量」无关，是叠在索引之上的第二层近似，两层的损失要分开度量。

### 边界：召回率 100% 也不等于精确

两个容易混的点。其一，recall@k 只定义在 top-k：ANN 把前 10 条全部找齐，第 11 条之后的排序完全可能不准，拿它做别的统计要小心。其二，IVF 加 PQ 的组合里，返回的分数是量化距离，同一查询内可比，跨查询不可比——想做「相似度低于阈值就拒答」这类逻辑，先确认分数的语义，之前聊引用与拒答护栏时用到的也是这类阈值，前提都是分数语义可靠。另外 ANN 的构建带随机性（聚类初始化、多线程建图的顺序），结果不严格可复现，精确检索则是完全确定的。

## 横向对比

| 维度 | 精确检索（暴力 KNN） | 近似检索（ANN） |
| --- | --- | --- |
| 延迟随规模 | 随 N 线性增长 | 大体平稳（访问的节点数是固定量级） |
| 召回保证 | top-k 严格正确 | 无 100% 保证，靠参数调 |
| 结果确定性 | 确定、可复现 | 构建带随机性，不完全可复现 |
| 分数语义 | 真实距离 | 可能是量化距离，跨查询不可比 |
| 内存与成本 | 索引简单，但扫全库吃带宽 | 索引自身有额外内存开销 |
| 适用规模 | 万到十万级（经验值） | 十万到亿级 |
| 典型场景 | 基准评估、小库、强一致性场景 | 通用问答、商品搜索、海量召回 |

| 路线 | 机制 | 关键参数 | 调召回的手段 | 内存 | 构建与更新 |
| --- | --- | --- | --- | --- | --- |
| Flat（暴力） | 全扫 | 无 | 不需要 | 原始向量 | 无构建，增删最灵活 |
| HNSW | 多层近邻图 | ef_search（查询期）、M、ef_construction（建库期） | 调大 ef_search | 图结构额外开销大 | 建图慢，支持增量但删除是弱项 |
| IVF / IVF+PQ | 聚类分桶 + 桶内扫 | nlist、nprobe | 调大 nprobe | 原始或量化向量，PQ 大幅省内存 | 需聚类训练，批量重建友好 |

| 现象 | 先查什么 | 对应动作 |
| --- | --- | --- |
| recall@10 低于预期 | 扫 ef_search / nprobe 曲线 | 取延迟拐点前的最大值；仍不够则换索引或收窄过滤面 |
| 延迟超标 | QPS 与 ef 配置 | 降 ef；上量化 + 原始向量重打分 |
| 过滤后结果变少甚至为空 | 过滤命中占比 | 改引擎内嵌过滤，或按过滤维度分片 |
| 内存放不下 | 索引大小 vs 机器规格 | IVF+PQ 或标量量化，必要时分片 |

## 工程实践

### 把 recall@k 做成发布指标

ANN 的取舍能不能落地，全看有没有把 recall@k 测出来。做法：从线上日志采样查询（经验值 1k 到 1w 条，覆盖长短查询与各类过滤组合），用 Flat 精确检索当基准，逐查询对比 ANN 结果，算 recall@10 与 recall@100。这跟之前排查 badcase 用的黄金集是同一套思路：基准集建好之后，每次调参、换索引、升级版本，都先跑一遍再上线。

```python
# 伪代码：ANN 召回率评估
# index_flat: 精确索引（基准）；index_ann: 待评估的近似索引
def evaluate_recall(queries, k=10):
    hits = 0
    for q in queries:
        _, exact_ids = index_flat.search(q, k)   # 基准：精确 top-k
        _, ann_ids   = index_ann.search(q, k)    # 待测：近似 top-k
        hits += len(set(exact_ids) & set(ann_ids))
    return hits / (len(queries) * k)            # recall@k

# 调参：扫 ef_search（或 nprobe），画「召回率-延迟」曲线
for ef in [50, 100, 200, 400, 800]:
    index_ann.hnsw.efSearch = ef               # faiss 写法；hnswlib 对应 set_ef(ef)
    r = evaluate_recall(sample_queries, k=10)
    p95 = measure_p95_latency(sample_queries)   # 同一批查询压延迟
    print(ef, r, p95)
# 经验值：recall 做到 0.95 之后边际收益明显变缓，拐点后再加 ef 不划算
```

经验值：通用问答场景通常把 recall@10 做到 0.95 以上再谈延迟优化；风控、合规类场景阈值往上提，必要时直接退回精确检索或更保守的索引配置。

### 过滤和 ANN 会互相拖累

线上查询很少是纯向量搜索，几乎都带过滤条件。过滤发生在 ANN 之后（post-filter）的写法，极端情况是 ANN 取回的候选全被过滤条件滤光，返回为空——库里明明有答案。更隐蔽的是「有结果但质量差」：候选池被过滤削薄，等于变相缩小了 ef 的有效值。缓解手段按代价从低到高：用引擎内嵌的过滤检索（如 faiss 搜索时挂 IDSelector，只对命中条件的向量算距离）；按高频过滤维度预分片，让每个分片的过滤命中密度足够高；实在不行，把该分片降级成精确扫描。之前讲过权限过滤要放在检索前，落到 ANN 这一层，就是这三种选型之间的权衡。

### 放宽召回、rerank 兜底

ANN 漏掉的多数是长尾近邻。常见组合是召回池放宽（top_k 取 20～50），重排后只取 3～8 条进上下文——这套口径前面聊混合检索与重排时给过。rerank 在这里多了一层身份：它不只是排序质量的补丁，也是 ANN 召回损耗的补偿。代价是召回池越大、重排延迟越高，所以 ef 与 top_k 不要同时拉满，先测 recall 曲线再定档位。

## 追问逐条作答

### 追问一：ANN 会漏召回，线上系统为什么还敢用？

因为漏的部分可测量、可控制。漏的主要是长尾近邻，头部命中在 ef 足够时相当稳定；recall 曲线测出来之后，「漏多少」从概率问题变成参数问题。再叠加 rerank 补偿与 badcase 监控，残余风险被压到业务可接受的范围。反过来，不测 recall 就上 ANN 才是真正的「不敢用」——不是技术不行，是心里没数。

### 追问二：recall@k 怎么测？样本多大才可信？

用精确索引当基准，采样真实查询逐条对比。样本量经验值 1k 起步、1w 更稳，且要分层：长查询短查询、带过滤与不带过滤、热门与冷门都要覆盖——只拿简单查询测出来的 recall 会虚高。样本集还要定期更换，避免参数在固定集合上过拟合。

### 追问三：HNSW 和 IVF 怎么选？

粗略经验：内存充裕、数据量在百万级上下、查询延迟优先，HNSW 通常更省心；数据量大到内存吃紧（千万级以上）、要压缩存储、或需要频繁批量重建，IVF+PQ 更合适。HNSW 的隐性成本是图结构的额外内存和较慢的建图；IVF 的隐性成本是聚类训练和桶间分布不均。没有哪个参数能两头都占：先算内存账，再测 recall，最后定。

### 追问四：把 ef_search 或 nprobe 拉满，不就变成精确检索了吗？

方向对，但代价不值得。faiss 里 nprobe 设为 nlist 确实退化成全扫，等价精确；ef_search 拉到远超库规模需要的探索深度后，召回增长趋平、延迟继续涨。既然目标就是精确，不如直接换 Flat 索引，语义更干净、行为更可预期。参数的意义是停在拐点上，不是拉满求安心。

### 追问五：过滤条件一多，召回为什么反而掉？

两个原因叠加。一是 post-filter 把候选池滤薄了：ANN 只保证「过滤前的 top-k」，过滤后剩多少它不管。二是过滤命中的向量在库里越稀疏，越可能落在没被扫到的区域——IVF 场景下目标桶被跳过的概率上升。对策就是工程实践那三条：内嵌过滤、按过滤维度分片、必要时局部退精确。

### 追问六：向量量化的精度损失怎么看？

量化是第二层近似，它的损失和索引层的漏召回要分开度量：评估方法不变，拿量化索引和 Flat 比 recall@k，差值就是量化的代价。经验值：标量量化通常损失很小；PQ 压缩比更高、损失也更大一些。对精度敏感的场景，用「量化粗排取大候选池、再取原始向量对候选重打分」的 refine 路线，把量化损失限制在召回阶段，排序阶段仍是真实距离。

## 60 秒面试回答模板

> 这题本质是性能和效果的取舍。精确检索 top-k 严格正确，但每个查询都要扫全库，延迟随数据量线性涨，百万级以上就顶不住。近似检索用图索引或聚类分桶，每个查询只访问一小部分向量，延迟平稳、吞吐高，代价是可能漏召回。所以工程上不是二选一：小库、基准评估、强一致场景直接用精确；海量召回用近似，先用精确结果把 recall@k 测出来——通用场景经验做到 0.95 以上——再按延迟预算定 ef 或 nprobe，配 rerank 兜底，召回池放宽、重排后取头部，漏的长尾大多能补回来。一句话：近似检索敢不敢用，不看胆子，看 recall 曲线测没测。

## 加分项

- 点出「ANN 分数语义」：IVF+PQ 返回的是量化距离，跨查询不可比，做阈值拒答前先确认——多数候选人意识不到分数还有语义问题。
- 知道 faiss 里 nprobe 设为 nlist 退化等价、HNSW 的删除是弱项这类实现层细节，说明真调过索引。
- 谈参数时先讲「扫曲线、找拐点」而不是报一个固定值，并能说清评估样本要分层。
- 把过滤对 ANN 的削弱单独拎出来，给出内嵌过滤、分片、局部退精确三档对策。

## 常见误区

- 把「recall 率 100%」当成「等于精确检索」：recall@k 只覆盖 top-k，且返回分数可能是近似距离。
- 只谈延迟不谈内存：HNSW 的图结构额外内存不小，不少场景是内存先爆，不是延迟先爆。
- 参数拍脑袋定值：ef_search=200 写死在配置里，库从十万长到千万，曲线再没重测过。
