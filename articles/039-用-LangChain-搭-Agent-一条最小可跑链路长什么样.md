# 用 LangChain 搭 Agent：一条最小可跑链路长什么样？

## 面试官为什么爱问这题

这题高频，因为它能一下子分出两类人。背过 API 的人会脱口而出某个创建函数，看着很熟；真正做过的人会先讲底层那条主线——工具怎么定义、模型怎么知道有什么工具、prompt 里怎么规定停止条件、决策到执行到回传的闭环怎么转起来。面试官问"最小可跑链路"，考的不是你记不记得某一个函数名，而是你能不能把 Agent 拆回那几块骨架，并且说清楚它为什么这时候调工具、什么时候停、失败了怎么办。前面聊过一条 `tool_calls` 消息在运行时怎么流转，也聊过把循环落成图时状态、节点、边怎么分工；这一篇退回到"动手搭"的视角，看这几块怎么用最少的代码接成一条能跑的东西。

## 一句话先给结论

**一条最小可跑的 LangChain Agent 就四步：定义工具 → 选模型并让它知道工具的 schema → 写 prompt（讲清角色、工具使用规则、停止条件、输出边界）→ 让"模型决策 → 工具执行 → 结果回传 → 继续或结束"形成闭环。框架给了两条路线：classic 路线用 `create_tool_calling_agent` 加 `AgentExecutor` 把结构一层层摆出来，适合看清内部；1.x 路线直接用 `create_agent`，由基于 LangGraph 的运行时驱动循环、状态和工具调用，更接近官方主线。API 会变，底层主线不变。**

## 核心原理：两条路线与一条主线

### 先看那条不变的主线

不管用哪条路线、哪个版本，Agent 的核心都是同一件事：让模型在循环里决定下一步，需要外部能力时调工具，看到结果后再决定继续还是停。拆开是四步。

**第一步，定义工具。** 把外部能力封成一个个边界清晰的能力单元：一个工具干什么、需要哪些参数、参数是什么类型，都要说清楚。粒度太细，模型要在十几个原子操作里选，容易选错；粒度太粗，一个工具塞进七八种行为，模型传参又容易出错。前面讲单工具设计时提过命名和描述的重要性，这里不再展开，只强调一点：工具是 Agent 和外部世界之间唯一的接口面，这一步没设计好，后面全在补坑。

**第二步，选模型并让它知道工具 schema。** 模型本身不知道你能调用什么，得把工具的定义随请求一起交给它。这一步依赖模型支持工具调用能力——模型的输出里会带上"我要调哪个工具、参数是什么"这样的结构化意图，而不是一段需要你自己去正则解析的文本。支持与否是模型能力问题，和用哪个框架无关。

**第三步，设计 prompt。** 这是最容易被低估的一步。prompt 里至少要讲清四件事：这个 Agent 的角色是什么；什么时候该用工具、什么时候直接回答；什么条件下算完成、可以停；输出有什么边界，比如"只根据工具返回回答，不要编"。少了停止条件，模型会没完没了地调工具；少了输出边界，模型会把工具没返回的内容自己补上。

**第四步，跑通闭环。** 把模型决策、工具执行、结果回传、继续或结束接成一个循环，直到模型判断任务完成或触发停止条件。这条闭环就是 Agent 和一次性的"调模型 → 拿结果"最本质的区别。

| 步骤 | 要解决的问题 | 没做好的典型症状 |
| --- | --- | --- |
| 定义工具 | 外部能力怎么封成清晰单元 | 模型在相似工具间反复选错 |
| 模型知道 schema | 模型怎么知道有哪些工具能调 | 模型凭空编一个不存在的工具名 |
| 设计 prompt | 角色、工具规则、停的条件、输出边界 | 不停止、不停调工具，或越过工具编答案 |
| 跑通闭环 | 决策到执行到回传怎么循环 | 工具结果没回灌，模型反复问同一件事 |

### 两条路线的差别在哪

框架把上面这套东西封装成了两种用法，差别不在能力，在抽象层次。

| 维度 | classic 路线 | 1.x 路线 |
| --- | --- | --- |
| 创建方式 | `create_tool_calling_agent` + `AgentExecutor` | 一个 `create_agent` |
| 循环驱动 | `AgentExecutor` 显式管理 | 基于 LangGraph 的运行时驱动 |
| 能看到的结构 | 模型、工具、prompt、执行器一层层摆出来 | 封装更高，细节藏在运行时里 |
| 适合场景 | 想理解内部结构、需要逐层定制 | 快速起步、贴近官方主线 |
| 代价 | 拼装代码多，要理解每个部件 | 抽象更厚，想改内部机制时不够直观 |

classic 路线的价值在"看得见"：你能清楚看到 prompt 模板、工具列表、模型和执行器是怎么接起来的，适合用来讲清内部结构，也适合需要逐层定制的场景。1.x 路线把循环、状态、工具调用都交给了一个基于 LangGraph 的运行时，一行创建就能起步，代价是内部机制被藏得更深。两条路线不是新旧对立的能力差距，而是抽象层次的取舍：理解内部用前者，快速落地用后者。面试时两条都能说出个所以然，比只背一个函数更是加分。

### 为什么"会调 create_agent"不等于"懂 Agent"

因为创建函数只解决了组装问题，没解决运行时的三个真问题：为什么调工具、什么时候停、失败怎么办。

为什么调工具，取决于工具的定义和 prompt 里的使用规则写得够不够清楚；什么时候停，取决于停止条件有没有落到 prompt 和判停逻辑里；失败怎么办，取决于执行器或运行时对工具报错、解析失败、超时的兜底策略。这三件事都发生在创建函数之外。所以面试官追问一句"它什么时候会停"，只会喊 API 名的人就答不上来了。

## 工程实践：一条能照抄的最小链路

以 classic 路线为例，把四步摆开：

```python
from langchain_core.tools import tool
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain.agents import create_tool_calling_agent, AgentExecutor

@tool
def get_order_status(order_id: str) -> str:
    """根据订单号查询订单状态。入参是订单编号字符串。"""
    # 真实实现里这里查数据库或调内部接口
    return f"订单 {order_id} 的状态是已发货"

tools = [get_order_status]

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是订单助手。需要查订单时调用工具；只根据工具返回回答，不要编造。"
               "当已经能回答用户问题时就停止，不要重复调用工具。"),
    ("human", "{input}"),
    MessagesPlaceholder(variable_name="agent_scratchpad"),
])

# model 是已初始化、且支持工具调用的聊天模型
agent = create_tool_calling_agent(model, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools, verbose=True)

result = executor.invoke({"input": "订单 12345 到哪了？"})
```

几个必须点出来的细节：

第一，`agent_scratchpad` 这个占位符不是可有可无。它承载的是 Agent 的中间步骤——模型的思考、工具调用、工具返回。少了它，模型在多轮循环里看不到自己之前做过什么，会重复调用同一个工具。前面讲 `tool_calls` 消息流转时说过这条"消息轨迹"是怎么一层层攒起来的，这里它就被塞进这个占位符里。

第二，system prompt 里那三句话分别对应三个运行时问题：只根据工具返回回答，管的是输出边界；能回答就停止，管的是停止条件；需要查就调工具，管的是触发条件。别小看这几句大白话，Agent 会不会乱调、会不会编，很大程度就靠它们。

第三，`verbose=True` 会把每一步的决策和工具调用打出来，调试阶段一定打开。Agent 的问题大多不是"跑不通"，而是"跑偏了"——调错工具、多调一轮、停不下来，这些都得看轨迹才能发现。

第四，兜底要提前想。工具会报错、模型可能返回解析不了的工具调用、循环可能超过预期轮数。经验值：`AgentExecutor` 里可以给 `max_iterations` 设一个上限（常见取个位数），并把 `handle_parsing_errors` 打开，让解析错误不至于直接把整条链打挂。具体数值要按任务复杂度试，不是越大越好。

如果走 1.x 路线，拼装会短很多：把工具和一个带停止条件的 system prompt 交给 `create_agent`，循环和状态交给它背后的运行时。但上面四条经验依旧成立——占位符、提示词三要素、看轨迹、设兜底，换条路线一样要处理，只是有些被运行时替你做了。

## 追问逐条作答

题库没有预设追问，下面几条是面试官最可能顺着深挖的。

**1. 两条路线你更推荐哪条？**

分开答：理解和教学用 classic，因为它把模型、工具、prompt、执行器一层层摆出来，内部结构看得见；快速落地用 1.x，因为一行 `create_agent` 就能起步，循环和状态交给基于 LangGraph 的运行时，贴近官方主线。真实项目里我倾向 1.x 起步，但前提是团队里有人能讲清底层主线，否则出问题时不知道从哪查。

**2. 为什么说"调一个 create_agent 就结束"是错的？**

因为创建函数只负责组装，运行时真正要解决的三个问题都在它之外：为什么这时候调工具（工具定义 + prompt 规则）、什么时候停（停止条件 + 判停逻辑）、失败怎么办（兜底策略）。答不出这三个，就说明没搞懂 Agent 怎么转。

**3. prompt 里为什么要写停止条件？不写会怎样？**

模型默认倾向于继续行动，不写"能回答就停"，它可能在已经拿到答案后还去调工具，导致多轮空转、延迟和成本都上去。停止条件是把"什么时候算完成"这个判断显式交给模型，配合执行器的最大轮数上限，一个管语义、一个管兜底。

**4. Agent 和 Workflow 有什么本质区别？**

Agent 的下一步由模型在运行时根据结果决定，路径不固定；Workflow 的步骤和分支是人事先编排好的，路径确定。之前聊过什么时候工作流比 Agent 更合适：路径固定、要求确定的场景用 Workflow 更稳，只有确实需要模型动态决策才上 Agent。二者不是替代关系。

**5. 工具调用失败了怎么兜底？**

分三层想：工具本身对可预期的错误返回结构化错误信息而不是抛异常，让模型能读懂并决定重试还是换路；执行器层开解析错误处理和最大轮数上限，防止解析失败打挂整链、防止死循环；再往上做观测，把每次工具调用的成功失败记下来，才能定位是哪一环的问题。

**6. 最小链路里工具粒度怎么把握？**

一个工具对应一个清晰的业务动作，参数尽量少且类型明确。别把"查订单 + 退款 + 改地址"塞进一个工具，模型传参会乱；也别把查订单拆成"查单号是否存在""查状态""查物流"三个，模型要多轮才能拼出答案。经验值：起步时工具数量控制在十几个以内，描述里把边界写清楚，比堆一堆细粒度工具更好用。

**7. 1.x 路线背后是 LangGraph，那还要单独学图编排吗？**

要。`create_agent` 只是把常见的 Agent 循环做成了封装，一旦你的任务需要自定义节点、人工审批、复杂分支、多角色协作，还是得回到图这一层。前面讲状态、节点、边三件套时说过，那套心智模型是进阶能力的基础，封装越厚越需要懂底层。

## 60 秒面试回答模板

> 最小可跑的 Agent 按四步搭：定义工具，封成边界清晰的单元；选支持工具调用的模型，把工具 schema 随请求交给它；写 prompt，讲清角色、何时用工具、什么条件算完成、输出边界；最后把模型决策、工具执行、结果回传、继续或结束接成闭环。框架有两条路：classic 用 create_tool_calling_agent 加 AgentExecutor，结构看得见；1.x 直接 create_agent，由基于 LangGraph 的运行时驱动，更贴近官方主线。API 在变，这四步主线不变。加分的不是背函数名，而是说清它为何调工具、何时停、失败怎么兜底。

## 加分项

- 两条路线都能讲，且说清差别在抽象层次而非能力高低。
- 明确点出"创建函数只解决组装，运行时三问题在函数之外"。
- 把 prompt 的三句话对应到输出边界、停止条件、触发条件，落到具体机制。
- 主动提兜底：工具返回结构化错误、执行器设上限、再往上做观测。

## 常见误区

- **只背一个创建函数**：答不出底层四步主线，面试官一追问"什么时候停"就露馅。
- **把两条路线说成新旧能力差距**：它们的差别是抽象层次和适用场景，不是谁更强。
- **忽略 prompt 里的停止条件和输出边界**：以为接上工具就自然正确，实际不写这两条就会空转和编造。
- **混淆 Agent 和 Workflow**：路径由模型动态决定才叫 Agent，路径人事先定好的是 Workflow。
