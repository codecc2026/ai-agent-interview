# 如何为 Agent 设计短期记忆和长期记忆系统？技术上通常怎么落地？

<!-- growth-hook:v1 -->
“短期记忆”“长期记忆”听着像一对现成组件，真落地时却最容易混成一锅：什么都往上下文里塞，或者什么都往向量库里存。这题考的就是你会不会先把两种记忆的职责切开，再按场景选实现。

## 面试官为什么爱问这题

这题高频，而且和"记忆分层是什么"那类问题不同——它追的是"技术上怎么落地"。面试官想听的不只是"分短期和长期"，而是你能不能说出具体用什么技术存、怎么注入回模型、什么场景选哪套方案。一个答得出"短期用 checkpointer、长期用向量库、超长对话用摘要加检索"的人，和一个只会说"要分层"的人，差距是实打实的项目经验。前面讲过记忆三层的分工是什么，这一篇往前走到实现层：短期和长期各自用什么技术、LangChain 体系里几套方案怎么定位、超长对话怎么兼顾不断档和省 token。

## 一句话先给结论

**先把记忆拆成两层，否则所有信息都塞进上下文，最后又贵又乱。短期记忆解决当前会话/线程不断档，核心是"读历史 → 拼进提示 → 调模型 → 写回历史"；长期记忆解决跨会话保留偏好、画像、结论和可复用事实，核心是"存结构化信息，按需召回"，不是每轮全量塞 prompt。技术上短期常把消息历史或线程状态存在内存、Redis 或 checkpointer，再用 `MessagesPlaceholder` 或图状态注入下一轮；长期更适合数据库、向量库，关系重要时放知识图谱。二者分开设计：短期服务任务连续性，长期服务跨任务复用。**

## 核心原理：两层的技术落点

### 短期记忆：读历史、注入、写回

短期记忆的核心循环是固定的：读历史 → 拼进提示 → 调模型 → 写回历史。技术落点有两个环节——存在哪、怎么注入。

存在哪：常见的选择是内存、Redis 或 checkpointer。内存最简单但进程重启就丢；Redis 是内存数据库、读写快，适合会话状态；checkpointer 是 LangGraph 里的持久化机制，按 `thread_id` 存线程状态，天然契合图编排。

怎么注入：下一轮把存下来的历史重新放进提示。在 LangChain 体系里用 `MessagesPlaceholder` 把消息列表插进 prompt 模板；在图里则是从状态里读出历史、组装进本轮输入。两条路径对应两类系统，见下面的定位辨析。

### 长期记忆：结构化存储、按需召回

长期记忆存的是跨会话的信息：偏好、画像、历史结论、可复用事实。核心是"存结构化信息，按需召回"。技术上放在数据库、向量库，或者当信息之间的关系很重要时放进知识图谱。关键点是不每轮全量塞进 prompt，而是当前任务需要时按相关性召回一小部分。

| 层 | 解决什么 | 核心循环 | 典型技术落点 |
| --- | --- | --- | --- |
| 短期记忆 | 当前会话/线程不断档 | 读历史 → 拼提示 → 调模型 → 写回 | 内存、Redis、checkpointer + 消息注入 |
| 长期记忆 | 跨会话保留偏好、事实 | 存结构化信息 → 按需召回 | 数据库、向量库、知识图谱 |

### 两套短期方案的定位辨析

这是这题的一个关键考点，题库专门点出：在 LangChain / LangGraph 体系下，有两套东西容易混淆。

`RunnableWithMessageHistory + BaseChatMessageHistory`：更适合理解为"对话历史注入"。它解决的是"历史消息怎么读写、怎么塞进下一轮 prompt"这件事，适合先把消息层面的读写讲明白。

LangGraph persistence / checkpointer：更适合理解为"线程级状态持久化"。它存的不是一个扁平的消息列表，而是整个图的状态，适合 Agent、图编排、需要线程级状态管理的场景。

两者不是谁替代谁，而是抽象层次和适用场景不同。一个偏"消息历史"，一个偏"线程状态"。

| 方案 | 更适合理解为 | 适合场景 |
| --- | --- | --- |
| RunnableWithMessageHistory + BaseChatMessageHistory | 对话历史注入 | 聊天助手、轻量多轮问答 |
| LangGraph checkpointer | 线程级状态持久化 | 复杂 Agent、图编排、线程级状态管理 |

据此，一个稳的落地划分是：聊天助手或轻量多轮问答，优先消息历史方案；复杂 Agent 或 LangGraph，优先 `thread_id + checkpointer`；跨会话的偏好、事实、画像，走长期存储、按需检索，不硬塞上下文。

这个划分不是非此即彼的宗教之争，而是看你的状态有多复杂。如果你的状态就是一串消息，消息历史方案够用且直观；如果你的状态里还有"当前意图""待办队列""审批标记"这些结构，图的状态持久化才划算，因为它管的本来就不只是消息。经验值：从消息历史起步，等状态里出现消息装不下的字段时再迁到 checkpointer，比一上来就上图更省事。

## 工程实践：超长多轮对话的四种手段

当对话轮次多到塞不下时，怎么兼顾"不断档"和"省 token"?题库给了四种手段，各有适用面：

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| 滑动窗口 | 只保留最近 N 轮原文 | 简单直接，但容易丢早期约束 |
| 周期性摘要 | 每隔几轮压成结构化总结，保留目标、已确认事实、待办、偏好 | 丢细节，摘要本身要额外调用 |
| 检索式补充 | 旧对话写入向量库/长期存储，按当前问题召回相关片段 | 要建索引，工程复杂 |
| 结构化记忆槽 | 城市、会员等级、偏好等固定信息直接落键值/数据库 | 只适合固定字段，覆盖面窄 |

这四种不互斥，生产里常组合：近期对话用滑动窗口保原文细节，更早的做周期性摘要保脉络，关键事实落结构化记忆槽让模型不用每次"回忆"，需要时再从向量库检索相关旧对话。记忆系统不是"历史保存得越多越好"，而是要区分什么该原样保留、什么该摘要、什么该结构化、什么该按需检索。

一段伪代码示意短期循环：

```python
# 伪代码：短期记忆的"读历史 → 注入 → 调模型 → 写回"循环
history = store.load(thread_id)                    # 读历史：从 Redis/checkpointer
messages = build_messages(history, current_input)  # 注入：含 MessagesPlaceholder
answer = model.invoke(messages)                    # 调模型
store.append(thread_id, current_input, answer)     # 写回：更新历史

# store/build_messages 为业务侧：store 对应 Redis 或 checkpointer
# build_messages 负责把历史拼进符合模板的消息列表
```

要点：`store` 是存储介质（Redis 或 checkpointer），`build_messages` 负责把历史按模板注入。四个步骤构成闭环，变量都是业务侧实现。具体 API 按你用的库来，这里只示意这个不变的循环。

## 追问逐条作答

### 追问一：RunnableWithMessageHistory 和 LangGraph checkpointer 怎么理解各自的定位？

前者是"对话历史注入"，解决历史消息怎么读写、怎么塞进下一轮 prompt，适合聊天助手这类先把消息层讲清楚的场景；后者是"线程级状态持久化"，存的是整个图的状态，适合复杂 Agent、图编排和需要线程级状态管理的场景。抽象层次不同：一个管消息历史，一个管线程状态。落地时按系统复杂度选：轻量问答用前者，复杂 Agent 用 `thread_id + checkpointer`。

### 追问二：Redis 更适合做短期记忆持久化，还是长期记忆？

更适合短期。Redis 是内存数据库、读写快，适合存会话状态、近期历史这类高频读写、随会话释放的数据，做短期记忆的持久化或缓存层很合适。长期记忆那种按语义检索、按相关性召回、量大且要长期保存的场景，更适合向量库或数据库——Redis 不是为语义检索设计的。经验值：高频会话状态用 Redis，语义检索的长期沉淀用向量库/数据库，按访问模式选。

### 追问三：为什么不能把长期记忆每轮全量塞进 prompt？

两个原因。一是成本，长期记忆可能积累几百上千条，全塞进去 token 成本很高；二是效果，大量记忆会稀释当前输入的相关性，模型在长上下文里容易顾此失彼。正确做法是按需召回——当前任务需要哪些，就检索出相关的几条放进窗口。前面讲记忆分层时说过窗口是昂贵资源，这里是同一个道理在实现层的体现。

### 追问四（自补）：什么信息该做成结构化记忆槽，而不是走检索？

固定的、扁平的、能用一个字段装下的信息，适合做结构化记忆槽。比如用户所在城市、会员等级、明确表达的偏好、任务的关键状态。这类信息用检索反而绕远——直接读一个字段又快又准，也不用担心检索召回不到。判断标准：这个信息能不能用一个键值直接取到？能，就落结构化槽；不能（比如是一段需要语义匹配的历史经历），才走检索。

### 追问五（自补）：摘要压缩会丢细节，怎么降低损失？

靠结构化摘要。不要让模型自由发挥写一段笼统总结，而是按固定结构抽取：目标是什么、已确认的事实、还没做完的待办、用户明确表达的偏好。结构化字段能保住关键信息，减少重要细节被压掉。另外，摘要是渐进的——每隔几轮压一次，而不是一次性把所有历史压成一段，这样近期的细节还能以原文形式保留在窗口里。经验值：摘要触发的轮数阈值按任务调，别每轮都做。

## 60 秒面试回答模板

> 记忆分两层。短期解决当前会话不断档，核心循环是读历史、拼提示、调模型、写回历史，技术上把消息历史或线程状态存在内存、Redis 或 checkpointer，再用 MessagesPlaceholder 或图状态注入下一轮。长期解决跨会话保留偏好、画像、结论，存结构化信息、按需召回，放数据库或向量库，关系重要时放知识图谱，不每轮全塞。方案上，轻量问答用消息历史，复杂 Agent 用 thread_id 加 checkpointer，长期信息按需检索。超长对话组合四种手段：近期滑动窗口保细节，早期周期摘要保脉络，固定信息落结构化槽，需要时从向量库检索。核心是区分什么原样保留、什么摘要、什么结构化、什么按需检索。

## 加分项

- 把短期记忆讲成"读历史—注入—调模型—写回"的闭环，落到实现动作。
- 分清消息历史方案和 checkpointer 的定位：一个注入消息，一个持久化线程状态。
- 给出按场景选方案的清晰划分，而不是笼统说"分层"。
- 四种省 token 手段讲清各自代价，并说生产里怎么组合。

## 常见误区

- **把记忆全塞进上下文**：又贵又乱，长期记忆应按需召回，不能每轮全量注入。
- **混淆消息历史和 checkpointer**：前者管对话历史注入，后者管线程级状态持久化，抽象层次不同。
- **认为 Redis 适合长期记忆**：Redis 适合高频读写的短期状态，语义检索的长期沉淀更适合向量库/数据库。
