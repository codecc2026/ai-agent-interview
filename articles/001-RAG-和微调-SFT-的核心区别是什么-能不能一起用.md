# RAG 和微调（SFT）的核心区别是什么？能不能一起用？

## 一句话先给结论

**RAG 改的是模型的"输入"，微调改的是模型的"参数"。**

RAG 解决「知识从哪里来」，微调解决「模型应该怎么表现」。这两件事不在一个层次上，所以它们不是二选一，而是各管一摊。

## 先把区别说清楚

| 维度 | RAG | 微调（SFT） |
| --- | --- | --- |
| 作用对象 | 喂进去的上下文 | 模型的权重参数 |
| 生效时机 | 每次推理时动态检索 | 训练时一次性内化 |
| 知识更新 | 改文档即可，分钟级生效 | 需重新训练，天到周级 |
| 成本结构 | 检索成本 + 每次调用的 token | 一次性算力 + 高质量标注数据 |
| 可溯源性 | 天然支持引用原文 | 无法追溯来源 |
| 主要解决 | 缺知识、知识过期、私有知识 | 缺稳定行为、格式、语气、分类习惯 |
| 典型失败 | 检索没召回，模型就无米下锅 | 过拟合、灾难性遗忘 |

有个比方很好用：**RAG 是开卷考试，微调是考前背进脑子**。开卷考的好处是资料能随时换，坏处是翻不到就等于不会；背进脑子的好处是脱口而出，坏处是改一个字都得重新背一遍。

## 为什么这个区分在工程上很重要

因为它们的**失败模式完全不同**，排查方向也完全不同。

RAG 出问题，你要查的是切块策略、Embedding 模型、召回率、重排序、上下文拼接顺序——全是链路工程问题。微调出问题，你要查的是训练数据分布、标注一致性、学习率、灾难性遗忘——全是数据和训练问题。

把这两类问题混在一起谈"效果不好"，是面试里最常见的减分项。

## 能不能一起用

能，而且企业项目里这种组合很常见。分工通常是这样：

- **RAG 负责知识供给**：产品政策、技术文档、最新法规，这些会变的东西必须放外边。
- **微调负责行为稳定**：输出格式、行业语气、固定的分类标准，这些不会变的东西放进去。

举个具体例子。一个保险客服智能体：理赔条款每季度都更新，这部分靠 RAG，保证答案永远基于最新条款；但对客话术、合规表述、"请先提供保单号"这样的引导习惯，靠微调或强结构化输出保证稳定。

**落地顺序上的经验是：先做 RAG，把知识链路跑通，再看行为问题要不要上微调。** 因为很多你以为需要微调的行为问题，其实换个 Prompt 或加个结构化输出约束就解决了，成本从几万块降到几行字。

## 面试官的追问，你该怎么接

### 追问一：为什么多数企业项目不会优先做续训？

这里要区分**续训（Continued Pre-training）**和**微调（SFT）**。续训是在大量领域无标注语料上继续做预训练，为的是让模型"懂这个行业的黑话"。

它不优先的理由很实在：

1. **数据门槛高**。续训要的是海量领域语料，不是几百条问答。多数企业拿不出这个量，也凑不齐质量。
2. **算力成本高**。动辄几卡几天的训练，对中小团队不划算。
3. **灾难性遗忘风险**。通用能力可能掉，等于捡了芝麻丢了西瓜。
4. **收益不可控**。投入产出比不如直接上 RAG 明显，而 RAG 的效果是能立刻验证的。
5. **失效不灵活**。语料变了要重训，不如换文档来得快。

一句话总结：**续训是"让模型懂行"，但懂行这件事，用 RAG 把资料递到眼前也能做到，且便宜得多。**

### 追问二：什么场景适合 RAG + 微调组合？

三个典型场景：

- **强专业领域问答**：法律、医疗、金融研报。术语密度高，微调解决术语理解，RAG 解决具体条款和案例的引用。
- **客服 / 电销**：话术风格和合规约束靠微调固化，产品信息和政策靠 RAG 保鲜。
- **结构化抽取**：从合同、票据里抽字段。微调保证输出格式百分百稳定，RAG 提供抽取规则和样例。

回答时可以补一句判断标准：**当"知识会变"和"行为要稳"这两个需求同时存在时，才需要组合。**只满足其一，单用一种就够了。

### 追问三：预算有限，先做哪一个？

先做 RAG。理由是可验证、可回退、成本低：

- RAG 一周内就能上线一个可用版本，效果不好随时调切块和检索，试错成本几乎为零。
- 微调一旦训坏，可能把通用能力搞崩，回退成本高。
- RAG 自带引用溯源，业务方能直接验收答案对不对；微调输出的结果，错了你都不知道错在哪。

如果行为问题确实卡得死，可以走 **LoRA** 这类低成本微调的路径，几千条高质量数据就能见效，训不好也只是丢掉一个适配器，不动基座模型。

## 60 秒面试回答模板

> RAG 和微调不是替代关系，它们解决不同层次的问题。RAG 改的是输入，解决知识来源问题，适合时效性强、需要溯源、更新频繁的场景；微调改的是参数，解决行为稳定问题，适合固定格式、固定语气、固定分类标准的场景。
>
> 工程上我一般先上 RAG，因为见效快、成本低、可回退、还能溯源。只有在行为稳定性真的靠 Prompt 和结构化输出解决不了时，才考虑微调，而且优先用 LoRA 这类低成本方案。
>
> 二者可以组合：RAG 供知识，微调管行为。收益最大的是知识会变、行为要稳同时成立的场景，比如保险客服——条款用 RAG 保持最新，话术和合规用微调固化。

## 加分项

如果你能再说出这几点，基本就是加分回答了：

- **微调的数据质量远比数量重要**。500 条干净数据，往往胜过 5 万条噪声数据。
- **RAG 的上限在于检索**。检索不到，模型再强也无米下锅，所以优化 RAG 的优先级是"召回 > 排序 > 生成"。
- **不要为了微调整而微调**。很多需求其实用「好的 Prompt + 结构化输出 + 少量示例」就能达标。
