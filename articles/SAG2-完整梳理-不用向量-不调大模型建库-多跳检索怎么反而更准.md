# SAG2 完整梳理：不用向量、不调大模型建库，多跳检索怎么反而更准

## 2.36 秒和 7000 倍，先把账看明白

11,656 段文本建库，从 4.57 小时变成 2.36 秒，离线模型调用从逐段抽取变成 0，2,826 万 tokens 的消耗也一起归零。这两个耗时分属两篇论文、两台机器，不是同条件对比，后面会拆口径。10 月中旬挂出来的这篇论文，11 月初在中文技术圈刷屏，标题一个比一个狠，最流行的一句是「RAG 这次真死了」。

## 先给结论

**SAG2 把多跳检索里最贵的「建立关联」从建库阶段搬到了提问阶段：本地只对原文分词建一个 SQLite 倒排索引，提问时用 BM25 粗筛，用一个只输出判定分数的 JEV 模型挑出真证据，再从证据段落里抽关键词继续检索，最多迭代两轮，最后把原始段落交出去。**

代价也一起搬了过去：建库几乎免费，每次提问却要对上百个候选做模型判定。理解这一点，后面所有数字都顺了。

## 它要解决的是「线索断了」

多跳问题的麻烦，用一个流传很广的例子就能说清：

- 文档一：A 公司全资收购了 B 公司
- 文档二：张三被任命为 A 公司 CTO
- 文档三：张三离职，加入盘古大模型项目
- 提问：收购 B 公司的企业，其 CTO 后来加入了哪个项目？

文档三里「收购」「B 公司」「CTO」一个词都没有。按问题去算相似度，无论向量还是 BM25，都很难一步跳到它。人类做法是顺着已知事实往下找：先确认收购方是 A 公司，再查 A 公司的 CTO 是张三，最后查张三去了哪。

过去几年补这一课的路子有共同点：向量 RAG 靠语义召回但线索容易断；GraphRAG、LightRAG、HippoRAG 2 这些结构增强方案在入库前用大模型抽取实体关系、建图谱索引；SAG 一代轻量一些，只抽「事项 + 一组实体」，查询时用 SQL join 现场串；LLM Wiki 让模型把资料编译成一套 wiki 页，NotebookLM 则走云端笔记本的问答与摘要。这些做法都要在入库时先把资料读一遍。

**每往前走一步，基本都是在入库时多花一点钱、多调几次模型，换检索的准确度。** 于是维护成本跟着涨：文件改一个字，重新切块、重新向量化，图谱和 wiki 还得重算关系或重写页面。

SAG2 反过来走：入库时什么语义都不理解，把理解留到真正有人提问、且只处理当前问题需要的那一小批候选。

## 六条路线，各自在补哪一块

先把概念摆正：SAG2 不是 RAG 的对立面，它换掉的只是 RAG 链路里检索这一段，答案仍然由模型基于检索证据生成。下面说的「RAG 各种方案」，指的是检索这一段这些年换过的几条路线。

这条链路同时被四个约束拽着：问法和原文用词不一样还能不能找到（语义鸿沟）；答案散在几份文档里能不能串起来（多跳关联）；文件改一个字要重算多少东西（维护成本）；每次提问愿意付多少延迟和模型费（查询预算）。历史上，语义鸿沟和多跳关联大多靠入库时多算来解决，查询预算也鼓励把工作提前；只有维护成本反过来要求入库越轻越好。历代方案基本是在推同一个滑块：入库多算一点，查询就省一点；入库什么都不算，查询就得现场补。SAG2 把滑块推到入库为零那一端，再用查询侧的判定把丢掉的关联补回来，等于拿查询预算换维护成本。

| 要解的约束 | 主要承接方案 | 用什么换 | 换完剩下的麻烦 |
| --- | --- | --- | --- |
| 词面不一致 | 向量 RAG、混合检索 | 入库算 embedding，多一套稠密索引 | 多跳线索仍会断；改字要重新向量化 |
| 跨文档线索串联 | GraphRAG、LightRAG、HippoRAG 2 | 入库用 LLM 抽实体关系、建图 | 建库成本随文档量涨，改文件要重算图 |
| 查询时才串线索 | SAG 一代 | 事项—实体超边，提问时 SQL join | 仍要逐段调 LLM 建库，小时级 |
| 建库太重、改动太贵 | SAG2 | 只分词建 SQLite，判定挪到查询时 | 语义鸿沟重新出现，每问几百次判定 |
| 判定模型不可用 | 本地 rerank 模式 | 用 0.6B 级 reranker 换私有化 | 多轮带上下文的判定明显掉点 |

把优缺点摊开，六条路线的差别就清楚了：

| 方案 | 强项 | 短处 | 成本重心 |
| --- | --- | --- | --- |
| 向量 RAG（单跳 dense） | 改述、同义、口语化问法能召回，工程生态成熟 | 只比相似度，线索断在跨文档那一跳；Enterprise Overall 仅 46.0% | 入库算 embedding，查询一次向量检索 |
| BM25 / 词法 | 零模型调用建库，表名、条款号、代码标识符精确命中；Enterprise Overall 68.4% | 改述与别名直接漏，Semantic 类只有 43.2% | 几乎全在查询，且极轻 |
| 混合检索 + rerank | 两路召回互补，工程上常被当作默认起点 | 两套索引都要维护；单次召回仍是单跳，多跳证据不会自己串 | 入库加每次 rerank |
| 图谱类方案 | 把多跳变成图遍历，关系显式可解释 | 在规模研究的资源约束下，51 万文档全量建不完索引 | 入库时 LLM 抽取，最重 |
| SAG 一代 | 不建全局图，查询时按实体现场 join；MuSiQue R@10 83.37 | 4.57 小时、2,826 万 tokens 建库；MySQL 加 Elasticsearch 两套底座 | 入库重，查询反而轻 |
| SAG2 | 2.36 秒、0 次调用建库，单 SQLite 文件可增量更新；MuSiQue R@10 86.62 | 千题 331,325 次判定、约 $4.33；依赖托管 JEV；词法召回天花板 | 几乎全搬到查询侧 |

表中 Enterprise 数值是文档召回率，来自基准论文 Tables 6–7 的基线实现，不是等价算力下的同实现比较；MuSiQue 数字出自 SAG2 论文 Table 1，其中三个基线转引自 SAG 一代论文，口径见后文数字一节。这两个数据集的结论不能互相外推：前者是合成企业语料的文档召回，后者是多跳证据段落的召回。

各自真正解决的核心问题，一句话一条：

- **向量 RAG**：用户问法和原文用词对不上时，还能把相关段落找回来
- **BM25 / 混合检索**：不让语义模糊匹配把编号、条款、代码这类精确线索冲掉
- **图谱类**：把「顺着线索找下一份文档」提前到入库，让多跳变成一次图遍历
- **SAG 一代**：不建全局图也能做多跳，代价留在建库那一侧
- **SAG2**：让建库降到 0 次模型调用，同时别把多跳能力一起丢掉
- **Agentic SAG2 / 本地 rerank**：补上「固定轮数循环」和「判定模型不合规」这两个新冒出来的问题

**向量 RAG 和 SAG2 不是精度之争，是分工之争。** SAG2 在三个多跳集上比 BM25 高 32.21 / 25.93 / 12.10 点，赢的是证据串联；换到需要理解改述的 Semantic 类，它只有 58.40%，比自己 Basic 类的 86.86% 低 28.46 点，词法召回的天花板就露出来了。同一份企业语料里，基准论文给的纯向量 Overall 46.0%、Semantic 24.8%，都低于 BM25 的 68.4% 与 43.2%，「向量一定比词法准」在这份合成语料上并不成立。两类方法补的是不同窟窿，别拿一个数据集的胜负去选底座。

**SAG 一代到 SAG2，砍的是抽取，留的是动态关联。** 两代都认定关联该在提问时按当前问题展开，区别是一代还得先把事项和实体抽成结构化记录，二代直接从命中段落里拿现成的词。放到账上：一代把成本一次性付在建库（4.57 小时），二代把它摊到每次提问（千题 331,325 次判定）。二代并不总更划算，SAG 一代在 MuSiQue 的 R@1、R@2 还高于二代，说明二代优势集中在「能给阅读模型多几条候选」的时候；语料稳定、查询极高频时，一代那笔一次性的入库成本反而摊得更薄。

**和图谱类比，区别只在关联什么时候建。** 图谱类把关系在建库阶段一次性建好，之后每次查询顺着边走；SAG2 每次提问只现场建一小块关联，用完就丢。前者在语料稳定、查询密集时划算，规模研究里 LightRAG 只建到 2,254 份、MS-GraphRAG 到 8,750 份、HippoRAG 2 与 LinearRAG 到 131,876 份，卡住的是入库而不是准确率；后者在文件天天改、一天问不了几次的本地库里更合适。规模研究的末档是 511,959 份文档，与基准的 511,962 份只差 3 份；在这个量级上，图谱类没跑完全量，SAG2 的清点、建库与完整性检查合计 8 分 32 秒（官方稿口径），差别就在于它从不预先理解内容。

把这些对比叠起来，选型的分歧不在「谁更准」，而在成本记在哪本账上。下面把 SAG 到 SAG2 这张账单逐项拆开。

## 从 SAG 到 SAG2：砍掉的到底是什么

官方作者给过一个说法叫「智能守恒」：有多少计算就有多少智能。Embedding 是介于简单计算和 LLM 之间的弱智能，负责快速模糊匹配；JEV 恰好也在那个位置，负责快速判断内容有没有用。既然查询时已经有了一个便宜的弱智能，就没必要再在建库时把整库过一遍模型。

| 维度 | SAG 一代 | SAG2 |
| --- | --- | --- |
| 关联单位 | 事项 → 实体 → 另一个事项 | 段落 → 关键词 → 另一个段落 |
| 关联何时建立 | 建库时抽取，查询时 SQL join 激活 | 查询时按本次问题即时展开 |
| 建库要调模型 | 逐段调 LLM 抽事项与实体 | 0 次 |
| 需要 Embedding | 需要，稠密检索由 Elasticsearch 承担 | 不需要 |
| 存储 | MySQL + Elasticsearch | 单个 SQLite FTS5 文件 |
| MuSiQue 建库 | 4.57 小时，2,826 万 tokens | 2.36 秒，25.87 MiB，0 次调用 |
| 返回给模型 | 映射回原始 chunk | 原始段落，全程不改写 |

「动态超边」这个词容易被架构图带偏，其实说的是一件很朴素的事：一个关键词连着好几个段落，一个段落里也有好几个关键词，这些联系直接来自原文，不需要预先抽取。SAG 一代得先把「张三 = A 公司 CTO」这类事项抽成结构化记录；SAG2 只是从命中的段落里拿现成的词，再去索引里找同样含这个词的段落。

注意两个数字不能直接当成同条件对比：4.57 小时是 SAG 一代论文对同一批 11,656 段语料的离线统计；2.36 秒的硬件与测法出自官方发布稿，作者写的是「在一台 M4 Pro、64 GB 内存的 Mac 上，从空数据库连续重建三次，中间值只有 2.36 秒」，SAG2 论文 Table 3 只给结果数字，没披露机器和计时边界。官方稿原话是「两次记录的建库耗时相差约 7,000 倍」，并点明前一个数字出自 SAG 一代论文 —— 这是两篇论文、两台机器两次记录的比值，不是同一台机器跑同一个任务的加速比。

## 建库：只做分词和写索引

建库这一步薄到几乎没什么可讲，但几个参数值得抄下来，因为复现时改任何一个都会改变结果：

- 文本先归一化、分词，论文实现里用 Jieba，并额外处理连写的拉丁词，去掉固定停用词表，再用一条轻量大小写规则提取多词名称短语，不做实体分类、不做消歧
- 相邻段落按名义 2,200 字符分组，单个超长段落保持完整不切；MuSiQue 的 11,656 个段落对应 11,656 个索引单元
- 索引含 title、heading、body 三个字段，BM25 字段权重为 (2, 2, 1)；基准数据的 heading 字段为空
- 同一个 SQLite 文件里同时存原文、标题别名和词项文档频率，别名与统计都是本地派生，不调模型
- 建库产物 25.87 MiB，离线模型调用与费用均为 0

这里藏着一个产品层面的变化：索引只是原文的一个可查询投影，文件留在原目录、改了自动增量更新，不需要「上传—等待处理—重新发布」这套流程。SAG Wiki 把这一点做成了卖点，后面会讲。

## BM25 是什么：一个不用模型的打分公式

前面一直把 BM25 当默认底座，这里把它拆开。BM25 是 Best Matching 25 的缩写，出自上世纪 90 年代伦敦城市大学的 Okapi 检索系统，Robertson 与 Walker 在 1994 年 SIGIR 给出了它的近似形式，名字里的 25 指 Best Matching 系列的第 25 版。它是 TF-IDF 的改良版，今天 Lucene、Elasticsearch 和 SQLite FTS5 的默认相关性公式都出自这一支。

它只回答一个问题：查询里的每个词，在一段文本里值多少分。把查询词逐项算分再加总，就是这段文本对这次查询的相关度：

```text
score(D,Q) = Σ IDF(q) · TF(q,D)
TF = f·(k1+1) / (f + k1·B)
B  = 1-b + b·|D|/avgdl
IDF(q) = ln(1 + (N-df+0.5)/(df+0.5))
```

f 是词 q 在文本 D 里出现的次数，|D| 是 D 的词元数，avgdl 是全库平均长度，N 是总文本数，df 是含 q 的文本数。IDF 有几种平滑变体，这里写的是 Lucene 常用的形式，不同实现的常数略有差别。公式里藏着三条经验，每条治 TF-IDF 的一个老毛病：

| 机制 | 在公式里 | 治什么毛病 | 取值 |
| --- | --- | --- | --- |
| 词频饱和 | 分子分母同时含 f | 重复堆一个词不能无限刷分 | k1 通常 1.2–2.0 |
| 长度归一化 | 分母里的 B | 长段落别靠篇幅白占便宜 | b 通常 0.75 |
| 逆文档频率 | 乘在最前的 IDF | 满库都是的词几乎不给分 | 由 N 与 df 算出 |

这套打分全程只统计词，不认识同义词、别名和改述，也不懂「这段是不是答案链上必需的一环」。开头那个收购例子断在这里；论文 limitations 里写的「改述、别名、没有可用词面联系的证据仍会漏」，根子也在这里。所以 SAG2 里的 JEV 判定和迭代扩展不是锦上添花，是给 BM25 补语义、补线索的必需零件。

落到 SQLite FTS5，几个复现时会踩的点值得记。内置的 `bm25()` 不用自己实现公式，k1 与 b 硬编码为 1.2 和 0.75；列权重按表的列顺序作为额外参数传入，论文给的 (2, 2, 1) 对应 title / heading / body 三列。FTS5 返回的是取负后的分数，**数值越小越相关**，直接按默认升序排就对，习惯性加 DESC 反而会把最好的结果排到最后。

```sql
-- 示意写法，非论文仓库原码
SELECT rowid,
       bm25(idx, 2.0, 2.0, 1.0) AS s
FROM idx WHERE idx MATCH ?
ORDER BY s LIMIT 100;
```

论文首轮用最多 80 个词元以 OR 连接，取前 B=100 条候选；扩展轮要求命中挑出的扩展词，不再要求命中原问题词。BM25 在这儿只负责快速粗筛，排完还会被 JEV 整个重排 —— 后面消融表里 54.41 到 67.93 那一跳，就是重排带来的。

## 检索：三轮循环把证据串起来

查询时才是 SAG2 的主体。论文 Algorithm 1 的默认参数如下：

| 参数 | 值 | 作用 |
| --- | --- | --- |
| B | 100 | 首轮 BM25 候选、每轮新增候选、最终保留上限 |
| p | 5 | 首轮 BM25 前 5 条受保护，后续不被挤掉 |
| s | 10 | 每轮用作扩展起点的段落数 |
| L | 20 | 每轮挑出的扩展词数 |
| H | 2 | 首轮之后最多再扩展两轮，即最多三轮打分 |
| 查询词 | 最多 80 | 首轮用 OR 连接的不同词元上限 |
| 并发 | 20 | 问题级与 HTTP 级并发均封顶 20 |

流程可以压成一段伪代码：

```python
# 伪代码，参数取论文默认值
def search(q, idx, B=100, s=10, L=20, H=2):
    C = bm25(q, B)
    P, E, R, seeds = C[:5], [], [], []
    for r in range(H + 1):
        if not C:
            break
        U = merge(P, seeds, C)
        R = rank(U, jev(q, U, E))
        if r == H:
            break
        seeds = top(R, s)
        terms = pick(seeds, L)
        if not terms:
            break
        C = expand(terms, B)
        E = context(R, C)
    return diversify(R[:10])
```

几个容易被一句「BM25 + 判定模型」糊过去的细节：

**扩展词不是随便挑高频词。** 打分按词频、逆文档频率、该词所在句与原始问题的重合度、以及来源段落的 JEV 分数加权；整段完全由原问题词构成的词、以及在全库文档频率为零的词会被排除。这套权重偏向「在有用段落里反复出现、在全库罕见、且和原问题出现在同一句」的词。

**判定分数只用来排序，不是阈值。** 每轮给候选段落算 `s = J(q, d; E) ∈ [0, 1]`，表示在已有证据 E 的条件下，这段是否提供了完整答案链必需的事实。中间识别事实也算，纯话题相关或背景补充不算，而且明令禁止用外部知识推断。论文没有给 accept / reject 的截断阈值。

**共享上下文是核心，不是装饰。** 首轮 E 为空；扩展轮把已保留的证据段落与新候选一起放进上下文；最后一轮改用上一轮前十及其暂定分数，让模型对着引用过的事实复核早先判断。上下文里只有检索到的文本，没有标准答案和证据标注。

**逐词检索再交错合并。** 每个扩展词单独召回未见过的段落，按词优先级交错合并、去重，最多收 B 条；匹配扩展词是硬要求，匹配原问题词不是。最终只对前十条做一次本地贪心多样性重排，保留第一条和整个前十集合，这一步不发起模型请求。

论文里的 Erik Hort 例子能看清循环：问「Erik Hort 的出生地属于哪个县」，首轮命中人物段落，得知出生地是 Montebello，但没命中地点段落；从人物段落里挑出 montebello 继续检索，两段原文凑齐，该题召回从 50% 到 100%。在全部 1,000 道 MuSiQue 题上，有 389 道题的支撑段落原本不在首轮 BM25 前 100 里，循环总共捞回 433 段。

## JEV 是什么：一个不写字的判定模型

TypeSafe 在 2026 年 9 月 15 日发布 JEV，署名人是创始人 Diogo Almeida，博客自述曾任职 OpenAI 并参与指令跟随相关研究，这类模型被归为「System One Model」。它不生成字符串，输入非结构化状态，输出预先定义好类型的概率决策，训练方法叫 RLCD，采样是并行而非逐 token 自回归。

| 项 | 官方博客与论文给出的说法 |
| --- | --- |
| 单次响应 | 70 ms – 500 ms |
| 价格 | 输入 $0.042 / MTok，输出免费 |
| 输出 | 类型安全的结构化值 + 校准置信度 |
| 官方主张 | 不会输出类型错误，也不可能幻觉 |
| 状态 | early access；论文 limitations 注明评测版本的架构、参数量、权重未公开 |

在 SAG2 里，JEV 通过 OpenRouter 的 Noul 接口调用，论文记录的实际返回版本是 `typesafe/jev-1.13-20260917`；仓库 `.env.example` 配的是 `typesafe/jev-1.13`，README 另外记下论文那次跑分返回的历史版本，复现时值得把实际返回型号一起记进日志。

别把它当成 reranker 的别名。传统 reranker 给「查询—文档」相关度打分，JEV 拿的是问题、候选段落和当前已找到的证据，判断的是「这一段是不是答案链上必需的一环」。后面消融里会看到，把中间判定全砍掉、只在最后打分，效果会掉一大截。官方「不会幻觉」是厂商主张，不是第三方独立验证过的结论，按宣传口径读比较稳妥。

## 数字：三个测试集、两类消融、一个企业级语料

论文在 MuSiQue、2WikiMultiHopQA、HotpotQA 各取 1,000 道开发题，语料由这些题的支撑段落与干扰段落组成，指标是前 k 条去重重排结果里找回多少标注证据（R@k），以及前十条是否凑齐全部证据（AE@k）。答案生成不在评测范围内。

| 方法 | MuSiQue R@5 / R@10 | 2Wiki R@5 / R@10 | HotpotQA R@5 / R@10 |
| --- | --- | --- | --- |
| BM25 | 47.47 / 54.41 | 67.05 / 71.50 | 74.40 / 86.90 |
| NV-Embed-v2 | 68.84 / 77.27 | 77.00 / 80.75 | 95.25 / 97.70 |
| HippoRAG 2 | 65.13 / 73.76 | 90.35 / 93.40 | 94.35 / 97.15 |
| SAG 一代 | 80.36 / 83.37 | 93.34 / 93.57 | 96.50 / 97.70 |
| **SAG2** | **80.68 / 86.62** | **97.35 / 97.43** | **98.45 / 99.00** |

单位 %，数值取自 SAG2 论文 Table 1。表注写明：NV-Embed-v2、HippoRAG 2、SAG 一代三个稠密与结构化基线的数值转引自 SAG 一代论文，BM25 则是 SAG2 在相同题目子集上自己跑的固定词法基线。SAG 一代论文里的 BM25 是另一套实现，MuSiQue R@10 为 49.69，不能和这里的 54.41 混用。

SAG2 论文把这张表定性为「完整系统之间的比较」，各方法的模型与实现并不相同，不是统一组件的控制变量实验。SAG2 相对 SAG 一代的 R@10 提升是 3.25 / 3.86 / 1.30 个百分点，相对 BM25 是 32.21 / 25.93 / 12.10 点。MuSiQue 的 R@5 比 HippoRAG 2 高 15.55 点，官方稿开篇就用了这个数字；也别忽略 SAG 一代在 MuSiQue 的 R@1、R@2 仍高于 SAG2 —— 优势主要体现在「能给阅读模型多几条候选」的时候。

更能说明机制的是 MuSiQue 上的消融链：

| 配置 | R@10 | AE@10 | 判定次数 |
| --- | --- | --- | --- |
| 纯 BM25 | 54.41 | 17.40 | 0 |
| BM25 + 单轮 JEV 判定 | 67.93 | 36.00 | 99,925 |
| SAG2，扩展一轮（H=1） | 83.36 | 63.10 | 211,081 |
| SAG2，扩展两轮（H=2） | 86.62 | 69.50 | 331,325 |
| 同等判定预算、不扩展 | 69.82 | 39.60 | 329,194 |
| SAG2 去掉共享上下文 | 76.25 | 52.20 | 330,990 |
| 只在最后用 JEV 打分 | 61.34 | 29.60 | 98,836 |

判定次数指「一个候选在某问题、某上下文下被评一次」，重打分要再计一次，一个 HTTP 请求可以装很多次判定。三组对照值得记：给不扩展的对照组和 SAG2 几乎相同的判定预算（331,325 对 329,194），它仍差 16.80 点，说明收益来自迭代策略而非单纯堆算力；去掉共享上下文掉 10.37 点；把中间判定全放到最后掉 25.28 点。扩展一轮比两轮少用 36.29% 判定、R@10 只少 3.26 点，是一个更便宜的工作点。

企业侧用的是 EnterpriseRAG-Bench 全量 511,962 份源文档，官方稿给出的语料规模是约 24.65 亿字符，内容模拟邮件、消息、工单、会议记录与文档；500 道主问题里有 470 道带参考文档标注，其余 30 道不参与文档召回评测。SAG2 复现时把文档切成约 1,000 字符、上限 1,200 字符的块，这是它自己的设置，不是基准论文规定的切块方式（后者按 512 token 切）；检索参数与多跳实验相同，最后按源文档去重取前十。

| 问题类型 | 题数 | BM25 | 向量 | Bash Agent | SAG2 |
| --- | --- | --- | --- | --- | --- |
| Basic | 175 | 77.7 | 48.6 | 61.7 | 86.86 |
| Semantic | 125 | 43.2 | 24.8 | 29.6 | 58.40 |
| Intra-document reasoning | 40 | 90.0 | 57.5 | 75.0 | 100.00 |
| Project related | 40 | 65.5 | 49.2 | 43.2 | 83.58 |
| Constrained | 30 | 85.0 | 83.3 | 78.3 | 96.67 |
| Conflicting information | 20 | 82.5 | 55.0 | 72.5 | 92.50 |
| Completeness | 20 | 46.5 | 33.4 | 59.0 | 76.24 |
| Miscellaneous | 20 | 90.0 | 75.0 | 100.0 | 100.00 |
| Overall | 470 | 68.4 | 46.0 | 55.8 | **81.10** |

单位 %。BM25、向量、SAG2 是固定返回十条的文档 R@10；Bash Agent 每题返回条数不固定，是没有 top-10 截断的文档召回，不与前三列等价。BM25、向量、Bash Agent 三列数值引自基准论文 Tables 6–7，SAG2 一列出自 SAG2 论文 Table 2。SAG2 论文 Section 5.2 自己写明「对比描述的是检索表现，不建立等价算力预算，也不代表端到端答案质量」。同一份语料上，官方稿给出的清点、建库与完整性检查合计 8 分 32 秒，折算约 200 ms / 百万字符，完整跑分一个多小时。

对照 2026 年 7 月那篇规模研究：在其资源约束下，LightRAG 只建到 2,254 份文档，MS-GraphRAG 到 8,750 份，HippoRAG 2 与 LinearRAG 到 131,876 份，都没跑到全量。研究的结论是「大规模图谱结果谈的是建库可行性，不是外推准确率」。它把 BM25 定位为「无 LLM 建库环节」的低成本 Pareto 前沿点，还特意注明这里的零指的是模型 token 建库成本为零，不是 CPU、存储和索引工作为零。

## 真正在涨的不是建库速度，是查询侧

把上面两张表放一起看，那 32 个点的提升全来自查询时的模型判定与迭代，和 2.36 秒的建库没关系。SAG2 论文 Table 3 给的成本数字也很直白：MuSiQue 上 100 道题模型费 $0.433769，1,000 道题 $4.326379，费用按成功响应计算（含中断续跑复用的响应），不含机器租赁与答案生成。

这是一次成本搬家，不是成本消失。对个人本地知识库，一周建一次库、一天问几十次，搬过去非常划算；对几千员工或几个常驻 Agent 同时查的企业库，查询侧的模型费用和延迟会很快盖过建库那一次的成本。论文没有报告在线延迟，理由是服务等待时间没能从并发执行里拆出来；官方稿给的「单次检索通常 1–3 秒，取决于检索参数」是产品侧口径，别拿它当论文结论。

还有一处口径要小心：判定次数不等于 HTTP 请求数，也不等于读完答案的总时间。论文并发封顶 20，一个请求里可以塞多次判定；一个 HTTP 请求能装多少，直接决定了这套方案在真实流量下的账单。

## 落到手边：SAG Wiki 与复现仓库

SAG Wiki 是把这套方法做成桌面应用的产物：Svelte + Tauri 界面、Rust 核心、本地文件索引，MIT 开源；README 强调不用另装数据库服务。选一个本地文件夹就是知识库，文件不移动、改动自动增量更新，PDF、Office、EPUB 开箱可转，图片识别与音视频转写是按需下载的可选组件，最终仍然走文本索引。答案里的引用可以点开回到原文段落。

配置分三层，别混：文件索引和 Quick Search 完全本地，不需要任何 Key；深度语义检索要配 JEV 服务；带引用的问答还要再配一个答案模型和它的 Key。README 也写清楚了数据边界：原文件留在本机，但深度检索与问答会把必要的问题、段落或上下文发到你配置的服务。

| 项 | 说明 |
| --- | --- |
| 平台 | macOS / Windows 桌面端；npm 二进制为 macOS Apple Silicon 与 Windows x64 |
| 体积 | 官方稿 9.5 / 12.5 MB，当前 README 约 14 MB，第三方实测 13 / 18 MB，随版本变化 |
| CLI | `npm i -g @zleap-ai/sag`，需 Node.js 18+，可脱离桌面端运行 |
| Agent 接入 | 提供 Skill，支持 Claude Code、Codex、OpenCode |
| 常用命令 | `sag add`、`sag check`、`sag "问题" . -m 5` |

想验论文数字就走 SAG-Benchmark。默认 SAG2 不需要 Docker、MySQL、Elasticsearch 或 GPU，只要 Python 3.11+、uv 和一个 C 编译器（首次会编译 SQLite 打分扩展）。所有命令在 `sag2/` 目录下执行：

```bash
uv sync --frozen
cp .env.example .env
uv run python \
  scripts/run_sag2_benchmark.py \
  --download --index-only
uv run python \
  scripts/run_sag2_benchmark.py \
  --dataset musique --limit 10
```

`.env` 里是 `OPENROUTER_API_KEY`、`JEV_BASE_URL`（指向 OpenRouter 的 decisions 端点）、`JEV_MODEL`（默认 `typesafe/jev-1.13`）。Key 只从环境变量或 `--env-file` 读，不要写进命令行参数。

几个复现时容易踩的坑：`--download --index-only` 完全不调模型，真正开始花 Key 的是后面那个 10 题 smoke run；`--limit` 只改题数，不缩小语料；索引签名包含 schema 和切块策略，改 `--chunk-chars` 会改变候选边界和分数；plain SAG2 不持久化每次 JEV 请求，中断的题可能重复发请求，正式跑之前先确认 endpoint、并发和输出目录。

## 接进 Agent 和记忆之后

仓库里还有一个可选扩展叫 Agentic SAG2：让 LLM 把 SAG2 当工具调用，保留原问题、检索历史、已确认和未解决的关系，自己决定下一次查什么或何时停，最后从工具返回的候选里排序。最佳设置是 `gpt-6.1-sol`、high 思考档、每次 SAG2 扩展一轮、每题最多 3 次工具调用、每次返回 20 段、最终选 10 段。

| 方法 | MuSiQue R@10 | 2Wiki R@10 | HotpotQA R@10 |
| --- | --- | --- | --- |
| SAG2 | 86.617 | 97.425 | 99.000 |
| Agentic SAG2 | 95.392 | 99.875 | 99.650 |

前十条凑齐全部证据的题数，MuSiQue 从 695 涨到 891。这个结果挺有意思：SAG2 负责精准找证据，Agent 负责理解问题、判断线索缺哪一段、决定要不要补搜，两者互补而不是替代。官方稿里那句「Agent 调用 SAG2 可以比单独用 SAG2 更准」，出处就是这里。

同一篇发布稿还提到两件事：用 SAG2 替代 grep 作为 Agent 可调用的工具，在相关任务里 Token 消耗减少约三分之二；在 LOCOMO 和 LongMemEval 两个记忆数据集上「未做适配即取得 SOTA」。前者是作者自述、未给具体任务与数字，后者明确标为论文待发的预告，目前没有公开论文可核，别当成已验证结论写进方案。

SQLite 本身就是一个文件，原文和索引都在文件系统里，Agent 调一次搜索就能拿到多跳后的原文证据，不用额外部署数据库服务 —— 这确实是它和 Harness、Agent 记忆场景契合的地方。但同一个事实也意味着：权限、审计、多租户这些企业级要求，得在索引之外自己补。

## 该打折的地方：七条边界

论文自己列了不少限制，社区质疑也补了几条。按严重程度梳理：

| 边界 | 具体表现 |
| --- | --- |
| 依赖托管 JEV | 论文称「主要部署限制就是决策模型」：架构、参数量、权重未公开，只能通过托管 API，问题与候选文本必须外发，无法完全私有化 |
| 合规与可用性 | Jev 是美国 TypeSafe 的模型，基准经 OpenRouter 调用；数据出境、境内可用性、私有部署三条会挡住不少国内企业 |
| 词法召回天花板 | 论文写明改述、别名、没有可用词面联系的证据仍会漏；Enterprise 的 Semantic 类只有 58.40%，是所有类别最低 |
| 跳数越多越吃力 | MuSiQue 四跳题 R@10 为 69.58%，凑齐全部证据只有 28.31%；两跳题 AE@10 是 87.07% |
| 评测外推范围 | 固定开发子集，MuSiQue 还用于方法开发；没有独立留出集、私有企业语料、下游答案生成评测；Enterprise 语料是合成的 |
| 统计与延迟 | 置信区间只衡量题目间波动，不衡量重复模型运行波动；在线延迟未报告；成本研究只覆盖一个语料 |
| 中文与多模态 | 评测全是英文数据集；社区指出中文领域词表、跨语言改写没有评测数字，图片走 OCR、音视频走转写后仍是文本检索 |

补两条口径上的提醒。一是有社区文章质疑「三个测试集、8 项指标全部第一」这类宣传图的对照组偏窄；论文正文其实比过 NV-Embed-v2、HippoRAG 2 等强基线并且赢了，只放自家旧版反而显得可疑。二是「RAG 死了」这个说法站不住：SAG2 只是换了检索这一段，答案仍由模型基于检索证据生成，它本身就是 RAG 家族里的一员。真正被顶到的是「只做向量、连 BM25 都没有」的那类方案。

本地替代方案也在推进：仓库提供 `--mode local`，用 Qwen3-Reranker-0.6B（Apache-2.0）或 Jina 系列（CC BY-NC 4.0，商用需另行授权）替换每轮 JEV 打分，权重与语料备齐后查询过程可完全离线。官方的说法是目前本地模型还达不到 JEV 的速度和效果；腾讯云那篇质疑文引述官方消融数字指出，单轮打分时 Jina reranker 67.43 与 JEV 67.93 几乎打平 —— 这两个数不在仓库的 local-rerank 文档里，引用时别记错出处，差距也主要集中在多轮、带上下文的判定上。

## 怎么选：按问题路由，别按流派站队

过去两年，向量 RAG、GraphRAG、SAG、SAG2 换了好几代，每代都有人宣布上一代死了。更实际的问法是：下次方法再升级，我要不要迁移数据、换掉底座。

| 看什么 | 更适合混合检索 | 更适合检索循环 |
| --- | --- | --- |
| 问题形态 | 单跳、口语化、同一件事多种问法 | 多跳、要把几份文档的证据串起来 |
| 语料特点 | 自然语言、多语言、图片视频 | 表名、条款号、代码标识符多 |
| 延迟预算 | 毫秒级搜索框、客服 | 秒级可接受的深度研究、Agent、审计 |
| 判定模型 | 没有也能跑 | 需要可用且合规的判定模型 |
| 更新频率 | 语料稳定，可承受重建 | 文件频繁改动，增量索引更重要 |

大多数场景两类问题都有，简单问题一步返回，复杂问题进入循环，比赌一个方法通吃靠谱。真要上生产，还有三件在论文里看不到的事：每一轮检索的权限过滤要落在引擎层而不是查完再筛；每轮召回、判定、扩展都要留 trace，否则「为什么漏了这条」没法查；以及按查询量重新算一遍模型账单 —— 这一步常被 2.36 秒的标题盖过去。

## 结语

SAG2 值得认真对待的地方，不是把建库做到了几秒，而是证明了「词法召回 + 判定模型 + 迭代扩展」这条看起来很土的链路，在多跳检索上能压过纯向量乃至图谱方案，而且只需要一个 SQLite 文件。它对「向量是 RAG 唯一答案」是一次直接反驳。

剩下的悬念也很清楚：判定模型能不能本地化到不带合规风险，词法召回在中文和语义类问题上能走多远，以及查询侧那几百次判定在高并发下会不会把省下的建库成本重新吃掉。这几件事没有答案之前，把它当成一个很强的检索选项，比当成一次技术换代更准确。
