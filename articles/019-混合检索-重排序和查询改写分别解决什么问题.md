# 混合检索、重排序和查询改写分别解决什么问题？

## 面试官为什么爱问这题

这三个词在 RAG 岗位 JD 里几乎必出现，但很多人是把它们当一个「优化套餐」记的——全上了，效果变好了点，但说不清哪个组件出了力、各自治什么病。面试官问的就是这层：**你有没有检索优化的职责分工意识**。答得好的人开口先分层，而不是先报工具名。

第 15 篇讲完整流水线时，改写和重排作为两环顺过一遍；本篇把它们从流水线里拆出来，加上混合检索，专门回答一个问题：**badcase 出现时，怎么判断该补哪个组件**。这也是面试官真正的追问路径——他会给你一个「检索效果差」的现象，看你会不会归因。

## 一句话先给结论

**三者管三层：查询改写管「问题没被说成检索系统听得懂的话」，混合检索管「单路召回漏掉另一路才能命中的证据」，重排管「候选对了、顺序不对」。顺序是先改写、再多路召回、最后精排——按表达层、召回层、排序层分层补，别当成一件事。**

## 核心原理：三个组件，三种失灵

### 查询改写：问题出在进系统之前

用户的问题和检索系统擅长处理的语言，天然有落差。三种典型情况：

- **指代不完整**：多轮对话里「那它的税率呢」——「它」只有靠历史轮次才能补全，这句话直接去检索，捞回来的是一堆「税率」高频文档。
- **口语与术语的错位**：用户说「报销单贴错了怎么办」，语料里写的可能是「发票粘贴错误更正流程」。两边都在说同一件事，用词完全对不上。
- **问题太短或太散**：一两个词的输入信息量不足，无论稠密还是稀疏都只能瞎猜意图。

改写做的事就是把「人话」翻译成「检索语句」。它可以是规则（拼接上一轮的主题词），也可以是一次模型调用。关键判断标准是：**改写带来的召回增益，要大于它新增的延迟和失败面**。

### 混合检索：单路召回的天生盲区

稠密检索的机制是把 query 和文档各自压成一个向量再比距离。压缩是它的效率来源，也是它的信息损失点：**错误码、产品型号、订单字段名、法条编号这类精确 token，被压进向量后细节容易糊掉**——「E0451」和「E0452」在向量空间里几乎是同一个点，但对用户是两个完全不同的答案。

稀疏检索正相反：它按词项精确匹配，「E0451」这个字符串在语料里出现就命中，不出现就不命中。代价是它不懂同义改述——「报销贴错」查不中「粘贴错误」。

制度、产品参数、订单字段、错误码这类企业知识，关键词常常非常重要，所以只靠稠密检索往往不够。混合检索的做法是两路都跑、再把两份榜单融合：语义的路负责「换个说法也能找到」，词项的路负责「一字不差才能命中」。

### 重排序：「相关」和「能答」是两回事

召回必须在几十毫秒内扫完百万级块，只能用省算力的粗排方式。粗排的代价是分不清「话题相关」和「真正含答案」——候选里全是相似话题的块，真证据可能排在第十位。重排对 query 和每个候选**逐对**精细打分，把真证据顶到最前面，下游只喂最有用的几条。分工沿用第 15 篇的口径：召回给宽（经验值 top_k 20～50），重排收窄（经验值进上下文 3～8 条）。

### 边界：三个都救不了什么

分层的另一面是知道每层的无能。**改写救不了脏语料**——文档本身解析错了，改得再好也没用。**混合检索救不了索引侧**——块切坏了、向量算错了，两路都漏。**重排救不了没召回的证据**——候选里根本没有的东西，排不出来。每个组件都有上游依赖，这也是为什么排查永远从「证据在不在候选里」这个分叉开始（第 15 篇的分层定位法）。

## 工程实践：融合、路由和一段能落地的伪代码

先讲融合。两路检索拿回两份榜单，不能直接把分数相加——**两路的分数量纲不同，向量余弦和词项得分没有可比性**。通用做法是只认排名不认分数，用 RRF（倒数排名融合）：每一路里排第 r 名的文档得 1/(k+r)，k 是平滑常数（经验上取 60 上下），两路得分相加后重排。

```text
伪代码：两路召回的 RRF 融合
def rrf_fuse(list_a, list_b, k=60, top_n=30):
    # list_a / list_b: 各路检索返回的 doc_id 列表，按相关性降序
    scores = {}
    for doc_id, rank in ranked(list_a):   # rank 从 1 开始
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    for doc_id, rank in ranked(list_b):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)[:top_n]
```

再讲改写的护栏。改写最容易翻车的三种方式：把错误码「E0451」改写成「E451」；把语料里的标准术语替换成模型的自由发挥；把长问题压缩到丢掉限定条件。所以工程上改写是**扩**不是**替**——原 query 永远保留一路，改写结果作为额外的一路参与融合；含字母数字串的部分用正则保护，不许模型碰。

```text
伪代码：改写作为额外查询路
def rewrite_and_search(query, history, corpus):
    routes = [search_all(query)]                      # 原 query 永远在跑
    if needs_rewrite(query, history):                 # 多轮指代 / 口语落差判据
        rewritten = llm_rewrite(query, history, protect(query))
        routes.append(search_all(rewritten))
        routes.append(sparse_search(rewritten))       # 改写后的关键词路
    fused = rrf_fuse(*routes)
    return rerank(query, fused, keep=8)               # 对融合后的总榜精排
```

最后是省成本的路由。混合检索不必对所有 query 开放：先用规则判断 query 里有没有精确 token（字母数字串、型号格式、引号内的原词），有就走两路，没有就只走稠密——经验上能让混合的额外成本只花在真正需要它的那一部分流量上。

## 追问逐条作答

### 追问一：稠密检索和稀疏检索的区别是什么？

原理上一个靠语义、一个靠词项。稠密把文本压成向量比距离，擅长「换个说法也能找到」；稀疏按词项精确匹配，擅长「一字不差才能命中」。各自的弱项正好是对方的强项：稠密的向量压缩会糊掉精确 token 的细节，稀疏对同义改述无能为力。所以企业场景里语料含大量错误码、型号、字段名时，两路混合比单路稳——语义和关键词互为兜底。

### 追问二：Rerank 放在哪一层最合适？

召回之后、上下文组装之前，而且是对**融合后的总榜**做。往前放不行——重排逐对打分，百万级候选算不动，它的前提是召回已经把范围缩到几十条；往后放也不行——进了上下文之后顺序已定，精排失去意义。多路召回时尤其注意：不是每路各自精排再拼，而是 RRF 融合出唯一榜单后统一精排，否则两路的分数还是不可比。

### 追问三：混合检索会不会更贵？

会，但增量可控，而且不是每一分钱都花在检索上。成本拆开看：稀疏检索本身便宜；融合是一次排序，开销可忽略；**真正的增量在重排——候选从一路的 top 50 变成两路融合后的量**。控法有三个：控制进重排的条数（经验值 30～50 条以内）、对无精确 token 的 query 路由回单路、重排只在需要高质量排序的业务线上开。账要这么算：多花的延迟买回来的是「文档明明有却答不上」这类最难堪的 badcase。

### 追问四：三个组件能不能只上一个？先上哪个？

能，而且应该按归因决定，不是按套餐。先拿标注好的「问题—应命中文档」对做分层定位：应命中的块不在候选里，看 query——问题不自足就先上改写，语料关键词重就上混合；在候选里但没进上下文，上重排。单轮、query 规整、语料是自然语言的系统，可能一个都不用；多轮对话系统里改写几乎是必选项，因为不做指代补全，后面两层全在替它背锅。全上的时候还有个容易漏的收口：三件套解决的是「找得全、排得对」，**最后一道还得靠 metadata 过滤**——权限、生效版本、业务分区都要放进检索请求里做 pre-filter（第 13 篇讲过：后过滤会出现「取 10 条剩 1 条」），这是把检索结果约束在合法范围内的那一步。

### 追问五：改写会不会把问题改坏？

会，这是改写最大的失败面。三种典型翻车：专名被改（错误码少一位）、标准术语被替换、限定条件被压缩掉。护栏三件套：原 query 永远保留一路参与融合，改写只是扩路；字母数字串和引号内原词用正则保护，改写器无权改动；上线前用固定评测集守召回率，改写器换版本必须回归，和第 7 篇讲提示词版本管理的逻辑一致——改写器本身就是个提示词资产。

### 追问六：怎么向老板证明这三个组件各自值回票价？

分别建基线。每个组件单独开关，用同一套评测集测四个数：全关、只开改写、只开混合、只开重排，再看全开的组合。汇报时讲的是增量——「改写把多轮场景的命中率抬了多少、混合把错误码类问题的命中率抬了多少」。这套分层实验也是第 15 篇讲的参数实验方法的推广：一次只动一个变量，否则永远说不清是哪个组件在起作用。

## 60 秒面试回答模板

> 这三个组件管的是三层问题。查询改写管表达层——多轮对话的指代、口语和术语的错位，问题得先变成检索系统听得懂的话；混合检索管召回层——稠密向量会糊掉错误码、型号这类精确 token，稀疏检索又不懂同义改述，两路融合互相兜底；重排管排序层——召回分不清「话题相关」和「真正含答案」，用逐对精打分把真证据顶到前面。顺序是先改写、再多路召回、最后精排。但我不建议当套餐无脑全上：先用「应命中的块在不在候选里」做分层归因，缺哪层补哪层——改写救不了脏语料，混合救不了坏切块，重排救不了没召回的证据。

## 加分项

- **说得出 RRF 为什么存在**：两路分数量纲不可比，只能认排名不认分数——这一句能区分「用过」和「懂为什么」。
- **改写是扩不是替**：原 query 永远保留一路，改写结果作为额外路参与融合。很多人栽在改写翻车上，就是把它做成了替换。
- **成本路由**：按 query 是否含精确 token 分流单路/双路，把混合的成本花在刀刃上——证明你考虑过预算，而不只是效果。
- **主动讲边界**：三个组件各有救不了的事，检索效果差要先归因再动手。敢说「这个组件解决不了你的问题」，比堆名词更像做过的人。

## 常见误区

- **当套餐全上**：不做归因就三件套齐发，多花钱事小，把「问题根本在索引侧」的真病根盖住事大。
- **拿混合检索替代重排**：一个在召回层解决「找没找到」，一个在排序层解决「谁先谁后」，融合榜单的顺序仍可能是粗排的。
- **改写只做多轮**：单轮场景的口语和术语错位同样需要改写，「那它呢」只是最显眼的一种。
- **重排万能论**：第 15 篇讲过——解析错了救不回来，重排的能力上限是候选集的上限。
