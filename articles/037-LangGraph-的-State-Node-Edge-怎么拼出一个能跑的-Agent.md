# LangGraph 的 State / Node / Edge：怎么拼出一个能跑的 Agent？

## 面试官为什么爱问这题

这是第 6 章的开篇题，考的是基础心智模型，不考你背没背 API。之前聊过 ReAct 那种"思考—行动—观察"的循环机制，也聊过一个能跑的 Agent 到底要哪几样组件；这一篇换到框架层，看的是当你用一个图去搭 Agent 时，手里到底有哪几个积木、各自该负责什么。面试官问 State / Node / Edge，真正想听的是两件事：你能不能把一个循环抽象成"共享状态 + 处理步骤 + 流转规则"这三件套；以及你有没有踩过那种"图写着写着就没法维护"的坑，知道根源通常不在图复杂，而在于把过多隐式逻辑塞进了某一个节点。基础题反而最能分出高下，因为概念清楚的人三句话讲透，含糊的人背一堆 API 名也讲不到点上。

## 一句话先给结论

**State 是共享状态，决定图里大家共同操作的上下文是什么；Node 是处理逻辑，决定每一步具体做什么，比如调用模型、查库、执行工具；Edge 是流转规则，决定当前节点执行完后下一步去哪，可以是固定跳转，也可以是条件路由。三者拼起来就是一个能跑的 Agent。设计好不好看三点：State 是否清晰、Node 粒度是否合理、Edge 条件是否可解释；图难维护多半不是图本身复杂，而是把太多隐式逻辑塞进了一个节点。**

## 核心原理：三件套拆开讲

### 为什么用"图"来搭 Agent

回到最朴素的写法：一个 Agent 循环就是 `while`，里面调模型、看有没有工具调用、执行、再回到开头。它能跑，但一切控制流都藏在代码的执行顺序和变量里，想看清"哪一步决定继续还是停"得通读整段函数，想插入一个审批节点或一条分支就得改循环体。

图做的事情是把这些隐式的东西显式化：每一步是一个节点，节点之间怎么走是边，走的时候共享什么数据是状态。于是"下一步去哪"不再藏在 `if` 的嵌套里，而是一条看得见、能单独改的边；想加一个人工审批，就插一个节点、改两条边。这个显式化还带来一个附带好处：图结构能被观察和恢复——在节点之间存一次状态，就能做到中断后从断点继续、出错后重放某一步，这些在裸 `while` 里都要自己造轮子。之前讲整机组件取舍时提过"运行循环"是骨架之一，图就是把这层骨架做成了一等公民。

### State：决定"大家共同操作的上下文"

State 是整个图共享的那份数据，每个节点读它、也可能更新它。它决定了节点之间能看见什么——一个字段不放进 State，后面的节点就读不到；一个字段放进去了，就等于向所有能到达的节点公开。所以设计 State 的第一原则是**最小化**：只放真正需要跨节点传递的东西，能在一个节点内部算完的中间变量就留在函数里，别往 State 里塞。

State 通常用一个类型来声明字段，再给需要"累加"或"合并"的字段配一个 reducer。为什么需要 reducer：图并行执行多个节点时，两处可能同时更新同一个字段，默认行为是后者覆盖前者，消息列表这类数据就会被丢掉；配了 reducer 之后，更新会按约定合并（比如追加而不是覆盖）。消息的合并一般用框架提供的专用 reducer，而不只是简单的列表相加——它在按消息 id 覆盖更新、去重这些细节上更周全。一个常见的经验口径是（经验值）：State 里除消息历史外，再放一两个显式的控制字段，比如"当前意图""是否待审批""重试次数"，让条件边有明确的判断依据，而不是去消息文本里猜。

State 设计糟的症状很典型：一个字段谁都在写，出问题却没人说得清是哪一步写坏的；或者 State 里塞了十几个字段，大半只有一两个节点用。前者要给字段定清归属，后者该把局部数据收回到节点内部。

### Node：决定"每一步具体做什么"

Node 是一个处理单元，调用模型、查库、执行工具都发生在节点里。它最好被写成一个职责单一的函数：接收当前 State，做完一件事，返回对 State 的部分更新。这里有个和裸循环很不一样的心智：**节点不直接修改全局状态，而是返回"要更新哪些字段"**，由框架合并回 State。这样一来节点的输入输出是明确的，单独测一个节点、单独重放一个节点都变得可行。

Node 粒度的判断标准是"一个节点一个明确的动作"。切得太粗，把调模型、解析结果、执行工具、判断下一步全塞进一个节点，图就退化成了裸循环——外面看只有一个节点，边和条件全藏在函数内部，这正是"隐式逻辑塞进一个节点"的典型。切得太细也不好，每个节点只做一两行的事，节点数和边数爆炸，读图反而更累。经验上（经验值）按"能被单独描述和单独测试的一步"来切：调模型是一个节点，执行工具是一个节点，做一次业务判断可以是一个节点，但"调模型顺便把结果解析了再顺便执行了"就该拆。

### Edge：决定"下一步去哪"

Edge 分两种。固定边是无条件的：这个节点跑完，固定去下一个，比如工具节点跑完总是回到模型节点。条件边带一个判断函数：读 State，返回下一个节点名，比如模型产出里有工具调用就去工具节点，没有就结束。条件边是让图"活"起来的东西——循环、分支、提前终止、按意图分流，全靠它。

可解释性是条件边设计的核心：判断应该基于 State 里显式的字段，返回清晰的节点名，而不是在一个长长的函数里做一串副作用后再决定去哪。一个好的条件路由，看函数本身就能说出"什么条件去 A、什么条件去 B"；一个坏的条件路由，判断逻辑和业务逻辑搅在一起，改一处分支不敢保证不影响另一处。和 State 的原则呼应起来看：State 里为什么要留一个显式的意图或重试计数字段，就是因为条件边需要一个能读、能测、能解释的判断依据。

### 三件套的关系

把它们放一起看，一个图就是数据、计算、控制流三件事：State 是数据，Node 是计算，Edge 是控制流。设计得好的图，这三样各归各位——数据不夹带逻辑，计算不偷偷决定流转，控制流不藏进计算。设计糟的图，往往是某个 Node 既改数据、又做判断、又决定下一步，等于把三件套揉成一团，外面这个图就只剩形式意义了。

## 横向对比：把三件套和设计取舍摆清楚

### 三件套各管什么

| 件 | 本质 | 决定什么 | 设计好的标准 | 设计糟的症状 |
| --- | --- | --- | --- | --- |
| State | 共享数据 | 节点间能看见什么上下文 | 字段清晰、最小化、归属明确 | 谁都在写、塞满没人用的字段 |
| Node | 处理逻辑 | 每一步具体做什么 | 职责单一、可单独测试 | 一个节点里塞满隐式逻辑 |
| Edge | 控制流 | 执行完下一步去哪 | 条件可解释、基于显式字段 | 判断藏在副作用里、分支搅成一团 |

这张表里最有诊断价值的是最后一列：拿到一个难维护的图，先看哪个症状对得上，就知道该动 State、Node 还是 Edge，别一上来重写整张图。

### State 里放什么、不放什么

| 该放 State | 不该放 State | 原因 |
| --- | --- | --- |
| 跨节点要用的消息历史 | 只在单个节点内算的中间变量 | 后者放进去只会污染共享上下文 |
| 条件边要读的显式字段（意图、重试数） | 能从其他字段随时算出来的派生值 | 派生值放进去会产生两处真相、容易不同步 |
| 需要断点恢复的进度信息 | 大块原始资料（可按需再取） | State 每步都可能被持久化，塞太大拖慢存取 |
| 需要在节点间累加的结果 | 一次性的临时开关 | 临时开关属于控制流，该落到边或节点逻辑 |

一个判断口诀：问自己"后面的节点会不会用到、断了要不要恢复"，两个都是否，就别进 State。

### 固定边 vs 条件边

| 维度 | 固定边 | 条件边 |
| --- | --- | --- |
| 有无判断 | 无，固定去下一个 | 有，读 State 决定去哪 |
| 适合场景 | 线性步骤、工具后固定回模型 | 循环、分支、按意图分流、提前结束 |
| 判断依据 | 不需要 | State 里的显式字段 |
| 可读性 | 看图即懂 | 取决于判断函数是否可解释 |
| 出错形态 | 走错节点多为接错线 | 判错条件导致走错分支、死循环 |

## 工程实践：一个最小可跑的图

### 三件套落成代码

下面是一段最小 Agent 图的骨架。用伪代码写，模型调用和工具执行是业务侧实现，这里只展示 State、Node、Edge 怎么拼。依赖里的导入路径在不同版本略有差异，以所用版本文档为准。

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages   # 消息专用 reducer

class State(TypedDict):
    messages: Annotated[list, add_messages]   # 消息按 id 合并，不是简单相加
    needs_tool: bool                          # 条件边要读的显式字段

def call_model(state: State) -> dict:
    # call_llm 由调用方注入：接收 messages，返回带 tool_calls 的消息
    reply = call_llm(state["messages"])
    return {"messages": [reply], "needs_tool": bool(reply.tool_calls)}

def call_tool(state: State) -> dict:
    # run_tools 由调用方注入：执行工具，返回结果消息
    result_msg = run_tools(state["messages"][-1].tool_calls)
    return {"messages": [result_msg], "needs_tool": False}

def route(state: State) -> str:
    # 条件边：判断依据来自 State 的显式字段，可读可测
    return "tool" if state["needs_tool"] else END

builder = StateGraph(State)
builder.add_node("model", call_model)
builder.add_node("tool", call_tool)
builder.add_edge(START, "model")
builder.add_conditional_edges("model", route, {"tool": "tool", END: END})
builder.add_edge("tool", "model")     # 工具跑完固定回到模型，形成循环
graph = builder.compile()
```

这段代码把三件套摆得很清楚：`State` 声明共享数据和合并方式，两个 `add_node` 是处理逻辑，`add_edge` 和 `add_conditional_edges` 是流转。注意节点返回的是字段更新字典而不是整个 State，合并交给框架；`needs_tool` 这个显式字段是专门为条件边准备的——如果省掉它、让 `route` 去消息列表里翻 `tool_calls`，判断就变得难读也难测。这就是前面说的"State 为可解释的 Edge 服务"。

### 让图可观察、可恢复

图结构显式的最大回报在这一步：`compile` 时可以挂一个 checkpointer，框架会在节点之间自动存状态。这样长任务中断后能从最近的节点继续，某一步出错也能拿到当时的 State 去复现，不用自己把每一步的快照写进数据库。要插入人工审批时，做法是在关键节点后用条件边走到一个审批节点，配合中断机制暂停、等人确认后再恢复——这类进阶 API 各版本差异较大，用到时按所用版本的文档接。对面试官说清"为什么图比裸循环好扩展"时，checkpoint 和分支插入是两个最具体的例子，比空谈"框架更规范"有说服力。

## 追问逐条作答

### 追问一：State 里到底该放什么，是不是越多越好？

不是，最小化是原则。只放两类：跨节点必须共享的数据（最典型是消息历史），以及条件边要读的显式控制字段（意图、是否待审批、重试次数）。能在一个节点内部算完的中间变量留在函数里，能从其他字段随时算出来的派生值别单列一个字段，否则会出现两处真相、改一处忘一处。还有个容易忽略的点：State 每步都可能被 checkpointer 持久化，塞进大块原始资料会拖慢存取，那种数据按需再取更合适。判断口诀是"后面的节点会不会用到、断了要不要恢复"，两个都是否就别进 State。

### 追问二：Node 粒度怎么切，一个节点塞太多逻辑会怎样？

按"能被单独描述、单独测试的一步"来切。调模型是一个节点，执行工具是一个节点，一次独立的业务判断可以是一个节点。塞太多的后果不是跑不动，而是图退化成裸循环：外面看只剩一个节点，条件、分支、错误处理全藏在函数内部，边和图结构失去意义，也没法单独重放某一步。切得太细同样有代价，节点和边数量爆炸，读图成本反而上升。一个务实的信号是：如果你没办法用一句话说清某个节点做什么，或者写它的单测要 mock 掉一大半外部依赖，就该拆了。

### 追问三：固定边和条件边分别什么时候用？

线性、确定的衔接用固定边，比如工具节点跑完总是回到模型节点。需要分支、循环、按意图分流、提前结束的场合用条件边，比如模型有工具调用就去工具节点，没有就结束。条件边的关键是可解释：判断函数读 State 里的显式字段、返回清晰的节点名，看函数本身就能说出什么条件去哪。不要在条件函数里做一堆副作用再决定走向，也不要去消息文本里正则匹配意图——那会让分支逻辑变得不可测，改一处不敢保证不影响别处。

### 追问四：循环和停止条件在图里怎么表达？

用条件边表达。让模型节点的条件路由判断"还有没有工具调用"：有就去工具节点，工具节点再用固定边回到模型，形成循环；没有就返回 END，循环终止。停止条件的判断依据同样建议落到 State 的显式字段上，需要防不收敛时再加一个重试计数，超过上限就走一个降级节点或 END。之前聊 ReAct 循环时讲过观察驱动下一步、以及要给循环加轮数上限防止空转，落到图上就是这条条件边加一个计数字段，机制一样，只是从代码里的 `if` 变成了图里看得见的一条边。

### 追问五：LangGraph 和自己写个 while 循环比，值不值？

看任务复杂度。简单的一两轮调用，裸循环更直接，引框架反而是负担。一旦出现三种情况，图的收益就明显了。一是分支或并行，多个工具能并发、不同意图走不同路径；二是中断恢复，长任务要能断点续跑、出错要能复现某一步；三是多人协作维护，图结构让"下一步去哪"一眼可见，不用通读整段循环。这几种需求在裸循环里都得自己造轮子，而图把它们做成了一等公民。反过来说，如果只是线性地调两下模型，别为了"上框架"而上框架。

### 追问六：图写着写着难维护，通常问题出在哪？

基本逃不出题库说的那条：把太多隐式逻辑塞进了某个节点。表现是节点名字叫 `agent` 或 `handle`，函数几百行，调模型、解析、执行、判断全在里面，图上就一个大节点加几条边，等于图白画了。改法是把节点按职责拆开，把藏在执行里的判断提到条件边，把节点间偷传的数据收进 State 的显式字段。其次常见的是 State 设计不清——字段没归属、谁都写，出错定位不到人。诊断顺序建议先对照那张症状表：State 脏先治 State，节点臃肿先拆节点，分支混乱先理条件边，别一上来重构整张图。

### 追问七：并行节点、断点续跑这些进阶能力，和这三件套是什么关系？

它们是三件套的自然延伸，不是额外发明。并行是同一批数据分给多个节点、结果按 reducer 合并回 State，靠的是 State 的合并规则和图的分支能力；断点续跑是 checkpointer 在节点之间存 State，靠的是"节点是明确边界、State 是可序列化数据"这个前提。State 设计得干净、Node 边界清楚，这些能力就是顺手能加的；反过来，如果 State 里塞满不可序列化的临时对象、Node 里全是隐式逻辑，想加并行和断点就会处处碰壁。这也解释了为什么基础心智模型重要：进阶能力能不能上，先看这三件套打没打好。

## 60 秒面试回答模板

> LangGraph 的核心就是三件套。State 是共享状态，决定节点之间共同操作什么上下文，通常最小化设计，只放跨节点要用的数据和条件边要读的显式字段；Node 是处理逻辑，调模型、查库、执行工具都发生在节点里，一个节点一个明确动作，返回对 State 的部分更新；Edge 是流转规则，固定边做确定衔接，条件边读 State 决定下一步，支持循环和分支。三者就是数据、计算、控制流。设计好不好看 State 清不清晰、Node 粒度合不合理、Edge 条件可不可解释。图难维护通常不是图复杂，而是把太多隐式逻辑塞进了一个节点，把它拆开、把判断提到条件边就好了。比起裸 while 循环，图的优势在分支、断点续跑和可维护性。

## 加分项

- **把三件套归约成数据、计算、控制流**：State 是数据、Node 是计算、Edge 是控制流，这句归纳比逐个背 API 更能显示心智模型清楚。
- **点出节点返回部分更新**：说清节点不直接改全局状态、而是返回字段更新交给框架合并，这是 LangGraph 心智模型里容易被忽略的一层。
- **用症状反推该动哪一件**：State 脏治 State、节点臃肿拆节点、分支乱理条件边，把"难维护"变成可定位的诊断，而不是笼统重构。
- **把进阶能力归到三件套上**：并行靠 State 的 reducer、断点靠节点边界和可序列化 State，说明你理解基础打好了进阶才顺手。

## 常见误区

- **把图当银弹，简单任务也硬上**：一两轮线性调用用裸循环更直接，为"上框架"而上框架只会增加负担。
- **把 State 当垃圾桶**：什么中间变量都往里塞，字段没归属、谁都在写，出错定位不到，还拖慢持久化。
- **一个节点包打天下**：调模型、解析、执行、判断全塞进一个节点，图退化成裸循环，边和结构全失意义。
- **条件边里藏副作用**：判断函数里做一堆操作再决定走向，或去消息文本里猜意图，分支变得不可测、不可解释。
