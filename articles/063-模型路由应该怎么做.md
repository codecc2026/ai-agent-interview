# 模型路由应该怎么做？

<!-- growth-hook:v1 -->
“路由”两个字很容易被答成“给请求找个最强的模型”。但真正好的路由是分层：简单的走轻模型，复杂的走强模型，危险的加一道审核——既保效果又控成本，还要有线上数据持续校准。

## 面试官为什么爱问这题

这题偏难，考的是成本治理和路由策略设计能力。很多人把模型路由理解成"自动挑最便宜的模型"，那是把它当成纯粹的省钱工具；题库开头就把这个理解否掉了——路由的核心不是让所有请求找最强模型，也不是一味找最便宜的，而是让不同复杂度、不同风险的请求走到最合适的链路。面试官想听的是你能不能讲出路由的几个层次、怎么靠数据调、怎么防止省钱把效果打穿。前面聊成本时提过模型分层的场景，这一篇深入"路由具体怎么做"。

## 一句话先给结论

**模型路由的核心不是"让所有请求自动找最强模型"，而是让不同复杂度、不同风险等级的请求走到最合适的链路。常见三层：意图路由先判断是 FAQ、RAG、工具调用、复杂 Agent 还是转人工；复杂度路由让简单分类、抽取、总结走小模型，多步规划、开放生成、复杂决策走大模型；成本路由让热点问题先查缓存、能规则化就别进大模型、高价值或高风险任务给更强预算。路由本质是效果、成本和稳定性的平衡器，要配合评测和线上数据调。**

## 核心原理：三层路由

### 第一层：意图路由

先判断这个请求是什么类型：FAQ、RAG、工具调用、复杂 Agent，还是应该直接转人工。不同类型走不同链路，而不是统一丢给某个模型。这一步是分流的第一道闸：一个简单 FAQ 和一个要调多个工具的复杂任务，从一开始就该进不同处理路径。转人工也是路由的一个出口，有些请求模型不该硬接。

### 第二层：复杂度路由

在同一类请求里，按复杂度分模型。简单分类、格式化抽取、轻量总结走小模型；多步规划、开放生成、复杂决策走大模型。这一层的前提是能判断复杂度——什么算简单、什么算复杂，要有依据，不能拍脑袋。

### 第三层：成本路由

从成本视角再收一道：热点问题先查缓存，命中就直接返回，不进模型；能规则化解决的别进大模型；高价值用户或高风险任务才给更强的预算。这一层把"省"和"花"分开——该省的地方省掉，该花的地方花对。

| 路由层 | 判断依据 | 分流去向 |
| --- | --- | --- |
| 意图路由 | 请求是什么类型 | FAQ / RAG / 工具 / Agent / 转人工 |
| 复杂度路由 | 任务有多复杂 | 简单走小模型，复杂走大模型 |
| 成本路由 | 命中缓存？价值/风险多高？ | 缓存直返 / 规则处理 / 强模型预算 |

三层不是互斥的，一个请求可能依次经过：先判意图，再在意图内判复杂度，最后按价值和风险定预算。它们共同构成一条分流链。

| 路由层 | 判错的后果 | 怎么发现 |
| --- | --- | --- |
| 意图路由 | 复杂任务被当简单意图处理 | 某类请求完成率突然偏低 |
| 复杂度路由 | 复杂问题被下沉到小模型 | 小模型分支效果指标掉队 |
| 成本路由 | 高价值任务没给够预算 | 高风险场景出错代价高 |

这张表说明：每一层判错都有不同的失效模式，也对应不同的观测信号。路由上线后要分层看数据，才能对准是哪一层出了问题。

### 路由不做成纯主观规则

题库特别强调：落地时通常不会把路由做成纯主观规则，而会配合评测和线上数据来调。看三个东西：

**不同分支的完成率、延迟、每任务成本。** 每个路由分支表现怎么样，要用数据看——完成率够不够、延迟可不可接受、成本是不是符合预期。

**有没有某类问题被错误下沉到小模型。** 这是路由失败的典型症状：本该用大模型的复杂问题被判成简单，分给小模型，结果效果崩了。要能发现这种误判。

**要不要引入回退机制。** 比如小模型失败后升级到大模型。路由不是一锤子买卖，允许失败后升级——先看小模型，不行再上大模型，兼顾成本和效果。

## 工程实践：设计一条带回退的路由链

把三层和数据反馈落到实现上：

```python
# 伪代码：意图 → 复杂度 → 成本的分流，带小模型失败回退
def route(request):
    intent = classify_intent(request)              # 意图路由
    if intent == "faq":
        if hit_cache(request):                     # 成本路由：缓存直返
            return cache_answer(request)
        return small_model.answer(request)         # 简单意图走小模型

    if intent == "complex_agent":
        return large_model.solve(request)          # 复杂意图直接大模型

    # 复杂度路由：先试小模型，失败回退大模型
    result = small_model.answer(request)
    if not is_acceptable(result):                  # 业务侧：判断结果是否达标
        result = large_model.solve(request)        # 回退升级
    return result
```

要点：意图决定大方向，缓存和规则先挡一层，简单任务走小模型，复杂任务走大模型，小模型结果不达标时回退升级。`classify_intent`、`hit_cache`、`is_acceptable` 和各模型对象是业务侧实现。回退机制是路由的关键——它让"先省后花"成为可能，而不是一省到底。

## 追问逐条作答

### 追问一：什么场景下适合先用规则路由，而不是一开始就做模型路由？

当分流规则明确、能用简单条件判断时。比如特定前缀的请求直接走某条链路、命中固定名单的走人工、已知的热点问题查缓存——这些用规则又快又省，不需要额外调用一个模型来做路由判断。模型路由本身也有成本和延迟，如果分流逻辑用规则就能表达，没必要引入。经验值：先用规则覆盖能明确判断的部分，只有规则判不了的模糊请求才交给模型路由，避免"为了路由又加一次模型调用"。

### 追问二：小模型路由失败后，怎样设计升级和回退策略？

关键是要有"失败"的判断标准。小模型返回后，用规则或评测判断结果是否达标，看格式对不对、置信度够不够、有没有触发明显的错误信号。不达标就升级到大模型。回退要设上限，避免无限升级；还要记录每次升级的原因，用于后续优化路由规则。前面讲成本排查时说过"别为注定失败的调用付钱"，回退设计是它的另一面：该花的时候要花，别为了省一直用小模型硬撑。

### 追问三：如何避免为了省成本把系统整体效果打穿？

靠评测和数据。建立一套和路由无关的评测集，优化前后都用同一批请求测效果，设一条不可接受的效果底线——低于这条线，再省也不能上线。同时监控线上各分支的完成率，发现某类问题被错误下沉就及时调规则。经验值：改动路由规则要一次改一处、改完验一次，别一次下沉一大片，否则掉了效果也说不清是哪条规则导致的。前面讲成本与效果平衡时提过这个思路，这里是它在路由上的具体应用。

### 追问四（自补）：路由判断本身会不会成为新的成本和延迟？

会，所以要轻。用一个模型做路由判断，本身就是一次模型调用——如果它又慢又贵，省下来的钱还不够它花的。做法：能规则化就用规则；必须用模型时，用最小的模型、最短的提示词做判断；路由判断的结果可以缓存，相似请求不用重复判。经验值：路由判断的成本要显著小于它省下的成本，否则这个路由就没意义。

### 追问五（自补）：怎么发现"某类问题被错误下沉"？

靠分群看数据。把线上请求按意图、按业务维度分组，分别看每组的完成率和效果指标。如果某一组的完成率明显低于其他组，就去看这组是不是被大量分到了小模型。再抽样看具体 case，确认是路由判错还是小模型确实做不了。前面讲性能定位时说过"先看分布再动手"，这里同样要先定位到是哪类问题、哪条规则，再针对性调整。

### 追问六（自补）：路由规则需要一直调吗？

需要，它不是一次配好就不用管的东西。业务在变、请求分布在变、模型能力也在更新，今天合理的分流规则过段时间可能就不合适了。经验值：把路由的关键指标做成常态化看板，包括各分支的完成率、延迟、成本、升级率，定期回看，发现趋势性变化再调。调的时候一次动一处、改完验一次，别大批量改规则，否则出了问题说不清是哪条导致的。把路由当成需要持续经营的策略，而不是一次性的配置，才不会慢慢劣化。

## 加分项

- 纠正"路由=挑最便宜模型"的误解，定性为最合适链路的平衡器。
- 讲出三层路由，各层判断依据清楚。
- 强调数据驱动和回退机制，不是纯主观规则。
- 主动提路由判断本身也有成本，要轻、可缓存。

## 常见误区

- **把路由当纯省钱工具**：核心是效果、成本、稳定性的平衡，不是一味找便宜模型。
- **路由做成纯主观规则**：要配合评测和线上数据调，还要有回退机制。
- **忽略路由自身的成本**：为路由又加一次贵调用，省的钱还不够花。
