# 如果让你设计一个 NL2SQL Agent，你会重点控制哪些风险？

<!-- growth-hook:v1 -->
NL2SQL 上线后翻车，往往不是 SQL 写错，而是把整个库的表结构一股脑塞给模型、放它自由执行。这题真正要的是四道风险闸门：schema 裁剪、只读约束、执行前校验、含糊就澄清。

## 面试官为什么爱问这题

这题高频且偏难，考的是结构化查询能力和安全意识。NL2SQL 让模型把自然语言转成 SQL 直接查库，能力很强，但风险也很集中：生成错了查出错数据、被注入生成危险语句、表结构全塞进上下文、用户问题有歧义模型自己脑补。面试官想听的是你能不能把这四类风险说清，并给出对应的控制手段。前面聊过 RAG 的权限、代码解释器的沙箱、意图路由的澄清，这一篇把这些经验落到 NL2SQL 这个具体场景，它同时涉及上下文治理、执行安全和歧义处理，是前面很多主题的交叉点。

## 一句话先给结论

**重点控制四类风险：schema 注入、SQL 安全、执行验证和歧义澄清。首先不能把整个数据库 schema 全量塞进上下文，而要按问题做裁剪和 schema linking；其次要限制只读查询、禁止危险语句、加执行沙箱和超时控制；再次要做语法检查和执行前校验，避免生成看似合理但跑不通的 SQL；最后对时间范围、口径定义、字段歧义这类问题要支持澄清，不要让模型自行脑补。**

## 核心原理：四类风险与控制

### 一、schema 注入：别把整个库塞进上下文

不能把整个数据库 schema 全量塞进上下文，表多、字段多时既浪费 token，又会干扰模型选对表。正确做法是按问题做裁剪和 schema linking：先根据问题判断可能涉及哪些表、哪些字段，只把相关的 schema 给模型。这既是成本控制，也是准确率控制，给得越精准，模型越不容易选错表、用错字段。前面讲上下文治理时说过"只放高信号内容"，这里是它在 NL2SQL 的落地。

schema 注入还有一层含义：恶意用户可能通过输入影响模型去探测不该看到的表结构。所以 schema 暴露也要按权限裁剪——用户能看到哪些表，就只暴露哪些。

### 二、SQL 安全：只读、禁危险语句、沙箱

限制只读查询，绝大多数 NL2SQL 场景用户只是查数据，没必要给写权限。禁止危险语句，DROP、DELETE、TRUNCATE 这类直接拦掉。加执行沙箱和超时控制，即使生成了有问题的 SQL，也能在执行层兜住：限制它能访问的数据范围、限制执行时间，防止一条慢查询拖垮数据库。前面讲代码解释器沙箱、多用户隔离时说过这些，这里落到数据库查询场景。

### 三、执行验证：语法检查和执行前校验

生成 SQL 后不能直接执行，要先做语法检查，看 SQL 写得对不对、能不能解析；再做执行前校验，看查的表在不在白名单、有没有越权访问、有没有危险模式。目的是避免生成"看似合理但跑不通"的 SQL，模型经常生成语法正确但语义错误的查询，比如引用了不存在的字段、join 条件写错。执行前多一道校验，能挡住大部分这类问题。

### 四、歧义澄清：别让模型脑补

对时间范围、口径定义、字段歧义这类问题要支持澄清，不要让模型自行脑补。"上个月的销售额"是自然月还是最近 30 天？"活跃用户"的口径是什么？"订单"指哪个业务线的订单？这些含糊点如果不澄清，模型会自己选一个解释，查出来的数可能完全不是用户要的。正确做法是识别歧义、反问用户确认，而不是猜。

| 风险 | 表现 | 控制手段 |
| --- | --- | --- |
| schema 注入 | 全量塞 schema、越权探表 | 按问题裁剪、schema linking、权限过滤 |
| SQL 安全 | 危险语句、慢查询 | 只读、禁危险语句、沙箱、超时 |
| 执行验证 | 看似合理但跑不通 | 语法检查、执行前校验 |
| 歧义澄清 | 时间/口径/字段含糊 | 识别歧义、反问确认 |

四类风险的优先级不同，出事时的严重性也不一样：

| 风险 | 后果严重性 | 发生概率 | 优先级 |
| --- | --- | --- | --- |
| SQL 安全 | 高，可能删库、泄露数据 | 中 | 最高，必须硬性兜住 |
| 歧义澄清 | 高，查出错误结论误导决策 | 高 | 高，要主动识别 |
| 执行验证 | 中，查询失败或结果不准 | 高 | 高，每次都要过 |
| schema 注入 | 中，浪费资源、选错表 | 中 | 中，影响成本和准确率 |

SQL 安全必须最高优先级，因为它后果不可逆；歧义澄清紧随其后，因为用户问题含糊是常态、而错误结论会误导决策。

### 还有一类容易被忽略的风险：结果呈现

查到了数据不等于用户用对了数据。一个数字脱离上下文很容易被误读，没说统计口径、没说时间范围、没说数据量级，用户可能得出错误结论。所以结果呈现时要带上元信息：这次查询用的是什么口径、覆盖什么时间范围、基于哪些表；数据为空时说明是真的没有还是查询条件太严；结果量大时给出摘要而不是全量倾倒。前面讲幻觉治理时说过"看起来很像真的但细节偏了"，NL2SQL 的结果呈现也有这类问题，数字是对的，但用户理解偏了。把上下文交代清楚，是这类系统的责任。

## 工程实践：一条查询的全流程

把四类控制串成一次查询的流程：

```python
# 伪代码：NL2SQL 查询的风险控制流程
def query(question, user):
    schema = schema_linker.select(question, user.permissions)  # 裁剪 + 权限过滤
    if ambiguous(question, schema):                            # 歧义识别
        return ask_clarification(question)                     # 反问，不脑补
    sql = model.generate(question, schema)                     # 生成 SQL
    if not validator.check(sql, allowed_tables=user.tables):   # 语法 + 执行前校验
        return self_correct(sql, question)                     # 修正重试
    result = sandbox.execute(sql, readonly=True, timeout=SEC)  # 只读 + 沙箱 + 超时
    return present(result)
```

要点：schema 按权限裁剪、歧义先澄清、生成后校验、只读沙箱执行。`schema_linker` / `ambiguous` / `validator` / `sandbox` 是业务侧实现。这段伪代码把四类风险控制串成了一条流水线。

## 追问逐条作答

### 追问一：生成 SQL 前要不要先展示预览？

看场景和风险。低风险的内部探索场景可以不预览，直接出结果快；高风险场景，比如涉及敏感数据、结果要用于决策或对外，先展示生成的 SQL 让用户确认再执行，能挡住"模型理解错了"的情况。经验值：预览的代价是多一步交互，收益是防止错误查询返回错误结论；用户体验允许的话，展示 SQL 预览是个稳妥做法，尤其在用户懂 SQL 的场景。

### 追问二：如何做 self-correction？

执行失败或有明显问题时，把错误信息反馈给模型让它修正。SQL 执行报错，比如语法错、字段不存在、表不存在，把错误原文和原 SQL 一起给模型，让它重新生成。校验不通过，比如引用了不在白名单的表，也把原因反馈回去。关键是要设重试上限，别无限修正；修正几次还不行就转人工或报错，而不是一直试。前面讲代码执行闭环时说过"根据反馈继续修正"，这里是它在 SQL 场景的应用。

### 追问三：什么时候该放弃生成 SQL，转人工或转报表模板？

几种情况：多次 self-correction 都失败，说明这个问题模型处理不了，别硬试；问题需要复杂跨表逻辑、模型容易出错，这类用预设的报表模板更稳；问题反复出现且有标准答案，做成固定报表或指标，不用每次让模型生成；涉及高风险数据或不可逆操作，转人工把关。经验值：把"放弃"当成一种正常路径，而不是失败，及时转人工比持续产出错误 SQL 更负责。

### 追问四（自补）：schema linking 具体怎么做？

先根据问题里的关键词、业务术语，匹配可能相关的表和字段，比如问题提到"订单"，就把订单相关的表捞出来。再做进一步的关联，根据表之间的关系，把可能 join 的表也纳入。最后按权限过滤，用户无权访问的表直接排除，连 schema 都不暴露。这样给模型的就是"跟这个问题相关、且用户有权看"的那一小部分 schema，精准又安全。前面讲 RAG 检索时说过"按相关性召回"，schema linking 是同一思路用在表结构上。

### 追问五（自补）：只读约束怎么落到数据库层？

不要只靠生成的 SQL 文本判断，模型可能在注释、子查询里藏写操作。更稳的做法是数据库层面给这个查询账号只授予 SELECT 权限，从根上让它没有写的能力。再配合 SQL 解析做语句类型检查，确认是 SELECT 开头、不含多语句、不含危险函数。应用层检查和数据库层权限双管齐下：应用层快筛，数据库层兜底。前面讲纵深防御时说过这个思路，这里正是它，不把安全押在"生成的 SQL 看起来没问题"上。

### 追问六（自补）：超过权限的数据被查出来怎么办？

这在设计正确的系统里不该发生，因为权限过滤在 schema 裁剪阶段就做了，用户看不到无权访问的表结构，模型自然生成不出查那些表的 SQL。但要有第二道防线：执行层的数据库账号只授予该用户有权访问的库的读权限，即使 SQL 里写了越权的表，数据库也会拒绝。两道防线的意义在于，第一道提高准确率、减少无效尝试，第二道兜住安全底线。经验值：权限过滤一定要在生成之前做，而不是查完结果再过滤，后者已经让数据泄露到了系统内部。

### 追问七（自补）：NL2SQL 和固定报表、BI 工具怎么配合？

不是替代关系，是分工。NL2SQL 适合灵活、临时的问题，用户随口问一个数，不用预先配报表；固定报表适合高频、标准的问题，比如每天要看的运营大盘，做成报表更稳、更快、更可信。经验值：把高频且口径固定的问题沉淀成报表或指标，NL2SQL 只处理长尾的、非标准的问题。这样既保证核心数据的准确性，又保留灵活查询的能力。前面讲"什么时候放弃生成 SQL"时提过转报表模板，这里是同一思路的系统化，不是出了问题才转，而是本来就该各司其职。

> 我重点控四类风险。schema 注入：不把整个库塞进上下文，按问题做裁剪和 schema linking，只给相关的、用户有权看的表结构。SQL 安全：限制只读、禁止 DROP DELETE 这类危险语句、加执行沙箱和超时，最好在数据库层面就只给 SELECT 权限。执行验证：生成后先做语法检查和执行前校验，挡住看似合理但跑不通的 SQL，失败就反馈给模型 self-correction，但设重试上限。歧义澄清：时间范围、口径定义、字段歧义要反问确认，不让模型脑补。另外高风险场景先展示 SQL 预览让用户确认，多次修不好或需要复杂逻辑时就转人工或报表模板，及时放弃比硬试更负责。

## 加分项

- 四类风险分类清楚，每类都有对应控制手段。
- schema linking 讲清"按问题裁剪 + 权限过滤"，兼顾成本和准确。
- 只读约束落到数据库层权限，体现纵深防御。
- 把"放弃生成"当正常路径，显示工程判断力。

## 常见误区

- **全量塞 schema**：浪费 token 还干扰选表，应按问题裁剪。
- **只靠文本判断只读**：要在数据库层真正收回写权限。
- **歧义让模型脑补**：口径不清时必须澄清，否则查出的数不是用户要的。
