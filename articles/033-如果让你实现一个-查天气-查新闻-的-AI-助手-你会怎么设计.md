# 如果让你实现一个"查天气、查新闻"的 AI 助手，你会怎么设计？

## 面试官为什么爱问这题

这题看着像玩具题，其实是最能区分"背过 Agent 定义"和"真把助手做过一遍"的一道。给个具体需求，很多人张口就是"上个 ReAct Agent，配几个工具"。可面试官真正要听的不是你会不会用框架，而是你能不能先判断：这件事到底需不需要 Agent。查天气、查新闻本质是查完就答的单轮任务，硬套多步循环只会平白多出延迟和不确定性。会做场景判断、能把一个模糊需求拆成可落地的几层、知道哪一层最容易出事，才是这道题的考点。

## 一句话先给结论

**先做场景判断再谈方案：这类需求的核心是"意图识别 + 工具调用 + 结果整合"，按输入与路由、工具、调度、输出四层来拆；单轮查询用 Prompt + Function Calling 往往就够，只有需求升级成"查完再顺着追问"的多步动态链路时才需要完整 Agent。**

## 核心原理：四层怎么切，为什么这么切

### 第一层，输入与路由

用户一句话进来，系统要先回答三个问题：他要查天气还是查新闻，还是两个都要；参数齐不齐；要不要拆成多个子任务。

这里干的是意图识别加参数抽取。城市、时间、新闻主题这几个槽位要显式抽出来，别指望工具层自己去猜。路由判断尤其关键——"今天北京天气和科技新闻都要看"这句话要能拆成两个并行子任务，而不是让模型随机先查一个。

为什么单独设一层，而不丢给模型临场发挥？因为这一层的错误是"上游污染"：意图判错、城市抽错，后面四层全白干，而且工具返回的是另一个城市的天气，模型会一本正经地把它讲成你要的那个城市。把它做成可单独测试、可单独打日志的一层，排查时才知道是"没听懂"还是"工具没查到"。

### 第二层，工具层

天气查询和新闻检索各自封成一个边界清晰的 Tool。每个工具要定义四件事：schema（入参出参长什么样）、参数说明（每个字段什么意思、什么格式）、异常返回（查不到、限流、超时分别返回什么结构）、超时策略（多久算失败、失败几次停）。

这层最容易犯的错是把工具描述写成给程序员看的注释。工具描述是写给模型读的，它决定了模型会不会正确调用、会不会在参数上乱填。之前聊过工具设计好坏要看可发现性、参数清晰度这些维度，这里不再展开，只强调一点：天气工具的 `city` 字段要写清楚"中文城市名，如'北京'"还是"adcode，如 110000"，含糊一次，模型就会两种都试。

工具层还要和"外部 API"分开看。工具是给模型的能力描述，外部 API 是真正发请求的那一步，中间隔着一个适配器。这个适配器负责把第三方千奇百怪的返回（有的字段叫 `temp`，有的叫 `temperature`）归一成 schema 约定的结构。没有这层归一，输出层就要面对N种返回格式。

### 第三层，调度层

这一层决定：调哪个工具、参数怎么传、要不要串联多个工具。两种做法。

最简单的是 Function Calling：把工具定义随请求发给模型，模型返回一个结构化的调用意图（调哪个函数、参数是什么），系统执行它，把结果塞回去让模型接着说。它是模型的一次"输出格式约定"，不是模型自己会执行函数——执行永远在你这边。这个边界常被搞混， Function Calling 也不等于 MCP，后者是另一套工具发现与连接协议。

复杂一点的是轻量 Agent：让模型在一个循环里自主决定下一步调什么、要不要继续。它的价值只在"下一步依赖上一步结果"时才显现——比如"先查天气，再按天气推荐本地新闻"，新闻工具的参数依赖天气查询的输出，这就有动态链路了。单轮"查一下今天天气"根本用不上循环，加进去只是多烧几轮 token。

### 第四层，输出层

工具返回的是结构化数据，用户要的是自然语言。输出层先把结果整理成干净形态：天气只留关键字段（温度、天气状况、降水概率），新闻留标题、摘要和来源链接；再把这份整理好的内容交给模型生成回复。

为什么要"先整理再交给模型"，而不是把工具原始返回整个丢进去让模型自己挑？因为原始返回里常有模型不该看或看不懂的东西——一长串调试字段、内部 id、嵌套三层的 JSON。字段越多，模型越容易抓错重点，甚至把某个数字当成另一个字段的值讲出来。整理这一步是在收窄模型的输入面。

## 横向对比：三种调度方案怎么选

同样是这个助手，调度层用哪种做法，直接决定延迟、成本和能覆盖的需求。

| 方案 | 适用需求 | 延迟与成本 | 主要风险 |
| --- | --- | --- | --- |
| Prompt + Function Calling | 单轮查天气、单轮查新闻、两项并列查询 | 一次或两次模型调用，最低 | 复杂多步需求表达不了，模型可能漏调工具 |
| 轻量 Agent 循环 | 查完按结果再查、多步依赖链路 | 多轮调用，延迟与 token 随步数涨 | 不收敛、重复调用、状态被挤出窗口 |
| 完整 ReAct Agent | 需求开放、步骤无法预先枚举 | 最高，步数不可控 | 可复现性差，出问题难定位到某一步 |

| 对比维度 | 让它直接联网搜 | 封成专用 Tool | 用 RAG 检索 |
| --- | --- | --- | --- |
| 数据时效 | 取决于搜索引擎 | 取决于 API，实时可调 | 索引更新有滞后 |
| 结构化程度 | 杂，需二次清洗 | 高，schema 已归一 | 中等，片段化 |
| 适用场景 | 开放信息、无明确数据源 | 有稳定 API 的天气/新闻 | 私有文档、历史资料库 |

第二张表要点在最后一句边界：RAG 是把内容找出来喂进窗口，长上下文是把内容直接摊在窗口里，两者都不是"调一个实时 API 拿结构化数据"。天气这种要拿实时结构字段的需求，该走工具调用，不该硬塞进检索。把这几种能力混为一谈，是面试里很容易被追问到答不上来的地方。

## 工程实践：把四层落成可运行的东西

### 工具定义与调度配置

下面是一份可直接照抄的工具定义与调度配置，用 Function Calling 的写法给出。关键是每个字段都有说明，异常和超时写在工具侧而不是让模型临场处理。

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询指定城市指定日期的天气，返回温度、天气状况、降水概率",
        "parameters": {
          "type": "object",
          "properties": {
            "city": {"type": "string", "description": "中文城市名，如 北京"},
            "date": {"type": "string", "description": "日期 YYYY-MM-DD，缺省为今天"}
          },
          "required": ["city"]
        }
      }
    },
    {
      "type": "function",
      "function": {
        "name": "get_news",
        "description": "按主题检索近期新闻，返回标题、摘要、来源链接",
        "parameters": {
          "type": "object",
          "properties": {
            "topic": {"type": "string", "description": "新闻主题关键词"},
            "date": {"type": "string", "description": "日期 YYYY-MM-DD，缺省为今天"}
          },
          "required": ["topic"]
        }
      }
    }
  ],
  "tool_choice": "auto"
}
```

`tool_choice` 设成 `auto`，让模型自己判断要不要调工具；如果某轮是纯闲聊（"你好"），它可以选择不调。这里不要图省事硬编码成总调天气工具，否则用户打个招呼也会触发一次查询。

### 降级与超时的落点

外部 API 一定有挂的时候。天气接口的降级策略要提前写进适配器：超时按经验的 P95 加余量设（比如接口 P95 是 1.5s，超时给 3s 是经验值），重试前先确认接口幂等——查询类一般幂等，可以重试一到两次；重试仍失败就返回一个带 `status: "unavailable"` 的结构化结果，而不是抛异常把整条链路打断。

这个降级结果怎么告诉用户，比怎么重试更重要。错误不能被吞掉后让模型自由发挥：如果工具返回空，模型很可能会用自己的知识编一段"北京今天大概二十几度"。正确做法是把"数据源不可用"这个事实显式送进输出层，让回复变成"暂时查不到北京天气，请稍后再试"。这也是为什么前面强调异常返回要有固定结构——输出层靠这个结构判断该不该让模型生成内容。

### 缓存与频控

天气数据有个天然性质：同一城市短时间内变化很小，没必要每个请求都打外部 API。给天气工具加一层按"城市 + 日期"为键的缓存，过期时间设几分钟（经验值），既能砍掉大量重复调用，也能在接口抖一时的时候靠旧值顶住。新闻检索的时效要求更高，缓存窗口要短得多，或者干脆只缓存主题到来源列表的映射。

缓存之外还要有频控。单用户连续快速发问、或者路由层一次拆出十几个子任务，都会在瞬间放大下游压力。给每个用户的单位时间请求数设上限，超了直接返回降级话术，比让限流错误一路冒泡到模型更可控。注意缓存键里要带上影响结果的全部参数，漏掉 `date` 就会把昨天的天气当今天的返回，这类 bug 在演示时几乎看不出来，上了量才暴露。

### 主循环伪代码

```python
def handle(query, trace):
    intents = route(query)              # 第一层：意图 + 槽位，可单测
    trace.log("route", intents)
    if not intents.need_tool:           # 纯闲聊，直接答
        return model.reply(query)

    results = []
    for task in intents.tasks:          # 第二、三层：按意图调度工具
        spec = TOOL_SPECS[task.name]    # 白名单，非法工具名不会走到这里
        try:
            raw = call_api(task.name, task.args, timeout=3)  # 超时 3s：经验值
            results.append(normalize(raw, spec))             # 归一成约定结构
        except ApiError as e:
            results.append({"status": "unavailable", "error": e.code})
            trace.log("degrade", task.name, e.code)

    bundle = polish(results)            # 第四层：只留关键字段 + 来源
    return model.reply(query, context=bundle)  # 带结构化上下文生成回复
```

注意 `polish` 之后才交给模型，且每个失败任务都带 `status` 字段进 `bundle`。这样模型看到的永远是收窄过、带可信标记的输入，而不是一堆原始 JSON。

## 追问逐条作答

题库这题没给固定的常见追问，下面几条是面试官顺着这道题最可能深挖的方向，逐条正面回答。

### 追问一：用户说"查一下天气"，没给城市，你怎么办？

这是槽位缺失，不是意图不明。第一层抽取后要判断必填槽位 `city` 是否为空，为空就走澄清话术反问"请问查哪个城市"，而不是拿一个默认城市（比如模型所在的服务器位置）去猜。猜错城市比多问一句的代价大得多。工程上可以把"必填槽位"写进工具的 `required` 字段，抽取层直接读它来判断缺什么，避免两处各写一份规则导致不一致。

### 追问二：为什么不用一个工具把天气和新闻都查了，要拆成两个？

因为两件事的数据源、参数、失败模式都不同。天气来自实时 API，新闻来自检索，一个可能限流、一个可能索引滞后；合进一个工具，参数 schema 会变成两种结构的并集，模型传参更容易错，其中一个失败时整个工具都算失败，也没法分别降级。拆开后还能并行调用，延迟取最慢的那个而不是两者相加。判断标准是：失败模式不同、可独立复用，就拆。

### 追问三：两个工具都要调时，串行还是并行？

看有没有依赖。查天气和查新闻互不依赖，就并行发，延迟取最大值。"先查天气，再按天气推荐本地新闻"有依赖，新闻工具的参数来自天气结果，只能串行，而且这正是轻量 Agent 循环派上用场的场景。别为了省事一律串行，也别在没依赖时硬套循环。

### 追问四：模型把工具结果又"编"了一遍，比如天气接口返回 18 度它说成 28 度，怎么防？

两层防线。输入侧就是前面说的 `polish`：把结果收窄成关键字段，减少模型抓错字段的概率；输出侧做事实校验——把回复里的关键数字和工具返回比对，对不上就不发或重新生成。彻底的做法是让回复直接拼装结构化字段里的值（温度那段由模板填），模型只负责生成连接词和语气，不负责复述数字。这属于"结果整合"这层的活，不是换个更强的模型就能解决的。

### 追问五：用户接着问"那后天呢"，如何实现多轮？

这要求上下文里记住"那"指的是刚才那次查询，且要复用之前的城市参数。做法是把上一轮的意图和关键槽位存进会话状态，新一轮抽取时把"城市=北京"这类已确定槽位带进去做继承，只抽新增的"日期=后天"。注意状态只存抽好的槽位和关键结果，不要把完整对话历史无脑堆进 messages——之前聊过把中间结论一股脑塞进窗口会让关键观察被挤掉，多轮助手同样踩这个坑。

### 追问六：为什么不直接用 Agent 一把梭，非要分四层？

分层不是为了好看，是为了让每一层能单独测试和定位。用户答非所问，你能一眼判断是路由层没听懂、工具层没查到、还是输出层编造了数字；一个黑盒 Agent 出了问题只能笼统归因为"模型不太行"。之前讨论过落地组件怎么取舍，核心判据就在这里：能定位到层的系统才谈得上迭代。而且分层之后，单轮场景可以只跑前四层里的必要部分，不为用不上能力付成本。

### 追问七：这个助手做出来，你怎么判断它好不好？

分两层测。先看每层单独准不准：路由层用一批标注好意图和槽位的句子测意图分类准确率、槽位抽取准确率；工具层测调用成功率、参数正确率和超时率；这两层是确定性的，能看到具体错在哪条。再看端到端：准备一批真实问题，核对回复里的关键字段是否和工具返回一致，这就是前面说的数字校验，重点统计"编造率"——工具给了 A 却说成 B 的比例。

别只看"回答读起来通顺不通顺"，通顺但数字错了是最危险的，用户完全看不出。分层指标能定位问题在哪一层，端到端指标能兜住用户实际感受，两者都要有。面试里能讲出"我怎么测、盯哪个数"，比"我做完了"有说服力得多，因为它说明你知道线上会怎么坏。

## 60 秒面试回答模板

> 我会先做场景判断，不直接上 Agent。查天气、查新闻本质是查完就答，核心是意图识别、工具调用和结果整合。我按四层设计：输入路由层判断查天气还是查新闻、抽出城市和时间这些槽位；工具层把天气和新闻各封成一个 Tool，写清 schema、参数说明、异常返回和超时；调度层单轮就用 Function Calling 让模型决定调哪个、传什么参，只有查完再按结果接着查的多步链路才上轻量 Agent；输出层先把工具结果整理成关键字段加来源，再交给模型生成回复。工程上重点盯三件事：工具描述写清楚免得乱调、外部 API 做超时降级、结果带结构化字段防模型二次编造。插槽位缺失就反问澄清，两个工具没依赖就并行调。

## 加分项

- **说出"先判断要不要 Agent"**：这是这题和"背定义"的分水岭，开口先做场景判断，比直接抛框架名高一个层次。
- **区分工具与外部 API**：能点出中间有个归一适配器，说明你处理过第三方返回格式不统一的真实问题。
- **给降级结果设固定结构**：不说"失败了重试一下"就完，而是说返回带 `status` 的结构让输出层能判断，这是做过的痕迹。
- **主动提多轮状态的槽位继承**：把追问里才该答的点提前带一句，显示你考虑的是完整对话而不只是一次请求。

## 常见误区

- **一上来就说用 ReAct Agent**：单轮查询用不上循环，平白多出延迟和不确定性，还没法复现。先判断是否多步，再决定要不要 Agent。
- **把 Function Calling 当成模型在执行函数**：执行永远在自己的系统里，模型只返回一个结构化调用意图。这个边界答糊了，等于暴露没真接过。
- **把工具原始返回整个丢给模型**：字段越多越容易抓错、越容易编数字。整理成关键字段再送进去，是可复现性的前提。
- **失败就吞掉让模型自由发挥**：工具查不到时模型会用自有知识补一段看似合理的答案，用户根本分不清真假。失败必须显式传达到输出层。
