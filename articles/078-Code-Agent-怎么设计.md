# Code Agent 怎么设计？

<!-- growth-hook:v1 -->
Code Agent 的价值不在“会写几行代码”，而在能不能读完整个仓库、定计划、改文件、跑验证、按失败结果再改回来。这题拉开差距的，是上下文怎么管、验证怎么做、失败怎么回退。

## 面试官为什么爱问这题

这题高频且偏难，考的是代码场景下的 Agent 设计能力。很多人把 Code Agent 理解成"会写代码的自动补全"，面试官想听的是它能围绕一个代码任务完成完整闭环：读代码库、定计划、改文件、跑验证、根据结果继续修正。题库给了很好的骨架：它本质仍是"模型 + 工具集 + 运行循环 + 当前状态"的执行系统，只是工具和状态更偏代码场景。更关键的是三个真难点：上下文治理、验证闭环、失败处理，这些才是区分成熟系统和 Demo 的地方。前面聊过类 Manus 通用智能体、浏览器自动化、完成判断，这一篇把这套思路落到代码场景。

## 一句话先给结论

**Code Agent 的核心不是"会写几行代码"，而是能围绕一个代码任务完成读代码库、定计划、改文件、跑验证、根据结果继续修正的闭环。它本质仍是模型 + 工具集 + 运行循环 + 当前状态的执行系统，按模块分六层：任务理解、代码库理解、计划与执行、工具、反馈闭环、安全治理。真正难点在三个地方：上下文治理（大代码库怎么只拿相关上下文）、验证闭环（怎么判断修复真生效，而不是模型说改好了）、失败处理（连续修不好时怎么停、怎么暴露诊断、怎么交还给人）。成熟的 Code Agent 更接近面向代码任务的执行系统，不是代码自动补全的放大版。**

## 核心原理：六层设计

### 任务理解层

先把需求转成明确目标，判断是读代码、改 bug、补测试、重构，还是回答架构问题。不同类型任务后续路径不同——改 bug 要定位修复，补测试要理解现有测试风格，回答架构问题只要读不需要改。先把任务定性，才不会用错流程。

### 代码库理解层

通过代码搜索、文件树、符号索引、依赖关系、提交历史建立"最小必要上下文"，而不是把整个代码库一股脑塞进模型。这是代码场景特有的关键层——代码库往往很大，不可能全塞进窗口。要靠搜索和索引找到与任务相关的那部分。前面讲检索和上下文治理时说过"只放高信号内容"，这里是它在代码库的落地。

### 计划与执行层

先列出修改计划，再决定读哪些文件、改哪些文件、跑哪些命令、需要哪些验证。计划先行很重要——复杂改动不规划好就动手，容易改一处坏三处。计划让执行有序，也便于中途检查进度。

### 工具层

至少要有搜索、读文件、编辑文件、运行测试、执行命令、查看日志这些能力。工具是 Code Agent 的手脚——前面讲 MCP 工具生态时提过文件与代码类工具，这里是它们在代码场景的完整集合。少了哪一类，闭环就断一环：不能跑测试就没法验证，不能看日志就没法诊断。

### 反馈闭环层

根据 lint、测试、运行报错、diff 结果继续修正，而不是生成一次补丁就结束。这是区分 Code Agent 和普通代码生成的关键——它知道自己改完的东西有没有用。测试过了没、lint 有没有新错误、diff 是不是符合预期，这些反馈驱动下一轮修正。前面讲执行闭环和反思时说过"每步后检查"，这里正是那个机制。

### 安全治理层

限制执行权限、隔离危险命令、保留变更和执行日志，避免 Agent 在代码库里无约束乱改。代码库是资产，Agent 不能随意删改；执行命令可能有副作用，要隔离危险命令；变更要留痕，出问题能回滚。前面讲行为边界和沙箱时说过这些，这里落到代码场景。

| 层 | 做什么 | 缺了会怎样 |
| --- | --- | --- |
| 任务理解 | 定性任务目标 | 用错流程，方向跑偏 |
| 代码库理解 | 建立最小必要上下文 | 上下文爆炸或遗漏关键代码 |
| 计划与执行 | 列计划、读写文件、跑命令 | 改一处坏三处 |
| 工具 | 搜索/读写/测试/命令/日志 | 闭环断环 |
| 反馈闭环 | 按 lint/测试/报错继续修正 | 生成一次就结束，不管对不对 |
| 安全治理 | 权限、隔离、日志、回滚 | 在代码库里乱改 |

六层可以按作用分成两组：

| 分组 | 包含层 | 作用 |
| --- | --- | --- |
| 能干活 | 任务理解、代码库理解、计划执行、工具、反馈闭环 | 搭出从理解到验证修正的执行闭环 |
| 别闯祸 | 安全治理 | 限权限、隔离危险命令、留回滚余地 |

只会干活不会收住的 Agent 风险极高，只讲安全却干不了活的没价值，两组缺一不可。

### 三个真难点

题库点出真正的难点不在"会不会生成代码"，而在三处：

**上下文治理。** 代码库很大时，怎么只拿到和当前任务最相关的上下文。这靠代码库理解层——搜索、索引、依赖分析，把范围收窄到相关文件。前面讲检索治理时说过"无关内容既费钱又扰效果"，代码库场景尤其明显。

**验证闭环。** 怎么判断修复真的生效，而不是只让模型说"我已经改好了"。这靠反馈闭环层——跑测试、看 lint、查报错，用真实执行结果说话。模型的自我声明不算数。

**失败处理。** 当 Agent 连续修不好 bug 时，怎么停下来、怎么暴露中间诊断、怎么交还给人。这靠安全治理层和完成判断——设重试上限、保留诊断信息、必要时转人工。前面讲终止条件和 need_human 时说过，这里是它的代码场景应用。

## 工程实践：验证闭环怎么建

落到实现，核心是把"改完"和"验证通过"分开：

```python
# 伪代码：修改—验证—修正闭环
def fix_bug(task):
    context = codebase.understand(task)          # 代码库理解：最小上下文
    plan = planner.make_plan(task, context)      # 计划
    for attempt in range(max_attempts):           # 带上限的循环
        patch = editor.apply(plan)                # 改文件
        feedback = {
            "lint": tools.run_lint(),             # 验证：lint
            "tests": tools.run_tests(),           # 验证：测试
            "diff": tools.show_diff(),            # 验证：改动范围
        }
        if all_passed(feedback):                  # 只有验证通过才算完成
            return patch
        plan = planner.revise(plan, feedback)     # 不通过就按反馈修正计划
    return handoff_with_diagnostics(plan, feedback)  # 修不好，带诊断交还人

# codebase / planner / editor / tools / all_passed 为业务侧实现
```

要点：`all_passed` 看的是真实验证结果，不是模型说"改好了"；带 `max_attempts` 上限，修不好就带诊断交还人。变量都是业务侧实现。

## 追问逐条作答

### 追问一：千万行代码库里，Code Agent 最容易先卡在哪里？

卡在上下文治理。代码库太大，不可能全塞进窗口，如果搜索和索引做得不好，要么拿不到关键代码，改错了地方；要么塞进去太多无关代码，噪声淹没信号、token 烧光。所以第一步要能把范围收窄到与任务相关的文件和符号，靠符号索引、依赖分析、提交历史这些手段建立最小必要上下文。前面讲大代码库的检索时说过，上下文质量决定后面所有步骤的质量。

### 追问二：Agent 修不好 bug 时，怎么设计停止条件和人工接管？

设重试上限和进展判断。连续几次修改都没让测试通过、或者改动没有实质进展，就该停，而不是无限试。停的时候要做两件事：一是暴露中间诊断，说清试过哪些方案、每次为什么失败、当前的判断是什么，让人能接手；二是明确交还控制权，把任务状态和诊断打包给人，由人决定怎么继续。前面讲 need_human 终态和失败处理时说过这些，代码场景里诊断信息尤其重要，因为没有它人就得从头查。

### 追问三：静态知识和动态数据在代码场景里怎么区分？

静态知识是代码本身的结构，包括文件、符号、依赖、历史，这些通过索引获取，相对稳定，可以预先建立。动态数据是运行时才产生的，包括测试输出、运行报错、日志、实际 diff，这些靠执行反馈获取，每次都不一样。判断标准：这个信息是"代码里写着的"还是"跑起来才有的"。前者靠索引，后者靠运行反馈。两类要配合，索引帮 Agent 找到该改哪，运行反馈帮它确认改对了没。

### 追问四（自补）：为什么"生成一次补丁就结束"不算合格的 Code Agent？

因为生成不等于正确。模型写出补丁时并不知道它能不能编译、测试过不过、有没有引入新问题。只有跑了验证、看了反馈，才知道修复是否生效。一次就结束的 Agent 把验证责任推给了用户，用户还得自己跑测试、发现问题、再回来让它改——那它只是个代码生成器，不是能闭环解决问题的 Agent。反馈闭环层正是为了把验证纳入系统内部。

### 追问五（自补）：安全治理层为什么在代码场景特别重要？

因为代码库是核心资产，且执行命令有真实副作用。一个无约束的 Agent 可能删掉重要文件、改坏核心模块、执行危险命令。安全治理层限制执行权限，只给必要的文件操作权限；隔离危险命令，rm、部署类命令不能直接跑；保留变更和执行日志，出问题能定位和回滚。前面讲行为边界和沙箱隔离时说过这些，代码场景里它们直接保护着资产安全。

## 60 秒面试回答模板

> Code Agent 的核心不是会写几行代码，而是围绕代码任务完成读代码库、定计划、改文件、跑验证、按结果修正的闭环，本质还是模型加工具集加运行循环加当前状态。分六层：任务理解先定性；代码库理解靠搜索、索引、依赖建立最小必要上下文，不把整个库塞进去；计划与执行先列计划再动手；工具层要有搜索、读写、测试、命令、日志；反馈闭环按 lint、测试、报错、diff 继续修正；安全治理限权限、隔离危险命令、留变更日志。三个真难点是上下文治理、验证闭环和失败处理：大库怎么拿相关上下文、怎么确认修复真生效而不是模型说改好了、连续修不好怎么停下来带诊断交还人。它是面向代码任务的执行系统，不是自动补全的放大版。

## 加分项

- 用"执行系统"定性，六层覆盖完整。
- 点出三个真难点不在写代码本身，拔高一层。
- 验证闭环用真实测试结果，不采信模型自我声明。
- 失败处理给出停止上限和带诊断交接，落到实现。

## 常见误区

- **当成代码补全放大版**：忽略读代码库、验证、修正的完整闭环。
- **把整个代码库塞进上下文**：要靠索引和搜索拿最小必要上下文。
- **生成补丁就算完成**：没跑验证就不能说修复生效。
