# 什么时候工作流比 Agent 更合适？

<!-- growth-hook:v1 -->
一说“智能体”就默认要上 Agent，是很多方案翻车的开始。企业里大量任务其实步骤固定、输出明确、还要可追责——这种场景工作流往往比 Agent 更稳。这题考的是你有没有“不用 Agent”的判断力。

## 面试官为什么爱问这题

这题高频，考的是流程治理意识，也就是你有没有"不是所有问题都该交给 Agent"的克制。Agent 是热点，很多人一说智能体就把流程也往 Agent 上套，结果把本来稳定可控的业务流程搞得路径不可预测、难以审计。面试官想听的是你能不能划清边界：业务步骤固定、输出格式明确、要求强可控和易审计时，工作流通常更合适；只有开放任务和动态决策才真正需要 Agent。前面聊过图编排的价值、也聊过什么时候拆多智能体，这一篇从"流程治理"的角度看另一半问题——什么时候该克制住不上 Agent。

## 一句话先给结论

**当业务步骤固定、输出格式明确、希望强可控和易审计时，工作流通常比 Agent 更合适。分类、摘要、内容审核、报告生成、表单填充、固定审批链这类场景，流程路径通常是稳定的，用工作流能更清楚地定义节点职责、失败重试、人工介入点和 SLA。Agent 更适合开放任务和动态决策，工作流更适合企业里大量"有规则、可追责、可回放"的流程型任务。**

## 核心原理：两条路线的适用边界

### 判断的核心：路径是否已可预测

把"工作流"和"Agent"放到一条轴上，区别在"下一步去哪由谁决定"。工作流的路径是人事先编排好的，每一步、每个分支都能提前列出来；Agent 的路径是模型在运行时根据结果动态决定的，走哪条不完全可预测。

由此推出判断标准：如果你的任务路径本来就是稳定的，比如先做 A、再做 B、满足条件走 C 否则走 D，那把它写成固定流程最清楚，让模型在固定节点里做单点决策即可。如果路径本身无法提前列全，要模型根据中间结果决定接着查什么、要不要换路、何时停，才是 Agent 的用武之地。

### 工作流更合适的三类信号

**一、步骤固定。** 分类、摘要、内容审核、报告生成、表单填充、固定审批链，这些场景的流程路径通常是稳定的。步骤固定意味着能提前编排，不需要模型来决定流程走向。

**二、要强可控和易审计。** 企业流程往往要求"有规则、可追责、可回放"。工作流把节点职责、失败重试、人工介入点、SLA 都定义得清清楚楚，出了问题能定位到具体节点、能回放当时的执行。这些正是治理要求。

**三、输出格式明确。** 要求输出固定格式、固定字段时，工作流的节点能明确约定输入输出 schema，比让 Agent 自由发挥更可靠。

| 维度 | 工作流 | Agent |
| --- | --- | --- |
| 谁决定下一步 | 人事先编排 | 模型运行时动态决定 |
| 路径 | 固定、可预测 | 开放、不固定 |
| 可控与审计 | 节点职责、重试、介入点、SLA 清晰 | 路径不固定，治理更难 |
| 适合任务 | 分类、审核、审批、报告等规则型流程 | 开放任务、动态决策 |

### 这不是否定 Agent

要讲清：说工作流更合适，不是说 Agent 不好，而是不同任务配不同工具。前面讲图编排的价值时说过，当任务有分支、循环、人工中断时，图编排能把控制流显式化；这里说的"工作流"正是这类显式编排思路在流程型任务上的应用。Agent 的价值在开放场景，工作流的价值在确定性场景，两者互补。真正成熟的系统常常混着用：主体是固定工作流，个别需要动态决策的节点里嵌一个小型 Agent。

用一张表把任务特征和对策对应起来，选型时会更直接：

| 任务特征 | 更合适的方案 | 原因 |
| --- | --- | --- |
| 步骤固定、路径可提前列全 | 工作流 | 编排清楚，治理要素好定义 |
| 要强可控、易审计、可回放 | 工作流 | 节点职责和状态都可追踪 |
| 开放任务、路径无法预测 | Agent | 需要模型在运行时动态决策 |
| 主体固定、个别节点要动态 | 混合：工作流嵌 Agent | 兼顾整体可控与局部灵活 |

最后一行是很多真实系统的形态：主体流程是固定的、可审计的，只在真正需要灵活的一两个节点里放进 Agent。比如一个内容审核工作流，整体步骤固定，但"判断内容是否违规"这个节点可能需要模型结合上下文灵活判断。这样既保住了流程治理，又拿到了模型的理解能力。经验值：从固定工作流起步，只在确实需要动态性的地方局部引入 Agent，比一开始就用全 Agent 架构更容易管控。

## 工程实践：怎么设计一条工作流

落到设计上，工作流的优势是能把治理要素显式定义。几个关键动作：

**哪些节点交给 LLM。** 工作流里的节点不都是模型调用——有些是确定性的代码逻辑（查库、格式校验、计算），有些才需要模型的理解能力。判断标准：需要语义理解、非结构化处理的环节交给 LLM；确定性、规则明确的环节用代码。把该用代码的地方也塞给模型，只会增加成本和不确定性。

**人工审核点加在哪。** 加在有风险或不可逆的动作之前，而不是之后。支付、删改数据、对外发送这类动作，执行前要有审核节点；只读的、可逆的中间步骤不必加。人工点的位置还决定了流程的可中断性——审核期间流程挂起，批准后继续，这些在工作流里都是显式节点。

**失败重试和 SLA。** 工作流的每个节点都能单独定义重试策略和超时。哪些节点失败可重试、重试几次、超时怎么处理，都要提前定。SLA 也一样——整条流程的耗时目标拆解到各节点，才能知道瓶颈在哪。

```python
# 伪代码：一条带人工审核和重试的工作流骨架
workflow = [
    Step("classify", handler=llm_classifier, retry=2),   # 需要语义理解，交给 LLM
    Step("load_data", handler=db_query, retry=1),        # 确定性逻辑，用代码
    Step("generate", handler=llm_report, retry=2),       # 生成报告，交给 LLM
    Step("human_review", handler=wait_for_approval),     # 副作用动作前的人工审核
    Step("send_out", handler=external_call, retry=0),    # 不可逆动作，审核后才执行
]
```

要点：LLM 节点和代码节点按任务性质分工；人工审核卡在不可逆动作前；每个节点的重试策略单独定义。`llm_classifier`、`db_query` 等 handler 是业务侧实现。这套显式定义正是工作流"可控、可审计"的来源。

## 追问逐条作答

### 追问一：Workflow 中哪些节点适合交给 LLM？

需要语义理解和非结构化处理的环节：分类、摘要、抽取、生成、内容审核的判断等。确定性的环节，比如查数据库、格式校验、数值计算、调用固定接口，用代码更合适，又快又稳又省成本。判断标准是这个节点需不需要"理解"：需要就交给 LLM，不需要就用代码。把确定性逻辑也塞给模型，只会增加成本和不确定性。

### 追问二：人工审核点应该加在哪里？

加在有风险或不可逆的动作之前。支付、删改数据、对外发送消息这类动作，执行前要有审核节点，因为做了就收不回来。只读查询、中间计算、生成草稿这类可逆的中间步骤不必加，加了只会拖慢流程、让人被无意义的确认淹没。经验值：一条流程里真正需要人工卡点通常就一两个，多了说明把可逆步骤也当成了风险点。

### 追问三：工作流如何逐步升级成 Agentic Workflow？

从个别节点引入动态性开始，而不是把整条流程推倒重来。先把某个固定节点换成"让模型决定下一步"的动态节点——比如检索节点从"固定查一次"变成"模型判断资料够不够、不够再查"。这样主体流程仍是可控的工作流，只在局部获得动态决策能力。经验值：一次只动一个节点，观察可控性有没有下降、效果有没有提升，再决定要不要继续加动态节点。逐步升级比一次性改成全 Agent 风险小得多。

### 追问四（自补）：工作流这么可控，为什么不全部用工作流？

因为有些任务的路径本来就列不全。开放式的客服对话、需要多轮探索的研究任务、要根据中间发现不断调整方向的场景，你没法提前把每条分支画出来。硬用工作流要么分支爆炸、要么覆盖不全，反而不如让模型动态决策。工作流的优势建立在"路径可预测"的前提上，前提不成立时，它的可控性就变成了僵化。

### 追问五（自补）：工作流里的 LLM 节点也要做提示词管理吗？

要，而且更要。工作流里的 LLM 节点通常职责单一，分类就只分类、摘要就只摘要，提示词相对短、边界清楚，但还是要做版本管理和回归测试。因为工作流是强可控系统，一个提示词改动导致分类结果漂移，会影响整条下游流程。前面聊过提示词版本管理和回归，那套工程纪律在这里同样适用，不因为节点简单就省掉。

## 60 秒面试回答模板

> 判断看"路径是否可预测"。业务步骤固定、输出格式明确、要强可控和易审计时，工作流比 Agent 更合适。像分类、摘要、内容审核、报告生成、表单填充、固定审批链，路径稳定，用工作流能清楚定义节点职责、失败重试、人工介入点和 SLA，适合企业里有规则、可追责、可回放的流程型任务。Agent 更适合开放任务和动态决策。设计工作流时，需要语义理解的节点交给 LLM，确定性逻辑用代码；人工审核卡在不可逆动作前；重试和 SLA 逐节点定义。要升级成 Agentic Workflow，就从个别节点引入动态决策，别一次推倒重来。不是否定 Agent，是不同任务配不同工具。

## 加分项

- 用"路径是否可预测"作为判断核心，可操作、不空泛。
- 点出工作流的可控来自节点职责、重试、介入点、SLA 的显式定义。
- 讲清 LLM 节点与代码节点的分工标准（需不需要"理解"）。
- 给出"逐步升级成 Agentic Workflow"的渐进路径，不推倒重来。

## 常见误区

- **什么都往 Agent 上套**：路径本就固定的流程用工作流更稳，硬上 Agent 只会失去可控性。
- **把确定性逻辑也交给 LLM**：查库、校验、计算用代码，交给模型只会增加成本和不确定性。
- **人工点乱加**：加在不可逆动作前才有意义，加在可逆步骤上只会拖慢流程。
