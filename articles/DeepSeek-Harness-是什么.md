# DeepSeek Harness 是什么？

## 一个月涨了一百多万日活，但它不是 Agent 产品

2026 年 8 月 13 日，DeepSeek 把一个叫 Harness 的项目悄悄开源，MIT 协议，命令行工具叫 `dsh`。没有发布会，当时也没多少人当回事。

到了 11 月初，官方公布的数据是：单日活跃用户 154 万，月活 548 万，单日 Token 消耗约 92 万亿，人均每天 261 次请求。从 9 月底桌面端发布算起，日活涨了 5 倍多，一个月增超百万。

但如果把它当成「又一个 Agent 产品」来看，会完全看错方向。

## 一句话结论

**DeepSeek Harness 不是 Agent 产品，而是一套「把模型变成 Agent」的运行时。官方给了一个公式：**

> Agent = Model + Harness

模型是脑子，Harness 是身体：工具、权限、会话记忆，还有让 Agent 持续运转的那个循环。同一颗脑子，接不同的身体，能干完全不同的活。

跟 ChatGPT 式对话产品的区别就一句：**聊天产品卖「答得顺」，Harness 卖「做得成」。**

## 先把时间线捋直

| 时间 | 事件 |
| --- | --- |
| 2026-08-13 | v0.1 开发者预览发布，MIT 开源（CLI 形态） |
| 2026-09-29 | v0.2 桌面端预览版：macOS（Apple 芯片）/ Windows x64 |
| 2026-09-30 | 日活 27.1 万（7 天日均值） |
| 2026-10-21 | 日活 113 万 |
| 2026-10-31 | Super-agent 原型开源，长在 dsh 之上 |
| 2026-11-04 | 单日日活 154 万，月活 548 万 |

生态侧的数据更值得看：第三方插件约 3.5 万个，约 59% 的活跃用户创建或使用过自定义插件。**将近六成用户不是拿它当现成产品用，而是在改它**——这个参与度是理解后面所有设计的钥匙。

两个附带数字：单日 Token 消耗较桌面端发布时涨了 306%，人均每天 261 次请求——用得越重的人粘得越紧；官方已经在筹备插件市场和插件创作者激励，生态打算长期做。

## 它解决什么问题：从买整机到自己攒机

过去用 Agent，拿到的是厂商做好的成品。厂商给它什么能力，你就用什么能力；想加个「生成 PPT」，只能等厂商排期。

dsh 的思路反过来：把 Agent 的每一项能力都拆成插件，你自己组装。**像买电脑，从「整机」变成「自己选 CPU、内存、硬盘」。**

为什么必须这么拆？因为 Agent 的能力边界一直在变：今天接个 MCP 工具、明天换个沙箱策略、后天想换掉主循环做实验。这些写死在代码里，每次都要改源码；拆成插件之后，**全变成配置变更**，不用动 Harness 一行代码。

## 一切皆插件：连主循环和界面都是插件

底层是一个叫 **Cordis** 的 TypeScript 插件框架，管插件的挂载卸载、依赖解析、服务注册、事件通信，还有卸载时的清理——插件下线时，它注册的工具、命令、UI、监听器会被一起撤销，不留残留。很多插件系统做不到这一点。

插件能提供的东西比想象中多：

- **工具**：搜索、读写文件、执行命令、浏览器
- **服务**：模型适配、会话存储、沙箱
- **事件监听**、**提示词与技能**
- **UI 模块**——界面本身也是插件

注意一个常见误解：**插件 ≠ 工具**。工具只是插件可能提供的能力之一。

所以一个运行中的 dsh，本质上是一棵插件树：启动过程就是按配置把插件逐个挂上去。没有「主程序 + 外挂」的中心结构，**连 Agent Loop 本身都是插件**。

## 配置四层：新人最容易劝退的地方

| 层 | 是什么 | 类比 |
| --- | --- | --- |
| Bundle | 官方打包的插件集合（Base / Web / Headless） | 餐厅套餐 |
| Profile | 你命名的装配方案：用哪些 Bundle、再加什么 | 完整菜单 |
| Home | 用户级配置，对本机所有 Profile 生效 | 个人口味 |
| Patch | 覆盖层，定点替换某个插件条目 | 便利贴 |

实现上就是一串有序的 `cordis.patch.yml` 文件，越靠右优先级越高。

**最大的坑在 Patch：它是「整条替换」，不是「改一个参数」。** 假设原配置是 `A = 参数1 + 参数2 + 参数3`，你想改参数 1：

```yaml
# 示意：只想改第一条，其余必须原样抄回来
tools:
  - name: web-search      # 想改的：收窄生效范围
    scope: "github.com/*"
  - name: file-edit       # 不想动，也得写
    enabled: true
  - name: shell           # 漏了它，shell 就被冲掉了
    enabled: true
```

很多配置系统允许只写改动项、其余自动保留；dsh 不行，同条目下漏写的配置会被直接冲掉。第一次配的人十个有九个栽在这里。

Patch 的能力上限也很高：可以把本地的 **Claude Code / Codex 挂成子 Agent**，可以换 UI 模块，还能用 JavaScript 表达式写规则，让某项能力只在特定仓库、特定文件类型下生效。

顺带把模型这层也说清楚，因为它同样不绑定：**DeepSeek 官方 API、任意 OpenAI 兼容端点、本地模型（Ollama、LM Studio、vLLM）**三种都行，而且不同子 Agent 可以配不同模型——例行任务挂个便宜的，难活挂最强的。这一点在 SuperAgent 的设计里已经用上了：Router 用轻量模型做分派，Worker 用强模型干活。

## Agent Preset：顶栏那四个模式

Profile 决定「环境有什么」，**Preset 决定「这个 Agent 怎么干活」**：工具集、系统提示词、技能、子 Agent 配置。界面顶部的模式选择器，选的其实就是 Preset。

| 模式 | 定位 | 适合 |
| --- | --- | --- |
| Standard | 完整编程助手：编辑、shell、搜索、计划、子 Agent、工作流 | 日常主力 |
| PTC / Code | 工具走 Code Mode SDK，模型写一段 TypeScript 编排多步调用 | 机械性多步任务 |
| Minimal | 只留终端 + 文本替换编辑器 | 基准测试、教学 |
| Creation | Standard + 运行时检视、内存里试插件、写 Preset 的指导 | 让 Agent 给自己造能力 |

两个机制值得记：**PTC 模式里，循环、条件、并发都在代码里跑，只有最终输出进上下文**，多步机械操作的成本大幅下降；**Preset 在会话有内容后会锁定**，中途切换会让历史里的工具调用无法解释。

## 会话是事件流，不是聊天记录

工作按两个单位组织：**Step** 是一次模型请求加它发起的工具调用，**Turn** 是从下任务到完成的整个运行。

每个关键位置都是插件的拦截点：step 之前、工具执行前后、模型请求之前。插件可以在这些点上批准、改写、记录、阻断——审批策略、日志、护栏全都是挂在拦截点上的东西。

更本质的区别在会话日志：**append-only 的事件流**。系统提示词、思维链、工具调用与结果、上下文注入、子 Agent 往来，模型看到什么就记什么。

这份日志直接撑起了一排功能：会话恢复（resume）、自动标题、上下文压缩、跨会话搜索，还有 Trajectory 视图——按来源逐条检视「这一步模型到底看到了什么、做了什么」。排查「它为什么会这么干」的时候，这个视图比翻聊天记录好用得多。

**fork 和 replay 操作的是同一条事件流。** fork 出一条分支换种打法，或者 replay 复现当时的状态。聊天记录是给人看的文本，事件流是可重放的状态——这是「能重跑一遍当时发生了什么」和「翻聊天记录」之间的差距。

## 安全：四层，别跳过任何一层

Agent 能改文件、能跑命令，安全不是可选项：

| 层 | 做法 |
| --- | --- |
| 沙箱 | 三档：read-only / workspace-write / danger-full-access，用操作系统原生隔离（Linux 的 bwrap、macOS 的 Seatbelt、Windows 的受限令牌），并如实报告隔离是否真的生效 |
| 审批 | 风险操作先问人，严格程度由 Preset 的策略等级决定 |
| 护栏 | 插件形式：超时工具会被中断，重复循环会被识别 |
| 密钥 | 凭据走独立通道，日志里只有引用，不落明文 |

官方 README 的两条建议照做能避开大部分事故：**先在版本控制下的项目里试**（出问题至少能回滚），动手前**先读一遍 SAFETY.md**。`danger-full-access` 是真实存在的档位，不是吓唬人的。

隐私上有三点要有数：用 DeepSeek 模型时，提示词、文件内容、命令输出都会发到 DeepSeek 的服务，官方政策称数据存境内、除主动退出外可能用于训练；换本地模型可以让推理留在本机，但网页搜索默认仍走 DeepSeek；桌面端会发送使用事件（不含提示词正文）。**企业数据先过一遍隐私政策再上。**

## 五种接入方式，两类兼容层

| 方式 | 适合谁 |
| --- | --- |
| Web UI | 大多数人：本机浏览器界面，聊天、审批、切模式 |
| Headless CLI | CI / 脚本，跑完一个任务就退出 |
| Python SDK | 做集成的团队，`pip install deepseek-harness-sdk` |
| TypeScript SDK | 深度集成，直接走 JSON-RPC |
| ACP Server | 编辑器 / 工具厂商 |

两个兼容层很实用：任何 **MCP Server** 接进来，和内置工具走同一条管线；Claude Code / Codex 的 **hook 脚本**可以继续用。

实际用起来是分场景的组合：日常在 Web UI 里对话、审批、切模式；CI 里用 headless 跑「修一个 lint 报错就退出」这种一次性任务；要做进自家产品，就走 SDK 把运行时整个嵌进去。桌面端则是不想装 Node 的人的入口——官网下载安装包，登录账号，选工作区就能用。

## 和 Claude Code / Codex 差在哪

| 维度 | Claude Code / Codex | DeepSeek Harness |
| --- | --- | --- |
| 交付物 | 做好的 Agent | 可组装的运行时 |
| 能力边界 | 厂商定义 | 配置定义，可换可删 |
| 模型 | 绑定自家 | DeepSeek / 其他托管商 / 本地模型（Ollama、vLLM） |
| 主循环与界面 | 固定 | 插件，可替换 |
| 会话 | 记录 | 事件流，可 fork / replay |
| 与对方的关系 | — | **可以把对方挂成自己的子 Agent** |
| 许可 / 成熟度 | 专有、稳定 | MIT、开发者预览 |

它不是成熟产品的「平替」，是错位竞争：**不跟 Claude Code 抢位置，而是站在它们上面一层**——需要稳定交付时把活委派给 Claude Code，需要自己做实验时换掉任何部件。

## 和 SuperAgent 是什么关系

之前写过 SuperAgent 的架构（Router / Worker 双层调度那套）。关系其实是：

1. **dsh 是底座**：插件化的 Agent 运行时
2. **Super-agent 是长在它上面的插件包**，把双层调度、事件订阅、存算分离做成一个可安装的 bundle
3. 所以 SuperAgent 的安装命令才会是 `dsh plugin --profile superagent add ...`——它就是个插件

SuperAgent 不是另一个产品，是「dsh 能长出什么」的一个官方样例。

## 现在上手要知道的坑

- **仍是开发者预览**：README 明写会有破坏性变更，插件 API 还在演进
- **概念门槛**：Bundle / Profile / Home / Patch / Preset 五层，第一次配容易绕晕
- **插件即权限**：3.5 万个第三方插件，质量参差，装一个等于给它开口子
- **默认走云**：换本地模型可以，但网页搜索等能力仍依赖 DeepSeek 服务

想试的话，最小路径：装 Node.js（22.19+），`npx @deepseek-ai/dsh web` 打开 127.0.0.1:3080，填 API Key，**选一个练习目录当工作区**（别挂整个用户目录），先跑一个可验收的小任务——比如让它建一个 `notes/hello.md`，验收标准不是「它说完成了」，而是磁盘上真有文件、轨迹里真有工具调用。

## 为什么 DeepSeek 要做这个

官方没讲商业动机，这里是我的解读，仅供参考。

卖模型 API 的公司做开源 Harness，逻辑和云厂商做开源运行时一样：**运行时是模型的消耗入口**。单日 92 万亿 Token 里有多少流经 dsh，官方没拆，但人均每天 261 次请求的重度使用，说明它已经是一个稳定的消耗场景。

更关键的是生态位。Agent 这个层面的竞争，目前是 Claude Code、Codex 这些「成品」在抢用户；dsh 不抢这个位置，它把自己做成**所有成品的下游**——可以把它们挂成子 Agent，也可以把它们换掉。谁定义了「Agent 是怎么组装的」，谁就站在了成品的上面一层。插件市场还没上线，但 3.5 万个第三方插件已经先长出来了。

## 结语

如果只记一件事，记这个：**dsh 把「Agent 的能力边界」从厂商的代码，挪到了用户的配置里。**

六成活跃用户在改自己的 Agent，一个月涨百万日活，说明这不是极客玩具的需求。真正的悬念在后面：插件 API 还在破坏性变更期，官方插件市场还没落地，供应链安全没有答案——这套「一切皆插件」能不能撑住 154 万日活之后的世界，才是接下来值得盯的。
