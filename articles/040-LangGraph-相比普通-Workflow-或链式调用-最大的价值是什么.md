# LangGraph 相比普通 Workflow 或链式调用，最大的价值是什么？

## 面试官为什么爱问这题

这是必刷题，考的是你有没有"什么时候该上复杂工具"的判断力。很多人把所有流程都往一种写法上套：能跑通就行，直到系统里开始冒出"要不要继续查、什么时候结束、失败从哪恢复、状态怎么跨轮保留"这些问题，才发现原来的写法扛不住了。面试官问"最大的价值"，真正想听的是你能不能说清图编排解决的到底是什么痛点——它不是把同样的东西换种写法写一遍，而是把原本藏在代码执行顺序里的控制流，变成看得见、能单独改、能追踪、能恢复的显式结构。前面讲状态、节点、边三件套时已经把图长什么样拆开过，这一篇不看三件套本身，专门看"为什么非得是图"这个选择题。

## 一句话先给结论

**LangGraph 最大的价值，是把复杂流程里的状态、节点、边和循环显式表达出来，让模型驱动的动态流程变得可设计、可追踪、可恢复。链式调用适合简单串行，Workflow 适合固定路径，图编排适合有分支、有循环、要人工中断、要状态持久化、要多 Agent 协作的任务。判断信号很具体：当你开始纠结"要不要继续、什么时候停、失败从哪恢复、状态怎么跨轮保留"这四件事时，就是图编排该上场的时候。**

## 核心原理：从隐式控制流到显式图

### 三种写法解决的是三种确定性

把三种方式放在一条轴上看，区别在"下一步去哪"这件事由谁决定。

链式调用里，下一步在写代码时就定死了：`a | b | c`，顺序执行，没有回头路。它适合那种输入输出一条道走到黑的简单串行任务，好处是极简，坏处是一旦需要"根据结果决定下一步"就得往链里塞判断逻辑，很快变乱。

Workflow 里，路径也是人事先定好的，只是多了分支：条件 A 走这条、条件 B 走那条。它适合固定路径、要求确定的场景，缺点是所有可能的路径都得提前画出来，遇到模型在运行时才能决定的动态分支就很别扭。

图编排里，循环和分支都是一等公民。下一步可以是模型根据当前状态决定的，也可以绕回前面的节点再来一轮，还可以在某个节点暂停等人审批。它解决的正是前两种写法扛不住的那类任务：路径不完全可预测、要来回迭代、要跨轮保留状态。

| 维度 | 链式调用 | Workflow | 图编排 |
| --- | --- | --- | --- |
| 下一步谁决定 | 写代码时定死 | 人事先编排的分支 | 可由模型按状态动态决定 |
| 循环回退 | 不支持 | 通常不自然 | 一等公民，可绕回节点 |
| 人工中断 | 没有 | 较难插入 | 可在节点处暂停恢复 |
| 状态持久化 | 无 | 靠外部自己管 | 节点间可存状态，支持恢复 |
| 适用任务 | 简单串行 | 固定路径、要求确定 | 分支、循环、多 Agent、长任务 |

### "显式"二字带来的三个实际收益

把控制流从隐式变显式，不是审美问题，会实打实改变三件事。

**可设计。** 每一步是一个节点，节点之间怎么走是一条边，"下一步去哪"不再藏在 `if` 的嵌套和函数的执行顺序里，而是一张看得见的图。想插入一个审批节点，就加一个节点、改两条边，不用通读整段循环找该改哪里。前面讲三件套时说过，图难维护往往不是图复杂，而是把隐式逻辑塞进一个节点；反过来，图结构清晰时，改一处是局部的。

**可追踪。** 因为节点是明确的边界、状态是可序列化的数据，每个节点执行前后都能记录状态快照。出了问题能定位到具体是哪一步、当时的输入是什么，而不是对着一整段循环打日志猜。这对长任务尤其关键——跑错的往往不是第一个节点，而是第几轮之后的某次迭代。

**可恢复。** 在节点之间把状态存下来，就能做到中断后从断点继续、出错后重放某一步。裸循环里这些都要自己造轮子，而且得自己处理"状态存在哪、怎么序列化、断点在哪"这些细节。图编排把它们做成了基础设施。经验值：长任务（比如要跑很多轮的研究、批量处理）是否值得上图，很大程度就取决于"中断恢复"是不是硬需求——是的话，图的收益通常能盖过它的复杂度。

### 四个信号：什么时候该上图

面试官爱听的就是这种可落地的判断信号。下面四个问题，链和 Workflow 都得自己想办法，在图编排里却是一等公民：

| 信号 | 具体表现 | 为什么链 / Workflow 扛不住 |
| --- | --- | --- |
| 要不要继续 | 模型根据中间结果决定再查一轮还是收手，比如判断"资料够不够回答" | 链的路径写死，分支必须提前列全 |
| 什么时候结束 | 停止条件是运行时反复判断的结果，不是固定的一步 | 链走完就停，没有动态判停的位置 |
| 失败从哪恢复 | 任务长、步骤多，出错不能从头再来，要从断点续跑 | 链没有中间状态快照，只能整条重跑 |
| 状态怎么跨轮保留 | 多轮之间共享一份不断更新的上下文 | 链不跨轮保存状态，得在外部自己管 |

出现其中任意一条，就该认真考虑图编排。

## 工程实践：从链迁移到图的判断过程

假设你有一条链：`检索 → 生成 → 输出`，跑起来发现两个问题——检索结果经常不够，模型却照样硬答；偶尔某步失败，只能整条重跑。怎么改成图？

先识别出需要动态决策的点。"检索够不够"是运行时判断，把它做成一个条件边：检索后先评估，够了就走生成，不够就绕回检索并改写查询。这一步在链里做不到，在图里就是一条回边。

再想状态。把"已检索的查询""检索结果""是否达到停止条件"这些跨节点要用的东西放进状态里，让每个节点读写它。这样绕回检索时，之前检索过什么还在，不会重复。

最后加恢复。在节点之间存一次状态，失败后就能从最后一个成功的节点继续，而不是从头跑。

```python
# 伪代码：一个"检索—评估—生成"的最小图骨架
from langgraph.graph import StateGraph, END

# state 是带字段的状态类型，retrieve / grade / generate 是已定义好的节点函数
graph = StateGraph(state_schema=state)
graph.add_node("retrieve", retrieve)
graph.add_node("grade", grade)
graph.add_node("generate", generate)

graph.set_entry_point("retrieve")
graph.add_edge("retrieve", "grade")

# 条件边：资料够就生成，不够就绕回 retrieve 再查一轮
graph.add_conditional_edges(
    "grade",
    route_after_grade,            # 返回 "generate" 或 "retrieve"
    {"generate": "generate", "retrieve": "retrieve"},
)
graph.add_edge("generate", END)

app = graph.compile(checkpointer=checkpointer)   # checkpointer 负责状态持久化
```

几个要点：条件边的判断函数 `route_after_grade` 返回什么字符串，就走哪条分支，这让"要不要继续查"变成了一条看得见的边；`checkpointer` 让状态能跨轮保存、支持断点恢复。变量 `state`、`retrieve`、`grade`、`generate`、`route_after_grade`、`checkpointer` 都标为业务侧自定义，真实项目里按自己的数据和逻辑实现即可。

迁移的代价也要认：图的代码量和概念负担都比链高，能简单就别复杂。判断标准就是前面那四个信号——没有这些需求，一条链老老实实跑完更省心。

## 追问逐条作答

### 追问一：LangGraph 和 Agent 的关系是什么？

不是一个层面的东西。Agent 是一种系统形态——模型能决策、能调工具、能根据结果继续或停止；LangGraph 是实现这种系统的一种框架，尤其擅长把 Agent 里那些分支、循环、状态、人工中断显式搭出来。简单说，Agent 是要造的东西，LangGraph 是拿来造它的工具之一。你完全可以用裸循环写一个 Agent，只是当它变复杂时，图会让控制流更好管。

### 追问二：什么场景下普通 Workflow 就够了？

路径固定、步骤确定、不需要模型在运行时决定下一步走向时，Workflow 更稳也更简单。比如固定的数据清洗流水线、固定的审批流程、输入输出格式确定的批量任务。这类场景的动态性不强，上图只会引入不必要的复杂度。判断标准是：如果所有分支都能在写代码时列清楚，Workflow 就够。

### 追问三：图编排的维护成本会不会更高？

会，这是实话。图多了节点和边的概念，要理解状态怎么流转、条件边怎么判、检查点怎么存，学习成本和代码量都比链高。所以不能因为"听起来更强大"就上图。正确的取舍是：简单任务用链，固定路径用 Workflow，只有当分支、循环、人工中断、状态持久化这些需求真的出现、且裸写法开始难以维护时，图的成本才被它的收益抵掉。经验值：一个只有三五个固定步骤的流程，通常不值得上图。

### 追问四：图编排和可观测性、恢复能力是怎么联系起来的？

正因为节点是明确边界、状态可序列化，才能在每个节点前后记录状态快照，才能把状态存到检查点里支持断点恢复。可观测和恢复不是额外加的功能，而是"显式图 + 可序列化状态"这个设计的自然结果。裸循环里想做同样的事，得自己在每个步骤手动埋点、手动存状态，既容易漏又不统一。

### 追问五：说图适合多 Agent 协作，具体指什么？

指多个角色各自作为节点或子图，共享一份状态、按图的拓扑依次或并行工作。比如一个研究型任务里，规划、检索、写作、审校是不同角色，谁先谁后、什么条件下交给下一个、结果怎么汇总，都能在图上表达。相比让几个 Agent 在一个大循环里互相调用，图的拓扑是看得见的，职责边界更清楚。

### 追问六：如果你的系统现在是链式调用，怎么判断该不该重构到图？

看有没有开始为"动态决策"打补丁。如果链里出现了越来越多的 `if` 判断下一步、开始手动在外部存中间状态、失败只能整条重跑，这些都是信号。真要重构时不用一次全改——先把最需要动态决策的那一段（比如"检索够不够"）单独做成子图，其余保持链式，逐步迁移。

## 加分项

- 把三种写法放到"下一步由谁决定"这条轴上比较，而不是泛泛说谁更好。
- 明确图的三个收益（可设计、可追踪、可恢复）都源于"控制流显式化"这一个根。
- 主动认维护成本更高，给出"先局部做子图再逐步迁移"的务实路径。
- 用四个具体信号回答"什么时候上"，落到可判断的标准。

## 常见误区

- **把图说成链式调用的替代品**：它解决的是动态、有环、要恢复的任务，简单串行用链更省心。
- **混淆 Agent 和 LangGraph**：Agent 是系统形态，LangGraph 是实现框架，不是一个层面。
- **只夸收益不认成本**：维护成本更高是事实，答时主动认并给出取舍标准，比一味吹图更可信。
