# 多用户场景下，如何为 Agent 做安全沙箱隔离？

<!-- growth-hook:v1 -->
多用户场景下，光靠“工具权限”四个字已经兜不住了。用户会不会越权访问别人的数据、Agent 会不会被诱导执行危险操作——这题要的是从执行环境这一层就把边界立住。

## 面试官为什么爱问这题

这题高频且偏难，考的是你有没有从单机 Demo 思维切换到多用户生产思维。单机跑 Agent，风险不暴露——反正就你一个人用；一旦多用户共享，一个用户能不能碰到另一个用户的数据、一个 Agent 会不会读到宿主机的凭据，就成了硬问题。面试官想听的是你能不能把安全从"工具权限"上升到"执行环境隔离"，讲清环境、系统、应用三层的具体做法，以及协议层控制和环境层隔离的分工。前面聊过 MCP 的权限检查要和环境沙箱配合、也聊过给 Agent 行为划边界，这一篇深入"多用户场景怎么做隔离"这个具体问题。

## 一句话先给结论

**单机 Demo 里很多风险不会暴露，一旦进入多用户场景，安全隔离必须从"工具权限"上升到"执行环境隔离"。更稳的方案分三层：环境层用 Docker 或其他容器把每个任务或租户隔开，限制 CPU、内存、网络和文件系统访问范围；系统层配合 seccomp、AppArmor、只读根目录、临时工作目录、非 root 用户运行，避免直接碰宿主机；应用层对工具、文件访问、系统命令、外部连接做白名单和审计，不让模型拿到裸权限。MCP 或 Tool 负责"能不能调"，沙箱负责"即使调了也跑不出边界"，职责不同，最好一起上。**

## 核心原理：三层隔离

### 环境层：容器隔开

用 Docker 或其他容器技术，把每个任务或租户隔离到独立环境。限制 CPU、内存防止一个任务拖垮整机；限制网络和文件系统访问范围，让它只能碰到该碰的。这是最基础的一层——把一个用户的工作和另一个用户、和宿主机隔开。

### 系统层：加固容器内部

光有容器还不够，容器内部也要加固：用 seccomp、AppArmor 限制能调用的系统调用；根目录挂成只读、工作目录用临时目录；用非 root 用户运行，避免容器内的高权限进程突破边界。这一层的目标是"即使容器里有恶意行为，也碰不到宿主机"。

### 应用层：白名单与审计

对工具、文件访问、系统命令、外部连接做白名单和审计。只开放必要的工具、必要的路径、必要的外部连接；所有访问留痕。这一层是业务语义上的控制——环境层管"能访问哪些资源"，应用层管"这个任务该不该访问这个资源"。

| 层 | 核心手段 | 防什么 |
| --- | --- | --- |
| 环境层 | 容器、CPU/内存/网络/文件系统限制 | 租户之间互相干扰、碰宿主机 |
| 系统层 | seccomp、AppArmor、只读根目录、非 root | 容器内突破边界 |
| 应用层 | 工具/文件/命令/连接白名单与审计 | 业务语义上的越权 |

三层分别对应不同的失效模式，理解这一点才知道每层为什么都不能省、缺了会出什么事：

| 失效场景 | 哪层拦住 | 只靠其他层会怎样 |
| --- | --- | --- |
| 用户 A 读到用户 B 的数据 | 环境层隔离 | 应用层权限判断有漏洞就拦不住 |
| 容器内进程访问宿主机文件 | 系统层加固 | 容器本身挡不住容器内提权 |
| Agent 调用了不该调用的业务工具 | 应用层白名单 | 沙箱不知道哪个工具业务上不该用 |

### 关键：最小权限的工作空间

如果要执行代码、命令或读文件，通常不会只靠 Prompt 或业务代码做限制——软限制挡不住决心越界的行为。做法是把工作目录挂成最小权限空间：只挂载任务需要的目录，敏感目录不挂载；数据库密钥、主机凭据不进容器。这样即使 Agent 在容器里"乱来"，它能碰到的也只有那块被严格限定的空间。

### 职责分工：协议层控制 vs 环境层隔离

这是这题的一个关键考点。MCP 或 Tool 负责"能不能调"，这是应用层的准入判断，决定 Agent 有没有权限发起某个操作；沙箱负责"即使调了也跑不出边界"，这是环境层的强制隔离，决定操作就算被执行也造成不了越界影响。两者职责不同，不是二选一。

前面讲 MCP 接入时说过权限检查要和环境沙箱配合、讲行为边界时说过软约束要靠硬约束兜底，这里是同一结论落到多用户场景：只靠工具权限，一旦权限判断有漏洞或工具本身有 bug，Agent 就能碰到不该碰的资源；只靠沙箱，又缺少业务语义上的准入控制。两者一起上，才构成纵深防御。

## 工程实践：一个任务的执行环境怎么配

落到配置上，一个多用户 Agent 任务的执行环境大致这样：

```yaml
# 伪代码：一个任务容器的隔离配置示意
container:
  image: agent-sandbox:latest
  user: "1000:1000"                 # 非 root 运行
  read_only_root_fs: true           # 根目录只读
  tmpfs: ["/tmp"]                   # 临时工作目录
  volumes:
    - "/task/workspace:/workspace:rw"   # 只挂本任务工作区
    # 敏感目录不挂载，凭据不进容器
  security_opt: ["seccomp=profile.json", "apparmor=agent-profile"]
  resources:
    cpu: "1"
    memory: "1g"
  network: "restricted"             # 限制网络访问范围
```

要点：非 root、只读根、临时目录、只挂最小工作区、安全配置、资源限制、网络限制。每一项对应前面的一层——这是"最小权限工作空间"的具体化。实际情况按你的平台和任务调整，这里只示意思路：让 Agent 能干活，但干不出这个框。

## 追问逐条作答

### 追问一：为什么多用户场景必须做执行环境隔离，光靠工具权限不够？

因为工具权限是应用层的软判断，可能被绕过——权限逻辑有漏洞、工具本身有 bug、模型被注入诱导，都可能让越权发生。执行环境隔离是系统层的硬边界：即使越权调用真的发生，沙箱也让操作跑不出限定范围。多用户场景里，一个用户碰到另一个用户的数据是不可接受的事，不能把安全押在"权限判断一定正确"上。所以要纵深防御，两层一起上。

### 追问二：环境层、系统层、应用层三层分别解决什么？

环境层解决租户和宿主机的隔离，用容器把每个任务隔开、限制资源访问；系统层解决容器内的加固，用 seccomp、AppArmor、只读根目录、非 root 防止容器内突破边界碰宿主机；应用层解决业务语义的准入，对工具、文件、命令、连接做白名单和审计。三层从外到内、从资源到语义，层层收窄。

### 追问三：为什么凭据不能进容器？

因为容器是 Agent 执行不可信代码的地方。如果把数据库密钥、主机凭据放进容器，一旦 Agent 被执行代码有漏洞、或被诱导读取环境，凭据就泄露了——拿到凭据就能绕过所有隔离访问外部系统。正确做法是把凭据留在容器外，通过受控的方式提供最小必要的访问能力，而不是把钥匙直接给到不可信环境里。

### 追问四（自补）：seccomp 和 AppArmor 在这套方案里起什么作用？

它们是系统层的加固手段，限制容器内进程能做什么。seccomp 限制能调用哪些系统调用——砍掉用不上的危险调用；AppArmor 限制进程能访问哪些文件、能执行哪些操作。它们和容器配合：容器提供隔离边界，这些工具进一步缩小容器内部的活动空间。即使容器里的进程想做越界操作，也会被这些策略拦下。

### 追问五（自补）：沙箱会不会影响 Agent 的能力？

会有一定限制，但这是安全的必要代价。关键是"最小够用"，只限制不必要的访问，保留完成任务需要的能力。比如只读挂载敏感目录、但给任务一个可写的临时工作区；限制网络但开放必要的 API 端点。经验值：按任务类型设计不同的沙箱策略，纯文本处理可以限制得很死，需要执行代码的任务适当放宽，别用一套策略套所有场景。

### 追问六（自补）：沙箱的生命周期怎么管？

用完即弃，别复用。一个任务一个沙箱，任务结束就销毁，工作目录里的临时数据一并清理。这样能避免跨任务的状态残留，比如上一个用户任务留下的文件被下一个用户看到，那是典型的多租户泄露。经验值：设沙箱的最大存活时间，即使任务卡住也能自动回收；销毁时确认临时目录和挂载都被清理干净。另外审计要跟上——每个沙箱对应哪个用户、哪个任务、执行了什么，都要留痕，出事能追到具体那次执行。环境隔离管"跑不出边界"，生命周期和审计管"不留后患、出事能查"，两者配合才是完整的多用户安全。

## 常见误区

- **只靠工具权限**：软判断可能被绕过，多用户场景必须有硬隔离。
- **把凭据放进容器**：Agent 执行不可信代码的环境里不能放密钥。
- **混淆协议层和环境层**：一个管能不能调，一个管即使越界了也跑不出去，两者职责不同、互为补充，只做一层就留有缺口。
