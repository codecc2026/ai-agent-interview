# Super-agent 五模块架构拆解：让 Agent 从「单次会话」走向「持续在线」

## 这篇文章在讲什么

DeepSeek Harness 团队最近发了一篇《Super-agent 设计探索：迈向更自主的 Agent 系统》。它不像产品宣发稿，更像系统设计复盘：当单任务 Agent 已经能稳定交付之后，**瓶颈为什么会从「模型能不能干」转移到「人顾不顾得过来」**。

原文近万字。本文把它压成工程视角的骨架，并补上我自己的判断：哪些今天就能抄，哪些要看团队规模，坑在哪。

## 一句话先给结论

**想让 Agent 同时具备连续、高效、主动、持久四个特征，单个 ReAct 循环是不够的，必须在系统层补五个模块：双层路由、事件驱动、异步全双工交互、计算—状态—环境分离、独立 Watchdog。它们本质上都是把计算机系统的经典思想搬进了 Agent 系统设计。**

## 瓶颈为什么转到了人身上

过去一年的进展有一条清晰的曲线：模型能稳定用工具解决复杂问题，人类逐步退出逐步骤干预。但主流的 Agent 形态仍然**以单次 Session 为基本单位**，Session 之间彼此隔离。一个人通常只能同时跟进 **3 到 5 个活跃 Session**，超过这个数就得手动切换、自己记住「哪个会话里说过什么」。于是出现一个很不对称的结论：

> 单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

用 CLI、MCP、外部连接器给本地 Agent 打补丁并不能解决根问题——单会话同步阻塞、多任务上下文混杂、设备离线即停。真正的出路是**把 Agent 从一次手动会话里解放出来**，变成一个跨会话保持上下文、多任务并行且互不干扰的连续实体，这就是 Super-agent。它要满足四个特征：

- **连续**：在 IM、GitHub 评论等任意界面交互，感觉始终只有一个 Agent；
- **高效**：不用等上一条跑完就能接收新指令；
- **主动**：持续观察环境事件，值得处理就推进，不需要介入时保持安静；
- **持久**：始终在线，遇异常自动恢复。

## 模块一：双层架构，连续性与吞吐量的分工

第一个要面对的取舍是：所有事件进同一个 Session，上下文最连续但串行执行、吞吐低；每个事件各开一个 Session，并发最高但结果割裂、多个 Session 同时回应用户会乱。解法是拆分职责：

- **Router 层**：常驻的全局路由层，承接所有人类交互，充当全局的序点与记忆。它**不直接执行任务**，甚至可以不给 Bash 工具，实践中用较轻量的模型往往就够。
- **Worker 层**：上下文隔离、挂载完整工具、一次只专注一个任务的执行会话，通常配能力最强的模型。Worker 不直接对人说话，只向 Router 汇报。

单常驻 Router Session 之所以不容易成为瓶颈，是因为**批处理**：上一轮推理期间到达的 Trigger 会积压并合并到下一次 LLM 调用，Prefill 阶段并行计算，请求耗时增长远慢于 batch 规模。规模再往上可以按业务线把 Router 水平切分，但切得越细全局上下文连续性越低——在「全局记忆」被真正解决之前，这个权衡一直在。

把两级过滤与订阅直通串起来，主干逻辑其实很短：

```python
def on_event(e):                       # 环境事件入口
    policy = fast_path(e)              # 确定性准入：来源 / 群组 / 白名单，无需 LLM
    if policy == IGNORE:
        return
    if policy == HANDLE_NOW and not semantic_need(e):   # Slow Path：LLM 语义判断
        return
    tid = thread_of(e)                 # 同一 PR / 话题 / 邮件串 = 一条 Thread
    if (w := subscribed_worker(tid)) is None:           # 冷启动
        w = router.dispatch(e)         # Router 创建 Worker，不亲自执行
        subscribe(w, tid)              # 建立订阅，后续事件直通
    else:
        w.send(e)                      # Fast Path：绕开 Router 直达 Worker
```

## 模块二：事件驱动，让 Agent 自己动起来

驱动 Agent 的输入从「人逐条敲提示词」变成「环境半结构化事件」，这类事件叫 **Trigger**。围绕它有四个机制值得记：

**两级过滤（Fast Path / Slow Path）**。真实群聊里绝大多数消息不需要 Agent 介入，全丢给模型判断成本扛不住。先用确定性策略按来源、群组、白名单做准入滤掉噪音，通过的候选事件才交给 LLM 做语义判断；语义层策略本身就是一个用自然语言随时改的扩展点。

**Thread 订阅与直通**。同一个 PR、同一个 IM 话题、同一封邮件串下的连续事件构成一条 Thread。初始事件经 Router 冷启动并创建 Worker 后，该 Worker **直接订阅这条 Thread**，后续事件由程序直通过去，不再绕 Router。Thread 与 Worker 是多对多关系，多个 Worker 订阅同一 Thread 时会同时收到事件，因而无需点对点通信就能察觉彼此的改动并自行消解冲突。作者的实验也印证了这套调度：每次约 300 条消息（其中约 20 条是真实工作请求）、重复 5 次，Super-agent 的任务完成时间 p50 为 **12.4 分钟**、p95 **15.7 分钟**；只用 Subagent 工具的单 Session 在中性提示下 5 次里 1 次都没委派，p95 拉到 **29.5 分钟**。差距不来自模型，来自**分配动作是写在系统结构里，还是赌模型临场判断**。

**Inline & Spill 与链式召回**。上下文窗口要当 Cache 管：很可能用到的信息直接内联（Inline），长内容和低频信息留在窗外、只留引用或摘要（Spill），按需再召回。把这个规则一致地用到 Trigger、Thread、Worker 等对象上——每个对象发 ID，注入时内联关联对象的 ID——就形成一张引用图，模型可顺着引用**逐跳展开上下文**，即链式召回。一句话：**浪费上下文窗口，就是浪费模型的智能。**

第四个机制是**投机执行**：拿到环境信号先在后台试。群里有人反馈问题就静默复现并找修复方案，确认能修且方案简单才把 PR 递上来，否则全程安静。用后台算力换人的等待时间。

## 模块三：全双工交互与信道适配

经典 ReAct Loop 里同步的 `run()` 会阻塞整个循环，工具跑完之前会话对任何新输入无响应。改法是把耗时工具换成异步的 `start()` / `stop()`：调用即返回「已启动」，后台完成后结果作为新事件回投，模型也可主动 `stop()` 掉跑太久的任务。

同时输出要匹配信道带宽：IM 走低打扰路线，只在需要决策或验收时通知，给一条硬性约束——**单次回复不超过 100 词**；GitHub、邮件、文档这类异步信道反过来，要结构化、高信息密度，写清楚背景、改动与验证结果。

## 模块四：计算、状态、环境的三层解耦

本地 Agent 默认把三样东西绑在同一台机器上：推进循环的计算、要持久保存的会话状态、代码仓库与工具链构成的执行环境，机器一休眠 Agent 就停。

分两步拆：**先分离计算与状态**——Agent Loop 放进云端无状态容器，Session 状态入库，容器可随时扩缩、重启、替换，连续性交给存储；**再分离计算与环境**——真实工作环境留在原地（未提交的改动、私有凭据、内网依赖），端侧只留一个不保存会话状态的轻量 daemon，仅负责执行命令与返回结果，即 BYOM（Bring Your Own Machine）。这样 Agent 可以在多台设备间切换，甚至能在某台设备重新上线后自动补跑那里才能做的任务。

## 模块五：Watchdog，主系统之外的控制回路

长期运行的分布式系统很难只靠自身逻辑保证可靠，需要主系统之外的独立 Control Loop。Agent 系统还有一层特殊性：很多异常不是进程崩溃，而是**模型陷入无效循环或偏离目标**，所以要同时监控进程存活和任务进展。

做法是配一个独立的 Watchdog Session，用定时消息驱动，除处理接口报错与状态恢复失败外，还由模型判断各 Worker 是否有实质进展、方向有没有偏。它本身也带完整工具，维护者可以直接问它故障原因，或让它在线改提示词、调整触发规则。

## 速查表：五个模块各自解决什么

| 模块 | 解决的核心问题 | 可直接抄的做法 | 落地成本 |
| --- | --- | --- | --- |
| 双层路由 | 上下文连续 vs 并发吞吐 | Router 只做分派不干活，轻量模型；Worker 隔离配置强模型 | 中 |
| Thread 订阅直通 | 全局节点过载 | 冷启动后 Worker 直接订阅 Thread，后续事件绕开 Router | 低 |
| 两级事件过滤 | 高噪音低触发 | 确定性策略做 Fast Path，LLM 语义判断做 Slow Path | 低 |
| Inline & Spill | 上下文窗口浪费 | 每个对象发 ID，内联下一跳 ID，长内容截断留续读口 | 中 |
| 异步 ReAct | 前台被后台任务阻塞 | 耗时工具改 `start()` / `stop()`，结果作为事件回投 | 中 |
| 存算分离 + BYOM | 设备离线即停 | 云端无状态容器 + 状态入库，端侧只留轻量 daemon | 高 |
| 外部 Watchdog | 静默跑偏不自愈 | 独立 Session 定时巡检，既查进程也查任务进展 | 中 |

## 我的判断：谁该抄，怎么抄

先给一个自测：

| 现象 | 是否已有必要上双层 |
| --- | --- |
| 一个会话里同时跑 ≤2 件事，出问题能手动重启 | 不必，先把 Worker 内的单任务质量做好 |
| 经常 3 个以上并行任务、需要跨 IM / GitHub 连续推进 | Router + Thread 订阅已经值得做 |
| 要求 7×24 在线、任务中断要自动恢复 | 必须先做存算分离和 Watchdog |
| 接入了公开群聊、外部 PR 等不可信输入 | 先把沙箱和凭据隔离补齐，再谈自动化程度 |

落地顺序我建议分三段，**不要一上来就做云端迁移**：

1. **先在单机上做角色分离**：对外交互与执行拆成两层，Worker 不直接回人；耗时工具改异步。几乎不需要基础设施投入，收益最明显。
2. **再接事件源**：从最确定的一条 Thread 开始（比如某个仓库的 PR），加程序层白名单 + 订阅直通，观察 LLM 判别准确率后再放宽到群聊。
3. **最后才上云**：状态入库、端侧 daemon、Watchdog。这一步解决「持久」，但也放大安全边界——云端一旦被提示词注入攻破，所有连着的设备都危险。

一句话：**越靠前的模块越便宜越该做，越靠后的模块越贵，越要看业务真的需要。**

## 还没解决的问题

作者列了四条开放问题，我认为这也是衡量这套架构成熟度的坐标：**Router 何时该水平切分、粒度如何定**（跨月尺度的长程记忆仍是主要瓶颈）；**Session 不再是用户心智之后，人机界面会长什么样**（很可能走向领域特化界面，比如直接在 Issue / PR 里工作）；**多个隔离实例之间的 A2A 协作**如何保证权限边界；以及**安全与隐私**——终极目标是让 Agent 在完全不接触凭据的情况下使用凭据。

## 结语

这篇文章最有价值的地方不是提出新概念，而是把计算机系统的经典思想——Fast/Slow Path、局部性与 Cache、投机执行、存算分离、Control Loop——挨个搬进了 Agent 系统设计。具体实现会变，但「**系统接管会话管理与上下文同步，人上移到决策与验收**」这条方向我认为是稳的。
