# 文本切块应该怎么设计？有哪些常见坑？

## 一句话先给结论

**切块的目标不是「切得均匀」，而是让每个块在脱离原文之后，仍然是一个对检索有意义的语义单元：边界沿文档结构走、块内补回上下文、表格等特殊元素整体保护、固定长度只做兜底；而切块过碎、丢标题层级、重叠不足、脏文本、表格打散、多主题混块这六个常见坑，根因是同一件事——语义单元被切坏了。**

## 面试官为什么爱问这题

在 RAG 的八环链路里，切块是唯一一环「纯数据工程」：不调模型、不写 prompt，却直接决定系统上限。第 15 篇说过，线上效果差大多卡在解析、切块、检索相关性三处——切块占其一，而且是其中最容易被低估的一处，因为它看起来太简单了：一段十行的循环代码，谁都能写出来。

正因为门槛低，它成了最好用的筛子。demo 语料是干净的分章节 Markdown，怎么切都对；生产语料是 OCR 扫描件、图文混排 PDF、一份连标题层级都没有的合同——六类坑全是这时候冒出来的。这题问得密、难度不算高，但被它筛掉的人不少，因为它查的不是会不会调 API，是数据这一层的基本功。

上一篇（第 15 篇）从流水线视角给过一张四策略对比表和一段标题边界切块代码，那是概览；这里把切块单独放大，讲设计流程怎么走、六个坑各是什么症状怎么防、切得好坏怎么量化——不重复那四种策略的取舍论证。

## 核心原理：一道「保语义」的设计题

### 切块同时在为两个消费者服务

一个块切出来，下游有两个读者。第一个是 embedding 模型，它把整块压成一个向量——块内主题必须单一，多个主题混在一件，向量就成了几个主题的「平均值」，哪个主题来查都「有点像但都不够像」，这就是常说的「向量语义污染」。第二个是生成模型，它把块当证据读——块内信息必须自足，「自 2024 年起适用于一般纳税人」这种句子一旦失去主语，命中了也答不了题。

两个需求经常冲突：检索想要小块（主题纯、命中准），生成想要大块（上下文足、读得懂）。调和手段有两个：一是标题回填，把上级标题链写进块内，小块也能带上主语；二是父子块方案（第 15 篇的对比表里叫「小块检索、大块进上下文」），检索用小块、进上下文时换成它所在的父块，两边各取所需。

### 设计的四个维度，顺序不能乱

第一是**边界**：优先沿文档自身结构切——标题层级、段落、列表、条款编号，这些是作者亲手划好的语义边界；按固定字符数硬切是最后手段，只在既无结构又无语义信号时用。第二是**大小**：两个方向的失败都得认——太大，噪声多、命中不准；太小，丢上下文，检索回来也无法回答。第三是**重叠（overlap）**：相邻块之间留一段重复内容，防止关键句正好落在切口上被切成两半。第四是**上下文回填**：把标题路径、章节编号放进块内或 metadata，让块在脱离原文后仍然「知道自己是谁家的」。

顺序为什么不能乱：边界错了，大小和 overlap 调得再好也是在一个错误的切口上做优化——就像裁缝先量错了身位，再把针脚缝得再密也没用。

### 大小没有正确值，只有区间和收口方式

经验值起点是 200～500 token、overlap 10%～20%（与第 15 篇给的口径一致，随语料和模型调整）。但这组数字的正确用法是「分层实验的起点」：每次只动一个参数、固定评测集对比。要警惕任何「业界最佳 512」式的说法——手册和 FAQ 的合理块大小可以差出数倍，文档类型不同，答案就不同。

### 四类文档，四种切法

手册、FAQ、制度文档、图文混排 PDF 这几类，都不能只按字符数切，因为它们各自的结构信号完全不同。手册标题层级深，沿标题切、块内回填标题链，长章节再二次切；FAQ 的天然单位是「一问一答」，整对成块、绝不拆开，问题那句话留在块首；制度文档的条款编号是天然边界，「第十二条」就是切口；图文混排 PDF 必须先做版面分析，识别出标题、正文、表格、图片的版面角色，再按角色分别处理——跳过这一步直接切字符，表格和图注必然被打散。具体对照见下一节表二。

## 横向对比：三张表看设计与排坑

**表一：块大小的双向失败**

| 维度 | 块太小 | 块太大 |
| --- | --- | --- |
| 向量质量 | 单块信息量低，和很多块都「有点像」，区分度差 | 多主题混块，向量被稀释，语义污染 |
| 生成可用性 | 缺主语、缺前提，命中了也读不懂 | 证据淹没在无关句里，噪声多、命中不准 |
| 成本 | 块数多，库和索引变大 | 单条证据占用更多上下文预算 |
| 典型症状 | 召回排前面的块全都不含答案 | 检索命中了正确文档，答案却是错的段落 |

**表二：文档类型 × 切块设计**

| 文档类型 | 结构信号 | 切法 | 特别注意 |
| --- | --- | --- | --- |
| 产品手册 | 标题层级深 | 沿标题边界切 + 标题链回填 | 长章节滑动窗口二次切 |
| FAQ | 一问一答 | 整对成块，问题在块首 | 千万别把问和答切到两个块 |

| 图文混排 PDF | 版面结构 | 先版面分析再按角色切 | 表格、图注整体保护 |

**表三：六个常见坑速查**

| 坑 | 线上症状 | 修法 |
| --- | --- | --- |
| 切块过碎 | 命中的块读不懂，缺主语缺前提 | 提高聚合粒度、标题回填、父子块 |
| 忽略标题层级 | 块内出现「适用于……」却不知适用谁 | 解析时保留标题链并回填进块 |
| 重叠不足 | 关键句被切口切成两半，两个块都只含半句 | overlap 提到 10%～20% 起点 |
| OCR 脏文本不清洗 | 乱码和错字入库，每次检索都可能命中 | 切块前先过清洗环节 |
| 表格内容被打散 | 行列错位，数字密集块反而易命中，答案必错 | 表格整体成块，超长按行分组并复制表头 |
| 多主题塞一块 | 向量语义污染，查哪个主题都「差一点」 | 收紧边界，一块一主题 |

## 工程实践：流程、质检和一段能直接用的代码

先把落地流程排成六步：**分类**（语料按手册 / FAQ / 制度 / 扫描件分流，各有切法）→ **解析**（保留标题层级和版面角色）→ **清洗**（OCR 乱码、页眉页脚、断行，第 15 篇说过这是全流水线 ROI 最高的环节）→ **切块**（按各类型策略执行）→ **回填**（标题链进块内，doc_id 等元数据进 metadata）→ **抽检**。前五步是流水线，第六步是质检，也是大多数团队缺的那步。

抽检怎么做，给两个能立刻落地的动作。**块级自足性抽检**：随机抽一小批块，遮住来源文档，只看块本身问两个问题——「这块讲的是什么事」「这块的信息够不够独立回答一个相关问题」；答不上的块，要么缺回填，要么切碎了。**badcase 三看**：拿到「检索命中但答案错误」的案例，先看命中的块是不是被从中间切断（overlap 问题），再看块内有没有主语（回填问题），最后看块里是不是混了别的主题（边界问题）——六坑里的四个都能用这三看定位。

再给一段结构优先的切块伪代码，重点在「元素整体保护」和「聚合优先」：

```python
# 伪代码：结构优先切块——特殊元素整体成块，普通段落先聚合再细切
def chunk_by_structure(doc, max_tokens=400, overlap_ratio=0.15):
    chunks, buffer = [], []

    def flush():
        if buffer:
            text = "\n\n".join(buffer)
            # heading_path 是解析阶段保留的标题链，回填进块内防「无主语」
            chunks.append(Chunk(text=f"{doc.heading_path}\n{text}",
                                meta=doc.meta))
            buffer.clear()

    for el in doc.elements:          # 解析产物：paragraph / table / list / code
        if el.type in ("table", "code"):
            flush()                  # 表格代码整体成块，绝不切开
            chunks.append(Chunk(text=f"{doc.heading_path}\n{el.to_text()}",
                                meta=doc.meta))
        elif n_tokens(el.text) > max_tokens:      # 单段超长：滑动窗口细切
            flush()
            for piece in slide(el.text, max_tokens,
                               overlap=int(max_tokens * overlap_ratio)):
                chunks.append(Chunk(text=f"{doc.heading_path}\n{piece}",
                                    meta=doc.meta))
        elif n_tokens("\n\n".join(buffer + [el.text])) > max_tokens:
            flush()                  # 攒满一块先落盘，再收新元素
            buffer.append(el.text)
        else:
            buffer.append(el.text)  # 段落聚合：小段攒成一块
    flush()
    return chunks
```

三个设计意图值得说：普通短段落**聚合**成块而不是一段一块，避免切块过碎；表格和代码走整体保护分支，宁可块超长也不切碎——超长表格实在太大，就按行分组、每组复制表头行，而不是拦腰剁断；每块都回填 `heading_path`，配合第 15 篇那段按标题边界切的代码理解——那篇管「沿哪里切」，本篇管「元素怎么保护、怎么聚合」，两段是互补关系。

## 追问逐条作答

### 追问一：chunk 大小有没有「正确值」？怎么定？

没有，只有起点和收口方式。起点用经验值 200～500 token，再按文档类型偏移：FAQ 可以整对成块、经常偏小头也够用；手册类按标题聚合、经常偏大头。收口一律靠评测：固定评测集，每次只动 chunk 大小一个参数，看「应命中的块是否进入召回候选」和「命中后答案是否正确」两个指标。把别人的数字当圣旨，是这题最常见的翻车点。

### 追问二：overlap 是不是越大越保险？

不是，overlap 是带代价的保险。重叠越大，重复内容入库越多：同一段证据出现在多个块里，检索候选被重复块挤占，等于变相压缩了 top_k 的多样性；库体积和索引成本也同步上涨。经验值 10%～20% 起步就够防「关键句落在切口」。还要分清 overlap 和父子块是两种互补手段：overlap 保的是「句子不被切断」，父子块保的是「上下文够读」——一个管切口，一个管视野，可以叠加，不能互替。

### 追问三：语义切块（按相似度断点切）值不值得上？

先讲机制：把相邻句子各算 embedding，相似度骤降的位置就是主题切换点，在那里下刀，块内主题最纯。代价是嵌入调用量和句子数同阶，索引成本明显上升；而且效果不稳定——对话式、闲聊式文本的相似度曲线平滑，找不到明显断点。我的排序是：有结构（标题、条款）的语料，结构边界又免费又稳定，优先用结构；只有完全没有结构的纯文本流（比如长聊天记录转写），语义切块才值得为它付嵌入成本。

### 追问四：切块大小和 embedding 模型是什么关系？

两条约束。一是硬约束：embedding 模型有输入长度上限，块超过上限会被截断，截断的内容等于没进向量——所以 chunk 上限必须落在所用模型输入上限之内，这是设计时先查的参数。二是软约束：块越长，向量越接近「全块平均」，细节主题被稀释，这正是「块太大命中不准」的模型侧解释。方向上：切块大小要在模型上限之内、在语义自足之下取平衡点。

### 追问五：怎么知道我的切块切坏了？

分层定位，别猜。第一层做块级抽检：随机抽块、遮住原文，看块能不能独立读懂，检的是「自足性」。第二层做检索归因（第 15 篇追问五的方法）：拿标注好的「问题—应命中文档」对，看应命中的块在不在召回候选里——不在，问题在索引侧，切坏了；在候选里但答案错，配合 badcase 三看定位到切口、回填还是边界。六坑中除了「脏文本」，其余五个都能被这套分层法抓出来。

### 追问六：文档更新了，切块要重来吗？

按文档粒度增量，不按库粒度重建。用稳定 doc_id 定位到变更文档，删掉它的全部旧块，重新解析、切块、嵌入、写回；content_hash 没变就跳过，避免「重新发布但内容没变」造成无效重嵌——这套增量同步的契约正是第 13 篇讲版本管理时定下的。切块策略本身升级（比如换了切法）则是另一回事：向量空间里旧块是旧策略的产物，新旧混存会让排查失去基准，通常要全量重切重嵌。

## 60 秒面试回答模板

> 切块我按「先保语义、再定大小」设计。边界优先沿文档结构走——标题、段落、条款编号是作者划好的语义边界，固定字数只做兜底；FAQ 一问一答整对成块，表格代码整体不切；块内回填上级标题，解决块脱离原文后没主语的问题；超长内容滑动窗口二切，加 10%～20% 重叠防关键句落在切口。大小用 200～500 token 起步，收口靠评测集上的召回表现，不迷信任何「最佳值」。常见坑我重点防六个：切块过碎、丢标题层级、重叠不足、OCR 脏文本不清洗、表格被打散、多主题混块污染向量——根因都是语义单元被破坏。排查时先看应命中的块在不在候选里，再看块能不能独立读懂。

## 加分项

- **报出「两个消费者」框架**：embedding 要主题单一、生成要信息自足，冲突靠标题回填或父子块调和——一句话证明你理解切块为谁服务。
- **给出可落地的质检动作**：块级自足性抽检、badcase 三看——大多数候选人只会调参数，说不出怎么验证切得好不好。
- **讲超长表格的细节处理**：按行分组、每组复制表头——愿意处理这种边角，说明真趟过图文混排 PDF 的坑。
- **把 overlap 讲成带代价的保险**：能说出重复入库会挤占候选多样性，而不是只会说「加了更安全」。

## 常见误区

- **把切块当调参题**：上来就讨论 256 还是 512，全程不提边界、回填、特殊元素——面试官立刻知道没处理过真实语料。
- **迷信「业界最佳块大小」**：拿一个数字套所有文档类型，忽略手册和 FAQ 的合理大小可以差出数倍。
- **觉得语义切块更高级就该上**：有结构的语料里，标题边界免费又稳定；为不缺结构的文本付嵌入成本，是拿 sophistication 换稳定性的倒退。
- **把切块和清洗割裂开**：OCR 脏文本切得再讲究也没用——清洗在前、切块在后，顺序不能倒。
