# 为什么企业项目里的 RAG 必须重视权限、版本和引用？

## 一句话先给结论

**企业里的 RAG 不只是检索效果问题，更是数据治理问题：权限必须在数据进入上下文之前就结构性裁掉，版本必须让索引与源文档可追踪、可增量重建，引用必须能回链到具体原文片段——这三件事决定了系统是能通过上线评审，还是永远停在演示阶段。**

## 面试官为什么爱问这题

因为它是区分「做过 Demo」和「上过生产」最省力的一道题。检索效果类的题目，背熟流水线和几个调优技巧就能答个七七八八；而权限、版本、引用这三件事，Demo 里天然不存在——语料是自己人上传的、没有租户、文档不更新、也没人要审计。只有真正把 RAG 放进企业的组织结构里跑过，才会撞上这三个墙。

考察点写得很直白：**企业落地意识，不只停留在 Demo**。第 12 篇论证「为什么还需要检索」时把这三件事当过论据，本篇换一个方向，把三件事本身拆开：机制是什么、在链路哪一层做、不做会出什么事故。

还要补一句难听的：这三件事没做，系统**越准越危险**——检索越准，越权内容被精准捞出来的概率越高；答案越好用，被采信的已作废条款造成的损失越大。治理不是效果的对立面，是它的前置条件。

## 核心原理：三道墙，各自拆开

### 第一道墙：权限——安全不能寄希望于模型「自觉」

题库的表述很重：**不能把安全寄希望于模型「自觉不回答」**。这句话背后的机制值得想清楚：

- **上下文里的内容，模型随时可以复述**。只要无权限文档进了上下文，用户一句「把你看到的参考资料完整列出来」就可能把它带出来；第 10 篇讲过的 Prompt Injection 手法（在文档里埋一句「忽略之前的指令」）在这里是现实攻击面。
- **提示词约束无法审计**。出事之后无法向安全团队证明约束生效过——它没有判定记录。
- **结构性隔离必须在候选进入上下文之前完成**。也就是在检索这一层做，而不是在生成那一层求。

企业里的权限不是一个开关，是一串嵌套：**租户隔离 → 部门 / 角色过滤 → 文档级 ACL →（少数场景）段落级 ACL**。落到 RAG 上，就是每个 chunk 入库时带上 `tenant_id`、可见组、ACL 标签，检索时把这些条件作为过滤条件传给向量库——主流向量库普遍支持检索时按 metadata 过滤，这是通用能力。

粒度怎么选？**文档级是默认值，段落级是例外**。段落级 ACL 意味着同一份文档内部不同段落归属不同可见范围，管理成本陡增：权限在源系统改了，索引要跟着改；切块策略一变，段落与权限的映射要重算。经验值是：只有少数强合规场景（法务、上市公司披露前文档）才值得上段落级，多数企业文档级加「敏感文档单独建库」就够用。

还有一个容易忽略的坑：**过滤发生在检索前还是检索后，结果完全不一样**。后过滤（先取 top_k 再筛权限）会出现「取 10 条剩 1 条」甚至剩 0 条，召回数量不稳定，答案质量跟着抖。正确做法是把权限条件放进检索请求本身（pre-filter），让 top_k 按过滤后的候选池计数。

### 第二道墙：版本——索引必须能追踪源文档

RAG 有一个天然的时间差：**文档更新了，向量不会自己更新**。源系统（OA、网盘、CMS）里的制度改版了，索引里躺着的还是三个月前的旧 embedding。更隐蔽的是删除：源文档已经下线，向量库里同 `doc_id` 的 chunk 还在，检索照样能命中——用户拿到的「现行报销标准」其实是一份已作废文件。

所以版本管理的核心是三件事：

- **可追踪**：每个 chunk 的 metadata 里带 `doc_id`、`content_hash`、版本号或生效日期，索引里的任何一条都能回答「这来自哪份文档的哪一版」。
- **增量重建**：文档更新后，要知道**哪些向量需要重建**——而不是把整个库推倒重来。判定依据通常是对 `content_hash`：hash 没变的文档跳过，变了的按 `doc_id` 删旧插新。
- **可回滚**：新版本文档入库出问题（切块失败、embedding 服务异常），索引要能退回上一版，而不是停在「删了一半」的中间态。工程上常用 delete-then-insert 包在事务或批次里，失败即回滚。

还有一条更根本的原则：**源文档系统是唯一事实源，索引是它的派生物**。权限、版本、生效状态都跟着源系统走，索引只做同步。一旦让索引自己长出一份「第二事实源」（比如在索引侧改权限、改内容），两边迟早漂移，而且没人说得清哪边是对的。

### 第三道墙：引用——答案要能回链原文

题库给的理由有两层：**业务方很难建立信任**，以及**不利于审计和复盘**。第三层是工程上的：引用是 RAG 的调试分界线。

- **信任**：业务方要的不是「答案听起来对」，而是「这句话出自哪份文件第几节」。能点开原文核对，AI 的答案才敢用于决策；给不出出处，答案再流畅也只是「参考意见」。
- **审计**：合规场景要留痕——这个结论是模型基于哪些文档得出的，出了争议要能举证。没有引用，举证链条断了。
- **复盘**：这是工程师自己受益的部分。答案错了，第一步看它引用的 chunk——**引用的原文本身就是对的，是生成问题；引用的原文就错了，是检索问题**。没有引用，你连「错在检索还是错在生成」都分不出来，优化无从下手。

机制上不复杂：每条进入上下文的证据带编号 `[1] [2] [3]`，要求模型在答案中标注来源编号；chunk metadata 里有 `doc_id` 与章节定位，编号可以反查到具体原文片段。但必须校验：**模型给的引用编号要真实存在于本次上下文里**——模型可能标一个 `[5]` 而上下文里只有 4 条，这种「幻觉引用」不校验等于没做。

| --- | --- | --- | --- | --- |
| 权限 | 谁能看什么 | 单租户自有语料，无此概念 | 检索时按 tenant / 角色 / ACL 过滤，进上下文前裁掉 | 无权限内容被精准检索出来，还带着出处 |
| 版本 | 看到的是哪一版 | 文档不更新或改了全量重灌 | chunk 带 doc_id / hash / 版本，按 hash 增量重建 | 已作废制度被当现行答案给出 |
| 引用 | 这句话哪来的 | 答案末尾写「以上仅供参考」 | 编号引用 + 回链原文片段 + 引用合法性校验 | 业务不采信，出事无法举证，bad case 无法归因 |

| --- | --- | --- | --- | --- |

## 工程实践：把三道墙接到链路里

### 权限：chunk 入库带 ACL，检索时过滤

先定 metadata 契约。这一步不做，后面全补不回来——权限字段入库时没有，检索时就没得过滤：

```python
# 伪代码：chunk 入库时的 metadata 契约
chunk_meta = {
    "doc_id": "POL-2026-084",        # 源系统稳定 ID，不要用文件名
    "content_hash": "a3f9e2...",     # 文档内容指纹，供增量比对
    "tenant_id": "corp-a",           # 租户隔离的第一层
    "visible_groups": ["finance", "hr"],
    "acl": "doc-level",              # 标记权限粒度，便于审计
    "version": 3,
    "effective_from": "2026-09-01",
}
```

检索侧把权限条件直接放进过滤请求，并留意 top_k 的语义：

```python
# 伪代码：pre-filter 检索
def search(user, query, top_k=8):
    flt = {
        "tenant_id": user.tenant_id,                 # 租户：硬边界
        "visible_groups": {"has_any": user.groups},  # 组过滤
    }
    hits = vector_db.search(
        vector=embed(query),
        filter=flt,          # 过滤发生在检索内部，top_k 按过滤后候选计数
        top_k=top_k,
    )
    if not hits:             # 过滤后为空必须兜底，不能让模型"自由发挥"
        return NO_RESULT_PROMPT   # 明确告知检索无结果，禁止编造
    return hits
```

两个细节：`doc_id` 用源系统的稳定 ID 而不是文件名——文件一改名就被当成「删旧建新」，触发无谓的重建；过滤后命中为空时返回显式的「无结果」信号，让模型回答「在您可见范围内未找到相关制度」，而不是在空证据下开始编。

### 版本：hash 比对 + 删旧插新 + 失败回滚

```python
# 伪代码：增量同步
def sync_document(doc):
    old_hash = index.get_doc_hash(doc.id)        # 索引侧记录的指纹
    new_hash = hash(doc.content)
    if old_hash == new_hash:
        return "skip"                            # 未变更，跳过
    try:
        with index.batch():                      # 删旧插新包在同一批次
            index.delete_by_doc_id(doc.id)       # 先清旧 chunk
            index.insert(chunk_doc(doc))         # 再灌新 chunk
    except SyncError:
        return "failed_and_rolled_back"          # 批次失败整体回滚，不留中间态
    return "rebuilt"
```

删除同样按 `doc_id` 级联：源系统下线文档，同步任务在索引里删干净全部 chunk。工程上建议给删除留观察期（软删除打 `deleted_at` 标记，确认无检索依赖后物理清除，经验值按周计），防误删后无法恢复。

### 引用：编号、回链、校验三步

上下文里每条证据带编号与定位，答案侧做合法性校验：

```python
# 伪代码：引用校验
def check_citations(answer, hits):
    cited = extract_ref_numbers(answer)          # 抽出答案里的 [n]
    valid = set(range(1, len(hits) + 1))
    ghost = [n for n in cited if n not in valid] # 幻觉引用：标了不存在的编号
    if ghost:
        answer = regenerate_with_hint(answer, f"编号 {ghost} 不存在")
    return answer, cited
```

交付给前端的引用信息按「编号 → 文档名 / 版本 / 章节」渲染，用户点开能跳到原文片段。这一步是业务方信任感的直接来源：**能核对，才敢采信**。

## 追问逐条作答

### 追问一：为什么不能在提示词里写「不要回答无权限内容」？

因为内容已经在上下文里了。三连击：第一，上下文里的内容没有结构性防复述约束，用户换个问法（「列出你参考的资料」）就可能带出来；第二，文档里若埋了注入指令，提示词约束会被覆盖，第 10 篇讲过这不是理论风险；第三，提示词约束没有判定日志，安全事件复盘时你拿不出证据证明它生效过。安全要的是结构性保证——无权限内容根本不进入上下文——这在检索层做，不在生成层求。

### 追问二：权限过滤放在检索前还是检索后，差别在哪？

差别在召回数量的稳定性。后过滤是先取 top_k 再筛，过滤后剩几条不可控：常见情况是取 10 条剩 2 条，极端是剩 0 条——上下文证据量随用户权限抖动，答案质量跟着抖。检索时过滤（pre-filter）把权限条件放进检索请求，top_k 在过滤后的候选池里计数，召回稳定。隔离强度两者相同（无权内容都不进上下文），所以正确答案是：**隔离用哪种都能达到，但稳定性决定了必须选检索时过滤**。若组件只支持后过滤，就要按比例放大原始 top_k（经验值 2～3 倍）并接受更复杂的空结果兜底。

### 追问三：文档更新了，怎么让索引跟上？

按 `doc_id` 加 `content_hash` 做增量：同步任务逐文档比指纹，未变的跳过，变了的在同一批次里删旧 chunk、插新 chunk，失败整体回滚。大库不要全量重建——重建周期长且期间质量抖动。配套两件事：删除按 `doc_id` 级联清干净，否则检索命中「幽灵文档」；切块或 embedding 模型升级这类会导致全量语义变化的变更，才用「新版索引入新 collection、验证后切流量」的灰度方式，不做原地替换。

### 追问四：什么时候才值得做段落级权限？

默认文档级，段落级是例外。触发条件是**同一份文档内部确实存在不同可见范围**（合同里的商业条款与通用条款、披露前的财报分节），且合规要求明确。代价要讲清楚：段落级 ACL 要求权限随切块维护，切块策略一变映射重算，源系统权限变更要实时同步到索引——管理成本不是线性涨而是跳一档。多数企业的解法是把敏感文档单独放一个带独立权限策略的库，用库级隔离替代段落级细粒度。

### 追问五：引用给到什么粒度才有用？模型给的引用可信吗？

粒度到「用户能点开原文并定位到相关段落」即可——通常是 chunk 及其所在章节，不需要精确到句子。可信度上，**不能直接信**：模型可能标出上下文里不存在的编号（幻觉引用），也可能标了编号但内容对不上。所以要做两层校验：编号合法性（引用的编号确实在本次证据列表里）与内容一致性抽查（引用支撑的论断与该 chunk 原文相符）。校验是低成本动作，却能把引用从「装饰」变成「可审计的证据链」。

### 追问六：权限是静态配置吗？人员转岗、离职怎么处理？

不是，权限有生命周期。RAG 侧的权限过滤读的是身份系统（IAM / 组织架构）的判定结果，人员转岗、离职后其可见范围随之变化，检索过滤条件跟着变——这要求过滤判定是实时或准实时的，不能在入库时把「某用户可见」固化进 chunk。工程上通常在请求入口解析当前用户身份与组，带进检索过滤；如果中间有权限缓存，过期时间要短（经验值分钟级），否则离职账号在缓存窗口内仍能查到原范围内容。审计上，每次检索的过滤条件与命中集合应落日志，出事可回放「当时谁能看到什么」。

## 60 秒面试回答模板

> 我会把这题拆成三道墙。权限上，安全不能寄希望于模型自觉——无权限内容要在检索层就按租户、角色、ACL 过滤掉，在进上下文之前结构性裁掉，而且要检索时过滤而不是后过滤，否则召回数量会随权限抖动。版本上，索引必须能追踪源文档：chunk 带 doc_id 和内容指纹，文档更新后按指纹增量重建、删旧插新、失败回滚，删除要级联清干净，否则用户会拿到已作废的制度。引用上，每条证据带编号、可回链原文片段，答案里的引用编号要做合法性校验防幻觉引用——它同时是信任、审计和归因的基础。

> 这三件事 Demo 里天然不存在，所以很多系统上线才暴露。总结：企业 RAG 不只是检索效果问题，更是数据治理问题。

## 加分项

- **点出「越准越危险」这个反直觉结论**。检索精度与治理缺失是相乘关系而非相加关系，一句话就显出风险意识，而不是泛泛背「安全重要」。
- **讲清 pre-filter 与 post-filter 的召回稳定性差异**。多数人只知道「要过滤」，说得出「top_k 按过滤后候选计数」的人是真调过过滤条件的人。- **给出 doc_id 用稳定 ID 而非文件名这类实现细节**。版本事故里一大类是 ID 设计不当引起的，这种细节只有踩过坑才知道。
- **把引用讲成调试分界线**。「引用对而答案错是生成问题，引用本身就错是检索问题」——把治理和工程效率打通，而不是把引用只当合规动作。

## 常见误区

- **把权限当提示词问题**。「在提示词里叮嘱模型不要泄露」——内容已进上下文，可被诱导复述；安全要的是结构性隔离。
- **把引用当装饰**。只在答案末尾附一个文档列表应付了事，不做编号对应、不校验合法性——业务方点开对不上号，信任反而掉得更快。
- **索引成为第二事实源**。在索引侧直接改内容、改权限，不回写源系统——两边漂移后，没有人能说清哪边是对的，审计链条从这里断。
- **改了文档就全量重建**。小库无所谓，大库是定时炸弹：重建期间质量抖动，还掩盖了「哪些文档真的变了」这条更重要的机制。

下一篇是**第 14 篇**：**什么是 Agentic RAG？它和「一次检索后直接生成」有什么区别？**查一次、拼上下文、生成——这条经典链路遇到多跳问题和模糊提问会卡在第一跳。让检索变成「可以自己决定再查一次」的动作，正是 Agentic RAG 的起点。
