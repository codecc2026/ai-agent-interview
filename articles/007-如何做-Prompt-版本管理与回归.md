# 如何做 Prompt 版本管理与回归？

## 一句话先给结论

**把 Prompt 当代码资产管：模板、运行参数、评测集、发布信息四样东西同时入版本库，每次改动先过固定回归集，再灰度、抽样人工复核，并始终留一个能一键切回去的上一版。**

面试官把这题丢过来，不是想听"Prompt 很重要"，而是想看你是否经历过那次事故：有人改了三个字，客服开始胡说八道，全员两天才定位到原因。这类问题没法靠背答案通过，只能靠你真的搭过那条链路——要素很朴素：**改了什么、跟谁比、怎么判好坏、退到哪去**。

先划清边界：**第 6 篇说的是怎么组织 Prompt**（System Message 和 User Message 怎么分工），本篇接着往后走一步——组织好之后你必然要改它，**改完之后怎么证明它没变坏**。另外本篇只讲 Prompt 的版本管理，不讨论模型本身的版本管理：两者都要记版本号，但变更成本和回滚方式完全不同。

## 核心原理：改一行 Prompt，牵动的是四样东西

Prompt 一旦进入生产环境，就不能再当成"临时改改的字符串"，而要当成配置资产或代码资产。落到实处其实是：**一次改动会同时牵动四样东西，只管其中一样等于没管。**

**第一样是 Prompt 模板本身**：System 消息、User 模板、few-shot 示例、输出格式要求。它最容易被管住，因为大多数团队的第一反应就是把它挪进代码仓库。

**第二样是运行参数**：模型名、模型版本、temperature、top_p、max_tokens。这一样最容易被漏掉。模板一字没改、效果却变了，八成是模型快照换了或者采样参数被谁顺手调了一下。

**第三样是评测集**：固定 golden questions、典型 badcase、失败样例。没有它，两次改动谁更好只能靠主观感觉。评测集自己也要版本化——否则有人偷偷改期望答案去凑分数，回归就失去意义了。

**第四样是发布信息**：模板版本号、发布时间、负责人、灰度范围、回滚版本。它决定出事故之后多久能恢复、能不能说清影响面。

还有一条常被忽略的认知：**换底层模型之后，旧 Prompt 不一定还能保持原效果。** 同一段指令在不同模型上的服从程度不一样，few-shot 的引导力度也不一样。所以回归的对象从来不是孤立的"这段 Prompt 对不对"，而是**"Prompt 和当前模型组合起来还稳不稳"**。模板 hash、模型版本、关键参数必须三件套一起记，缺一个就容易出现"没改 Prompt 效果却变了"这种悬案。

## 四样资产的版本化清单

| 资产 | 包含什么 | 不管会怎样 | 通常管在哪 |
| --- | --- | --- | --- |
| Prompt 模板 | System、User 模板、few-shot 示例、输出格式要求 | 谁改了、改成什么都查不到，回退只能靠记忆 | 代码仓库里的模板文件，或统一的配置中心 |
| 运行参数 | 模型名、模型版本、temperature、top_p、max_tokens | "没改 Prompt 效果却变了"，因为换的是模型快照或采样参数 | 与模板同一条版本记录，或同一份配置文件的并列字段 |
| 评测集 | 固定 golden questions、典型 badcase、失败样例 | 只能靠主观手感判断，两次改动谁好说不清 | 独立目录，和模板一起走评审，改期望答案也要被审 |
| 发布信息 | 模板版本号、发布时间、负责人、灰度范围、回滚版本 | 出事时不知道退到哪一版，也不知道影响多大 | 每次发布追加一条记录，最好由流水线自动生成 |

要点是：**四样东西最好用同一个版本号串起来**，排查时不用做四次对齐。

## 离线回归、灰度、线上 A/B 是三件事

很多人把这三个词当同义词用，面试官一听就知道没真正做过。它们回答的是不同阶段的不同问题：

| 手段 | 回答什么问题 | 主要成本 | 通过标准 | 常见错误 |
| --- | --- | --- | --- | --- |
| 离线回归集 | 这次改动有没有把已修好的 badcase 又一次弄坏 | 一次性建设 + 每次跑批的 token 与时间 | 关键用例不退步，总分不低于上一版 | 用例太少或太同质，分数涨了线上没感觉 |
| 灰度发布 | 小流量真实请求会不会出现未知故障 | 需要版本开关与分流能力 | 观察窗内错误率、解析失败率、人工复核通过率不恶化 | 比例太小、时间太短，长尾没覆盖就全量 |
| 线上 A/B | 两版在真实流量上谁的业务指标更好 | 最高，需要样本量与统计口径 | 目标指标出现稳定差异再推广 | 样本量不足就下结论；同时改多处导致无法归因 |

顺带回答一个高频误解：**离线评测集涨分不等于线上会变好**。常见原因有三个——评测集分布和线上真实请求不一致；用例太少被个别样本带偏；优化错了指标，例如只看答案质量、没管解析失败率，结果内容变好但下游天天报错。所以回归跑完之后，灰度不能省。

## 工程实践：一条能跑起来的流水线

下面给一套可以直接照抄的最小实现，分五步。

### 第一步：模板和参数放在同一份文件里

把 System、User 模板、few-shot 示例、输出格式要求和采样参数写进同一个配置，"只改了半套"的情况就会少一半：

```yaml
# prompts/refund_assistant/v1.4.0.yaml —— 模型标识换成你们自己的
name: refund_assistant
version: v1.4.0
prev_version: v1.3.2          # 写死回滚目标，事故时不用现翻记录
owner: zhangsan
template: |
  你是电商客服助手，只依据【资料】回答，不得使用外部知识。
  【资料】
  {context}
  【用户问题】
  {question}
few_shot:
  - user: "七天无理由退货从哪天开始算？"
    assistant: "{\"answer\": \"从签收次日开始算，共七天。\", \"cited\": [\"policy.md#sec3\"]}"
output_format: "输出 JSON：answer 为字符串，cited 为字符串数组"
params:
  model: "<model-id>"         # 换成你们实际使用的模型标识
  model_version: "<snapshot>" # 模型快照标识，必须与模板同时记录
  temperature: 0.2
  top_p: 0.9
  max_tokens: 1024
regression_set: evals/refund_assistant/golden.yaml
```

### 第二步：版本号别用时间戳和人名

版本号的作用是让人一眼看出"这次改动风险有多大"。一个够用的约定如下（patch 以上都要跑回归，major 还要知会下游）：

```
v<major>.<minor>.<patch>

major：改输出契约（字段名、字段类型、必填项）——下游必须同步改造
minor：增删规则、增删 few-shot 示例、更换底层模型
patch：措辞、错别字、标点，不改变语义

版本号之外再补两个字段，缺一不可：
template_hash = sha256(template)[:12]   # 防止"版本号没动但内容被改过"
model_version = 模型快照标识             # 区分是 Prompt 变了还是模型变了
```

### 第三步：golden set 每条自带判分方式

```yaml
# evals/refund_assistant/golden.yaml —— 示例：每条用例写清期望与判分方式
- id: c001
  tag: [核心规则, 引用]
  input: {question: "七天无理由退货从哪天开始算？", context: "policy.md#sec3"}
  expect: {answer_contains: ["签收次日"], cited_contains: ["policy.md#sec3"]}
  scoring: keyword_and_citation
  source: 业务方验收用例
- id: c002
  tag: [边界, 拒答]
  input: {question: "我去年买的鞋还能退吗？", context: "policy.md#sec3"}
  expect: {answer_contains: ["超过七天"]}
  scoring: keyword_only
  source: 线上 badcase 2026-09-12
```

规模上的经验值：**先用 30～100 条覆盖主要分支和典型 badcase**，足够分辨两次改动谁更好。重点是每条都带 `tag`，某个子集掉分时能立刻定位到哪类能力退化了。

### 第四步：一条命令跑完回归

下面是回归评分的骨架，几个工具函数给了示意实现，接上你们自己的模型调用就能跑：

```python
import hashlib, json, statistics
from pathlib import Path
import yaml


def load_yaml(p):
    return yaml.safe_load(Path(p).read_text(encoding="utf-8"))


def render(template, inputs):
    return template.format(**inputs)        # 把 {context} / {question} 占位符填上


def call_llm(messages, **params):
    raise NotImplementedError("换成你们自己的模型调用封装，返回一段文本")


def parse_output(raw):
    try:
        return json.loads(raw)
    except json.JSONDecodeError:
        return {"answer": raw, "cited": [], "__parse_error__": True}


def run_case(case, template, params):
    messages = [{"role": "system", "content": render(template, case["input"])}]
    return parse_output(call_llm(messages, **params))


def score_case(case, out):
    exp = case["expect"]
    answer = out.get("answer", "")
    cited = set(out.get("cited") or [])
    hit_kw = all(k in answer for k in exp.get("answer_contains", []))
    if case["scoring"] == "keyword_and_citation":
        hit_cite = all(any(c in s for s in cited) for c in exp.get("cited_contains", []))
        return 1.0 if (hit_kw and hit_cite) else 0.0
    return 1.0 if hit_kw else 0.0


def regression(version_dir, baseline=None):
    """对某个版本目录下的 模板 + 参数 + 评测集 跑一次回归"""
    cfg = load_yaml(Path(version_dir) / "prompt.yaml")
    golden = load_yaml(Path(version_dir) / "golden.yaml")
    results = []
    for case in golden:
        out = run_case(case, cfg["template"], cfg["params"])
        results.append({"id": case["id"], "tag": case.get("tag", []),
                        "score": score_case(case, out),
                        "parse_error": out.get("__parse_error__", False)})

    base_map = {c["id"]: c["score"] for c in (baseline or {}).get("cases", [])}
    regressed = [r["id"] for r in results if r["score"] < base_map.get(r["id"], 1.0)]
    return {
        "version": cfg["version"],
        "prev_version": cfg.get("prev_version"),
        "template_hash": hashlib.sha256(cfg["template"].encode()).hexdigest()[:12],
        "model": "%s@%s" % (cfg["params"]["model"], cfg["params"]["model_version"]),
        "mean_score": round(statistics.fmean([r["score"] for r in results]), 4),
        "parse_fail_rate": round(sum(r["parse_error"] for r in results) / len(results), 4),
        "regressed_ids": regressed,
        "cases": results,
    }
```

返回值里有两个字段值得单独盯：`parse_fail_rate` 比平均分更敏感，下游报错往往先从这里冒出来；`regressed_ids`（相对上一版退步的用例）比总分更重要——**总分涨了但某个老 badcase 又坏回去，这种改动不能上线**。

### 第五步：发布信息、灰度与回滚

- **发布记录追加而不覆盖**：版本号、发布时间、负责人、灰度范围、回滚目标版本，最好由流水线自动生成，人工补的字段早晚会漏。
- **高风险链路保留快速回滚能力**：回滚的形态应该是"切一次版本指针"，而不是"重新发一次版"，后者在半夜基本做不到。
- **灰度配套抽样人工复核**：先用小比例流量（经验值 1%～5%，按你们的量级调整）观察一段时间，人工复核结果也不恶化再放量。

## 线上波动怎么归因

前面的东西准备好之后，归因就是一个查表过程，原则只有一条：**一次只改一处，用同一份评测集复测。**

| 你看到的现象 | 先怀疑谁 | 怎么验证 |
| --- | --- | --- |
| 模板 hash 没变，效果掉了 | 模型快照、采样参数、索引、下游解析 | 把 model_version 与 temperature 锁回上一版，重跑 golden set |
| 只有改到的那类用例变差 | 本次 Prompt 改动 | diff 两版模板，逐条回退，跑对应 tag 的子集 |
| 只有依赖外部知识的用例变差 | 索引或文档更新、召回链路 | 单独测召回命中率，先看资料有没有被送到模型眼前 |
| 各类用例一起变差，还伴随报错上升 | 上游接口变更、超时、限流 | 先看 trace 与错误码分布，排除工程故障再谈 Prompt |
| 输出格式崩了但内容大致对 | 输出约束参数或下游 schema 变更 | 直接统计解析失败率，比看平均分准 |

## 面试官的追问，你该怎么接

### 追问一：golden set 应该怎么构建？

讲清四件事：**来源、结构、规模、维护节奏**。

来源上至少四条路子：线上 badcase（最有价值，一条都不能丢）、业务方给的验收用例（决定上线能不能通过）、边界与拒答类（宁多勿少）、随机抽样的正常请求（防止只为坏样例优化、把正常场景改坏）。结构上每条必须有输入、期望输出、**判分方式**——不同人对"答得对"的理解不一样，不写判分方式等于没写。规模参考前面的经验值，30～100 条起步即可。维护上，每次线上出事故就把那条样例补进集里。

判分方式的选择直接决定这套评测能不能自动化：

| 判分方式 | 适用题型 | 优点 | 坑 |
| --- | --- | --- | --- |
| 精确匹配 | 分类、枚举、单一字段抽取 | 最快最稳，完全可复算 | 表达稍变就误判，不适合长文本 |
| 关键词 / 正则 | 答案必须包含某个事实点 | 实现简单，抗表达变化 | 关键词命中但整句可能仍是错的 |
| 结构化字段比对 | 输出 JSON 的多字段抽取 | 能定位到具体哪个字段退步 | 依赖解析成功率，格式崩时全判 0 |
| 模型打分 | 主观质量、语气、完整性 | 覆盖面广，能评开放式回答 | 需要人工校准，否则容易自欺欺人 |
| 人工复核 | 高风险链路、日常抽检 | 唯一可信的金标准 | 慢且贵，不能作为每次回归的主手段 |

### 追问二：如果线上效果波动，你怎么判断是 Prompt 问题还是模型版本问题？

关键动作是**锁变量重跑**，而不是盯着日志猜。三步走：

1. **先确认到底有没有变更**：查发布记录里的 template_hash、model_version、temperature 三件套。很多时候"没人改 Prompt"指的是没人改模板文件，参数早被谁动过了。
2. **只回退一个变量再跑同一份 golden set**：只把模板退回上一版、效果恢复，是 Prompt 改动的问题；只把模型锁回旧快照、效果恢复，是模型版本的问题；两个都得退才恢复，说明是新旧 Prompt 与新模型的兼容性问题，换底层模型时尤其常见。
3. **分层看错误**：只有某几个 tag 的用例掉了，通常指向 Prompt；全类型一起掉且报错率上升，先去查工程侧故障。

没记版本号和参数，第一步就走不下去——这也是发布信息必须版本化的原因。

### 追问三：Prompt、模型、索引三者一起变更时，如何设计回滚策略？

核心原则两条：**三者各自要有独立的开关，且必须知道上一组"已验证可用"的组合是什么。**

做法是给每个维度保留独立的版本指针（模板版本号、模型快照标识、索引版本号），发布记录里存三者的组合，而不是某条单独的变更单。回滚时按危险程度排序——模板和索引通常能秒级切回，模型往往受供应方约束、切换成本最高，所以**换模型前最好先在离线把另两个维度锁死，单独验证它**。

上线顺序上更稳的做法是逐个放行：每次只放一个维度的变更。真出事故时，回滚目标要写成"回到某个三元组"，而不是笼统的"回上一版"。另外评测集里要有专门覆盖"知识类"的子集，这样索引变更和 Prompt 变更各自退步时能被区分开。

### 追问四：Prompt 版本号应该怎么定？（自补）

用语义化版本号 `v<major>.<minor>.<patch>`，并且**版本号之外一定再记一个模板内容 hash**。原因是版本号靠人遵守，hash 靠机器算，只有 hash 能挡住"版本号没动、内容被顺手改了两个字"这种情况。

判定标准按"影响面"来划：改输出契约（字段名、类型、必填项）是 major，下游必须跟着改；增删规则、增删 few-shot 示例、换底层模型是 minor；措辞和错别字是 patch。容易忘的是另一条：**major 和 minor 都要重跑全量回归并留人工复核记录**，patch 至少跑一遍。

### 追问五：没有评测平台的小团队，最小可行做法是什么？（自补）

不要用"我们没人做平台"当理由，这套东西的最小形态不需要平台：

- 一个目录放模板 YAML，一个目录放 golden set YAML，和业务代码走同一个仓库、同一套评审。
- 一条回归脚本（就是前面那段）接到 CI 里，改模板自动跑，结果贴在合并请求上。
- 一个 changelog，每次发布追加一行：版本、时间、负责人、灰度范围、回滚版本。
- 一个灰度开关，最小实现甚至只是配置里的一个百分比字段。

做到这四条，就比"在后台直接改提示词然后祈祷"强一大截了。平台解决的是规模和协作效率，不是有没有的问题。

### 追问六：用模型当裁判打分，会不会自己骗自己？（自补）

会，而且这是现在最容易被忽视的坑。常见的自欺有三种：裁判模型与被评模型同源，天然偏好同一种说法；评分标准太抽象，尺度每次都不一样；裁判自己也会漏读关键信息，把错的判成对。

缓解办法都是经验做法：**定期和人工标注对齐**（抽样几十条算一致率，上不去就别信这个分数）；**给具体的评分维度**（包含哪个事实点、引用是否正确、有没有无依据内容），而不是一句"请打 1 到 5 分"；**关键结论尽量二值化**，连续分数只适合看趋势。

一句话收尾：**模型打分适合做"面"，关键的几个点永远要靠人工兜底。**

## 60 秒面试回答模板

> 生产上的 Prompt 不能当字符串改，我会把它当配置项，管四样东西：模板本身、运行参数里的模型和 temperature、评测集、发布信息，用同一个版本号串起来，另外记模板 hash 防止内容被偷改。

> 改一次的流程是：先在固定的 golden set 上跑回归，集里有线上 badcase 和业务方验收用例，每条写清判分方式；老 badcase 没退步、总分不降，再进灰度加抽样人工复核，盯错误率和解析失败率。

> 线上波动时，我先查发布记录的三件套，把模板 hash、模型版本、采样参数分别回退、逐个重跑，一次只动一个变量，就能区分是 Prompt 还是模型的问题。三者一起变的话，回滚目标要写成"回到某个已验证可用的组合"。

## 加分项

- **说出"回归的对象是 Prompt 与模型的组合，不是孤立的 Prompt"**。换模型后旧 Prompt 未必还有效，能讲到这点，基本说明你踩过坑。
- **提一句"评测集也要评审"**。改期望答案比改模型更容易刷分，没人审的评测集会慢慢失去意义。
- **主动区分离线回归、灰度、线上 A/B**。多数候选人只会含糊地说"我们做了测试"。
- **提到解析失败率这类工程指标**。只看平均分的人，通常没被下游报警叫醒过。

## 常见误区

- **把 Prompt 版本管理和模型版本管理混为一谈**。前者改一行字几秒生效，后者往往受供应方约束、回滚代价高，发布节奏完全不同。
- **只给模板打版本号**。参数、评测集、发布信息不入库，等于把一半的变更原因丢进黑盒。
- **离线跑分涨了就直接全量**。离线集是采样出来的，和线上分布通常不一致，跳过灰度就是把风险一次性放出去。
- **评测集只收坏样例**。全是 badcase 会让 Prompt 越改越保守，正常请求悄悄退化却没人发现。
